Exam Topics Beyond the Slides

Past papers on recovery also ask about buffer policies (steal and force), recoverable and cascadeless schedules, and the Silberschatz/ARIES style of recovery. None of these is on the Lec 05–06 slides, but each connects directly to them. Each topic is explained briefly, then the questions are answered in full.

1. Steal and force: the buffer policies behind the three logging methods

The three logging methods differ in when the buffer manager may write a changed block to disk. Two yes/no questions describe this, and other textbooks (Silberschatz, Ramakrishnan) name the answers:

Steal
The buffer manager may write a block changed by an uncommitted transaction to disk (for example to free (“steal”) its buffer frame for another page). No-steal: uncommitted changes never reach disk.
Force
When a transaction commits, all blocks it changed are forced to disk before the commit completes. No-force: committed changes may stay in memory and be written later.

Each choice decides what recovery must be able to do:

  • Steal means uncommitted data can be on disk after a crash, so recovery needs UNDO (old values in the log). No-steal: never any undo.
  • No-force means committed data can be missing from disk after a crash, so recovery needs REDO (new values in the log). Force: never any redo.

2. Recoverable and cascadeless schedules

Logging handles one transaction's own changes. When transactions run concurrently, one transaction can read a value written by another that has not committed yet (a dirty read). That creates a dependency that recovery cannot fix by itself.

Schedule
An interleaving of the actions of several transactions; ri(X) and wi(X) are a read and a write of X by Ti, and ci is Ti's commit.
Tj reads from Ti
Tj reads X after Ti wrote it, with no other write of X in between.
Recoverable schedule
Whenever Tj reads from Ti, Ti commits before Tj commits. Then a committed transaction never depends on one that might still be undone.
Cascading rollback
Aborting Ti forces aborting every transaction that read from it, and every transaction that read from those, and so on.
Cascadeless (avoids cascading rollback)
Every transaction reads only values written by transactions that have already committed. Cascadeless schedules are recoverable.

Why does this matter for crash recovery? Recovery undoes every transaction without a COMMIT. If a committed transaction read a value from one of them, its committed result is built on a value that recovery erases, and no log record can fix that. This is the “strange behaviour” the textbook mentions for undo/redo recovery (Lecture 06, Chapter 3), and it is why the DBMS keeps schedules recoverable, usually by holding write locks until commit (textbook §19.1).

3. Silberschatz/ARIES-style recovery, in one paragraph

Some answers in the question banks use the other standard textbook (Silberschatz) or the ARIES algorithm. There, recovery has a redo phase that “repeats history”: starting from the last checkpoint it replays every update record forward, committed or not, and builds the list of incomplete transactions. Then an undo phase rolls back the incomplete transactions backward, writing a compensation log record (CLR) for each undo so a crash during recovery does not undo anything twice; each page stores the log sequence number (LSN) of the last change applied to it, so redo can skip changes already on the page. The final database state is the same as with this course's undo/redo recovery; only the intermediate writes differ. For this course, use the methods of Lec 05–06, and recognise the other style when a question's wording (“redo phase and undo phase”, <T0 start>) suggests it.

In this course's terms: undo logging is steal + force, redo logging is no-steal + no-force, undo/redo logging is steal + no-force.

Answer: under the force policy the redo phase has nothing to do: every committed transaction's changes were already on disk when it committed, so a crash can never lose a committed update. (Undo logging, which forces data before the COMMIT record by rule U2, has no redo step at all.)

BUET QBank · CSE 215 | L-2/T-1 | 2023–24 · 10 marks

Consider the following schedule where ci represents a commit action for transaction Ti:

w1(A); r2(A); w2(A); w2(B); r3(B); w3(C); c3; c2; c1

(a) Does the given schedule preserve database consistency in case of system failure? Justify your answer. (b) Rearrange the commit statements so that the schedule preserves database consistency in case of system failure. (c) Rearrange the commit statements so that the schedule avoids cascading rollback.

Show worked answer

Reads-from relations: r2(A) follows w1(A), so T2 reads from T1. r3(B) follows w2(B), so T3 reads from T2.

(a) No. The schedule is not recoverable: T3 commits (c3) before T2, from which it read, and T2 commits before T1. Suppose the system crashes right after c3. Recovery sees COMMIT records only for T3, so it undoes T1 and T2: A and B get their old values. But T3 is committed, and the value of C it wrote was computed from B as written by T2, which no longer exists. The database is left in a state that no execution of complete transactions produces, and recovery cannot fix it because T3's commit is permanent. The same happens if T1 or T2 aborts after c3.

(b) Make it recoverable: each transaction commits after the ones it read from, i.e. c1 before c2 before c3:

w1(A); r2(A); w2(A); w2(B); r3(B); w3(C); c1; c2; c3

Now a crash at any point leaves a consistent result: whoever has committed only depends on committed transactions. (If T1 aborted, T2 and T3 would still have to be rolled back: a cascading rollback.)

(c) Avoid cascading rollback: every read must see only committed data, so c1 must come before r2(A) and c2 before r3(B). T1's only action is w1(A) and T2's last action is w2(B), so:

w1(A); c1; r2(A); w2(A); w2(B); c2; r3(B); w3(C); c3

This schedule is cascadeless (and therefore also recoverable). It is in fact serial: T1, T2, T3. (The CSE215 bank's answers to all three parts agree with these.)

Summary: steal → undo needed, no-force → redo needed; undo logging = steal/force, redo logging = no-steal/no-force, undo/redo = steal/no-force; under force there is never anything to redo. A schedule is recoverable if each transaction commits after those it read from, and cascadeless if it reads only committed data. ARIES-style recovery repeats all history in its redo phase and then undoes incomplete transactions, reaching the same final state.
