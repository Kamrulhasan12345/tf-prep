Redo Logging and Recovery

Undo logging forces every change to disk before a transaction may commit. Redo logging turns this around: it logs new values, commits first, and writes data later. This chapter gives the redo rule, the slide's step table, the forward-scanning recovery algorithm, the slide's three crash points, and two exam questions that compare undo and redo logging.

1. What is wrong with undo logging? (slide 2)

Under rule U2, a transaction cannot commit until all its changed elements have been written to disk. That costs disk I/Os at the worst moment, at every commit. It is often more efficient to keep updated blocks in memory for a while:

  • other transactions may be updating the same blocks,
  • so it is better to write a block once, after several transactions have changed it,
  • instead of writing it again for each transaction's commit.

The solution is redo logging, which lets changes stay in memory after the commit, as long as the log can recreate them.

2. The redo rules (slide 3)

<T, X, v> in a redo log
Transaction T wrote the new value v into element X. The old value is not recorded.
R1 (slide)
Before any update of X reaches disk, the log record <T, X, v> must be on disk.
R2 (slide)
The COMMIT log record must be written to disk (i) before any updated X is written to disk and (ii) after all <T, X, v> records are written to disk.

The textbook states this as a single rule, which it calls R1 (the write-ahead logging rule for redo): before modifying any database element X on disk, all log records pertaining to this modification of X, including both the update record <T,X,v> and the <COMMIT T> record, must appear on disk. The slide's R1 + R2 say the same thing. (Part (ii) of R2 is automatic: the COMMIT record is created only after the transaction's last write, so it comes after all update records in the log, and the log reaches disk in order.) Either way, the order for one transaction is:

(1) update records <T,X,v> → (2) <COMMIT T> → (3) the changed elements X

Compare undo logging: there the data went to disk before the COMMIT record, here after. The three differences, from the textbook:

Undo loggingRedo logging
Update record holdsold valuenew value
Data vs COMMIT on diskdata first, then COMMITCOMMIT first, then data
Recoveryundo incomplete transactions, ignore committed onesredo committed transactions, ignore incomplete ones
Scan directionbackwardforward

As the slide notes: the update records <T,A,16> and <T,B,16> carry the new values and come before <COMMIT T>; and the update records and the COMMIT are flushed to disk (step 9) before A and B are. Steps 10 and 11 could happen much later; the buffer manager may wait until other transactions have also changed A and B.

Try moving OUTPUT(A) above COMMIT: the tool reports a violation of R1, because A would reach disk while recovery might still decide T never happened, and a redo log has no old value to put back.

4. Recovery with redo logging (slide 5)

Committed or not? If <COMMIT T> is on the log on disk, T is committed; otherwise it is uncommitted.

Slide 5 question: why does nothing need to be done for uncommitted transactions?

By the redo rule, no change of T may reach disk until <COMMIT T> is on disk. If recovery finds no <COMMIT T>, then T's COMMIT never reached disk, so none of T's changes did either. The disk still has the values from before T, exactly as if T had never run. There is nothing to undo (and the log has no old values to undo with anyway). Incomplete transactions are treated as if they never occurred; they only get an <ABORT T> record.

Committed transactions are the problem: we do not know which of their changes reached disk. But the log has the new values, so we write them all again:

1. Identify the committed transactions (those with <COMMIT T> on the log).
2. Scan the log FORWARD from the beginning. For each record <T, X, v>:
      if T is committed:   write X = v on disk
      if T is uncommitted: do nothing
3. For each incomplete transaction T, write <ABORT T> to the log; flush the log.

Why forward? Several committed transactions may have written the same element X at different times. That is perfectly normal (they ran one after another). Scanning earliest to latest makes the last value written the final one, as it should be. (Undo scanned latest to earliest for the mirror-image reason.) Writing a value that is already on disk is harmless, so redo is idempotent too.

5. Analysing crash points (slide 6)

Slide 6 (worked answers)

Crash after <START T> is written to disk (and nothing after it). No COMMIT on disk: T is incomplete. By R1 no change of T reached disk, so A = B = 8 on disk. Recovery does nothing to the data and writes <ABORT T>.

Crash after <COMMIT T> is written to disk (step 9 or later). T is committed. Forward scan: <T,A,16> → write A = 16; <T,B,16> → write B = 16. If the crash came before step 10, both writes are essential; between steps 10 and 11, the write of A is redundant and the write of B essential; after step 11, both are redundant but harmless. Result: A = B = 16.

Crash after <T,A,16> is written to disk but before the COMMIT is. (In Fig. 17.7 this can only happen if some other transaction flushes the log after step 4.) T has no COMMIT on disk, so it is incomplete. <T,A,16> is ignored; by R1, A = 8 is still on disk. Recovery writes <ABORT T>. Result: A = B = 8.

(The textbook's Example 17.7 adds: a crash between steps 8 and 9 is one of the two cases, depending on whether the COMMIT record happened to reach disk.)

DB QB · 22-23 2d · 7 marks  |  BUET QBank · CSE 215 | L-2/T-1 | 2022–23 · 7 marks

Suppose you are given the following sequence of log records representing the actions of a transaction T: <START T>; <T, A, 10>; <T, B, 20>; <COMMIT T>. Answer the following questions:

(i) For undo logging, what is the last log record that must be sent to disk before updated A is sent to disk?
(ii) For undo logging, what is the last log record that must be sent to disk before updated B is sent to disk?
(iii) For redo logging, what is the last log record that must be sent to disk before updated A and B are sent to disk?

Show worked answer

(i) <T, A, 10>. Rule U1: the update record for A must reach disk before the new A. Log records reach disk in order, so <START T> goes before it. Nothing later is required: <T,B,20> may still be in memory when A is written (U1 is per element), and <COMMIT T> must not be on disk yet (U2).

(ii) <T, B, 20>. Same reasoning for B. <COMMIT T> must not precede B under undo logging, because U2 requires all data on disk first.

(iii) <COMMIT T>. Under redo logging, both update records and the COMMIT record must be on disk before any changed element is written. Since <COMMIT T> is the last of them, it is the last record that must be sent before A and B.

DB QB · 23-24 6c · 12 marks  |  BUET QBank · CSE 215 | L-2/T-1 | 2023–24 · 12 marks

Consider the following sequence of log records:

<START S>; <S, A, 60>; <COMMIT S>; <START T>; <T, A, 10>; <START U>;
<U, B, 20>; <T, C, 30>; <START V>; <U, D, 40>; <V, F, 70>; <COMMIT U>;
<T, E, 50>; <COMMIT T>; <V, B, 80>; <COMMIT V>.

(i) Assume a system crash happens before <COMMIT T> is recorded in the log. Considering that "undo logging" is used, describe the actions the recovery manager will perform after the crash. Your answer should list each action in the format <X, A> where database element X is written with the value A.
(ii) Answer the question (i) above for "redo logging".
(iii) Why is it necessary to write an <ABORT T> log record in the logfile for every uncommitted transaction T after the completion of the recovery operation?

Show worked answer

The log on disk ends with <T, E, 50>. Committed: S, U. Uncommitted: T, V.

(i) Undo logging (values are old values; scan backward; undo T and V):

  • <T,E,50> → <E, 50>
  • <COMMIT U> → U committed
  • <V,F,70> → <F, 70>
  • <U,D,40> → ignore; <START V>
  • <T,C,30> → <C, 30>
  • <U,B,20> → ignore; <START U>
  • <T,A,10> → <A, 10>; <START T>
  • <COMMIT S>, <S,A,60> → ignore

Actions: <E,50>, <F,70>, <C,30>, <A,10>; then <ABORT T> and <ABORT V> are logged and flushed.

(ii) Redo logging (values are new values; scan forward; redo S and U):

  • <S,A,60> → <A, 60>
  • <T,A,10> → ignore (T uncommitted)
  • <U,B,20> → <B, 20>
  • <T,C,30> → ignore
  • <U,D,40> → <D, 40>
  • <V,F,70>, <T,E,50> → ignore

Actions: <A,60>, <B,20>, <D,40>; then <ABORT T> and <ABORT V> are logged and flushed.

(iii) The ABORT record tells every future recovery that T has been dealt with. Without it, T would look incomplete forever:

  • Under undo logging, a later recovery would undo T's records again. If, meanwhile, a committed transaction changed one of those elements (say E), the stale undo would overwrite the committed value, destroying a committed update.
  • T would look active forever, so no checkpoint could ever cover it (a quiescent checkpoint waits for all transactions to have COMMIT or ABORT; a nonquiescent one would list T and never end), and the log before T's START could never be deleted.

The log is flushed after writing the ABORT records so that they themselves survive the next crash.

Note: the CSE215 bank prints this log with <COMMIT V> and <COMMIT T> swapped and asks about a crash “before <COMMIT V>”. In its version too the crash comes right after <T, E, 50>, so the log on disk and the answers are the same as above (its answers agree).

Summary: redo logging logs new values and requires update records and <COMMIT T> on disk before any changed element (slides: R1 + R2; textbook: one rule R1). Data may stay in memory after the commit. Recovery identifies committed transactions, scans forward and rewrites their new values; uncommitted transactions changed nothing on disk and just get <ABORT T>.
