Protecting Against Media Failures: Archiving

The log repairs system failures, where the disk survives. When the disk itself is lost, we need an archive: a copy of the database kept elsewhere, plus the log since the copy was made. This chapter covers full and incremental dumps, the nonquiescent dump, and recovery from an archive, using the slides' example.

1. The archive (slide 19)

Archive
A copy of the database kept separately from the database itself, for example on tape or optical disk, stored at a secure remote location.
Archiving (dump)
Making that copy.

The simplest way: shut the database down, copy its state to the backup medium, and store it far away. After a media failure the database can be restored to the state at the time of the copy. To get to a more recent state we also need the log since the archive was made, and the log must survive the failure too. So:

  • keep all log files written since the archived copy; replaying them on the archived copy brings the database up to date;
  • once a log block is written to disk, also write it to the archive medium;
  • to survive the loss of the whole site, send the log to a remote site almost as soon as it is created. Then, even if both data and local log are lost, the archive plus the remote log recover the database up to the last log record sent.

Why not just back up the log? (textbook sidebar)

If we never archived the data, we would have to keep the log forever and replay it from the very first transaction. A large database changes only a small fraction of itself per day, but over a year the logged changes become much larger than the database. An archive lets us throw away the log before it.

2. Full and incremental dumps (slide 20)

Full dump
The entire database is copied.
Incremental dump
Only the database elements changed since the previous dump are copied. (The slide says “since the previous full dump”; the textbook says since the previous full or incremental dump. The textbook also allows several levels: a full dump is level 0, and a level-i dump copies everything changed since the last dump at level ≤ i.)

To restore: copy back the most recent full dump, then apply the later incremental dumps in order, earliest first. This is much like replaying a redo log.

3. Nonquiescent archiving (slides 21–22)

Most databases cannot be shut down for the hours a dump takes. A nonquiescent dump copies the database while transactions keep running. It is the counterpart of a nonquiescent checkpoint:

Because elements change while they are being copied, the archive may hold a state that never existed. Textbook Example 17.13: the database has A, B, C, D = 1, 2, 3, 4 when the dump begins; during the dump A becomes 5, C becomes 6, B becomes 7, and the copying runs in order A, B, C, D:

The archive holds (1, 2, 6, 4), although the database was (1, 2, 3, 4) at the start and (5, 7, 6, 4) at the end. That is fine, as long as the log written during the dump is kept: it records every change, so recovery can fix the archive.

The algorithm (slide 21, textbook §17.5.2). The textbook adds that the log must be a redo or undo/redo log; an undo log is not suitable for archiving, because it lacks the new values needed to bring the archive forward.

1. Write a log record <START DUMP>.
2. Perform a checkpoint appropriate for the logging method in use.
3. Perform a full or incremental dump of the data disk(s), making sure the
   copy has reached the secure remote site.
4. Make sure enough of the log has been copied to the remote site that at least
   the log up to and including the checkpoint of step 2 will survive a media
   failure of the database.
5. Write a log record <END DUMP>.

The slides' example (textbook Example 17.14): T1 writes A and B, T2 writes C; both are active when the dump begins. A possible undo/redo log during the dump:

<START DUMP>
<START CKPT(T1,T2)>
<T1,A,1,5>
<T2,C,3,6>
<COMMIT T2>
<T1,B,2,7>
<END CKPT>
Dump completes
<END DUMP>

Slide 22 question: why is it safe to ignore the log records before <START CKPT(T1,T2)>?

The checkpoint of step 2 is an undo/redo checkpoint: between <START CKPT> and <END CKPT> it flushes every dirty buffer to disk. So every change logged before <START CKPT(T1,T2)> is on the data disk by the time the dump copies it, and therefore in the archive. Everything that may be missing from, or wrong in, the archive was logged after the START CKPT: those are the changes made while the copy was being taken. To recover from this archive we only need the log from <START CKPT(T1,T2)> onward (plus, for undo, the START records of transactions in its list). The textbook is a little more cautious, since the copying can overlap the checkpoint: after the dump completes it keeps the log back to the start of the checkpoint previous to the one in step 2, and deletes only what lies before that.

4. Recovery from an archive (slide 23)

Step 1: Restore the database from the archive.
        (a) Find the most recent full dump and copy it into the database.
        (b) If there are later incremental dumps, apply each of them, earliest first.
Step 2: Modify the database using the surviving log, with the recovery method
        of the logging method in use.

Slide 23: crash (media failure) at the end of the dump (textbook Example 17.15)

The log above survives, but, to make it interesting, it has no <COMMIT T1> record. T2 has committed.

  1. Restore the archive: A, B, C, D = (1, 2, 6, 4).
  2. Redo T2 (committed): C = 6. Here C is already 6 in the archive, but the archive could have copied C before T2 changed it, so the redo is needed in general.
  3. Undo T1 (no COMMIT), latest first: B = 2, then A = 1. They happen to be 2 and 1 in the archive already, but the copy could have caught the new values 5 or 7.

Result: (1, 2, 6, 4), and <ABORT T1> is logged. Note on the slide: it lists “Undo <T1,A,1,5>. Undo <T1,B,2,7>” in that order. Undo works latest-first, so B (the later record) is restored before A. With two different elements the result is the same either way.

Key terms

Quick check

Summary: media failures are survived with an archive (full or incremental dumps, kept remotely) plus a log copied to the remote site. A nonquiescent dump runs while transactions continue, bracketed by <START DUMP> and <END DUMP> with a checkpoint inside; the archive may hold a state that never existed, and the log fixes it. Recovery restores the latest full dump, applies incremental dumps earliest first, then runs normal (redo or undo/redo) recovery on the surviving log.
