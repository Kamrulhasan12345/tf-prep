Undo/Redo Logging

Undo logging writes data too early, redo logging holds it too long. Undo/redo logging logs both the old and the new value, and in exchange drops almost every ordering constraint. This chapter gives rule UR1, the slide's step table, the two-pass recovery (redo, then undo), why the order of the passes is delicate, and the many exam questions on undo/redo recovery.

1. Why combine the two? (slide 12)

  • Undo logging requires data to be written to disk before a transaction commits. This increases the number of disk I/Os.
  • Redo logging requires changed data to stay in buffers until the transaction commits and its log records are flushed. This increases the average number of buffers transactions need.
  • The textbook adds a third problem: when two elements share a buffer, the two methods can contradict each other. If a buffer holds A, changed by a committed transaction, and B, changed by a transaction whose COMMIT is not yet on disk, a redo checkpoint must write the buffer (because of A) and must not write it (because of B).

Combining both kinds of information in the log removes these conflicts, at the price of bigger log records.

2. The undo/redo rule (slide 13)

<T, X, v, w>
The undo/redo update record: transaction T changed element X; its previous value was v and its new value is w.
UR1
Before X is updated on disk because of a change made by T, the log record <T, X, v, w> must appear on disk.

UR1 is write-ahead logging and nothing more. It enforces only the constraint that undo and redo logging have in common. In particular there is no constraint on <COMMIT T>: it may reach disk before, between or after the changed elements.

The update records now carry both values. As the slide notes, <COMMIT T> is written in the middle of the outputs and is not flushed while A and B are written. Step 10 could equally come before step 8 or 9, or after step 11; all are legal.

A problem with delayed commitment (textbook sidebar). As with undo logging, a user may be told a transaction committed (say, they booked a seat and logged off), yet the <COMMIT T> record was never flushed; a crash then makes recovery undo the booking. If that is unacceptable, add rule UR2: a <COMMIT T> record must be flushed to disk as soon as it appears in the log (in Fig. 17.9, add FLUSH LOG after step 10).

4. Recovery with undo/redo logging (slide 15)

The log has both values, so recovery can undo or redo any transaction. And it must do both, because the flexible rule allows both kinds of damage: a committed transaction may have some changes not yet on disk, and an uncommitted one may have some changes already on disk.

Step 1 (redo): redo all committed transactions, earliest first:
        scan forward; for each <T,X,v,w> with T committed, write X = w.
Step 2 (undo): undo all incomplete transactions, latest first:
        scan backward; for each <T,X,v,w> with T incomplete, write X = v.
Then write <ABORT T> for each incomplete T and flush the log.

Slide 15 question: what if redo and undo involve the same element X?

Suppose uncommitted T1 changed X, then committed T2 changed X, then the system crashed. Concretely: <T1, X, 1, 2>, later <T2, X, 2, 3>, <COMMIT T2>.

  • Redo first, then undo (the order of the algorithm above): redo sets X = 3, then undo of T1 sets X = 1. T2's committed change is lost, which is what the slide means by “T2's changes will not be reflected”.
  • Undo first, then redo: undo sets X = 1, then redo sets X = 3. Now T1's change is gone, as it should be, but T2's value 3 was computed from 2, a value written by T1, which never committed. The final state does not correspond to any execution of whole transactions.

So neither order gives a sensible result. The textbook's conclusion: the problem is not the order of recovery but the fact that T2 was allowed to read or overwrite a value written by an uncommitted transaction. The DBMS must prevent this with concurrency control (Lectures 07–08: for example, a transaction keeps its locks until it commits, so no other transaction can touch X in between). Under that assumption the two passes never touch the same element in conflicting ways and their order does not matter. This book and the simulator use the slides' order: redo, then undo.

5. Analysing the crash points (slide 16, textbook Example 17.11)

Slide 16 (worked answers), the log of Fig. 17.9

Crash after <COMMIT T> is flushed to disk. T is committed, so it is redone: write A = 16 and B = 16. Given the order of events, A is already 16 on disk; B may or may not be, depending on whether the crash came before or after step 11. Result A = B = 16.

Crash before <COMMIT T> reaches disk. T is incomplete, so it is undone, latest first: write B = 8, then A = 8. If the crash came between steps 9 and 10, A was 16 on disk and the undo is necessary. B was never written, and if the crash came before step 9 neither was A, but recovery cannot know, so it always performs the undo. Then <ABORT T> is logged. Result A = B = 8.

DB QB · 24-25 3c · 11 marks  |  BUET QBank · CSE 215 | L-2/T-1 | 2024–25 · 11 marks

Assume that the database recovery manager takes a redo or undo action which is expressed as <X,V> implying database object X is written with value V in the disk. Consider the sequence of following log records.

<T0 start>; <T0, A, 40, 60>; <T1 start>; <T1, B, 100, 150>; <T0, C, 50, 100>;
<T2 start>; <T2, D, 100, 70>; <T1, C, 20, 50>; <T1 commit>; <T2, C, 60, 80>;
<T0 commit>; <T2 commit>

Answer the following questions: (i) For both redo and undo phases, write down the actions of the recovery manager if a system crash happens between <T2, C, 60, 80> and <T0 commit>. (ii) For both redo and undo phases, write down the actions of the recovery manager if a system crash happens between <T1, C, 20, 50> and <T1 commit>. Your answer should consist of a sequence of <X,V> statements in order of their occurrence.

Show worked answer

Each update record is <T, X, old, new>. Redo writes the new value of committed transactions (forward); undo writes the old value of uncommitted ones (backward). (The values in this question are not mutually consistent, e.g. T1's old value of C is 20 although T0 had set C to 100; recovery does not care, it just copies values from the log.)

(i) Crash between <T2,C,60,80> and <T0 commit>. Committed: T1. Uncommitted: T0, T2.

  • Redo phase (forward, T1 only): <T1,B,100,150> → <B, 150>; <T1,C,20,50> → <C, 50>.
  • Undo phase (backward, T0 and T2): <T2,C,60,80> → <C, 60>; <T2,D,100,70> → <D, 100>; <T0,C,50,100> → <C, 50>; <T0,A,40,60> → <A, 40>.

Sequence: <B,150>, <C,50>, <C,60>, <D,100>, <C,50>, <A,40>; then <T0 abort> and <T2 abort> are logged. Final: A = 40, B = 150, C = 50, D = 100.

(ii) Crash between <T1,C,20,50> and <T1 commit>. No transaction has committed.

  • Redo phase: nothing to redo.
  • Undo phase (backward, T0, T1, T2): <T1,C,20,50> → <C, 20>; <T2,D,100,70> → <D, 100>; <T0,C,50,100> → <C, 50>; <T1,B,100,150> → <B, 100>; <T0,A,40,60> → <A, 40>.

Sequence: <C,20>, <D,100>, <C,50>, <B,100>, <A,40>; then aborts for T0, T1, T2. Final: A = 40, B = 100, C = 50, D = 100.

If the question is meant in the Silberschatz style (the notation <T0 start> and “redo and undo phases” come from that textbook), the redo phase “repeats history”: it replays every update record forward, committed or not, and then the undo phase rolls back the incomplete transactions as above. Then (i) redo is <A,60>, <B,150>, <C,100>, <D,70>, <C,50>, <C,80> and (ii) redo is <A,60>, <B,150>, <C,100>, <D,70>, <C,50>; the undo phases are unchanged and the final values are the same. Write the course method, and mention this variant if the question seems to expect it.

BUET QBank · CSE 303 | L-3/T-1 | 2013–14 · 12 marks, and CSE 303 | L-3/T-1 | 2011–12 · 12 marks (parts b, c only)

The following is a sequence of undo/redo-log records written by two transactions T and U:

<T, start>; <T, A, 10, 11>; <U, start>; <U, B, 20, 21>; <T, C, 30, 31>;
<U, D, 40, 41>; <U, commit>; <T, E, 50, 51>; <T, commit>

Describe the action of the recovery manager, including changes to both disk and the log, if there is a crash and the last log record to appear on disk is: (a) <U, start> (b) <U, commit> (c) <T, E, 50, 51> (d) <T, commit>.

Show worked answer

(Textbook Exercise 17.4.3.) Redo committed transactions forward with new values, then undo incomplete ones backward with old values, then log ABORTs.

(a) Last record <U, start>. No commits; T and U incomplete. Redo: nothing. Undo: <T,A,10,11> → A = 10. U has no updates. Log: append <ABORT T> and <ABORT U>, flush.

(b) Last record <U, commit>. U committed, T incomplete. Redo U forward: B = 21, D = 41. Undo T backward: C = 30, A = 10. Log: append <ABORT T>, flush.

(c) Last record <T, E, 50, 51>. Same, with one more update of T to undo. Redo: B = 21, D = 41. Undo: E = 50, C = 30, A = 10. Log: <ABORT T>, flush.

(d) Last record <T, commit>. Both committed. Redo forward: A = 11, B = 21, C = 31, D = 41, E = 51. Nothing to undo; nothing is added to the log.

Unlike undo logging, case (d) still writes everything: under undo/redo logging the COMMIT can reach disk before the data, so the data may be missing.

BUET QBank · CSE 303 | L-3/T-1 | 2014–15 · 5 marks

After a system crash, the following log records are found: <T0, start>; <T0, commit>; <T1, start>; <T1, C, 800, 600>. Describe the recovery actions for the above log records.

Show worked answer

The update record has an old and a new value, so this is an undo/redo log.

  • T0 has START and COMMIT: committed, so it is redone. It has no update records, so redo writes nothing.
  • T1 has START but no COMMIT: incomplete, so it is undone. Backward: <T1, C, 800, 600> → write C = 800 (the old value).
  • Log: append <T1, abort> and flush.

After recovery C = 800, whether or not 600 had reached disk.

BUET QBank · CSE 303 | L-3/T-1 | 2015–16 · 15 marks

The initial account balances of A1, A2 and A3 are 1000, 2000 and 3000 respectively. Two serial transactions are given:

T20T21
READ(A1)
A1 = A1 + 100
WRITE(A1)
READ(A3)
A3 = A3 − 100
WRITE(A3)
COMMIT






READ(A2)
A2 = A2 + 0.1 × A2
WRITE(A2)
COMMIT

(a) Write log records for the above transactions. (b) Show the log-based recovery if a failure occurs after WRITE(A3). (c) Show the recovery if a failure occurs after WRITE(A2).

Show worked answer

(a) With undo/redo logging (old and new values); A1 + 100 = 1100, A3 − 100 = 2900, A2 + 0.1 × 2000 = 2200:

1 <START T20>
2 <T20, A1, 1000, 1100>
3 <T20, A3, 3000, 2900>
4 <COMMIT T20>
5 <START T21>
6 <T21, A2, 2000, 2200>
7 <COMMIT T21>

(READs and the arithmetic are not logged: they do not change the database.) With an undo log the update records would be <T20,A1,1000>, <T20,A3,3000>, <T21,A2,2000>; with a redo log <T20,A1,1100>, <T20,A3,2900>, <T21,A2,2200>.

(b) Failure after WRITE(A3). The log holds records 1–3: T20 has no COMMIT, so it is incomplete. Nothing to redo. Undo backward: A3 = 3000, then A1 = 1000. Log <ABORT T20>. Final: A1 = 1000, A2 = 2000, A3 = 3000, the state before both transactions. (The user re-runs T20.)

(c) Failure after WRITE(A2). The log holds records 1–6: T20 committed, T21 incomplete. Redo T20 forward: A1 = 1100, A3 = 2900. Undo T21: A2 = 2000. Log <ABORT T21>. Final: A1 = 1100, A2 = 2000, A3 = 2900. The total money is 6000, as before.

BUET QBank · CSE 303 | L-3/T-1 | 2010–11 · 10 marks

Describe log-based recovery methodology. For the given transactions ⟨T1, T2, T3⟩, write the log records.

T1T3T2
Read(A)
A = A − 50
Write(A)		Read(A)
DISPLAY(A)		Read(B)
Read(A)
B = B + 50
Write(B)
DISPLAY(A+B)
Show worked answer

Methodology. Every change a transaction makes is recorded in a log on stable storage: <T start> when T begins, an update record for every write, <T commit> or <T abort> at the end. Write-ahead logging: an update record reaches disk before the changed data does. The record's content depends on the method: undo logging stores the old value (and forces data to disk before the COMMIT), redo logging the new value (and keeps data off disk until the COMMIT is on disk), undo/redo logging both (only WAL is required). After a crash the recovery manager reads the log: committed transactions are redone (forward, new values), incomplete ones undone (backward, old values), and <ABORT T> is logged for each incomplete one. Checkpoints limit how much of the log must be read.

Log records. Reads, local arithmetic and DISPLAY are not logged, only starts, writes and commits. The table shows three separate transactions with no interleaving, so take them as running one after another in the order shown (T1, T3, T2). With initial values A0, B0 and undo/redo records:

<T1 start>
<T1, A, A0, A0 − 50>
<T1 commit>
<T3 start>
<T3 commit>              -- T3 only reads: no update record
<T2 start>
<T2, B, B0, B0 + 50>
<T2 commit>

For example with A0 = 1000, B0 = 2000: <T1, A, 1000, 950> and <T2, B, 2000, 2050>; T3 displays 950 and T2 displays 950 + 2050 = 3000. (If they run in the order T1, T2, T3 instead, move T3's two records to the end.)

Note: the CSE215 bank's answer interleaves the three transactions row by row and puts <T3 commit> before T1's write. Nothing in the question says the rows are simultaneous, and in that order T3 would display a value of A that T1 later changes; the serial reading above is the natural one.

Summary: undo/redo update records <T,X,v,w> hold old and new values. The only rule, UR1, is write-ahead logging; the COMMIT may reach disk before or after the data (UR2 optionally flushes it at once). Recovery redoes committed transactions forward (new values), then undoes incomplete ones backward (old values), then logs ABORTs. When a committed and an uncommitted transaction touched the same element, no order of the two passes is right; concurrency control must prevent that situation.
