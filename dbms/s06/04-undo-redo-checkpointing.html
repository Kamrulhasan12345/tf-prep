Checkpointing an Undo/Redo Log

The simplest checkpoint of the three: flush every dirty buffer. This chapter gives the algorithm, the textbook's Example 17.12 with the slide's two crash scenarios and its “why not <START T2>?” question, a comparison of all three checkpoint methods, and an exam question.

1. The algorithm (slide 17)

1. Write <START CKPT(T1, …, Tk)>, where T1 … Tk are all the active
   (uncommitted) transactions, and flush the log.
2. Write to disk ALL dirty buffers, i.e. every buffer holding a changed
   database element, whoever changed it.
3. Write <END CKPT> and flush the log.

The difference from redo logging is in step 2: flush all dirty buffers, not just those of committed transactions. Undo/redo logging tolerates uncommitted data on disk (it can be undone from the old values), so there is no need to sort buffers by transaction. That also means elements smaller than a block can share a buffer without the conflict described in the previous chapter.

The textbook adds one requirement: a transaction must not write any values, even to memory buffers, until it is certain not to abort. Concurrency control (textbook §19.1) needs this anyway, to stop other transactions from reading uncommitted (“dirty”) data.

2. Textbook Example 17.12 and slide 18

<START T1>
<T1,A,4,5>
<START T2>
<COMMIT T1>
<T2,B,9,10>
<START CKPT(T2)>
<T2,C,14,15>
<START T3>
<T3,D,19,20>
<END CKPT>
<COMMIT T2>
<COMMIT T3>

This is the redo log of Fig. 17.8 with old values added (each old value is one less than the new one). T2 is the only active transaction when the checkpoint begins. Under undo/redo logging T2's new value B = 10 may already be on disk, which was impossible under redo logging, but it does not matter: during the checkpoint B is flushed anyway, since all dirty buffers are. So is T1's A, if it was not on disk already.

Slide 18 (worked answers)

Crash after <COMMIT T3>. T2 and T3 committed. T1 is before the checkpoint, and since <END CKPT> is on the log, T1's changes are on disk: ignore it. Recovery starts at <START CKPT(T2)>: redo <T2,C,14,15> (C = 15) and <T3,D,19,20> (D = 20). Nothing to undo.

Why start at <START CKPT(T2)> and not at <START T2>? Under redo logging we had to go back to <START T2>, because T2's earlier change B = 10 might not be on disk. Under undo/redo logging the checkpoint flushed every dirty buffer, including B, before <END CKPT>. So every change logged before the START CKPT is on disk, and redo can start at the START CKPT.

Crash before <COMMIT T3> (after <COMMIT T2>). T2 committed, T3 incomplete. Redo T2 from the START CKPT: C = 15 (B = 10 is already on disk). Undo T3: D = 19. Write <ABORT T3>. Unlike redo logging, T3 must be undone, because its D = 20 may have reached disk (the checkpoint itself may have flushed it). Could recovery have to go before the START CKPT? For the redo pass, no. For the undo pass, yes, if the incomplete transaction was already active at the START CKPT: its changes before the checkpoint were flushed to disk too, and must be undone, so the backward scan continues to that transaction's START record. T3 started after the START CKPT, so here it does not.

Exam questions

DB QB · 20-21 4b · 15 marks  |  BUET QBank · CSE 215 | L-2/T-2 | 2020–21 · 15 marks

The log records for transactions are given as follows:

1. <T0 start>              8. <T3 start>
2. <T0, A, 1000, 200>      9. <T3, D, 1000, 200>
3. <T1 start>             10. <T3 commit>
4. <T1, B, 1000, 200>     11. <T4 start>
5. <T1 commit>            12. <T3, E, 1000, 200>
6. <T2 start>             13. <T4 commit>
7. <T2, C, 1000, 200>

a. Perform checkpoint after instruction 7. b. Assume a failure is occurred after instruction 13. Run the log-based recovery algorithm to recover the transactions from failure considering the checkpoint.

Show worked answer

The update records carry old and new values, so this is an undo/redo log.

(a) Checkpoint after instruction 7. Active at that moment: T0 (started, not committed) and T2. T1 has committed. A quiescent checkpoint would have to wait for T0 and T2 to finish, which never happens in this log, so we take a nonquiescent one:

  1. Write <START CKPT(T0, T2)> and flush the log.
  2. Write all dirty buffers to disk: A (T0), B (T1), C (T2), whichever are not already there. New transactions may keep running meanwhile.
  3. Write <END CKPT> and flush. It does not wait for T0 and T2; say the flushing finishes after instruction 8.
1 <T0 start>  2 <T0,A,1000,200>  3 <T1 start>  4 <T1,B,1000,200>  5 <T1 commit>
6 <T2 start>  7 <T2,C,1000,200>  <START CKPT(T0,T2)>  8 <T3 start>  <END CKPT>
9 <T3,D,1000,200>  10 <T3 commit>  11 <T4 start>  12 <T3,E,1000,200>  13 <T4 commit>

(b) Failure after instruction 13. Committed: T1, T3, T4. Incomplete: T0, T2. (Record 12 is printed as an update of T3 after T3's commit, which a transaction cannot do; it is probably a typo for <T4, E, 1000, 200>. Either way it belongs to a committed transaction, so the answer is the same.)

  • The last checkpoint record is <END CKPT>; its START CKPT lists T0 and T2. All dirty data from before the START CKPT is on disk, so T1 (committed before the checkpoint) needs nothing.
  • Redo forward from <START CKPT(T0,T2)>: record 9 → D = 200; record 12 → E = 200.
  • Undo backward from the end for T0 and T2. Both were active at the START CKPT, so the scan continues past it to their START records: record 7 → C = 1000; record 2 → A = 1000; stop at <T0 start>.
  • Log: append <T0 abort> and <T2 abort>, flush.

Database after recovery: A = 1000, B = 200, C = 1000, D = 200, E = 200.

Summary: an undo/redo checkpoint writes <START CKPT(active list)>, flushes all dirty buffers, and writes <END CKPT>, without waiting for anyone. After a crash with a completed checkpoint, redo starts at the START CKPT (everything earlier is on disk); undo goes back as far as the START of each incomplete transaction, which can be before the checkpoint if that transaction was in its list.
