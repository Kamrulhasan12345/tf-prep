Checkpointing a Redo Log

With redo logging, a committed transaction's changes may sit in memory long after it commits, so a checkpoint must write them out. This chapter gives the nonquiescent checkpoint for redo logs, the recovery algorithm that uses it, the slides' “why?” questions, and the three crash scenarios of slide 11.

1. A new problem

For undo logging, a checkpoint only had to wait until the active transactions finished: after that, U2 guaranteed their data was on disk. Redo logging gives no such guarantee. A transaction that committed an hour ago may still have changed blocks sitting in memory, and if the log before the checkpoint were thrown away, nothing could redo them. So, whether quiescent or nonquiescent, a redo checkpoint must write to disk all elements modified by committed transactions. For that the buffer manager must track which buffers are dirty (changed but not yet written to disk) and which transactions changed them.

On the other hand, the checkpoint does not need to wait for the active transactions: under the redo rule they are not allowed to write their changes to disk anyway.

2. The nonquiescent checkpoint for redo logging (slide 7)

1. Write <START CKPT(T1, …, Tk)>, where T1 … Tk are all the active
   (uncommitted) transactions, and flush the log.
2. Write to disk all database elements that were written to buffers but not yet
   to disk by transactions that had ALREADY COMMITTED when the START CKPT
   record was written.
3. Write <END CKPT> and flush the log.

The slide's example (slide 8, textbook Fig. 17.8)

<START T1>
<T1,A,5>
<START T2>
<COMMIT T1>
<T2,B,10>
<START CKPT(T2)>
<T2,C,15>
<START T3>
<T3,D,20>
<END CKPT>
<COMMIT T2>
<COMMIT T3>

When the checkpoint starts, T1 has committed and T2 is active, so the record is <START CKPT(T2)>. The value A = 5 written by T1 may or may not have reached disk; if not, the checkpoint must write it before <END CKPT>. B = 10 belongs to T2, which has not committed, so the checkpoint must not write it.

While the checkpoint is writing A, the log keeps growing: T2 writes C, T3 starts and writes D. After <END CKPT>, T2 and T3 commit.

3. Recovery with a checkpointed redo log (slides 9–10)

Case 1: the last checkpoint record on the log is <END CKPT>.

  1. Find the last <END CKPT>, and scan back to the matching <START CKPT(T1,…,Tk)>.
  2. Every transaction that committed before that START CKPT has its changes on disk, so it can be ignored.
  3. Only T1 … Tk and transactions that started after the START CKPT can need redoing. Find the earliest <START Ti> among T1 … Tk.
  4. From there, scan forward and redo every update of a committed transaction that is one of T1 … Tk or started after the START CKPT. (Updates of transactions that committed before the START CKPT may appear in this stretch too; they are skipped.)

Slide 9 questions (worked answers)

Why do all transactions committed before <START CKPT…> have their updates on disk? Because step 2 of the checkpoint wrote to disk every element changed by a transaction that had committed when the START CKPT was written, and <END CKPT> is written only after step 2 finished. Seeing <END CKPT> on the log proves that step 2 completed.

Why can none of T1 … Tk have a <COMMIT> record before <START CKPT…>? By definition the list holds the transactions that were active, i.e. uncommitted, at the moment the START CKPT record was written. A transaction that had committed earlier would not be in the list. So their COMMIT records, if any, come after the START CKPT, and they can still have committed changes that are not on disk.

Case 2: the last checkpoint record is <START CKPT(T1,…,Tk)> with no END after it (slide 10).

Slide 10 question: why are transactions that committed before this START CKPT not guaranteed to be on disk?

The crash interrupted the checkpoint in step 2, while it was still writing committed transactions' data to disk. We do not know how far it got, so this checkpoint guarantees nothing. Instead we use the previous complete checkpoint: find the previous <END CKPT> and its matching <START CKPT(S1,…,Sm)>, and redo all committed transactions that are among S1 … Sm or started after that START CKPT, beginning at the earliest <START Si>. If there is no earlier checkpoint, start at the beginning of the log. (A detail from the textbook's footnote: we look for an <END CKPT> first, then its START CKPT, because an older START CKPT might itself have no END after an earlier crash.)

The textbook also suggests putting into <START CKPT> not just the names of T1 … Tk but pointers to their START records. Then, once <END CKPT> is written, everything before the earliest of those START records can be deleted.

4. The three scenarios of slide 11 (textbook Example 17.9)

Slide 11 (worked answers), log of Fig. 17.8

System crashes at the end. Scanning back, the last checkpoint record is <END CKPT>; its START CKPT lists T2. Candidates for redo: T2 and transactions that started after the START CKPT, i.e. T3. Both have COMMIT records, so both are redone. Scan forward from <START T2> (the earliest start among the list): redo B = 10, C = 15, D = 20. T1 committed before the START CKPT: its A = 5 was flushed by the checkpoint, so <T1,A,5> is not redone (it lies before <START T2> anyway).

Crash between <COMMIT T2> and <COMMIT T3>. Same as above, except T3 has no COMMIT. Its record <T3,D,20> is in the scanned range but is not redone. Redo B = 10, C = 15; then write <ABORT T3>.

Crash just before <END CKPT>. The last checkpoint record is <START CKPT(T2)> with no END, so it guarantees nothing. We would look for the previous END CKPT, but there is none, so we go back to the beginning of the log. The only committed transaction is T1: redo A = 5. Write <ABORT T2> and <ABORT T3>.

Practice

Key terms

Quick check

Summary: a redo checkpoint writes <START CKPT(active list)>, flushes the dirty data of transactions that had already committed, then writes <END CKPT>; it does not wait for active transactions. Recovery uses the last completed checkpoint: redo committed transactions that are in its list or started after its START CKPT, scanning forward from the earliest START of the listed ones. If the last checkpoint is incomplete, fall back to the previous complete one, or the start of the log.
