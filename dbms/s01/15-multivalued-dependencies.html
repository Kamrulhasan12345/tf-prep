Multivalued Dependencies: Redundancy That BCNF Misses

A relation can be in BCNF and still repeat data, when it stores two independent sets of facts about the same thing. This chapter shows the slides' shirts example, defines the multivalued dependency precisely, and checks the definition on the data.

1. BCNF with redundancy (slide 60)

A shop stores which sizes and which colors each shirt is available in:

Sizes and colors are each repeated: shirt_01's size 15 appears twice (white, blue), and white appears three times (sizes 15, 16, 17). Yet the relation is in BCNF. Slide 60 asks: verify?

Why AvailableShirts is in BCNF

Look for a nontrivial FD. shirt_code → size fails (shirt_01 has sizes 15, 16, 17). shirt_code → color fails. size → color fails (size 16 comes in white, blue, grey, black). shirt_code size → color fails ((shirt_01, 15) has white and blue). shirt_code color → size fails. color → shirt_code (and so also size color → shirt_code) happens to hold in these 12 rows, because the two shirts share no color, but nothing stops a second shirt from also coming in white, so it is not a real FD (Chapter 2: an instance cannot prove an FD). No nontrivial FD holds, so the only key is all three attributes {shirt_code, size, color}, and with no nontrivial FDs there is nothing to violate BCNF.

The textbook explains the cause: the most common source of redundancy in BCNF schemas is an attempt to put two or more set-valued properties of the key into a single relation. Its own example (§3.6.1) stores a star's set of addresses and set of movies in one relation, so each address is repeated once per movie and each movie once per address. Sizes and colors of a shirt are the same situation.

2. Definition (book §3.6.2)

Multivalued dependency (MVD) A₁…Aₙ ↠ B₁…Bₘ
Holds in R if, whenever we fix values for the A's, the set of values among the B's is independent of the set of values of the remaining attributes (those not among the A's or B's). Precisely: for each pair of tuples t and u of R that agree on all the A's, R also contains a tuple v that agrees with t and u on the A's, with t on the B's, and with u on all the other attributes.

Swapping the roles of t and u, a fourth tuple w (A's from both, B's from u, the rest from t) must exist too. So for each A-value, every B-combination appears with every rest-combination: a cross product. That is exactly what Figure 1 shows: for shirt_01, every size appears with every color.

The slide writes the shirts' MVDs as shirt_code ↠ size and shirt_code ↠ color: the sizes depend on the shirt, the colors depend on the shirt, and the set of sizes is independent of the set of colors.

MVDs and FDs

Every FD A → B is also an MVD A ↠ B: if t and u agree on the A's, they agree on the B's, so u itself serves as v. The converse fails: shirt_code ↠ size holds but shirt_code → size does not. MVDs capture independence; FDs capture uniqueness.

DB QB · 17-18 7c · 10 marks  |  BUET QBank · CSE 215 | L-2/T-2 | 2017–18 · 10 marks

Give an example of a relation which is in 3NF but not in BCNF. Define Multivalued Dependency.

Show worked answer

3NF but not BCNF. Bookings(title, theatre, city) with theatre → city and title city → theatre. Keys: {title, city} and {title, theatre}, so every attribute is prime. theatre → city has a non-superkey left side (theatre⁺ = {theatre, city}), so R is not in BCNF; but its right side, city, is prime, and the other FD has a key on its left, so R is in 3NF. (Chapter 14 gives two more examples.)

Multivalued dependency. X ↠ Y holds in R if for every two tuples t, u of R that agree on X, there is a tuple v in R that agrees with both on X, with t on Y, and with u on all attributes of R − X − Y. Informally: for a fixed X-value, the set of Y-values is independent of the values of the remaining attributes, so they appear in all combinations. Example: AvailableShirts(shirt_code, size, color) with shirt_code ↠ size: since (shirt_01, 15, white) and (shirt_01, 16, blue) are present, (shirt_01, 15, blue) must be present too. Every FD X → Y is an MVD, but not conversely. MVDs cause redundancy that BCNF does not detect; 4NF removes it.

Summary: storing two independent set-valued properties of a key in one relation forces every combination to appear, which is redundancy even in BCNF (AvailableShirts has no nontrivial FD at all). The multivalued dependency X ↠ Y says: for tuples agreeing on X, the Y-values and the remaining values combine freely. Every FD is an MVD. The cure is to store each independent set in its own relation (4NF).
