Recovering the Original: Lossless Joins and the Chase Test

Why does a BCNF split never invent tuples, while the employee split of Chapter 1 did? This chapter gives the argument from slides 51–52, a quick test for two-way splits, and the chase: a general, animated test for any decomposition.

1. Recovering R from a BCNF split (slide 51)

Take R(A, B, C) with the BCNF-violating FD B → C, decomposed into R₁(A, B) and R₂(B, C).

  • Every original tuple comes back. A tuple t = (a, b, c) projects to (a, b) in R₁ and (b, c) in R₂. They share b, so the natural join pairs them and produces (a, b, c) = t.
  • No bogus tuple appears (book §3.4.1). Suppose R has t = (a, b, c) and v = (d, b, e). The join can pair (a, b) from t with (b, e) from v, producing (a, b, e). Is this new? No: t and v agree on B, so by B → C they agree on C, so e = c, and (a, b, e) is just t.

So R₁ ⋈ R₂ = R exactly. Such a join is called a lossless join. The argument works for attribute sets too: if Y → Z holds in R(X, Y, Z), then R = πXY(R) ⋈ πYZ(R). By induction over the steps of the BCNF algorithm, the whole BCNF decomposition is lossless.

2. Why the BCNF split is lossless (slide 52)

For a violation X → Y, the algorithm makes R₁ = X⁺. In R₁, X is a key. R₁ and R₂ share exactly the attributes X. So when we join, each row of R₂ matches exactly one row of R₁ (the one with its X-value), and the join cannot multiply rows.

Slide 52's example: R(A, B, C) with AB → C and C → A. AB is a key ({A, B}⁺ = {A, B, C}). C → A violates BCNF, so R₁ = C⁺ = {A, C} and R₂ = {B, C}.

The two-relation test

R₁, R₂ is lossless ⇔ (R₁ ∩ R₂) → R₁ or (R₁ ∩ R₂) → R₂

That is, the common attributes must be a superkey of at least one piece; this is slide 4's condition (Chapter 1) made precise. Test it with one closure: compute (R₁ ∩ R₂)⁺ and see whether it contains all of R₁ or all of R₂. For the example: R₁ ∩ R₂ = {C}, C⁺ = {A, C} ⊇ R₁. Lossless.

The book's warning example (3.21): R(A, B, C) with neither B → A nor B → C, holding (1, 2, 3) and (4, 2, 5). Projected onto AB and BC and rejoined, it gives four tuples, including the bogus (1, 2, 5) and (4, 2, 3), exactly like the two Kims of Chapter 1. Here R₁ ∩ R₂ = {B} and B⁺ = {B}: the test says lossy.

3. The chase test (book §3.4.2)

For a decomposition into more than two relations, or when you want a proof you can draw, use the chase. Suppose R is decomposed into S₁, …, Sₖ with FDs F. The join always contains every tuple of R; the question is whether a tuple t in the join must already be in R.

Tableau
A table with one row per relation Sᵢ. Write t = (a, b, c, …). Row i has the plain letter (a, b, …) in the columns of Sᵢ, because the tuple of R that produced t's projection onto Sᵢ agrees with t there, and a subscripted letter (b₁, c₁, …) everywhere else, standing for unknown values.
Chasing
Apply each FD X → A to the tableau: if two rows agree on all of X, make their A-symbols equal. If one of the two symbols is a plain letter, use it; otherwise pick either. Replace every occurrence in that column.
Result
If some row becomes all plain letters (equal to t), then t was in R: the join is lossless. If no FD can change anything and no row is all plain, the join is lossy, and the final tableau itself is a counterexample instance.

Book Example 3.23: lossless

R(A, B, C, D) decomposed into {A, D}, {A, C}, {B, C, D}, with A → B, B → C, CD → A.

In words: rows 1 and 2 agree on A, so A → B makes b₂ = b₁. Now they agree on B, so B → C makes c₁ = c (plain wins). Rows 1 and 3 now agree on C and D, so CD → A makes a₃ = a. Row 3 becomes (a, b, c, d): lossless.

Book Example 3.24: lossy

R(A, B, C, D) with B → AD, decomposed into {A, B}, {B, C}, {C, D}. Rows 1 and 2 agree on B, so a₂ = a and d₁ = d₂. Nothing else applies, and no row is all plain: lossy. Read the final tableau as a three-tuple instance: it satisfies B → AD, but projecting and rejoining produces (a, b, c, d), which is not one of its rows. Try it: enter A B C D, B -> AD, AB; BC; CD.

DB QB · 19-20 8c · 5 marks  |  BUET QBank · CSE 215 | L-2/T-2 | 2019–20 · 10 marks

Suppose that we decompose the schema R = (A, B, C, D, E) into (A, B, C) and (A, D, E). Show whether this decomposition is a lossless decomposition or not if the following set F of functional dependencies holds: A → BC, CD → E, B → D, E → A.

Show worked answer

Two-relation test. R₁ ∩ R₂ = {A}. A⁺: A → BC adds B, C; B → D adds D; CD → E adds E. A⁺ = {A, B, C, D, E}, which contains R₁ = {A, B, C} (and R₂). So A → R₁ holds: the common attribute is a key of R₁, and the decomposition is lossless.

Same result with the chase:

Rows agree on A, so A → B makes b₂ = b and A → C makes c₂ = c; row 2 becomes (a, b, c, d, e), all plain. Lossless.

Summary: a decomposition is lossless if joining the pieces returns exactly R. Every original tuple always comes back; the danger is extra tuples. A two-way split is lossless iff the common attributes determine all of one piece, which BCNF splits guarantee (X is a key of X⁺). For any number of pieces use the chase: one tableau row per piece, equate symbols with the FDs, and the join is lossless iff some row becomes all plain letters.
