Why We Need Design Theory: Redundancy and Decomposition

A relation that stores too much in one place repeats facts. This chapter shows the problem on the slides' teacher table, fixes it by splitting the table, and then shows a split that goes wrong and invents tuples that never existed.

1. Two ways to design a database (slide 2)

Before a database holds any data, someone has to decide which tables (relations) exist and which columns (attributes) each one has. The slides describe two routes:

  • Intermediate design. First draw a high-level picture of the data, such as an ER diagram (entities, attributes, relationships), and then convert that picture into relations.
  • Straight approach. Read the requirements and write down relations directly. The slides mark this as not recommended, because it is easy to miss structure.

Both routes share one weakness: the first relation schemas you get can contain redundancy. The usual cause is a relation that tries to hold too much information, such as facts about teachers and facts about departments in one table. Design theory is the set of tools that detects this and repairs it. Its main tool is the functional dependency (Chapter 2).

Relation schema
The name of a relation and its list of attributes, for example teacher_in_dept(ID, name, salary, dept_name, building, budget). A relation instance is the set of tuples (rows) stored in it at one moment.
Redundancy
The same fact stored more than once. Every copy must be kept identical, and that is where errors creep in.

2. Redundancy on a real table (slide 3)

The slide's relation records each teacher together with the building and budget of the teacher's department:

A department's building and budget belong to the department, not to any teacher. Yet the table repeats them in every row of every teacher in that department. With 50 CSE teachers, the same building and budget would appear 50 times. If the budget changes, all 50 copies must change together. Chapter 9 names the problems this causes (update, insertion and deletion anomalies).

3. The fix: decompose into two relations (slide 4)

The slides split the table into two smaller relations, each about one thing:

teacher(ID, name, salary, dept_name)   department(dept_name, building, budget)

The two relations share the attribute dept_name. Each department's building and budget is now stored once. To answer a question that needs both, such as “which building does Rahim Ahmed work in?”, we put the tables back together with a natural join: pair every teacher row with the department row that has the same dept_name.

Decomposition
Replacing a relation R by two or more relations whose attribute sets together cover all of R's attributes. Each new relation holds the projection of R's tuples onto its attributes.
Natural join (R ⋈ S)
Combine every tuple of R with every tuple of S that has equal values on all attributes the two relations share.
Lossless decomposition
A decomposition where the natural join of the pieces gives back exactly the original relation: no tuple lost, no tuple added.

The slide states the condition that made this work: the common attribute must be a key of at least one of the decomposed relations. Here dept_name is a key of department: no two department rows share a dept_name. So each teacher row matches exactly one department row in the join, and the join rebuilds each original tuple and nothing else. (A key is defined precisely in Chapter 3. For now: a set of attributes whose values identify a single row.)

4. A bad decomposition (slide 5)

Not every split is safe. The slide's example decomposes

employee(ID, name, street, city, salary)  →  (ID, name)  and  (name, street, city, salary)

The common attribute is name, and name is not a key of either piece: two different employees are both called Kim. Watch what the join does:

The original relation had two tuples. The join of the pieces has four. Two of them, (57766, Kim, North, Hampton, 67000) and (98776, Kim, Main, Perryridge, 75000), never existed. Since both pieces are consistent with either version of the data, no algorithm can tell which Kim lives where. We got more tuples, but we have lost information: the link between each ID and its address. This is a lossy decomposition.

Lossy decomposition
A decomposition whose natural join produces tuples that were not in the original relation (called spurious tuples), so the original cannot be reconstructed.

Why does the teacher split work while the employee split fails?

In the teacher split, the shared attribute dept_name determines a single department row, so each teacher row can join with exactly one partner. In the employee split, the shared attribute name determines nothing: the value Kim appears with two different addresses, so each Kim row from the left piece joins with both Kim rows from the right piece. 2 × 2 = 4 joined tuples. The general rule (made precise in Chapter 12): a two-way split R₁, R₂ is lossless when the common attributes R₁ ∩ R₂ functionally determine all of R₁ or all of R₂.

The rest of the lecture builds the tools to make these decisions mechanically: functional dependencies (what determines what), keys, closures, and normal forms (BCNF and 3NF) that say when a relation needs splitting and how to split it without loss.

Practice

Key terms

Quick check

Summary: a relation that mixes facts about several things (teachers and departments) stores some facts many times. That redundancy is removed by decomposing the relation into smaller ones and rejoining them with a natural join when needed. A decomposition must be lossless: the join must return exactly the original tuples. It is safe when the shared attributes form a key of one of the pieces; when they do not (two employees named Kim), the join invents spurious tuples.
