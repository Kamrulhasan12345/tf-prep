First, Second and Third Normal Form, Step by Step

The classic ladder: atomic values (1NF), no partial dependencies (2NF), no transitive dependencies (3NF). This chapter explains each rung with the slides' examples, connects it to the FD-based definitions of earlier chapters, and provides a normal-form checker.

1. First normal form (slide 62)

1NF
Every attribute value is atomic (indivisible): each cell of the table holds one value.
  • Lists, sets and groups are not allowed. Several phone numbers in one phone attribute break 1NF.
  • Composite values are not allowed when the business needs their parts. If queries need the city or postcode of an address separately, a single address attribute is not acceptable; store city, country, postcode as separate attributes. The slide notes this is not a rigid rule: if nobody ever needs the parts, one address string is fine.

The textbook (box “Other Normal Forms”) agrees: 1NF is “simply the condition that every component of every tuple is an atomic value”. Every relation in the relational model is assumed to be in 1NF; the higher normal forms are all about FDs.

2. Second normal form (slide 63)

Non-key (non-prime) attribute
An attribute that is not part of any key.
Partial dependency
A non-key attribute is determined by a proper part of a composite key (not the whole key).
2NF
1NF, and for every FD X → Y where Y is a non-key attribute, X is not a proper subset of a key. “Every non-key attribute must depend on the whole key.”

Slide 63's example: CUSTOMER(Cust_ID, Name, Order_ID) with key {Order_ID, Cust_ID}. Name depends on Cust_ID alone, a part of the key: a partial dependency, so not 2NF. The second example: Registration(student_id, course_id, course_name), key {student_id, course_id}, FD course_id → course_name.

The fix: move the partially dependent attributes into a new relation keyed by the part of the key they depend on. A relation whose keys are all single attributes is automatically in 2NF (a single attribute has no proper non-empty part).

3. Third normal form, classic form (slide 64)

Transitive dependency
A non-key attribute determines another non-key attribute, so the second depends on the key only through the first: key → A → B.
3NF (slide 64)
2NF, and for every FD X → Y where Y is a non-key attribute, X is a superkey. “Every non-key attribute must depend on the key, the whole key, and nothing but the key.”

This is the same as the definition of Chapter 14 (left side a superkey, or right side prime), stated for non-prime right sides. Slide 64's examples: EMPLOYEE(Emp_ID, F_Name, L_Name, Dept_ID, Dept_Name) with Dept_ID → Dept_Name; and Student(student_id, home_town, home_country) with key student_id and home_town → home_country.

4. The ladder, and a checker

FormForbidsFix
1NFnon-atomic values (sets, lists, needed composites)one value per cell; repeating groups to their own relation
2NFnon-prime attribute determined by part of a keymove it out with that part of the key
3NFnon-prime attribute determined by a non-superkeymove it out with its determinant
BCNFany nontrivial FD with a non-superkey left sideBCNF decomposition (Chapter 11)

Each form includes the ones above it: BCNF ⊂ 3NF ⊂ 2NF ⊂ 1NF. One subtlety: the slides' definitions say “a key”, meaning any candidate key. Some textbooks (Connolly & Begg) first define 2NF and 3NF with respect to the primary key only and then generalize. When a relation has several candidate keys, use the general version, as the checker below does.

DB QB · Jan 20 8 (Q63 and Q73) · 10 marks  |  BUET QBank · CSE 215 | L-2/T-2 | 2018–19 · 10 marks

Suppose we are generating a StaffPropertyInspection table to include property inspection by staff members. When the staffs are required to undertake the inspections, they are allocated a company car for use on the day of the inspections. However, a car may be allocated to several staff members on the same day at different time slots. A member of staff may inspect several properties on a given date, but a property is only inspected once by a single staff member on a given date. Now normalize the Table StaffPropertyInspection of the following figure up to 2NF. Hint: you have to perform and only show the results of the following steps: i) Find all the candidate keys. ii) Determine the primary key. iii) Find all the functional dependencies. iv) Get the first normal form. v) Get the second normal form.

Show worked answer

(iii) Functional dependencies (from the rules and the data):

  • fd1: propertyNo iDate → iTime comments staffNo carReg (a property is inspected once, by one staff member, on a date)
  • fd2: propertyNo → pAddress (a property has one address)
  • fd3: staffNo → sName
  • fd4: staffNo iDate → carReg (a staff member gets one car for the day)
  • fd5: carReg iDate iTime → propertyNo comments staffNo (a car is used by one staff member in a time slot, who is at one property)
  • fd6: staffNo iDate iTime → propertyNo comments (a staff member is at one property at a given time)

The data agrees: SG14 on 22-Apr-01 has car M533 HDR in both rows (fd4); PG4's address is the same in all three rows (fd2).

(i) Candidate keys. iDate appears on no right side, so it is in every key. Closures (checked with the key finder): {propertyNo, iDate}⁺ = all attributes (fd1, fd2, fd3). {staffNo, iDate, iTime}⁺ = all (fd6, fd2, fd3, fd4). {carReg, iDate, iTime}⁺ = all (fd5, then the rest). No proper subset of these works, so the candidate keys are {propertyNo, iDate}, {staffNo, iDate, iTime} and {carReg, iDate, iTime}.

(ii) Primary key: {propertyNo, iDate}: the shortest, and it names what the table is about (an inspection of a property on a date).

(iv) 1NF. The table as given has one value per cell and a primary key, so it is already in 1NF: StaffPropertyInspection(propertyNo, iDate, iTime, pAddress, comments, staffNo, sName, carReg). (If the property data had been written once with several inspections nested under it, we would first flatten it into this form.)

(v) 2NF. Prime attributes: propertyNo, iDate, iTime, staffNo, carReg. Non-prime: pAddress, comments, sName. Partial dependencies:

  • propertyNo → pAddress: propertyNo is part of the key {propertyNo, iDate}.
  • staffNo → sName: staffNo is part of the key {staffNo, iDate, iTime}.

(staffNo iDate → carReg does not count: carReg is prime.) Remove both:

  • Property(propertyNo, pAddress)
  • Staff(staffNo, sName)
  • PropertyInspection(propertyNo, iDate, iTime, comments, staffNo, carReg)

Note: the CSE 215 bank's answer removes only propertyNo → pAddress and keeps sName in PropertyInspection. That is 2NF with respect to the primary key alone (Connolly & Begg's first definition). With the slides' definition (“X cannot be a proper subset of a key”), staffNo → sName is also a partial dependency, on the candidate key {staffNo, iDate, iTime}, so Staff must be split off as well. Under the bank's reading, staffNo → sName is removed one step later, as a transitive dependency in 3NF.

Summary: 1NF: atomic values. 2NF: no non-key attribute depends on part of a key. 3NF: no non-key attribute depends on anything but a superkey (no transitive dependency). In each step the fix is to move the offending attributes, with their determinant, into a new relation. Check against all candidate keys, not just the primary key.
