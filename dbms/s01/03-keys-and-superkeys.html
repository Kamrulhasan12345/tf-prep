Keys, Superkeys and Primary Keys

A key is a smallest set of attributes that pins down a whole tuple. This chapter states the two conditions, proves the slides' claim that {title, year, starName} is the key of Movies1, separates keys from superkeys and primary keys, and shows how to count superkeys, a frequent exam question.

1. Definition of a key (slide 15)

Key
A set of one or more attributes {A₁, A₂, …, Aₙ} is a key of relation R if
Condition 1 (uniqueness): A₁, …, Aₙ functionally determine all other attributes of R. Equivalently, two distinct tuples of R cannot agree on all of A₁, …, Aₙ.
Condition 2 (minimality): no proper subset of {A₁, …, Aₙ} functionally determines all other attributes. Remove any attribute and the key property is lost.

Why are the two forms of condition 1 the same? If X determines every other attribute, two tuples that agree on X agree everywhere, so they are the same tuple (a relation is a set, so it has no duplicate tuples). So distinct tuples must differ somewhere in X.

For Movies1(title, year, length, genre, studioName, starName) the slides claim: {title, year, starName} is a key.

2. Proving the claim (slides 16–17)

A key proof always has two parts, one per condition.

Step 1: {title, year, starName} determines every other attribute. Suppose two tuples agree on title, year and starName. Since they agree on title and year, the FD title year → length genre studioName (Chapter 2) says they also agree on length, genre and studioName. Now they agree on all six attributes.

Step 2: no proper subset works. It is enough to check the three subsets with two attributes, because a smaller set cannot determine more than a bigger set containing it:

  • {title, year} does not determine starName: the same movie has several stars (the three Star Wars rows).
  • {title, starName} does not determine year: two movies with the same title and the same star may be made in different years (a remake). The slide writes “startName”; it means starName.
  • {year, starName} does not determine title: a star can appear in two different movies in the same year.

Both conditions hold, so {title, year, starName} is a key. In fact it is the only key: every key must contain starName (nothing else determines it), and must contain title and year (nothing determines them). Chapter 6 turns this kind of reasoning into an algorithm.

3. Primary keys and superkeys (slides 18–19)

Primary key
A relation can have more than one key. The designer picks one of them as the primary key. The choice is up to the designer and usually follows practical concerns (section 5).
Superkey
Any set of attributes that contains a key (a superset of a key). It satisfies condition 1 but need not satisfy condition 2.
Candidate key
Another name for “key”, used in Korth (Silberschatz) and many exams. The slides and Garcia-Molina just say “key”.

So every key is a superkey (a set contains itself), but not every superkey is a key. Slide 19's example for Movies1: the primary key is {title, year, starName}, and {title, year, starName, length} is a superkey that is not a key, because dropping length still leaves a superkey. The book adds that the term key always means minimal; if you mean “unique but maybe not minimal”, say superkey.

4. Counting superkeys

Because a superkey is “any set containing a key”, counting superkeys is counting subsets, a classic exam question. Let R have n attributes A₁, …, Aₙ.

  • One key K with k attributes: a superkey must contain all of K, and each of the other n − k attributes is in or out freely. Count = 2n−k.
  • Several keys: use inclusion–exclusion. For keys K₁ and K₂: |sets ⊇ K₁| + |sets ⊇ K₂| − |sets ⊇ K₁ ∪ K₂| = 2n−|K₁| + 2n−|K₂| − 2n−|K₁∪K₂|.

For Figure 1 (n = 3, keys {A} and {B, C}): 2² + 2¹ − 2⁰ = 4 + 2 − 1 = 5. The figure shows exactly 5.

5. Choosing a primary key

When several keys exist, good practice is to pick one that is:

  1. Never null and always known when the tuple is created (a student ID is known at admission; an email may not be).
  2. Stable: its value should never change, because other tables refer to it (foreign keys). Names and phone numbers change; IDs do not.
  3. Small and simple: one short attribute is cheaper to index, store in foreign keys and compare than a long composite one. That is why systems often add a surrogate key (an auto-numbered ID).
  4. Minimal and meaningful to the business: it must really be unique by the rules of the organization, not just in today's data.

DB QB · 24-25 7c · 9 marks

Define super key, candidate key and primary key with examples.

Show worked answer

Use Movies1(title, year, length, genre, studioName, starName) with the FD title year → length genre studioName, and a second relation Student(studentID, email, name, dept) where studentID and email are each unique.

Superkey: a set of attributes whose values identify a tuple uniquely, i.e. it functionally determines every attribute of the relation. It need not be minimal. Examples: {title, year, starName}, {title, year, starName, length}, and the set of all six attributes are superkeys of Movies1. In Student, {studentID}, {email}, {studentID, name} are superkeys.

Candidate key (the slides' “key”): a minimal superkey: it determines all attributes, and no proper subset does. Movies1 has one candidate key, {title, year, starName}: drop title, year or starName and uniqueness fails (shown in section 2). Student has two candidate keys, {studentID} and {email}. {studentID, name} is a superkey but not a candidate key, since {studentID} alone suffices.

Primary key: the one candidate key the designer chooses to identify tuples (and that foreign keys refer to). In Student we would choose {studentID} as primary key because it is short, stable and never null; {email} remains an alternate key. In Movies1 the only candidate key {title, year, starName} is the primary key.

Relationship: every primary key is a candidate key, and every candidate key is a superkey; the converses are false.

DB QB · 24-25 1a · 3 marks  |  BUET QBank · CSE 215 | L-2/T-1 | 2024–25 · 8 marks

Suppose R is a relation with attributes A₁, A₂, …, Aₙ. As a function of n, determine how many superkeys R has for each of the following cases: (i) The only key is A₁. (ii) The only keys are {A₁, A₂} and {A₁, A₃}.

Show worked answer

(i) A superkey is any set that contains a key. The only key is {A₁}, so a superkey is A₁ plus any subset of the other n − 1 attributes: 2n−1 superkeys.

(ii) A superkey contains {A₁, A₂} or {A₁, A₃}. Inclusion–exclusion:

  • sets containing {A₁, A₂}: 2n−2
  • sets containing {A₁, A₃}: 2n−2
  • sets containing both, i.e. {A₁, A₂, A₃}: 2n−3 (counted twice above)

Total = 2n−2 + 2n−2 − 2n−3 = 2n−1 − 2n−3 = 3 · 2n−3 (for n ≥ 3).

Check with n = 3: the superkeys are {A₁A₂}, {A₁A₃}, {A₁A₂A₃}: 3 = 3 · 2⁰. ✓ (Verified by brute force for n = 3…6: 3, 6, 12, 24.)

BUET QBank · CSE 303 | L-3/T-1 | 2015–16 · 6 marks

Suppose R is a relation with attributes A₁, A₂, …, Aₙ. As a function of n, find how many superkeys R has if the only keys are {A₁} and {A₂, A₃}.

Show worked answer
  • sets containing {A₁}: 2n−1
  • sets containing {A₂, A₃}: 2n−2
  • sets containing both, {A₁, A₂, A₃}: 2n−3

Total = 2n−1 + 2n−2 − 2n−3 = (4 + 2 − 1) · 2n−3 = 5 · 2n−3 (n ≥ 3). For n = 3 this is 5, matching Figure 1 (with A = A₁, B = A₂, C = A₃). Brute force for n = 4, 5, 6 gives 10, 20, 40. ✓

BUET QBank · CSE 303 | L-3/T-1 | 2013–14 · 12 marks

Which considerations should be applied while choosing the primary key of a relation? Discuss with example how the multi-valued attribute problem in database design can be solved.

Show worked answer

Choosing a primary key. The primary key must first be a candidate key (unique and minimal). Among candidate keys choose one that is (1) never null, known as soon as the tuple is created; (2) stable, never updated, because foreign keys in other relations copy it; (3) small and simple, ideally one short attribute, since it is stored in every index and every referencing table; (4) unique by business rule, not by accident of current data. Example: in Student(studentID, email, phone, name), both studentID and email may be unique, but email can change and phone can be shared or missing, so studentID is the better primary key. If no natural key is good, add a surrogate key (an auto-increment ID).

Multivalued attributes. A multivalued attribute holds a set of values, such as a department with several locations, or a student with several phone numbers. Storing the set in one cell, e.g. Dlocations = {Bellaire, Sugarland, Houston}, violates first normal form (atomic values, Chapter 16), and makes queries like “departments in Houston” and updates of one location awkward. The fix (slide 62's example) is to move the multivalued attribute into its own relation together with the key of the owner:

Before (not 1NF)After
DEPARTMENT(Dname, Dnumber, Dmgr_ssn, Dlocations) with Research, 5, 333445555, {Bellaire, Sugarland, Houston} DEPARTMENT(Dname, Dnumber, Dmgr_ssn)
DEPT_LOCATIONS(Dnumber, Dlocation): (5, Bellaire), (5, Sugarland), (5, Houston), (4, Stafford), (1, Houston)

The key of DEPT_LOCATIONS is {Dnumber, Dlocation}, one row per (department, location) pair, and Dnumber is a foreign key to DEPARTMENT. Each value is now atomic and a location can be added or removed by inserting or deleting one row.

Summary: a key determines every attribute (uniqueness) and is minimal (no proper subset works). Prove both parts: show agreement on the key forces agreement everywhere, then break each smaller subset. A superkey is any superset of a key, so the number of superkeys is a subset count: 2n−k for one k-attribute key, inclusion–exclusion for several. The primary key is the candidate key the designer chooses, preferably stable, non-null and small.
