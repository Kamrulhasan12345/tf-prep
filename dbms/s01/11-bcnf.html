Boyce-Codd Normal Form and BCNF Decomposition

BCNF is the condition that guarantees the anomalies of Chapter 9 cannot occur: every nontrivial FD must have a superkey on its left. This chapter tests Movies1 and Movies2, proves that two-attribute relations are always in BCNF, runs the BCNF decomposition algorithm on the slides' studio example as a tree, and works eight exam questions.

1. Definition (slide 45)

Boyce-Codd Normal Form (BCNF)
A relation R is in BCNF if and only if, whenever A₁A₂…Aₙ → B₁B₂…Bₘ is a nontrivial FD that holds on R, {A₁, A₂, …, Aₙ} is a superkey of R. In short: the left side of every nontrivial FD is a superkey. Equivalently: the left side of every nontrivial FD contains a key.
BCNF violation
A nontrivial FD X → Y on R whose left side X is not a superkey.

Why this kills anomalies: an FD X → Y with X not a superkey means several tuples can share the same X-value, and each of them repeats the same Y-value. That repetition is the redundancy behind every anomaly. If X is a superkey, only one tuple has each X-value, so there is nothing to repeat.

Test for a violation (slide 45): for each nontrivial FD X → Y, compute X⁺. If X⁺ contains every attribute of R, X is a superkey and the FD is fine; otherwise the FD violates BCNF.

Which FDs must be checked? For the original relation R with its given FD set F, checking the FDs of F is enough: if no FD in F violates BCNF, no FD that follows from F does either. For a relation produced by decomposition, check the projected FDs (Chapter 10), because a violation can hide in an FD that is not in the original list.

2. Movies1 and Movies2 (slides 46–47)

Movies1: not in BCNF

Only key: {title, year, starName}. The FD title year → length genre studioName is nontrivial, and {title, year}⁺ = {title, year, length, genre, studioName} lacks starName. So {title, year} is not a superkey: BCNF violation.

Movies2: in BCNF

Movies2(title, year, length, genre, studioName) has only key {title, year}. Its nontrivial FDs all have title and year on the left (neither alone determines anything), so every left side is a superkey: BCNF. Movies3(title, year, starName) has no nontrivial FDs at all, so it is in BCNF too.

Every two-attribute relation is in BCNF (book Example 3.17)

Let R(A, B). A nontrivial FD must have one attribute on each side, so the only candidates are A → B and B → A. Four cases:

  1. Neither holds: there are no nontrivial FDs, nothing can violate BCNF ({A, B} is the key).
  2. Only A → B holds: A is the key, and the only nontrivial FD has A on the left.
  3. Only B → A holds: symmetric, B is the key.
  4. Both hold: A and B are both keys, so either left side is a superkey.

In every case each nontrivial FD has a superkey on its left. This is why the decomposition below always terminates: pieces only get smaller, and pieces of size 2 are automatically in BCNF.

3. The BCNF decomposition algorithm (slide 48)

BCNF_decompose(R, S):                         -- "BCNF analysis"
  Step 1. If R is in BCNF, return {R}.
  Step 2. Let X → Y be a BCNF violation. Compute X⁺.
            R₁ := X⁺                         (X and everything it determines)
            R₂ := X ∪ (R − X⁺)                (X and everything it does not)
  Step 3. Project S onto R₁ and onto R₂, giving S₁ and S₂ (Chapter 10).
  Step 4. Recursively decompose (R₁, S₁) and (R₂, S₂); return the union.

Using all of X⁺ (rather than just Y) for R₁ is optional, but the textbook recommends it: it moves everything X determines at once and usually saves later steps.

4. Slides 49–50: the studio example

Relation {title, year, studioName, president, presAddr}: each movie, its studio, the studio's president and the president's address. FDs:

title year → studioName   studioName → president   president → presAddr

  • Closing sets shows the only key is {title, year}. The last two FDs violate BCNF.
  • Take studioName → president. {studioName}⁺ = {studioName, president, presAddr}. Split into R₁ = {studioName, president, presAddr} and R₂ = {title, year, studioName}.
  • Projected FDs: on R₂, title year → studioName; key {title, year}; BCNF. On R₁, studioName → president and president → presAddr; key {studioName}; president → presAddr violates BCNF.
  • Split R₁ on president → presAddr: R₃ = {president, presAddr}, R₄ = {studioName, president}.
  • Final: {title, year, studioName}, {studioName, president}, {president, presAddr}. All in BCNF.

Slide 50 errata: it writes “S₁ = {title yaer → studioName} and S₂ = {studioName → president, …}” (the second set runs off the edge of the slide). The labels are swapped: S₁ belongs to R₁ = {studioName, president, presAddr}, so S₁ = {studioName → president, president → presAddr}, and S₂ = {title year → studioName} belongs to R₂. “yaer” means year.

DB QB · 21-22 3c · 10 marks  |  BUET QBank · CSE 215 | L-2/T-2 | 2021–22 · 20 marks

Consider a relation with schema R(A, B, C, D, E) and FD's AB → C, DE → C, and B → D. Decompose the relations, as necessary, into collections of relations that are in BCNF. Show your work, and the final normalized schema including all keys.

Show worked answer

Key. A and E appear on no right side, so they are in every key. (AE)⁺ = {A, E}. Add B: (ABE)⁺: B → D, AB → C → {A, B, C, D, E}. Adding C or D instead: (ACE)⁺ = {A, C, E}, (ADE)⁺ = {A, C, D, E} (DE → C), neither complete; (ACDE)⁺ = ACDE. So the only key is ABE.

Violations. AB⁺ = ABCD, DE⁺ = CDE, B⁺ = BD: none is a superkey, so all three given FDs violate BCNF.

Split 1 on AB → C. (AB)⁺ = {A, B, C, D}. R₁ = ABCD, R₂ = AB ∪ (R − ABCD) = ABE.

  • R₂(A, B, E): projected FDs: none nontrivial (no subset of ABE determines another attribute of ABE). Key ABE. BCNF.
  • R₁(A, B, C, D): projected FDs: AB → C, B → D (DE → C needs E, which is not in R₁). Key AB. B → D violates BCNF (B⁺ = BD).

Split 2 of R₁ on B → D: B⁺ ∩ R₁ = {B, D}. R₃ = BD, R₄ = B ∪ (ABCD − BD) = ABC. R₃: B → D, key B. R₄: AB → C, key AB. Both BCNF.

Final schema: R₂(A, B, E), R₃(B, D), R₄(A, B, C). (Keys underlined.) The decomposition is lossless. It is not dependency preserving: DE → C cannot be checked in any piece (no piece contains D, E and C together). Splitting on B → D first and then on AB → C gives the same three relations; choosing the derived violation BE → C instead would give BD, BCE, ABE, which is also a correct BCNF decomposition.

BUET QBank · CSE 303 | L-3/T-1 | 2015–16 · 10 marks

For the relation schema R(A, B, C, D, E) with FDs AB → C, DE → C, and B → D: (a) Indicate all the BCNF violations. (b) Decompose the relations, as necessary, into a collection of relations that are in BCNF.

Show worked answer

Only key: ABE (previous question). A violation is any nontrivial X → A (single attribute on the right) that follows from the FDs with X not a superkey, i.e. X not containing A, B and E together.

(a) Closing every subset that is not a superkey gives 12 violations:

B→D, AB→C, AB→D, BC→D, BE→C, BE→D, DE→C, ABC→D, ABD→C, BCE→D, ADE→C, BDE→C

The three given FDs and the derived BE → C (BE⁺ = BCDE via B → D, DE → C) are the essential ones; the rest add extra attributes to these left sides.

Note: the CSE 303 bank's answer lists only the three given FDs (AB → C, DE → C, B → D). They are violations, but the list is incomplete: the derived BE → C (and the other FDs above) also violate BCNF, since BE⁺ = BCDE is not all of R.

(b) Same decomposition as the previous question: BD (key B), ABC (key AB), ABE (key ABE). All three are in BCNF; DE → C is not preserved.

DB QB · 20-21 7a + 7b · 10 + 10 marks  |  BUET QBank · CSE 215 | L-2/T-2 | 2020–21 · 20 marks

(a) Find all functional dependencies that hold on this table. You only need to write a minimal set of functional dependencies that logically imply all others. (b) Using the functional dependencies you have identified, decompose the relation in BCNF. Show your work, and the final normalized schema including all keys.

Show worked answer

(a) Look for rules that the meaning of the columns guarantees and that the instance does not contradict (Chapter 2: an instance can refute an FD but cannot prove one).

  • FirstName → FirstInitial: an initial is the first letter of the name.
  • LastName → LastInitial.
  • FirstName LastName → FullName and FullName → FirstName LastName: the full name is the two names joined, and can be split back.
  • FullName → FullAddress: each person in the table has one address (no full name repeats with two addresses).
  • FullAddress → ZipCode: the zip code is part of the address.

FDs that fail on the instance: FullAddress ↛ FullName (two people at 45h St), ZipCode ↛ FullAddress (98185 appears with two addresses), LastName ↛ FirstName (two Levys). One FD holds on these five rows only by accident: FirstInitial → FirstName (A, B, C each happen to belong to one first name); a future “Adam” would break it, so it is not included. The six FDs above are a minimal basis (none follows from the others, no left side can shrink). Keys: {FullName} and {FirstName, LastName}.

(b) Violations: FirstName → FirstInitial, LastName → LastInitial, FullAddress → ZipCode (none of these left sides is a superkey).

  1. Split on FirstName → FirstInitial: R₁(FirstName, FirstInitial) and R₂ = everything except FirstInitial.
  2. R₂ still has LastName → LastInitial: split into R₃(LastName, LastInitial) and R₄(FirstName, LastName, FullName, FullAddress, ZipCode).
  3. R₄ has FullAddress → ZipCode (FullAddress is not a superkey of R₄): split into R₅(FullAddress, ZipCode) and R₆(FirstName, LastName, FullName, FullAddress).
  4. R₆: FDs FullName → FirstName LastName FullAddress and FirstName LastName → FullName FullAddress. Keys {FullName} and {FirstName, LastName}; every left side is a key: BCNF.

Final: R₁(FirstName, FirstInitial), R₃(LastName, LastInitial), R₅(FullAddress, ZipCode), R₆(FullName, FirstName, LastName, FullAddress) with alternate key {FirstName, LastName}. Lossless and, here, dependency preserving (every FD lies inside one piece).

DB QB · 17-18 7b · 15 marks  |  BUET QBank · CSE 215 | L-2/T-2 | 2017–18 · 15 marks  |  BUET QBank · CSE 303 | L-3/T-1 | 2011–12 · 15 marks

The following schema has been designed for an address book application: R(SSN, Name, PhoneType, PhoneNumber). A person can have different types of phone numbers (e.g. Mobile, Home or Office). The following set F of functional dependencies hold on R: SSN → Name; SSN, PhoneType → PhoneNumber; SSN, PhoneType → Name; PhoneNumber → SSN, Name, PhoneType. (i) What are the keys for R? (ii) Is R in BCNF? Why or why not? (iii) Decompose R into BCNF (if it is already not in BCNF).
2011–12 version adds: Can you remove any dependency without violating equivalency of F?

Show worked answer

(i) Keys. PhoneNumber⁺ = {PhoneNumber, SSN, Name, PhoneType}: everything, and a single attribute is minimal, so {PhoneNumber} is a key. (SSN, PhoneType)⁺ = {SSN, PhoneType, PhoneNumber, Name}: everything. SSN⁺ = {SSN, Name} and PhoneType⁺ = {PhoneType} are not, so {SSN, PhoneType} is a key. Any other key would have to avoid PhoneNumber and contain SSN and PhoneType, so these are the only two.

(ii) Not in BCNF. SSN → Name is nontrivial and SSN⁺ = {SSN, Name} is not all of R, so SSN is not a superkey. (The other three FDs have superkeys on the left.) The consequence: a person's name is repeated once per phone.

(2011–12, can a dependency be removed?) Yes. SSN, PhoneType → Name follows from SSN → Name (left augmentation), so it can be removed. Also Name can be dropped from the right side of PhoneNumber → SSN, Name, PhoneType, since PhoneNumber → SSN and SSN → Name give it. A minimal basis: SSN → Name, SSN PhoneType → PhoneNumber, PhoneNumber → SSN, PhoneNumber → PhoneType.

(iii) Split on SSN → Name: SSN⁺ = {SSN, Name}.

  • R₁(SSN, Name), FD SSN → Name: BCNF.
  • R₂(SSN, PhoneType, PhoneNumber), FDs SSN PhoneType → PhoneNumber and PhoneNumber → SSN PhoneType. Keys {SSN, PhoneType} and {PhoneNumber}; both left sides are keys: BCNF.

Lossless (common attribute SSN is the key of R₁) and dependency preserving.

BUET QBank · CSE 303 | L-3/T-1 | 2012–13 · 15 marks

Suppose that we have a schema R = (A, B, C, D) with functional dependencies: B → C, D → A. List the keys of R. Is R in BCNF? If not, convert R to BCNF.

Show worked answer

Keys. B and D appear on no right side, so they are in every key. (BD)⁺ = {B, D, C, A} = R. The only key is BD.

BCNF? No. B⁺ = {B, C} and D⁺ = {A, D}; neither B nor D is a superkey, so both B → C and D → A violate BCNF.

Decompose. On B → C: R₁(B, C), R₂(A, B, D). R₂ has D → A with key BD: violation. Split R₂ on D → A: R₃(D, A), R₄(B, D).

Final: (B, C), (D, A), (B, D), all in BCNF, lossless and dependency preserving. R₄(B, D) stores which B goes with which D; without it the join would lose that pairing.

BUET QBank · CSE 303 | L-3/T-1 | 2015–16 · 7 marks

Prove that any two-attribute relation is in BCNF.

Show worked answer

Let R(A, B). A nontrivial FD has a right side that is not contained in its left side. With only two attributes, a nontrivial FD must have one attribute on the left and the other on the right (a left side {A, B} would make every right side trivial). So the only possible nontrivial FDs are A → B and B → A.

  1. Neither holds: no nontrivial FD exists, so no violation is possible.
  2. Only A → B holds: then A⁺ = {A, B}, A is a key, and the only nontrivial FD has the superkey A on the left.
  3. Only B → A holds: symmetric; B is a key.
  4. Both hold: A and B are both keys, so the left side of each FD is a superkey.

In all cases every nontrivial FD has a superkey on its left, so R is in BCNF. ∎

BUET QBank · CSE 303 | L-3/T-1 | 2010–11 · 10 marks

Describe the BCNF decomposition algorithm.

Show worked answer

Input: relation R₀ with FD set S₀. Output: a set of relations, each in BCNF, whose natural join is R₀ (lossless). Apply recursively to (R, S), starting with (R₀, S₀):

  1. Check whether R is in BCNF: for each nontrivial FD X → Y in S, compute X⁺; if X⁺ ⊇ R for all of them, return {R}.
  2. Otherwise take a violation X → Y. Compute X⁺. Let R₁ = X⁺ and R₂ = X ∪ (R − X⁺).
  3. Compute the projected FD sets S₁ on R₁ and S₂ on R₂ (close each subset of the piece with S and keep FDs inside the piece).
  4. Recursively decompose (R₁, S₁) and (R₂, S₂); return the union of the results.

Termination: each piece has fewer attributes than R (R₁ lacks R − X⁺, which is nonempty since X is not a superkey; R₂ lacks X⁺ − X, which is nonempty since the FD is nontrivial), and a two-attribute relation is always in BCNF. Lossless: X is a key of R₁ and X = R₁ ∩ R₂, so each tuple of R₂ joins with exactly one tuple of R₁. Drawback: dependencies may not be preserved (Chapter 13). Example: the studio relation above, which splits into {title, year, studioName}, {studioName, president}, {president, presAddr}.

Summary: R is in BCNF when every nontrivial FD has a superkey on its left; test each FD with a closure (use projected FDs for decomposed pieces). Every two-attribute relation is in BCNF. To decompose, pick a violation X → Y and split R into X⁺ and X ∪ (R − X⁺), project the FDs, and repeat on each piece. The result is lossless but may lose dependencies.
