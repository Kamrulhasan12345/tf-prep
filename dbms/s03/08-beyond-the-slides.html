Exam Topics Beyond the Slides

Past concurrency-control papers also ask about three things Lec 02–03's slides do not teach: strict two-phase locking and cascading rollback, locking at several granularities, and locking B-tree nodes with the tree protocol. Each gets a short textbook-based explanation here, followed by its exam questions.

1. Strict 2PL and cascading rollback (textbook §19.1)

Lec 04 covers this in full; here is what the exam questions need.

Dirty data
A value written by a transaction that has not yet committed.
Cascading rollback
When T aborts, every transaction U that read dirty data written by T must also be rolled back (it used a value that is being undone), then every transaction that read from U, and so on.
Recoverable schedule
Each transaction commits only after every transaction it read from has committed. (Otherwise a committed transaction might depend on one that later aborts.)
ACR schedule (avoids cascading rollback)
Transactions read only values written by committed transactions. Every ACR schedule is recoverable.
Strict two-phase locking
A transaction must not release any exclusive lock (any lock that allows writing) until it has committed or aborted, and the commit or abort log record has been flushed to disk. Strict 2PL transactions are 2PL.

Basic 2PL allows cascading rollback: T₁ may write A, unlock A in its shrinking phase, T₂ reads A, and then T₁ aborts. Strict 2PL stops this by keeping the write lock until the outcome of T₁ is known.

(22-23) Show that a schedule satisfying strict 2PL (two-phase locking) is ACR (avoids cascading rollback).

Show worked answer

Claim. In a schedule of strict 2PL transactions, no transaction reads dirty data; hence the schedule is ACR, and no abort can force another rollback.

Proof. Suppose transaction U reads element X, and the value it reads was written by another transaction T: so wT(X) precedes rU(X).

  1. By consistency, T held an exclusive lock on X when it executed wT(X), and U holds a shared (or exclusive) lock on X when it executes rU(X).
  2. By legality, these locks cannot be held at the same time (X is incompatible with S and X). So T must release its exclusive lock on X, uT(X), before U's lock on X is granted, and therefore before rU(X).
  3. By strictness, T releases its exclusive lock on X only after it has committed or aborted. If T aborted, its write of X was undone before the release, so U would not read T's value at all. Hence T had committed before rU(X).

So every value any transaction reads was written by a committed transaction: the schedule is ACR. If some transaction aborts, nobody has read its writes, so no other transaction needs to roll back: no cascading rollback. (The schedule is also recoverable, since ACR implies recoverable, and conflict-serializable, since strict 2PL transactions are 2PL.)

Example. T₁: xl₁(A); w₁(A); … and T₂: sl₂(A); r₂(A). Under strict 2PL, sl₂(A) is denied until T₁ commits (or aborts and restores A), so T₂ never sees T₁'s uncommitted A (right animation above).

2. Locks at several granularities (textbook §18.6)

A “database element” can be a whole relation, a block, or a tuple. Large elements mean few locks but little concurrency (one deposit at a time if the whole accounts relation is locked); small elements mean much concurrency but many locks to manage. Some applications need both: tuple locks for updates, and a relation-wide lock for an audit that reads every account.

Mixing sizes naively is unsafe: a shared lock on the relation for the audit must not coexist with exclusive locks on some of its tuples. The warning protocol solves this with intention locks IS and IX (“I intend to lock something below in S / X mode”):

  1. To lock any element in S or X, start at the root of the hierarchy (relation → blocks → tuples).
  2. At the element you want, request S or X.
  3. At each element above it, request IS (if you will want S below) or IX (if X below), and go down only once it is granted.

Two transactions that intend to work on different parts (IS/IX, IX/IX) can coexist at the relation and sort out real conflicts at the tuple level; an S lock on the whole relation excludes any intention to write below it (IX), and an X lock on it excludes everything. Insertions are treated as writes of the whole relation to avoid phantoms (§18.6.3).

What are the tradeoffs of locking with multiple granularities?

Show worked answer
  • Coarse granules (relations, files): few locks to request and store, small lock-table, cheap for transactions that touch much of the data (scans, audits, aggregations); but low concurrency, because transactions that touch different tuples of the same relation still block each other (e.g., only one deposit at a time on a locked accounts relation).
  • Fine granules (tuples): maximum concurrency for transactions touching few tuples; but many lock requests and a large lock table (memory and CPU overhead), and a scan of a big relation must take thousands of locks.
  • Multiple granularity lets each transaction choose: a scan takes one S lock on the relation, an update takes IX on the relation and X on one tuple. The cost is extra intention locks (every lock request must lock all ancestors in IS/IX first, top-down, and release bottom-up), a more complex compatibility matrix and group modes (e.g., SIX), and choosing the right level (systems may “escalate” many tuple locks to one relation lock). Phantoms still need care: inserting a tuple must be treated as a write of the relation (or of an index range).

Example (textbook Example 18.21): T₁ reads the King Kong tuples (IS on Movie, S on each tuple) while T₂ updates Gone With the Wind (IX on Movie, X on that tuple). IS and IX are compatible, so both run concurrently; with only a relation-level lock one would wait.

3. Locking B-trees: the tree protocol (textbook §18.7)

Treat each node of a B-tree (or B+ tree) as a lockable element. Every index operation starts at the root. Under 2PL a transaction cannot unlock the root until it has acquired all its locks, and since an insert or delete might split or merge nodes all the way up, a modifying transaction needs at least an update lock on the root. So only one modifying transaction at a time can use the index: 2PL serializes all index updates at the root.

Usually, though, a transaction can tell after one step that the root will not change: if it inserts and the child it moves to is not full, the split cannot reach the root (for a delete: the child has more than the minimum number of keys). It would like to release the root immediately, which 2PL forbids. The tree protocol allows it:

  1. A transaction's first lock may be on any node of the tree (in a B-tree, the root).
  2. Each later lock may be acquired only while the transaction holds a lock on the node's parent.
  3. Nodes may be unlocked at any time.
  4. A node that was unlocked may not be relocked by the same transaction.

Transactions are consistent and schedules legal, but they need not be 2PL. Every legal schedule of such transactions is still serializable: if two transactions both lock some node, the one that locked it first must lock every common node first (it is always ahead on the shared path from the top), so the precedence relation “locks a common node first” has no cycles. In practice this is “lock coupling” or “crabbing”: lock the child, then release the parent if the child is safe.

“Two-phase locking is efficient for B+ tree index structure” — Justify this statement using illustrative examples.

Show worked answer

The statement is not true as written; the justification shows why, and what is used instead.

  • Every search, insert or delete enters a B+ tree at the root. Under 2PL a transaction may not unlock the root until its lock point, i.e. until it has acquired every lock it needs, usually at commit.
  • An insert or delete might split or merge nodes up to the root, so it needs an update or exclusive lock on the root. Hence under 2PL at most one updating transaction can use the index at a time; all others wait at the root. Example: T₁ inserts key 15 and holds X on the root while it works on a leaf; T₂, inserting key 90 into a completely different leaf, waits for T₁ to commit.
  • But in the usual case the root is never modified: if the child T₁ visits is not full, no split can propagate upward, so the root lock could be released at once. 2PL forbids that.

The efficient approach is the tree protocol (lock coupling): lock a node only while holding its parent; release a node as soon as it cannot change (the child is safe); never relock. In Figure 2, T₂ starts as soon as T₁ has released the root, and the two inserts proceed in parallel in different subtrees. The tree protocol is not 2PL, yet it guarantees serializability, because transactions that meet in the tree always meet in the same order along every shared path.

BUET QBank · CSE 303 | L-3/T-1 | 2013–14 · 15 marks

Why does two-phase locking not work for B+ tree index structures? Write down the rules for accessing tree-structured data that ensure a serial order of transactions in a schedule.

Show worked answer

Why 2PL does not work well. All accesses to a B+ tree begin at the root. Any insert or delete may in principle rewrite the root (splits and merges propagate upward), so a modifying transaction must lock the root in update or exclusive mode, and under 2PL it cannot release that lock until it has taken all its locks (in practice, until commit). So only one transaction that is not read-only can be in the index at any time: the root becomes a bottleneck and the index is effectively single-user. 2PL is correct but gives almost no concurrency. Releasing the root early, when the child visited is safe (not full for inserts, more than minimally full for deletes), would fix that, but it violates 2PL.

Tree protocol rules (one lock mode; consistent transactions; legal schedules; no 2PL requirement):

  1. A transaction's first lock may be at any node of the tree.
  2. Subsequent locks may be acquired only if the transaction currently holds a lock on the parent node.
  3. Nodes may be unlocked at any time.
  4. A transaction may not relock a node it has unlocked, even if it still holds the node's parent.

Why a serial order exists. Say Ti <S Tj if they lock a common node and Ti locks it first. If Ti and Tj lock several common nodes, then the highest common node is locked first by one of them, say Ti; to reach any lower common node, Tj must pass through its parent while Ti is ahead on the same path, so Ti locks every common node first. Hence the relation is consistent on every node, its precedence graph is acyclic (textbook §18.7.3), and any topological order is an equivalent serial order.

Example (textbook Fig. 18.31): T₁ locks A, B, then C, unlocks A, then locks D (allowed: it holds B, D's parent); it is not 2PL, but the schedule is serializable.

Summary: strict 2PL holds write locks until commit or abort, so nobody reads uncommitted data and aborts never cascade. Multiple-granularity locking uses intention locks (IS, IX) on ancestors so that relation, block and tuple locks can coexist; it trades lock overhead against concurrency. 2PL serializes all updates of a B-tree at its root; the tree protocol (lock a node only while holding its parent, unlock any time, never relock) releases ancestors early and still guarantees serializability.
