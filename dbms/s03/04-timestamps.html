Timestamp Concurrency Control: the Ideas

Instead of locking, give every transaction a timestamp and insist that the schedule behave as if the transactions ran in timestamp order. This chapter introduces the timestamps kept on transactions and on elements, the two “physically unrealizable” situations that force an abort, dirty reads and the commit bit, and the Thomas write rule with its pitfall.

1. Timestamps on transactions (slide 15)

Timestamp TS(T)
A unique number the scheduler gives each transaction when it starts. Timestamps are issued in ascending order: a transaction that starts later gets a larger timestamp.

Two ways to generate them: (a) the system clock, provided the scheduler never assigns two timestamps within one clock tick; (b) a counter maintained by the scheduler, incremented by 1 at each transaction start (then timestamps have nothing to do with real time, but still increase with start order). Either way the scheduler keeps a table of the active transactions and their timestamps.

Optimistic concurrency control
A method that lets transactions proceed on the assumption that conflicts are rare, and fixes things (by aborting and restarting a transaction) only when a violation actually appears. Timestamping (and validation, textbook §18.9) are optimistic. Locking is pessimistic: it assumes things will go wrong and delays transactions in advance, but never aborts one just because a lock cannot be granted.

2. Timestamps on elements (slide 16)

Each database element X carries two timestamps and a bit:

RT(X), read time
The highest timestamp of any transaction that has read X: RT(X) = max{TS(Ti) : Ti has read X}.
WT(X), write time
The highest timestamp of any transaction that has written X: WT(X) = max{TS(Ti) : Ti has written X}. It identifies the writer of X's current value.
C(X), commit bit
True if and only if the most recent transaction to write X has already committed. Its purpose is to prevent dirty reads (Section 5).

3. The presumed serial order (slide 17)

A timestamp scheduler commits in advance to one serial order: the order of the timestamps. If TS(T₁) < TS(T₂) < ⋯ < TS(Tn), the schedule must be equivalent to the serial schedule (T₁, T₂, …, Tn). Pretend each transaction executes instantaneously at the moment of its timestamp; every real read and write must be consistent with that pretence. Any read or write that would violate the order is prohibited, and its transaction is aborted and restarted (with a new, larger timestamp).

Correction to slide 17: it says that if TS(T₁) < TS(T₂), “T₁ is younger than T₂, T₂ is older than T₁”. It is the other way round. A smaller timestamp means the transaction started earlier, so T₁ is older and T₂ is younger. (This matters in Lec 04's wait-die and wound-wait rules.)

4. Physically unrealizable behaviour (slides 18–19)

In the timelines below the horizontal axis is real time. Upward arrows mark when transactions start (their timestamps); downward arrows mark actual reads and writes; dotted lines link each action back to its transaction's timestamp, the moment it “theoretically” happened.

Case 1: read too late

T tries to read X, but TS(T) < WT(X): the current value of X was written by a transaction U that started after T. In the presumed serial order U runs after T, so T should never see U's value; but U's value is the only one there. The read is physically unrealizable, and T is aborted.

Case 2: write too late

T tries to write X, but TS(T) < RT(X): a transaction U that started after T has already read X. In the serial order, U should have read the value T is about to write, but it read an older one. (The textbook states the full condition as WT(X) < TS(T) < RT(X): no later writer has overwritten X either, which would otherwise excuse T.) T is aborted.

Slides 18–19 question: why abort and restart T?

To keep the presumed serial order. The scheduler promised that the result equals the timestamp-order serial schedule. In both cases something T should have come before (U's write, U's read) has already happened, and it cannot be undone without undoing U too. The cheap fix is to abort T and restart it with a new, larger timestamp: the restarted T comes after U in the serial order, which is consistent with what U did.

5. Dirty reads and the commit bit (slides 20–21)

Case 3: dirty read

T reads X, last written by U, with TS(U) < TS(T) and U's write before T's read in real time. This is physically realizable: U precedes T in both orders. But if U has not committed yet, U might still abort (an error in U, or the scheduler rolling U back for an unrealizable action). Then T has read a value that officially never existed: a dirty read.

How to avoid it: check the commit bit. If C(X) is true, U has committed and the read is granted. If C(X) is false, T is delayed (put to wait) until U commits (C(X) becomes true) or aborts (then X's previous value is restored and T retries).

6. The Thomas write rule (slides 22–23)

Case 4: a later value is already there

T wants to write X. If RT(X) > TS(T), this is a write too late and T aborts (Case 2). But suppose RT(X) ≤ TS(T) and WT(X) > TS(T): a transaction U with a later timestamp has already written X, and nobody later than T has read X.

Slide 22 question: why can T's write be skipped?

In the serial order (T, U), T writes X and then U overwrites it. Nobody reads X between those two writes: a reader V with TS(T) < TS(V) < TS(U) that wanted T's value would have read X after U's write and been aborted as a read-too-late, and RT(X) ≤ TS(T) says no such read happened. Every later reader wants U's value or a later one. So T's value would be invisible in the serial schedule anyway. Ignoring the write gives exactly the effect of the serial order (T, U), and T can continue instead of aborting.

Thomas write rule
When TS(T) ≥ RT(X) but TS(T) < WT(X), skip T's write of X and let T continue.

The slide's bracket summarizes the trade-off: the rule allows more concurrency (no abort), and the result is serializable but not necessarily conflict-serializable. For example r₁(A); w₂(A); w₁(A) has a cycle (r₁(A) before w₂(A) gives T₁ → T₂, w₂(A) before w₁(A) gives T₂ → T₁), but with w₁(A) skipped its effect equals (T₁, T₂). This is the blind-write situation of Lec 02 Chapter 3.

The problem with the Thomas write rule (slide 23)

Suppose T's write was skipped because of U's write, T then commits, and later U aborts. U's value must be removed from X and the previous value restored. Since T committed, X should now hold T's value, but T's write was thrown away and it is too late to repair.

The textbook's fix, built into the rules of the next chapter: every write is tentative until its transaction commits; the scheduler keeps a copy of the old value of X and its previous WT(X), and sets C(X) = false. The Thomas write rule may skip T's write only if C(X) is true (U has committed); if C(X) is false, T is delayed until U commits (then skip) or aborts (then T's write is performed on the restored X).

DB QB · 22-23 2a · 9 marks  |  BUET QBank · CSE 215 | L-2/T-1 | 2022–23 · 18 marks

Consider the following two transactions:
T₁: r₁(A); w₁(A);
T₂: w₂(A);
(i) Construct a concurrent schedule of T₁ and T₂ that utilizes "Thomas write rule". Show a serial schedule which is equivalent to your given concurrent schedule.
(ii) What is the problem of allowing Thomas write rule?

Show worked answer

(i) Let TS(T₁) = 1 < TS(T₂) = 2 (T₁ starts first). Schedule:

r₁(A); w₂(A); c₂; w₁(A); c₁
  • r₁(A): TS 1 ≥ WT(A) = 0, C(A) true → granted, RT(A) = 1.
  • w₂(A): TS 2 ≥ RT(A) = 1 and ≥ WT(A) = 0 → written, WT(A) = 2, C(A) = false.
  • c₂: C(A) = true.
  • w₁(A): TS 1 ≥ RT(A) = 1 (only T₁ itself read A), but TS 1 < WT(A) = 2 and C(A) = true → Thomas write rule: the write is skipped; T₁ continues and commits.

Effect: T₁ read the initial A, and A ends with T₂'s value. The serial schedule (T₁, T₂) = r₁(A); w₁(A); w₂(A) has exactly the same effect: T₁ reads the initial A, and T₂'s write overwrites T₁'s. So the schedule is equivalent to (T₁, T₂), the timestamp order. (As written, r₁(A); w₂(A); w₁(A) is not conflict-serializable: it has arcs T₁ → T₂ and T₂ → T₁. The Thomas rule makes it serializable by dropping w₁(A).)

(ii) The skipped write cannot be recovered if the later writer aborts. In r₁(A); w₂(A); w₁(A) skipped; c₁; a₂, T₂'s abort restores A to its value before T₂, i.e. the initial value; but T₁ has committed, so A should hold T₁'s value, and that write was discarded. The database is wrong. Fix: allow the skip only if the later writer has committed (C(A) true); otherwise delay T₁ until T₂ commits or aborts. The rule also yields schedules that are serializable but not conflict-serializable, so a system relying on conflict-serializability tests cannot verify them.

BUET QBank · CSE 303 | L-3/T-1 | 2015–16 · 5 marks

Explain the Thomas Write Rule with an example.

Show worked answer

In timestamp ordering, transaction T requesting wT(X) with TS(T) ≥ RT(X) but TS(T) < WT(X) finds that a transaction U later in the timestamp order has already written X, and that no transaction later than T has read X. In the serial order T's value would be overwritten by U's before anyone read it, so the Thomas write rule ignores (skips) T's write instead of aborting T. (If TS(T) < RT(X), T must still be aborted: write too late.) With commit bits, the skip is done only if C(X) is true; if U has not committed, T waits.

Example: TS(T₁) = 10, TS(T₂) = 20, RT(X) = WT(X) = 0.

w₂(X)  → WT(X) = 20          c₂ → C(X) = true
w₁(X)  → RT(X) = 0 ≤ 10, but 10 < WT(X) = 20  ⇒  skip w₁(X); T₁ continues

Result: X holds T₂'s value, exactly as in the serial order (T₁, T₂). Plain timestamp ordering without the rule would have aborted T₁ needlessly. Benefit: fewer aborts, more concurrency. Cost: schedules are serializable (view) but not always conflict-serializable, and skipped writes are lost if the later writer aborts unless commit bits are used.

Summary: each transaction gets a timestamp at start; the schedule must be equivalent to the serial order of timestamps. Each element keeps RT(X), WT(X) and a commit bit C(X). A read with TS(T) < WT(X) (read too late) or a write with TS(T) < RT(X) (write too late) is physically unrealizable, and T is rolled back. A read of uncommitted data waits for the writer's commit. A write with RT(X) ≤ TS(T) < WT(X) can be skipped (Thomas write rule), but only once the later writer has committed.
