The Rules of Timestamp-Based Scheduling

Four rules decide every read, write, commit and abort under timestamp ordering. This chapter states them exactly as the textbook does, runs the slides' two examples, and gives a scheduler simulator that applies the rules to any schedule, with or without commit bits. All exam questions on timestamp ordering are worked with it.

1. The scheduler's three choices

For each read or write request from T, a timestamp scheduler can:

  1. grant the request;
  2. abort T, if the request would violate physical reality, and restart it with a new timestamp (abort followed by restart is called rollback);
  3. delay T and decide later whether to grant or abort (when the outcome depends on whether an uncommitted writer commits).

Writes are tentative: when T writes X, the scheduler keeps the old value of X and its previous WT(X), and sets C(X) = false, so the write can be undone if T aborts.

2. The rules (slides 24–26)

R1. T requests a read rT(X).

  1. If TS(T) ≥ WT(X), the read is physically realizable.
    1. If C(X) is true, grant the request. If TS(T) > RT(X), set RT(X) := TS(T); otherwise leave RT(X) unchanged.
    2. If C(X) is false, delay T until C(X) becomes true or the transaction that wrote X aborts.
  2. If TS(T) < WT(X), the read is physically unrealizable: roll back T (abort, restart with a new, larger timestamp).

R2. T requests a write wT(X).

  1. If TS(T) ≥ RT(X) and TS(T) ≥ WT(X), the write is physically realizable and is performed: write the new value of X, set WT(X) := TS(T), and set C(X) := false.
  2. If TS(T) ≥ RT(X) but TS(T) < WT(X), the write is realizable but a later value is already in X (Thomas write rule). If C(X) is true, ignore T's write and let T proceed. If C(X) is false, delay T as in R1(a)(ii).
  3. If TS(T) < RT(X), the write is physically unrealizable: roll back T.

R3. T commits. Set C(X) := true for every element X written by T (those with WT(X) = TS(T)). Transactions waiting for these commit bits may proceed.

R4. T aborts (or is rolled back by R1(b) or R2(c)). T's writes are cancelled (old values and write times restored). Any transaction waiting on an element X that T wrote must repeat its read or write attempt and see whether it is now legal.

Order of checks for a write: first compare with RT(X) (is it too late?), then with WT(X) (perform, or skip/wait). Order for a read: compare with WT(X), then check C(X).

3. Slide 27: three transactions on A, B, C

Timestamps: TS(T₁) = 200, TS(T₂) = 150, TS(T₃) = 175 (T₂ registered first, then T₃, then T₁, even though T₁ makes the first access). All read and write times start at 0. As in the slide and the textbook's Fig. 18.39, commits are not shown, so this run treats each write as committed at once (commit bits off).

Slide 27 questions: why is T₂ aborted, and why does w₃(A) not update WT(A)?

T₂ is aborted at w₂(C): C has already been read by T₃ (RT(C) = 175), which in the serial order comes after T₂ (150). T₃ should have read the value T₂ is now writing, but read the old one. TS(T₂) = 150 < RT(C) = 175: write too late, rule R2(c).

w₃(A) does not change WT(A) because of the Thomas write rule, R2(b): TS(T₃) = 175 ≥ RT(A) = 150, so no later transaction has read A, but TS(T₃) = 175 < WT(A) = 200: T₁, later in the serial order, has already written A. In the serial order (T₂, T₃, T₁) T₃'s value of A would be overwritten by T₁'s before anyone read it, so the write is skipped; T₃ is not rolled back, and WT(A) stays 200.

With commit bits. T₁ never commits in the slide. Under the full rules C(A) is false when w₃(A) arrives, so R2(b) delays T₃ until T₁ commits; only then is the write skipped. Run the same schedule with c₁ added (… w₂(C) w₃(A) c₁) in the simulator below with “use commit bits” ticked to see the wait.

4. Slide 28: a read that is too late

TS(T₁) = 150, TS(T₂) = 200, TS(T₃) = 175, TS(T₄) = 225, all on element A (textbook Fig. 18.40). The slide's “issues RT(X)” means T issues a read of X.

When T₃ reads A, the current value was written by T₂ (WT(A) = 200), which is later than T₃ in the serial order: read too late, R1(b), T₃ is aborted. Notice that an old value of A, written by T₁ at time 150, would have been exactly right for T₃. Keeping such old versions is the idea of the next chapter (MVCC), where T₃ would not need to abort.

5. Timestamp scheduler simulator

Type a schedule of reads, writes, commits (c1), aborts (a1) and optional starts (st1, which assign timestamps in start order). Give timestamps explicitly (T1=200, T2=150) or leave the box blank for TS(Ti) = i. BUET QBank · CSE 303 | L-3/T-1 | 2010–11 · 10 marks

Explain the rules of performing read and write operations in the timestamp ordering protocol. What are the advantages and disadvantages of this protocol? How is the protocol improved by the Thomas Write Rule?

Show worked answer

Rules. Every transaction T gets a unique increasing timestamp TS(T); every element X keeps RT(X), WT(X) (and commit bit C(X)). The schedule must be equivalent to the serial order of timestamps.

  • Read rT(X): if TS(T) < WT(X), roll back T (X was overwritten by a later transaction). Otherwise grant (waiting first if C(X) is false), and set RT(X) := max(RT(X), TS(T)).
  • Write wT(X): if TS(T) < RT(X), roll back T (a later transaction already read X). Else if TS(T) < WT(X), basic timestamp ordering also rolls back T; with the Thomas write rule the write is ignored instead. Otherwise perform it and set WT(X) := TS(T) (C(X) := false until T commits).

Advantages. Conflict-serializable (basic version) schedules in a known order; no locks, so no lock waits: in the basic protocol a transaction is never blocked, only granted or rolled back (with commit-bit delays waits do occur, and in rare cases two transactions can even wait for each other, e.g. TS(T₁) = 1, TS(T₂) = 2: w₁(Y); w₂(X); w₁(X) waits for T₂; r₂(Y) waits for T₁, cf. textbook Exercise 18.8.3); read-only and low-conflict workloads run with little overhead; optimistic, no blocking for most operations.

Disadvantages. Frequent rollbacks when transactions conflict, wasting work; possible starvation of a long transaction that keeps being restarted; overhead of storing and updating RT/WT for every element (a read becomes a write of RT); without commit bits, schedules may be unrecoverable or cause cascading rollback.

Thomas write rule. When RT(X) ≤ TS(T) < WT(X), T's write is obsolete: a later transaction has already written X and no later transaction read the value T would have written. Instead of rolling T back, simply skip the write. This avoids unnecessary aborts (more concurrency) and still gives a schedule equivalent to the timestamp order, though not always conflict-serializable. Example: TS(T₁) = 1, TS(T₂) = 2: r₁(A); w₂(A); w₁(A): w₁(A) is skipped instead of aborting T₁; the effect equals (T₁, T₂).

Summary: reads: abort if TS(T) < WT(X); otherwise wait while C(X) is false, then grant and raise RT(X). Writes: abort if TS(T) < RT(X); perform (WT := TS, C := false) if TS(T) ≥ WT(X); otherwise skip by the Thomas write rule once C(X) is true, waiting while it is false. Commit sets C(X) for the transaction's writes and releases waiters; abort cancels its writes and makes waiters retry.
