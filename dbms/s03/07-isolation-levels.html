Transaction Isolation Levels

Serializability is the strongest guarantee, and the most expensive. SQL lets a transaction ask for weaker isolation: read uncommitted, read committed, or repeatable read. This chapter defines each level with the slides' ticket-booking example, animates what the reading transaction sees, and compares the anomalies each level permits.

1. Why weaker levels exist

Everything so far aimed at serializable schedules. Enforcing that costs waiting (locks) or aborts (timestamps). Many applications can tolerate small anomalies in exchange for speed, so SQL lets each transaction choose its isolation level: how much it may see of other, concurrent transactions' work.

SET TRANSACTION ISOLATION LEVEL READ COMMITTED;     -- SQL syntax (textbook §6.6)

The level is a property of the transaction that reads: it controls what that transaction may observe. The anomalies involved:

Dirty read
Reading a value written by a transaction that has not committed (and may abort).
Non-repeatable (unrepeatable) read
Reading the same element twice in one transaction and getting different values, because another transaction committed a change in between.
Phantom
Running the same query twice and getting different sets of rows, because another transaction inserted (or deleted) rows that satisfy the condition (textbook §18.6.3).

2. The four levels (slides 35–37)

The slides' scenario: a ticket portal. One seat is left: availability = 1. T₁ books it, changing availability from 1 to 0, but has not yet committed. T₂ is checking availability for another customer.

Serializable

The strongest level: the execution must be equivalent to some serial order of the transactions. T₂ sees either the state before T₁ or the state after T₁ commits, never anything in between, and the same in every read. This is what 2PL or timestamp ordering (Chapters 1–6) provide.

Read uncommitted

Dirty reads are allowed. T₂ reads availability = 0 written by the uncommitted T₁, and tells a customer “no seats available”. Then T₁ aborts and availability returns to 1: the customer was turned away because of a value that never officially existed.

Read committed

Dirty reads are not allowed. While T₁ is uncommitted, T₂ sees availability = 1, the last committed value (the slide says it comes from the UNDO data: the system keeps the old value for possible rollback and shows it to readers, which is a multiversion read). After T₁ commits, a second read by T₂ sees 0, the new committed value. So the same item read twice gave 1 and then 0: non-repeatable reads are possible.

Repeatable read

Dirty reads are not allowed, and a value once read stays the same. T₂ sees 1 before T₁ commits and still sees 1 after T₁ commits, because it keeps reading the value that was committed when it first read the item. (In SQL's definition, repeatable read still allows phantoms: newly inserted rows may appear in a repeated query; the textbook describes it as locking or fixing the tuples already read, but not new ones.)

Each weaker level trades correctness for concurrency: fewer locks are held (or held for shorter times), so transactions wait less. In a lock-based system, roughly: read uncommitted takes no read locks; read committed takes short read locks (released right after each read), or reads the last committed version; repeatable read keeps read locks on the rows read until commit; serializable also prevents phantoms (e.g. by locking ranges or whole relations).

BUET QBank · CSE 215 | L-2/T-2 | 2021–22 · 15 marks

The SQL standard defines three weak isolation levels: dirty reads, read committed, and repeatable reads. Compare these three levels with illustrative examples.

Show worked answer

(“Dirty reads” is the level SQL calls READ UNCOMMITTED.) All three are weaker than SERIALIZABLE; they differ in which anomalies a reading transaction may observe. Scenario: one ticket left, availability = 1; T₁ books it (writes 0); T₂ checks availability.

  1. Read uncommitted (dirty reads allowed). T₁ writes 0 and has not committed; T₂ reads 0 and answers “sold out”. T₁ then aborts; availability is 1 again. T₂ acted on data that never existed. Allows dirty reads, non-repeatable reads and phantoms. Fastest: no read locks.
  2. Read committed. T₂ can read only committed values. While T₁ is uncommitted, T₂ reads 1 (the old committed value, or it waits for T₁'s lock). After T₁ commits, T₂ reads again and gets 0. No dirty reads, but non-repeatable reads are possible: two reads of the same item in T₂ returned 1 and 0. Typical implementation: short-duration read locks, or reading the last committed version.
  3. Repeatable read. No dirty reads, and any item T₂ has read keeps the value T₂ first saw: T₂ reads 1 before and after T₁'s commit (T₁'s write may even be blocked until T₂ finishes, in a lock-based system). Phantoms are still possible: if T₂ runs SELECT COUNT(*) FROM seats WHERE free = 1 twice while another transaction inserts a new free seat, the second count is larger.

Going down the list, isolation increases and concurrency decreases; SERIALIZABLE removes phantoms too.

Summary: SQL offers four isolation levels. Serializable gives the effect of a serial order. Read uncommitted allows dirty reads. Read committed forbids dirty reads but a repeated read may see a newly committed value. Repeatable read also keeps every value read stable, but new rows (phantoms) may appear. Weaker levels mean less waiting and more anomalies.
