The Lock Table and the Locking Scheduler

How does a real scheduler decide, in constant time, whether a lock can be granted? It keeps a hash table of lock-table entries, each with a group mode, a waiting bit and a list of holders and waiters. This chapter describes the textbook's two-part scheduler, the entry structure, and the rules for lock and unlock requests, with an animated lock table and the exam questions on lock tables.

1. A scheduler that inserts the locks (textbook §18.5.1)

Real transactions do not write lock and unlock actions themselves. The textbook's simple architecture rests on two principles: (1) the scheduler inserts lock actions into the stream of reads and writes; (2) transactions do not release locks: the scheduler releases all of a transaction's locks when the transaction manager says it is committing or aborting. (Holding locks until commit is “strict” two-phase locking; it is automatically 2PL.)

  1. Part I takes each request and puts the right lock action in front of it, choosing the mode (S for a read, X for a write; U for a read when it knows a write of the same element will follow). On commit or abort it releases all the transaction's locks and tells Part II which elements became free.
  2. Part II executes the lock and access actions. If the transaction is already waiting, the action joins that transaction's list of delayed actions. Otherwise an access is executed, and a lock is looked up in the lock table: granted (entry updated) or recorded as waiting (and the transaction is delayed).
  3. When an element becomes free, Part II picks the transaction(s) that now get the lock and lets them run their delayed actions until they finish or hit another lock that cannot be granted.

Knowing future actions. To choose U instead of S, Part I needs advance notice that the transaction may later write the element. That information is available: a query never writes, an SQL update statement says what it modifies, and a compiler sees all the SQL statements of an embedded-SQL program (textbook Example 18.19). Here is Example 18.19 itself: transactions issue only reads, writes and commits; Part I inserts S, U and X locks; commit releases locks.

2. The structure of the lock table (slides 10–11)

Abstractly the lock table is a relation from database elements to locking information. It is usually a hash table keyed on the element (its address). An element without locks does not appear at all, so the table's size is proportional to the number of locked elements, not to the size of the database.

Each entry (textbook Fig. 18.26, for the S/X/U scheme) contains:

Group mode
A summary of the most stringent lock held on the element: S = only shared locks are held; U = one update lock and zero or more shared locks; X = one exclusive lock and nothing else. A new request is compared with the group mode only, instead of with every lock held.
Waiting bit
“Yes” if at least one transaction is waiting for a lock on this element.
List
One node per transaction that holds or waits for a lock on the element: transaction name, lock mode, whether it is holding or waiting (Wait?), a Next link to the next node of this element, and a Tnext link to the next node of the same transaction (for another element). Tnext lets the scheduler find all locks of a committing or aborting transaction quickly.

3. Handling lock requests (slide 12)

Transaction T requests a lock on A:

  • No entry for A: there are no locks on A, so create the entry and grant the request. Group mode = the requested mode.
  • Entry exists, group mode U or X: no lock can be granted (except when T itself holds the U lock and asks to upgrade: footnote of §18.5.2). Add T to the list with Wait? = yes, set the waiting bit.
  • Entry exists, group mode S: a shared or update lock can be granted. Add T with Wait? = no; the group mode becomes U if the new lock is U, otherwise stays S. (An X request is refused and T waits.)

In every case the new list node is linked through Next and Tnext. The group mode alone answered the question; the list was never scanned.

4. Handling unlocks (slides 13–14)

Transaction T unlocks A: delete T's node from A's list. Then:

  • T's lock ≠ group mode (e.g., T held S while the group mode is U): no change.
  • T's lock = group mode: scan the list for the new group mode. If T held U (or the only S), the remaining holders can only be shared, so the new mode is S, or there are no holders left. If T held X, nobody else held anything.
  • If the waiting bit is yes: grant one or more waiting requests.

Slide 13 question: why does the group mode not change when T's lock differs from the group mode?

The group mode is the most stringent lock held by anyone. If T's lock is not equal to it, T's lock was weaker (T held S while the group mode was U), so the lock that made the group mode U belongs to another transaction and is still held. Removing a weaker lock cannot change the strongest one. (With the S/X/U modes, the only possible case is S under U, since group mode X means T would have to be the X holder.)

Which waiting request is granted (slide 14 and textbook §18.5.2)?

  1. First-come-first-served: grant the request that has waited longest. No starvation (no transaction waits forever while others keep getting the lock).
  2. Priority to shared locks: grant all waiting S locks, then one U, and an X only if nothing else waits. Can starve a transaction waiting for U or X.
  3. Priority to upgrading: if a transaction holding U waits to upgrade to X, grant that first; otherwise use one of the other policies.

A group mode of “nothing” never appears: when the last holder leaves and nobody waits, the entry is deleted.

DB QB · 21-22 5b · 10 marks  |  BUET QBank · CSE 215 | L-2/T-2 | 2021–22 · 10 marks

With necessary figures and examples, explain how Two-Phase Lock is implemented using Lock Table.

Show worked answer

Architecture. Transactions send reads, writes, commits and aborts to the scheduler (Figure 1). Part I inserts a lock before each access: S before a read, X before a write, U before a read when a write of the same element will follow. Locks are never released by the transaction itself; Part I releases all of a transaction's locks when it commits or aborts. So every transaction acquires locks while it runs (growing phase) and releases them all at the end (shrinking phase): this is two-phase locking (in its strict form).

Lock table. A hash table keyed on element; an entry exists only for locked elements. Each entry holds the group mode (S, U or X), a waiting bit and a list of (transaction, mode, Wait?) nodes linked by Next, with Tnext linking all nodes of one transaction (Figure 3).

Lock request by T on A: no entry → create it, grant. Group mode X or U → T is added with Wait? = yes, waiting bit = yes, T is delayed. Group mode S → grant S or U (group mode becomes U for U), refuse X. The decision uses the group mode and the compatibility matrix only.

Commit/abort of T: follow T's Tnext chain, delete each of T's nodes, recompute the group mode where T's lock equalled it, and if the waiting bit is set, grant waiting requests (FCFS, shared-first or upgrade-first); granted transactions resume their delayed actions.

Example (Figure 2): r₁(A); r₂(A); r₂(B); r₁(B); w₁(B); c₂; c₁. Part I inserts sl₁(A), sl₂(A), sl₂(B), ul₁(B) (T₁ will write B), xl₁(B). Entry B: group mode S after sl₂(B), U after ul₁(B); xl₁(B) is refused because T₂ holds S on B (T₁: Wait? = yes). At c₂ the scheduler removes T₂'s nodes from A and B; B's group mode drops to U, the waiting upgrade is granted (group mode X), and T₁ finishes. The resulting schedule is conflict-serializable in the order (T₂, T₁), the order in which the transactions released their locks.

DB QB · 19-20 4b · 5 marks  |  BUET QBank · CSE 215 | L-2/T-2 | 2019–20 · 15 marks

The hash values of data items A, B and C are 5, 1 and 8 respectively. Show and explain the lock table entries for the instructions with transactions as follows: {READ (A), T1} {READ (B), T2} {READ (C), T1}, {READ (A), T2}, {READ (B), T1} {READ (C), T2}, {WRITE (A), T3}, {WRITE (A), T4}, {WRITE (B), T3}, {WRITE (C), T1}

Show worked answer

Reads request S locks, writes request X locks; locks are kept (2PL) since no transaction finishes in the list. Processing in order:

  1. READ(A),T₁: no entry for A (bucket 5) → create, grant S. A: group S.
  2. READ(B),T₂: create entry in bucket 1, grant S.
  3. READ(C),T₁: create entry in bucket 8, grant S.
  4. READ(A),T₂: group mode S → grant S. A: T₁ S, T₂ S.
  5. READ(B),T₁: group S → grant S. B: T₂ S, T₁ S.
  6. READ(C),T₂: group S → grant S. C: T₁ S, T₂ S.
  7. WRITE(A),T₃: X requested, group mode S → wait. A: waiting bit yes; T₃ X waiting.
  8. WRITE(A),T₄: wait, queued behind T₃.
  9. WRITE(B),T₃: T₃ is already waiting, so the scheduler delays this request; it is not yet in the lock table. (If it were issued, it would also wait: B is held in S by T₂ and T₁.)
  10. WRITE(C),T₁: T₁ holds S on C and asks for X (an upgrade). T₂ also holds S on C, so the upgrade waits. C: waiting bit yes.

Final lock table: bucket 1 → B (group S, waiting no: T₂ S, T₁ S); bucket 5 → A (group S, waiting yes: T₁ S, T₂ S, T₃ X wait, T₄ X wait); bucket 8 → C (group S, waiting yes: T₁ S, T₂ S, T₁ X wait). Waits-for: T₃ → T₁, T₂; T₄ → T₁, T₂; T₁ → T₂. No cycle, so no deadlock: when T₂ commits, T₁'s upgrade on C is granted; when T₁ and T₂ have both released A, T₃ and then T₄ get A.

The lock table is a hash table on the data item; items with the same hash value are chained in one bucket (bucket 2: F, G; bucket 3: S; bucket 5: A, D, H). Each entry carries the group mode, the waiting bit and the list of granted and waiting requests in arrival order.

Modes are not given, so they are inferred: an item locked by several transactions at once must be locked in S mode, and a transaction waiting behind shared holders must have asked for X. For F and H (one holder) either mode is possible; F's holder must conflict with T₅'s request, so we show X held by T₂ (S held + X requested would also fit).

Notes. (1) D has a waiting transaction but no holder. A correct lock manager never leaves a request waiting on a free element: T₃'s request would be granted at once (or, if D was just released, granted at that moment). So D's entry is shown with T₃ waiting as the data says, but in a consistent state T₃ would be holding D. (2) Waits-for arcs: T₂ → T₁, T₅ (on A); T₅ → T₂ (on F); T₁ → T₂, T₃, T₄ (on G). T₂ → T₁ → T₂ is a cycle, so this state is a deadlock (also T₂ → T₅ → T₂); the scheduler would have to abort one of T₁, T₂, T₅.

BUET QBank · CSE 303 | L-3/T-1 | 2010–11 · 10 marks

Describe the implementation of lock manager using a lock table data structure and show the following locks: (a) T1 has granted locks for data items 10, 22, 35 and is waiting for data item 44. (b) T2 has granted locks for data items 44 and 22. (c) T3 has been waiting for data item 22. (d) T4 has been granted locks for data items 8, 10, 22 and is waiting for data item 35. Also explain how the lock manager processes a lock request using the structure.

Show worked answer

Implementation. The lock manager keeps an in-memory hash table indexed by data item (hash function here: item mod 8, chaining on collisions). Each entry is an item that is currently locked or requested: group mode, waiting bit, and a linked list of request nodes (transaction, mode, granted or waiting) in arrival order; each node also links to the next node of the same transaction, so all of a transaction's locks can be found and released at commit/abort.

Modes. Item 22 is granted to T₁, T₂ and T₄ simultaneously, so those are S locks, and T₃'s waiting request must be X. Item 10 is shared by T₁ and T₄ (S). Items 35, 44, 8 have one holder each; 35 and 44 have waiters, so holder and waiter conflict (shown as X held, X requested).

Processing a lock request for item x by T: compute h(x), walk the bucket's chain to find x's entry. If absent, create it with T's request granted. If present, append T's node at the end of x's list; grant it if the requested mode is compatible with the group mode and no earlier request is waiting (FCFS), otherwise mark it waiting, set the waiting bit and suspend T. On unlock or commit, remove T's nodes (via its transaction chain) and grant the waiting requests at the front of each list that have become compatible. Here: T₁ waits for T₂ (44), T₄ waits for T₁ (35), T₃ waits for T₁, T₂, T₄ (22). No cycle, so no deadlock: when T₂ finishes, T₁ gets 44, finishes and releases 35 to T₄, and so on.

Summary: the scheduler inserts lock requests itself and releases a transaction's locks at commit or abort, which makes every transaction two-phase locked. The lock table is a hash table of entries for locked elements only; each entry stores the group mode (most stringent lock held: S, U or X), a waiting bit, and a list of holders and waiters linked per element and per transaction. A request is decided against the group mode; an unlock may change the group mode and wakes waiters under FCFS, shared-first or upgrade-first policy.
