Multiversion Concurrency Control, and Timestamps vs Locking

If the database keeps old versions of each element, a transaction that is “too late” to read the current value can read the version that was current at its timestamp, so reads never abort. This chapter gives the MVCC rules, animates the slides' two examples, and closes with when timestamps beat locking.

1. The idea (slide 29)

Chapter 5's Fig. 18.40 aborted T₃ (TS 175) because A had been overwritten by T₂ (TS 200), even though the value T₁ wrote at time 150 was exactly what T₃ needed. Multiversion concurrency control (MVCC; the textbook calls it multiversion timestamping, sometimes abbreviated MVTO) keeps that old value.

Version Xt
A copy of element X written by the transaction with timestamp t. Each write creates a new version; versions are identified by their write times, which never change.
RT(Xt)
The read time of a version: the largest timestamp of a transaction that has read that version.

When T reads X, the scheduler gives it the version of X that was current at T's timestamp, so a read is never aborted. The method is cheap when elements are disk blocks: the buffer manager just keeps the old blocks that some active transaction might still need.

2. The protocol (slides 30–31)

  1. Write. When a legal write wT(X) occurs, create a new version Xt with t = TS(T), i.e. WT(Xt) = TS(T).
  2. Read. When rT(X) occurs, find the version Xt with t ≤ TS(T) such that no other version Xt′ has t < t′ ≤ TS(T): the version written immediately before T theoretically executed. T reads it, and RT(Xt) := max(RT(Xt), TS(T)).
  3. Reject a write. For wT(X), find the version Xt with the largest t ≤ TS(T) (the version T's write would follow). If RT(Xt) > TS(T), reject the write and roll back T.
  4. Delete old versions. If a version Xt exists such that no active transaction has a timestamp less than t, every version of X older than Xt may be deleted.

Note on the slides' inequalities. Slide 29 says T reads the latest version with TS(T) > WT(X); slide 30 says t ≤ TS(T). The correct condition is t ≤ TS(T) (a transaction that wrote X and then reads it again must see its own version, whose write time equals its own timestamp). Slide 30's write check says “latest Xt with WT(Xt) < TS(T)”; again ≤ is the textbook's version, and it only matters when T writes X a second time.

Slide 31 question: why are versions older than Xt no longer required?

An old version Xs (s < t) could only be read by a transaction whose timestamp lies between s and t: any transaction with timestamp ≥ t reads Xt or a newer version. If no active transaction has a timestamp below t, and every new transaction gets a larger timestamp than all existing ones, no present or future transaction has a timestamp below t. So nobody will ever read Xs. Nor is Xs needed for write checks: a writer with timestamp below t would be required for that, and there is none. The versions can be discarded.

4. Slide 33: a write that must be rejected

X has versions X₅₀ and X₁₀₀. X₅₀ was read by a transaction with timestamp 80, so RT(X₅₀) = 80. Now a transaction T with timestamp 60 tries to write X.

If T's write were allowed, it would create X₆₀. Then the transaction with timestamp 80 should have read X₆₀ (60 is the latest write time ≤ 80), but it actually read X₅₀. The version T's write would follow is X₅₀, and RT(X₅₀) = 80 > 60 = TS(T), so the write is rejected and T is rolled back. Writes can still abort under MVCC; only reads cannot.

5. Timestamps versus locking (slide 34)

  • Timestamping is better when most transactions are read-only, or when concurrent transactions rarely read and write the same elements: there is little to abort, and nobody waits for locks.
  • Locking is better in high-conflict situations. Locking frequently delays transactions while they wait for locks, but if transactions often read and write the same elements, a timestamp scheduler rolls them back often, and a rollback wastes all the work done so far and adds even more delay than waiting.
  • Locking avoids such rollbacks because it maintains conflict-serializability by delaying, not aborting.

A compromise used by several commercial systems (textbook §18.8.6): split transactions into read-only and read/write. Read/write transactions use two-phase locking. Read-only transactions use multiversion timestamps: the versions created by writers are kept, and each read-only transaction reads the versions appropriate to its timestamp. A read-only transaction then never aborts and is rarely delayed. This is essentially how “snapshot” reads in systems like PostgreSQL and Oracle work.

Timestamps better: when most transactions are read-only, or concurrent transactions rarely access the same elements with at least one write. Then few transactions are ever rolled back and nobody pays for waiting on locks or for deadlock handling.

Locking better: in high-conflict workloads, where concurrent transactions often read and write the same elements. A timestamp scheduler would roll back many of them (losing their work and restarting), which costs more than the delays of waiting for locks. Locking delays but does not abort (except to break deadlocks).

MVCC rules. Each element keeps versions Xt, where t is the timestamp of the writer; each version has a read time RT(Xt).

  1. A legal write wT(X) creates a new version XTS(T).
  2. A read rT(X) reads the version Xt with the largest t ≤ TS(T) and sets RT(Xt) := max(RT(Xt), TS(T)). Reads never abort.
  3. A write wT(X) is rejected (T rolled back) if the version Xt with the largest t ≤ TS(T) has RT(Xt) > TS(T): a later reader already read Xt when it should have read T's value.
  4. Versions older than Xt can be deleted once no active transaction has a timestamp less than t.

Write rejection example (slide 33): versions X₅₀ (RT = 80) and X₁₀₀; a transaction with TS 60 writing X would follow X₅₀, whose read time 80 > 60, so it is rolled back.

Summary: MVCC keeps a version of each element per writer. A read gets the latest version written at or before its timestamp, so reads never abort. A write is rejected if the version it would follow has already been read by a later transaction. Versions older than Xt are discarded once no active transaction is older than t. Timestamping (especially multiversion) suits read-mostly, low-conflict workloads; locking suits high-conflict ones; systems often use 2PL for writers and multiversion reads for read-only transactions.
