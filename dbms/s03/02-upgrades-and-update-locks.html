Lock Upgrades and Update Locks

A transaction that reads X and only later writes it can take a shared lock first and upgrade it. That allows more concurrency, but two transactions upgrading the same element deadlock. The update lock, a third mode, removes that deadlock. Includes the asymmetric S/X/U compatibility matrix and three exam questions.

1. Upgrading a lock (slide 6)

Lock upgrade
A transaction T that holds a shared lock on X later requests an exclusive lock on X as well. The request is granted only when no other transaction holds a lock on X; until then T waits. (ui(X) releases all of Ti's locks on X.)

Slide 6's example (textbook Example 18.15): T₁ reads A and B, does a possibly long computation with them, and finally writes B. T₂ only reads A and B.

T₁: sl₁(A); r₁(A); sl₁(B); r₁(B); xl₁(B); w₁(B); u₁(A); u₁(B);
T₂: sl₂(A); r₂(A); sl₂(B); r₂(B); u₂(A); u₂(B);

Slide 6 question: why does upgrading allow more concurrency?

With upgrading, T₁ gets a shared lock on B even though T₂ is also reading B, so T₁ can read B and do its whole computation while T₂ is running. Only the final write has to wait for T₂ to release B. If T₁ had asked for an exclusive lock on B up front, that request would have been denied (T₂ holds S on B), and T₁ could not even read B until T₂ finished; all of its computation would then happen after T₂, and T₁ would finish later. Upgrading keeps the exclusive period as short as possible. The schedule is still conflict-serializable (order (T₂, T₁): T₂ unlocks first).

2. Upgrades can deadlock (slide 7)

Indiscriminate upgrading is a new source of deadlock (textbook Example 18.16). Let both transactions read A and then write it, both using the upgrade approach:

Both get shared locks on A (compatible). Then each asks to upgrade, and each is refused because the other holds a shared lock on A. Each waits for the other forever, or until the system detects the deadlock, aborts one, and gives the other its exclusive lock. This happens whenever two such transactions start at about the same time, which in a busy system is often.

3. Update locks (slides 8–9)

Update lock (U), uli(X)
A lock that gives Ti the right to read X (not write it), with the extra property that only an update lock can later be upgraded to an exclusive lock; a shared lock cannot. A transaction takes an update lock on X when it intends to write X later.

The slide's wording has a slip: it says “an exclusive lock can be upgraded to an exclusive lock later”. The intended rule is “an update lock can be upgraded to an exclusive lock later; a shared lock cannot”.

Granting rule. An update lock can be granted on X when others hold only shared locks on X. But once someone holds an update lock on X, no other lock of any kind (S, U or X) is granted on X. The reason: if new shared locks kept being granted, the updater might never get its chance to upgrade, because there would always be some reader holding X.

So a U lock looks like a shared lock when it is requested, and like an exclusive lock when it is held. That gives an asymmetric matrix: the U column equals the S column, and the U row equals the X row.

S/X/U compatibility matrix (textbook Fig. 18.19)

Slide 9's first note reads “no lock can be granted on X if another transaction is holding an update/exclusive/shared lock”. The word “shared” does not belong there: with a shared lock held, S and U can still be granted (the second note and the matrix say so). Correct reading: no lock can be granted if another transaction holds an update or exclusive lock; a shared or update lock can be granted while others hold shared locks.

Update locks remove the upgrade deadlock

T₁: ul₁(A); r₁(A); xl₁(A); w₁(A); u₁(A);
T₂: ul₂(A); r₂(A); xl₂(A); w₂(A); u₂(A);

Now T₂, the second to request an update lock on A, is denied at once, before it holds anything on A. T₁ upgrades without obstruction, writes, and unlocks; then T₂ proceeds. The two transactions effectively run one after the other, which is the only correct outcome here: any real overlap of two read-then-write transactions on the same element ends either in deadlock or in a lost update.

Update locks change nothing in Figure 1's example: T₁ would take ul₁(B) instead of sl₁(B), which is granted since only shared locks are held on B, and the same sequence follows.

(The textbook's §18.4.5 adds increment locks; they are outside this course's syllabus and not on the slides.)

Try it

Type only reads and writes and choose how the scheduler inserts locks: “S and X (upgrade)” reproduces the deadlock for r1(A) r2(A) w1(A) w2(A); “S, U and X” does not.

DB QB · 24-25 2c · 12 marks  |  BUET QBank · CSE 215 | L-2/T-1 | 2024–25 · 10 marks

Consider the two transactions given below:
T₁: sl₁(A); xl₁(B); u₁(A); u₁(B);
T₂: sl₂(B); xl₂(A); u₂(B); u₂(A);
(i) Show a schedule that results in a deadlock but is conflict-serializable to (T₂, T₁).
(ii) Does introducing update lock in the transactions solves the deadlock problem? Justify your answer.
(iii) Show the lock compatibility matrix for shared, exclusive, and update locks, indicating in each cell whether concurrent locks are allowed ("Yes") or not allowed ("No").

Show worked answer

T₁ reads A and writes B; T₂ reads B and writes A (the lock modes tell us which accesses happen).

(i) Schedule:

sl₂(B); r₂(B); sl₁(A); r₁(A); xl₂(A) denied; xl₁(B) denied

T₂ waits for A (T₁ holds S on A) and T₁ waits for B (T₂ holds S on B): the waits-for graph is T₁ ⇄ T₂, a deadlock (Figure 4). The part that executed, r₂(B); r₁(A), contains no conflicting pair (no write has happened), so its precedence graph has no arcs and it is conflict-equivalent to every serial order, in particular to (T₂, T₁). Moreover, if the deadlock is broken by aborting T₁ (the usual choice, rolling back the one that has done less), T₂ completes and the restarted T₁ runs after it: the final execution is exactly the serial schedule (T₂, T₁).

(ii) No. Update locks prevent only the upgrade deadlock, where two transactions hold shared locks on the same element and both try to upgrade it. Here the transactions wait for locks on different elements, each holding the element the other needs. Replacing sl by ul gives ul₁(A); ul₂(B); xl₁(B) denied (U held by T₂); xl₂(A) denied (U held by T₁): still a cycle (Figure 5). (Update locks are not even the right tool: neither transaction upgrades a lock; each reads one element and writes another.) This deadlock is avoided by ordering lock requests (e.g., every transaction locks A before B) or handled by detection and abort.

DB QB · 23-24 7b · 12 marks  |  BUET QBank · CSE 215 | L-2/T-1 | 2023–24 · 12 marks

Consider the following transactions T₁ and T₂ that use locks to preserve database consistency:
T₁: l₁(A), r₁(A), w₁(A), u₁(A)
T₂: l₂(A), r₂(A), w₂(A), u₂(A)
(i) Do the transactions cause a deadlock when they are executed concurrently? Justify your answer.
(ii) Use "shared" and "exclusive" locks with lock upgrades to improve concurrency. Show the resulting transactions.
(iii) After incorporating lock upgrades in the given transactions, show a concurrent schedule that causes a deadlock.
(iv) Use "update" locks to solve the deadlock problem appeared in question (iii) above. Show the resulting transactions.

Show worked answer

(i) No. Each transaction needs only one lock, on A. A deadlock needs a transaction that holds a lock while waiting for another lock, so that waits form a cycle. Whichever transaction gets l(A) first runs to u(A) without waiting for anything; the other just waits for that unlock and then proceeds (e.g., l₁(A) r₁(A) l₂(A)-denied w₁(A) u₁(A) l₂(A) r₂(A) w₂(A) u₂(A)). The waits-for graph has at most one arc, never a cycle.

(ii) Read under a shared lock and upgrade only for the write, so the two can read A at the same time:

T₁: sl₁(A); r₁(A); xl₁(A); w₁(A); u₁(A);
T₂: sl₂(A); r₂(A); xl₂(A); w₂(A); u₂(A);

(iii) sl₁(A); r₁(A); sl₂(A); r₂(A); xl₁(A) denied (T₂ holds S on A); xl₂(A) denied (T₁ holds S on A). Each waits for the other: deadlock (Figure 2 above shows this exact schedule).

(iv) Each transaction takes an update lock for the read, because it will write later:

T₁: ul₁(A); r₁(A); xl₁(A); w₁(A); u₁(A);
T₂: ul₂(A); r₂(A); xl₂(A); w₂(A); u₂(A);

Now ul₁(A); r₁(A); ul₂(A) is denied (U is incompatible with a held U), so T₂ waits while holding nothing; T₁ upgrades (xl₁(A) granted, since only T₁ holds A), writes, unlocks; then T₂ runs. No deadlock (Figure 3 above).

DB QB · 22-23 3c · 10 marks  |  BUET QBank · CSE 215 | L-2/T-1 | 2022–23 · 10 marks

Consider the following two transactions that use shared (sli(X)) and exclusive (xli(X)) locks:
T₁: sl₁(A); r₁(A); xl₁(A); w₁(A); u₁(A); c₁
T₂: sl₂(A); r₂(A); xl₂(A); w₂(A); u₂(A); c₂
(i) Construct a concurrent schedule of T₁ and T₂ that results in a deadlock due to lock upgrading.
(ii) Modify the given transactions using update (uli(X)) lock to prevent deadlocks.

Show worked answer

(i)

sl₁(A); r₁(A); sl₂(A); r₂(A); xl₁(A) denied; xl₂(A) denied

Both hold shared locks on A (S is compatible with S). Each upgrade request needs every other transaction's lock on A to be released, but the other is itself waiting: T₁ → T₂ → T₁ in the waits-for graph. Neither reaches u(A) or c.

(ii)

T₁: ul₁(A); r₁(A); xl₁(A); w₁(A); u₁(A); c₁
T₂: ul₂(A); r₂(A); xl₂(A); w₂(A); u₂(A); c₂

Only one transaction can hold U on A, so the second ul request waits before its transaction holds anything on A; the first upgrades to X freely, finishes and unlocks, and then the second proceeds. The S–S overlap that caused the cycle can no longer happen.

Summary: a transaction can read under a shared lock and upgrade to exclusive just before writing, which lets it work concurrently with readers. Two transactions upgrading the same element deadlock. An update lock (granted only when others hold at most shared locks, and blocking all new locks once held) is the only lock that may be upgraded, so at most one transaction can be heading for an upgrade on an element, and the upgrade deadlock disappears. Update locks do not prevent deadlocks on different elements.
