Shared and Exclusive Locks

With a single kind of lock, two transactions that only read X still block each other. Shared locks for reading and exclusive locks for writing fix that. This chapter gives the rules for the two modes, the compatibility matrix, the slides' example, and a scheduler you can run on your own schedules.

1. Two lock modes (slide 2)

Lec 02's single lock had to be taken for any access, even a read. That is wasteful: any number of transactions can read X at the same time without harm, as long as nobody writes X meanwhile. So the scheduler uses two kinds of lock:

Shared lock (S, read lock), sli(X)
Requested by Ti when it wants to read X but not write it. Several transactions may hold shared locks on X at once.
Exclusive lock (X, write lock), xli(X)
Required for writing X (and also allows reading). While Ti holds it, no other transaction may hold any lock on X.
ui(X)
Ti releases all its locks on X (whatever their modes).

An exclusive lock is stronger than a shared one: it prevents both reads and writes by others, while a shared lock only prevents writes. So if a transaction only wants to read, it should take only a shared lock.

2. The three requirements (slides 3–4)

Lec 02's rules carry over, adjusted for two modes (textbook §18.4.1):

1. Consistency of transactions
(a) A read ri(X) must be preceded by sli(X) or xli(X), with no ui(X) in between. (b) A write wi(X) must be preceded by xli(X), with no ui(X) in between. Every lock must later be followed by an unlock of the same element.
2. Two-phase locking of transactions
All locking actions precede all unlocking actions: no sli(X) or xli(X) may come after any ui(Y).
3. Legality of schedules
An element may be locked exclusively by one transaction, or in shared mode by several, but not both. (a) If xli(X) appears, there cannot be a later xlj(X) or slj(X), j ≠ i, without ui(X) in between. (b) If sli(X) appears, there cannot be a later xlj(X), j ≠ i, without ui(X) in between.

Note what legality does not forbid: sli(X) followed by slj(X) (shared with shared), and one transaction holding both a shared and an exclusive lock on the same element. A transaction that knows in advance it will write X can simply ask for xl(X); one that only discovers later that it must write can ask for sl(X) first and xl(X) later (an upgrade, Chapter 2).

The proof of Lec 02 Chapter 7 still works unchanged: a legal schedule of consistent 2PL transactions with shared and exclusive locks is conflict-serializable, and the transaction that unlocks first can be placed first.

3. The compatibility matrix (textbook §18.4.2)

Compatibility matrix
A table with a row for each mode a lock may be held in by another transaction, and a column for each mode that may be requested. A lock on X in mode C can be granted if and only if, for every mode R in which some other transaction holds a lock on X, the entry in row R, column C is “Yes”.

The S column says a shared lock can be granted if the only locks on X are shared locks. The X column says an exclusive lock can be granted only if no other transaction holds any lock on X. Note that locks held by the requester itself are not checked against the matrix.

4. Slide 5: an example

T₁: sl₁(A); r₁(A); xl₁(B); r₁(B); w₁(B); u₁(A); u₁(B);
T₂: sl₂(A); r₂(A); sl₂(B); r₂(B); u₂(A); u₂(B);

Both read A and B; only T₁ writes B; nobody writes A. In the slide's interleaving T₁ gets a shared lock on A, then T₂ gets shared locks on A and B. When T₁ asks for an exclusive lock on B it is denied, because T₂ holds a shared lock on B. T₁ waits until T₂ unlocks:

The slide notes that the schedule is conflict-serializable. The equivalent serial order is (T₂, T₁), even though T₁ started first: r₂(B) comes before w₁(B), and T₂ unlocks before T₁, just as the 2PL proof predicts.

5. Run the scheduler

Type locks yourself (sl1(A) xl2(B) u1(A) …) with “Locks: as written”, or type only reads, writes and commits and let the scheduler insert shared and exclusive locks (as in Part I of the textbook's scheduler, Chapter 3). With commit actions, locks are released at commit.

BUET QBank · CSE 303 | L-3/T-1 | 2016–17 · 6 marks

Mention the requirements of using shared and exclusive locks.

Show worked answer
  1. Consistency of transactions. A read ri(X) must be preceded by sli(X) or xli(X) with no intervening ui(X); a write wi(X) must be preceded by xli(X) with no intervening ui(X); every lock must eventually be followed by an unlock of the same element.
  2. Two-phase locking of transactions. In each transaction no sli(X) or xli(X) may be preceded by any ui(Y): all locks before all unlocks.
  3. Legality of schedules. An element is locked either exclusively by one transaction or in shared mode by any number, never both: after xli(X) there is no xlj(X) or slj(X) (j ≠ i) without ui(X) in between; after sli(X) there is no xlj(X) (j ≠ i) without ui(X) in between.

The scheduler enforces legality through the compatibility matrix (S–S Yes, all other pairs No). A transaction may hold both an S and an X lock on one element. With all three requirements, every schedule is conflict-serializable.

Show and explain the lock compatibility matrix with examples.

Show worked answer

Rows: mode in which another transaction already holds a lock on X. Columns: mode requested. Grant the request iff every held mode's row has “Yes” in the requested column.

SYesNoYes

(The S/X matrix is the top-left 2 × 2 part; the U row and column are for update locks, Chapter 2.)

  • S held, S requested: Yes. sl₁(A); sl₂(A): T₁ and T₂ both read A; reads do not interfere.
  • S held, X requested: No. sl₂(B); xl₁(B): T₁ must wait until T₂ unlocks B, otherwise T₂ might read B before and after T₁'s write (slide 5's example).
  • X held, S or X requested: No. xl₁(A); sl₂(A): T₂ may not read A while T₁ may still change it (that would be a dirty or inconsistent read).
  • S held, U requested: Yes; U held, anything requested: No. An update lock is requested like a shared lock but, once held, blocks everyone, so its holder can later upgrade to X.

The matrix is used with the group mode of a lock-table entry, so the scheduler checks one value instead of every holder (Chapter 3).

BUET QBank · CSE 303 | L-3/T-1 | 2016–17 · 9 marks  |  BUET QBank · CSE 303 | L-3/T-1 | 2012–13 · 10 marks

Consider the following schedule: r₁(A); r₂(B); r₃(C); w₁(B); w₂(C); w₃(D). Insert shared and exclusive locks and place necessary unlocks to maximise concurrency. (2012–13 wording: insert shared and exclusive locks and place necessary unlocks in appropriate positions.)

Show worked answer

Each transaction reads one element and writes another: T₁ reads A, writes B; T₂ reads B, writes C; T₃ reads C, writes D. Reads get S locks, writes get X locks.

Two-phase locked version (guarantees serializability). To maximise concurrency under 2PL, each transaction releases each lock as early as 2PL allows: its S lock right after it has obtained its X lock (its lock point), and its X lock right after the write.

T₁: sl₁(A); r₁(A); xl₁(B); u₁(A); w₁(B); u₁(B);
T₂: sl₂(B); r₂(B); xl₂(C); u₂(B); w₂(C); u₂(C);
T₃: sl₃(C); r₃(C); xl₃(D); u₃(C); w₃(D); u₃(D);

Run in the given order: the three S locks are granted. xl₁(B) is denied (T₂ holds S on B), so T₁ waits. xl₂(C) is denied (T₃ holds S on C), so T₂ waits. xl₃(D) is granted; T₃ unlocks C and writes D. Now xl₂(C) is granted; T₂ unlocks B and writes C. Now xl₁(B) is granted and T₁ finishes. The reads and writes reach the database as r₁(A) r₂(B) r₃(C) w₃(D) w₂(C) w₁(B), equivalent to the serial order (T₃, T₂, T₁). Step through it in Figure 2 below.

Unlock-immediately version (most concurrency, not 2PL). If each transaction unlocks right after each access (sl₁(A); r₁(A); u₁(A); … xl₁(B); w₁(B); u₁(B); …), nothing ever waits and the given order runs unchanged. The transactions are then not two-phase locked (each locks B, C or D after unlocking), so serializability is no longer guaranteed in general. Here the result happens to be conflict-serializable: r₂(B) before w₁(B) gives T₂ → T₁ and r₃(C) before w₂(C) gives T₃ → T₂, again the order (T₃, T₂, T₁).

BUET QBank · CSE 303 | L-3/T-1 | 2013–14 · 10 marks

Consider the following schedule involving transactions T₁, T₂, and T₃: r₁(A), r₂(B), r₃(C), r₁(B), r₂(C), r₃(D), w₁(A), w₂(B), w₃(C). Insert shared locks, exclusive locks, and unlock actions in appropriate places. Tell what happens when the schedule is run by a scheduler supporting shared and exclusive locks.

Show worked answer

T₁ reads A and B, then writes A; T₂ reads B and C, then writes B; T₃ reads C and D, then writes C. Each transaction reads the element it later writes, so it takes a shared lock first and upgrades to exclusive just before the write (2PL: all unlocks at the end):

T₁: sl₁(A); r₁(A); sl₁(B); r₁(B); xl₁(A); w₁(A); u₁(A); u₁(B);
T₂: sl₂(B); r₂(B); sl₂(C); r₂(C); xl₂(B); w₂(B); u₂(B); u₂(C);
T₃: sl₃(C); r₃(C); sl₃(D); r₃(D); xl₃(C); w₃(C); u₃(C); u₃(D);

What happens (Figure 3): all six shared locks are granted, because S is compatible with S (T₁ and T₂ share B; T₂ and T₃ share C). xl₁(A): only T₁ holds a lock on A, so the upgrade is granted; T₁ writes A and unlocks A and B. xl₂(B): T₁ has released B, so it is granted; T₂ writes B and unlocks. xl₃(C): T₂ has released C, so it is granted; T₃ finishes. No transaction ever waits. The executed schedule is the given one, and it is conflict-serializable: r₁(B) before w₂(B) gives T₁ → T₂, r₂(C) before w₃(C) gives T₂ → T₃, so the order is (T₁, T₂, T₃), which is also the order in which they unlock.

If instead each transaction took an exclusive lock on its write element at the first read (no upgrades), xl₂(B) at r₂(B) would block T₁'s r₁(B), and xl₃(C) at r₃(C) would block T₂'s r₂(C): T₁ waits for T₂ and T₂ waits for T₃, so the transactions finish one after another in the order T₃, T₂, T₁. Less concurrency, same correctness.

Figure 4 steps through it. No downgrade is needed: at step 6 T₁ already holds X on B, which permits reading.

If locks are held until a later commit (strict 2PL; this is what the question bank's answer assumes), T₃ keeps its S lock on A, so T₁'s upgrade at step 10 must wait for T₃, and T₂ waits for T₁: the waits-for graph is T₂ → T₁ → T₃, a chain, not a deadlock; everything proceeds once T₃ commits. Note: the bank's answer “downgrades” T₁'s X(B) to S(B) at step 6. That is unnecessary, since an exclusive lock already allows reading, and releasing write privileges before commit would break strict 2PL.

Summary: read with a shared lock, write with an exclusive lock. Any number of shared locks may coexist; an exclusive lock excludes all other locks. The compatibility matrix (rows held, columns requested) encodes this: only S–S is Yes. Consistency, two-phase locking and legality are restated for the two modes, and the same proof shows that such schedules are conflict-serializable, in the order of the transactions' first unlocks.
