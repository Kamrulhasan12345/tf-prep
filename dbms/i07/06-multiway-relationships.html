Multi-Way Relationships and Converting Them to Binary

A contract involves an actor, a film and a studio at once. This chapter defines n-ary relationships, explains what an arrow means when three entity sets meet, decides where the salary goes, and converts the three-way relationship into an entity set with binary relationships, as slides 69–70 do.

1. Why the ER model matters (slide 62)

The Entity-Relationship model was introduced by Peter Chen in 1976. It gave database design a visual, conceptual notation, and it separates what the data means from how a DBMS later stores it. The same diagram can be implemented in Oracle, in PostgreSQL or even in a non-relational system. ER diagrams are still used because both technical and non-technical people can read them. (Chen's original notation writes 1, N, M on the lines; the slides use the arrow notation of the Garcia-Molina–Ullman–Widom textbook. Both describe the same model.)

2. Multi-way relationships (slides 63–64)

Multi-way (n-ary) relationship
A relationship that connects three or more entity sets at once. One recorded association chooses one entity from each participating entity set. If the entity sets are E1, E2, …, En, then formally R ⊆ E1 × E2 × ⋯ × En, a set of n-tuples. A relationship with three participants is ternary; the number of participants is the degree.

The key point of slide 63: a multi-way relationship represents one combined fact, not separate pairwise facts. "Shakib signed with Studio X to act in Film Y" is a single fact. Splitting it into binary relationships can lose information, as the animation shows.

3. Arrows in multi-way relationships (slide 65)

In a multi-way relationship, an arrow toward an entity set means uniqueness after fixing the other entity choices. With an arrow into Studio:

for each (actor, film) there is at most one studio in contract

In functional-dependency language (Sukarna sir's Lec 01), Actor, Film → Studio. The animation tests this on a small instance of contract.

A correction to slide 65. The slide says this constraint is "stronger than simply saying each actor has one studio". It is the other way round. "Each actor has one studio" (Actor → Studio) implies "each (actor, film) has one studio", because fixing the film as well cannot add studios. The arrow allows an actor to work with Studio X on one film and Studio Y on another, which "each actor has one studio" forbids. So the arrow is the weaker (less restrictive) and more precise statement; what the slide means is that it is different from a per-actor rule and should not be confused with it.

Lines without arrows (Actor, Film) mean "many": for a given (film, studio) there can be many actors, and for a given (actor, studio) many films.

4. Where should the salary go? (slides 66–68)

Salary is not a property of only the actor, only the film or only the studio. It describes the whole association, so it is an attribute of contract. Slide 68 gives the reasons and the test:

  • The salary is determined by the complete three-way fact.
  • Same actor, different film: the salary may differ.
  • Same actor and film, different studio: the salary may differ.

Test (slide 68)

After fixing all entities connected by the relationship, is there one value for this attribute? For salary: fix actor, film and studio, and there is exactly one contract salary. So salary belongs on contract.

(With the arrow into Studio, the pair (actor, film) already determines the studio, so in practice salary is also fixed by (actor, film). That does not move salary onto any one entity set; it only means the table for contract will have the key (actor, film), Chapter 11.)

5. Converting a multi-way relationship to binary (slides 69–71)

Some notations and tools allow only binary relationships (UML, many CASE tools, the ODL language). The standard conversion:

  1. Replace the multi-way relationship by a new entity set (here Contracts). Each entity of it represents one occurrence of the association: one contract.
  2. Move the relationship's attributes (salary) to the new entity set.
  3. Connect the new entity set to each original entity set by a binary relationship: signedBy (Actor), forMaking (Film), ownerOf (Studio).
  4. Multiplicity (slide 70): each contract is for one actor, one film and one studio, while an actor, film or studio may appear in many contracts. So every new relationship is many-to-one from Contracts, with the arrow pointing from the diamond toward the original entity set.

Why create a new entity (slide 71)? The new entity can have its own attributes (salary, signing date, duration, cancellation status); it can connect to other relationships later (a contract may be approved by a lawyer); and it makes constraints easier to state when the association itself becomes important. Slide 71's example: a contract with salary, signing date, duration and cancellation status has enough structure to be an entity set.

One thing is lost: the arrow "for each (actor, film) at most one studio" cannot be drawn in the binary version, because no single binary relationship sees both the actor and the film. It must be written as a design note (and later enforced by a UNIQUE (actor, film) constraint on the Contracts table). The textbook (§4.1.10 of Garcia-Molina et al.) gives the same construction and calls the new entity set a connecting entity set.

DB QB · 24-25 7b · 8 marks  ·  BUET QBank · CSE 215 | L-2/T-1 | 2024–25 · 8 marks

Write the general procedure to convert ternary relationship to binary relationships.

Show worked answer

Let R be a ternary relationship among entity sets A, B and C (keys a, b, c), possibly with attributes.

  1. Create a connecting entity set E to stand for R. Each tuple (ai, bj, ck) of R becomes one entity e of E. Give E an identifying attribute: either a new surrogate key (e.g. contract_id), or treat E as a weak entity identified through its three relationships, whose key is then (a, b, c).
  2. Move R's attributes to E (e.g. salary).
  3. Create three binary relationships RA (E–A), RB (E–B), RC (E–C). For each e created from (ai, bj, ck), add (e, ai) to RA, (e, bj) to RB, (e, ck) to RC.
  4. Multiplicities: each RX is many-to-one from E to X (arrow into A, B and C), and E participates totally in all three, because every occurrence involves exactly one entity of each set. A, B and C may appear in many E's.
  5. Carry over constraints. A constraint of R that involves several participants, such as an arrow into C (A, B → C), cannot be drawn on the binary relationships; record it as a design note, and enforce it later as a UNIQUE (a, b) constraint on E's table. If E uses a surrogate key, also declare (a, b, c) UNIQUE so the same triple is not stored twice.

Do not replace R by the three pairwise relationships A–B, B–C, A–C: that loses information (the pairs can be recombined into triples that never happened; see the animation in section 2).

In tables (Chapter 11) both designs give Contracts(actor_id, film_title, film_year, studio_name, salary) with three foreign keys, or, with a surrogate key, Contracts(contract_id, actor_id, film_title, film_year, studio_name, salary).

DB QB · 22-23 6b · 5 marks  ·  BUET QBank · CSE 215 | L-2/T-1 | 2022–23 · 5 marks

Give an example of a Non-Binary Relationship. What issues arise for Non-Binary Relationships?

Show worked answer

Example. Supplier S supplies part P to project J, with a quantity: a ternary relationship supplies among Supplier, Part and Project. One fact names all three; "S1 supplies P1" and "P1 is used in J1" do not tell us that S1 supplied P1 to J1.

Issues.

  1. Cannot be split into binary relationships without losing information. Store {(S1,P1,J2), (S1,P2,J1), (S2,P1,J1)}. The pairwise projections are SP = {(S1,P1),(S1,P2),(S2,P1)}, PJ = {(P1,J2),(P2,J1),(P1,J1)}, SJ = {(S1,J2),(S1,J1),(S2,J1)}. Recombining them gives also (S1,P1,J1), which never happened. (Checked by joining the three projections.)
  2. Multiplicity is harder to read and to state. An arrow into one entity set means "the others together determine it", not "each of the others determines it" (slide 65). Several arrows on one multi-way relationship are ambiguous, which is why Silberschatz allows at most one arrow. Constraints between only two of the participants cannot be drawn at all.
  3. Many notations and tools support only binary relationships (UML class diagrams, ODL, many design tools), so the relationship must be converted to a connecting entity set with binary relationships (slides 69–70). The conversion cannot draw arrows like (S, P) → J; they become design notes.
  4. Every tuple needs all participants. We cannot record that a supplier can supply a part before any project needs it, because a tuple needs a project. If that fact matters, add a separate binary relationship (Supplier–Part "canSupply"), which is a different fact.
  5. Wider keys in tables. The relationship's table has a composite key of all (or all but the "one") participants' keys, and queries join several tables.

The question bank's answer covers the same points; its claim that a NULL project must be stored for a not-yet-assigned part describes a bad workaround, not a requirement. The correct design is a separate binary relationship, as in point 4.

DB QB · 20-21 6c · 5 marks  ·  BUET QBank · CSE 215 | L-2/T-2 | 2020–21 · 5 marks

Consider the following multi-way relation between Actor, Film and Studio. Answer the following questions based on this relationship: (i) There is an arrow pointing to entity set Studios. What is its interpretation? (ii) There are no arrows pointing to entity sets Actor or Film. What are their interpretations?

Show worked answer

(i) The arrow into Studio means: once an actor and a film are fixed, there is at most one studio with which that actor has a contract for that film. In FD form, (Actor, Film) → Studio. It does not say an actor works with only one studio overall: the same actor may have contracts with different studios for different films.

(ii) No arrow into Actor: for a fixed film and studio there may be many actors (a studio signs the whole cast of a film). No arrow into Film: for a fixed actor and studio there may be many films (an actor makes several films for the same studio). Consequently a contract is identified by (actor, film); in a table its key is (actor_id, film_id) and studio_name is an ordinary foreign-key column.

Summary: a multi-way relationship records one combined fact over three or more entity sets, R ⊆ E1 × ⋯ × En; splitting it into pairs loses information. An arrow into an entity set means the other participants together determine it. Attributes that depend on all participants (salary) go on the relationship. To convert to binary, make a connecting entity set, move the attributes to it, and connect it by many-to-one relationships to each original entity set; multi-participant constraints become design notes.
