From ER Diagram to Tables, Rule by Rule

Almost every ER exam question ends with "convert the diagram into a relational schema". The conversion is mechanical: eleven rules, the first nine animated here on one university diagram, with the result as runnable Oracle CREATE TABLE statements. Then the figure-based exam questions, all worked.

The slides stop at the diagram. Converting it to tables is taught in the textbook (Garcia-Molina et al. §4.5–4.6; Silberschatz §6.7; Elmasri–Navathe ch. 9) and asked in nearly every paper. The notation for results: Table(pk, column, fk), with each foreign key's target listed under it.

1. The rules

#ER elementBecomes
1Strong entity setA table; simple attributes are columns; its key is the primary key.
2Composite attributeOnly its components become columns (flattened); the composite name disappears.
3Multivalued attributeA new table (owner key, value); primary key = all columns; owner key is a foreign key.
4Derived attributeNot stored; computed by a query or view.
5Weak entity setA table with the owner's key added; primary key = owner key + partial key; no table for the identifying relationship.
6Many-to-one (1:N) relationshipNo new table: put the key of the "one" side into the "many" side's table as a foreign key, with the relationship's attributes. NOT NULL if participation of the many side is total.
7One-to-one relationshipA foreign key on either side (prefer the side with total participation, NOT NULL), declared UNIQUE.
8Many-to-many relationshipA new table with both keys (each a foreign key) and the relationship's attributes; primary key = both keys.
9Recursive relationshipAs rule 6 or 8, with the key columns renamed by role.
10Multi-way relationshipA new table with the keys of all participants and its attributes; primary key = keys of the participants without an arrow.
11isA hierarchyThree strategies (E/R, object-oriented, nulls): Chapter 12.

Rule 6 is an optimisation: the textbook's basic rule turns every relationship into a table (keys of both sides plus attributes) and then merges a many-to-one relationship's table into the "many" entity's table, because both have the same key. The merged result is what exams expect when they say "minimum" or "fewest" relations. When the many side's participation is partial and most entities have no partner, keeping a separate table avoids many NULLs; both answers are correct if stated.

3. Multi-way relationships (rule 10)

A multi-way relationship becomes a table with the keys of all its participants. Which of them form the primary key depends on the arrows: an arrow into Studio says (actor, film) determines the studio, so the key is (actor, film) and the studio is an ordinary (foreign-key) column. With no arrows, the key is all three.

4. Common mistakes in conversions

  • Making a table for every many-to-one relationship when the question asks for the minimum number of relations.
  • Putting the foreign key on the wrong side of a many-to-one: it goes into the "many" side (Course gets dept_id), never the "one" side (a department cannot hold a list of course codes in one column).
  • Forgetting part of a composite key: a foreign key to Section must carry all of (code, sec_no, semester).
  • Giving the M:N table only one key column as primary key: then a student could enroll in only one section.
  • Storing derived attributes without saying why.
  • Forgetting NOT NULL / UNIQUE that come from total participation and one-to-one relationships.

DB QB · 24-25 8d · 10 marks  ·  BUET QBank · CSE 215 | L-2/T-1 | 2024–25 · 10 marks

How composite attributes and multivalued attributes are handled when an ER model is transformed into relational database schema. Explain with examples.

Show worked answer

Composite attributes are flattened. The relational model allows only atomic column values, so a composite attribute is replaced by its leaf components; the composite's own name does not appear. Example: Employee(emp_id, name(first, last), address(street, city)) becomes Employee(emp_id, first, last, street, city). (If a component is itself composite, keep descending to the leaves.) Prefixing helps when two composites share component names (home_city, office_city).

Multivalued attributes get their own table. One column cannot hold several values (first normal form), and phone1, phone2, … is an unstable design (slide 17). So a multivalued attribute M of entity set E becomes a table E_M(key of E, M): one row per value, the owner's key as a foreign key (usually ON DELETE CASCADE), primary key = all columns. Example: {phone} of Employee becomes Employee_Phone(emp_id, phone). If the multivalued attribute is composite (several {address(street, city)}), the new table has all its components, and the key is the owner key plus enough components to be unique.

Reading the arrows. Each arrowhead is drawn on the line belonging to one entity set (B for R1, R4, R5; C for R3), so we read it as marking that entity set as the "one" side, as in Chen's "1" label. (The printed arrowheads touch the diamonds instead of the entity sets; that is a drawing quirk. State this assumption in the exam.)

RelationshipTypeTreatment
R1 (A, B)many A : one Bb1 goes into A
R2 (A, C)many-to-manyown table R2(a1, c1)
R3 (C, D)many D : one Cc1 goes into D
R4 (B, D)many D : one Bb1 goes into D
R5 (B, C)many C : one Bb1 goes into C

Minimum: 5 relations: B(b1, b2); A(a1, a2, b1); C(c1, c2, b1); D(d1, d2, c1, b1); R2(a1, c1). The question bank's answer is the same.

The other possible reading. In Ramakrishnan–Gehrke's notation an arrow drawn from an entity set to a diamond is a key constraint: each entity of that set takes part in at most one instance. Read that way, each B has at most one A, one C and one D, and each C at most one D, so the foreign keys go the other way: A(a1, a2); B(b1, b2, a1, c1, d1); C(c1, c2, d1); D(d1, d2); R2(a1, c1). It is also 5 relations. Either answer earns full marks if the reading is stated; the first matches the question bank.

Account branch and Loan branch are many-to-one into Branch with total participation of Account and Loan: each account (loan) belongs to exactly one branch. Depositor and Borrower have no arrows: many-to-many.

BUET QBank · CSE 303 | L-3/T-1 | 2011–12 · 5 marks

A database schema consists of four relations: Product(maker, model, type), PC(model, speed, ram, hd, price), Laptop(model, speed, ram, hd, screen, price), Printer(model, color, type, price). Suggest suitable keys and foreign keys of the above relations.

Show worked answer

This is the textbook's (Garcia-Molina et al. Exercise 2.4.1) schema, which is the E/R-style conversion of an isA hierarchy: Product is the superclass and PC, Laptop, Printer are subclasses (Chapter 12). A maker makes many models, so maker is not a key; model numbers are unique across all products.

  • Product: primary key model.
  • PC, Laptop, Printer: primary key model; and model is a foreign key referencing Product(model), so every PC/laptop/printer is listed as a product.
  • Optionally a CHECK on Product.type ∈ {'pc', 'laptop', 'printer'}. (Printer.type, e.g. 'laser', is a different attribute from Product.type.)

Summary: entity sets become tables keyed by their keys; composites flatten; multivalued attributes get a table keyed by owner key + value; derived ones are computed. Weak entities borrow the owner key into their primary key. Many-to-one relationships add the "one" side's key to the "many" side (NOT NULL if total); one-to-one adds a UNIQUE foreign key; many-to-many and multi-way relationships become tables keyed by the participants' keys (minus those with arrows). Rename columns by role in recursive relationships.
