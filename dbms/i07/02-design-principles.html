Relationship Attributes and Design Principles

Where does a fact belong: on an entity, on a relationship, or in an entity set of its own? This chapter answers that question with the slides' rules of thumb and the four design principles of Part 2: represent the domain, avoid duplication, choose the right element, do not overcomplicate.

1. Relationship attributes (slide 15)

A relationship can have its own attributes. Such an attribute belongs to the association, not to either entity alone. The standard example is a grade:

Why not put grade on Student? A student has many grades, one per course, so "Amina's grade" is not one value. Why not on Course? A course has many grades, one per student. The value is fixed only when both the student and the course are fixed: Amina in CSE101 got an A. That is exactly the definition of an attribute of the relationship: for each pair in the relationship set there is one value.

for each pair (student, course) in enrolls → exactly one grade

Chapter 6 states the same test for relationships with three or more entity sets (slide 68): after fixing all entities connected by the relationship, is there one value for this attribute? If yes, the attribute belongs on the relationship.

2. Entity or attribute? (slides 16–18)

Some facts can be drawn as simple attributes; some deserve their own entity set. The choice depends on what the system must remember. Slide 16 gives the question to ask:

Ask

Is this just one descriptive value, or is it an object we need to describe, count, reuse, or connect?

An employee's name and salary are single descriptive values, so they stay as attributes (left figure below). Addresses are different. Slide 17 shows what goes wrong when an employee may have several addresses and we keep them as attributes: we invent addr1, addr2, addr3.

That design has three problems:

  1. How many address attributes should we create? Three is too few for someone with four addresses and wasteful (mostly empty) for everyone with one. There is no right number, so the design is not stable.
  2. It hides facts about each address. An address has internal structure (street, city, postal code). With addr1 as one string we cannot ask "which employees live in Dhaka?" reliably.
  3. Queries become awkward. "Find the employee living at 12 Lake Road" must check addr1 OR addr2 OR addr3.

Slide 18's fix is to model repeating values as entities. Make Address an entity set with attributes street, city and postal code, and connect it to Employee with a relationship addrOf. Now an employee can have any number of addresses, each address is described properly, and an address can even be shared by two employees who live together.

Rule of thumb (slide 18): use a new entity set when several values may exist, or when the value has useful internal structure. If we need to store several values or describe the value itself, choose an entity.

Chapter 10 shows a lighter alternative from the textbook, the multivalued attribute (a double oval), and Chapter 11 shows that both designs turn into the same kind of extra table.

3. Design principles (slides 19–20)

ER diagrams are not only about notation. A diagram should represent what is actually true in the domain, the same fact should not be modeled in several ways, and each kind of fact should use the right element (entity set, relationship or attribute). The guiding question for every fact: what does this fact mean in the real world, and where does it naturally belong in the ER model? The slides give four principles, which match the design principles in the textbook (Garcia-Molina et al., §4.2: faithfulness, avoiding redundancy, simplicity, choosing the right kind of element).

Principle 1: represent the domain (slide 21)

Draw a relationship only when that association is actually true and useful for the system to remember. A store's database records which person made which purchase of which product: that is a real, useful fact. A relationship isPresident between Person and Country may be true in the world, but a shop has no use for it, and if we drew it we would have to keep it correct. The textbook calls this faithfulness: the design must be faithful to the requirements, neither missing what they need nor adding what they do not. Faithfulness also covers multiplicity: if the real rule is "a course can have several instructors", the diagram must not say one.

Principle 2: avoid duplication (slide 22)

If ownedBy already connects a movie to its studio, storing studioName on Movie repeats the same fact. Redundancy has two costs. It wastes space, and, worse, the two copies can disagree: if a studio is renamed and only one copy is updated, the database contradicts itself. The fix is simple: delete the attribute studioName from Movie; the studio's name is reachable through ownedBy.

Principle 3: choose the right element (slide 23)

Here the relationship purchase carries personName and personAddr. These two attributes describe a person, not a purchase, so they indicate a missing Person entity set. With the attributes on the relationship, a person who buys ten things has their address stored ten times (duplication again), and a person who has not bought anything yet cannot be stored at all. The animation repairs the design by making Person an entity set and connecting it to purchase; date stays on purchase because it really describes one purchase.

Principle 4: do not overcomplicate (slide 24)

The opposite mistake is to create an entity set for every value. A date may simply be an attribute of a relationship. Here Date adds structure without adding meaning: an entity set with one attribute and no relationships of its own is just a value dressed up as a box. Make Date an entity only if dates have their own facts or relationships (for example a calendar of holidays with a name and a flag "office closed"). The principle: model enough structure to capture meaning, and no more. The textbook's version is simplicity counts.

Question (worked answer): Principles 3 and 4 seem to pull in opposite directions. How do we decide?

Use slide 16's question for each fact. personName and personAddr are facts about something else (a person) that has its own identity and appears in many purchases: that something deserves an entity set (Principle 3). The date is one value that describes the purchase itself and has nothing further to say about it: it stays an attribute (Principle 4). In short, promote a value to an entity set when it has its own attributes, identity or relationships; keep it as an attribute when it is a single descriptive value.

How can redundancy and incompleteness lead to a bad database design? Explain with appropriate examples.

Show worked answer

Redundancy means the same fact is stored more than once (Principle 2). Example: a single table Emp_Dept(emp_id, emp_name, dept_id, dept_name) stores the department name once per employee of that department.

emp_idemp_namedept_iddept_name
E101AliceD01Engineering
E102BobD02Marketing
E103CharlieD01Engineering

It causes three anomalies. Update anomaly: renaming D01 must change every Engineering row; if one row is missed the data contradicts itself. Insertion anomaly: a new department D03 Finance with no employees cannot be stored, because every row needs an emp_id (the key). Deletion anomaly: deleting Bob, the only Marketing employee, also deletes the fact that D02 is called Marketing. It also wastes space. In ER terms the department name is a fact about a Department, so Department should be its own entity set connected to Employee by worksIn; the schema becomes Department(dept_id, dept_name) and Employee(emp_id, emp_name, dept_id → Department), where each department name is stored once.

Incompleteness means the design cannot record facts the requirements need (a failure of Principle 1, faithfulness). Examples: (1) an Employee entity with attributes addr1, addr2 cannot store a fourth address (slide 17); (2) a Patient table with one column prescribed_drug cannot store a patient taking three drugs, nor the date, dose or prescribing doctor of each prescription, so history is lost every time the column is overwritten; (3) an enrollment design without a semester attribute cannot record that a student retook a course. Incompleteness forces users to cram several values into one column (breaking first normal form), invent dummy values, or lose information.

The fix for incompleteness is to model the missing structure: a Prescription relationship between Patient and Drug (and Doctor) with attributes date and dose, or an Address entity set. A good design is therefore both non-redundant (each fact once) and complete (every required fact has a place).

Summary: a fact that is fixed only when two or more entities are paired belongs on the relationship. Promote a value to an entity set when several values may exist, when it has internal structure, or when it connects to other things; keep single descriptive values as attributes. Represent only true and useful facts, store each fact once, put each fact on the right element, and add no structure that carries no meaning.
