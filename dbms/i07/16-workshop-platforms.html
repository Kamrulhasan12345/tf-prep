Lec 07 (Ishrak) · Chapter 16 · ER design workshop (exam questions)

ER Design Workshop III: YouTube, the BPL and a Hospital

Three large modern scenarios: a video platform designed feature by feature, a cricket league with two roles of one team in every game, and a hospital's drug treatment and payroll system. Each with assumptions, diagrams and schema.

1. Two techniques used here

Designing in portions. A big system is easier to draw as several small diagrams, one per feature, that share entity sets. The YouTube question asks for exactly that. Draw each shared entity set (User, Channel, Video) with its key in every portion, and its other attributes once.

Two relationships between the same pair of entity sets. A game has a host team and a guest team; a patient has a ward and also staff who attend. When the same two entity sets are related in two different ways, draw two relationships (or two role-labelled lines), never one relationship with a "type" attribute.

DB QB · 22-23 5a, 5b · 20 + 15 marks · Compulsory  ·  BUET QBank · CSE 215 | L-2/T-1 | 2022–23 · 20 + 15 marks

YouTube is a very popular platform for hosting videos. People create channels and upload videos on that. Sometimes the creators can batch up the videos into playlists. Videos can be free to view or behind paywall which requires subscription to YouTube Premium. A free video can be watched with or without signing into YouTube. However, only signed-in users' views are considered when counting the number of viewers for a video. A signed-in account may or may not have corresponding channels. Each video has a comment section where a signed-in user can comment; and comment to other people's comments. Also, videos contain some tags (given by the uploader or YouTube itself) that help to filter videos. Signed-in users can subscribe to other channels. Now, for each of the mentioned features below, design the corresponding portion of ERD for YouTube only. Add attributes as you see fit and mark primary keys.

(i) User management: Users should be able to create accounts, create channels on top of the accounts (one user can create at most one channel), and subscribe to different channels.
(ii) Video hosting: Creators should be able to upload videos with different tags, and create playlists by batching up multiple videos. Users should be able to view the videos, find them in their history when needed and, also, check the number of viewers to the videos.
(iii) Commenting: Users should be able to comment on any video any number of times, They should also be able to comment on other peoples comments.
(iv) Subscription system: Creators should be able to mark some videos as premium (i.e., only subscribed users can view). Users should be able to buy subscriptions up to some end date.

(5b) Implement relational schemas for each ERD you designed in Question 5a.

Show worked answer

Only signed-in users are stored: anonymous views of free videos are not counted, so the database needs no "guest" entity.

(i) User management

User(user_id, name, email, joined_on). Channel(channel_id, name, created_on). owns is one-to-one: a user creates at most one channel and a channel belongs to exactly one user (total for Channel; partial for User, since "an account may or may not have channels"). subscribesTo: User – Channel, many-to-many, attribute subscribed_on. Design note: a user does not subscribe to their own channel.

(ii) Video hosting

Video(video_id, title, description, upload_time, is_premium, /viewer_count). uploads: Video → Channel, many-to-one, total for Video. Tag(tag_name) is an entity set (tags are shared by many videos and used to filter); taggedWith: Video – Tag, many-to-many, attribute given_by ('uploader' or 'youtube'). Playlist(playlist_id, title) with creates: Playlist → Channel (many-to-one, total) and contains: Playlist – Video, many-to-many with position. watches: User – Video, many-to-many, attribute last_watched; this is the history, and viewer_count is derived as the number of distinct users who watched (so it is a dashed oval and not stored).

(iii) Commenting

"Any number of times" means a user may comment on the same video repeatedly, so Comment must be an entity set (a relationship would allow one comment per (user, video) pair). Comment(comment_id, text, posted_at). writes: Comment → User and on: Comment → Video, both many-to-one and total. Replies: recursive replyTo on Comment, many-to-one into the role parent (each reply has one parent; a comment has many replies; top-level comments have none). Design note: a reply is on the same video as its parent.

(iv) Subscription system

Premium is a flag on Video (is_premium, already in (ii)). A premium subscription is bought by a user and has its own facts and history (a user buys again when it ends), so Subscription(sub_id, start_date, end_date, amount) is an entity with buys: Subscription → User (many-to-one, total). Design note (business rule): a user may watch a premium video only if they have a subscription with start_date ≤ today ≤ end_date; this is checked by the application or a trigger on watches.

DB QB · 21-22 2a · 10 marks  ·  BUET QBank · CSE 215 | L-2/T-2 | 2021–22 · 10 marks

Suppose you are given the following requirements for a simple database for the Bangladesh premier League (BPL) in a season: The BPL has many teams. Each team has a name, a city, a coach, a captain, and a set of players. Each player belongs to only one team; a player may not be hired by any team. Each player has a name, a position during fielding (such as slip, mid-wicket, long on, long off etc), a ranking and a set of injury records. A team captain is also a player. Injury records must have an id, period (start and end), and a short description. A game is played between two teams (referred to as host_team and guest_team) and has a date (such as May 11th, 2023) and scores (winning and losing team scores such as 143/10 and 148/6). Construct a clean and concise E/R diagram for the BPL database using the notation as in your textbook. List your assumptions and clearly indicate the cardinality mappings as well as any role indicators in your E/R diagram.

Show worked answer

Assumptions.

  1. Team names are unique (key name). The coach is just a name (an attribute); if coaches had their own facts, Coach would be an entity set.
  2. Player(player_id, name, position, ranking): players can share names, so an id is assumed.
  3. playsFor: Player → Team, many-to-one ("belongs to only one team"), partial for Player ("may not be hired by any team"); total for Team ("a set of players").
  4. captain: Team → Player, one-to-one with roles (a team has one captain; a player captains at most one team), total for Team. Design note: the captain must play for that team.
  5. Injury records exist only for a player and their id is unique only per player, so InjuryRecord is weak, owned by Player: InjuryRecord(injury_id, start_date, end_date, description) with partial key injury_id, identifying relationship suffered. (If injury ids are unique league-wide, make it a strong entity with a many-to-one relationship; the tables are almost the same.)
  6. A game involves the same entity set Team twice, in two roles, host_team and guest_team. Two teams can meet more than once in a season, so Game is an entity set Game(game_id, game_date, host_score, guest_score) with two many-to-one relationships, hosts and visits, both total for Game. Scores like "143/10" are stored as text per team; the winner is derived by comparing them.

Schema (for reference): Team(name, city, coach, captain_id UNIQUE NOT NULL); Player(player_id, name, position, ranking, team_name NULL allowed); Injury_Record(player_id, injury_id, start_date, end_date, description); Game(game_id, game_date, host_score, guest_score, host_team NOT NULL, guest_team NOT NULL) with CHECK (host_team <> guest_team). The circular reference Team ↔ Player is created with ALTER TABLE in Oracle.

The question bank's answer models a game as a recursive relationship Team–Team; that cannot store two games between the same host and guest (a relationship holds a pair once), which is why an entity set Game is used here.

BUET QBank · CSE 303 | L-3/T-1 | 2010–11 · 10 marks

Consider the following scenario of a hospital: Patients are treated in a single ward by the doctors assigned to them. Usually each patient will be assigned a single doctor, but in rare cases he/she will be assigned two doctors. Healthcare assistants also attend to the patients; a number of these are associated with each ward. Initially the system will be concerned solely with drug treatment. Each patient is required to take a variety of drugs a certain number of times per day and for varying lengths of time. The system must record details concerning patient treatment and staff payment. Some staffs are paid on a part time basis and doctors and care assistants work varying amounts of overtime at varying rates (subject to grade). The system will also need to track what treatments are required for which patients and when, and it should be capable of calculating the cost of treatment per week for each patient. Define entities and their attributes for the hospital management system described above.

Show worked answer

With the entity sets of the previous answer, the relationships are:

  • admittedTo: Patient → Ward, many-to-one, total for Patient ("treated in a single ward").
  • assigned: Patient – Doctor, many-to-many, total for Patient. Design note: a patient has 1 or 2 doctors (in (min,max) notation: (1,2) next to Patient).
  • worksIn: CareAssistant → Ward, many-to-one ("a number of these are associated with each ward"), total for CareAssistant.
  • attends: CareAssistant – Patient, many-to-many.
  • receives: Treatment → Patient, uses: Treatment → Drug, prescribedBy: Treatment → Doctor; all many-to-one, total for Treatment. Treatment is an entity (not a Patient–Drug relationship) because the same drug can be given to the same patient again later, with different times and dates.
  • hasGrade: Staff → Grade, many-to-one, total for Staff.
  • worked: identifying relationship Overtime → Staff.
  • Staff isA {Doctor, CareAssistant}: disjoint, total.

Pay for a period = basic_rate × contracted_hours (prorated for part-time staff) + Σ overtime hours × overtime_rate of the staff member's grade; both rates come from Grade, so changing a grade's rate changes everyone's pay consistently. The question bank's answer is similar; it adds a Payment weak entity, which is fine if pay slips must be stored.

Summary: split a large system into feature-sized diagrams that share entity sets. If the same pair can be associated many times (repeated comments, repeated games, repeated treatments), the association must be an entity set. Roles name the two ends of a relationship between one entity set and itself, or the two parts a team plays in a game. Derived counts (viewers, weekly cost) are dashed ovals computed by queries.
