Entities, Attributes, Keys and Relationships

Before we create a single table we decide what the data means. This chapter introduces the Entity-Relationship (ER) model and its four building blocks: entity sets, attributes, keys and relationships, and shows how to find them in a written requirement.

1. What ER stands for and why we use it (slides 1–3)

So far in this course we have worked with tables: we created them (Lec 03), queried them (Lec 04), changed them (Lec 05) and protected them with constraints (Lec 06). But somebody has to decide which tables to create in the first place. That step is called conceptual database design: we describe what the data means in the real world, without yet thinking about tables, columns or data types. The tool the slides use for this step is the ER diagram.

Entity
A real-world object or concept we want to remember: one particular student, one course, one book. "The thing we store."
Relationship
An association among entities: student Amina is enrolled in course CSE101. "The association between things."
ER diagram (ERD)
A visual model of the entities, their attributes, the relationships between them and the constraints on those relationships. "The visual model."

Slide 3 lists the reasons we draw an ER diagram before writing SQL:

  • It helps us understand the domain before implementation. We talk about students and courses, not about VARCHAR2(40).
  • It is visual enough to discuss with non-technical stakeholders. A registrar can look at a box labelled Student and a diamond labelled enrolls and say "yes, but a student can enroll in the same course twice if they fail it". That kind of correction is exactly what we want early.
  • It shows entity sets, attributes, relationships, keys and multiplicity in one picture.
  • It catches design mistakes early, when changes are cheap. Moving a box in a diagram costs nothing; changing a table that already holds a million rows and is used by twenty programs costs a lot.

The slide's main idea: first model what the data means; implementation details can come later. In Part 2 of these notes (Chapters 10–13) we will turn diagrams into Oracle tables mechanically, so a good diagram leads straight to a good schema.

2. Requirements analysis: reading a requirement (slides 4–5)

Design starts from a written requirement, a short description in plain language of what the system must remember. Slide 5's example:

The department wants to store students, courses, instructors, and course enrollments. Each student has a name and department. Each course has a title and credits. Students enroll in courses each semester and receive grades.

The slide gives three reading rules, which are really three questions we ask about every phrase:

  1. Important nouns (students, courses, instructors) suggest things the system must remember: candidate entity sets.
  2. Verbs or action phrases (enroll in) suggest how those things are connected: candidate relationships.
  3. Descriptive facts (name, department, title, credits) suggest what we need to store about them: attributes.

The animation applies the three rules to slide 5's requirement and builds the diagram one decision at a time.

Two phrases need care. "Course enrollments" is a noun, but it is the noun form of the verb "enroll", so it describes the association between a student and a course rather than a separate kind of thing. And "grades" are received for an enrollment: a grade only makes sense once a particular student and a particular course are paired. We come back to both points in Chapter 2 (relationship attributes) and Chapter 5 (when a relationship deserves to become an entity). The requirement also mentions instructors but says nothing about what connects them to courses, so for now Instructor is a box with no lines; a real design would ask the department "who teaches what?".

4. Entities and entity sets (slides 7–8)

Entity
A distinguishable object in the world: the student with ID 2105001, the course CSE215.
Entity set
A set of similar entities, all described by the same attributes: the set of all students, the set of all courses. An entity set is drawn as a rectangle with its name inside.

The textbook (Garcia-Molina, Ullman and Widom) compares an entity set to a class in object-oriented programming and an entity to an object of that class. In the relational world an entity set will usually become a table and each entity a row.

Finding entity sets (slide 8)

Look for the important nouns in the requirement: Student, Course, Instructor, Department. Two cautions from the slide:

  • Avoid modeling individual objects as boxes. A box called Amina is wrong; Amina is one member of the entity set Student.
  • Model the type, not one instance. The diagram must stay the same when Amina graduates and a thousand new students join. Only the data changes.

A useful test: if you can say "a ___" or "each ___" in front of the name ("each student", "a course"), it is a type and can be an entity set. "Each Amina" makes no sense, so Amina is an instance.

5. Attributes (slide 9)

Attribute
A property that describes the entities of an entity set (or the pairs of a relationship, Chapter 2). Each entity has a value for each attribute: Amina's name is "Amina", her dept is "CSE". Attributes are drawn as ovals joined to their rectangle by a line.

All entities in an entity set usually share the same attributes: every student has a name, an email and a department. In the basic model of the slides an attribute value is a single atomic value such as a string or a number. Chapter 10 shows the extended kinds (composite, multivalued and derived attributes) that appear in exam questions.

6. Keys (slides 10–11)

Key
A set of attributes whose values identify an entity inside its entity set: no two entities of the set may agree on all key attributes. A key must be unique (no two entities share the value) and minimal (no attribute can be dropped without losing uniqueness).
Primary key in an ER diagram
The key chosen for the entity set. Its attribute names are underlined.

Composite keys

Sometimes one attribute is not enough, and a key contains several attributes. Slide 11's example: a section of a course is identified by course, semester and section number together. CSE215 has a section 1 every semester, and every course has a section 1, so none of the three alone is unique. In a diagram, every attribute of a composite key is underlined.

Minimality: if removing any attribute breaks uniqueness, the key is minimal. The table below has four sections. Try dropping each attribute of the key and see whether two rows collide.

Worked check: is {course, semester, sec_no} minimal?

Drop course: rows 1 and 4 both have (Jan 2025, 1). Drop semester: rows 1 and 3 both have (CSE215, 1). Drop sec_no: rows 1 and 2 both have (CSE215, Jan 2025). Every smaller set fails on this data, and more importantly it fails in principle, since the rules of the university allow all three collisions. So the key is minimal. Note that {course, semester, sec_no, room} is also unique, but it is not minimal because room can be dropped; such a set is called a superkey.

7. Relationships (slides 12–14)

Relationship
An association among entities: "Instructor Rahman teaches CSE215".
Relationship set
The set of all such associations of one kind. It is drawn as a diamond with lines to the entity sets it connects. Verbs in the requirement often indicate relationships (teaches, enrolls, borrows).

The diamond names the association (slide 13: "Student enrolls in Course", the diamond says enrolls). Choose a name that reads naturally from one box through the diamond to the other: Student enrolls Course, Instructor teaches Course.

Important idea from slide 13: the diagram shows the general association, not a list of individual records. The current value of a relationship set is a set of pairs, one pair per actual association. The figure below shows the same diagram with a possible set of pairs beside it; the pairs change every semester, the diagram does not.

Relationships can involve more entity sets (slide 14)

Most relationships in this lecture are binary: they connect two entity sets. Later we meet relationships that connect more than two entity sets (multi-way relationships, Chapter 6) and relationships where an entity set connects to itself (recursive relationships, Chapter 3). The slide's advice: start with binary relationships; they are easier to read and to check.

BUET QBank · CSE 303 | L-3/T-1 | 2012–13 · 15 marks

What are the different elements of Entity-Relation Model? Briefly discuss them.

Show worked answer

The ER model describes a database with three kinds of elements, each with its own symbol, plus constraints that restrict them.

1. Entity sets. An entity is a distinguishable real-world object (one student); an entity set is a collection of similar entities (all students), drawn as a rectangle. A strong entity set has a key of its own. A weak entity set (double rectangle) cannot be identified by its own attributes and borrows the key of an owner entity set through an identifying relationship (double diamond); its own identifying attribute is a partial key (dashed underline). (Chapter 8.)

2. Attributes. Properties of entities or of relationships, drawn as ovals. Kinds: simple (atomic, e.g. salary); composite (made of parts, e.g. name = first + last; the parts hang off the composite oval); single-valued vs multivalued (several values per entity, e.g. phone numbers; double oval); derived (computed from other data, e.g. age from date of birth; dashed oval); key attributes (underlined), which identify an entity within its set. (Chapter 10.)

3. Relationship sets. Associations among entities, drawn as diamonds joined to the participating entity sets. Their degree is the number of entity sets involved: binary, ternary (multi-way, Chapter 6) or recursive when one entity set appears twice in different roles (role names on the lines). A relationship may have its own attributes (e.g. grade on enrolls).

4. Constraints. Keys (unique, minimal identifying attributes). Multiplicity / cardinality ratio: one-to-one, many-to-one, many-to-many, shown in the slides by an arrowhead toward the "one" side and written 1, N, M on the lines in Chen's notation (Chapter 3). Participation: total (every entity must take part; double line) or partial (single line) (Chapter 10). Specialization (isA): subclasses that inherit the attributes of a superclass, with disjoint/overlapping and total/partial constraints (Chapter 7).

Summary: conceptual design describes what the data means before choosing tables. Read the requirement for nouns (entity sets, rectangles), verbs (relationships, diamonds) and descriptive facts (attributes, ovals). Model types, never single instances. A key is a unique and minimal set of attributes and is underlined; a composite key underlines several attributes. A diagram shows the general association; the relationship set holds the actual pairs.
