Exam Topics Beyond the Slides: Materialized Views and Object Types

The ER part of the question banks also asks about views versus materialized views, and about turning composite, multivalued attributes and subclasses into SQL:1999/2003 object types. None of this is on the Lec 07 slides; this chapter teaches enough to answer those questions in Oracle.

1. Views and materialized views

View
A named query, CREATE VIEW v AS SELECT …. Only the definition is stored. Each time a query uses the view, the DBMS runs (or merges in) the defining query on the current base tables, so a view is always up to date and takes no space.
Materialized view (MV)
A view whose result is computed and stored as a table. Queries read the stored rows, which is fast for expensive joins and aggregates, but the stored result becomes stale when the base tables change and must be refreshed.
Refresh
Complete: recompute the whole query. Fast (incremental): apply only the changes recorded since the last refresh (in Oracle, from a materialized view log on each base table). Timing: ON COMMIT (immediately, as part of each transaction) or ON DEMAND / on a schedule.

In Oracle:

CREATE MATERIALIZED VIEW LOG ON Sales WITH ROWID, SEQUENCE (store_id, amount) INCLUDING NEW VALUES;

CREATE MATERIALIZED VIEW store_totals
  REFRESH FAST ON COMMIT
AS SELECT store_id, COUNT(*) AS n, COUNT(amount) AS n_amt, SUM(amount) AS total
   FROM Sales GROUP BY store_id;

BUET QBank · CSE 215 | L-2/T-2 | 2019–20 · 10 marks

What do you mean by materialized view? Explain with examples the problems associated with materialized view. What restrictions do most database implementations have to allow updates on materialized views?

Show worked answer

Materialized view: a view whose result is computed once and stored physically, like a table, instead of being recomputed on every use. Example: CREATE MATERIALIZED VIEW dept_pay AS SELECT dept_id, SUM(salary) total FROM Employee GROUP BY dept_id. Reports read dept_pay directly instead of summing the whole Employee table each time.

Problems:

  1. Staleness (view maintenance). After UPDATE Employee SET salary = salary + 1000 WHERE emp_id = 7, dept_pay still shows the old total until it is refreshed. Queries can return out-of-date answers.
  2. Maintenance cost. Refreshing ON COMMIT makes every update of Employee slower (the transaction also updates dept_pay); refreshing ON DEMAND keeps updates fast but lets the MV be stale between refreshes. A complete refresh of a big join is expensive.
  3. Storage for the stored result, and for the logs needed for incremental refresh.
  4. Some changes cannot be propagated incrementally. Deleting the employee with the maximum salary from a MAX(salary) view requires rescanning the department; deleting from a view without COUNT(*) cannot tell when a group becomes empty.
  5. Updating through the view raises the general view-update problem: a change to an aggregated or joined row has no unique translation into base-table changes.

Restrictions (Oracle's rules for fast refresh and for updatable MVs are typical):

  • Fast refresh needs a materialized view log on every base table, and the MV must include the rowids or primary keys of the base rows (for join MVs).
  • Aggregate MVs must include COUNT(*), and COUNT(x) for every SUM(x) or AVG(x); only SUM, COUNT, AVG, (VARIANCE, STDDEV) are fast-refreshable on all changes; MIN/MAX only for inserts.
  • No non-deterministic expressions (SYSDATE, ROWNUM), no set operations in some forms (only UNION ALL with markers), restricted outer joins and subqueries; no references to other remote/complex views.
  • An MV may be updated directly (FOR UPDATE, an "updatable MV") only if it is a simple selection/projection of a single table that includes its primary key, with no aggregates, DISTINCT, GROUP BY, joins or set operations, so that every MV row maps to exactly one base row. Otherwise MVs are read-only and changes go to the base tables.

BUET QBank · CSE 303 | L-3/T-1 | 2016–17 · 20 marks

A car rental company maintains a database for all vehicles. For all vehicles: vehicle identification number, license number, manufacturer, size (height, width, length) and color. Special data for certain types: Trucks: load capacity, type; Sports car: power, renter age; Bus: number of passengers, seat-type (array of 40 seats of different types). (a) Construct an SQL:99 schema definition for this database using appropriate inheritance. (b) Write constructor functions for the above schema and an insert statement to insert data.

Show worked answer

The ER view: Vehicle(vin, license_no, manufacturer, size(height, width, length), color) with subclasses Truck(load_capacity, truck_type), SportsCar(power, renter_age), Bus(num_passengers, {seat_type} with at most 40 values). Size is composite → a structured type; seat types are multivalued → an array; subclasses → UNDER.

(a) SQL:1999:

CREATE TYPE Size_T AS (height DECIMAL(5,2), width DECIMAL(5,2), length DECIMAL(5,2)) NOT FINAL;
CREATE TYPE Vehicle_T AS (
  vin VARCHAR(17), license_no VARCHAR(15), manufacturer VARCHAR(30),
  size Size_T, color VARCHAR(15)) NOT FINAL;
CREATE TYPE Truck_T     UNDER Vehicle_T AS (load_capacity DECIMAL(8,2), truck_type VARCHAR(20)) NOT FINAL;
CREATE TYPE SportsCar_T UNDER Vehicle_T AS (power INTEGER, renter_age INTEGER) NOT FINAL;
CREATE TYPE Bus_T       UNDER Vehicle_T AS (num_passengers INTEGER, seat_type VARCHAR(20) ARRAY[40]) NOT FINAL;

CREATE TABLE vehicle   OF Vehicle_T (PRIMARY KEY (vin));
CREATE TABLE truck     OF Truck_T     UNDER vehicle;
CREATE TABLE sportscar OF SportsCar_T UNDER vehicle;
CREATE TABLE bus       OF Bus_T       UNDER vehicle;

A row inserted into truck is also visible in vehicle (a subtable's rows belong to its supertable), which is exactly isA. renter_age is a minimum age requirement of the car (a property of the vehicle), as the question lists it under sports cars.

(b) Constructors and insert. The system generates a constructor for every type, named like the type, that takes no arguments and sets all attributes to NULL; values are set with mutators, or we define a constructor that takes all values:

CREATE FUNCTION Size_T(h DECIMAL(5,2), w DECIMAL(5,2), l DECIMAL(5,2)) RETURNS Size_T
BEGIN
  DECLARE s Size_T;
  SET s = NEW Size_T();          -- system constructor, all NULL
  SET s.height = h; SET s.width = w; SET s.length = l;
  RETURN s;
END;

VALUES ('1HTMMAAL57H123456', 'DHAKA-TA-11-2233', 'Tata', Size_T(3.2, 2.4, 9.0), 'red', 12000, 'covered van');

INSERT INTO bus (vin, license_no, manufacturer, size, color, num_passengers, seat_type)
VALUES ('JTDBR32E720654321', 'DHAKA-BA-15-0042', 'Hino', Size_T(3.4, 2.5, 12.0), 'white', 40,

The same in Oracle (the course's DBMS): types are CREATE TYPE … AS OBJECT, the array is a VARRAY, inheritance is UNDER with the parent NOT FINAL, and one object table of the root type stores every subtype:

CREATE TYPE Size_T  AS OBJECT (height NUMBER(5,2), width NUMBER(5,2), length NUMBER(5,2));
/
CREATE TYPE Seats_T AS VARRAY(40) OF VARCHAR2(20);
/
CREATE TYPE Vehicle_T AS OBJECT (vin VARCHAR2(17), license_no VARCHAR2(15), manufacturer VARCHAR2(30),
                                 vsize Size_T, color VARCHAR2(15)) NOT FINAL;
/
CREATE TYPE Truck_T     UNDER Vehicle_T (load_capacity NUMBER(8,2), truck_type VARCHAR2(20));
/
CREATE TYPE SportsCar_T UNDER Vehicle_T (power NUMBER(5), renter_age NUMBER(3));
/
CREATE TYPE Bus_T       UNDER Vehicle_T (num_passengers NUMBER(3), seat_type Seats_T);
/
CREATE TABLE Vehicles OF Vehicle_T (PRIMARY KEY (vin));

INSERT INTO Vehicles VALUES (Truck_T('1HTMMAAL57H123456', 'DHAKA-TA-11-2233', 'Tata',
                                     Size_T(3.2, 2.4, 9.0), 'red', 12000, 'covered van'));
INSERT INTO Vehicles VALUES (Bus_T('JTDBR32E720654321', 'DHAKA-BA-15-0042', 'Hino',
                                   Size_T(3.4, 2.5, 12.0), 'white', 40, Seats_T('window', 'aisle')));
SELECT v.vin, TREAT(VALUE(v) AS Bus_T).num_passengers FROM Vehicles v WHERE VALUE(v) IS OF (Bus_T);

Oracle's default constructor takes all attributes in order, including inherited ones, as the inserts show.

BUET QBank · CSE 303 | L-3/T-1 | 2010–11 · 10 marks

Consider the E-R diagram (Figure 2) which contains composite, multivalued and derived attributes. (a) Give an SQL:2003 schema definition corresponding to the E-R diagram. (b) Give constructors for each of the structured types defined above.

Show worked answer

Figure 2 is lost from the bank. The question is Silberschatz's exercise on its figure of an instructor entity with composite, multivalued and derived attributes, so we use that figure: instructor(ID, name(first_name, middle_initial, last_name), address(street(street_number, street_name, apt_number), city, state, zip), {phone_number}, date_of_birth, age()).

(a) SQL:2003. Composite → structured types (nested for street); multivalued → a multiset (or array); derived → a method:

CREATE TYPE Name AS (first_name VARCHAR(20), middle_initial CHAR(1), last_name VARCHAR(20)) NOT FINAL;
CREATE TYPE Street AS (street_number VARCHAR(10), street_name VARCHAR(30), apt_number VARCHAR(10)) NOT FINAL;
CREATE TYPE Address AS (street Street, city VARCHAR(20), state VARCHAR(20), zip VARCHAR(10)) NOT FINAL;
CREATE TYPE InstructorType AS (
  ID            VARCHAR(5),
  name          Name,
  address       Address,
  phone_number  VARCHAR(15) MULTISET,
  date_of_birth DATE)
  NOT FINAL
  METHOD age() RETURNS INTEGER;

CREATE METHOD age() RETURNS INTEGER FOR InstructorType
BEGIN
  RETURN EXTRACT(YEAR FROM CURRENT_DATE) - EXTRACT(YEAR FROM SELF.date_of_birth);
END;

CREATE TABLE instructor OF InstructorType (PRIMARY KEY (ID));

(b) Constructors (SQL:2003 constructors are written as functions with the type's name that set each attribute and return SELF):

CREATE CONSTRUCTOR METHOD Name(fn VARCHAR(20), mi CHAR(1), ln VARCHAR(20)) RETURNS Name
BEGIN SET SELF.first_name = fn; SET SELF.middle_initial = mi; SET SELF.last_name = ln; RETURN SELF; END;

CREATE CONSTRUCTOR METHOD Street(sno VARCHAR(10), sname VARCHAR(30), apt VARCHAR(10)) RETURNS Street
BEGIN SET SELF.street_number = sno; SET SELF.street_name = sname; SET SELF.apt_number = apt; RETURN SELF; END;

CREATE CONSTRUCTOR METHOD Address(s Street, c VARCHAR(20), st VARCHAR(20), z VARCHAR(10)) RETURNS Address
BEGIN SET SELF.street = s; SET SELF.city = c; SET SELF.state = st; SET SELF.zip = z; RETURN SELF; END;

CREATE CONSTRUCTOR METHOD InstructorType(i VARCHAR(5), n Name, a Address, p VARCHAR(15) MULTISET, d DATE)
  RETURNS InstructorType
BEGIN SET SELF.ID = i; SET SELF.name = n; SET SELF.address = a; SET SELF.phone_number = p;
      SET SELF.date_of_birth = d; RETURN SELF; END;

INSERT INTO instructor VALUES (NEW InstructorType('10101',
   NEW Name('Rafiq', 'A', 'Islam'),
   NEW Address(NEW Street('12', 'Lake Road', '3B'), 'Dhaka', 'Dhaka', '1205'),
   MULTISET['01711000001', '01911000002'], DATE '1980-04-12'));

In Oracle the same design uses AS OBJECT types, a nested-table or VARRAY type for phone numbers, and a MEMBER FUNCTION age RETURN NUMBER implemented in a CREATE TYPE BODY (computing TRUNC(MONTHS_BETWEEN(SYSDATE, date_of_birth)/12)); Oracle generates the attribute-value constructors automatically. The question bank's answer invents a different figure and uses a generated column with CURRENT_DATE for age, which standard SQL and Oracle reject (generated columns must be deterministic); a method is the correct tool.

Summary: a view stores a query and is always current; a materialized view stores the result, is fast but must be refreshed, and supports fast refresh or direct updates only for restricted queries. Object-relational SQL maps composite attributes to structured types, multivalued ones to arrays or multisets, derived ones to methods, and isA to UNDER; constructors create the values.
