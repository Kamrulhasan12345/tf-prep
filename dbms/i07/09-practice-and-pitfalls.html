Practice, Common Mistakes and the Design Checklist

Part 6 of the lecture: the library mini case, four common mistakes with their fixes, a checklist to run over every diagram, and the advising practice task worked step by step.

1. Mini case study: the library (slides 87–88)

A library stores books, members, and loans. A book has ISBN, title, and publisher. A member has ID, name, and email. Members borrow books. For each loan, store issue date, due date, and return date.

The slide's answer: entity sets Book and Member; relationship borrows; relationship attributes issue date, due date, return date. Note that "loans" is a noun in the requirement, but it is the noun form of "borrow", so it names the relationship, not a third entity set (compare "course enrollments" in Chapter 1).

Slide 88 shows the keys member_id and isbn and only due_date, to keep the slide readable; the complete diagram (last frame) has all the attributes the requirement lists. Publisher is kept as an attribute here because the requirement gives no facts about publishers; if it did (address, country), Principle 3 of Chapter 2 would make Publisher an entity set.

2. Common mistakes (slides 89–92)

Mistake 1: modeling instances

Not goodBetter
Boxes named Amina, Rahim and Nabila.One entity set named Student; actual students are examples (rows) of that set.

Mistake 2: missing keys

Every strong entity set needs a key. Keys should be stable (they should not change over an entity's life) and unique. Names alone are poor keys because people share names: use student_id rather than name as the key for Student.

Mistake 3: wrong multiplicity

Multiplicity is not decoration; it changes the meaning of the design and, later, the tables. Ask domain questions carefully; "can this happen more than once?" is often the deciding question. Slide 91's example: if a course can be taught by several instructors, teaches is not simply one-to-many from Instructor to Course.

Mistake 4: relationship attributes on entities

Grade belongs to a student's enrollment in a course. It does not belong to Student alone, and it does not belong to Course alone. Correct location: put grade on the enrolls relationship (Chapter 2).

3. Design checklist (slide 93)

Run this list over every diagram before handing it in:

  • Are all important entity sets included?
  • Does each strong entity set have a key? (And each weak one a partial key and an identifying relationship?)
  • Are attributes atomic where needed? (No "addr1, addr2"; no list of phone numbers in one oval unless it is drawn as multivalued.)
  • Are relationships named clearly? (A verb that reads from box to box.)
  • Are multiplicity and relationship constraints correct? (Test with "can this happen more than once?")
  • Are important requirement notes written beside the ERD? ("Every student has exactly one advisor", extra candidate keys, disjointness.)

4. Practice task: university advising (slides 94–96)

Students are assigned advisors. An advisor is a faculty member. A student has exactly one advisor, but a faculty member can advise many students. Store the date from which advising started.

Identify entity sets; identify the relationship and multiplicity; decide where start_date belongs; draw the ERD.

Practice answer (slide 95)

  • Entity sets: Student, Faculty. (Advisor is a role of Faculty, not a separate entity set.)
  • Relationship: advises.
  • Multiplicity: arrow toward Faculty, plain connector toward Student.
  • Requirement note: every Student has exactly one advisor. (The arrow says "at most one"; the note adds "at least one".)
  • start_date belongs to advises: it describes the advising assignment.

5. What you should remember (slide 97)

  • Databases store related facts about a domain.
  • Keys and constraints protect the meaning of those facts.
  • ER diagrams model entity sets, attributes, relationships and constraints.
  • Multiplicity answers how many related entities are allowed.
  • Good ERD design comes from testing the diagram with examples.

BUET QBank · CSE 303 | L-3/T-1 | 2015–16 · 7 marks

A university has a large number of courses. Each course may have one or more different courses as prerequisites, or may have no prerequisites. Similarly, a particular course may be a prerequisite of any number of courses or may not be a prerequisite of any other course. Sketch an E-R diagram that includes COURSE as the single entity, including cardinality. Each course has a course number and title. Convert the E-R diagram into a relational schema.

Show worked answer

One entity set, Course(course_no, title), and a recursive relationship prereq with two roles: course (the course that has the requirement) and prerequisite. Fix a course: it may have many prerequisites (or none). Fix a course in the prerequisite role: it may be required by many courses (or none). So prereq is many-to-many (M:N), with no arrows, and partial participation on both lines ("may have no prerequisites", "may not be a prerequisite").

Schema. The entity set gives Course(course_no, title). A many-to-many relationship always becomes its own table holding both participants' keys; since both participants are Course, the two copies of the key are renamed by role:

Prereq(course_no, prereq_no)
  course_no → Course(course_no), prereq_no → Course(course_no)

The primary key is both columns, so the same prerequisite cannot be listed twice for a course. A CHECK (course_no <> prereq_no) stops a course from being its own prerequisite. Run it:

Summary: model types not instances; give every strong entity set a stable, unique key; get multiplicity right by asking "can this happen more than once?"; put facts about a pair on the relationship. Before finishing, run the checklist and write design notes for rules the diagram cannot show, such as "every student has exactly one advisor".
