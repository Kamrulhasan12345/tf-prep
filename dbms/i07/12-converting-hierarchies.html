Converting isA Hierarchies to Tables

The textbook gives three ways to store subclasses: E/R style, object-oriented style and the null-value style. This chapter animates all three on the slides' Product hierarchy with real rows, compares them, and works the four hierarchy questions from past papers.

1. Three strategies

Take slide 73's hierarchy: Product(pid, name, price) with subclasses SoftwareProduct(platforms) and EducationalProduct(ageGroup), overlapping (KidPix is both). Four sample products: a chair (neither), Photoshop (software), an atlas (educational) and KidPix (both).

E/R style ("a table per entity set")
One table for each entity set in the hierarchy. The root table has all root attributes; each subclass table has only the key plus the subclass's own attributes, and its key is a foreign key to the parent. An entity is spread over the tables of all classes it belongs to.
Object-oriented style ("a table per kind of object")
One table for each subtree that includes the root, i.e. for each combination of classes an entity can belong to. The table has all attributes of all classes in the combination. Each entity is stored in exactly one table, complete.
Null style ("one big table")
One table with every attribute of every class. An entity has NULL in the attributes of classes it does not belong to.

Rules of thumb: the E/R style is the default and the only one that keeps every subclass relationship clean; it avoids NULLs, which is what exam questions mean by "avoid keeping null values". The OO style suits disjoint hierarchies with few subclasses, where it needs only k tables (or k + 1 if the root may have plain members). The null style suits small hierarchies with few subclass attributes and many queries over the whole set; add a discriminator column (product_type) or boolean flags so the class of each row is explicit.

DB QB · 21-22 2b · 10 marks  ·  BUET QBank · CSE 215 | L-2/T-2 | 2021–22 · 20 marks

Consider the following descriptions of an organization having many EMPLOYEES. (i) An EMPLOYEE has a name, nid number, data of birth, and address. (ii) Based on the EMPLOYEE's Job, EMPLOYEE may be further grouped into: SECRETARY, ENGINEER, TECHNICIAN, and MANAGER. (iii) Based on the EMPLOYEE's method of pay, EMPLOYEE may also be grouped into: SALARIED_EMPLOYEE, and HOURLY_EMPLOYEE. (iv) A salaried employee who is also an engineer belongs to the two subclasses: ENGINEER, and SALARIED_EMPLOYEE. (v) A salaried employee who is also an engineering manager belongs to the three subclasses: MANAGER, ENGINEER, and SALARIED_EMPLOYEE. (vi) We want to record typing speed of each SECRETARY. (vii) Each technician has a technical grade (a number) which depends on his skill level. (viii) Each Engineer has a type (ME, CSE, EEE, etc ...). (ix) Each MANAGER manages at least one project, each project has a project id, title, and a project value. (x) Each HOURLY_EMPLOYEE is a member of some TRADE_UNION which has a name and member count. Construct an E/R diagram with the above description; clearly indicate the cardinality mappings as well as any role indicators in your E/R diagram. Convert the E/R diagram into a set of relational database schema. You should avoid keeping null values in attributes.

Show worked answer

Reading the requirements. Two independent specializations of Employee:

  • By job: Secretary, Engineer, Technician, Manager. (v) shows an engineer can also be a manager, so this one is overlapping; "may be grouped" makes it partial.
  • By pay: SalariedEmployee, HourlyEmployee: disjoint (one method of pay); assume total (everyone is paid somehow).

(iv) and (v) show one employee can be in subclasses of both specializations at once. Relationships: manages Manager–Project, one-to-many (a project has one manager; assumed), with total participation of Manager ("manages at least one project") and of Project (every project has a manager, assumed). memberOf HourlyEmployee–TradeUnion, many-to-one, total on HourlyEmployee ("is a member of some trade union"). member_count of a union can be derived by counting members.

Schema with no NULLs: E/R style (each subclass gets its own table, so no row has a column that does not apply to it; foreign keys to the "one" side are NOT NULL because participation is total):

Manager and SalariedEmployee have no attributes of their own but still need tables, so that "is a manager" / "is salaried" is recorded and Project can reference Manager. "Each manager manages at least one project" cannot be enforced by keys (it needs a trigger). member_count is derived (SELECT COUNT(*) FROM Hourly_Employee WHERE union_name = …) and is better computed by a view; store it only if required. The null style is rejected because it would leave typing_speed, tech_grade, eng_type and union_name NULL for most employees.

Summary: E/R style: one table per entity set, subclass tables hold the key and their own attributes (no NULLs, joins needed). Object-oriented style: one table per combination of classes an entity can have, each complete (no joins for one entity, UNIONs for the whole set; 2k tables if k subclasses overlap). Null style: one table, NULLs where a class does not apply. Overlap and totality decide how many OO tables you need.
