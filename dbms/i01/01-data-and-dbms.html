Data, Databases and the DBMS

The first lecture introduces the course and then builds up three words step by step: data, database and database management system (DBMS). This chapter explains each one with the slides' university examples and shows what happens when an application asks a DBMS for data.

1. The course in one picture (slides 1–7)

CSE 215 is taught in two halves. The first half (slide 4) is about using and designing data: the relational model (how data is shaped into tables), SQL (the language for asking questions of those tables), ER modeling (drawing the things and relationships a system must remember) and normalization (checking that a table design does not repeat facts). The second half (slide 5) opens the box and asks how a DBMS stays fast, correct and dependable: storage (how tables sit on disk), indexes (how rows are found without reading everything), transactions (how many users work at once without damage) and recovery (how the data survives a crash).

Slide 6 gives the learning method: concepts (the slides explain the idea), examples, practice and build (write real queries and designs yourself). Every chapter of this book follows the same order and ends with practice. Slide 7 lists the plan for the first day: meet the course, meet data, meet the DBMS. Slides 1–3 are the title, the instructor (Md. Ishrak Ahsan, Lecturer, CSE, BUET) and contact details (email, office Room 515 ECE Building, and Moodle as the course channel).

2. Where did you use a database today? (slide 8)

Slide 8 lists four everyday systems: a messaging app, BIIS (BUET's academic information system, where you register for courses and see results), Pathao/Uber and a payment app. Each one is mostly a story built around data:

  • A messaging app remembers who sent which message to whom, and when.
  • BIIS remembers students, courses, registrations and grades.
  • A ride app remembers riders, drivers, trips, locations and fares.
  • A payment app remembers accounts, balances and every transfer.

The screens you see are thin. Behind every screen there is a program that reads and writes stored facts, and those facts must still be there tomorrow, correct, even if a thousand people use the app at the same moment. Keeping such facts is the job this course studies.

3. Data = recorded facts (slide 9)

Data
Recorded facts: values that have been written down so that they can be used later. A sentence like “A student enrolled in CSE 215” becomes data once it is recorded in a fixed form.
Field (attribute)
One named piece of a recorded fact, such as Student ID, Course or Status. Each field holds one value.
Record
The group of field values that together state one fact, such as (24FF501, CSE 215, Enrolled).

Slide 9 turns the English sentence “A student enrolled in CSE 215.” into a small card with three labelled values: Student ID = 24FF501, Course = CSE 215, Status = Enrolled. The sentence and the card say the same thing, but the card is far more useful to a computer. A program can find every card whose Course is CSE 215, count them, or change one Status to “Dropped”, because each value sits in a known, named place. A program cannot do that reliably with free English text. Structuring facts into named fields is the first step toward a database.

4. A database organizes related data (slide 10)

Database
A collection of related data, organized so that it can be stored, found and updated, and kept over a long period of time (the textbook, §1.1: “a collection of information that exists over a long period of time”).
Entity
A thing the system needs to remember facts about: a student, a course, a professor. Things of the same kind form an entity set (all students).
Attribute
A property that describes an entity: a student's ID, name and email. Each attribute has a value for each entity.
Relationship
A connection between entities: “student 24FF501 is enrolled in CSE 215”. An enrollment involves one student and one course.

Slide 10 shows three groups of facts kept together: Students (ID, name, email), Courses (code, title, credit) and Enrollments (student + course). The first two are entity sets with their attributes. The third is a relationship: each enrollment links one student to one course. The point of the slide is “related facts, kept together”: the three groups belong to one university, and the enrollment facts only make sense together with the student and course facts they refer to.

Why keep enrollments separate instead of writing the course list inside each student? Because a fact should be stored once. If “CSE 215 has 3 credits” were copied into every enrolled student's data, a change to the credit value would have to be made in hundreds of places. Lecture 02 (Chapter 4 of the next part) returns to this trade-off.

5. A DBMS manages the database (slide 11)

Slide 11 quotes the definition from Connolly and Begg, Database Systems (6th ed.):

Database management system (DBMS)
A “software system that enables users to define, create, maintain and control access to the database.” Oracle, PostgreSQL, MySQL, SQL Server and SQLite are DBMSs. CSE 215 uses Oracle.
Database system
The database together with the DBMS software and the applications that use it.
Application
A program written for end users (the BIIS portal, a mobile app, a web API). It never touches the database files directly. It sends requests to the DBMS.

Each verb in the definition is a separate job:

  • Define: describe what will be stored, for example “a student has an ID, a name and an email; the ID is unique”. This description is the schema. In SQL it is written with CREATE TABLE.
  • Create: actually store the data: insert students, courses and enrollments.
  • Maintain: keep the data correct and available over time: answer queries, apply updates, change the structure when requirements change, survive crashes.
  • Control access: decide who may see or change what, and keep many simultaneous users from damaging each other's work.

Slide 11's diagram is a chain: Application (portal / app / API) sends a request to the DBMS, which “stores, queries, protects”, and only the DBMS does the read / write on the Database. The animation below follows one request through that chain.

The most important consequence of this design is that applications describe what data they want, and the DBMS decides how to get it. The application above never says which file or which disk block holds the enrollments. That knowledge lives in one place, inside the DBMS, which is why the DBMS can reorganize storage, add an index, or block an unauthorized user without any application changing. The next two chapters show what goes wrong when there is no such layer.

Why put a separate DBMS between the application and the data?

Without a DBMS, every application must contain its own code to find records in files, check that values are valid, stop two users from overwriting each other, and repair the files after a crash. Each application does this differently, and each one can get it wrong. With a DBMS, these jobs are written once, carefully, in the DBMS, and every application gets them for free. The application only states its question (in SQL). Chapters 2 and 3 compare the two approaches question by question, as slides 12–23 do.

Practice

Key terms

Quick check

Summary: data are recorded facts; structuring them into named fields makes them usable by programs. A database is a collection of related data (entities such as students and courses, and relationships such as enrollments) kept over a long time. A DBMS is the software that lets users define, create, maintain and control access to the database. Applications send requests to the DBMS, and only the DBMS reads and writes the stored data.
