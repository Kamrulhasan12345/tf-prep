Many Users, Crashes and Security

Slides 18–23 ask three more questions: what if two users update the same data, what if the system crashes halfway, and who may access the data. This chapter animates the slides' seat-booking race and money-transfer crash, shows how a DBMS prevents both, and answers the exam questions on the requirements and key properties of a DBMS.

1. Two users, one seat (slide 18)

The scenario: CSE 215 has only one seat left, stored in a shared record available_seats = 1. Alice and Bob try to enroll at the same moment. Each one's program does the obvious thing: read the number of seats, check it is positive, enroll, and write back the number minus one.

Both read 1, both see a free seat, both enroll, and both write 0. The final state says available_seats = 0 with two students enrolled in a course that had one seat. One of the two decrements was lost, because Bob's write overwrote Alice's without ever seeing it. The slide calls this a race condition: both users act on an outdated value.

Concurrent access
Several users or programs reading and writing the same data during overlapping periods of time.
Race condition
A bug in which the result depends on the exact order in which concurrent actions happen to interleave.
Lost update
The specific race on slide 18: two users read the same value, both compute a new value from it, and the second write silently erases the first.

2. Who coordinates the users? (slide 19)

Files: manual coordination, possible with custom locks. Your program must detect conflicts, lock files and protect every update, and every other program touching the file must follow the same rules. One program that forgets breaks everyone.

Spreadsheets: some support. Cloud tools such as Google Sheets coordinate edits to individual cells, which is useful for collaborative editing, but a multi-step operation (check seats, add the enrollment, decrement seats) cannot be made one indivisible unit.

DBMS: built in. Every unit of work is a transaction, and the DBMS's concurrency control (using locking or MVCC, multiversion concurrency control) makes concurrent transactions behave as if they ran one after another. The slide's caveat: contention (many users wanting the same row) still requires good design, because they have to wait for each other.

Transaction
A sequence of reads and writes that the DBMS treats as one logical unit of work, such as “enroll Alice: check seats, insert enrollment, decrement seats”. It ends with COMMIT (make it permanent) or ROLLBACK (undo it all).
Lock
A mark a transaction places on a data item so that other transactions must wait before writing (or reading) it.
MVCC
Multiversion concurrency control: writers create new versions of a row, so readers can keep reading the old committed version instead of waiting. Oracle uses MVCC for reads and row locks for writes.

In SQL the race disappears if the check and the decrement happen in one statement. A single UPDATE is atomic and the DBMS locks the row while it runs, so the second user's statement sees the first one's result:

Run it: the first UPDATE reports 1 row affected; the second reports 0 rows, because available_seats > 0 is no longer true. The application treats “0 rows” as “course full”. How the DBMS's scheduler does this in general is the subject of Sukarna sir's Lec 02–03 (concurrency control).

3. What if the system crashes halfway? (slide 20)

The scenario: transfer $100 from Account A ($500) to Account B ($300). The transfer is two steps: Step 1, debit A (A becomes $400); Step 2, credit B (B becomes $400). The power fails between the two steps. A has lost $100 and B never received it. Before the transfer the total was $800; after the crash it is $700. The database is now inconsistent: it states something that was never true in the real world.

Atomicity
A transaction happens completely or not at all. A half-done transfer must never be visible.
Durability
Once a transaction has committed, its changes survive any later crash.
Log (transaction log)
A file, written before the data itself, that records each change (“T changed A from 500 to 400”) and each commit. After a crash the DBMS reads the log to repair the database.
Rollback / undo
Restoring the old values written by a transaction that did not commit.
Redo
Re-applying the new values of a transaction that did commit, in case they had not reached the disk.

4. Crash recovery: files, spreadsheets, DBMS (slide 21)

Files: application-defined. Backups and logs are manual. The programmer must design, implement and test rollback or recovery logic, and recovery code that runs only after crashes is the code most likely to be wrong.

Spreadsheets: document recovery. Autosave and version history can restore a whole document to an earlier version, but they do not understand a multi-step business transaction: restoring yesterday's version also throws away every correct change made since.

DBMS: transactional. Rollback, redo and durability are built in. The transaction log lets the DBMS restore the database to a consistent state after a failure: incomplete transactions are undone and committed ones are kept. Sukarna sir's Lec 05–06 (system failures) teach the exact algorithms (undo logging, redo logging, undo/redo logging).

5. Who should be allowed to access the data? (slide 22)

Files: coarse-grained. Operating-system permissions apply to a whole file or folder. If a file holds every student's record, a user who may read one record may read all of them, including fields such as CGPA or phone number that they should not see.

Spreadsheets: sharing-based. Share links and protected ranges are convenient for collaboration, but controls vary between tools and a link shared with “anyone” is a common misconfiguration.

DBMS: fine-grained. The DBMS knows users, roles (named bundles of privileges) and privileges (permission to do one kind of operation on one object). It can restrict access to particular tables, particular columns, or (through views) particular rows, and it can keep audit records of who did what. In Oracle:

CREATE ROLE advisor;
GRANT SELECT ON students TO advisor;                -- read whole table
GRANT UPDATE (email, address) ON students TO portal; -- only two columns
CREATE VIEW my_dept_students AS                      -- only some rows
  SELECT sid, name, email FROM students WHERE dept = 'CSE';
GRANT SELECT ON my_dept_students TO cse_office;
GRANT advisor TO ishrak;                             -- give a user the role
REVOKE SELECT ON students FROM advisor;

Roles exist so that privileges are managed per job, not per person: when a new advisor joins, one GRANT advisor TO … gives them everything the job needs. The SQL lectures cover GRANT and views in detail.

Slide 23's message: a DBMS does more than store data: it coordinates users and protects correctness. Combined with slide 17 (large data, querying, structure changes), these six questions are the full case for a DBMS. The four transaction guarantees behind slides 18–21 are usually summarized as ACID:

A: Atomicity
All of a transaction's steps happen, or none do (slide 20).
C: Consistency
A transaction that starts from a correct database leaves it correct (total money unchanged; seats never negative).
I: Isolation
Concurrent transactions do not see each other's half-finished work; the result equals some one-at-a-time order (slide 18).
D: Durability
Committed changes survive crashes (slide 21).

DB QB · Jan 20 9 · 10 marks  |  BUET QBank · CSE 215 | L-2/T-2 | 2018–19 · 10 marks

What are the requirements of an ideal DBMS? Define entity and attribute in the context of database with suitable example(s).

Show worked answer

Requirements of an ideal DBMS. The textbook (Garcia-Molina, Ullman, Widom, §1.1) lists five things a DBMS is expected to do; the lecture's six questions add the rest.

  1. Data definition. Let users create databases and specify their schema (logical structure) with a data-definition language, e.g. CREATE TABLE students (…).
  2. Querying and modification. Let users ask questions and change data with a high-level query / data-manipulation language (SQL), without writing access code.
  3. Large, persistent storage with efficient access. Store very large amounts of data (terabytes) for long periods, and access it efficiently with indexes and good storage organization (slide 14).
  4. Durability and recovery. Recover the database to a correct state after failures, errors or misuse (slides 20–21).
  5. Concurrent access with isolation and atomicity. Let many users work at once without unexpected interactions (isolation) and without actions being done partially (atomicity) (slides 18–19).
  6. Security. Fine-grained authorization of users and roles on tables, columns and rows (slide 22).
  7. Integrity and controlled redundancy. Enforce constraints (keys, foreign keys, checks) and store each fact once so that data stays consistent.
  8. Data independence. Let structure and storage change (ALTER TABLE, new indexes) without rewriting existing applications (slide 16).

Entity. An entity is a real-world thing or concept, distinguishable from other things, about which the database stores facts. Entities of the same kind form an entity set. Example: each student, such as Jalil (ID 2405190), is an entity of the entity set Students; each course, such as CSE 215, is an entity of Courses.

Attribute. An attribute is a named property that describes an entity; each entity has a value for it, drawn from a set of allowed values (its domain). Example: Students has attributes sid, name and email; for Jalil, sid = 2405190, name = 'Jalil', email = 'jalil@university.edu'. In a relational table, an entity set becomes a table, each entity a row, and each attribute a column.

BUET QBank · CSE 303 | L-3/T-1 | 2011–12 · 8 marks

What are the key properties of a DBMS?

Show worked answer
  1. Self-describing data and data abstraction. The DBMS stores the schema (metadata) in a data dictionary, and users see a logical view (tables) instead of files and bytes.
  2. Data independence. Physical storage can change without changing the logical schema (physical independence), and the logical schema can grow without changing existing programs (logical independence).
  3. Controlled redundancy and integrity. Each fact is stored once in a shared database, and declared constraints (PRIMARY KEY, FOREIGN KEY, CHECK, NOT NULL) are enforced on every change.
  4. Declarative query language. SQL lets users state what they want; the optimizer chooses how to compute it.
  5. Transactions with ACID guarantees. Atomicity (all or nothing), Consistency (correct state to correct state), Isolation (concurrent transactions do not interfere, solving the lost update of the seat example), Durability (committed work survives crashes).
  6. Concurrency control. Locking or MVCC lets many users read and write at once.
  7. Backup and recovery. A transaction log lets the DBMS undo incomplete and redo committed transactions after a failure.
  8. Security. Users, roles and privileges at table, column and row level, with auditing.
  9. Efficient storage of large data. Indexes, buffering and storage management for data much larger than memory.

The bank's answer lists the same properties and is correct.

Summary: when two users read the same value and both write back, one update is lost (slide 18); a DBMS prevents this with transactions and concurrency control (locking or MVCC). When a crash interrupts a multi-step change, the database is left inconsistent (slide 20); a DBMS's log lets it undo uncommitted work and redo committed work. Files offer only manual coordination, manual recovery and whole-file permissions; a DBMS offers built-in concurrency control, transactional recovery and fine-grained users, roles and privileges. These are the ACID properties: atomicity, consistency, isolation, durability.
