Files, Spreadsheets or a DBMS?

Why not keep everything in plain files or a spreadsheet? Slides 12–17 compare the three options on three questions: how much data, what we do with it, and whether its structure changes. This chapter works through each comparison and answers the classic exam question on the advantages of a DBMS over a file system.

1. Easy to start, hard to control (slide 12)

Slide 12 puts a pile of files (A.txt, B.csv, C.xlsx) next to a DBMS. Files are easy to start: any program can write a text file, and anyone can open a spreadsheet. A DBMS is structured, shared and protected, but it takes more setup. The rest of the lecture asks when the extra setup pays off.

File-processing system
The approach used before DBMSs (and still common in small scripts): each application program stores its data in its own operating-system files (text, CSV, binary) and contains its own code to read, search and update them.
Spreadsheet
A grid of cells (Excel, Google Sheets) with formulas, filters and sorting. Good for small tables that people edit by hand.
Workload
What the data will be used for: how big it is, which questions are asked of it, how often it is updated, and by how many users at once.

Slide 13 gives the three questions used to compare the options, and the rule behind them: the best choice depends on the workload, not only on where data is stored.

  1. How much data? Can it grow comfortably?
  2. What will we do with it? Search, query and update.
  3. Will the structure change? New columns, rules and relationships.

2. What if the data becomes very large? (slide 14)

Files are technically possible: log files of many gigabytes are common. But once a file is large, everything around it becomes your responsibility: splitting it into pieces (partitioning), checking that values are valid (validation), making copies (backup), and keeping track of which piece holds what. None of that comes with the file.

Spreadsheets are limited. They are good for small datasets, but a large sheet becomes slow, uses a lot of memory (the whole sheet is usually loaded at once), and is hard to maintain safely. Excel, for example, has a hard limit of 1,048,576 rows per sheet.

A DBMS is designed for it. It is built for persistent data (data that must outlive the program that created it) and handles storage systematically: it reads only the disk blocks a query needs, keeps indexes, and manages space as tables grow. The cost is that a DBMS requires more setup and administration. How it does this is the subject of Lec 13 and Lec 15.

3. What if we need to search, query or update? (slide 15)

Files need custom code. Simple scans are possible: grep "CSE 215" enroll.csv finds lines containing a string. But a question such as “names of students who took more than 18 credits this term” needs a program that parses every line, looks up each course's credits in another file, adds them up and filters. Every new question means new code. Safe updates also need code: to change one line in the middle of a text file, a program usually rewrites the whole file.

Spreadsheets offer basic operations: filters and formulas help with sorting and simple analysis, but combining sheets (joins) and repeated updates become messy (VLOOKUP chains, copied formulas that break).

A DBMS is powerful: it offers SQL, joins and indexes. You state the question and the DBMS finds an efficient way to answer it. The cost is that users must learn the query language.

Query
A question asked of the data, such as “which courses did student 2405190 take in Jan26?”
SQL
Structured Query Language, the standard language for defining, querying and updating relational databases. It is declarative: you say what result you want, not how to compute it.
Join
Combining rows of two tables that refer to each other (an enrollment row with the matching student row). Lecture 02 shows one.
Index
An extra structure that finds the rows with a given value without reading the whole table, like the index at the back of a book.

4. What if the structure changes? (slide 16)

The new requirement on slide 16: add an address to every student.

With files the change is brittle. The file format must change (a new comma-separated field in every line), and every program that reads or writes the file may also need to be changed, because each program has the old format built into its parsing code. A program that expected 3 fields per line may now crash or, worse, read the address where it expected something else. This tight coupling between programs and the physical file layout is called program–data dependence.

With a spreadsheet it is easy, but loose: you add a column in a second. That is fast for small datasets, but nothing forces the column to be filled, so blank cells appear; formulas that referred to column positions break; and people keep separate copies that drift apart.

With a DBMS it is controlled: one statement, ALTER TABLE, changes the table's definition. A default value can fill existing rows, and constraints (rules such as NOT NULL) can be enforced from then on. Programs that did not ask for the address keep working, because they request columns by name, not by position in a file. On a huge production table, such a change (a migration) can still be costly, which is the slide's caveat.

Try it. This is Oracle SQL; the box runs it on an in-browser engine. Press Run, then try adding a second column of your own.

After the ALTER TABLE, the query SELECT sid, name FROM students returns exactly what it returned before. That is the property files lack: adding data to the structure did not break the existing question. The general name for this property is logical data independence, explained in the architecture chapter.

5. Redundancy and inconsistency: the classic file-system problem

The slides' three questions have a fourth, older companion that every textbook lists first (Silberschatz, Database System Concepts, §1.2). In a file-processing system, different offices write different programs, and each program keeps its own files. The same fact ends up stored in several files. This is data redundancy. When the fact changes and only some copies are updated, the copies disagree. This is data inconsistency. Step through the example.

The slide's conclusion: a DBMS is not merely a place to store data. It is a complete data-management layer. Files and spreadsheets store data; a DBMS also organizes it, answers questions about it, and controls how it changes. The next chapter adds the three remaining questions (slides 18–23): many users at once, crashes, and security.

When is a file or spreadsheet the right choice?

The slides do not say “always use a DBMS”. A single user's small, rarely changing data (a personal budget, a one-off experiment's results, an application's configuration file, a log that is only appended and occasionally searched) is fine in a file or spreadsheet: the DBMS's setup and administration would cost more than they save. A DBMS pays off as soon as the data is large, shared by several programs or people, queried in new ways, updated concurrently, or valuable enough that a crash or a wrong edit would hurt.

BUET QBank · CSE 303 | L-3/T-1 | 2010–11 · 14 marks

Describe the key properties that give a DBMS edge over a file system.

Show worked answer

In a file-processing system each application keeps its own files and its own code to read and update them. A DBMS replaces this with one shared, managed database. The properties that give it the edge, each with the file-system problem it solves:

  1. Controlled redundancy, hence consistency. Files: the same fact (a student's address) is copied into the files of several programs; updating one copy and forgetting another leaves the data inconsistent. DBMS: the fact is stored once in an integrated database and every program reads that copy, so one update is seen everywhere.
  2. Data independence. Files: programs depend on the physical file format; adding a field or reorganizing a file forces every program that reads it to change (program–data dependence). DBMS: programs see a logical schema (tables and columns by name); storage can be reorganized (physical data independence) and columns added (logical data independence) without rewriting existing programs.
  3. Easy access through a query language. Files: each new question needs a new program. DBMS: a declarative language (SQL) answers new questions without new code, and a query optimizer picks efficient access paths such as indexes.
  4. Integrity constraints. Files: rules such as “credit must be positive” or “an enrollment must refer to an existing student” are buried in each program's code and are easy to bypass or forget. DBMS: constraints (PRIMARY KEY, FOREIGN KEY, CHECK, NOT NULL) are declared once in the schema and enforced for every program.
  5. Concurrency control. Files: two programs updating the same file at once can overwrite each other (the lost update of the seat example). DBMS: transactions with locking or multiversion concurrency control let many users work at once safely.
  6. Atomicity and crash recovery. Files: a crash in the middle of a multi-step update (debit A, credit B) leaves the files half-updated. DBMS: transactions are all-or-nothing, and the log lets the DBMS undo incomplete work and redo committed work after a failure (durability).
  7. Security. Files: operating-system permissions apply to a whole file. DBMS: users, roles and privileges can be granted per table, per column or (through views) per row, and access can be audited.
  8. Handling large data efficiently. Files: partitioning, indexing and backup are the programmer's job. DBMS: storage management, indexes, buffering and backup are built in.

Data isolation is a further file-system problem worth naming: data scattered in files of different formats is hard to combine in one program. A DBMS keeps everything in one model (tables) so any data can be joined with any other.

The bank's answer covers the same points correctly. One detail to sharpen: it says the DBMS removes redundancy “via normalization”. Normalization is a design technique the designer applies; what the DBMS itself provides is a single shared copy of each table plus constraints that keep related data consistent.

Summary: files and spreadsheets are easy to start but leave size, querying and structural change to you: large files need manual partitioning and backup, every new question needs new code, and a format change breaks every program (program–data dependence). Separate files per program also cause redundancy and inconsistency. A DBMS handles large data systematically, answers declarative SQL queries, changes structure with ALTER TABLE without breaking existing programs, and stores each fact once. It is a complete data-management layer, at the cost of setup and administration.
