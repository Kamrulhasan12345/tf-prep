Query Trees and Logical Optimization

An RA expression can be drawn as a tree and evaluated bottom-up. Many different trees give the same answer; logical optimization picks one in which selections and projections happen as early as possible, so that every later operator handles fewer and narrower tuples. This chapter follows slides 28–44 and measures the gain on sample data.

1. Logically equivalent plans (slides 28–30)

Logically equivalent expressions
Two RA expressions are equivalent if they produce the same relation on every possible database instance, not just on one sample.
Logical optimization
Rewriting an RA expression into an equivalent one that is expected to be cheaper, using algebraic laws. It works on the expression only; choosing algorithms (hash join, index scan…) is physical optimization, Sukarna sir's Lec 07–08.

Slide 29: for R(A, B) and S(B, C), do σ and π commute?

σA=5(πA(R)) = πA(σA=5(R)): yes. The projection keeps A, the only attribute the selection tests, so filtering before or after projecting gives the same set of A values (Chapter 2).

σA=5(πB(R)) ?= πB(σA=5(R)): no. On the left, πB has already removed A, so σA=5 has nothing to test; the left side is not a valid expression. The right side is fine: "the B values of the tuples with A = 5". Rule: a selection can move below a projection, never above one that removes its attributes.

2. Plans as trees (slides 31–32)

Slide 31 draws πB(R(A,B) ⋈ S(B,C)) as a query tree (expression tree): leaves are relations, inner nodes are operators, and each node's children are its inputs. "Bottom-up tree traversal = order of operation execution": a node can run once its children have produced their results, so execution starts at the leaves and ends at the root.

Slide 32: what SQL query does this correspond to? Are there logically equivalent RA expressions?

The join pairs R and S tuples with equal B, and the projection keeps B without duplicates:

SELECT DISTINCT R.B
FROM R, S
WHERE R.B = S.B;

Equivalent expressions (all return "the B values that occur in both R and S"):

  • πB(R) ⋈ πB(S), the plan of slide 33;
  • πB(R) ∩ πB(S), because a natural join of two relations with the same single attribute is their intersection (Chapter 4);
  • πB(R ⋈ πB(S)) and πB(S ⋈ R) (joins commute).

All of them are in the evaluator below; on the sample data they all return the same B values.

3. Pushing down projections and selections (slides 33–37)

Slide 33: why might we prefer πB(R) ⋈ πB(S)?

Because the join then works on narrower and fewer tuples. Projecting R and S onto B first (1) drops the attributes A and C that the query never outputs, so each tuple is smaller and more of them fit in a block, and (2) merges duplicate B values, so the join has fewer tuples to match. The join's output is also tiny: just the common B values, with no A or C. On the sample data below, the original join outputs 13 tuples of 3 attributes (39 values) only to throw A and C away; in the pushed-down plan the join receives 6 and 7 one-attribute tuples and outputs 6 values. With realistic tables, where tuples are wide and many share a B value, the difference is far larger.

Slide 34: "It is always possible to change the order of selections": σA=10(σB>0(R)) = σB>0(σA=10(R)). Both keep exactly the tuples with A = 10 and B > 0. Slide 35: a projection can be pushed through a join, provided the join attributes are kept: πA,C(R(A,B,D) ⋈ S(B,C)) = πA,C(πA,B(R) ⋈ S). D is not needed anywhere, so it is projected out before the join; B must stay because the join needs it.

Slide 36's takeaways: this process is called logical optimization; the optimizer generates many equivalent plans and searches them for a good one; relational algebra is the abstraction that makes this possible. 4. Optimizing an SFW plan (slides 38–44)

Slide 39 translates this query over R(A,B), S(B,C), T(C,D):

SELECT R.A, T.D
FROM R, S, T
WHERE R.B = S.B AND S.C = T.C AND R.A < 10;

The two equalities equate shared attributes, so they become natural joins; R.A < 10 becomes a selection, and the SELECT list a projection: πA,D(σA<10(T ⋈ (R ⋈ S))). Slide 40 states the heuristic: selections and projections should happen as early as possible, because then "we will have fewer tuples in a plan". Slides 41–44 apply it in two moves. Step through them; each frame shows the plan and, measured on the sample data, the number of tuples every operator outputs.

Slide 44: in general, when is an attribute not needed?

An attribute is not needed above some point of the tree when no operator above that point uses it: it is not in the final projection list, and it does not appear in any selection condition or join condition that is still to be evaluated higher up. In slide 44's plan, B is used only by the join R ⋈ S. Once that join is done, B is dead, so πA,C drops it immediately; A is kept for the output and C for the join with T. (Slide 44 writes the subscript as "A,c"; it means A, C.)

Selection pushing usually gives the biggest gain, because it reduces the number of tuples; projection pushing reduces their width. Real optimizers combine these heuristics with cost estimates (sizes, available indexes) to choose the join order and algorithms, which is the topic of Lec 07–08 and the textbook's §16.4–16.6.

Summary: A query tree has relations at the leaves and operators inside; it is evaluated bottom-up. Equivalent expressions give the same result on every instance. Logical optimization rewrites the tree with laws: selections commute with each other, move below projections that keep their attributes and below joins onto the side whose attributes they use; projections move below selections and joins as long as condition and join attributes are kept. Heuristic: push selections and projections as far down as possible. An attribute can be dropped as soon as no operator above uses it.
