Triggers: Syntax, Row vs Statement, :NEW and :OLD

A trigger is a block of code the database runs by itself when a table is changed. This chapter explains the Oracle trigger syntax of slide 50 clause by clause, animates how row-level and statement-level triggers fire, walks through the two example triggers of slides 51–52 line by line, and lets you experiment in a trigger simulator.

1. What a trigger is

Trigger (ECA rule)
A named piece of code stored in the database and executed automatically when a specified event happens to a table. The textbook (§7.5) calls triggers event-condition-action rules: an event (INSERT, UPDATE or DELETE on a table) awakens the trigger; a condition is tested; if it holds, the action runs.
Triggering statement
The INSERT, UPDATE or DELETE statement whose execution fires the trigger.

Why not just use constraints? A CHECK constraint can only look at the row being written, and a foreign key can only reject, cascade or set null. A trigger can run arbitrary code: look at other tables, change other tables, change the row being written, or reject the change with your own message. That flexibility is also the danger: triggers run invisibly, so a simple-looking UPDATE can do a lot more than it says. Prefer a declarative constraint when one can express the rule (Lec 06), and use a trigger when it cannot.

2. The Oracle syntax (slide 50)

CREATE [OR REPLACE] TRIGGER trigger_name{BEFORE | AFTER}{INSERT [OR] | UPDATE [OR] | DELETE}[OF col_name]ON table_name[REFERENCING OLD AS o NEW AS n][FOR EACH ROW]WHEN (condition)BEGIN  Executable-statementsEND;
LineClauseMeaning
1CREATE [OR REPLACE] TRIGGER nameCreates the trigger. OR REPLACE overwrites an existing trigger of the same name instead of failing, which is what you want while developing.
2BEFORE | AFTERThe timing: run the trigger before or after the triggering statement changes each row (row-level) or the table (statement-level). A third option, INSTEAD OF, exists for views (Chapter 11).
3INSERT OR UPDATE OR DELETEThe event. Several can be combined with OR; inside the body the predicates INSERTING, UPDATING, DELETING tell which one fired it.
4OF col1, col2Only for UPDATE: fire only when the UPDATE's SET list names one of these columns. Without OF, any UPDATE of the table fires it.
5ON tableThe table whose changes are watched.
6REFERENCING OLD AS o NEW AS nOptional: renames the correlation names OLD and NEW (section 4) to o and n. Useful only if your table is itself called NEW or OLD; the slides use it to name them oldTupple / newTupple.
7FOR EACH ROWMakes the trigger row-level: it fires once per affected row. Without it, the trigger is statement-level and fires once per statement (section 3).
8WHEN (condition)The condition. It is optional, although the slide's template shows it without the [ ] it puts around the other optional clauses. Allowed only for row-level triggers. It may refer to new.col and old.col without a colon, and it cannot contain a subquery.
9–11BEGIN … END;The action, a PL/SQL block. It may start with DECLARE for local variables. Inside it, the row values are :NEW.col and :OLD.col with a colon.

In SQL*Plus and SQL Developer a PL/SQL block (a trigger, procedure or function) must be followed by a line containing only /, which tells the tool to send the block to the server. That is the slash at the end of slides 51 and 52. If the trigger has a compilation error, Oracle still creates it but marks it invalid; SHOW ERRORS lists the problems.

3. Row-level and statement-level triggers

Row-level trigger (FOR EACH ROW)
Fires once for every row the triggering statement inserts, updates or deletes. It can see that row's old and new values. If the statement affects no row, it never fires.
Statement-level trigger (the default)
Fires exactly once per triggering statement, even if the statement affects zero rows. It cannot see individual rows (:NEW and :OLD are not available).

When several triggers exist on one table, Oracle fires them in this order for one statement:

  1. BEFORE statement-level triggers (once);
  2. for each affected row: BEFORE row-level triggers, then the row is changed, then AFTER row-level triggers;
  3. AFTER statement-level triggers (once).

The animation runs UPDATE PC SET price = price - 100 WHERE speed >= 2.80, which changes 3 rows, with four triggers on PC (one of each kind). Count how often each fires.

4. :NEW and :OLD

In a row-level trigger, :OLD is the row as it was before the statement changed it and :NEW is the row as it will be after. Which ones exist depends on the event:

Event:OLD:NEW
INSERTall columns NULL (there was no old row)the row being inserted
UPDATEthe row before the updatethe row after the update
DELETEthe row being deletedall columns NULL
  • In a BEFORE row trigger you may assign to :NEW.col (for example :NEW.price := 0;) and the changed value is what gets stored. In an AFTER row trigger the row is already written, so assigning to :NEW is a compile error (ORA-04084).
  • Write the colon in the body (:NEW.price), not in WHEN (new.price). With REFERENCING NEW AS n, write :n.price and n.price.

5. Slide 51: refusing negative values

CREATE OR REPLACE TRIGGER NoNegativeBEFORE UPDATE OF Price, speed ON PCREFERENCING new as newTuppleFOR EACH ROWWHEN (newTupple.price < 0 OR newTupple.speed < 0)BEGIN    RAISE_APPLICATION_ERROR(-20000, 'no negative value allowed');END;/
  • Line 1. Create (or replace) a trigger called NoNegative.
  • Line 2. It runs before an UPDATE of PC that sets price or speed (column names are not case-sensitive, so Price = price). An UPDATE that only changes ram does not fire it.
  • Line 3. Inside this trigger the new row is called newTupple instead of NEW (the spelling is the slide's).
  • Line 4. Row-level: once per updated row.
  • Line 5. The condition: the new price or the new speed is negative. No colon here, because it is the WHEN clause.
  • Lines 6–8. The action raises an error, which stops the UPDATE (section 6).
  • Line 9. The slash runs the CREATE in SQL*Plus.

BEFORE or AFTER? Either would stop the statement, but BEFORE is the right choice for validation: the bad value is rejected before any row is written, so there is less work to undo.

A gap in the slide's trigger: it fires only on UPDATE, so INSERT INTO PC VALUES (1020, -2.0, 512, 80, 400) still stores a negative speed. To guard both, write BEFORE INSERT OR UPDATE OF price, speed ON PC. (For a rule about a single row like this one, a CHECK (price >= 0 AND speed >= 0) constraint does the same job more simply; the slide uses it to show the syntax.)

Try it. 6. RAISE_APPLICATION_ERROR

RAISE_APPLICATION_ERROR(error_number, message) is a built-in Oracle procedure that raises an error with your own number and text. The number must be between −20000 and −20999 (the range Oracle reserves for applications). When a trigger raises an error that it does not handle itself:

  • the triggering statement fails, and every change it made, including changes made by triggers it fired, is undone (statement-level atomicity);
  • the transaction is not rolled back: earlier statements of the same transaction keep their effects, and the application decides whether to roll back;
  • the client receives the error, e.g. ORA-20000: no negative value allowed.

7. Slide 52: cascading a delete

CREATE OR REPLACE TRIGGER cascadingBEFORE delete ON PCREFERENCING OLD AS oldTuppleFOR EACH ROWBEGINDELETE FROM ProductWHERE model = :oldTupple.model;END;/
  • Line 1. Create the trigger "cascading".
  • Line 2. Fire before each DELETE on PC.
  • Line 3. Call the deleted row oldTupple (instead of OLD).
  • Line 4. Once per deleted PC row.
  • Lines 5–8. No WHEN clause, so the action always runs: delete the Product row with the same model. Note the colon: :oldTupple.model is in the body.

So deleting a PC also deletes its row in Product, keeping the two tables consistent: a model listed in Product as a pc always has a PC row. One deleted PC row fires the trigger once; DELETE FROM PC WHERE price < 600 deleting 3 rows fires it 3 times.

A caution about timing. In the textbook's schema PC.model is usually a foreign key referencing Product.model. In that case this BEFORE trigger fails with ORA-02292 (child record found): when it runs, the PC row still exists, so the parent Product row cannot be deleted yet. Declared as AFTER DELETE, the PC row is already gone and the Product delete succeeds. Without the foreign key, as on the slide, both work.

SQLite version (syntax differs from Oracle): run the DELETE and look at Product: the deleted PCs' models are gone from Product too.

Exam questions

DB QB · 20-21 8c · 12 marks  |  BUET QBank · CSE 215 | L-2/T-2 | 2020–21 · 12 marks

Consider the following two schemas: Product(maker, model, type), Laptop(model, speed, ram, hd, screen, price). Write necessary triggers to implement the following constraints:

(i) speed, ram, hd, screen and price cannot be negative.
(ii) When a Laptop model is deleted, that model must also be deleted from the Product table.

Show worked answer

(i) A negative value can enter through an INSERT or through an UPDATE of one of the five columns, so one row-level BEFORE trigger covers both events:

CREATE OR REPLACE TRIGGER LaptopNoNegative
BEFORE INSERT OR UPDATE OF speed, ram, hd, screen, price ON Laptop
FOR EACH ROW
WHEN (new.speed < 0 OR new.ram < 0 OR new.hd < 0
      OR new.screen < 0 OR new.price < 0)
BEGIN
  RAISE_APPLICATION_ERROR(-20001,
    'Laptop ' || :NEW.model || ': speed, ram, hd, screen and price cannot be negative');
END;
/

BEFORE rejects the row before it is written; FOR EACH ROW is needed to see the new values; the WHEN clause uses new. without a colon, the body uses :NEW. with one. A NULL value makes its comparison unknown, so NULLs are allowed (add IS NULL tests if they should be rejected too).

(ii)

CREATE OR REPLACE TRIGGER LaptopDeleteProduct
AFTER DELETE ON Laptop
FOR EACH ROW
BEGIN
  DELETE FROM Product WHERE model = :OLD.model;
END;
/

Row-level, because each deleted laptop has its own model; :OLD holds the deleted row. AFTER is the safe timing if Laptop.model is a foreign key to Product.model (with BEFORE, the laptop row would still exist and the parent delete would fail with ORA-02292), and it works equally well without the foreign key. This is slide 52's pattern applied to Laptop.

Note: the question bank's answer is written in MySQL syntax (DELIMITER, SIGNAL SQLSTATE, two separate INSERT and UPDATE triggers). The course uses Oracle, where one trigger with INSERT OR UPDATE and RAISE_APPLICATION_ERROR is the expected form.

Summary: A trigger is an event-condition-action rule: CREATE OR REPLACE TRIGGER name {BEFORE|AFTER} {INSERT OR UPDATE [OF cols] OR DELETE} ON table [REFERENCING …] [FOR EACH ROW] [WHEN (cond)] BEGIN … END; /. Row-level triggers fire once per affected row and see :OLD/:NEW (colon in the body, none in WHEN); statement-level triggers fire once per statement, even for zero rows. Order: BEFORE statement, then per row BEFORE row / change / AFTER row, then AFTER statement. Only BEFORE row triggers can change :NEW. RAISE_APPLICATION_ERROR(−20000…−20999, msg) aborts the triggering statement.
