Natural Join (⋈) and Translating SQL to RA

The natural join pairs rows that agree on every attribute the two relations share. This chapter derives it from ×, σ, π and ρ as slide 17 does, answers slide 19's three schema questions, and then turns SQL blocks into RA, including the question bank's "write it using a Cartesian product, then using a natural join" questions.

1. Definition (slide 17)

Natural join R1 ⋈ R2
Pairs each tuple of R1 with each tuple of R2 that has equal values on all shared attributes (attributes with the same name), and keeps one copy of each shared attribute. If R1 has attribute set A and R2 has B, the result's attributes are A ∪ B.
Shared attributes C = A ∩ B
The attributes that appear in both schemas. Slide 17 also writes the join as R1 ⋈C R2 to make them explicit.
Dangling tuple
A tuple of one relation that matches no tuple of the other. It does not appear in the natural join at all. (The outer joins of Chapter 6 keep dangling tuples.)

The natural join is the slides' first derived operator. Slide 17 gives its meaning in terms of the basic operators:

R1 ⋈ R2 = πA ∪ B(σC = D(ρC→D(R1) × R2))

  1. ρC→D(R1) renames the shared attributes C in one relation to new names D, so the product does not contain two attributes with the same name.
  2. × R2 forms all pairs.
  3. σC = D keeps the pairs where every renamed attribute equals its original partner.
  4. πA ∪ B drops the renamed copies D, leaving one copy of each shared attribute.

The same thing in SQL, for Students(sid, name, gpa) and People(ssn, name, address), which share name (slide 17):

SELECT DISTINCT sid, S.name, gpa,
       ssn, address
FROM Students S, People P
WHERE S.name = P.name;

Students ⋈ People

The slide's SQL says ssid in the SELECT list; that is a typo for sid. Oracle also has the join written out as a keyword, SELECT * FROM Students NATURAL JOIN People;, which does the matching and the single copy of name automatically.

Slide 18's example, step by step

The animation evaluates slide 17's formula literally, so you can see each of the four steps, and then the ⋈ operator directly. Both give the same two tuples. (Slide 18 prints Bob's address in the result as 216 Rosse; People says 217 Rosse, and a join only copies values, so 217 Rosse is correct.)

2. Slide 19's three questions

Given R(A, B, C, D) and S(A, C, E), what is the schema of R ⋈ S?

The shared attributes are A and C. The result has every attribute once: (A, B, C, D, E). A tuple r of R joins a tuple s of S when r.A = s.A and r.C = s.C.

Given R(A, B, C) and S(D, E), what is R ⋈ S?

There are no shared attributes, so the condition "agree on all shared attributes" is true for every pair (there is nothing to check). R ⋈ S = R × S, with schema (A, B, C, D, E).

Given R(A, B) and S(A, B), what is R ⋈ S?

Every attribute is shared, so a pair joins only when the two tuples are identical, and the result keeps one copy of each attribute. R ⋈ S = R ∩ S, schema (A, B).

Check all three in the evaluator below (examples 3–5 use small relations R, S with those schemas).

A trap: shared names that mean different things

The natural join matches attributes by name only. If two relations happen to use the same name for unrelated things, the join silently adds an unwanted condition. Example from the question bank: Emp(eno, ename, title, city) and Proj(pno, pname, budget, city). Emp ⋈ Works ⋈ Proj would also force Emp.city = Proj.city, keeping only employees who live in their project's city. The fix is to project away (or rename) the clashing attribute first, or to use a theta join with an explicit condition (Chapter 6). Always list the shared attributes before writing ⋈.

3. Converting an SFW query to RA (slide 20)

A SELECT-FROM-WHERE (SFW) query translates mechanically:

  1. FROM R1, R2, … becomes R1 × R2 × … (rename with ρ if a table appears twice or has an alias that the query uses).
  2. WHERE c becomes σc on top.
  3. SELECT DISTINCT list becomes πlist on top of that.
  4. Optionally, a σ whose condition equates the shared attributes, on top of ×, can be written as ⋈ (and other equality conditions as a theta join).

Slide 20: how do we represent this query in RA?

Schema: Students(sid, sname, gpa), People(ssn, sname, address).

SELECT DISTINCT gpa, address
FROM Students S, People P
WHERE gpa > 3.5 AND S.sname = P.sname;

Literal translation: πgpa,address(σgpa>3.5 ∧ S.sname=P.sname(ρS(Students) × ρP(People))). The condition S.sname = P.sname equates the only shared attribute, so σ and × together are a natural join, which gives the slide's answer:

πgpa,address(σgpa>3.5(S ⋈ P))

Both are in the evaluator above (examples 6 and 7). On the sample data (John 3.4, Bob 1.3, Rina 3.8, Tanvir 3.6, and only John and Bob are People) the result is empty: the two students with gpa > 3.5 have no matching person. That is a correct answer, not a bug; an empty relation is still a relation.

DB QB · Jan 20 15 · 10 marks + Jan 20 16 · 10 marks  |  BUET QBank · CSE 215 | L-2/T-2 | 2018–19 · 20 marks

Consider the following schema of Sonali Bank Limited.

customer (customer_id, customer_name, customer_address)
account (account_id, account_type, account_branch, account_balance)
branch (branch_routing_number, branch_name)
transaction (account_id, transaction_amount, transaction_date)
loan (loan_id, customer_id, loan_amount)

Notice that the attribute account_branch of table account is a foreign key referencing the primary key branch_routing_number from table branch. On the other hand, the attribute account_id of table account is a foreign key referencing the primary key customer_id from table customer.

(a) Write a relational algebra expression using Cartesian product to find out the customers' name and their corresponding loan amounts who have a "savings" type account at the branch named "BUET Br.".

(b) Write the equivalent relational algebra expression for the following SQL statement:

select c.customer_name, a.account_id, t.transaction_amount
from customer c, account a, transaction t
where c.customer_id = a.account_id and a.account_id = t.account_id
and t.transaction_date = "01-JAN-2020" and t.transaction_amount > 5000
Show worked answer

Reading the schema. The odd foreign key says that an account's id is the id of the customer who owns it, so "customer c owns account a" is the condition c.customer_id = a.account_id. A loan belongs to a customer through loan.customer_id. An account is at a branch through account_branch = branch_routing_number.

(a) Take the product of the four relations, keep the combinations that are linked by the three foreign keys and that satisfy the two filters, and project:

πcustomer_name, loan_amount(σθ(customer × account × branch × loan))

θ = customer.customer_id = account.account_id ∧ account.account_branch = branch.branch_routing_number ∧ loan.customer_id = customer.customer_id ∧ account.account_type = 'savings' ∧ branch.branch_name = 'BUET Br.'

All the attribute names except customer_id are unique, so only customer_id needs its relation prefix. A customer with two loans appears twice with two amounts, which is what "their corresponding loan amounts" asks for. A better plan pushes the two filters down (σaccount_type='savings'(account), σbranch_name='BUET Br.'(branch)) before the products, but the question asks for the Cartesian-product form.

(b) FROM is a product, WHERE is a selection, SELECT is a projection. The aliases c, a, t become ρ (or simply the relation names, since each table appears once):

πc.customer_name, a.account_id, t.transaction_amount(σφ(ρc(customer) × ρa(account) × ρt(transaction)))

φ = c.customer_id = a.account_id ∧ a.account_id = t.account_id ∧ t.transaction_date = '01-JAN-2020' ∧ t.transaction_amount > 5000

Note the SQL is not SELECT DISTINCT, so strictly it returns a bag; the RA answer is the set version, which is the standard reading in this course. (The date literal in double quotes is not valid Oracle; it should be DATE '2020-01-01' or TO_DATE('01-JAN-2020', 'DD-MON-YYYY').)

Both expressions were evaluated on invented sample data in the evaluator below; the SQL box under it runs the matching Oracle SQL and gives the same rows. (In the SQL box the table name is written "transaction" in double quotes, because the playground's SQLite engine treats TRANSACTION as a keyword. Oracle accepts it unquoted.)

BUET QBank · CSE 303 | L-3/T-1 | 2016–17 · 20 marks

Given three relations: customer(customer_id, name, street, city), account(account_number, type, balance), transaction(customer_id, account_number, date, amount).

(a) Write a relational algebra expression using Cartesian product to find customer_id, date and amount of all transactions made by customer id "C005".
(b) Rewrite the expression of (i) using natural join.
(c) Write the equivalent relational algebra expression for the following SQL:

SELECT a.customer_id, b.account_number, name, street, city
FROM customer AS a, account AS b, transaction AS c
WHERE a.customer_id = c.customer_id
  AND b.account_number = c.account_number
  AND date = '01-JAN-2017'
  AND amount > 10000;
Show worked answer

(a) Pair customers with transactions, keep the pairs that belong together and are for C005, then project:

πtransaction.customer_id, date, amount(σcustomer.customer_id = transaction.customer_id ∧ customer.customer_id = 'C005'(customer × transaction))

Only customer_id appears in both relations, so only it needs a prefix. (All three wanted attributes are in transaction, so πcustomer_id,date,amount(σcustomer_id='C005'(transaction)) would also do; the product is there because the question asks for it. The two differ only if a transaction referred to a customer that does not exist, which the foreign key forbids.)

(b) The selection's first conjunct equates the only shared attribute, so σ + × is a natural join:

πcustomer_id, date, amount(σcustomer_id = 'C005'(customer ⋈ transaction))

(c) Literal translation (the aliases a, b, c are renamings):

πa.customer_id, b.account_number, name, street, city(σa.customer_id = c.customer_id ∧ b.account_number = c.account_number ∧ date = '01-JAN-2017' ∧ amount > 10000(ρa(customer) × ρb(account) × ρc(transaction)))

Equivalently with natural joins, because customer–transaction share only customer_id and account–transaction share only account_number (customer and account share nothing):

πcustomer_id, account_number, name, street, city(σdate = '01-JAN-2017' ∧ amount > 10000(customer ⋈ transaction ⋈ account))

All four expressions were run on sample data below (dates stored as 'YYYY-MM-DD' text, so the evaluator compares with '2017-01-01'). In real Oracle, DATE is a reserved word, so the column would have to be called something else (for example txn_date).

Summary: R ⋈ S pairs the tuples that agree on all shared attributes and keeps one copy of each, = πA∪B(σC=D(ρC→D(R) × S)). No shared attributes: ⋈ = ×. All attributes shared: ⋈ = ∩. A SQL block becomes πSELECT(σWHERE(FROM-product)); equalities on shared attributes turn σ + × into ⋈. Check for accidental shared names before using ⋈.
