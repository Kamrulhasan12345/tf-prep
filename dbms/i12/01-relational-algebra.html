Relational Algebra and the SQL Engine

Why a database turns your SQL into relational algebra, what the operators of that algebra are, and the two conventions the slides use (sets, and named attributes). It also introduces the RA evaluator you will use in every chapter of this lecture.

The title slide calls this deck "Lecture 11, Chapter 2: The Relational Algebra and Triggers". In this course it is Lecture 12. The first part (slides 2–49) is relational algebra; the second part (slides 50–52) is triggers, covered from Chapter 10 on.

1. How a SQL engine runs a query (slides 2–3)

SQL is declarative: a query says what rows you want, never how to find them. Before a database can run it, it must turn it into a precise sequence of operations. Slide 2 shows the four stages:

  1. SQL query. The user writes a declarative query.
  2. Relational algebra (RA) plan. The engine translates the query into an expression of relational algebra: a formula built from a few operators, each taking relations as input and producing a relation.
  3. Optimized RA plan. Many different RA expressions give the same answer. The optimizer rewrites the expression into an equivalent one that is cheaper to run (Chapter 7).
  4. Execution. Each operator of the chosen plan is run by a physical algorithm, such as a scan, a sort or a hash join. Those algorithms are Sukarna sir's Lec 07–08 (the query processor).

Slide 3 states the point of the whole topic: relational algebra allows us to translate declarative (SQL) queries into precise and optimizable expressions. "Precise" because every RA operator has an exact mathematical definition. "Optimizable" because algebra has laws (like x·(y+z) = x·y + x·z in arithmetic) that let you rewrite an expression into a faster equivalent one.

Relational algebra (RA)
A set of operators that take one or two relations as input and produce a new relation as output. Expressions are built by applying operators to relations and to the results of other operators.
Algebra
In general, a set of operands (here: relations) and operators that build new operands from old ones (textbook §2.4.2). Ordinary arithmetic is an algebra over numbers with +, −, ×, ÷.
Closure
The output of every RA operator is again a relation. So operators can be nested to any depth: the output of one is the input of the next. Slide 10 calls this being compositional.
Relation, tuple, attribute, schema
A relation is a table. Each row is a tuple, each column an attribute. The schema of a relation is its name plus its list of attributes, written like Students(sid, sname, gpa). The number of attributes is the relation's arity (degree); the number of tuples is its cardinality.

3. Two conventions: sets and named attributes (slide 5)

RA operates on sets

A set contains each element at most once. A bag (multiset) may contain the same element several times. Real database systems store and return bags: a SQL table can hold two identical rows, and SELECT dept_name FROM instructor returns one row per instructor, repeats included. The relational algebra of these slides works on sets: every relation, including every intermediate result, has no duplicate tuples. Whenever an operator would produce the same tuple twice (projection is the usual culprit), the copy is dropped. That is why π is matched with SELECT DISTINCT, and why the evaluator below always removes duplicates.

The named perspective

The slides use the named perspective: every attribute has a unique name, and you refer to an attribute by its name, never by its position. As a result attribute order does not matter: (sid, sname, gpa) and (gpa, sid, sname) describe the same relation. When two relations with the same attribute name meet (for example in R × S, where both have an attribute B), the attributes are told apart by prefixing the relation name: R.B and S.B.

Why does the theory use sets when real systems use bags?

Sets make the algebra simpler and give it more laws. For example, R ∪ R = R holds for sets but not for bags. Systems use bags because removing duplicates costs a sort or a hash (see δ in Lec 07) and because duplicates are often needed, for instance to compute an average correctly. The book treats bag semantics in §5.1. For this lecture, assume sets unless a question says otherwise; one exam question that says "assume bags" is answered in Sukarna sir's Lec 08 chapter.

4. The RA evaluator used in this lecture

Every chapter of this lecture has a live RA evaluator. You type an expression in a plain-ASCII syntax, it draws the expression as a tree, and then runs it bottom-up, one operator per step, showing each intermediate relation. Summary: A SQL engine translates a declarative query into a relational-algebra expression, optimizes that expression with algebraic laws, and executes it operator by operator. RA has five basic operators (σ, π, ×, ∪, −), derived ones (∩, the joins) and renaming ρ. Every operator returns a relation, so operators compose. In this lecture relations are sets (no duplicates) and attributes are referred to by name, so attribute order does not matter.
