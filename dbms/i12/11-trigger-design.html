Designing Triggers: Statement Triggers, INSTEAD OF, Mutating Tables

The slides show two simple row triggers. Exam questions ask for harder ones: a trigger that reads the table it is attached to, one that updates related rows, one that keeps an average in bounds. This chapter covers what those need in Oracle (statement-level and compound triggers, the mutating-table rule, INSTEAD OF triggers, cascading), what triggers are used for and what they may not do, and then works the bank's trigger questions.

1. Statement-level triggers and event predicates

A statement-level trigger (no FOR EACH ROW) suits rules about the statement, not about individual rows: "no changes to PC outside office hours", "log who ran a DELETE". With several events in one trigger, the predicates INSERTING, UPDATING (or UPDATING('price')) and DELETING say which event fired it:

CREATE OR REPLACE TRIGGER pc_audit
AFTER INSERT OR UPDATE OR DELETE ON PC
BEGIN                                   -- statement-level: once per statement
  INSERT INTO pc_audit_log(who, what, at_time)
  VALUES (USER,
          CASE WHEN INSERTING THEN 'INSERT'
               WHEN UPDATING  THEN 'UPDATE'
               ELSE 'DELETE' END,
          SYSDATE);
END;
/

USER is the current Oracle user and SYSDATE the current date and time. A statement-level trigger cannot read :NEW or :OLD; if it needs the changed rows it must query the table.

2. The mutating-table rule (ORA-04091)

Mutating table
A table that is being changed by the statement currently running. In Oracle, a row-level trigger may not query or modify the table it is defined on (nor tables being changed by ON DELETE CASCADE from it). Doing so raises ORA-04091: table … is mutating, trigger/function may not see it at run time.

The reason: a row trigger fires in the middle of the statement. After 2 of 5 rows have been updated, the table is half old, half new, so any query on it would see an inconsistent state, and the answer would depend on the order in which Oracle happened to visit the rows. Oracle forbids the read rather than return such an answer. (Statement-level triggers are allowed to read the table, because they run before the first row or after the last one.)

Typical cases that hit it, both in the question bank: a row trigger on MovieExec that computes AVG(netWorth) from MovieExec, and a row trigger on works that updates other rows of works. The standard fixes:

  1. Use a statement-level trigger when the check can be made once, after the statement (for example "if the average is now too low, raise an error").
  2. Use a compound trigger (Oracle 11g and later) when you need both per-row information and the whole table. One trigger has sections that share variables: BEFORE STATEMENT, BEFORE EACH ROW, AFTER EACH ROW, AFTER STATEMENT. Read the table in a statement section, remember what you need in variables, and use it in the row sections (or collect rows in the row section and act on them in AFTER STATEMENT).

SQLite, the playground's engine, has no mutating-table rule, so the SQLite versions below can read and write the same table directly; just remember that the Oracle answer needs one of the two fixes.

3. Cascading and recursive triggers

A trigger's action can change another table, which fires that table's triggers, and so on: cascading. Slide 52's trigger is one (deleting a PC deletes a Product row, which would fire any delete trigger on Product). If a chain comes back to the table it started from, the triggers are recursive, which can loop forever. Oracle stops a chain after 32 nested trigger levels with an error. Design rule: give every trigger a condition that eventually becomes false (for example WHEN (new.salary <> old.salary)), and prefer foreign keys with ON DELETE CASCADE over hand-written cascading triggers when they express the rule.

4. INSTEAD OF triggers on views

INSTEAD OF trigger
A row-level trigger defined on a view. When someone runs INSERT, UPDATE or DELETE on the view, Oracle does not try to change the view; it runs the trigger body instead, which changes the underlying base tables (textbook §8.2.3). It makes views updatable that Oracle could not update by itself, such as join views.
CREATE OR REPLACE VIEW pc_catalog AS
  SELECT p.maker, c.model, c.speed, c.price
  FROM Product p JOIN PC c ON p.model = c.model;

CREATE OR REPLACE TRIGGER pc_catalog_ins
INSTEAD OF INSERT ON pc_catalog
FOR EACH ROW
BEGIN
  INSERT INTO Product(maker, model, type) VALUES (:NEW.maker, :NEW.model, 'pc');
  INSERT INTO PC(model, speed, ram, hd, price)
    VALUES (:NEW.model, :NEW.speed, NULL, NULL, :NEW.price);
END;
/

An INSERT into the view now adds one row to each table. INSTEAD OF triggers are always row-level, have no BEFORE/AFTER, and can only be defined on views. SQLite version (syntax differs from Oracle) to try:

5. What triggers are used for, and their restrictions

Typical uses:

  1. Integrity rules that constraints cannot express: rules involving several rows or tables (a prerequisite check at registration, an average that must stay above a bound), or rules that should repair instead of reject.
  2. Maintaining derived data: keep a total, a count or a summary table up to date (a hand-made materialized view), or denormalized copies of a value.
  3. Auditing and logging: record who changed what and when, with old and new values.
  4. Propagating changes: cascades that foreign keys cannot do (slide 52 deletes the parent when a child is deleted), or replication to another table.
  5. Making views updatable with INSTEAD OF triggers.
  6. Security and business-hour rules: reject changes at certain times or by certain users.

Restrictions in Oracle:

  • No transaction control: COMMIT, ROLLBACK and SAVEPOINT are not allowed in a trigger (the trigger is part of the triggering statement's transaction). The exception is a trigger declared as an autonomous transaction, typically for logging.
  • The mutating-table rule for row-level triggers (section 2).
  • WHEN only for row-level triggers, and it cannot contain a subquery or call a PL/SQL function.
  • :NEW and :OLD only in row-level triggers; :NEW may be assigned only in BEFORE row triggers; INSERT has no :OLD values and DELETE no :NEW values.
  • INSTEAD OF only on views, always row-level; BEFORE/AFTER triggers cannot be defined on views.
  • A trigger body is limited to 32 KB (put long logic in a procedure and call it), and at most 32 triggers can cascade.
  • DDL statements (CREATE, ALTER, DROP) cannot be issued directly in a DML trigger.

DB QB · 23-24 4b · 10 marks  |  BUET QBank · CSE 215 | L-2/T-1 | 2023–24 · 10 marks

Consider the following schema: Student(Ssn, Name), TakenCourses(Ssn, CourseNo), Register(Ssn, CourseNo), Course(CourseNo, Name, Year, Term), PreRequisite(CourseNo, ReqCourseNo). Table TakenCourses manages courses info that a student has taken previously. A course may require pre-requisite courses and the pre-requisite course info is managed in table PreRequisite. Write a trigger to check if the student took the pre-requisite courses when s/he registers for a new course. If s/he didn't take a prerequisite course, the registration of the course should fail and an appropriate message should be displayed.

Show worked answer

Design. Event: a new row in Register (INSERT, and also an UPDATE that changes Ssn or CourseNo). Timing: BEFORE, so a bad registration is never written. Level: row, because each registration has its own student and course (:NEW.Ssn, :NEW.CourseNo). Condition: some prerequisite of :NEW.CourseNo is not among the courses :NEW.Ssn has taken. Action: RAISE_APPLICATION_ERROR, which makes the INSERT fail with the message. The trigger reads PreRequisite and TakenCourses, not Register, so there is no mutating-table problem.

CREATE OR REPLACE TRIGGER CheckPrerequisites
BEFORE INSERT OR UPDATE OF Ssn, CourseNo ON Register
FOR EACH ROW
DECLARE
  v_missing NUMBER;
BEGIN
  SELECT COUNT(*) INTO v_missing
  FROM PreRequisite p
  WHERE p.CourseNo = :NEW.CourseNo
    AND NOT EXISTS (SELECT * FROM TakenCourses t
                    WHERE t.Ssn = :NEW.Ssn
                      AND t.CourseNo = p.ReqCourseNo);

  IF v_missing > 0 THEN
    RAISE_APPLICATION_ERROR(-20002,
      'Registration failed: student ' || :NEW.Ssn || ' has not taken ' ||
      v_missing || ' prerequisite course(s) of ' || :NEW.CourseNo);
  END IF;
END;
/

Line by line: DECLARE introduces a local variable for the count; SELECT … INTO stores the number of prerequisites of the new course that have no matching TakenCourses row for this student; if it is positive the registration is rejected and the INSERT (or UPDATE) fails with ORA-20002 and the message. A course with no prerequisites gives a count of 0 and the registration goes through. NOT EXISTS is used instead of NOT IN because NOT IN returns no rows at all if the subquery produces a NULL. (The bank's answer is correct apart from using NOT IN and covering only INSERT.)

SQLite version (syntax differs from Oracle): SQLite allows a subquery in WHEN, so the whole check fits in the condition. Sara has taken only CSE105, so her registration for CSE215 (which needs CSE105 and CSE107) fails; Rafi's succeeds.

DB QB · 24-25 6b · 18 marks  |  BUET QBank · CSE 215 | L-2/T-1 | 2024–25 Q2 · 18 marks

Consider the following relational database schema: employee(employee_name, street, city), works(employee_name, company_name, salary), company(company_name, city), manages(employee_name, manager_name). Write SQL statements for the following scenarios:

(i) Give a 20% salary rise to employees who are manager.
(ii) Delete all tuples in the works relation for employees of the company "Sonali Bank".
Note that works.employee_name is a foreign key referencing employee(employee_name), manages.employee_name is a foreign key referencing employee(employee_name), manages.manager_name is a foreign key referencing employee(employee_name).
(iii) Design a trigger such that whenever a manager's salary is updated, all employees managed by that manager get a 10% salary increase.

Show worked answer

(i) A manager is anyone who appears as manager_name in manages:

UPDATE works
SET salary = salary * 1.20
WHERE employee_name IN (SELECT manager_name FROM manages);

(ii)

DELETE FROM works
WHERE company_name = 'Sonali Bank';

The foreign keys in the note all point from works and manages to employee. Deleting rows of works removes no employee, so no foreign key is violated and nothing cascades; the employees stay in employee and manages.

(iii) Event: UPDATE OF salary ON works. The action updates other rows of works, so in Oracle a plain row-level trigger would fail with ORA-04091 (works is mutating). A compound trigger avoids it: the row section only records which employees' salaries changed, and the statement section, which runs after the triggering UPDATE is complete, raises their subordinates.

CREATE OR REPLACE TRIGGER RaiseTeam
FOR UPDATE OF salary ON works
COMPOUND TRIGGER
  TYPE name_list IS TABLE OF works.employee_name%TYPE;
  changed name_list := name_list();

  AFTER EACH ROW IS
  BEGIN
    IF :NEW.salary <> :OLD.salary THEN          -- a real change
      changed.EXTEND;
      changed(changed.COUNT) := :NEW.employee_name;
    END IF;
  END AFTER EACH ROW;

  AFTER STATEMENT IS
  BEGIN
    FOR i IN 1 .. changed.COUNT LOOP
      UPDATE works
      SET salary = salary * 1.10
      WHERE employee_name IN (SELECT employee_name FROM manages
                              WHERE manager_name = changed(i));
    END LOOP;
  END AFTER STATEMENT;
END;
/

If the updated employee manages nobody, the inner UPDATE matches no row, so non-managers need no special test. Two consequences worth stating in an answer: (1) the UPDATE inside AFTER STATEMENT fires RaiseTeam again, so if a subordinate is also a manager, their team gets 10% too, cascading down the hierarchy (it stops at employees who manage nobody; a cycle in manages would hit Oracle's 32-level limit). (2) Once this trigger exists, statement (i) also gives every employee managed by a manager a 10% raise. If only direct subordinates should be raised, add a package variable that switches the trigger off while it runs its own UPDATE.

A student who writes the "obvious" version, AFTER UPDATE OF salary ON works FOR EACH ROW with the UPDATE in the body, gets ORA-04091 the first time it fires.

SQLite version (syntax differs from Oracle) to test the effect. SQLite has no mutating-table rule, so a row trigger can do it directly; its recursive triggers are off by default, so here the raise goes one level down only.

DB QB · 17-18 8a · 10 marks  |  BUET QBank · CSE 215 | L-2/T-2 | 2017–18 · 10 marks

Consider the schema MovieExec(name, address, cert#, netWorth). Suppose that we want to prevent the average net worth of movie executives from dropping below 50,000$. This constraint could be violated by insertion, update and deletion to the netWorth column. Write a trigger that checks this constraint before each update to the netWorth column and if the constraint is violated then sets the value of networth equal to the minimum amount required to satisfy the constraint.

Show worked answer

The arithmetic. With n executives and current total S, updating one executive from vold to vnew makes the total S − vold + vnew. The average stays ≥ 50000 iff that total ≥ 50000·n, so the smallest acceptable new value is vmin = 50000·n − (S − vold). If vnew < vmin, store vmin instead.

Example. Four executives worth 60000, 70000, 40000, 50000: S = 220000, average 55000. Lowering the second from 70000 to 30000 would give S = 180000, average 45000. vmin = 200000 − 150000 = 50000, so 50000 is stored and the average is exactly 50000.

Oracle. "Before each update … set the value" means a BEFORE row trigger that assigns :NEW.netWorth. But it needs SUM and COUNT of MovieExec, which a row trigger on MovieExec may not query (ORA-04091). A compound trigger reads them once in BEFORE STATEMENT and keeps a running total, which also handles an UPDATE that changes several executives at once:

CREATE OR REPLACE TRIGGER KeepAvgNetWorth
FOR UPDATE OF netWorth ON MovieExec
COMPOUND TRIGGER
  v_sum NUMBER;
  v_cnt NUMBER;

  BEFORE STATEMENT IS
  BEGIN
    SELECT NVL(SUM(netWorth), 0), COUNT(*) INTO v_sum, v_cnt FROM MovieExec;
  END BEFORE STATEMENT;

  BEFORE EACH ROW IS
  BEGIN
    v_sum := v_sum - :OLD.netWorth + :NEW.netWorth;      -- total if this row changes
    IF v_sum < 50000 * v_cnt THEN
      :NEW.netWorth := :NEW.netWorth + (50000 * v_cnt - v_sum);   -- = v_min
      v_sum := 50000 * v_cnt;
    END IF;
  END BEFORE EACH ROW;
END;
/

Adding (50000·n − total) to :NEW.netWorth is the same as setting it to vmin. The question only asks for the update case; deletions and insertions can lower the average too and would need their own triggers (for those, "set the value" makes no sense, so they would reject with RAISE_APPLICATION_ERROR). The textbook's version of this rule (§7.5.2, Fig. 7.6) is a statement-level trigger that undoes the whole update using OLD TABLE / NEW TABLE, which is standard SQL but not Oracle syntax.

Note: the bank's answer uses MySQL syntax and itself warns that it would hit the mutating-table error in Oracle; the compound trigger above is the Oracle solution.

BUET QBank · CSE 303 | L-3/T-1 | 2013–14 · 10 marks (similar: 2014–15)

What is a Materialized View? Discuss four instances when a trigger can be applied. (2014–15: What is a Materialized View? Discuss the restrictions on triggers in brief.)

Show worked answer

Materialized view. An ordinary view stores only its query; every use re-runs it. A materialized view stores the query's result as a table on disk. Reads are fast (no joins or aggregation at query time), but the stored result goes stale when the base tables change, so it must be refreshed: completely (recompute) or incrementally (apply only the changes), either immediately when base tables change or periodically/on demand. Oracle syntax:

CREATE MATERIALIZED VIEW dept_salary_mv
  BUILD IMMEDIATE
  REFRESH COMPLETE ON DEMAND
AS SELECT dept_name, SUM(salary) AS total, COUNT(*) AS cnt
   FROM instructor
   GROUP BY dept_name;

(REFRESH FAST ON COMMIT refreshes incrementally at every commit, which needs materialized-view logs on the base table.) Materialized views are used for expensive aggregate queries in reporting and data warehouses, and the optimizer can answer matching queries from them.

Four instances when a trigger can be applied (any four of section 5, each with an example):

  1. Enforcing a complex integrity rule: reject a course registration if a prerequisite has not been taken (the 23-24 question above), which no CHECK or foreign key can express.
  2. Maintaining derived data: keep dept_total(dept_name, total) correct with AFTER INSERT/UPDATE/DELETE triggers on instructor, i.e. a materialized view maintained by hand.
  3. Auditing: an AFTER UPDATE trigger writes (who, when, :OLD.salary, :NEW.salary) to a log table.
  4. Propagating changes: when a PC is deleted, delete its Product row (slide 52); or make a join view updatable with an INSTEAD OF trigger.

Restrictions on triggers (2014–15 variant), in brief: no COMMIT/ROLLBACK/SAVEPOINT inside a trigger; a row-level trigger cannot query or modify its own (mutating) table; WHEN is allowed only in row-level triggers and cannot contain subqueries; :NEW/:OLD exist only in row-level triggers and :NEW can be changed only in BEFORE row triggers; INSTEAD OF triggers only on views; at most 32 cascading trigger levels; body at most 32 KB; no DDL statements directly in a DML trigger.

Summary: Statement-level triggers fire once per statement and can read the table; row-level triggers cannot read or change their own table (mutating table, ORA-04091), so rules that need aggregates over the same table use a statement-level or compound trigger. INSTEAD OF triggers make views updatable. Triggers cascade; guard against recursion. No COMMIT in triggers. Use triggers for complex rules, derived data, auditing and propagation; use constraints when they suffice.
