Tables, Schemas and Domains

The vocabulary of relational data: table, attribute, tuple, schema, instance, domain. Then the first DDL statement, CREATE TABLE, compared with a C struct, and the three kinds of relations SQL knows about.

1. The parts of a table (slide 10)

Slide 10 labels the parts of the Product table. The same labels appear in the figure below, together with the formal name of each part.

Table (relation)
A named two-dimensional structure of rows and columns. The relational model, proposed by E. F. Codd at IBM in 1970, calls it a relation; SQL calls it a table. Slide 11: "a relation is a table".
Attribute (column)
A named column of a table, such as Price. Every value in that column describes the same property of the rows.
Tuple (row, record)
One row of a table: one value for each attribute. Slide 12's example: (SingleTouch, 149.99, Photography, Canon).

2. Schemas and databases (slide 11)

Relation schema
The table's name followed by its list of attributes: Product(PName, Price, Category, Manufacturer). A full schema also gives each attribute's type and the keys. (The slide spells it "Manfacturer"; that is a typo.)
Database
A collection of relations (tables).
Database schema
The set of the relation schemas of all tables in the database.
Relation instance
The set of tuples a table holds at one moment. The schema changes rarely (by DDL); the instance changes all the time (by INSERT, UPDATE, DELETE). The textbook (§2.2.6) makes the same distinction.

Think of the schema as the empty form with labelled boxes and the instance as the pile of filled-in forms. CREATE TABLE prints the empty form; INSERT adds filled-in copies.

3. A table is a set of tuples (slide 12)

Slide 12 says a table is "like a list, but unordered: no first(), no next(), no last()". In the relational model a relation is a set: its tuples have no position. Two consequences follow.

  • There is no "third row". A query cannot ask for "the row after Gizmo". Rows are found only by their values (for example WHERE pname = 'Gizmo').
  • Output order is not guaranteed. SELECT * FROM Product may return the rows in any order, and the order may change after an update or on another day. If the order matters, ask for it with ORDER BY (Lec 04, Chapter 6).

One refinement: a mathematical set has no duplicates, but an SQL table may contain two identical rows unless a key forbids it. SQL tables are therefore bags (multisets). This matters for DISTINCT in Lecture 4.

4. Domains: every attribute has a type (slide 13)

Domain
The set of values an attribute may take, given by its data type. The domain of PName is strings; the domain of Price is real numbers.
Atomic value
A value of an elementary type (an integer, a string, a date) that the database does not split into parts. The relational model requires every attribute value to be atomic: a cell cannot hold a list, a set or a nested table. (This rule is the first normal form, studied in Sukarna sir's normalization lectures.)

For example, a student with two phone numbers cannot have phone = {01711…, 01811…} in one cell. The design must use two rows, or a separate Phone table.

5. CREATE TABLE compared with a C struct (slide 14)

The CREATE TABLE statement declares a relation schema: the table name, then each attribute with its type. Slide 14 puts it next to a C structure with the same fields:

CREATE TABLE Student (
    name     CHAR(50),
    id       NUMBER(10),
    gender   CHAR(1),
    address  CHAR(100),
    gpa      FLOAT
);
struct Student {
    char  name[50];
    int   id;
    char  gender[1];
    char  address[100];
    float gpa;
};

The slide's point is the word order: in SQL the attribute name comes first and the type second; in C the type comes first. Other differences worth knowing:

  • SQL separates attributes with commas and has no comma after the last one; C ends every field with a semicolon. The SQL statement ends with );.
  • A C struct only describes the layout of one record in memory. A CREATE TABLE creates a persistent, named table in the database that can hold any number of rows, survives program exits, and can be shared by many users.
  • NUMBER(10) is a decimal number of up to 10 digits (Chapter 3), not a fixed 32-bit binary integer like C's int.
  • In C, char gender[1] leaves no room for the terminating '\0', so it cannot hold a C string; SQL's CHAR(1) holds exactly one character.

Run the slide's statement. The table is created with no rows; its schema exists, its instance is empty.

In Oracle's SQL*Plus or SQL Developer you can see a table's schema with DESCRIBE Student. That is a client command, so the playground does not support it; use Show tables instead.

6. Three kinds of relations in SQL (textbook §2.3.1)

The textbook separates three kinds of relations, and an exam question asks for them:

  1. Stored relations (tables). Declared with CREATE TABLE, stored on disk, and changed by INSERT, UPDATE and DELETE. Everything in Lectures 3–5 is about these.
  2. Views. Relations defined by a query (CREATE VIEW … AS SELECT …). A view is not stored; its rows are computed from the stored tables when the view is used. See Lec 05 Chapter 5.
  3. Temporary tables. Intermediate relations that the SQL processor builds while it executes a query (for example, the rows that survive WHERE before SELECT is applied, or a sorted run in an external sort). They are thrown away afterwards and are never declared by the user.

What are the three types of relations in SQL?

Show worked answer

SQL distinguishes three kinds of relations (Garcia-Molina, Ullman and Widom, §2.3.1):

  1. Stored relations, called tables. They exist in the database, are declared with CREATE TABLE, are kept on disk, and can be both queried and modified by changing their tuples (INSERT, UPDATE, DELETE). Example: CREATE TABLE Movie (title VARCHAR2(50), year INTEGER, PRIMARY KEY (title, year));
  2. Views. Relations defined by a computation (a query). They are not stored; they are constructed, in whole or in part, when needed. Example: CREATE VIEW OldMovie AS SELECT title, year FROM Movie WHERE year < 1950;
  3. Temporary tables. Relations constructed by the SQL language processor while it executes queries and data modifications (for example, the intermediate result after the WHERE clause). They are thrown away when the statement finishes, are not stored, and are never declared by the user.

Note: the question bank calls the third kind "temporary/derived relations" and includes CTEs and CREATE TEMPORARY TABLE. Oracle does have declared global temporary tables (CREATE GLOBAL TEMPORARY TABLE), but in the textbook's classification those are still declared tables; the textbook's "temporary tables" are the undeclared intermediate results. Give the textbook's three: tables, views, temporary tables.

Summary: a relation (table) has a name, attributes (columns) and tuples (rows). Its schema is the name plus attributes; the database schema is the set of all relation schemas; the instance is the current set of tuples. Tables are unordered (use ORDER BY for order) and may hold duplicate rows unless a key forbids it. Every attribute has a domain of atomic values. CREATE TABLE lists "name type" pairs separated by commas, the reverse of C's "type name". SQL has three kinds of relations: stored tables, views, and temporary tables.
