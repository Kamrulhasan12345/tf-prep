The Document Model and Duplication

The non-relational answer to the same CMS problem: keep each student and their enrollments together in one document. This chapter explains documents and embedding (slide 9), the duplication it causes (slide 10), how the same question is answered in each model (slide 14), and what happens when course information changes (slide 15). It ends with the exam question on redundancy and incompleteness.

1. Keep related data together (slide 9)

Document
A self-contained record stored as nested fields, usually in JSON (JavaScript Object Notation): { "field": value, … }. A value may be a number, a string, another document, or an array (a list in square brackets).
Collection
A group of documents of the same kind, the document-model counterpart of a table. Documents in one collection need not have exactly the same fields.
Embedding
Storing related data inside a document instead of in a separate table: the enrollments array inside the student document.
Document database
A DBMS built around documents, such as MongoDB (slide 11).

Slide 9 stores Jalil as one document. The top-level fields hold the student information; the enrollments field holds an array, and each array element is a small document describing one enrollment, including the course's name and credits:

{
  "sid": 2405190,
  "name": "Jalil",
  "email": "jalil@university.edu",
  "enrollments": [
    { "cid": 215, "cname": "DB",  "credits": 3, "term": "Jan26" },
    { "cid": 205, "cname": "DLD", "credits": 3, "term": "Jan26" },
    { "cid": 101, "cname": "SPL", "credits": 3, "term": "Jan25" }
  ]
}

Compare with the relational version: Jalil's facts were spread over one Students row, three Enrolled rows and three Courses rows. Here the student information and the enrollment list belong to the same document. The application can read Jalil's courses directly from the enrollments array, with no join. This is not a legal relational tuple (a relational cell must hold one atomic value, never a list), which is exactly why it needs a different model.

2. Embedding is convenient, but may duplicate data (slide 10)

The slide lists both sides:

ConveniencePossible duplication
One document contains most of the needed information.“DB” may appear in many student documents.
Fewer joins are needed.Its name and credits may be repeated.
Reading one student's courses is straightforward.Updating course information may require several documents.

Write out all three students and the duplication is visible: “DB, 3 credits” is stored in Jalil's and Karim's documents; “SPL, 3 credits” in Jalil's and Faria's.

The slide's summary: relational model: store the course once and reference it. Document model: course details may be embedded where they are used. Duplication in a document database is often intentional: it buys fast reads of the most common screen. The price is paid on updates (Section 4).

Document databases also allow referencing: store only "cid": 215 in the enrollment and keep course details in a separate courses collection. That removes the duplication but brings back the lookup, which is a join done by the application or by the database's lookup operator. Choosing between embedding and referencing is the main design decision in a document database.

3. Same question, different access paths (slide 14)

Question: which courses did Jalil take in Jan26? Both models return DB and DLD, but they reach the answer differently. Step through them side by side.

In a document database the query might look like this (MongoDB shell syntax, for illustration only; it is not part of the course's Oracle SQL):

db.students.find(
  { sid: 2405190 },
  { name: 1,
    enrollments: { $filter: { input: "$enrollments",
                              cond: { $eq: ["$$this.term", "Jan26"] } } } }
)

The relational version is the slide-8 join from Chapter 2. The document path touches one document; the relational path touches three tables. That is why document stores are attractive for “show me everything about this one thing” screens.

4. What happens when course information changes? (slide 15)

Suppose the course name DB is changed to Database Systems.

  • Relational model: update the row for cid = 215. The course is stored once, and all enrollment links still point to the same course. One main update. 
    UPDATE Courses SET cname = 'Database Systems' WHERE cid = 215;
  • Embedded document model: the old name may appear in many student documents. Each copied occurrence may need updating, and the application must prevent inconsistent copies. Potentially many updates.

This is the same redundancy-and-inconsistency problem as the file-processing system in Lec 01, now inside a database. The relational model avoids it by design; a document design accepts it in exchange for faster reads and must handle it in application code (or by choosing references instead of copies for data that changes).

DB QB · Jan 20 10 · 10 marks

How redundancy and incompleteness can lead to a bad database design? Explain with appropriate example(s).

Show worked answer

A database design should store every fact exactly once (avoid redundancy) and should be able to record every fact the organization needs (avoid incompleteness). Silberschatz, Database System Concepts (§7.1) names these as the two major pitfalls of a bad design.

Redundancy means the same fact is stored in several places. Example: a single relation that records each enrollment together with the course's details,

sidnamecidcnamecreditsterm
2405190Jalil215DB3Jan26
2405191Karim215DB3Jan26
2405190Jalil205DLD3Jan26

“Course 215 is named DB and has 3 credits” is stored once per enrolled student, and Jalil's name once per course he takes. This leads to:

  • Wasted space: the same values repeated in many rows.
  • Update anomaly / inconsistency: renaming DB to “Database Systems” must change every row with cid 215; if one row is missed, the database states two different names for the same course.
  • Deletion anomaly: if Karim drops DB and Jalil drops DB, deleting their rows also deletes the only record that course 215 exists and has 3 credits.

Incompleteness means some facts cannot be represented at all. In the design above, course information exists only inside enrollment rows, so a new course that no one has enrolled in yet cannot be stored, unless we insert a row with NULL sid and term, which is awkward and breaks the key (sid, cid, term). Likewise a newly admitted student who has not registered for any course cannot be stored. The same happens in the embedded document design of slide 9: course details exist only inside student documents, so a course with no students has nowhere to live.

Good design splits the data into Students(sid, name, email), Courses(cid, cname, credits) and Enrolled(sid, cid, term), slides 5–6. Each fact is stored once (no redundancy), a course or student can exist with no enrollments (no incompleteness), and a join reassembles the combined view when needed. Normalization (Sukarna sir's Lec 01) gives the formal method for reaching such designs.

Summary: a document database stores each item as a nested JSON document; embedding puts related data (Jalil's enrollments, with course names and credits) inside it. Reading one student's courses then needs no join, but course details are duplicated across documents, so renaming a course means updating every copy, and a missed copy makes the data inconsistent. The relational model stores each course once and references it, so the rename is one update; the cost is a join on reads.
