Exam Topics Beyond the Slides: DBMS Architecture and Abstraction

Lectures 01–02 explain why a DBMS exists and how data is modeled, but past exams also ask about how a DBMS is organized: levels of abstraction and data independence, schema versus instance, DDL versus DML, the data dictionary, the internal components of a DBMS, 2-tier and 3-tier architectures, and derived attributes. This chapter teaches each topic from the standard textbook account (Silberschatz, Database System Concepts, Ch. 1) and answers every such question in the banks.

1. Data abstraction: three levels

A DBMS stores data in complicated structures (blocks, slotted pages, B+ trees, hash files) so that it can be fast. Most users should never see those structures. The DBMS therefore hides them behind simpler descriptions of the same data. This hiding is called data abstraction, and the standard design (the ANSI/SPARC three-schema architecture) has three levels:

Physical level (internal schema)
The lowest level: how the data is actually stored. Files, record layouts, block sizes, indexes, compression, which disk. Example: “Students is a heap file in tablespace USERS with a B+ tree index on sid.” See Lec 14 and Lec 15.
Logical level (conceptual schema)
The middle level: what data is stored and how it is related, for the whole database. Example: Students(sid, name, email, dob), Courses(cid, cname, credits), Enrolled(sid, cid, term), with keys and constraints. Database designers and administrators work here, with DDL.
View level (external schemas)
The highest level: each group of users sees only the part of the database it needs, possibly reshaped. Example: an advisor's view shows name and email of students in one department; the accounts office's view shows sid and fee balance. There are many views, one logical schema and one physical schema.
Mapping
The DBMS's record of how one level is built from the level below: the external/logical mapping (each view's definition) and the logical/physical mapping (which file and structure holds each table).

Why use data abstraction? (1) Simplicity: users and programmers work with tables and views instead of bytes and pointers. (2) Security: a view shows a user only the rows and columns they may see. (3) Data independence: a change at one level can be absorbed by a mapping instead of rippling up to every program (next section). (4) Efficiency without effort: the DBMS can choose and change efficient storage behind the scenes.

2. Data independence

Physical data independence
The ability to change the physical schema (add an index, reorganize a file, move a table to faster disks) without changing the logical schema, and therefore without changing application programs. Only the logical/physical mapping changes.
Logical data independence
The ability to change the logical schema (add a column, add a table, split a table) without changing the external views, and therefore without changing programs that use those views. Only the external/logical mapping changes. It is harder to achieve, because programs depend directly on the logical structure.

Lec 01 slide 16 (“ALTER TABLE … controlled”) and Lec 14–15 (indexes and file organizations that can be changed under running applications) are both instances of data independence. The file-processing system of Lec 01 Chapter 2 had none: every program depended on the physical file format.

3. Schema versus instance, DDL versus DML

Schema (intension)
The design of the database: relation names, attributes, domains, keys, constraints. Changes rarely. Stored as metadata in the data dictionary.
Instance (extension)
The data actually in the database at one moment. Changes with every insert, update and delete.
DDL (data-definition language)
The part of SQL that defines and changes the schema: CREATE, ALTER, DROP, TRUNCATE, RENAME, and in Oracle also GRANT/REVOKE. Executing DDL updates the data dictionary.
DML (data-manipulation language)
The part of SQL that reads and changes the instance: SELECT, INSERT, UPDATE, DELETE, MERGE. DML runs inside transactions and can be rolled back.

An analogy: the schema is the blueprint of a house; the instance is the furniture and people inside it today. Run the DDL and DML below; afterwards the second query reads Oracle's data dictionary view of the table's columns (that view is Oracle-only, so in the playground it is replaced by SQLite's equivalent, pragma_table_info).

In Oracle every DDL statement performs an implicit COMMIT before and after it runs, so DDL cannot be rolled back and it also commits any pending DML. (PostgreSQL, by contrast, can roll back most DDL inside a transaction.)

4. The data dictionary

A DBMS stores data about the data, called metadata, in the data dictionary (or system catalog). It is itself a set of relations, which the DBMS reads before every statement: does this table exist, what are its columns and types, is this user allowed, which indexes can be used, how many rows are there. Silberschatz's dictionary schema is

Relation_metadata (relation_name, number_of_attributes, storage_organization, location)
Attribute_metadata(relation_name, attribute_name, domain_type, position, length)
User_metadata     (user_name, encrypted_password, group)
Index_metadata    (relation_name, index_name, index_type, index_attributes)
View_metadata     (view_name, definition)

plus integrity constraints and statistics (number of tuples, distinct values) for the optimizer. In Oracle the dictionary is read through views such as USER_TABLES, USER_TAB_COLUMNS, USER_CONSTRAINTS, USER_INDEXES and USER_VIEWS:

SELECT column_name, data_type, data_length, nullable
FROM   user_tab_columns
WHERE  table_name = 'STUDENTS'
ORDER  BY column_id;

Lec 14 (the data dictionary chapter) shows how the dictionary itself is stored.

5. Components of a DBMS

Inside, a DBMS has two main modules on top of the stored data (Silberschatz §1.8):

  • The query processor turns SQL into actions: the DDL interpreter records definitions in the data dictionary; the DML compiler translates a query into an evaluation plan, and its query optimizer picks the cheapest of the equivalent plans; the query evaluation engine executes the plan.
  • The storage manager is the interface between the stored data and the query processor: the authorization and integrity manager checks permissions and constraints; the transaction manager (concurrency-control manager plus recovery manager) keeps the database consistent despite concurrency and crashes; the file manager allocates disk space and the structures that represent data on disk; the buffer manager fetches blocks from disk into main memory and decides which to keep.
  • On disk: the data files, the data dictionary, the indices, and statistical data about the stored data.

The people around it: naive users (students, bank tellers) use application interfaces; application programmers write those programs; sophisticated users (analysts) write queries in query tools; the database administrator (DBA) defines schemas, storage, authorization and backups using administration tools.

6. Two-tier and three-tier architectures

Lec 01 slide 11 showed an application in front of the DBMS. Where that application runs gives two standard architectures:

Two-tier architecture (client–server)
The application runs on the user's machine (the client) and talks directly to the database server, sending SQL through an API such as ODBC or JDBC. The client holds both the user interface and the business logic (a “fat client”).
Three-tier architecture
The client is only a user interface (a browser or thin app). It talks (over HTTP) to an application server, which holds the business logic and is the only part that sends SQL to the database server. BIIS, Pathao and every web application work this way.

7. Derived attributes

Stored attribute
An attribute whose value is kept in the database, such as a student's date of birth.
Derived attribute
An attribute whose value is computed from other stored data whenever it is needed, such as age (from date of birth and today's date) or a student's total credits (from Enrolled and Courses). In an ER diagram it is drawn with a dashed ellipse.

Storing age would make it wrong one year later unless something updates every row on every birthday. Deriving it means it is computed at query time from the current date, so it is always current. In Oracle a view can expose it as if it were a column; the playground fixes the date with a value so the result is reproducible, and the comment shows the live version.

DB QB · 24-25 6c · 5 marks  |  BUET QBank · CSE 215 | L-2/T-1 | 2024–25 · 5 marks

Draw the diagram of 2-tier and 3-tier database architectures.

Show worked answer

2-tier: the client machine runs the user interface and the application (business logic), and connects directly to the database server through a standard API (ODBC/JDBC), sending SQL. Simple and fast for a small number of users, but each client needs its own connection and database credentials, and changing the logic means updating every client.

3-tier: the client runs only the presentation layer (browser or thin app) and sends requests (HTTP) to an application server, which holds the business logic, issues SQL to the database server and returns results. The database is not exposed to clients, connections are pooled, the middle tier can be replicated for scale, and logic changes are made in one place; the cost is an extra layer to build and run.

The bank's diagrams are correct; its claim that 2-tier is “difficult to scale beyond 100 users” is a rule of thumb, not a fixed limit.

DB QB · 24-25 7a · 8 marks  |  BUET QBank · CSE 215 | L-2/T-1 | 2024–25 · 8 marks

Why do we use data abstraction? Describe different data abstraction levels.

Show worked answer

Why. A DBMS uses complex storage structures for efficiency. Data abstraction hides that complexity behind simpler descriptions, so that (1) users and programmers work with tables and views, not files and pointers; (2) each user group sees only the data it needs (security and simplicity through views); (3) changes at a lower level do not force changes at higher levels (physical and logical data independence); (4) the DBMS can choose and change efficient storage freely.

Levels (three-schema architecture, Figure 1):

  1. Physical (internal) level: how data is stored: files, record formats, indexes, blocks. Example: Students stored as a heap file with a B+ tree index on sid.
  2. Logical (conceptual) level: what data is stored and the relationships among it, for the whole database: relations, attributes, keys, constraints. Example: Students(sid, name, email, dob), Enrolled(sid, cid, term) with sid referencing Students.
  3. View (external) level: the part of the database a particular user group sees. Example: an advisor's view (sid, name, email) of CSE students only; the accounts view (sid, fee_due). Many views exist over one logical schema.

The DBMS keeps two mappings, external/logical and logical/physical. Changing the physical level only changes the lower mapping (physical data independence); adding to the logical level only changes the upper mapping (logical data independence).

DB QB · 23-24 2b · 10 marks  |  BUET QBank · CSE 215 | L-2/T-1 | 2023–24 · 10 marks; CSE 303 | L-3/T-1 | 2014–15 · 7 marks

Why does it yield current values when derived attributes are not stored in database? Discuss with an example.

Show worked answer

A derived attribute is computed from stored attributes (and possibly the current date) each time it is requested, instead of being stored. Because the computation runs at query time, it always uses the current values of its inputs, so the result is current. A stored copy, in contrast, is correct only at the moment it was written; when its inputs change (another birthday passes, a new enrollment is added), the stored value becomes stale unless every change also updates it. Not storing it also removes redundancy: the fact exists only once (date of birth), so it cannot contradict itself.

Example. Student(sid, name, dob) with derived attribute age. If age = 20 were stored for a student born 15 May 2002 when inserted on 1 June 2022, the database would still say 20 on 29 October 2026, when the student is 24. Deriving it:

CREATE OR REPLACE VIEW student_profile AS
SELECT sid, name, dob,
       FLOOR(MONTHS_BETWEEN(SYSDATE, dob) / 12) AS age
FROM   student;

Every query on student_profile recomputes age from SYSDATE: on 29 Oct 2026 it gives FLOOR(293.45 / 12) = FLOOR(24.45) = 24, and on 15 May 2027 it gives 25 with no update. Another example: total credits of a student, derived as SUM(credits) over Enrolled ⋈ Courses, automatically reflects a newly added enrollment.

The trade-off: deriving costs computation on every read, so a value that is expensive to compute and read very often is sometimes stored deliberately (and kept up to date by a trigger). In an ER diagram a derived attribute is drawn as a dashed ellipse.

Note: the bank's SQL uses DATEDIFF(DAY, …), which is SQL Server syntax; in Oracle use MONTHS_BETWEEN as above.

BUET QBank · CSE 303 | L-3/T-1 | 2011–12 · 15 marks

Show the major components and their interactions in a DBMS. Briefly explain the functionalities of major components.

Show worked answer

Draw Figure 2. Then explain:

Query processor. DDL interpreter: interprets DDL statements and records the definitions (schemas, constraints, authorizations) in the data dictionary. DML compiler: translates a DML query into an evaluation plan of low-level operations; its query optimizer chooses the lowest-cost plan among equivalent ones, using statistics and available indices. Query evaluation engine: executes the plan, requesting data from the storage manager.

Storage manager. Authorization and integrity manager: checks that the user has the needed privileges and that changes satisfy integrity constraints. Transaction manager: ensures atomicity and durability despite failures (recovery manager) and correct interleaving of concurrent transactions (concurrency-control manager). File manager: allocates disk space and manages the data structures that represent data on disk. Buffer manager: fetches blocks from disk into main memory, decides which blocks to cache and which to write back.

Disk storage. Data files (the tables), data dictionary (metadata), indices (fast access by key), statistical data (sizes and value distributions, used by the optimizer).

Interactions. A user's query arrives through an application or query tool, is compiled and optimized by the query processor (consulting the dictionary), and executed by the evaluation engine, which calls the storage manager; the storage manager checks authorization, runs the work as a transaction, and reads/writes blocks through the buffer and file managers. DDL from the DBA goes through the DDL interpreter into the dictionary.

BUET QBank · CSE 303 | L-3/T-1 | 2010–11 · 7 marks

Discuss ‘Schema versus Data’ and ‘DDL versus DML’.

Show worked answer

Schema versus data. The schema is the description of the database: relation names, attributes and their domains, keys and constraints, e.g. Employee(emp_id NUMBER PRIMARY KEY, name VARCHAR2(50), salary NUMBER(10,2)). It is designed once, changes rarely, and is stored as metadata in the data dictionary. The data (the instance) is the set of tuples stored at a given moment, e.g. (101, Alice, 75000), (102, Bob, 68000); it changes with every insert, update and delete. Schema = intension, instance = extension. Every instance must satisfy the schema's constraints.

DDL versus DML. DDL defines and changes the schema: CREATE TABLE, ALTER TABLE, DROP TABLE, TRUNCATE; it is used mainly by designers and DBAs and its effect is recorded in the data dictionary. DML reads and changes the instance: SELECT, INSERT, UPDATE, DELETE; it is used by applications and users, runs inside transactions, and can be rolled back. In Oracle, DDL statements commit implicitly and cannot be rolled back.

CREATE TABLE employee (emp_id NUMBER PRIMARY KEY, name VARCHAR2(50), salary NUMBER(10,2));  -- DDL
INSERT INTO employee VALUES (101, 'Alice', 75000);                                         -- DML
UPDATE employee SET salary = 80000 WHERE emp_id = 101;                                      -- DML

The bank's answer is correct; its statement that DDL cannot be rolled back holds for Oracle and MySQL, not for PostgreSQL.

BUET QBank · CSE 303 | L-3/T-1 | 2010–11 · 10 marks

Explain the data dictionary schema for DBMS. List the advantages and disadvantages for storing a relational database as follows: (a) Store each relation in one file. (b) Store multiple relations in one file.

Show worked answer

Data dictionary. The DBMS stores metadata as relations of its own (Section 4): relation metadata (name, number of attributes, storage organization, location), attribute metadata (relation, attribute, domain type, position, length), user metadata (name, encrypted password, group), index metadata (relation, index name, type, attributes), view metadata (name, definition), plus integrity constraints and statistics. The query processor reads it to check names, types, permissions and available indexes before running any statement, and the DDL interpreter writes to it.

(a) Each relation in its own file. Advantages: simple to implement (the OS file system does space management); every record in a file has the same format, so fixed-length layouts and free lists are easy; a scan of one relation reads only that relation's blocks; a table can be dropped, copied or backed up as one file. Disadvantages: a large database has many files (OS limits, file-system overhead, small tables waste a partly filled block each); records that are often used together (a department and its instructors) live in different files, so a join needs blocks from several places; the DBMS has less control over placement.

(b) Several relations in one file (multitable clustering, Lec 14). Advantages: related records can be placed in the same block (each department followed by its instructors), so the common join reads fewer blocks; few large files, managed by the DBMS itself, which can control placement and allocation. Disadvantages: a scan of one relation must read blocks that also contain other relations' records (slower, e.g. reading all departments); records of different formats in one file make space management and free space reuse harder; the DBMS must implement its own file organization.

The bank's answer covers the same points correctly.

Summary: data abstraction has three levels: physical (how data is stored), logical (what is stored, for the whole database) and view (what each user group sees), linked by two mappings. Physical data independence means storage changes do not affect the logical schema; logical data independence means logical changes do not affect views. The schema is the stable design; the instance is today's data. DDL changes the schema; DML reads and changes the data. The data dictionary stores metadata as relations. A DBMS consists of a query processor (DDL interpreter, DML compiler and optimizer, evaluation engine) and a storage manager (authorization and integrity, transactions, files, buffers) over data files, dictionary, indices and statistics. Two-tier: clients send SQL directly; three-tier: an application server sits between clients and the database. Derived attributes are computed at query time and so are always current.
