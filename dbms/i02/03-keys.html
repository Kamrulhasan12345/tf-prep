Keys: Identifying and Connecting Rows

Slide 2 says “tables are connected using keys”, and slide 5 says “sid uniquely identifies each student”. This chapter makes those two sentences precise: super keys, candidate keys, primary keys and foreign keys, with a tool to test attribute sets yourself, and the exam questions on key definitions and on whether a primary key should carry meaning.

1. Identifying a row

Every row of Students describes a different student, so we need some attribute (or combination) whose value is different for every row that could ever be stored. Name will not do: two students can both be called Karim. sid will: the university never gives two students the same ID. That is exactly what slide 5's notes say.

Super key
A set of attributes whose values are guaranteed to be different for every two tuples the relation may ever contain. Knowing the values of a super key identifies at most one tuple. {sid}, {sid, name} and {sid, name, email} are super keys of Students.
Candidate key (key)
A minimal super key: a super key from which no attribute can be removed without losing uniqueness. {sid} is a candidate key; {sid, name} is not, because {sid} alone already works. If emails are unique, {email} is a second candidate key.
Primary key
The one candidate key the designer chooses as the main identifier of the table. Its attributes may not be NULL (entity integrity). Students' primary key is sid. In the textbook's notation it is underlined: Students(sid, name, email).
Alternate key
A candidate key that was not chosen as primary key, such as email. Declared with UNIQUE in SQL.
Composite key
A key made of more than one attribute. Enrolled's key is {sid, cid, term}.
Foreign key
A set of attributes in one table whose values must appear as the primary key (or a unique key) of another table. Enrolled.sid is a foreign key referencing Students.sid (slide 6). This rule is referential integrity.

The relationships between these terms: every candidate key is a super key; the primary key is one of the candidate keys; adding any attribute to a super key gives another super key.

2. A key is a rule about every possible instance

A key is part of the schema. It says “no two tuples will ever share this value”, which is a fact about the real world (the university assigns unique IDs), not about today's rows. Looking at one instance can disprove a key (two rows with the same value) but never prove one.

Is {sid, cid} a key of Enrolled?

In slide 6's six rows, no two rows share the same (sid, cid) pair, so the current instance does not contradict it. But a student who fails DB in Jan26 and retakes it in a later term would produce a second row (2405190, 215, …) with the same sid and cid. The rule “a pair may appear only once” is false in the real world, so {sid, cid} is not a key. {sid, cid, term} is: a student enrolls in a course at most once per term. Try both in the tool below.

4. Keys in Oracle SQL

Keys are declared when the table is created, and the DBMS then rejects any change that would break them:

CREATE TABLE Students (
  sid   NUMBER(7) PRIMARY KEY,          -- primary key: unique and NOT NULL
  name  VARCHAR2(30) NOT NULL,
  email VARCHAR2(40) UNIQUE              -- alternate key
);
CREATE TABLE Enrolled (
  sid  NUMBER(7) REFERENCES Students(sid),   -- foreign key
  cid  NUMBER(3) REFERENCES Courses(cid),    -- foreign key
  term VARCHAR2(6),
  PRIMARY KEY (sid, cid, term)               -- composite primary key
);

BUET QBank · CSE 215 | L-2/T-1 | 2024–25 · 9 marks

Define super key, candidate key, and primary key with examples.

Show worked answer

Use STUDENT(Roll_No, Reg_No, Email, Name, Age, Branch), where Roll_No, Reg_No and Email are each unique for every student, while Name, Age and Branch can repeat.

Super key. A set of attributes K of relation R such that no two tuples of any legal instance of R agree on all attributes of K; equivalently, K functionally determines every attribute of R (K → R). Examples: {Roll_No}, {Reg_No, Name}, {Email, Age, Branch}, and the set of all six attributes. Any set containing Roll_No, Reg_No or Email is a super key: there are 26 − 23 = 64 − 8 = 56 super keys (all subsets except the 8 subsets of {Name, Age, Branch}).

Candidate key. A minimal super key: a super key K such that no proper subset of K is a super key. Here the candidate keys are {Roll_No}, {Reg_No} and {Email}. {Reg_No, Name} is a super key but not a candidate key, because its subset {Reg_No} is already a super key. {Name, Age} is not a super key at all: two students can share a name and an age.

Primary key. The candidate key chosen by the designer to identify tuples. It must be unique and must not contain NULL (entity integrity), and there is exactly one per table. Choosing Roll_No: STUDENT(Roll_No, Reg_No, Email, Name, Age, Branch). The remaining candidate keys, {Reg_No} and {Email}, are alternate keys, declared UNIQUE.

Relationship: primary key ⊆ candidate keys ⊆ super keys (Figure 1). In Oracle:

CREATE TABLE student (
  roll_no NUMBER(7)    PRIMARY KEY,
  reg_no  VARCHAR2(12) UNIQUE NOT NULL,
  email   VARCHAR2(40) UNIQUE NOT NULL,
  name    VARCHAR2(30), age NUMBER(3), branch VARCHAR2(10)
);

The bank's answer is correct. One detail in its comparison table: it says a super key “may contain NULLs”; in the textbook definition, keys are about identifying tuples, and SQL only forbids NULL in the primary key (a UNIQUE column in Oracle may hold several NULLs).

BUET QBank · CSE 303 | L-3/T-1 | 2014–15 · 6 marks

Should a primary key have any semantic meaning? Explain your answer.

Show worked answer

Generally no. A primary key's job is to identify a row permanently and to be copied into every foreign key that refers to it. A key with real-world meaning (a natural key: email, phone number, NID, a course code) tends to break that job; a meaningless, system-generated key (a surrogate key: a sequence number) does not.

  1. Meaningful values change. If email is the primary key of Students and a student changes email, the new value must be written into the student row and into every Enrolled, Grade and Payment row that references it. A surrogate value never needs to change.
  2. Formats change. If course codes change from “CSE 215” to “CSE 2105” in a new curriculum, a meaningful key forces a change to every referencing table (and possibly to column sizes).
  3. Meaning can be wrong or missing. A natural value may be unknown when the row is created (a new applicant without an NID yet), but a primary key cannot be NULL. Real-world identifiers are also sometimes reused (phone numbers).
  4. Privacy and size. Keys appear in URLs, logs and many tables; a meaningful key such as an NID spreads personal data, and long strings make indexes and joins slower than a short number.

But keep the natural key as a constraint. Uniqueness of email or NID is still a real rule, so declare it as an alternate key with UNIQUE. In Oracle:

CREATE TABLE customer (
  cust_id NUMBER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,  -- surrogate (Oracle 12c+)
  email   VARCHAR2(60) NOT NULL UNIQUE,                      -- natural key kept unique
  name    VARCHAR2(40)
);

When a meaningful key is fine: when the value is stable, short, always known and assigned by the organization itself, such as BUET's student ID (it never changes for a student). For a relationship table such as Enrolled, the composite of the foreign keys, (sid, cid, term), is the natural and usual primary key.

The bank's answer is correct.

Summary: a super key is any attribute set that identifies a tuple; a candidate key is a minimal super key; the primary key is the chosen candidate key (unique, not NULL); the other candidate keys are alternate keys (UNIQUE). A foreign key refers to another table's key and connects the tables. Keys are rules about every possible instance: one instance can disprove a key but not prove it. Primary keys are best kept free of real-world meaning (surrogate keys), with natural identifiers kept UNIQUE.
