Exam Topics Beyond the Slides: XML, MapReduce, Bags, Objects and Distributed Data

Lecture 02 ends by contrasting relational and non-relational storage. Past exams have pushed further in the same direction: semistructured data (XML and DTDs), large-scale processing (MapReduce), bag semantics, object identity and references, and databases spread over many sites (two-phase commit, semijoins, parallel joins). Each topic is taught briefly here and every related bank question is answered.

1. Bags versus sets

Set
A collection in which each element appears at most once. A relation in the formal relational model is a set of tuples.
Bag (multiset)
A collection in which an element may appear several times; only the count matters, not the order. SQL tables and query results are bags unless DISTINCT, a key, or a set operator removes duplicates.

Write C(x, A) for the number of times x occurs in bag A. The bag operations are defined by counts (the textbook, §5.1):

C(x, A ∪ B) = C(x, A) + C(x, B)
C(x, A ∩ B) = min(C(x, A), C(x, B))
C(x, A − B) = max(0, C(x, A) − C(x, B))

Why do DBMSs use bags? Removing duplicates requires sorting or hashing the whole result, which is expensive, and some queries need duplicates (an average of salaries must count two equal salaries twice). In SQL, UNION ALL is bag union and UNION is set union. Oracle 21c also has INTERSECT ALL and MINUS ALL/EXCEPT ALL for bag intersection and difference; the plain operators are set operations.

2. Object identity and reference types

In the relational model a row is identified only by its values (its key). Object-relational SQL (SQL:1999, supported by Oracle) adds user-defined types, tables whose rows are objects of a type (typed tables), and pointers between them.

Object identifier (OID)
A system-generated, unique, immutable identifier given to each row object of a typed table. It is independent of the row's attribute values: updating every attribute keeps the same OID.
Reference type, REF(T)
A data type whose values are OIDs of objects of type T, that is, typed pointers. SCOPE restricts a reference to objects of one particular table.
Dereferencing
Following a reference to the object it points to: -> in standard SQL, a dot in Oracle, or the DEREF function for the whole object.

3. XML and DTDs

Semistructured data
Data that carries its own structure (tags or field names) instead of following a fixed table schema; elements may be nested, repeated or missing. XML and JSON are the two common formats (the textbook, §11.1).
XML element
A start tag, content, and the matching end tag: <NAME>Tom Hanks</NAME>. Elements nest to form a tree with one root element.
DTD (document type definition)
A grammar that says which elements may appear and what each may contain: <!ELEMENT STAR (NAME, ADDRESS+, MOVIES)> means a STAR contains a NAME, then one or more ADDRESSes, then MOVIES, in that order. * = zero or more, + = one or more, ? = optional, #PCDATA = text.
Valid XML
A document that is well formed (tags properly nested and closed) and also follows its DTD.

4. MapReduce

MapReduce (the textbook, §20.2) is a framework for running a computation over a huge dataset on a cluster of many machines. The programmer writes only two functions; the framework does the rest (splitting the input, running tasks in parallel, moving data between machines, restarting failed tasks).

Map function
Applied to each input element independently, in parallel; outputs a list of key–value pairs. Word count: for each word w in a line, output (w, 1).
Shuffle (group by key)
Done by the framework: all pairs with the same key are collected and sent to the same reduce task. Which reducer gets a key is usually decided by hashing the key.
Reduce function
Applied to each key with the list of all its values; outputs the final result for that key. Word count: (w, [1, 1, 1]) → (w, 3).

5. Distributed and parallel databases

Distributed database
One logical database whose data is stored at several sites (machines) connected by a network. A relation may be fragmented (different rows or columns at different sites) or replicated (copies at several sites).
Distributed transaction
A transaction that reads or writes data at several sites. Its parts at each site must all commit or all abort.
Two-phase commit (2PC)
The standard protocol for that all-or-nothing decision (the textbook, §20.5.2). The coordinator (usually the site where the transaction started) runs phase 1 (voting): it logs <prepare T> and sends prepare T to every participant; each participant either makes its part durable, logs <ready T> and replies ready T, or logs <abort T> (“don't commit”) and replies abort T. In phase 2 (decision), if every reply was ready the coordinator logs <commit T> and sends commit T to all; if any reply was abort (or a site timed out) it logs <abort T> and sends abort T. Participants log the decision, apply it, and send ack T; after all acks the coordinator logs <complete T>.
Semijoin
R ⋉ S: the tuples of R that join with at least one tuple of S. Used to reduce how much data crosses the network before a distributed join (the textbook, §20.4.2).
Parallel join
Splitting a join over several processors: partition both relations on the join attribute with the same hash function, join each pair of partitions on its own processor, and union the results.

Two-phase commit is unrelated to two-phase locking (Sukarna sir's Lec 02); they only share the phrase “two-phase”.

What are bags in DBMS? How are they different from sets? Give examples of union, intersection and minus operation on bags to highlight the differences.

Show worked answer

A bag (multiset) is an unordered collection in which an element may occur more than once. A set allows each element at most once. Relational algebra on paper uses sets; SQL tables and query results are bags, because eliminating duplicates costs a sort or hash of the whole result and because some aggregates need duplicates. In SQL, duplicates are removed only by DISTINCT, keys, or set operators (UNION, INTERSECT, MINUS).

Take A = {a, a, a, b, b, c} and B = {a, a, b, b, b, d}, so C(a,A)=3, C(b,A)=2, C(c,A)=1, C(a,B)=2, C(b,B)=3, C(d,B)=1.

OperationBag ruleBag resultSet result (on {a,b,c} and {a,b,d})
A ∪ BC(x,A) + C(x,B){a×5, b×5, c, d} (12 elements){a, b, c, d}
A ∩ Bmin(C(x,A), C(x,B)){a, a, b, b}{a, b}
A − Bmax(0, C(x,A) − C(x,B)){a, c}{c}

The difference row shows the sharpest contrast: as sets, a is in B so it is removed from A; as bags, A has one more a than B, so one a survives. Laws also differ: for sets, A ∪ A = A, but for bags A ∪ A has every element twice as often. In SQL: UNION ALL = bag union, UNION = set union; Oracle 21c adds INTERSECT ALL and MINUS ALL.

BUET QBank · CSE 303 | L-3/T-1 | 2010–11 · 10 marks

Describe with an example, the object identity and reference types in SQL. How can you process queries using reference type?

Show worked answer

Object identity. In a typed table (a table whose rows are objects of a user-defined type), each row object gets a system-generated object identifier (OID). The OID is unique, never changes, and does not depend on attribute values, unlike a primary key, which is made of values.

Reference types. REF(T) is a type whose values are OIDs of objects of type T; it acts as a typed pointer. A SCOPE clause limits it to the objects of one table. Example (Oracle syntax; the SQL:1999 standard is similar):

CREATE TYPE dept_t AS OBJECT (dept_no NUMBER, dept_name VARCHAR2(50));
/
CREATE TABLE departments OF dept_t (dept_no PRIMARY KEY);   -- typed table: each row has an OID

CREATE TYPE emp_t AS OBJECT (emp_id NUMBER, name VARCHAR2(50), works_for REF dept_t);
/
CREATE TABLE employees OF emp_t (emp_id PRIMARY KEY, SCOPE FOR (works_for) IS departments);

INSERT INTO departments VALUES (dept_t(10, 'Research'));
INSERT INTO employees
  SELECT emp_t(101, 'Alice', REF(d)) FROM departments d WHERE d.dept_no = 10;  -- store the pointer

Querying with references. A reference is followed with a path expression instead of a join. Standard SQL writes e.works_for->dept_name; Oracle writes it with a dot:

SELECT e.name, e.works_for.dept_name FROM employees e;            -- implicit dereference, no join
SELECT DEREF(e.works_for) FROM employees e WHERE e.name = 'Alice';  -- the whole department object
SELECT e.name FROM employees e WHERE e.works_for.dept_name = 'Research';

The equivalent relational query needs JOIN departments d ON e.dept_no = d.dept_no. References make queries shorter and let the DBMS go directly to the referenced row; the cost is that the pointer has no meaning outside the DBMS and dangling references (to deleted objects) are possible.

The bank's answer uses the SQL:1999 syntax (REF IS … SYSTEM GENERATED, ->), which is correct for the standard; in Oracle use the forms above.

From the Document Type Definition (DTD) given below describe the structure of the data in XML. Write a sample XML file using this DTD.

<!DOCTYPE STARS [
  <!ELEMENT STARS (STAR*)>
  <!ELEMENT STAR (NAME, ADDRESS+, MOVIES)>
  <!ELEMENT NAME (#PCDATA)>
  <!ELEMENT ADDRESS (STREET, CITY)>
  <!ELEMENT STREET (#PCDATA)>
  <!ELEMENT CITY (#PCDATA)>
  <!ELEMENT MOVIES (MOVIE*)>
  <!ELEMENT MOVIE (TITLE, YEAR)>
  <!ELEMENT TITLE (#PCDATA)>
  <!ELEMENT YEAR (#PCDATA)>
]>
Show worked answer

Structure. The root element is STARS, which contains zero or more STAR elements (*). Each STAR contains, in this order, exactly one NAME, one or more ADDRESS elements (+), and exactly one MOVIES element. Each ADDRESS contains one STREET followed by one CITY. MOVIES contains zero or more MOVIE elements, and each MOVIE contains one TITLE followed by one YEAR. NAME, STREET, CITY, TITLE and YEAR contain only text (#PCDATA). So the data is a list of movie stars, each with a name, at least one address, and a (possibly empty) list of movies with titles and years.

Sample valid document (one star with two addresses and two movies, one with one address and no movies):

<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE STARS SYSTEM "stars.dtd">
<STARS>
  <STAR>
    <NAME>Carrie Fisher</NAME>
    <ADDRESS><STREET>123 Maple St.</STREET><CITY>Hollywood</CITY></ADDRESS>
    <ADDRESS><STREET>5 Locust Ln.</STREET><CITY>Malibu</CITY></ADDRESS>
    <MOVIES>
      <MOVIE><TITLE>Star Wars</TITLE><YEAR>1977</YEAR></MOVIE>
      <MOVIE><TITLE>Empire Strikes Back</TITLE><YEAR>1980</YEAR></MOVIE>
    </MOVIES>
  </STAR>
  <STAR>
    <NAME>Mark Hamill</NAME>
    <ADDRESS><STREET>456 Oak Rd.</STREET><CITY>Brentwood</CITY></ADDRESS>
    <MOVIES></MOVIES>
  </STAR>
</STARS>

The second star has an empty MOVIES element, which is valid because MOVIE is *; it could not omit MOVIES itself or its ADDRESS, because those are required. (The DTD can also be included inline in the DOCTYPE, as the bank's answer does.)

DB QB · 17-18 8d · 5 marks  |  BUET QBank · CSE 215 | L-2/T-2 | 2017–18 · 5 marks

Briefly describe Map-Reduce framework.

Show worked answer

MapReduce is a programming model and runtime for processing very large datasets in parallel on a cluster of commodity machines. The user writes two functions; the framework handles distribution, parallelism and fault tolerance.

  1. Input split: the input (typically in a distributed file system) is divided into chunks, each given to a map task, preferably on the machine that stores the chunk.
  2. Map: Map(k1, v1) → list of (k2, v2), applied to every input element independently.
  3. Shuffle and sort: the framework groups all intermediate pairs by key and sends each key, with all its values, to one reduce task (chosen by hashing the key).
  4. Reduce: Reduce(k2, list of v2) → list of (k3, v3), combining the values for one key.

Example, word count on the lines “the cat sat”, “the dog sat”, “the cat ran”: map emits (the,1), (cat,1), (sat,1), …; the shuffle produces (the,[1,1,1]), (cat,[1,1]), (sat,[1,1]), (dog,[1]), (ran,[1]); reduce sums each list: the 3, cat 2, sat 2, dog 1, ran 1 (Figure 1).

Fault tolerance: if a machine fails, the master re-runs its map or reduce tasks elsewhere; this works because map and reduce are deterministic functions of their inputs. Typical uses: indexing the web, log analysis, joins and aggregations over huge files.

BUET QBank · CSE 303 | L-3/T-1 | 2015–16 · 20 marks

A distributed database system consists of five sites (S1–S5). A transaction T1 initiated from site S1 reads and writes data items A (fragmented in S2 and S4) and B (fragmented in S2, S3 and S5). Any write operation must be performed to all related sites. T1: READ(A); READ(B); WRITE(A); WRITE(B); COMMIT.
(a) Show all the messages (e.g. <Prepare T1>, etc.) passing between S1 and the related sites (S2, S3, S4, S5) for Phase 1 and Phase 2 to COMMIT the transaction T1 using the two-phase commit protocol.
(b) Show all the message passing for Phase 1 and Phase 2 to ABORT the transaction T1 because of an <Abort T1> message sent from S5 to S1.

Show worked answer

Participants. T1 writes A (at S2, S4) and B (at S2, S3, S5), so it has a component at S2, S3, S4 and S5. S1, where T1 started, is the coordinator.

(a) Commit.

PhaseLog record writtenMessages
1 (voting)S1: <prepare T1>S1 → S2, S3, S4, S5: <prepare T1> (4 messages)
each of S2–S5: flushes T1's log records, then <ready T1>S2 → S1, S3 → S1, S4 → S1, S5 → S1: <ready T1> (4 messages)
2 (decision)S1: <commit T1> (all four voted ready)S1 → S2, S3, S4, S5: <commit T1> (4 messages)
each of S2–S5: <commit T1>, commits locally; then S1: <complete T1>S2, S3, S4, S5 → S1: <ack T1> (4 messages)

Total: 16 messages.

(b) Abort because S5 votes abort.

PhaseLog record writtenMessages
1 (voting)S1: <prepare T1>S1 → S2, S3, S4, S5: <prepare T1>
S2, S3, S4: <ready T1>; S5: <abort T1> (“don't commit”) and aborts its part at onceS2, S3, S4 → S1: <ready T1>; S5 → S1: <abort T1>
2 (decision)S1: <abort T1> (one abort vote is enough)S1 → S2, S3, S4 (and, by the textbook protocol, also S5): <abort T1>
S2, S3, S4: <abort T1>, undo their parts; S1: <complete T1> after acksS2, S3, S4 (and S5 if it was sent the decision) → S1: <ack T1>

The coordinator may send <abort T1> as soon as S5's abort arrives, without waiting for the other votes. Sending the decision to S5 is harmless; S5 already knows the outcome, so sending it only to the sites that voted ready (as the bank's answer does) is also accepted.

BUET QBank · CSE 303 | L-3/T-1 | 2010–11 · 10 marks

Given relations R1(A, B, C, D) and R2(C, D, E) stored in sites S1 and S2. Describe the join operation of R1 and R2 using the semi-join strategy. Give an example of parallel join.

Show worked answer

The join attributes are C and D. Suppose the result R1 ⋈ R2 is wanted at S2. Shipping all of R1 to S2 wastes bandwidth on R1 tuples that match nothing. The semijoin strategy:

  1. At S2, compute L = πC,D(R2) (only the join columns, duplicates removed).
  2. Ship L to S1.
  3. At S1, compute R1′ = R1 ⋉ L = R1 ⋈ L projected on R1's attributes: exactly the R1 tuples that will join.
  4. Ship R1′ to S2.
  5. At S2, compute R1′ ⋈ R2, which equals R1 ⋈ R2.

It pays off when L is small and few R1 tuples match. Worked example (checked in Python):

Parallel join example. Join Orders(order_id, cust_id, amount) with Customer(cust_id, name) on cust_id using 3 processors P0, P1, P2. Partition both relations with h(cust_id) = cust_id mod 3: customers 12 (→ P0), 10 and 13 (→ P1), 11 (→ P2), and every order goes to the processor of its cust_id. Matching tuples land on the same processor, so each Pi joins its own Ordersi ⋈ Customeri independently and in parallel; the final result is the union of the three local results. With balanced partitions the join takes about one third of the single-processor time.

Summary: bags allow duplicates; bag union adds counts, intersection takes the minimum, difference subtracts with a floor of zero. Object-relational SQL gives typed-table rows immutable OIDs and REF types that are followed with path expressions instead of joins. XML is semistructured, tree-shaped data; a DTD fixes which elements nest where (* zero or more, + one or more). MapReduce runs map (emit key–value pairs), shuffle (group by key) and reduce (combine values per key) across a cluster. Distributed transactions commit with two-phase commit (prepare/vote, then commit or abort, then ack); distributed joins shrink network traffic with semijoins; parallel joins hash-partition both inputs so each processor joins its own partitions.
