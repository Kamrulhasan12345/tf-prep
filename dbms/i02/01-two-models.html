Two Ways to Model Data

Lecture 02 compares the two big families of data models: relational (tables connected by keys) and non-relational (documents, key–value pairs, graphs, wide columns). This chapter defines a data model, states the core idea of each family, and introduces the course-management example that the rest of the lecture models both ways.

1. What is a data model?

Lecture 01 said a DBMS lets users define what is stored. To define anything you need a vocabulary: what shapes can data take, and how are pieces connected? That vocabulary is a data model.

Data model
A notation for describing data, made of three parts (the textbook, §2.1.1): the structure of the data (tables? nested documents? nodes and edges?), the operations allowed on it (queries and modifications), and the constraints it must satisfy (for example “sid is unique”).
Relational model
A data model in which all data is organized into relations, usually shown as tables.
Non-relational model (NoSQL)
Any data model that does not force everything into fixed tables: document, key–value, graph and wide-column models. “NoSQL” is the popular name for databases that use them; it is usually read as “not only SQL”.

2. Relational model: data as tables (slide 2)

A relational model organizes data into relations, usually shown as tables. The slide states four rules:

  • Each table represents one type of entity or relationship. One table for students, one for courses, one for enrollments. A table never mixes students and courses.
  • Each row is one record: one student, one course, or one enrollment.
  • Each column is one attribute: sid, name, email.
  • Tables are connected using keys. An enrollment row stores a student's sid and a course's cid, and those values point to the matching rows in the other tables.

Core idea: split data into structured tables, then connect them. Every fact is stored in exactly one place, in a simple flat shape, and a query reassembles the pieces when they are needed. The relational model was proposed by E. F. Codd in 1970 and is used by Oracle, PostgreSQL, MySQL and SQL Server. Chapter 2 names every part of a table precisely.

3. Non-relational model: data in flexible forms (slide 3)

A non-relational model stores data without forcing everything into fixed tables. The slide's four points:

  • Data may be stored as documents, key–value pairs, graphs, or wide columns. These are the four main families (Chapters 4 and 5).
  • Related information can be kept together. A student's document can contain the student's enrollments inside it, instead of in a separate table.
  • Schema is often more flexible. Two documents in the same collection may have different fields; a new field needs no ALTER TABLE.
  • Joins are less central than in relational databases. Because related data is stored together, the common questions can be answered by reading one item.

Core idea: store data in the shape that matches how the application uses it. If the app's main screen shows one student with all their courses, store exactly that unit together.

4. The running example: a course management system (slide 4)

The rest of the lecture models one problem both ways: storing information for a university CMS such as BIIS.

Entities (things)Relationships (connections)
StudentsWho takes which course
CoursesWho teaches which course
ProfessorsWhat grade a student receives

Recall from Lec 01: an entity is a thing we store facts about; a relationship connects entities. “What grade a student receives” is a fact about the student–course relationship (it belongs to one enrollment), not about the student alone or the course alone. The slides' examples use students, courses and the “takes” relationship (with its term); professors and “teaches” would be modeled the same way.

Same problem, two different modeling styles. The data is identical; what changes is how it is grouped, how connections are stored, and therefore which questions are cheap and which updates are risky. Keep that question in mind through Chapters 2–5.

Summary: a data model fixes the structure, operations and constraints for describing data. The relational model splits data into tables (one per entity or relationship type; rows are records, columns are attributes) and connects them with keys. Non-relational models (document, key–value, graph, wide-column) keep related data together in the shape the application uses, with flexible schemas and fewer joins. Lecture 02 models one course-management system both ways.
