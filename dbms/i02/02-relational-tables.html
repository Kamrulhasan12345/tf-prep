Relational Tables and Joins

2. The vocabulary of a relation

The relational model has precise names for the parts of a table. Exams use them, and so does every later lecture.

Relation
A table. Formally, a set of tuples that all have the same attributes. Students is a relation.
Attribute
A named column of a relation: sid, name, email. Attribute names label the header row.
Tuple
A row of a relation: one record, such as (2405190, Jalil, jalil@university.edu). It has exactly one value for each attribute.
Domain
The set of values an attribute may take, its type. The domain of sid is 7-digit student numbers (in Oracle, NUMBER(7)); the domain of credits is positive numbers such as 1.5 or 3. Values must be atomic: a single value, not a list or a nested record.
Degree (arity)
The number of attributes. Students has degree 3; Enrolled also has degree 3.
Cardinality
The number of tuples currently in the relation. Students has cardinality 3, Courses 4, Enrolled 6. Cardinality changes with every insert and delete; degree changes only when the structure changes.
Relation schema
The relation's name and its list of attributes (with domains): Students(sid, name, email). The schema is the design and changes rarely.
Relation instance
The set of tuples in the relation at one moment. The instance changes all the time; the schema stays.
Database schema
The set of all relation schemas: Students(sid, name, email), Courses(cid, cname, credits), Enrolled(sid, cid, term).

Three properties follow from “a relation is a set of tuples” (the textbook, §2.2.5–2.2.6):

  • Row order does not matter. Listing Faria first gives the same relation.
  • Column order does not matter, as long as each value stays with its attribute name. (Students(name, sid, email) is the same relation.)
  • No two tuples are identical. A set has no duplicates. (SQL tables actually allow duplicate rows unless a key forbids them; the textbook calls these bags.)

3. Connecting the tables (slides 6–7)

Enrollments are a relationship between students and courses, so they get their own table. Each row of Enrolled(sid, cid, term) represents one student–course enrollment:

  • Enrolled.sid refers to Students.sid.
  • Enrolled.cid refers to Courses.cid.

A column that refers to the key of another table is a foreign key. To read an Enrolled row, you follow each value to the row it refers to. Slide 7 does this for the first row (2405190, 215, Jan26). Step through it:

The meaning of the row: Jalil enrolled in DB during Jan26. Notice what the Enrolled row does not store: Jalil's name or email, or the course's name or credits. Those facts live once, in Students and Courses. The Enrolled row stores only the two IDs and the one fact that belongs to the enrollment itself (the term).

Why does Enrolled need the term column?

Look at the full table on slide 6: Jalil (2405190) appears with course 101 in Jan25 and with courses 215 and 205 in Jan26. Without the term, we could not tell when he took each course, and a student who retakes a course in a later term would produce two identical (sid, cid) rows. With the term, (sid, cid, term) identifies one enrollment.

4. Combining tables with a join (slide 8)

Question: which courses did Jalil take in the Jan26 term? No single table answers it: names are in Students, enrollments in Enrolled, course names in Courses. The slide's SQL:

SELECT s.name, c.cname, e.term
FROM Students s
JOIN Enrolled e ON s.sid = e.sid
JOIN Courses c ON e.cid = c.cid
WHERE s.sid = 2405190
  AND e.term = 'Jan26';

Read it clause by clause:

  • FROM Students s starts from Students and gives it the short name (alias) s. In Oracle a table alias is written directly after the table name, without AS.
  • JOIN Enrolled e ON s.sid = e.sid pairs each student row with each enrollment row that has the same sid.
  • JOIN Courses c ON e.cid = c.cid extends each pair with the course row whose cid matches.
  • WHERE … keeps only combinations for student 2405190 in term Jan26.
  • SELECT s.name, c.cname, e.term outputs three columns.

(The slide prints the string as ’Jan26’ with typographic quotes; in real SQL they must be plain apostrophes, 'Jan26'.)

Quick check

Summary: a relation is a table: attributes are its columns, tuples its rows, each attribute has a domain of atomic values, degree counts attributes and cardinality counts tuples. The schema (name and attributes) is stable; the instance (current tuples) changes. Students and Courses are entity tables; Enrolled is a relationship table whose sid and cid are foreign keys referring to them. A join follows these IDs to reassemble facts stored in separate tables, as in the slide-8 query that returns DB and DLD for Jalil in Jan26.
