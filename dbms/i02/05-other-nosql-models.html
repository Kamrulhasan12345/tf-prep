Key–Value, Graph and the Big Comparison

Slide 11 models Jalil's enrollments in three non-relational ways: document, key–value and graph. Slides 12–13 look closely at the graph model, and slide 16 compares relational and non-relational models feature by feature. This chapter draws all four models of the same data side by side and explains when each one fits.

1. The same data in four models (slide 11)

Slide 11's three non-relational versions:

  • Document model (example: MongoDB). Jalil's record contains an array of courses and terms. Chapter 4 covered it.
  • Key–value model (example: Redis). The key student:2405190 maps to Jalil's complete student record.
  • Graph model (example: Neo4j). Jalil is a node, linked by “enrolled in” edges to the course nodes DB and DLD. The relationship is stored as an edge.

2. The key–value model

Key–value store
A database that stores pairs (key, value) and supports essentially three operations: PUT(key, value), GET(key) and DELETE(key). It is a huge, persistent hash table.
Key
A unique string chosen by the application, often with a prefix naming the kind of thing: student:2405190, course:215, session:a91f….
Value
Whatever the application stores under the key: a string, a number, a JSON text, a list. To the database the value is usually opaque: it does not look inside.

Fetching Jalil's complete record is one GET student:2405190, the fastest possible lookup. But because the database cannot see inside values, it cannot answer “which students took DB?” by itself: the application would have to read every student value and search it, or maintain a second key such as course:215:students by hand. Key–value stores are therefore used where access is always by a known key: caches, user sessions, shopping carts, counters.

SET student:2405190 '{"name":"Jalil",
                     "courses":[{"cid":215,"term":"Jan26"},
                                {"cid":205,"term":"Jan26"}]}'
GET student:2405190

3. The graph model (slides 12–13)

A graph model stores data as:

Node
An entity, such as a student or a course. Nodes carry a label (Student, Course).
Edge
A relationship between two nodes, with a direction and a type, such as ENROLLED_IN from Jalil to DB.
Property
Extra information on a node or an edge: sid: 2405190 on Jalil, cid: 215 on DB, term: Jan26 on the enrollment edge.

Slide 12 writes one fact as Jalil —ENROLLED_IN, term = Jan26→ DB. Slide 13 draws Jalil's two Jan26 enrollments:

Notice where the term lives. In the relational model it is a column of Enrolled, the relationship table. In the graph model it is a property of the edge, which is the relationship itself. The two say the same thing: the term belongs to the enrollment, not to the student or the course.

The graph model shines when questions follow chains of relationships. “Which students took a course together with Jalil?” is a two-hop walk: Jalil → his courses → their other students. In SQL this is a self-join of Enrolled; in a graph database it is a short traversal. In Neo4j's query language (Cypher, for illustration only):

MATCH (j:Student {name: 'Jalil'})-[:ENROLLED_IN]->(c:Course),
      (other:Student)-[:ENROLLED_IN]->(c)
WHERE other <> j
RETURN DISTINCT other.name

On slide 6's data this returns Karim (who also took DB) and Faria (who also took SPL, in a different term). Social networks, recommendations, road maps and fraud detection are relationship-heavy in this way.

4. The fourth family: wide-column

Slide 3 and slide 16 also name wide-column stores (example: Cassandra). A wide-column table groups rows by a partition key (for example sid), and each row can have its own, possibly very large, set of columns (for example one column per (term, cid) enrollment). All of one student's data sits together on one machine and in sorted order, so such stores handle huge write volumes spread across many servers. The schema is flexible per row, and joins are not supported; you design one table per query.

5. Relational vs non-relational (slide 16)

FeatureRelational modelNon-relational model
Main structureTables containing rows and columnsDocuments, key–value pairs, graphs, or wide columns
Data organizationStudents, Courses and Enrolled are stored separatelyRelated data may be grouped in one document or graph
RelationshipsForeign keys and joinsEmbedded data, references, or graph edges
SchemaUsually predefined and consistentOften flexible and easier to change
DuplicationUsually minimizedMay be intentional for faster access
Jalil's coursesJoin Students, Enrolled and CoursesRead an embedded array or traverse graph edges
Suitable forStructured data and strong consistencyFlexible data and relationship-heavy applications
ExamplesPostgreSQL, MySQL, Oracle, SQL ServerMongoDB, Redis, Neo4j, Cassandra

Relational: tables, keys and joins. Non-relational: storage shaped around access needs.

Which model would you choose for BIIS?

BIIS stores structured data (students, courses, registrations, grades, fees) whose correctness matters: a grade or a payment must never be lost or duplicated, many offices ask many different questions (results by course, by department, by term), and course details change. That is the relational model's home ground: each fact stored once, any question answerable with a join, strong transactions. A non-relational store could still help at the edges, for example a key–value cache of each student's dashboard page, or a document store for free-form application forms whose fields vary by program. Many real systems use a relational database as the source of truth and non-relational stores for specific access patterns.

Summary: the same enrollments can be stored as rows of IDs (relational), an embedded array (document, MongoDB), part of an opaque value under a key (key–value, Redis), or edges with properties between nodes (graph, Neo4j); wide-column stores (Cassandra) group a partition's data in flexible rows. Relational databases minimize duplication and connect tables with foreign keys and joins, suiting structured data and strong consistency. Non-relational databases shape storage around access needs, with flexible schemas and sometimes deliberate duplication.
