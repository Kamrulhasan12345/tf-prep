Storing Large Objects

What happens when one value is bigger than a whole block, like a photo, a PDF or a long article? This chapter covers BLOBs, CLOBs, and the three ways a database can store them.

1. What a large object is

Chapter 1 assumed every record is smaller than a disk block. Usually that is true: an instructor row is about 50 bytes, and a block is 4,096 bytes or more. But some columns hold values that are far larger than a block:

BLOB (Binary Large OBject)
Raw bytes with no text meaning: an image, a video, an audio clip, a compiled file. Example column: photo BLOB in a student table.
CLOB (Character Large OBject)
A very long piece of text: a book chapter, a legal document, a long product description. Example column: thesis_text CLOB.

A single student photo might be 2 MB, which is 500 blocks of 4 KB. It cannot fit into the slotted page from Chapter 5. The slide notes that some DBMSs simply require records to be smaller than blocks, so the large value has to be stored somewhere other than inside the row itself.

2. Three ways to store them

Option 1: store it as a file in the file system

The photo is saved as a normal file on disk, like any file on your computer, and the row only stores its path (for example /img/101.jpg). This is simple and the files are easy to serve from a web server. The downside is that the database does not control the file: if someone deletes or renames it, the row now points at nothing, and a database backup or transaction rollback does not include the file.

Option 2: store it as a file managed by the database

The value is still a separate file, but the database creates, names, backs up and deletes it. The row stores an internal file ID. This keeps the efficiency of separate files while letting the database keep everything consistent: deleting the row also deletes the file, and a rollback restores it.

Option 3: break it into pieces stored as rows in a separate relation

The large value is cut into chunks that each fit in a block, for example 2 KB each. Each chunk is stored as an ordinary small row in a hidden side table, with the object's ID and a sequence number (0, 1, 2, …) so the pieces can be put back together in order. The main row stores only the object's ID. Because the chunks are ordinary rows, all the normal machinery (slotted pages, transactions, recovery) works on them unchanged.

PostgreSQL TOAST

The slide names a real example of option 3. PostgreSQL calls it TOAST (The Oversized-Attribute Storage Technique). When a row would be larger than about 2 KB, PostgreSQL first tries to compress its large values. If the row is still too big, it moves those values into a separate TOAST table, split into chunks of about 2 KB, and leaves a small pointer in the main row. This happens automatically. You write ordinary SQL and never see the TOAST table.

Quick check

Summary: BLOBs (binary) and CLOBs (text) can be far larger than a block, so they are kept out of the row. The database can store them as plain OS files, as files it manages itself, or as chunks in a separate table (PostgreSQL's TOAST). In every case the row keeps only a small reference.
