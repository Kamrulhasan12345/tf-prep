Data Dictionary Storage

The database has to remember what tables exist, what columns they have, who may use them and where they are stored. It keeps all of that in the data dictionary, which is itself stored as tables. Includes the answer to Question w2-4.

1. Metadata and the data dictionary

The rows in instructor are data. But to read them, the database also needs to know things like: does a table called instructor exist? What are its columns, in what order, of which types and lengths? Which file is it in? This information is metadata, meaning data about data.

The place where a DBMS keeps all its metadata is called the data dictionary, also known as the system catalog. Every SQL statement you run starts by consulting it. For SELECT name FROM instructor, the database first checks that instructor exists, that it has a name column, where that column is in each record, and where the file is.

2. What the dictionary stores (slides 20–21)

Information about relations
Names of relations. The names, types and lengths of each relation's attributes. Names and definitions of views (a view is a saved query that can be used like a table). Integrity constraints, such as primary keys, foreign keys and NOT NULL rules.
User and accounting information
User names, their (encrypted) passwords, and which group or role each user is in, so the database can check permissions.
Statistical and descriptive data
For example, the number of tuples (rows) in each relation. The query optimizer uses these numbers to choose the fastest way to run a query.
Physical file organization information
How each relation is stored (sequential, hash, clustered, …) and where it is physically located on disk.
Information about indices
Which indexes exist, on which relation and which attributes, and of which type. (Indexes are covered in a later lecture.)

3. The dictionary is stored as relations (slide 22)

The neat trick is that the database stores its own metadata as ordinary tables. This is called the relational representation of system metadata. The slides show one possible design:

Storing metadata as relations has a big benefit: the database can use its own machinery (storage, queries, transactions, recovery) on its own catalog, with no separate system. That is why you can usually run SQL queries on the catalog itself, for example SELECT * FROM information_schema.tables.

The slide adds one practical detail: the catalog is stored as relations on disk, but the DBMS also keeps specialized data structures in memory for fast access. The catalog is read for every single query, so going to disk each time would be far too slow. Frequently used catalog entries are cached in memory, in structures like hash tables keyed by name.

Question w2-4 (worked answer)

In a DBMS you cannot create two tables or two views with the same name, or two attributes or two indices with the same name in the same table. How are these rules implemented?

They are implemented as primary key (or unique) constraints on the catalog relations themselves. A primary key is a set of attributes whose value must be different in every row. Creating an object means inserting a row into the catalog, and if that row would repeat an existing key value, the insert fails and so does the CREATE statement.

  • Two tables with the same name: CREATE TABLE instructor inserts a row into Relation_metadata, whose primary key is relation_name. A second instructor row would duplicate the key, so it is rejected.
  • Two views with the same name: the same rule, using the key view_name of View_metadata. Tables and views are used the same way in queries (FROM instructor could be either), so a real DBMS also checks that a new view's name is not already used by a table, and vice versa. Many systems keep tables and views in one catalog table with one key, for this reason.
  • Two attributes with the same name in one table: Attribute_metadata has the composite key (relation_name, attribute_name). (instructor, salary) can appear only once, but (instructor, name) and (student, name) are both allowed, because the pairs differ.
  • Two indices with the same name: Index_metadata has the composite key (index_name, relation_name) on the slide, so an index name is unique within one table, the same pattern as attributes. (Oracle and PostgreSQL go further and make index names unique across the whole schema.)

Real example: PostgreSQL keeps tables, views and indexes in one catalog table, pg_class, with a unique index on (name, schema). Columns live in pg_attribute with a unique index on (table id, column name). These are exactly the constraints described above.

Quick check

Summary: the data dictionary (system catalog) stores metadata: relations, attributes, views, constraints, users, statistics, indexes and physical storage details. It is stored as ordinary relations on disk and cached in memory. Naming rules such as “no two tables with the same name” are just primary key constraints on those catalog relations.
