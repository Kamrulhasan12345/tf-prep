File Organization and Table Partitioning

The slides show how records sit inside a block. Exams also ask how records are arranged across the blocks of a file, and how a huge table can be split into smaller pieces. This chapter teaches both, following Silberschatz, Database System Concepts, §13.3, and answers the partitioning question from the bank.

1. What a file organization is

Chapters 2–5 answered “where is a record inside a block?”. The next question is “which block does a record go into?”. The rule a DBMS uses to decide this is the file's organization.

File organization
The way records of a relation are placed into the blocks of a file. It decides where a new record goes, and therefore how records can be found again.

Silberschatz lists these organizations:

  1. Heap file organization. Any record can go anywhere in the file where there is space.
  2. Sequential file organization. Records are stored in sorted order of a search key.
  3. Multitable clustering file organization. Records of several relations share one file (Chapter 7).
  4. B+-tree file organization. Records are kept in key order inside the leaves of a B+ tree, which stays ordered under inserts and deletes (Lecture 15).
  5. Hashing file organization. A hash function on an attribute decides the block.

2. Heap file organization

In a heap file, a new record is placed in any block that has room, usually the last block or a block found through a free-space map. Records are in no particular order. A free-space map is a small array with one entry per block that records roughly how full the block is (for example in eighths), so the DBMS can find a block with room without reading every block.

Inserts are cheap: one block write. Finding a record by value needs a full file scan unless there is an index, because the value tells you nothing about the block. Heap files are the default in most systems (PostgreSQL tables are heap files), with indexes added for lookups.

3. Sequential file organization

A sequential file keeps records sorted by a search key (any attribute or set of attributes, not necessarily the primary key). The records are linked by pointers in key order, and as far as possible they are also stored in that order physically, so reading the whole file in key order needs few seeks. This makes sorted output and range queries fast, and it is what a primary (clustering) index in Lecture 15 relies on.

The difficulty is keeping the order during inserts and deletes:

  • Deletion uses pointer chains: the record is removed from the chain (as in the free-list method of Chapter 3).
  • Insertion first locates the record that comes just before the new one in key order. If there is a free slot in that block, the new record goes there. If not, it goes into an overflow block. In both cases the pointers are adjusted so the chain still visits records in key order.
  • After many overflow inserts, the physical order no longer matches key order and scans need extra seeks. The file is then reorganized: rewritten in sorted order, usually at a quiet time.

4. Hashing file organization

In a hashing file organization, a hash function h is computed on one attribute of each record, and the result is the number of the block (bucket) the record is stored in. To find the record with ID = 76766, compute h(76766) and read only that bucket. This is very fast for equality lookups on the hashed attribute, and useless for range queries, because neighbouring keys go to unrelated buckets. Hashing is taught fully in Lecture 15's hashing chapter.

5. Table partitioning

Some tables grow to billions of rows: a bank's transactions, a university's course registrations over decades. Many databases let such a relation be split into smaller relations that are stored separately but still look like one table to SQL. This is table partitioning (Silberschatz §13.3.3).

Partition
One of the smaller relations a table is split into. Each partition has the same schema and is stored (and can be indexed, backed up or moved) on its own.
Partitioning key
The attribute whose value decides which partition a row belongs to, for example the year of a registration.
Horizontal partitioning
Splitting by rows: each partition holds some of the rows, with all their columns. This is what “table partitioning” usually means.
Vertical partitioning
Splitting by columns: each piece holds some columns of every row, plus the key to join them back. Column stores (Chapter 9) are the extreme case.

Horizontal partitioning comes in three common kinds:

  • Range partitioning: each partition holds a range of key values, such as year 2005–2009, 2010–2014, …
  • List partitioning: each partition holds an explicit list of values, such as department ∈ {CSE, EEE} or division = Dhaka.
  • Hash partitioning: the partition is h(key) mod p, which spreads rows evenly over p partitions without any natural order.

The main gain is partition pruning: when a query's condition fixes the partitioning key, the DBMS reads only the matching partitions and skips the rest. A query on this year's registrations reads one small partition instead of 20 years of data.

Exam questions

DB QB · 21-22 7b · 10 marks

Suppose, BIIS has a large number of records in its Course Registration table, accumulated over last 20 years. Explain how table partitioning can be done on this table, and what benefits and drawbacks it could offer.

Show worked answer

How to partition. Almost every query on registrations names a session or year (“this term's registrations”, “results of the 2023 July session”), and old years are rarely touched. So use horizontal range partitioning on the academic year (or session): one partition per year, 20 partitions, plus a new one created each year. Each partition is a separate relation with the same schema. For example, in PostgreSQL syntax:

CREATE TABLE course_registration (
    student_id  char(7), course_code char(10), session char(9),
    year        int,     grade       char(2)
) PARTITION BY RANGE (year);
CREATE TABLE reg_2024 PARTITION OF course_registration
    FOR VALUES FROM (2024) TO (2025);
-- … one partition per year, 2005 to 2024

A very large year can be sub-partitioned, for example by list on department or by hash on student_id. Inserts go automatically to the partition of their year, and SQL still sees one table.

Benefits.

  • Partition pruning: a query with year = 2024 scans only reg_2024, about 1/20 of the data, instead of the whole table.
  • Smaller indexes: each partition has its own, shallower indexes, so lookups and index rebuilds are cheaper.
  • Cheap archiving: old years can be moved to slower, cheaper storage, compressed or made read-only, and removing a year is “drop or detach a partition” instead of a DELETE of millions of rows.
  • Maintenance per partition: backups, statistics and reorganization can run on the active year only.
  • Less contention and more parallelism: this term's heavy registration load touches one partition; queries over many years can scan partitions in parallel.

Drawbacks.

  • Queries that do not restrict the year get no pruning and must visit every partition, which is slightly slower than one table: for example “all courses a student has ever taken” (a transcript spans about 4–5 yearly partitions) or “every registration for CSE 215 since 2005” (all 20).
  • Uniqueness across the whole table (such as a primary key on (student_id, course_code, session)) usually has to include the partitioning key, and global indexes are harder.
  • Updating the partitioning key moves the row to another partition (a delete plus an insert).
  • More objects to manage: new partitions must be created every year, and too many partitions add planning overhead.
  • Load is skewed: nearly all activity hits the current year's partition, so it gets no benefit from being split further unless sub-partitioned.

Summary: a file organization decides which block a record goes into: anywhere (heap), in key order with pointer chains and overflow blocks (sequential), by a hash function (hashing), next to related records (multitable clustering), or in a B+ tree. Table partitioning splits a huge relation into separately stored pieces by range, list or hash of a key, so queries that fix the key read only their partition, and old data can be archived or dropped cheaply, at the cost of slower queries that span all partitions.
