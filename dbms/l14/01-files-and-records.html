Files, Records and Fields

How a table you write in SQL actually turns into bytes on a disk. This chapter sets up the vocabulary every later chapter uses.

1. From tables to files

When you write CREATE TABLE instructor (…), you think of a neat grid with rows and columns. The disk knows nothing about grids. It only stores long sequences of bytes, grouped into blocks (a block is the unit the disk reads or writes in one go, typically 4 KB to 8 KB). Lecture 13 was about the disks themselves. This lecture answers the next question: how does the database arrange a table's rows inside those bytes?

The slide gives the answer in three nested layers:

File
The database is stored as a collection of files. A file is a named sequence of bytes that the operating system (or the database itself) manages. Usually one file holds one table.
Record
Each file is a sequence of records. A record is the bytes for one row of the table. “Tuple” and “row” mean the same thing.
Field
A record is a sequence of fields. A field is the bytes for one column value inside that row, such as the ID or the salary.

So the mapping is: table → file, row → record, column value → field. Throughout the lecture the example table is the instructor relation (“relation” is the formal word for a table):

2. The simplest approach: fixed-size records

The slide says to start with “one approach” that makes everything easy, and to deal with harder cases later. It makes four simplifying assumptions:

  1. Record size is fixed. Every record takes exactly the same number of bytes. For example, if ID is always 5 characters, Name is always 20, Dept. always 20 and Salary always 8, every record is 53 bytes even when the name is just “Wu”. Short values are padded with spaces. This is what char(n) columns do.
  2. Each file holds records of one type only. The instructor file contains only instructor records, never a department record mixed in.
  3. Different relations go in different files. instructor in one file, department in another, student in a third.
  4. Records are smaller than a disk block. One record always fits inside one block, so no single row needs several blocks.

Why bother with these assumptions? Because with them, finding record number i becomes simple arithmetic, which is the topic of the next chapter. Later chapters relax each assumption one by one:

Summary: a database is a set of files, a file is a sequence of records (rows), and a record is a sequence of fields (column values). The easiest case is fixed-size records, one table per file, each record smaller than a block.
