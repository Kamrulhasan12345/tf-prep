Compression, and When to Use Columns

How a column store shrinks its data with dictionary encoding, how it answers queries without fully unpacking it, and why column storage suits data warehouses while row storage suits everyday transactions.

1. Dictionary encoding (slide 27)

The slide shows a small parts catalogue with four columns: Part (a chip name), Pins (number of pins), Technology (CMOS or TTL) and Programmable (Yes or No). Here is the table in normal form:

The compression method is dictionary encoding. For each column:

  1. Make a list of the distinct values in the column. This list is the column's dictionary.
  2. Give each distinct value a short binary code: its position in the dictionary.
  3. Store the column as a list of codes instead of the real values. This list is the code vector.

The number of bits per code depends on how many distinct values there are. k bits can count up to 2k different values:

Look at Technology. Stored as text, “CMOS” and “TTL” take about 4 bytes each, so 6 rows take about 24 bytes. Encoded, they take 6 bits, less than a single byte, plus a tiny dictionary stored once. On a real table with millions of rows and only a handful of distinct values, the saving is enormous.

The slide also shows how the column store keeps track of this. Each column has a small Field descriptor with three pointers: Dict points to the column's dictionary, Vec points to its code vector, and Next points to the next column's Field descriptor, so all the columns of the table are chained together.

2. Query processing on compressed columns (slide 28)

The clever part: most of a query can run on the codes, without turning them back into the original values. Take:

SELECT Part FROM parts WHERE Technology = 'TTL';
  1. Compression engine. The query contains the constant 'TTL'. The engine looks it up in the Technology dictionary and finds code 1. The condition becomes “Technology code = 1”.
  2. Scan. The scan runs over the compressed Technology vector 0 0 1 1 0 0 and compares tiny 1-bit codes instead of strings. Rows 3 and 4 match.
  3. Decompression engine. Only for those matching rows, it takes the Part codes (010, 011) and looks them up in the Part dictionary.
  4. Expanded result table. The answer is returned in normal, readable form: DMPAL16L8 and DMPAL10H8.

This is why the slide says queries can be processed “in compressed form with a very low decompression overhead”. Comparing codes is faster than comparing strings, more codes fit in each block and in the CPU cache, and only the few result rows ever get decompressed.

3. Advantages and drawbacks (slide 29)

AdvantagesDrawbacks
Storage efficient. Repeated values are stored once in a dictionary and referred to by short codes. Cost of decompression. What? The columns are stored compressed, so every query has to decompress something: at least the values it returns. Inserting or updating a value may also need a dictionary lookup, or a new dictionary entry.
Query efficient. Filtering and scanning run directly on the compressed codes, and decompression is needed only for the result.

4. Conclusions: which workload suits which storage (slides 29–30)

Two kinds of database workload need to be told apart:

Transaction processing (OLTP)
The everyday operations of an application: a student registers for a course, a bank transfers money, a shop records an order. Each operation reads or changes a few whole rows, and there are many such operations every second, with lots of inserts, updates and deletes.
Decision support (OLAP), using a data warehouse
Analysis to help managers decide things: “What is the average salary per department over the last 10 years?” A data warehouse is a large database built for these questions. Each query reads a few columns of a huge number of rows. Data is loaded in bulk (inserted) and almost never updated or deleted.

Columnar is more efficient for decision support. Why?

The slide's reasons: the data warehouse uses only a few attributes per query, there are no updates, and data is only inserted. Each of these lines up with a strength from Chapter 9 or avoids a weakness:

  • Few attributes per query → column storage reads only those columns (reduced I/O).
  • Huge scans over one column → better cache use, compression and vector processing.
  • No updates or deletes → the expensive operations of column storage almost never happen.

Row-oriented is preferable for transaction processing. Why?

Transaction processing needs frequent updates and deletions of whole rows. In a row store, each one changes one record in one place. In a column store, each one would touch every column (and possibly re-compress data), and reading a whole row would need tuple reconstruction. Row storage wins here.

Hybrid row/column stores

Some databases support both representations in the same system. These are hybrid row/column stores. For example, recent changes may be kept in row format for fast updates and periodically converted into column format for fast analysis, or the user may choose per table.

Key terms

Quick check

Summary: dictionary encoding replaces each value with a short code into a per-column dictionary. Queries translate their constants into codes, scan the compressed codes, and decompress only the results. Column storage suits data warehouses (few columns, huge scans, inserts only). Row storage suits transaction processing (many small updates and deletes). Hybrid systems offer both.
