Deleting Fixed-Length Records

Deleting a row leaves a hole in the file. The slides give three ways to deal with that hole: shift everything up, move the last record in, or keep a list of holes to reuse later.

1. Why deletion is a problem

Chapter 2 relied on one fact: record i is always at byte n(i−1), with records packed back to back. Deleting a record breaks that. If you just erase record 3, the file now has an empty 100-byte gap in the middle. A scan would read garbage there, and the space is wasted. Something has to be done with the hole. The slides list three alternatives for deleting record i from a file of n records:

  1. Move records i+1, …, n to positions i, …, n−1 (shift everything after the hole up by one).
  2. Move record n (the last one) to position i (fill the hole with the last record).
  3. Do not move records at all. Instead, link all free slots together on a free list.

All three examples use the same query from the slides:

DELETE FROM instructor WHERE id = 22222;

22222 is Einstein, record 3.

2. Alternative a: shift every later record up

Record 3 is removed, then record 4 is copied into slot 3, record 5 into slot 4, and so on until record 11 is copied into slot 10. The file is one record shorter and has no gap. The order of the remaining records is unchanged.

Cost: deleting one record moved 8 others. Deleting near the start of a large file means rewriting almost the whole file, which is far too expensive for a busy database.

3. Alternative b: move the last record into the hole

Only one record moves: the last record in the file (record 11, Kim) is copied into the empty slot 3, and the file shrinks by one record.

Cost: one record move, however large the file is. Downside: the records are no longer in their original order. If the file was sorted (for example by ID), that order is now broken. Kim, ID 98345, now sits between 15151 and 32343.

4. Alternative c: the free list

The third option moves nothing. The deleted slot is left where it is and marked as free. The free slots are linked together so the next insert can find one quickly. This chain of free slots is the free list, and it works like this:

  • A small file header is added at the start of the file. It stores the address of the first free slot.
  • Each free slot uses its own (now unused) bytes to store the address of the next free slot. The last one stores “null”, meaning “end of the list”.

A pointer here is simply a stored address: “the next free slot is record 4”. Because a deleted slot holds no real data any more, its space can be reused to store that pointer at no extra cost.

The slide deletes three records: id = 12121 (record 1), id = 32343 (record 4) and id = 45565 (record 6).

Inserting with a free list

When a new instructor is inserted, the database looks at the header. If it points to a free slot, the new record goes into that slot, and the header is updated to point to whatever that slot pointed to next. With the list above, the first insert fills record 1 and the header then points to record 4. Only when the list is empty does a new record go at the end of the file. This is the main advantage of the free list: holes are always reused, so space is not wasted.

There is one more reason real systems prefer not to move records. Other structures, such as indexes, store the position of a record. If records move (alternatives a and b), every one of those stored positions has to be updated as well. With a free list, a record's position never changes.

5. Discussion: implementing a fixed-length record file

The last slide asks how you would implement this as a small program, with classes and methods, and how a relation would be stored using them. One reasonable design uses two classes: a record that knows how to turn itself into a fixed number of bytes, and a file that manages slots and the free list.

RECORD_SIZE = 53   # 5 + 20 + 20 + 8 bytes

class InstructorRecord:
    def __init__(self, id, name, dept, salary): ...
    def to_bytes(self):        # pad every field to its fixed width
        return (self.id.ljust(5) + self.name.ljust(20) +
                self.dept.ljust(20) + str(self.salary).rjust(8)).encode()
    @staticmethod
    def from_bytes(b): ...     # slice b[0:5], b[5:25], b[25:45], b[45:53]

class FixedLengthFile:
    # header: address of the first free slot (or -1 if none)
    def read(self, i):         # seek to HEADER + i * RECORD_SIZE, read RECORD_SIZE bytes
    def insert(self, rec):     # take the slot the header points to, else append at the end
    def delete(self, i):       # write the old header value into slot i, set header = i
    def scan(self):            # yield every slot that is not on the free list

Storing the instructor relation means creating one FixedLengthFile for it and calling insert once per row. read(i) uses exactly the formula from Chapter 2, and delete is alternative c.

BUET QBank · CSE 303 | L-3/T-1 | 2015–16 · 15 marks

Figure shows a fixed-length record file structure for a Customer relation. Show the file structure after deletion of records with customer IDs C0004 and C0007 for different file deletion methods. Compare the advantages and disadvantages among the different deletion methods.

Show worked answer

C0004 is record 3 and C0007 is record 6. Delete them in that order with each of the three methods of this chapter.

(a) shift later records up
(b) move the last record into the hole
(c) free list

(a) Shift. Deleting record 3 moves records 4–9 up one slot (6 moves). C0007 is now in slot 5, and deleting it moves the 3 records after it (3 moves). Total 9 record moves; the file has 8 records, still sorted.

(b) Move last. Deleting record 3 moves C0010 (record 9) into slot 3. The file now ends at record 8 (C0009). Deleting C0007 (record 6) moves C0009 into slot 6. Total 2 moves, but the order is broken: C0010 now sits between C0003 and C0005.

(c) Free list. No record moves. After deleting record 3, header → 3 → null. Deleting record 6 pushes it at the front: header → 6 → 3 → null. (If new free slots are added at the end, the list is header → 3 → 6.) The file still has 10 slots, two of them free.

A file containing fixed-length records of a student relation (attributes: student_id, name, department_code, level, term) is given. Show the file structures after deletion of record 3 for the following cases and give comparative advantages/disadvantages:
(a) Move record 4 to the space occupied by record 3, record 5 to record 4, and so on.
(b) Move record 8 to the space occupied by record 3.
(c) Mark record 3 as deleted and move no records. Use a header and record pointer.

Show worked answer

The figure is not printed with this question in the bank. The same exam's next question (multitable clustering, Chapter 7) gives this student file with records 0–8, which matches “move record 8”, so it is used here. Record 3 is (1205010, N14).

(a) shift up: 5 moves
(b) record 8 into slot 3: 1 move
(c) marked deleted, free list

(a) Records 4–8 each move up one slot, so 1205013 is now record 3 and the file has records 0–7, still in the original order. (b) Only record 8 (1204003) moves into slot 3; the file has records 0–7, but an EEE student now sits among the CSE students, so the grouping by department is lost. (c) Nothing moves. The header points to record 3, and record 3's space holds the next-free pointer (null, since it is the only free slot). The next insert goes into slot 3.

Comparison: (a) keeps order but costs a move per later record; (b) costs one move but breaks order; (c) costs no moves and keeps every record's position (so indexes stay valid) but leaves a hole until the next insert. The same table as in the previous question applies.

Note: the question bank's answer invents its own 8-record file numbered 1–8 (S101 … S108). Its three results are correct for that invented data.

Summary: a deleted record leaves a hole. Shifting everything up (a) keeps order but is slow. Moving the last record in (b) is fast but breaks order. A free list (c) moves nothing and reuses holes on later inserts, which is why it is the usual choice.
