Columnar File Formats: ORC and Parquet

Column storage is not only inside databases. Big-data systems store columnar data in ordinary files, using formats such as ORC and Parquet. This chapter explains what is inside such a file.

1. Columnar storage inside a file

Chapters 9 and 10 described column storage inside a database system. In big-data processing (for example Apache Spark, Hive or Presto analysing terabytes of logs), data often lives as plain files in a distributed file system rather than inside a DBMS. Two file formats bring the columnar idea to those files:

ORC (Optimized Row Columnar)
Developed for Apache Hive. Despite “Row” in the name, the data is stored column by column.
Parquet
Apache Parquet, the most widely used columnar file format today, supported by almost every big-data and analytics tool.

Both are columnar file representations: one file holds a table, but inside it the values are grouped by column, compressed, and stored so that a reader can load only the columns a query needs. They are very popular for big-data applications for the reasons from Chapter 10: analytics reads a few columns of a huge number of rows, and data is mostly written once and then only read.

2. Stripes: how ORC organises a file

A big-data file can be hundreds of gigabytes. Turning the whole file into four giant columns would be impractical: you would have to hold everything in memory before writing anything, and reconstructing one row would mean jumping across the entire file. ORC solves this by working in pieces:

  1. Take a run of consecutive rows (tuples) that together occupy several hundred megabytes.
  2. Convert just that run into columnar form: all its values of column 1, then all of column 2, and so on, each compressed.
  3. This columnar piece is called a stripe. Each stripe is around 250 MB.
  4. The file is a sequence of stripes, one after another.

So ORC is columnar inside each stripe, but the stripes themselves follow row order. That combines the advantages of both:

  • A query that needs only ID and salary reads just those two column chunks from each stripe and skips the rest (reduced I/O, as in Chapter 9).
  • Rebuilding a row only needs data from one stripe, not from the whole file.
  • A writer can produce the file stripe by stripe, without holding everything in memory.
  • Each stripe also stores small statistics, such as the minimum and maximum value of each column. A query looking for salary > 100000 can skip an entire stripe whose maximum salary is 90000 without reading it.

Parquet uses the same design under a different name: its stripes are called row groups, and each column's piece inside a row group is a column chunk.
