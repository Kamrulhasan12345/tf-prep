Fixed-Length Records: Finding a Record

If every record is the same size, the position of any record is one multiplication away. This chapter shows the formula, the “records crossing blocks” problem, and works through the slide example and Question w2-1.

1. The address formula

Picture the instructor file as one long line of bytes. Every record takes exactly n bytes, and the records are packed one after another with no gaps. The first record starts at byte 0, the second at byte n, the third at byte 2n, and so on. The slide writes this as:

record i starts at byte n × (i − 1)

Here i counts from 1 (the 1st record, the 2nd record, …). Subtract 1 because the 1st record has nothing in front of it. If you number records from 0 like the slide's tables do (“record 0”, “record 1”), the same formula is simply n × i. Both say the same thing: the number of whole records in front of you, times the size of one record.

A byte offset (or just “offset”) is this distance from the start of the file, measured in bytes. The database turns the offset into a physical place on disk (which track and sector), so it can jump straight there without reading anything in front of it.

Slide 3 example

Record size = 70 bytes. The disk head is at track 0, sector 0 (the start of the file). Find the location of the 5th record.

Location = 70 × (5 − 1) = 70 × 4 = 280. The 5th record starts at byte 280. In the table's 0-based labels, the 5th record is “record 4” (El Said). Four records of 70 bytes each sit in front of it: 4 × 70 = 280.

2. The problem: records crossing blocks

The disk does not read single bytes. It reads whole blocks. Suppose a block is 512 bytes and a record is 100 bytes. 512 is not a multiple of 100, so after 5 records (500 bytes) only 12 bytes are left in the block. The 6th record starts at byte 500 and ends at byte 599, so its first 12 bytes are in block 0 and its other 88 bytes are in block 1. This is what the slide means by records may cross blocks.

Why is that bad? Reading record 5 now needs two block reads instead of one. Writing it means updating two blocks, and if the system crashes between the two writes, the record is left half old and half new.

The slide's modification: do not allow records to cross block boundaries. Put as many whole records into a block as fit, and leave the leftover bytes empty. With 512-byte blocks and 100-byte records, each block holds ⌊512 ÷ 100⌋ = 5 records and wastes 12 bytes. The ⌊ ⌋ brackets mean “round down”. The formula changes to:

records per block = ⌊ block size ÷ record size ⌋

block of record i (0-based) = ⌊ i ÷ records per block ⌋

3. How a query is executed, and how to count its cost

Two numbers measure the cost of a query on disk. They are the units every question in this lecture asks for.

Seek
Moving the disk arm to a different track. Slow (milliseconds). Count one seek each time the head has to jump somewhere new.
Block transfer
Reading (or writing) one block once the head is in position. Count one transfer per block read.

Consecutive blocks of a file are stored next to each other, so after one seek to the start of the file, the disk can read block after block without seeking again.

With no index, the only way to find a row with a given ID is a file scan (also called a linear search): start at block 0, read each block, check every record in it, and stop when the record is found. You can stop early only if ID is the primary key, because then there is at most one match.

Slide 4 example (worked answer)

Block size = 512 bytes. Record size = 100 bytes. SELECT * FROM instructor WHERE id = 76766. The head is at track 1000, and the instructor file starts at track 0, sector 0.

(a) How does a record cross a block? Records are packed back to back, 100 bytes each, but the block holds 512. Records 0–4 fill bytes 0–499. Record 5 occupies bytes 500–599, while block 0 ends at byte 511, so record 5 is split: 12 bytes in block 0 and 88 bytes in block 1. The same happens to record 10 (bytes 1000–1099), split between block 1 (ends at 1023) and block 2 (Figure 2).

(b) Block number of id = 76766. 76766 (Crick) is record 9 counting from 0, the 10th record. It starts at 100 × 9 = 900 and ends at 999. Block 1 covers bytes 512–1023, so it is in block 1 (the 2nd block). It does not cross a boundary.

(c) How the query is executed.

  1. The arm seeks from track 1000 to track 0, where the file starts.
  2. Block 0 is read into memory. Its records (0–4 and the first part of 5) are compared with 76766. No match.
  3. Block 1 is read. It contains the rest of record 5 and records 6–9. Record 9 matches.
  4. ID is the primary key, so no other record can match. The scan stops and the row is returned.

(d) Seeks and block transfers. 1 seek (track 1000 → track 0) and 2 block transfers (blocks 0 and 1). If ID were not unique, the scan would have to read the whole file: 1,200 bytes = 3 blocks, so 1 seek and 3 block transfers.

Question w2-1 (worked answer)

Block size = 350 bytes. Record size = 100 bytes. SELECT * FROM instructor WHERE id = 98345. Head at track 1000, file at track 0, sector 0. Records do not cross block boundaries.

First, the layout. Records per block = ⌊350 ÷ 100⌋ = 3, leaving 50 bytes unused per block. 12 records ÷ 3 = 4 blocks (block 0 to block 3), as in Figure 3.

(a) Block number. The question text asks for id = 76766 while the query uses 98345, which looks like a copy-paste mix-up on the slide. Both answers:

  • 76766 is record 9 → block ⌊9 ÷ 3⌋ = block 3 (the 4th block).
  • 98345 is record 11 → block ⌊11 ÷ 3⌋ = block 3 (the 4th block, the last one).

(b) Execution. Seek from track 1000 to track 0. Read block 0 (records 0–2), block 1 (3–5), block 2 (6–8), checking each ID. Read block 3 (9–11) and find 98345 in record 11. Stop.

(c) Cost. 1 seek and 4 block transfers. The record is in the last block, so the entire file is read either way.

Summary: with fixed-size records, record i starts at byte n(i−1). If records may cross blocks, some reads touch two blocks, so databases pack only whole records per block. Without an index, a lookup is a file scan: 1 seek to the start of the file, then one block transfer per block read until the record is found.
