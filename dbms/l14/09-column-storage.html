Column-Oriented Storage

Everything so far stored a table row by row. Column-oriented storage turns that sideways and stores each column on its own. This chapter explains how, and works through each “How?” and “What?” on the slides.

1. Row storage versus column storage

Every chapter so far used row-oriented storage: all the fields of one record are stored together, then all the fields of the next record, and so on. A block of the instructor file holds a few complete rows.

Column-oriented storage, also called the columnar representation, does the opposite: each attribute of a relation is stored separately. All the IDs are stored together, then all the names together, then all the departments, then all the salaries. Each column is effectively its own file.

How does the database know which name belongs to which ID? By position. The 5th value of every column belongs to the same row, the 5th instructor. The position number is called the tuple-id (a tuple is a row). Row 5 is (32343, El Said, History, 60000) because those are the 5th entries of the four columns.

2. Benefits (slide 24)

Reduced I/O when only some attributes are accessed. How?

Take SELECT id, salary FROM instructor. In row storage, ID and salary are mixed in with name and department in every block, so the database has to read every block of the whole table just to pick two fields out of each row. In column storage, it reads only the ID column and the salary column. The name and department columns are never touched.

With the field sizes from Chapter 1 (id 5, name 20, dept 20, salary 8 bytes), a row is 53 bytes but id + salary is only 13 bytes. Column storage reads about 13/53 ≈ 25% of the data. Since block transfers are the main cost of a query, that is roughly 4 times faster. Real analytical tables often have 50 to 100 columns while a query uses 3 or 4, so the saving is much larger.

Improved CPU cache performance. How?

The CPU does not read memory one value at a time. It pulls in a chunk of neighbouring bytes (a cache line, typically 64 bytes) into its small, very fast cache. When summing salaries in row storage, each cache line contains one salary plus an ID, a name and a department the query does not need, so most of each cache line is wasted. In column storage, a cache line holds 8 salaries in a row, all useful. The CPU waits for memory far less often.

Improved compression. How?

Compression works best on data that is similar and repetitive. A column holds values of one type, and often the same values repeat. In the slide's dept column, “Comp. Sci.” appears 3 times, “Physics”, “History” and “Finance” twice each. Each department name could be replaced by a small code (Chapter 10 shows exactly how). A row mixes numbers, names and departments together, so much less repetition is visible to a compressor. Compressed columns take less disk space and need fewer block transfers.

Vector processing

Modern CPUs have vector (SIMD, “single instruction, multiple data”) instructions that perform the same operation on several values at once. For example, one instruction can compare 8 salaries with 70000 in a single step. That only works if the 8 values sit next to each other in memory, which is exactly what a column provides.

3. Drawbacks (slides 25–26)

Cost of tuple reconstruction. What?

Tuple reconstruction means putting a complete row back together from its separate columns. The slide's example:

SELECT * FROM instructor WHERE id = 32343;
  1. Search the ID column for 32343. It is the 5th value, so the tuple-id is 5.
  2. Fetch the 5th value of the name column (El Said).
  3. Fetch the 5th value of the dept-name column (History).
  4. Fetch the 5th value of the salary column (60000).
  5. Combine them into the result (32343, El Said, History, 60000).

In row storage the whole row sits in one block, so this is one block read. In column storage the four values are in four different column files, which can mean four separate block reads (and possibly four seeks). For queries that want whole rows, column storage is slower.

Cost of tuple deletion and update. What?

The slide's example:

DELETE FROM instructor WHERE dept_name = 'History';
  1. Search the dept-name column for ‘History’. Found at tuple-ids 5 and 8 (El Said and Califieri).
  2. Delete position 5 and position 8 from all four columns.

In row storage, each deleted row is one record in one place. Here every deletion has to be applied in four places, and the positions of all later values must stay aligned across the columns, so they cannot be shifted independently. An update is similar: “Similar is update”. Changing a whole row means writing to every column. For tables with frequent small changes, this is expensive.

Practice

Key terms

Quick check

Summary: columnar storage keeps each attribute separately and matches values across columns by position (the tuple-id). It reads less data when a query uses few columns, uses the CPU cache better, compresses better and allows vector processing. It is slower when a query needs whole rows (reconstruction) and when rows are deleted or updated, because every column must be changed.
