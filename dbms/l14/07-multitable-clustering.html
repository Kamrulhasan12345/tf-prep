Multitable Clustering File Organization

Normally each table gets its own file. Here, rows from two tables that are often used together are stored side by side in one file, so a join can read them in one go.

1. The idea

Chapter 1 assumed that different relations go in different files. That is the single-table file organization: one file for department, another for instructor. It is simple, but think about how the two tables are used. Very often a query wants a department together with its instructors, which is a join: combining rows from two tables where a column matches (here, dept_name).

A multitable clustering file organization stores several relations in one file, and places related rows next to each other. Each department record is immediately followed by the records of the instructors who belong to it. “Clustering” means grouping things that belong together physically close on disk.

2. The slide's example query

SELECT ID, building
FROM instructor i, department d
WHERE i.dept_name = d.dept_name
  AND dept_name = 'Comp. Sci.';

In words: list each Comp. Sci. instructor's ID together with the building of the Comp. Sci. department. The answer is (10101, Taylor), (45565, Taylor), (83821, Taylor).

Example (worked answer): how is this query processed?

(a) Single-table file organization.

  1. Seek to the department file and read its blocks until the Comp. Sci. row is found. Remember building = Taylor.
  2. Seek to the instructor file, which is somewhere else on disk.
  3. Scan the instructor file and keep every row with dept_name = Comp. Sci. Srinivasan, Katz and Brandt are scattered between Physics instructors, so in a real table they could be spread over many blocks.
  4. Pair each match with Taylor and output.

Cost: at least 2 seeks (one per file), plus block transfers for both files.

(b) Multitable clustering file organization.

  1. Seek to the clustered file and find the Comp. Sci. department record.
  2. Its instructors are the records directly after it, in the same block (or the next one). Read them until the next department record (Physics) appears.
  3. Output each instructor's ID with Taylor.

Cost: 1 seek, and usually a single block transfer, because everything the query needs is stored together.

3. Strengths and weaknesses (slide 19)

Good for

Queries that compute department ⨝ instructor (the symbol ⨝ means join), and queries about one department and its instructors. Both read rows that are already sitting next to each other.

Bad for

Queries that involve only department, such as SELECT * FROM department. In a separate file, all department rows would sit together in a few blocks. In the clustered file, department rows are spread out with instructor rows in between, so the scan must read every block of the file and skip all the instructor records. The more instructors per department, the worse this gets.

Results in variable-size records

The file now contains two kinds of record: a department record (3 fields) and an instructor record (4 fields). They have different sizes, so this is case (a) from Chapter 4: several record types in one file. The file must use variable-length techniques such as the slotted page, and each record must say which relation it belongs to.

Pointer chains

To soften the “bad for department-only queries” problem, the slide suggests adding pointer chains. Each department record stores the address of the next department record. A department-only scan follows the chain and jumps from department to department without looking at the instructor records in between.

DB QB · 24-25 8c · 10 marks  |  BUET QBank · CSE 215 | L-2/T-1 | 2024–25 · 10 marks

What is the purpose of using multiple clustering file organization? Give an example of its usage. Mention the disadvantages of this organization.

Show worked answer

Purpose. A multitable clustering file organization stores records of two or more relations in one file, and places each record next to the records of the other relation it joins with (on a common attribute, the cluster key). Its purpose is to make the frequent join of those relations, and lookups of one “parent” together with its “children”, cost as few block reads as possible: the matching records are already in the same block.

Example. In a university database, department and instructor are joined on dept_name all the time (“show the Comp. Sci. department with its instructors”). Clustering stores the Comp. Sci. department record followed directly by Srinivasan, Katz and Brandt, then the Physics record followed by Gold (Figure 2). The query

SELECT ID, building FROM instructor i, department d
WHERE i.dept_name = d.dept_name AND d.dept_name = 'Comp. Sci.';

then reads one block after one seek, instead of seeking to and scanning two separate files.

Disadvantages.

  • Queries on one relation alone become slower. SELECT * FROM department must read every block of the clustered file and skip the instructor records between department records (pointer chains reduce this).
  • The file holds records of different types and sizes, so it needs variable-length record handling (slotted pages) and a type tag per record.
  • Only joins on the cluster key benefit. Queries on other attributes see a spread-out, larger file.
  • Insertions are harder: a new instructor must go next to its department, which may need moving records or overflow blocks; a department with many instructors spans several blocks.

The bank's answer is correct.

The department and instructor relations are given in the following figures respectively. Show the multi-table clustering file organization for these relations and explain the types of queries for which this organization will be efficient and the type for which it is inefficient.

(The two relations are the ones in Figure 1.)

Show worked answer

Organization. Each department record is followed by the instructor records with the same dept_name: (Comp. Sci., Taylor, 100000), (10101, Srinivasan, Comp. Sci., 65000), (45565, Katz, Comp. Sci., 75000), (83821, Brandt, Comp. Sci., 92000), (Physics, Watson, 70000), (33456, Gold, Physics, 87000). This is exactly Figure 2.

Efficient for: joins of department and instructor on dept_name (for example, every instructor with the building of their department), and queries about one department and its instructors (the Comp. Sci. example in Section 2). The matching records share a block, so one seek and usually one block transfer answers them.

Inefficient for: queries that use only one relation. SELECT * FROM department must scan the whole file, reading all instructor records just to skip them. A query on instructor alone, such as “all salaries above 80000”, also reads more blocks than a compact instructor file, because department records are mixed in. Pointer chains (Figure 3) help the department-only case.

(a) Show the multitable clustering file structure for the given relations. Explain why executing SELECT * FROM department is more expensive in this structure.
(b) Show the multitable clustering file structure with pointer chain. How is the query in (a) executed faster in this structure?

Show worked answer

(a) Each department record is followed by its students. To count block reads, assume 4 records fit in a block (any small number gives the same picture).

In separate files, the 2 department records would sit in 1 block, so SELECT * FROM department would read 1 block. In the clustered file they are records 0 and 7, separated by 6 student records, and nothing tells the scan where the next department record is. It must read all 3 blocks and skip 9 student records. With hundreds of students per department, the department scan reads the whole (large) file instead of a few blocks.

(b) Add a pointer field to each department record that holds the address of the next department record (the last one holds null):

The scan reads block 0, outputs CSE, and follows CSE's pointer straight to the EEE record in block 1. EEE's pointer is null, so the scan stops. It reads 2 blocks instead of 3 and never looks at block 2. In a real file, the blocks that hold only student records are skipped entirely, so the department scan costs about one block per department instead of the whole file. (Instructor records can be chained per department the same way.)

The bank's answer is correct.

Summary: multitable clustering stores related rows of several tables together in one file (each department followed by its instructors). Joins and single-department queries get much faster. Queries on department alone get slower, the file has mixed record sizes, and pointer chains can be added to jump between records of one relation.
