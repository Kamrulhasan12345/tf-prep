Variable-Length Records

Real rows are not all the same size. This chapter explains where variable-length records come from, and how one record is laid out byte by byte using (offset, length) pairs and a null bitmap. It ends with the answer to Question w2-2.

1. Where variable-length records come from

Chapters 2 and 3 assumed every record has the same size. That assumption fails in three common situations, which the slide lists as a, b and c.

a. Several record types in one file

Sometimes two tables are stored in the same file (Chapter 7 shows why that can be useful). The slide's example stores student and takes records together:

student (id char(10), name char(30), address char(50), CGPA number(3,2), year-admit number(4))
takes   (id char(10), course-id char(20), level char(1), term char(1))

Every field is fixed size, so each table's records have a fixed size. But a student record and a takes record are different sizes (roughly 97 bytes versus 32), so the file contains records of different lengths.

b. Fields that can vary in length

This is the most common case. char(30) always takes 30 bytes, padded with spaces. varchar(30) means “up to 30 characters”, and only stores the characters actually used. “Wu” takes 2 bytes and “Srinivasan” takes 10. The slide's example:

student (id char(10), name varchar(30), address varchar(50), CGPA number(3,2), year-admit number(4))

Two students with different name and address lengths now produce records of different sizes.

c. Repeating fields

Some older data models allowed a field to repeat a variable number of times inside one record, for example a list of phone numbers. A record with three phone numbers is longer than one with a single number. Modern relational databases avoid this by putting repeating values in a separate table, but the storage problem is the same.

2. How a variable-length record is laid out

The difficulty is simple: if “name” can be 2 bytes or 10 bytes, the database can no longer know where “dept_name” starts by counting. The slide's solution has three rules:

  1. Attributes are stored in order, but in two parts: a fixed-size part at the start and a variable-size part at the end.
  2. Each variable-length attribute is represented in the fixed part by an (offset, length) pair. The offset is where its actual bytes start, measured from the beginning of the record. The length is how many bytes it uses. The pair itself is fixed size (here 2 bytes + 2 bytes = 4 bytes). The actual characters are stored after all the fixed-length data.
  3. Null values are recorded in a null bitmap. A bitmap is a row of bits, one per attribute. A bit is 1 if that attribute is NULL (has no value), and 0 if it has a value. One byte is enough for up to 8 attributes.

The result: the fixed part always has the same size and layout, so the database can jump to the 2nd attribute's pair at byte 4 every time, read “offset 26, length 10”, and jump straight to the name.

Notice how the offsets chain together: each string starts where the previous one ended. id starts at 21 (right after the 21-byte fixed part), 21 + 5 = 26 for name, 26 + 10 = 36 for dept-name. The record ends at byte 45, so it is 46 bytes long.

What the null bitmap does

If this instructor had no department (dept-name IS NULL), the bit for dept-name in the bitmap would be set to 1, giving 0010 (reading the bits in attribute order id, name, dept, salary). The database checks the bitmap first and does not even look at the (offset, length) pair for a null attribute. This is cheaper than storing a special “null” value in every field.

Key terms

Quick check

Summary: records become variable length when a file mixes record types, when fields are varchar, or when fields repeat. Each record is stored as a fixed part (an (offset, length) pair per variable field, the fixed-size fields, and a null bitmap) followed by the variable part holding the actual strings.
