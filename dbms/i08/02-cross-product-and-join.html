Cross Product and Join

What does SQL do when the FROM clause names two tables? This chapter builds the answer from the slides' tiny tables R and S: first every pairing of rows (the cross product), then keeping only the pairs that match (the join), then the natural join shorthand, and finally the nested-loop "meaning" of any SELECT–FROM–WHERE query.

1. The cross product (slide 7)

Slide 7 lists two tables after FROM and has no WHERE clause:

SELECT A, R.B, S.B, C
FROM   R, S;

R has columns A and B, and S has columns B and C. Both tables have a column called B, so inside this query a bare B would be ambiguous. We write R.B and S.B to say which one we mean. A and C exist in only one table, so they need no prefix.

Cross product (Cartesian product), R × S
The table that pairs every row of R with every row of S. Each result row is a row of R followed by a row of S. If R has m rows and S has n rows, R × S has m · n rows, and its columns are all of R's columns followed by all of S's.
Qualified column name
table.column, such as R.B. Needed whenever two tables in the FROM clause share a column name.

Here R has 2 rows and S has 3, so R × S has 2 · 3 = 6 rows and 2 + 2 = 4 columns. The arrows on the slide show row (1, x) of R being paired with x, y and z of S, then row (2, y) being paired with the same three. The animation builds the six rows one pairing at a time.

Most of these six rows are nonsense. Row (1, x, y, 6) glues R's "x" row to S's "y" row, although nothing connects them. The cross product is rarely the answer we want; it is the raw material that a WHERE condition then filters.

2. Join = cross product, then filter (slides 8–9)

Slide 8 adds a WHERE clause that keeps only the pairs whose B values agree:

SELECT *
FROM   R, S
WHERE  R.B = S.B;

Conceptually, SQL forms all 6 pairs and tests R.B = S.B on each. The slide circles the two pairs that pass: (1, x, x, 5) and (2, y, y, 6). Slide 9 shows the final result with just those two rows. That is a join.

Join (theta join), R ⋈C S
The rows of R × S that satisfy a condition C. In relational algebra, R ⋈C S = σC(R × S): a selection σ applied to a cross product.
Equijoin
A join whose condition is an equality between columns, such as R.B = S.B. Almost every join you write is an equijoin on a foreign key.

Row S(z, 7) has no partner in R, so it does not appear in the join at all. Remember this: an ordinary join silently drops rows that match nothing. Lecture 09's outer joins exist to keep such rows.

Question (worked answer): does the DBMS really build the whole cross product?

No. "Cross product, then filter" defines what the answer is, and it is the right way to reason about a query. A real DBMS computes the same answer far more cheaply: it uses an index on S.B, sorts both tables, or hashes them (the join algorithms of Lecture 08 of the query-execution part). The query optimizer is free to choose any method, because they all produce exactly the rows of σC(R × S).

3. Natural join (slide 10)

Joining on columns that have the same name is so common that SQL has a shorthand. Slide 10 compares the two forms:

SELECT A, R.B, C
FROM   R, S
WHERE  R.B = S.B;
SELECT A, B, C
FROM   R NATURAL JOIN S;
Natural join, R ⋈ S
A join that (1) matches rows on equality of every pair of columns with the same name, and (2) keeps only one copy of each such column. Here the only shared name is B, so the natural join is the equijoin on R.B = S.B with one B column: (1, x, 5) and (2, y, 6).

Because the two B columns are merged into one, the natural-join query writes plain B. In Oracle you are in fact not allowed to qualify it: SELECT R.B FROM R NATURAL JOIN S raises ORA-25155: column used in NATURAL join cannot have qualifier.

Natural join is convenient but fragile: it joins on whatever names happen to match. If someone later adds a column last_updated to both tables, the natural join silently starts requiring equal timestamps too. Oracle also accepts two explicit ANSI forms that you will meet in Lecture 09:

SELECT A, R.B, C FROM R JOIN S ON R.B = S.B;   -- condition written out (also: INNER JOIN)
SELECT A, B, C   FROM R JOIN S USING (B);      -- name the shared column(s) yourself

All three return the same two rows here. FROM R, S WHERE … (the slides' style) and FROM R JOIN S ON … are interchangeable for inner joins; use whichever your teacher writes, and be consistent.

4. The meaning of any SELECT–FROM–WHERE (slides 11–12)

Slide 11 generalises the idea to n tables. The meaning (the semantics) of

SELECT a1, a2, …, ak
FROM   R1, R2, …, Rn
WHERE  Conditions

is defined by nested loops, one loop per table in FROM:

Answer = {}
for x1 in R1 do
    for x2 in R2 do
        …
            for xn in Rn do
                if Conditions(x1, …, xn)
                    then Answer = Answer + {(a1, …, ak)}
return Answer

Each combination (x1, …, xn) is one row of R1 × … × Rn; the if is the WHERE filter; and the tuple added is the SELECT list (a projection, π in relational algebra). So the whole query is πa1…ak(σConditions(R1 × … × Rn)).

Note the + on slide 11. It means "append", so a row that is produced twice appears twice: SQL tables are bags (multisets), and a plain SELECT keeps duplicates. Slide 12 changes the query to SELECT DISTINCT and the + to ∪, set union, which adds a row only if it is not already there. DISTINCT turns the bag into a set.

Bag (multiset)
A collection in which the same element can occur several times; order does not matter. SQL query results are bags.
DISTINCT
Removes duplicate rows from the result, turning the bag into a set.

Summary: listing several tables in FROM forms their cross product: every row of one paired with every row of the other (m · n rows). A WHERE condition that compares columns of the two tables keeps only the matching pairs: that is a join, σC(R × S). Shared column names must be qualified (R.B). NATURAL JOIN joins on all same-named columns and keeps one copy of each. Any SELECT–FROM–WHERE means "nested loops over the FROM tables, test WHERE, output the SELECT list", producing a bag; DISTINCT makes it a set.
