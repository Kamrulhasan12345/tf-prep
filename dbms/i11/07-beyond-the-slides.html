Exam Topics Beyond the Slides: Advanced SQL

Some exam questions and model answers use SQL features that Lectures 08–11 do not teach: the WITH clause, analytic (window) functions such as RANK, views defined over joins, and hierarchical queries. This chapter teaches each briefly in Oracle syntax, with runnable examples, and works the restaurant view question from the banks.

1. The WITH clause (subquery factoring)

WITH name AS (subquery)
Defines a named temporary result (a common table expression, CTE) that the main query can use like a table, as often as it likes. It is a derived table with a name, written before the SELECT. Oracle has supported it since 9i.
WITH dept_total AS (
       SELECT DEPARTMENTID, SUM(SALARY) AS total
       FROM   EMPLOYEE
       WHERE  DEPARTMENTID IS NOT NULL
       GROUP BY DEPARTMENTID)
SELECT DEPARTMENTID, total
FROM   dept_total
WHERE  total > (SELECT AVG(total) FROM dept_total);

Without WITH, dept_total would have to be written out twice as a derived table (Chapter 6 of these notes did exactly that, because one question forbade WITH). WITH adds no power, only readability. Several question-bank answers use it; both forms earn full marks unless WITH is forbidden.

2. Analytic (window) functions

An aggregate with GROUP BY collapses each group to one row. An analytic function computes a value over a group of rows (a window) but keeps every row. The syntax is function(…) OVER (PARTITION BY … ORDER BY …).

AVG(SALARY) OVER (PARTITION BY DEPARTMENTID)
The department average, printed next to each employee. Solves "print each employee with the difference from his department average" without a derived table.
ROW_NUMBER() OVER (ORDER BY …)
1, 2, 3, … in the given order; ties get different numbers (arbitrarily).
RANK() OVER (ORDER BY …)
Ties share a rank and the next rank is skipped: 1, 2, 2, 4.
DENSE_RANK() OVER (ORDER BY …)
Ties share a rank and nothing is skipped: 1, 2, 2, 3. "Third highest value" = DENSE_RANK 3.

Analytic functions are computed after WHERE, GROUP BY and HAVING, so to filter on them, wrap the query in a derived table:

-- third highest salary (distinct values), with every employee who earns it
SELECT LASTNAME, SALARY
FROM  (SELECT LASTNAME, SALARY, DENSE_RANK() OVER (ORDER BY SALARY DESC) AS rnk
       FROM EMPLOYEE)
WHERE rnk = 3;

-- top earner(s) of each department
SELECT DEPARTMENTID, LASTNAME, SALARY
FROM  (SELECT e.*, RANK() OVER (PARTITION BY DEPARTMENTID ORDER BY SALARY DESC) AS r
       FROM EMPLOYEE e)
WHERE r = 1;

Oracle 12c also has the row-limiting clause ORDER BY … FETCH FIRST n ROWS ONLY (or WITH TIES, which keeps rows tied with the last one) and OFFSET k ROWS. Before 12c, top-N queries used the pseudo-column ROWNUM on an ordered subquery: SELECT * FROM (SELECT … ORDER BY SALARY DESC) WHERE ROWNUM <= 3 (ROWNUM is assigned before ORDER BY, so the subquery is essential). The playground does not support ROWNUM or WITH TIES.

3. Views over joins

View
A named, stored query: CREATE OR REPLACE VIEW name AS SELECT …. It stores no data; each time it is queried, its SELECT runs. It can join and aggregate, and it can then be queried like a table.
CREATE OR REPLACE VIEW emp_details AS
SELECT e.EMPLOYEEID, e.LASTNAME, j.JOBTITLE, d.DEPARTMENTNAME, e.SALARY
FROM   EMPLOYEE e
       JOIN JOB j             ON j.JOBID = e.JOBID
       LEFT JOIN DEPARTMENT d ON d.DEPARTMENTID = e.DEPARTMENTID;

SELECT DEPARTMENTNAME, COUNT(*) FROM emp_details GROUP BY DEPARTMENTNAME;

Updating through a view. INSERT, UPDATE and DELETE on a view must be translated into changes of the base tables. For a view over one table with no aggregates, DISTINCT or GROUP BY, that is straightforward. For a join view, Oracle allows a change only if it affects exactly one base table and that table is key-preserved in the view: every key of the base table is still a key of the view's result (each base row appears at most once in the view). In emp_details, EMPLOYEE is key-preserved (each employee appears once), so UPDATE emp_details SET SALARY = SALARY * 1.1 WHERE EMPLOYEEID = 104 is allowed; JOB and DEPARTMENT are not (a job appears once per employee holding it), so changing JOBTITLE through the view raises ORA-01779: cannot modify a column which maps to a non key-preserved table. Anything else needs an INSTEAD OF trigger, which tells Oracle explicitly what to do with the base tables. The question bank's question on inserting through a three-table join view (cust_balance) is worked in Lecture 05's beyond-the-slides chapter.

4. Hierarchical queries

A table with a foreign key to itself (EMPLOYEE.MANAGERID) stores a tree. Oracle's CONNECT BY walks it:

SELECT LEVEL, LPAD(' ', 2 * (LEVEL - 1)) || LASTNAME AS org_chart
FROM   EMPLOYEE
START WITH MANAGERID IS NULL                 -- the root(s): King
CONNECT BY PRIOR EMPLOYEEID = MANAGERID      -- children: rows whose MANAGERID is the parent's id
ORDER SIBLINGS BY LASTNAME;

LEVEL is the depth (1 for the root), which is why LEVEL is a reserved word in Oracle. CONNECT BY is Oracle-specific and the playground cannot run it. The standard alternative, which Oracle supports since 11g Release 2 and the playground runs, is a recursive WITH: an anchor query UNION ALL a step that joins the CTE to the table.

WITH chart (EMPLOYEEID, LASTNAME, lvl) AS (
       SELECT EMPLOYEEID, LASTNAME, 1 FROM EMPLOYEE WHERE MANAGERID IS NULL       -- anchor
       UNION ALL
       SELECT e.EMPLOYEEID, e.LASTNAME, c.lvl + 1                                 -- step
       FROM   EMPLOYEE e JOIN chart c ON e.MANAGERID = c.EMPLOYEEID)
SELECT lvl, LASTNAME FROM chart ORDER BY lvl, LASTNAME;

Exam questions

DB QB · 22-23 7b · 20 marks  |  BUET QBank · CSE 215 | L-2/T-1 | 2022–23 · 20 marks (SQL part)

A restaurant has provided a report listing, for each food item, its containing items (for packages, with quantities), its ingredients (for simple items, with unit cost and quantity), its marketed price, and its sales (buyer, date, quantity). For example: Chicken Burger (simple item): Chicken Patty 60 × 1, Lettuce 30 × 0.02, Pickle 5 × 4, Mayonnaise 100 × 0.02, Sause 70 × 0.01, marketed price 200, sales C1 01/02/24 2, C3 02/02/24 4, C8 02/02/24 1, C1 03/02/24 3. Fried Rice (simple item): Raw Rice 50 × 0.1, Egg 7 × 1, Oil 500 × 0.005, price 80, sales C4 02/02/24 1, C9 04/02/24 2. Set Menu 1 (package): Fried Rice 1, Vegetable 1, Chicken Steak 1, price 500, sales C2 01/02/24 3, C4 03/02/24 1, C1 04/02/24 4, C1 05/02/24 2. (Part (a) of the question asks for a relational schema normalized up to BCNF.)

(i) Using the schema created in (a), write a SQL query to create a view that contains the total cost of production of each food item. Cost of production depends on the total cost of ingredients (cost of ingredients = unit cost of ingredient × quantity of ingredients used) for simple items and the total cost of containing items (that are simple items) for packages.
(ii) Using the schema and the view, find the monthly profit for each food item. Here, profit = (marketed price − cost of production) × quantity sold in the month.

Show worked answer

Schema (the result of part (a), which belongs to the normalization chapters; each table is in BCNF with the underlined key):

Item        (item_name, item_type, price)            -- item_type 'S' simple / 'P' package
Ingredient  (ingr_name, unit_cost)
Recipe      (item_name, ingr_name, qty)              -- ingredients of simple items
PackageItem (package_name, simple_item, qty)         -- contents of packages
Sale        (item_name, buyer, sale_date, qty)

(i) Simple items: sum unit_cost × qty over the recipe. Packages: sum, over the contained simple items, qty × that item's cost, which is the first result again, so it appears as a derived table. UNION ALL puts both kinds into one view.

CREATE OR REPLACE VIEW item_cost AS
SELECT   r.item_name, SUM(r.qty * g.unit_cost) AS cost
FROM     Recipe r JOIN Ingredient g ON g.ingr_name = r.ingr_name
GROUP BY r.item_name
UNION ALL
SELECT   p.package_name, SUM(p.qty * s.cost)
FROM     PackageItem p
         JOIN (SELECT r.item_name, SUM(r.qty * g.unit_cost) AS cost
               FROM   Recipe r JOIN Ingredient g ON g.ingr_name = r.ingr_name
               GROUP BY r.item_name) s
         ON s.item_name = p.simple_item
GROUP BY p.package_name;

Costs: Chicken Burger 60 + 0.6 + 20 + 2 + 0.7 = 83.3; Fried Rice 5 + 7 + 2.5 = 14.5. The report gives no recipes for Vegetable and Chicken Steak, so the check below uses invented ones (Vegetable 21, Chicken Steak 111.4), making Set Menu 1 cost 14.5 + 21 + 111.4 = 146.9.

(ii) The report's dates (01/02/24 …) are read as DD/MM/YY, i.e. February 2024. Group the sales by item and month:

SELECT   s.item_name, TO_CHAR(s.sale_date, 'YYYY-MM') AS month,
         SUM((i.price - c.cost) * s.qty) AS profit
FROM     Sale s
         JOIN Item i      ON i.item_name = s.item_name
         JOIN item_cost c ON c.item_name = s.item_name
GROUP BY s.item_name, TO_CHAR(s.sale_date, 'YYYY-MM');

February 2024: Chicken Burger (200 − 83.3) × 10 = 1167; Fried Rice (80 − 14.5) × 3 = 196.5; Set Menu 1 (500 − 146.9) × 10 = 3531. (EXTRACT(YEAR FROM …) and EXTRACT(MONTH FROM …), as in the question bank's answer, also work in Oracle; the bank's view uses a WITH clause inside CREATE VIEW, which Oracle accepts too.)

Summary: WITH names a subquery so it can be reused (a readable derived table). Analytic functions (AVG … OVER, ROW_NUMBER, RANK, DENSE_RANK) compute over a window but keep every row; filter on them from an outer query; DENSE_RANK answers "n-th highest value". A view is a stored query; Oracle lets you modify a join view only through one key-preserved table, otherwise an INSTEAD OF trigger is needed. Oracle's CONNECT BY walks self-referencing hierarchies; recursive WITH is the portable equivalent.
