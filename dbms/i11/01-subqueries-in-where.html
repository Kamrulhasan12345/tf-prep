Subqueries in WHERE; ALL and ANY

A subquery is a query inside another query. This chapter covers slides 1–7: why "find the highest-paid employee" should not be answered with a hard-coded number, the scalar subquery that computes the number instead, the quantified comparisons >ALL, >=ALL, >ANY, <=ANY and friends, and IN / NOT IN, including the NULL trap. A tool lets you evaluate any x op ALL/ANY (set) yourself.

1. What is a subquery? (slides 2–3)

Slide 2 outlines the lecture: what a subquery is, subqueries in the WHERE clause, the comparisons >ALL, >ANY, >=ALL, <=ANY etc., and subqueries in the FROM clause.

Subquery (nested query, inner query)
A complete SELECT statement written in parentheses inside another statement (the outer query). It can appear in WHERE and HAVING (this chapter and the next two), in FROM (Chapter 4), in the SELECT list, and in INSERT, UPDATE and DELETE.

Slide 3 numbers the clauses of the outer query: (1) WHERE, (2) FROM. Read it as "a subquery placed in the WHERE clause (1) is a condition on the rows produced by FROM (2)": the WHERE clause can now ask questions whose answers come from another query. The running example (slide 4) is a small table Employee(id, dept, salary) with salaries 50,000, 55,000, 60,000 and 75,000.

2. The highest-paid employee (slides 5–6)

Find the employee(s) with the highest paid salary. Slide 5's "first thought" reads the maximum off the table and hard-codes it:

SELECT id FROM Employee WHERE salary = 75000;

It returns 5004, but it is wrong as a query: the moment salaries change, the number 75000 is stale, and the database cannot know where it came from. The query must compute the maximum. Slide 6 does that with a subquery:

SELECT id
FROM   Employee
WHERE  salary = (SELECT MAX(salary)
                 FROM   Employee);
Scalar subquery
A subquery that returns exactly one row with one column, so it can be used wherever a single value can (here, on the right of =). If it returned several rows, Oracle would raise ORA-01427: single-row subquery returns more than one row; if it returns no row, its value is NULL.

The inner query does not depend on the outer row, so it is evaluated once: MAX(salary) = 75000, and the outer query becomes the first-thought query, but with the value computed. Slide 6 also asks: suppose you are not allowed to use any aggregate function? That is what ALL is for.

3. Quantified comparisons: ALL and ANY (slide 7)

Slide 7 lists eight operators: > ALL, >= ALL, < ALL, <= ALL, > ANY, >= ANY, < ANY, <= ANY (and = and <> can be quantified too). Each compares one value with every value of a one-column subquery:

x op ALL (subquery)
TRUE if x op v is true for every value v the subquery returns. "x >= ALL (S)" means x is at least as big as everything in S.
x op ANY (subquery) (also written SOME)
TRUE if x op v is true for at least one value v. "x > ANY (S)" means x is bigger than something in S.
SELECT id
FROM   Employee
WHERE  salary >= ALL (SELECT salary
                      FROM   Employee);

A salary that is ≥ every salary, including itself, is the maximum. Only 75,000 qualifies, so the answer is 5004 again, without any aggregate. Note >= rather than >: with > ALL, 75,000 would have to be greater than itself, and no row would qualify.

Translating ALL and ANY

Quantified formEquivalent (when S has no NULLs and is not empty)
x > ALL (S)x > MAX(S)
x < ALL (S)x < MIN(S)
x > ANY (S)x > MIN(S)
x < ANY (S)x < MAX(S)
x = ANY (S)x IN (S)
x <> ALL (S)x NOT IN (S)

Two edge cases make ALL and the MAX/MIN versions differ, and both are popular exam traps:

  • Empty subquery. "x > ALL (empty)" is TRUE (there is no value to contradict it), and "x > ANY (empty)" is FALSE (there is no value to satisfy it). But MAX of nothing is NULL, so "x > (SELECT MAX …)" is UNKNOWN. Example: "products more expensive than all products the same company made before 1972" must include products of companies with no pre-1972 products when written with ALL.
  • NULL in the subquery. If S contains a NULL, then x > NULL is UNKNOWN, so "x > ALL (S)" can never be TRUE (at best UNKNOWN), and the row is dropped. Slide 7's query would return nothing if some employee's salary were NULL. MAX ignores NULLs, so the slide 6 version still works.

Try it: evaluate x op ALL/ANY (set)

Type a value for x and a comma-separated set (use NULL for a null; leave the set empty for an empty subquery).

4. IN and NOT IN

The most common subquery test is membership:

x IN (subquery)        -- same as x = ANY (subquery)
x NOT IN (subquery)    -- same as x <> ALL (subquery)

Example: makers who sell laptops, written with IN instead of a join: SELECT DISTINCT maker FROM Product WHERE model IN (SELECT model FROM Laptop). IN also works with a list of literals, type IN ('pc', 'laptop'), and with several columns at once, (dept, salary) IN (SELECT …) (next chapter).

Question (worked answer): the NOT IN NULL trap

Suppose some employee has MANAGERID NULL (King, in the HR schema). Query: "employees who are not managers":

SELECT LASTNAME FROM EMPLOYEE
WHERE  EMPLOYEEID NOT IN (SELECT MANAGERID FROM EMPLOYEE);

This returns no rows. NOT IN means "<> every value", and one of the values is NULL; 104 <> NULL is UNKNOWN, so the whole condition is at best UNKNOWN for every employee. Fix: exclude NULLs inside the subquery (WHERE MANAGERID IS NOT NULL) or use NOT EXISTS (Chapter 3), which does not have this problem. IN has no such trap: x IN (1, NULL) is TRUE when x = 1.

Summary: a subquery is a query in parentheses inside another query. A scalar subquery returns one value and replaces a hard-coded constant (salary = (SELECT MAX(salary) …)). x op ALL (S) must hold for every value of S, x op ANY (S) for at least one; >= ALL finds maxima without aggregates. ALL over an empty set is TRUE, ANY is FALSE; a NULL in S makes ALL and NOT IN never TRUE. IN = "= ANY", NOT IN = "<> ALL".
