Answering Ishrak sir's questions

This page skips the theory and covers how to write answers that get full marks. It includes every question type from Ishrak sir's half (Lec 01–12) and the storage and indexing lectures (Lec 13–15), from DB QB 2017–18 to 2024–25 and the older CSE 303 bank. Each card shows how to spot the type, the steps to write on paper, the full question, a model answer, and where marks get lost. The companion page for the other half is Answering Sukarna sir's questions.

How to drill each card (about 10–15 minutes): (1) read the template, (2) read the question in the grey box and write your answer on paper, (3) open Model answer just below it and compare, (4) check yourself against the red Marks lost by list. When you get stuck on a concept, follow the Practice link.

1. Eight rules for every answer in this half

  1. SQL: write the joins out in full. Use one alias per table and one join condition per link (n tables need n − 1 conditions). Most wrong SQL answers come from a missing join condition, which turns the query into a cross product.
  2. SQL: choose the pattern from the wording before you write. “no / not any” → NOT EXISTS (or NOT IN, when nothing can be NULL). “every / all” → NOT EXISTS … NOT EXISTS, or GROUP BY with a COUNT comparison. “more than the average of its own …” → a correlated subquery. “the most” → HAVING COUNT(*) >= ALL (…).
  3. ER: state your assumptions. Every scenario has gaps (can a book have many publishers?). An assumption you write down and stick to earns the marks; a silent guess looks like a mistake.
  4. ER: every relationship line needs a multiplicity and a participation. Mark the arrow or the 1/m label, and use a double line for total participation. Give keys underlined and a few attributes for every entity set.
  5. Drawings that change step by step (B+ trees, hashing, slotted pages, free lists): first state the parameters (n, split rule, bucket size, which bits), then draw the structure after every operation the question names.
  6. Name the convention when the textbook and the bank differ: leaf split 2 + 1 or 1 + 2, borrow first or merge first, first bits or last bits, average seek of ⅓ the distance or ½ the maximum. A stated convention gets full marks.
  7. Number questions: write the formula, then the numbers put in, then the result with units (ms, blocks, bytes).
  8. “Explain / compare” questions: use a comparison table (rows = properties, columns = the things compared) plus one small example. A table is quicker to write and easier to mark than paragraphs.

BUET QBank · CSE 303 | L-3/T-1 | 2012–13 · 5 marks

What are the three types of relations in SQL?

READY ANSWERS
  1. DBMS over a file system (one point per property, each with an example): less redundancy and inconsistency; data independence (programs survive schema changes); easy ad-hoc queries; integrity constraints enforced centrally; atomicity and recovery after crashes; concurrent access without anomalies; security and access control.
  2. Ideal DBMS requirements: persistent storage, a query language, a data model and schema, transactions (ACID), concurrency control, security, recovery. Entity: a thing with independent existence (a student); attribute: a property of it (name, CGPA).
  3. Keys: superkey = any set of attributes that identifies a row; candidate key = a minimal superkey; primary key = the candidate key chosen for identification. Example: Student(id, email, name): superkeys {id}, {id, name}, {email}; candidate keys {id}, {email}; PK id. Should a PK carry meaning? No: meaningful values change (a phone number, a name), and a change has to ripple through every foreign key. Use a stable surrogate key.
  4. Three levels of abstraction (why: data independence): physical (how data is stored: files, indexes), logical / conceptual (which tables and constraints exist), view / external (what each user sees). Changing a lower level without changing the one above = physical / logical data independence.
  5. 2-tier vs 3-tier: 2-tier: client application → database server (the client holds the business logic). 3-tier: client (browser) → application server (business logic) → database server. 3-tier is more secure (clients never touch the database), scales better and suits the web. Draw both as stacked boxes.
  6. Derived attributes give current values when not stored (23-24 2b): age computed from date_of_birth each time is always right; a stored age is wrong after the next birthday unless every row is updated. Store a derived value only when it is expensive to compute, and keep it correct with a trigger.
  7. Schema vs data: the schema is the structure (changes rarely); the data (instance) is the contents at one moment (changes constantly). DDL defines the schema (CREATE, ALTER, DROP); DML works on the data (SELECT, INSERT, UPDATE, DELETE). Three kinds of relations in SQL: stored tables, views, temporary tables (query results).

BUET QBank · CSE 303 | L-3/T-1 | 2010–11 · 10 marks

Describe with an example, the object identity and reference types in SQL. How can you process queries using reference type?

READY ANSWERS
  1. DTD → structure + sample XML: read each <!ELEMENT X (…)> as “X contains …”: * = zero or more, + = one or more, ? = optional, #PCDATA = text. Describe the tree in words, then write a sample file whose elements nest exactly in that order, using every element at least once.
  2. MapReduce: the input is split across machines. Map turns each record into (key, value) pairs; the framework shuffles them so that all values for one key reach the same reducer; Reduce combines each key's values. Example: word count (map emits (word, 1), reduce sums). The framework restarts failed tasks.
  3. Semi-join R₁ ⋉ R₂ across sites: send πC,D(R₂) from S₂ to S₁; compute R₁ ⋉ that projection at S₁ (the rows of R₁ that will join); send only those rows to S₂ and do the join there. It saves network transfer when few rows match. Parallel join: hash-partition both relations on the join attributes across k processors; each processor joins its own partition pair.
  4. Distributed transaction over several sites: two-phase commit. The coordinator sends PREPARE; each site votes ready or abort; COMMIT is sent only if all vote ready, otherwise ABORT.
  5. Object identity / REF types (SQL:1999): each row of a typed table gets an object identifier; another table stores a REF to it instead of a foreign key, and queries follow it with -> (e.g. SELECT s.dept->name FROM student s), with no explicit join needed.

TEMPLATE (for each part i, ii, iii …)

  2. Pick the pattern from the wording (rule 2 above). Underline the keyword in the question that decided it.
  3. Write the query with aliases, one condition per line, and the join conditions first.
  4. Check the traps: DISTINCT when a join can repeat a row; GROUP BY must list every non-aggregate SELECT column; conditions on aggregates go in HAVING; NOT IN breaks if the subquery can return NULL.

The question

DB QB · 21-22 1a · 25 marks  |  BUET QBank · CSE 215 | L-2/T-2 | 2021–22 · 25 marks

Consider the Toys database of a retail store. It has the following database schema: Toys (id, name, color, min_age, weight, number_available), Client (id, name, age, address, city), Request (client id, toy id). Toys records information about all of the toys in the store. Each toy has a unique integer id. Attributes name and color are strings that describe the toy; min_age, weight and number_available are integers giving the minimum age a child should be to use the toy, the weight of the toy in pounds, and how many are currently available in the store. Client stores information about each of the clients: a unique integer id, strings with the client's name, address and city, and an integer age. Request has a pair of integers indicating that a particular client has requested a particular toy. You should assume that all entries in all of the tables are not null. Answer the following:

i. Give the name of the clients who do not have any request at the moment for any toys.
ii. List the name of the toys that have weight more than the average weight of the toys with the same color.
iii. List the name of the requesting clients who have to wait because the toys are currently unavailable at the store.
iv. List all of the requests where age of the client is less than the min_age listed for the toy. The answer should include the client id, client name, and the toy id. The results should be sorted by client name.
v. Give the id and name of the "most popular" toy. The most popular toy is the one that has more requests than all others. If there is a tie so there is more than one toy with the maximum number of requests, give the ids and names of all of these toys.

Model answer

Links: Request.client_id = Client.id, Request.toy_id = Toys.id.

-- i. no request at all (anti-join; all NOT NULL, so NOT IN is safe) SELECT name FROM Client WHERE id NOT IN (SELECT client_id FROM Request); -- ii. heavier than the average of the same colour (correlated) SELECT t1.name FROM Toys t1 WHERE t1.weight > (SELECT AVG(t2.weight) FROM Toys t2 WHERE t2.color = t1.color); -- iii. waiting = requested a toy with nothing in stock SELECT DISTINCT c.name FROM Client c, Request r, Toys t WHERE c.id = r.client_id AND r.toy_id = t.id AND t.number_available = 0; -- iv. SELECT c.id, c.name, r.toy_id FROM Client c, Request r, Toys t WHERE c.id = r.client_id AND r.toy_id = t.id AND c.age < t.min_age ORDER BY c.name; -- v. most popular, ties included SELECT t.id, t.name FROM Toys t, Request r WHERE t.id = r.toy_id GROUP BY t.id, t.name HAVING COUNT(*) >= ALL (SELECT COUNT(*) FROM Request GROUP BY toy_id);

DB QB · 24-25 7b · 8 marks  ·  BUET QBank · CSE 215 | L-2/T-1 | 2024–25 · 8 marks

Write the general procedure to convert ternary relationship to binary relationships.

Model answer (24-25 7b: ternary → binary)
  1. Replace R(A, B, C) with a connecting entity set E (a surrogate key, or weak with key (a, b, c)).
  2. Move R's attributes to E.
  3. Add binary relationships E → A, E → B, E → C: each many-to-one, with total participation of E.
  4. For each triple (a, b, c) of R, create one e linked to a, b and c.
  5. Constraints such as “A, B → C” cannot be drawn any more: write a design note and enforce it with UNIQUE (a, b) on E's table.
  6. Do not replace R with three pairwise relationships: the pairs can be recombined into triples that never happened.

Explain the concept of total and partial participation of entities of the entity set in the relationship set using an example ER diagram.

Model answer (24-25 7d: total and partial participation)

Total = every entity takes part at least once (double line, minimum 1). Partial = it may take part zero times (single line, minimum 0).

Example: Employee — manages — Department. Employee is partial (not everyone manages); Department is total (every department has a manager). worksIn: Employee total, Department partial (a new department may have no staff yet).

In tables, total participation becomes a NOT NULL FK (when the FK is on that side). Participation is independent of multiplicity: total plus “at most one” means exactly one.

READY ANSWERS
  1. Access time and its implication: seek + rotational latency + transfer, about 10 ms against nanoseconds for RAM. So the DBMS counts block I/Os as its cost, keeps related data in the same or neighbouring blocks, caches blocks in a buffer, and prefers sequential reads.
  2. RAID levels: 0 = striping, no redundancy; 1 = mirroring (half the space, fast reads, 2 writes); 4 = block striping + a dedicated parity disk (that disk is a bottleneck on writes); 5 = parity rotated across the disks; 6 = two redundant blocks, survives two failures. RAID 1 for write-heavy workloads such as logs; RAID 5 for read-mostly, large data where space matters.
  3. RAID 4 update policy: new P = old P ⊕ old B ⊕ new B: read the old block and old parity, write both (4 I/Os, independent of the number of disks).
  4. Performance: place related blocks on the same cylinder, use several disks / striping, mirror, schedule the arm (elevator), prefetch / double-buffer. Elevator pros: high throughput, no starvation; cons: requests at the ends wait longer, and it is little better than FIFO when the load is light.
  5. Failures: intermittent (retry), media decay (checksums), write failure (stable storage), disk crash (RAID or backup + log). Stable storage: two copies on separate disks; write copy 1, verify, then write copy 2; read either one with a valid checksum.
  6. Buffer / work area / disk: INPUT(X) copies disk → buffer; READ(X, t) copies buffer → the transaction's local variable; WRITE(X, t) local → buffer; OUTPUT(X) buffer → disk.

Card 30 · B+ tree sizing: fan-out, height, blocks read

Asked: 24-25 4b (15) · 22-23 8b (5) · CSE303

TEMPLATE
  1. Fan-out: n·pointer + (n − 1)·key ≤ node size → the largest n.
  2. Leaves = ⌈records ÷ (n − 1)⌉; each level above = ⌈below ÷ n⌉ until you reach 1. Count the levels (best case, full nodes).
  3. Worst case uses half-full nodes: leaves with ⌈(n − 1)/2⌉ keys, internal nodes with ⌈n/2⌉ children, a root with 2.
  4. Point lookup = height (root to leaf). Range = height + the extra leaves (⌈matches ÷ keys per leaf⌉ − 1).
  5. Hash index: 1 block + overflow blocks; no range queries.

The question

DB QB · 21-22 7a · 15 marks  /  BUET QBank · CSE 215 | L-2/T-2 | 2021–22 · 15 marks

"Without bitmap index scan strategy, secondary index scan can sometimes perform worse than linear file scan." Justify or criticize this statement with proper explanation.

Model answer

The statement is correct. A plain secondary-index scan does one random block access per matching record; a linear scan reads each block once, sequentially.

Numbers: 10,000 blocks, tS = 4 ms, tT = 0.1 ms, 20,000 matches. Linear: 4 + 10,000 × 0.1 = 1,004 ms. Index: (3 + 20,000) × 4.1 ≈ 82,012 ms. Break-even ≈ 242 matches.

Bitmap index scan: set one bit per needed block, then read those blocks in physical order, once each. It is never much worse than the better of the two, and several conditions can be ANDed first.

Card 34 · Hashing: extendible, linear, static

Asked: 21-22 6a (15) · 17-18 3a (21) · CSE303 (six times)

TEMPLATE
  1. A table of key → h(key) → binary. State whether you use the first or the last bits.
  2. Extendible: global depth i (directory size 2i), a local depth per bucket. On overflow: if local depth < i, split the bucket only; if local depth = i, double the directory first. Redistribute on the next bit.
  3. Linear: n buckets, i bits, r records. Bucket = last i bits m if m < n, else m − 2i−1. After an insert, if r exceeds the threshold (e.g. 1.7n), add bucket n and split the bucket it mirrors; when n exceeds 2i, i++.
