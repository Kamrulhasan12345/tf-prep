Exam Topics Beyond the Slides: ACID, Transaction States, Buffers and Isolation Levels

The question banks for this lecture also ask about the ACID properties, the states of a transaction, how data moves between disk, buffers and a transaction, and the SQL isolation levels. The Lec 04 slides do not teach these, but the questions keep appearing, so each topic is taught briefly here and then every such question is answered.

1. Transactions and the ACID properties

A transaction is a sequence of database operations that the system treats as one logical unit of work, such as "transfer 100 taka from account A to account B": read A, subtract 100, write A, read B, add 100, write B, commit. The DBMS promises four properties for every transaction, known by their initials as ACID.

Atomicity ("all or nothing")
Either all of the transaction's operations take effect, or none of them do. If it fails half-way, its partial changes are undone. Enforced by the recovery manager using the log (undo), and by rollback on abort.
Consistency
A transaction run alone on a consistent database leaves it consistent: all integrity constraints (keys, foreign keys, CHECK constraints, business rules such as "A + B is unchanged by a transfer") hold before and after. Ensured by the application programmer writing correct transactions and by the DBMS checking declared constraints.
Isolation
Concurrent transactions do not see each other's intermediate states; the result of a concurrent execution is as if the transactions ran one at a time in some order (serializability). Enforced by the scheduler (concurrency control: locking, timestamps, validation).
Durability
Once a transaction has committed, its effects survive any later failure (crash, power loss). Enforced by the recovery manager: the commit record and the changes are in the log on stable storage before the commit is acknowledged, and recovery redoes committed work.

Why concurrent execution needs them. Running transactions concurrently raises throughput (one transaction uses the CPU while another waits for disk) and lowers waiting time. But interleaving creates anomalies that a serial execution never has: lost updates (two transfers both read A = 500, each subtracts, the second write overwrites the first), dirty reads (Chapter 1), unrepeatable reads (a value changes between two reads of the same transaction), and phantoms (new rows appear in a repeated query). Isolation rules these out; atomicity makes sure an aborted transaction (including one killed by the scheduler for a deadlock) leaves no trace; durability makes sure a crash in the middle of many interleaved transactions loses none of the committed ones; and together they preserve consistency.

2. Transaction states

The textbook used for the first half of the course (Silberschatz) describes the life of a transaction as five states:

Active
The initial state; the transaction stays here while it executes its operations.
Partially committed
After its final statement has executed. Its output may still be only in main memory, so a failure could still prevent it from committing.
Committed
After successful completion: enough information (the commit log record) is on stable storage that its updates can be recreated after a crash.
Failed
After it is discovered that normal execution can no longer proceed (logical error, constraint violation, deadlock victim, system failure).
Aborted
After the transaction has been rolled back and the database restored to its state before the transaction started. The system then either restarts it (if the cause was not its own logic, for example a deadlock or hardware failure) or kills it (internal logical error).

3. Disk, buffers and the transaction's workspace (textbook §17.1)

Data lives in three places: the database on disk, buffers in main memory (a pool of disk blocks managed by the buffer manager), and the transaction's own local workspace (its program variables). Four primitive operations move data between them:

OperationMovesIssued by
INPUT(X)disk block containing X → bufferbuffer manager
READ(X, t)X in buffer → local variable t (does INPUT(X) first if X's block is not in a buffer)transaction
WRITE(X, t)local variable t → X in buffer (INPUT(X) first if needed). The buffer is now "dirty"; the disk is unchanged.transaction
OUTPUT(X)buffer containing X → diskbuffer manager (at its own time, or when the log/recovery rules require)

The key point for this lecture: a WRITE changes only the buffer. Another transaction reading X reads the buffer, which is why dirty data "may be in buffers, on disk, or both" (Chapter 1). OUTPUT happens later and independently, which is why recovery needs the log.

4. SQL isolation levels (textbook §6.6)

Full serializability costs concurrency, so SQL lets a transaction choose a weaker isolation level, declared with SET TRANSACTION ISOLATION LEVEL …. The levels are defined by which anomalies (phenomena) they allow:

READ COMMITTEDnopossiblepossibleX locks to commit (strict); S locks released right after each read

SERIALIZABLE (default in the standard)nononorigorous 2PL plus locks on ranges / predicates
Non-repeatable (unrepeatable) read
T reads a row, another transaction updates it and commits, and T reads the row again and sees a different value.
Phantom
T runs a query twice; between the runs another transaction inserts (or deletes) rows satisfying the query's condition and commits, so the second run sees new "phantom" rows.

DB QB · 20-21 2c · 5 marks  |  BUET QBank · CSE 215 | L-2/T-2 | 2020–21 · 5 marks

Explain ACID properties of transaction with an example.

Show worked answer

Example transaction T: transfer 100 from A to B. Initially A = 500, B = 200, total 700.

T: read(A); A := A - 100; write(A); read(B); B := B + 100; write(B); commit
  • Atomicity: if the system crashes after write(A) but before write(B), A = 400 and B = 200 and 100 has vanished. Atomicity requires that the recovery manager undo write(A) (using the old value 500 from the log), so either both writes happen or neither.
  • Consistency: the rule "A + B is unchanged by a transfer" holds before (700) and after (400 + 300 = 700). Writing T correctly is the programmer's job; declared constraints (e.g., CHECK (balance ≥ 0)) are enforced by the DBMS, which aborts T if they fail.
  • Isolation: another transaction that computes A + B between write(A) and write(B) would see 400 + 200 = 600, a state that never "officially" existed. The scheduler (e.g., strict 2PL) makes it wait until T commits, so the result is as if the two ran one after the other.
  • Durability: once T commits and the user is told "transfer done", A = 400 and B = 300 must survive a crash a moment later, even if the buffers had not yet been written to disk. The commit record and the new values are in the log on disk, and recovery redoes them.

The question bank's answer is correct. It also draws a state diagram, which is covered by the transaction-states question below.

DB QB · Jan 20 1a · 10 + 5 marks  |  BUET QBank · CSE 303 | L-3/T-1 | 2016–17 · 8 marks (also 2017–18, 2018–19)

Explain the ACID properties of a transaction with an example. Why are these properties essential for the concurrent execution of transactions? (CSE 303 2016–17: "Briefly explain each of the ACID properties in DBMS.")

Show worked answer

The properties (with the transfer example of the previous question): Atomicity, all of T's actions happen or none (undo on failure, by the recovery manager); Consistency, T takes a consistent database to a consistent one (A + B preserved; programmer plus constraint checking); Isolation, concurrent execution is equivalent to some serial one (scheduler); Durability, committed effects survive failures (log on stable storage, redo).

Why they are essential for concurrency. The DBMS interleaves the actions of many transactions to use the CPU and disks in parallel. Without the properties, interleaving would produce:

  • Lost update (needs isolation): T1 and T2 both read A = 500, T1 writes 400, T2 writes 450; T1's withdrawal is lost. Serializable scheduling forbids this.
  • Dirty read and cascading effects (needs isolation and atomicity): T2 reads T1's uncommitted A, then T1 aborts (it may even be aborted by the scheduler itself as a deadlock victim). Atomicity must erase T1, and the scheduler must keep T2 from building on its value (ACR / strict 2PL, Chapters 2–3).
  • Inconsistent analysis (isolation): a report summing all balances while transfers run sees money "in flight".
  • Crash with many transactions in progress (atomicity + durability): after the crash, the half-done transactions must be undone and every committed one preserved, otherwise the interleaved state is meaningless. The recovery manager can do this only if the schedule is recoverable.

Consistency is the goal; atomicity, isolation and durability are what let the system keep it while transactions overlap and fail. The question bank's answer is correct.

BUET QBank · CSE 303 | L-3/T-1 | 2013–14 · 8 marks  |  BUET QBank · CSE 303 | L-3/T-1 | 2011–12 · 12 marks

(2013–14) What do you mean by the ACID properties of a DBMS? Give real-life examples (one for each property) showing the necessity of these properties.
(2011–12) What do you mean by the ACID properties in a DBMS? Give one example of each property of the ACID.

Show worked answer

ACID: the four guarantees a DBMS gives every transaction (definitions in section 1). One real-life example each:

  • Atomicity, ATM withdrawal/transfer: moving 500 from A to B is two updates. If the power fails after the debit, atomicity rolls the debit back, so money is not destroyed.
  • Consistency, bank constraint: rule "balance ≥ 0" (a CHECK constraint). A withdrawal of 500 from an account holding 300 would violate it, so the transaction is rejected and aborted, and the database never records −200.
  • Isolation, airline seat booking: two customers try to book the last seat at the same time. Without isolation both read "1 seat free" and both book it. With isolation (e.g., the first booking holds an exclusive lock on the seat row until commit) the second sees the seat taken.
  • Durability, online payment: the shop shows "payment successful", then the server crashes. Durability guarantees that after restart the order and payment are still recorded, because the commit record was on disk before the success message.

The question bank's answers are correct.

BUET QBank · CSE 303 | L-3/T-1 | 2012–13 · 5 marks

Which two ACID properties are maintained by the Recovery Manager of a DBMS?

Show worked answer

Atomicity and durability.

  • Atomicity: after a crash (or an abort) the recovery manager undoes the changes of every transaction that did not commit, using old values in the undo or undo/redo log, so incomplete transactions leave no trace.
  • Durability: it redoes (or has already forced to disk, depending on the logging method) the changes of every transaction whose commit record is in the log, so committed work survives even if those changes were only in buffers at the time of the crash.

Isolation is maintained by the scheduler (concurrency-control manager), and consistency by correct transactions plus integrity checking. The question bank's answer is correct.

BUET QBank · CSE 303 | L-3/T-1 | 2010–11 · 5 marks

Explain the transaction states with the state diagram.

Show worked answer

The diagram is the animation in section 2. The states and transitions:

  • Active → Partially committed when the last statement has executed.
  • Partially committed → Committed when the commit log record has been written to stable storage, so the updates can be reconstructed after any crash.
  • Active → Failed on an error: constraint violation, user abort, deadlock victim, system failure.
  • Partially committed → Failed if a failure occurs before the commit record reaches stable storage (for example, the log write fails or the system crashes).
  • Failed → Aborted after rollback: all the transaction's changes are undone. Then the system restarts it (if the failure was external, e.g., deadlock or hardware) or kills it (if its own logic is wrong).

Committed and aborted are the terminal states. Note: the question bank's answer says a committed transaction has "all its updates permanently stored in non-volatile storage". Strictly, committing only requires the log (including the commit record) to be on stable storage; the data blocks themselves may be written later, and redo recreates them after a crash.

BUET QBank · CSE 215 | L-2/T-2 | 2020–21 · 10 marks

Show the relationship among memory buffer, transaction work area and disk storage. Explain how data A is read from disk for a transaction and data B is written to the disk for a transaction.

Show worked answer

The relationship is drawn in the animation of section 3: disk ⇄ buffer via INPUT/OUTPUT (buffer manager), buffer ⇄ transaction work area via READ/WRITE (transaction). A transaction never touches the disk directly.

Reading A: the transaction issues READ(A, t). If the block containing A is not in a buffer, the buffer manager first performs INPUT(A), copying the block from disk into a free buffer frame (evicting another block if needed). Then the value of A is copied from the buffer into the local variable t in the transaction's work area.

Writing B: the transaction computes the new value in a local variable u and issues WRITE(B, u). If B's block is not in a buffer, it is first brought in with INPUT(B). The value is copied from u into the buffer, which is now dirty; the disk still holds the old B. Later the buffer manager issues OUTPUT(B), copying the block to disk, either when it needs the frame, at a checkpoint, or when the logging rules require it (e.g., redo logging writes the log and commit record first; undo logging forces data before the commit record). Before that OUTPUT, the log record for the change must already be on disk (write-ahead logging), so that a crash can be recovered from.

The question bank's answer is correct.

DB QB · 21-22 6c · 15 marks  |  BUET QBank · CSE 215 | L-2/T-2 | 2021–22 · 15 marks

The SQL standard defines three weak isolation levels: dirty reads, read committed, and repeatable reads. Compare these three levels with illustrative examples.

Show worked answer

"Dirty reads" is the textbook's name for READ UNCOMMITTED. All three are weaker than SERIALIZABLE; they differ in which anomalies they allow (table in section 4). Account A starts at 100.

READ UNCOMMITTED (dirty reads allowed). T2 may read data written by uncommitted transactions.

T1T2 (read uncommitted)
write(A) = 500
read(A) → 500 (dirty)
abort (A back to 100)
commit, having used 500

READ COMMITTED. T2 reads only committed values, so the dirty read above is impossible (T2 waits for T1's exclusive lock, or sees the last committed version). But reading the same item twice can give different answers:

T1T2 (read committed)
read(A) → 100
write(A) = 500; commit
read(A) → 500 (non-repeatable read)

REPEATABLE READ. Rows T2 has read stay locked (or its snapshot is kept) until T2 commits, so T1's update of A must wait and T2 sees 100 both times. But new rows can still appear:

T1T2 (repeatable read)
SELECT COUNT(*) FROM account WHERE branch = 'Dhaka' → 5
INSERT a new Dhaka account; commit
same query → 6 (phantom)

Comparison. Read uncommitted allows dirty reads, non-repeatable reads and phantoms; read committed prevents dirty reads only; repeatable read also prevents non-repeatable reads but allows phantoms; only serializable prevents all three. Each stronger level holds more locks for longer, so it gives more consistency and less concurrency. In GMUW's terms, read committed corresponds to strict locking of writes with short read locks, and repeatable read to rigorous locking of the tuples read. The question bank's answer is correct.

Summary: ACID = atomicity (all or nothing, recovery manager), consistency (constraints preserved, programmer + DBMS checks), isolation (serializable interleaving, scheduler), durability (committed work survives, recovery manager). A transaction moves Active → Partially committed → Committed, or into Failed → Aborted (then restart or kill). Transactions READ/WRITE buffers; the buffer manager does INPUT/OUTPUT to disk. SQL's weaker isolation levels trade anomalies (dirty reads, non-repeatable reads, phantoms) for concurrency.
