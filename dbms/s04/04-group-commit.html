Group Commit

Strict 2PL makes every transaction wait for a disk write of its commit record before it can release its locks. Group commit removes that wait without ever allowing a harmful dirty read. This chapter states the two rules, animates the slide's example including every crash case, and answers the slide's "Why?".

1. The cost that group commit removes

Under strict 2PL (Chapter 3), a transaction may release its exclusive locks only after its COMMIT log record has been flushed (written from the log buffer in memory to the log on disk). A disk write takes milliseconds, while the transaction's real work may take microseconds. If every commit waits for its own disk write, other transactions sit waiting for the locks, and the disk does one small write per transaction.

Log buffer
The area of main memory where new log records are appended before they are written to disk. Records in the buffer are lost in a crash.
Flush
Writing log blocks from the buffer to disk. Only flushed records survive a crash.

2. The group commit rule (slide 13)

The observation: we can avoid reading dirty data even without flushing each commit record immediately, as long as log records are flushed in the order they were written. Then locks may be released as soon as the commit record is in the log buffer.

Group commit
  1. Do not release locks until the transaction has finished and its COMMIT record at least appears in the log buffer.
  2. Flush log records (log blocks) to disk in the order in which they were created. Typically many transactions' records are flushed together, later, as one group.

Advantage: no transaction needs an immediate flush at commit. Locks are released earlier, and one disk write carries the commit records of many transactions. For example, if a flush takes 10 ms and 50 transactions finish within that time, one write commits all 50, instead of 50 writes taking 500 ms of disk time. The slide notes that Oracle, MySQL/InnoDB and Microsoft SQL Server all use group-commit-style log flushing.

Durable commit vs NOWAIT commit (the slide's "compare"): in a durable commit, the system tells the application "committed" only after the commit record is on disk; with group commit the application waits for the group's flush, but locks are already free. In a NOWAIT (asynchronous, "delayed durability") commit, the application is told "committed" immediately, before the flush. That is faster still, but a crash can lose transactions the user was told had committed. Group commit itself never loses a reported commit; NOWAIT trades durability for speed.

3. The slide's example, step by step (slide 14)

T1 writes X, finishes, and writes its COMMIT record into the log buffer. Following rule 1 it releases its lock on X at once. T2 then reads X, finishes and writes its own COMMIT record, which lands in the buffer after T1's. At this moment neither transaction is committed in the strict sense, because neither commit record is on disk, and T2 has read a value whose writer is not yet durably committed.

Slide 14: when T1 is not committed on disk, T2 is not committed either. Why?

T2 read X only after T1 released its lock, and T1 released the lock only after its COMMIT record was in the log buffer (rule 1). T2 wrote its own COMMIT record later still, so it sits after T1's in the log. Log records reach disk in the order they were created (rule 2). So T2's commit record cannot be on disk unless T1's already is. Contrapositive: if T1's is not on disk, T2's is not on disk, and the recovery manager aborts both. T2's read of an uncommitted value then has no effect on the database, so in effect there was no dirty read.

The two cases the recovery manager can find (textbook, Example 19.5):

  1. T1 is committed on disk. Then, whether or not T2 also is, T2 read X from a committed transaction. Nothing is wrong.
  2. T1 is not committed on disk. Then T2 is not either; both are rolled back, and the database is as if neither ran.

The animation's last frames show what happens if rule 2 is broken, for example because the buffer manager decides to write the block holding T2's commit record early to reuse the buffer. Then a crash can leave T2 committed and T1 not. T2's effect is permanent but based on a dirty read of X. This is exactly why the rule insists on flushing in creation order. Like the recoverable-schedule requirement of Chapter 2, group commit guarantees there is never a harmful read of dirty data.

4. When is a transaction really committed?

Group commit shows that "committed" covers several states. A transaction can (a) have finished its work, (b) have its COMMIT record in the log buffer, (c) have that record on the log disk, and (d) have it copied to an archive (a backup). A crash loses transactions in state (b); a media failure of the log disk can even lose those in state (c) that are not yet archived. Without failures all these states lead to the same outcome, but when reasoning about recovery the difference matters. In this lecture, "committed" means state (c).

Quick check

Summary: group commit lets a transaction release its locks once its COMMIT record is in the log buffer, provided log records are flushed to disk in the order they were created, usually many at once. A later reader's commit record then always follows its writer's, so either the writer is durably committed or both are rolled back: dirty reads never do harm, and no transaction waits for its own disk write. Flushing out of order would break this.
