Deadlocks: Timeouts and the Waits-For Graph

Locking makes transactions wait, and waiting in a circle is a deadlock. This chapter defines deadlock, covers the two simplest tools against it (timeouts and the waits-for graph), proves why a cycle means deadlock, animates the slides' four-transaction example, and gives you a waits-for-graph builder for any sequence of lock requests.

1. What a deadlock is (slide 15)

Deadlock
A situation where each of several transactions is waiting for a resource (here, a lock) held by one of the others, so none of them can make progress. (The slide's "held one on of the others" is a typo for "held by one of the others".)

Without outside help a deadlock lasts forever: every transaction in it is waiting, and the only events that could free a lock are actions of the waiting transactions themselves. The slide recalls two ways we have already met deadlocks:

(a) Two 2PL transactions locking in opposite orders
(b) Two shared locks both upgrading

In (a), each transaction holds one element and needs the other's. 2PL forbids releasing a lock and then taking another, so neither can back off. In (b), both hold a shared lock on A and both want to upgrade it to exclusive; each upgrade must wait until the other's shared lock goes away, which never happens.

Two approaches

  • Deadlock detection and treatment: allow deadlocks to happen, detect them, and fix them by rolling back (aborting and restarting) at least one transaction. When a deadlock exists, it is generally impossible to let all its transactions continue, so a rollback is unavoidable.
  • Deadlock prevention: manage transactions so that a deadlock can never form, by allowing only "conservative" schedules. (The slide writes "conversative".) Chapters 6 and 7 cover the prevention methods.

2. Detection by timeout (slide 16)

The simplest method: put a limit on how long a transaction may be active (a transaction timeout), or on how long it may wait for one lock (a lock timeout). A transaction that exceeds the limit is assumed to be deadlocked and is rolled back.

The numbers make it work. If typical transactions take about 1 ms, a timeout of 30 seconds is 30,000 times longer than normal, so it will essentially only hit transactions that are stuck. When one deadlocked transaction times out and rolls back, it releases its locks, and the others in the deadlock may then finish before their own timeouts.

The weaknesses (textbook §19.2.1): a deadlock is noticed only after the full timeout, and the transactions in a deadlock usually started at about the same time, so after one is rolled back others may also time out even though they are no longer deadlocked (spurious timeouts). A genuinely long transaction can also be killed by mistake.

The slide says major DBMSs support timeouts but set them to 0 (meaning unlimited) by default. That is PostgreSQL's convention (lock_timeout, transaction_timeout, default 0 = disabled). Other systems differ, for example MySQL/InnoDB's innodb_lock_wait_timeout defaults to 50 seconds. All of them rely mainly on the waits-for graph below, with timeouts as a backstop.

3. The waits-for graph (slides 17–18)

Waits-for graph
A directed graph with a node for each transaction that currently holds a lock or is waiting for one, and an edge (arc) T → U whenever there is some element X such that: (1) U holds a lock on X, (2) T is waiting for a lock on X, and (3) T cannot get its lock on X in the mode it wants unless U first releases its lock on X.

Read T → U as "T waits for U". Condition 3 matters with lock modes: if U holds a shared lock and T wants a shared lock, T does not wait for U, so there is no edge. The lock table (from the locking lecture) already records holders and waiters for each element, so the graph can be built from it. Oracle, SQL Server, MySQL and PostgreSQL all use variants of this graph; detection typically runs periodically, for example every 5 seconds.

Theorem: there is a deadlock if and only if the waits-for graph has a cycle

Cycle ⇒ deadlock. Every transaction on a cycle waits for the next one on the cycle. None of them can run until its successor releases a lock, which needs the successor to run first. Going around the cycle, no transaction on it can ever make progress.

No cycle ⇒ no deadlock. A finite directed graph with no cycle has at least one node with no outgoing edge: a transaction that is waiting for nobody. It can run to completion and release its locks, which deletes all edges into it. The remaining graph still has no cycle, so again some transaction is free, and so on until every transaction has finished. (This is the argument behind topological sorting.)

Transactions that are not on a cycle but wait (directly or through others) for a transaction on a cycle are also stuck, even though they are not part of the deadlock itself.

Detection versus prevention with the graph

  • Detection: let waits happen; periodically search the graph for cycles; roll back a victim on each cycle.
  • Prevention (the textbook's choice): maintain the graph at all times, and whenever a lock request would make the requester wait and thereby create a cycle, roll back that transaction immediately. The slide calls this aggressive: a cycle check on every wait is expensive when the graph is large.

4. The slides' example (slides 19–20, textbook Example 19.9)

Four transactions each read one element and write another, using a single lock mode:

T1: l1(A); r1(A); l1(B); w1(B); u1(A); u1(B);
T2: l2(C); r2(C); l2(A); w2(A); u2(C); u2(A);
T3: l3(B); r3(B); l3(C); w3(C); u3(B); u3(C);
T4: l4(D); r4(D); l4(A); w4(A); u4(D); u4(A);

The schedule's first eight steps: each transaction locks and reads its first element, then T2 asks for A (held by T1), T3 for C (held by T2), T4 for A (held by T1), and finally T1 for B (held by T3). Step through it; the graph and lock table update with each request.

After step 7 the graph is T3 → T2 → T1 ← T4: acyclic, so no deadlock (T1 waits for nobody and could finish). Step 8 adds T1 → T3, closing the cycle T1 → T3 → T2 → T1. T4 is not on the cycle but cannot finish either, because it waits for T1. Following the slide, T1's request is denied and T1 is rolled back. The graph right after the rollback is just T3 → T2, with T4 isolated, as on slide 20: the lock on A is free, so T2 and T4, which were waiting for it, have no edges.

What happens next (slide 20). The lock on A can go to only one of T2 and T4 at a time (the animation gives it to T2, the first to ask, so T4 now waits for T2). T2 then completes and releases A and C. Now T3 can get C and T4 can get A, and both complete. At some point T1 is restarted, but it cannot obtain its locks on A and B until T2, T3 and T4 have finished and released them. The slide's phrase "T2 and T4 can continue and finish" should be read in this sense: one after the other, not simultaneously.

DB QB · 17-18 3c · 5 marks  |  BUET QBank · CSE 303 | L-3/T-1 | 2017–18, 2016–17, 2011–12 · 5 marks

What is deadlock in database transaction? Explain with example.

Show worked answer

A deadlock is a state in which each transaction of a set is waiting for a lock held by another transaction of the same set, so none of them can ever proceed. It shows up as a cycle in the waits-for graph (edge T → U when T waits for a lock U holds).

Example. T1 transfers money from account A to B, T2 from B to A, both under 2PL with exclusive locks:

StepT1T2Effect
1l1(A); r1(A); w1(A)T1 holds A
2l2(B); r2(B); w2(B)T2 holds B
3l1(B) deniedT1 → T2
4l2(A) deniedT2 → T1: cycle

After step 4, T1 waits for T2 to release B and T2 waits for T1 to release A. Neither can unlock early (2PL, and they have not finished), so they wait forever. The DBMS resolves it by rolling back one of them (the victim), which releases its lock so the other can finish; the victim is restarted later. Deadlocks can also be prevented in advance by locking elements in a fixed order (Chapter 6) or with wait-die / wound-wait timestamps (Chapter 7), or detected crudely with timeouts.

Summary: a deadlock is a cycle of transactions each waiting for a lock held by the next. Timeouts detect it crudely (roll back anything that runs or waits too long). The waits-for graph has an edge T → U when T waits for a lock U holds; there is a deadlock exactly when the graph has a cycle. A detector rolls back a victim on each cycle; the textbook's prevention variant refuses (rolls back) any request that would close a cycle, as with T1 at step 8 of the slides' example.
