Dirty Data and Cascading Rollback

A scheduler can keep a schedule serializable and still let one transaction read a value that another transaction later takes back. This chapter explains that "dirty data" problem with the slides' two examples (a 2PL schedule and a timestamp schedule), answers the slide's "Why?", and animates the cascading-rollback algorithm that cleans up after it.

1. Where this lecture fits

The previous lectures built two separate pieces of a database system. The scheduler (concurrency control: locking, timestamps) decides the order in which the actions of concurrent transactions run, so that the result is serializable. The log manager and recovery manager (logging) make sure that after a crash the database reflects exactly the committed transactions. The textbook's Chapter 19 (the slides' "DS-TCB", Database Systems: The Complete Book) looks at what goes wrong when these two pieces meet. Serializability says nothing about when a transaction may abort, and logging says nothing about the order of reads and writes. Problems appear in the gap between them.

Transaction
A unit of work on the database (a sequence of reads, writes and computation) that must run as a whole. It ends either with commit (its changes become permanent) or abort (all its changes are cancelled, also called rollback).
Committed
In this lecture, a transaction counts as committed only when its COMMIT log record has reached disk. Until then a crash would undo it.
Notation
ri(X) and wi(X): transaction Ti reads or writes element X. li(X) and ui(X): Ti locks or unlocks X. ci and ai: Ti commits or aborts.

2. Dirty data (slide 2)

Dirty data
A value is dirty if it was written by a transaction that has not committed yet.
Dirty read
A read of a dirty value: transaction T1 reads X after T2 wrote X and before T2 commits.

The dirty value can sit in a main-memory buffer, on disk, or in both. Where it sits does not matter for the problem: another transaction reads it from the buffer just as easily as from disk.

The dirty-data problem is the following chain of events from the slide:

  1. T1 reads dirty data written by T2.
  2. T1 commits.
  3. T2 later aborts, so its write is cancelled. The value T1 read "never existed".
  4. T1's read, and every write T1 computed from it, are now based on a value that is not part of any consistent database state. The database is inconsistent.

Aborts happen for ordinary reasons: a constraint is violated, the user cancels, the scheduler kills a transaction to resolve a deadlock or a timestamp conflict. So the problem is real even without any crash.

3. Dirty data in a 2PL schedule (slide 3)

Two-phase locking (2PL) guarantees conflict-serializability, but plain 2PL lets a transaction release a lock before it commits. The slide's example (the textbook's Fig. 19.1) uses two transactions that should keep the constraint A = B: T1 adds 100 to both A and B, T2 doubles both. Both start at 25. Step through it:

Look at what T2 did. It read A = 125, a value produced by T1, and B = 25, a value from before T1. That is not a state the database was ever consistently in. The result A = 250, B = 50 breaks A = B. If T1 had never run, T2 alone would give A = B = 50. The schedule obeyed 2PL (each transaction took all its locks before releasing any), so the slide's conclusion is: a 2PL schedule allows dirty reads. The only clean fix after the fact is to roll back T2 as well.

4. Dirty data in a timestamp schedule (slide 4)

Recall timestamp-based concurrency control: each transaction T gets a timestamp TS(T), and the scheduler makes the schedule equivalent to the serial order of timestamps. Each element X keeps RT(X), the largest timestamp of a transaction that read X, and WT(X), the timestamp of the transaction that last wrote X. The slide (the textbook's Fig. 19.2) assumes the scheduler does not use the commit bit C(X), the flag that says whether the last writer of X has committed. Here TS(T1) = 200, TS(T2) = 150, TS(T3) = 175.

Slide 4 question: why is T2's write of C "physically unrealizable"?

The timestamp scheduler pretends that each transaction runs instantly at the moment of its timestamp. T2 has timestamp 150, so its write of C must look as if it happened at time 150. But T3, with timestamp 175, has already read C (RT(C) = 175). In the pretended serial order T2 (150) comes before T3 (175), so T3 should have seen T2's value of C. It saw the old value instead. Allowing the write would mean changing the past of a read that has already happened. The rule is: a write by T on X is too late when TS(T) < RT(X), here 150 < 175, so T2 must abort.

When T2 aborts, its write of B is cancelled and WT(B) goes back to 0. But T1 already read T2's value of B at step 2. Nothing stopped it, because without the commit bit the scheduler did not know that B was dirty. T1 may have used that value to compute and write other elements, and it could even have committed. T1's first read of B is now inconsistent.

With the commit bit (slide 4, bottom), the scheduler sees that C(B) is false when T1 tries to read B, and it delays the read until T2 commits or aborts. Here T2 aborts, B is restored, and only then does T1 read the restored committed value. So timestamp scheduling with a commit bit never allows a dirty read.

5. The fix: cascading rollback (slide 5)

Cascading rollback
When a transaction T aborts, every transaction that read dirty data written by T must also be aborted, and then every transaction that read from those, and so on. One abort can trigger a chain ("cascade") of aborts.

The slide's algorithm, written out:

cascade_rollback(T):            -- called when transaction T aborts
    roll back T: restore the old value of every element T wrote
    for each transaction U that read a value written by T:
        cascade_rollback(U)     -- abort U, then repeat for U's readers

To restore former values, the system uses the log if it is an undo log or an undo/redo log, because those record each element's old value. If the dirty value has not reached disk yet, the disk copy of the database still has the right value. The recursion is what makes it a cascade: if T2 read from T1 and T3 read from T2, aborting T1 forces T2 out, which forces T3 out.

Cascading rollback is expensive (work is thrown away, and the chain can be long), and it is only possible if none of the readers has committed. The next chapter turns these two observations into conditions on schedules: recoverable schedules make the cascade possible, and ACR schedules make it unnecessary.

Schedulers that never need it (slide 5 and the textbook, §19.1.2):

  • A timestamp scheduler with a commit bit never lets a transaction read dirty data, so it never needs cascading rollback.
  • A validation-based scheduler writes to the database (even to buffers) only after it has decided that the transaction will commit, so other transactions never see uncommitted values.
  • A strict 2PL scheduler (Chapter 3) holds exclusive locks until commit, which has the same effect.

Quick check

Summary: data is dirty while the transaction that wrote it is uncommitted. Reading it is dangerous because the writer may abort. Plain 2PL allows dirty reads (slide 3), and so does a timestamp scheduler without a commit bit (slide 4, where T2 aborts because its write of C comes after a later transaction already read C). The repair is cascading rollback: abort every transaction that read from the aborted one, recursively, restoring old values from the log.
