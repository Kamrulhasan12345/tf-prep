Recoverable Schedules and Schedules that Avoid Cascading Rollback

Two conditions on the order of commits and reads. A recoverable schedule makes cascading rollback always possible; an ACR schedule makes it never necessary. This chapter answers every "Why?" on slides 6–9, gives a step-by-step test you can run on any schedule, and works the question-bank problems.

1. The reads-from relation

Both conditions in this chapter are about who reads from whom, so we name that first.

Tj reads from Ti
Tj reads an element X, and the last write of X before that read was done by Ti (i ≠ j), and Ti has not aborted in between. Tj then depends on Ti's value.

To find it, scan left from each read rj(X) to the nearest earlier w?(X). If there is none, Tj reads the original, committed value, and depends on nobody.

2. Recoverable schedules (slide 6)

Recoverable schedule
A schedule in which each transaction commits only after each transaction from which it has read has committed. In symbols: if Tj reads from Ti and Tj commits, then ci comes before cj.

Slide 6: "T1 reads T2's written data. T1 commits before T2 commits. The schedule is not recoverable. Why?"

Suppose T2 now aborts. Its write is cancelled, so the value T1 read never officially existed, and T1's read is inconsistent. (The slide says "consistent" here, which is a typo; the argument only works with "inconsistent".) The normal remedy would be a cascading rollback of T1. But T1 has already committed, and a committed transaction is permanent by definition: its effects may already be visible to users and other transactions. So there is no way to roll T1 back, and the database cannot be brought back to a consistent state. That is what "not recoverable" means.

The slide's requirement says the same thing from the recovery manager's point of view. After a crash, the recovery manager decides which transactions count as committed (those whose COMMIT record is on disk). That set must be consistent: if T1 remains committed after recovery and T1 read a value written by T2, then T2 must also remain committed after recovery.

The textbook adds one assumption that makes recoverable schedules truly recoverable: the log's commit records reach disk in the order in which they are written. If c1 is written before c2 but c2's log block happens to be flushed first, a crash in between would leave T2 committed and T1 not, even though the schedule itself was recoverable. Chapter 4 (group commit) builds on exactly this assumption.

3. The three examples (slide 7)

Recoverability and serializability are independent ("orthogonal") properties: a schedule can have either, both, or neither. Slide 7 shows this with three schedules of the same actions, differing only in order.

Example 1 (Why?): S1: w1(A); w1(B); w2(A); r2(B); c1; c2 is recoverable and conflict-serializable

Recoverable: the only read is r2(B), and the last write of B before it is w1(B), so T2 reads from T1. T2 commits after T1 (c1 before c2), which is exactly the condition.

Conflict-serializable: the conflicting pairs are w1(A) … w2(A) and w1(B) … r2(B). Both give the edge T1 → T2 in the precedence graph, which has no cycle. In fact all of T1's actions come before T2's, so S1 is a serial schedule.

Example 2 (Why?): S2: w2(A); w1(B); w1(A); r2(B); c1; c2 is recoverable but not conflict-serializable

Recoverable: T2 reads B from T1 (w1(B) is the last write of B before r2(B)), and c1 comes before c2.

Not conflict-serializable: w2(A) comes before w1(A), giving T2 → T1. w1(B) comes before r2(B), giving T1 → T2. The precedence graph has the cycle T1 → T2 → T1. In words: T2 must come first because of A, and T1 must come first because of B.

Example 3 (Why?): S3: w1(A); w1(B); w2(A); r2(B); c2; c1 is conflict-serializable but not recoverable

Conflict-serializable: the actions are in the same order as S1, so the graph is again just T1 → T2.

Not recoverable: T2 reads B from T1 but commits first. The textbook's crash scenario: T2's commit record reaches disk, then the system crashes before T1's commit record does. Whatever logging method is used (undo, redo or undo/redo), T2 is committed after recovery and T1 is not. T2's effects are permanent, yet they were computed from a value of B that recovery has just erased.

4. Schedules that avoid cascading rollback (slides 8–9)

Slide 8 says "recoverable schedules require cascading rollback". The textbook's wording is more precise: they sometimes require it. Take S1 again. If T1 has to roll back right after the first four steps, then T2, which read B from T1, must be rolled back too. That is possible, because T2 has not committed yet. Recoverability guarantees the cascade can be done; it does not prevent the cascade from being needed.

ACR schedule (avoids cascading rollback, also called cascadeless)
A schedule in which transactions may read only values written by committed transactions. Equivalently, it has no dirty reads: if Tj reads from Ti, then ci comes before that read.

As before, "committed" means the commit log record is on disk. If nobody ever reads uncommitted data, an abort never affects anyone else, so no cascade is ever needed.

Slide 9: which of S1, S2, S3 are ACR? Answer: none. Why?

In all three, r2(B) reads the value written by w1(B), and in all three this read happens before c1. Every one of them contains the dirty read r2(B).

Slide 9: is S4: w1(A); w1(B); w2(A); c1; r2(B); c2 ACR? Yes. Why?

The only read is r2(B), and it now comes after c1. T1, the last writer of B, has committed (and its commit record is on disk), so T2 reads committed data. There is no dirty read. S4 is also recoverable, since c1 precedes c2.

Notice that w2(A) still overwrites A while T1 is uncommitted. ACR only restricts reads, so that is allowed. Chapter 3 shows that the stricter class of "strict" schedules forbids it too.

Every ACR schedule is recoverable

Suppose a schedule is ACR and Tj reads from Ti. By ACR, ci comes before that read. Tj can only commit after its own read, so ci comes before cj. That is the recoverability condition. The converse fails: S1 is recoverable but not ACR.

5. How to test a schedule (exam procedure)

  1. List the reads-from pairs. For each read rj(X), find the last earlier write of X by another transaction Ti (ignoring transactions that aborted before the read).
  2. Recoverable? For each pair, if Tj commits, check ci < cj. One violation makes the schedule not recoverable.
  3. ACR? For each pair, check ci < rj(X). One dirty read makes it not ACR.
  4. Strict? (Chapter 3) Also check that no write wj(X) happens while the last writer of X is uncommitted.

6. Interactive tool: classify any schedule

Type a schedule with r1(A), w2(B), c1 (commit) and a1 (abort), separated by semicolons, commas or spaces. The tool marks every dirty read, decides recoverable / ACR / strict / conflict-serializable with reasons, and steps through the schedule. Below it, pick a transaction and watch the cascading rollback its abort would cause. If that transaction committed, the tool assumes it aborts at the moment it would have committed. (ii) S2: r1(A); w1(A); r2(B); w2(B); c2; r1(B); w1(B); c1

S1: T2 reads A from T1 and commits first. If T1 later aborted, T2 (already committed) could not be rolled back, so S1 is not recoverable. A non-recoverable schedule is never ACR (every ACR schedule is recoverable), and indeed r2(A) is a dirty read.

S3: T1 reads B while T2 is still uncommitted (dirty read), so it is not ACR: if T2 aborted between steps 5 and 6, T1 would have to be rolled back too. But T2 commits before T1 does, so the cascade would always be possible: recoverable.

DB QB · 23-24 8c · 10 marks

Consider the given schedule where ci represents a commit action for transaction Ti:

w1(A), r2(A), w2(A), w2(B), r3(B), w3(C), c3, c2, c1

(i) Does the given schedule preserve database consistency in case of system failure? Justify your answer.
(ii) Rearrange the commit statements in the given schedule so that it preserves database consistency in case of system failure.
(iii) Rearrange the commit statements in the given schedule so that it avoids cascading rollback.

Show worked answer

Reads-from pairs. r2(A) (step 2) reads A written by w1(A): T2 reads from T1. r3(B) (step 5) reads B written by w2(B): T3 reads from T2. So T3 depends on T2, which depends on T1.

(i) No. "Preserving consistency in case of failure" means the schedule is recoverable, and it is not: T3 commits (step 7) before T2 (step 8), and T2 commits before T1 (step 9). Concretely, suppose the system crashes after c3's commit record reaches disk but before c2's and c1's do. Recovery keeps T3 (committed) and undoes T1 and T2. Then C holds a value that T3 computed from B written by T2, which itself came from A written by T1, and both of those writes have been erased. The database is inconsistent, and T3 cannot be rolled back because it committed.

(ii) Recoverable version: each transaction must commit after the one it read from, so the order must be c1, c2, c3:

w1(A), r2(A), w2(A), w2(B), r3(B), w3(C), c1, c2, c3

It is still not ACR (r2(A) and r3(B) are dirty reads), so a crash or abort may cause a cascading rollback, but the cascade is always possible.

(iii) ACR version: each read must come after the commit of the transaction it reads from. c1 must move before r2(A), and c2 must move before r3(B) (and after T2's last action w2(B)):

w1(A), c1, r2(A), w2(A), w2(B), c2, r3(B), w3(C), c3

Every read now sees committed data. This schedule is also recoverable, and in fact serial. (Checked with the tool: the original is not recoverable, (ii) is recoverable but not ACR, (iii) is ACR.)

DB QB · 22-23 4b · 11 marks  |  BUET QBank · CSE 215 | L-2/T-1 | 2022–23 · 11 marks

Consider the following two transactions T1 and T2:

T1: r1(A); w1(A); c1;
T2: r2(A); c2;

(i) Construct a concurrent schedule of T1 and T2 that is recoverable but not ACR (avoids cascading rollback).
(ii) Construct a concurrent schedule of T1 and T2 that is serializable but not recoverable.
(iii) Construct a schedule of T1 and T2 that is ACR (avoids cascading rollback).

Show worked answer

The only way to create a dependency is for r2(A) to come after w1(A), so that T2 reads from T1. Then the position of r2(A) relative to c1, and the order of the commits, decide everything.

(i) r1(A); w1(A); r2(A); c1; c2. T2 reads A from the uncommitted T1 (dirty read, so not ACR: if T1 aborted before c1, T2 would cascade). T2 commits after T1, so it is recoverable.

(ii) r1(A); w1(A); r2(A); c2; c1. T2 never writes, so the only conflicting pair is w1(A) before r2(A), giving the single edge T1 → T2: no cycle, so it is conflict-serializable (equivalent to T1, T2). T2 read from T1 but commits first, so it is not recoverable.

(iii) r1(A); w1(A); c1; r2(A); c2 (T2 reads only after T1 committed). A concurrent alternative is r2(A); r1(A); w1(A); c1; c2, where T2 reads the original committed A before T1 writes it, so there is no dirty read at all.

All five schedules were checked with the tool. The question bank's answer matches.

Summary: Tj reads from Ti when it reads a value Ti wrote. A schedule is recoverable if every transaction commits after all transactions it read from (so a cascading rollback is always possible), assuming commit records reach disk in order. It is ACR if transactions read only committed values (so no cascade is ever needed). ACR ⊂ recoverable, and both are independent of serializability: slide 7's S1, S2, S3 show all combinations.
