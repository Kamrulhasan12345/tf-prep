Deadlock Prevention by Ordering Elements

If every transaction asks for its locks in one agreed order, a circle of waiting transactions can never form. This chapter states the rule, proves it by contradiction, answers why the slides' T2 and T4 break it, and animates the rewritten schedule so you can check that no deadlock arises.

1. The rule (slide 21)

Element ordering
All database elements are put in some fixed order in advance (for example, lexicographically by name, or by physical block address). Every transaction must request its locks in that order.

Example from the slide: a transaction that needs locks on A, B, C and D must request them in the order A, B, C, D. It may not request them as A, D, B, C, because B and C come before D in the order. The transaction does not need to use the elements in that order; it only has to lock them in that order. The order is arbitrary, but it must be the same for everyone.

2. Why ordering prevents deadlock (slide 22)

The slide's proof by contradiction, written out carefully (following the textbook):

  1. Suppose there is a deadlock. Then the waits-for graph has a cycle T1 → T2 → … → Tn → T1.
  2. Each edge Ti → Ti+1 means Ti waits for an element Ai+1 that Ti+1 holds. So: T1 holds A1 and waits for A2; T2 holds A2 and waits for A3; …; Tn holds An and waits for A1.
  3. A transaction that holds X and then requests Y must have Y after X in the order (it requests in increasing order). So A1 < A2 (T1), A2 < A3 (T2), …, An−1 < An (Tn−1).
  4. Tn holds An and requests A1, so An < A1.
  5. Chaining: A1 < A2 < … < An < A1, so A1 < A1, which is impossible.

So no cycle, and hence no deadlock, can form. The slide states the last step directly: Tn cannot request A1 after locking An, because that would violate the ordering.

Slide 23: T2 and T4 are not consistent with the ordering rule. Why?

T2 locks C first and then A, but A comes before C alphabetically. T4 locks D first and then A, but A comes before D. T1 (A then B) and T3 (B then C) already lock in increasing order. To fix T2 and T4, each must take its lock on A first, even though it uses A only later. (The slide says "rewrite lock request of T2 and T2"; it means T2 and T4.)

4. The modified schedule (slide 24, textbook Fig. 19.8)

The rewritten transactions run with the same timing as in Chapter 5. T1 gets A. T2 starts by asking for A and must wait for T1. T3 gets B. T4 also starts by asking for A and waits. Since T2 is stalled, T3 gets its turn, locks C, and completes. Then T1 can lock B and complete. A becomes free and, first come first served, goes to T2, which completes; finally T4 completes.

Slide 24: now no deadlock arises. Check why.

By the theorem of section 2 there can be no cycle at all, but it is instructive to see it concretely in the animation. The only transactions that ever wait are T2 and T4, and they wait at their very first lock request, for A. A transaction waiting for its first lock holds nothing, so no edge can point into it, and it cannot be on a cycle. The graph never has more than the edges T2 → T1 and T4 → T1 (later T4 → T2), all pointing to a transaction that is running. Every transaction finishes, in the order T3, T1, T2, T4.

5. Costs of the method

  • Each transaction must know, before it starts locking, every element it will need, so that it can lock them in order. Queries whose later reads depend on earlier ones make this hard.
  • Locks are often taken earlier than needed (T2 holds A while it is only reading C), which lowers concurrency.
  • It does not by itself prevent starvation (a transaction can keep losing the race for its first lock), which Chapter 8 discusses.

Operating systems use the same idea (a global lock order) to avoid deadlocks between kernel locks.

Try it yourself: paste Chapter 5's original transactions into the waits-for tool there and you get the deadlock; paste the reordered ones and you do not.

Summary: fix a global order on elements and require every transaction to lock in that order. A deadlock cycle would need A1 < A2 < … < An < A1, which is impossible. In the slides' example, T2 (C before A) and T4 (D before A) break the alphabetical order; once they lock A first, the same timing completes with no deadlock. The price is knowing all locks in advance and holding some of them longer.
