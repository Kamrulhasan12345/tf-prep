Comparing Deadlock Methods, and Deadlocks in Real Databases

Wait-die, wound-wait, the waits-for graph and timeouts all handle deadlocks, but they differ in starvation, in how often they roll back, and in how much work each rollback throws away. This chapter goes through the slides' comparison point by point, measures it on the lecture's own examples, and summarises what SQL Server, Oracle and PostgreSQL actually do.

1. Starvation (slide 30)

Starvation
A transaction is rolled back and restarted again and again, and never gets to finish.
No starvation
The guarantee that every transaction eventually completes.

Wait-die and wound-wait have no starvation. In both schemes an older transaction kills a newer one, never the reverse. A killed transaction restarts with its old timestamp. Meanwhile time passes, older transactions finish, and new transactions arrive with larger timestamps. So the restarted transaction keeps getting relatively older until it is the oldest transaction in the system. The oldest transaction is never killed by anyone (nobody is older), so from then on it is guaranteed to complete.

The waits-for graph can starve a transaction if no extra measures are taken. The slide's scenario: a transaction is chosen as victim and rolled back; it restarts, falls into a deadlock again, is chosen as victim again, and so on. For example, with the rule "roll back the transaction whose request closes the cycle", a long transaction that always needs its last lock on a busy element can be the one that closes the cycle every time. Timeouts can starve a long transaction in the same way, since it is always the first to exceed the limit. Element ordering prevents deadlock but not starvation either: a transaction can keep losing the race for its first lock. Real systems add measures such as ageing the victim choice.

2. How often each scheme rolls back (slide 31)

  • Wait-die: the younger transaction is killed when it asks for a lock held by an older one. New transactions request their locks at their start, and most locks they want are held by older transactions, so this happens frequently. More rollbacks.
  • Wound-wait: the younger transaction is killed when an older one asks for a lock the younger already holds. If transactions take their locks near their beginning, it is rare for an old transaction to be beaten to a lock by a newer one. Rollbacks are rare.

3. How much work a rollback wastes (slide 32)

  • Wait-die: the killed transaction is the one asking for a lock, presumably while it is still gathering locks at its beginning. It has done little, so little work is lost per rollback.
  • Wound-wait: the killed transaction is a lock holder. It may have processed many actions and be close to the end, so a rollback can waste a lot of work.

So wait-die has more but cheaper rollbacks, wound-wait fewer but more expensive ones. The textbook concludes that either may waste more work overall, depending on the mix of transactions. (The slide's title "Would-wait" is a typo for wound-wait.)

6. Deadlocks in real databases (slide 33)

SystemWhat it does
SQL ServerA background deadlock monitor wakes every 5 seconds, and checks more often (down to about 100 ms) when deadlocks are frequent. It builds the waits-for graph, finds cycles, and chooses the victim with the lowest deadlock priority, then the one cheapest to roll back (least CPU/log cost). Pure detection: no wait-die or wound-wait.
OracleAn immediate cycle check whenever a session has to wait for a lock: it walks the waits-for graph starting from the waiting session. The victim is the transaction that closed the cycle (the last one to request the conflicting lock); in practice Oracle rolls back that statement and reports an error.
PostgreSQLA hybrid of timeout and graph: a waiting transaction first waits deadlock_timeout (default 1 s); only then does it run the waits-for-graph cycle check. If there is a cycle, a victim is aborted; if not, it simply keeps waiting. This avoids paying for the search on the many short waits that resolve themselves.

Notice that none of the three uses timestamp prevention: since real deadlocks are rare, they prefer detection, which never rolls back a transaction unnecessarily. The textbook's "check on every request" corresponds to Oracle's approach, and "detect periodically" to SQL Server's.

Summary: wait-die and wound-wait never starve a transaction, because a killed transaction keeps its timestamp and eventually becomes the oldest; the waits-for graph and timeouts can starve one. Wait-die rolls back often but early (little work lost); wound-wait rolls back rarely but possibly late (much work lost). Timestamp schemes are cheap but sometimes abort without a real deadlock; the waits-for graph aborts only on real deadlocks, which is why SQL Server, Oracle and PostgreSQL all use graph-based detection (periodic, immediate, or after a timeout).
