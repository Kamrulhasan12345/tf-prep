Managing Rollbacks with Locking: Strict and Rigorous 2PL

A lock-based scheduler can rule out dirty reads with one extra rule: keep exclusive locks until the commit (or abort) record is on disk. This chapter proves the slide's two properties of strict 2PL, explains rigorous 2PL and its "interesting" commit-order property, maps out how all the schedule classes contain each other, and shows how an aborted transaction's buffered changes are undone.

1. Strict 2PL (slide 10)

Strict 2PL locking
A transaction follows two-phase locking, and in addition it must not release any exclusive lock until it has committed or aborted and the commit or abort log record has been flushed to disk. Shared locks may be released earlier (still obeying 2PL).
Strict 2PL schedule
A schedule of transactions that all follow the strict 2PL rule. The textbook calls it simply a strict schedule, and its rule also covers other locks that allow a value to change, such as increment locks.

Why "flushed to disk"? Because "committed" means the commit record survives a crash. If T1 released its lock as soon as it wrote COMMIT into a log buffer, and the system crashed before the buffer reached disk, T1 would be undone at recovery, and anyone who read its values would have read dirty data after all. (Chapter 4 shows a careful way to relax this, called group commit.)

The slide notes that Oracle, MySQL and SQL Server use this rule at the READ COMMITTED isolation level. More precisely, all three hold write locks until commit; Oracle (and MySQL/InnoDB for plain reads) let readers see the last committed version of a row instead of taking shared locks, which has the same effect for dirty reads.

Slide 10, P1: every strict 2PL schedule is ACR. Why?

Suppose T1 writes X. To write, it must hold an exclusive lock on X. Any other transaction T2 that wants to read X needs at least a shared lock on X, which conflicts with T1's exclusive lock, so T2 must wait until T1 releases it. Under the strict rule, that release happens only after T1 has committed or aborted and the log record is on disk. So T2 reads X either after T1 committed (a committed value) or after T1 aborted (by then X has been restored to its old, committed value). Either way T2 never reads dirty data, which is the definition of ACR. Here are the slides' two transactions from Fig. 19.1 again, this time under strict 2PL:

Slide 10, P2: every strict 2PL schedule is serializable. Why?

A strict 2PL schedule is in particular a 2PL schedule: each transaction takes all its locks before releasing any. The earlier lecture proved that every 2PL schedule is conflict-serializable (order the transactions by their lock points, the moment each one holds all its locks; every conflict goes from an earlier lock point to a later one). The strict rule only adds a restriction, so the property carries over. The textbook gives another view: a strict schedule is equivalent to the serial schedule in which each transaction runs instantly at the moment it commits.

2. Rigorous (strong strict) 2PL (slide 11)

Strong strict 2PL, or rigorous 2PL
A transaction must not release any lock, shared or exclusive, until it has committed or aborted and the commit or abort record is on disk.

The "interesting" property: the commit order of conflicting transactions is their serializability order. Proof: take two conflicting actions, one of Ti and then one of Tj on the same element X (at least one a write). When Ti acts on X it holds a lock on X, and under rigorous 2PL it keeps that lock until it commits. Tj needs a conflicting lock on X, so it can act only after Ti commits. Since Tj commits after its own action, ci comes before cj. So every edge Ti → Tj of the precedence graph points from an earlier commit to a later commit, and listing the transactions in commit order is a valid serial order.

Plain strict 2PL does not guarantee this, because shared locks may go early. Example (strict 2PL, not rigorous): T1 takes sl1(A), reads A, takes xl1(B), then releases the shared lock on A. T2 now takes xl2(A), writes A and commits. Finally T1 writes B and commits:

sl1(A) r1(A) xl1(B) u1(A) xl2(A) w2(A) c2 u2(A) w1(B) c1 u1(B)

The conflict r1(A) before w2(A) forces the serial order T1, T2, yet T2 commits first. Rigorous 2PL would have made T2 wait for A until c1.

This matters in practice: with rigorous 2PL the system can tell users "the result is as if transactions ran in the order they committed", which is easy to reason about and useful for replication. The slide notes that SQL Server uses rigorous 2PL to provide the REPEATABLE READ and SERIALIZABLE isolation levels (it keeps shared locks until commit at those levels).

Reading the picture: the strict class is the one produced by strict 2PL, so it lies inside both ACR (property P1) and Serializable (P2). Serial schedules are trivially strict, since no two transactions overlap. ACR and recoverability constrain only reads and commits, so they say nothing about serializability, which is why those ovals cross the Serializable boundary.

4. Undoing an aborted transaction's changes in buffers (textbook §19.1.5)

Strict locking stops other transactions from reading dirty data, but when a transaction aborts its new values are still sitting in buffers (or on disk) and must be cancelled. How hard this is depends on the size of the lockable element.

When the lockable elements are blocks

Then there is a simple method that never needs the log, provided one rule is followed: blocks written by uncommitted transactions are pinned in main memory, that is, the buffer manager may not write them to disk. If T aborts, the system just tells the buffer manager to discard T's modified buffer for block A and return it to the pool of free buffers. Since T held the exclusive lock on A from its write until its abort, nobody else read or changed A in between, and the disk copy of A is still the most recent committed value. The same trick works in a multiversion system: remove T's version of A from the list of versions.

When the lockable elements are smaller than a block (tuples, objects)

Now one buffer can contain changes from several transactions, so the buffer cannot simply be thrown away; the other transactions' changes must survive. The old value of the aborted transaction's element A can be recovered in three ways:

  1. Read the original A from the disk copy and patch the buffer. Costs a disk access.
  2. Take the old value from the log, if it is an undo or undo/redo log. The same code used for crash recovery handles this "voluntary" rollback. It may need no disk access if the log records are still in a buffer, but it may also mean searching the log on disk.
  3. Keep a private main-memory log of each active transaction's changes, discarded when it ends. No disk access, but it can use a lot of memory.

None of the three is ideal; real systems mostly use option 2.

DB QB · 23-24 5b · 5 marks  |  BUET QBank · CSE 215 | L-2/T-1 | 2023–24 · 5 marks

Show that a "strict" two-phase locking (2PL) schedule avoids cascading rollback.

Show worked answer

Definitions. Strict 2PL: transactions follow 2PL and do not release exclusive locks until they have committed or aborted and the commit/abort log record is on disk. A schedule avoids cascading rollback (ACR) if every transaction reads only values written by committed transactions.

Argument. Let Tj read an element X whose last writer before that read is Ti (i ≠ j).

  1. To write X, Ti held an exclusive lock xli(X).
  2. To read X, Tj needs slj(X) (or xlj(X)), which conflicts with xli(X). So Tj can read only after Ti releases xli(X).
  3. By the strict rule, that release happens only after Ti's commit (or abort) record is on disk.
  4. If Ti committed, Tj reads a committed value. If Ti aborted, X was restored before the lock was released, so Ti is no longer X's last writer and Tj reads the previous committed value.

So no transaction ever reads uncommitted data, and an abort can never force another transaction to roll back: the schedule is ACR. Timeline: xli(X), wi(X), … Tj requests slj(X) and waits …, ci (flushed), ui(X), slj(X) granted, rj(X). The animation in section 1 shows this with real values. The question bank's answer is correct.

DB QB · 22-23 1d · 5 marks  |  BUET QBank · CSE 215 | L-2/T-1 | 2022–23 · 5 marks

Show that a schedule satisfying strict 2PL (two-phase locking) is ACR (avoids cascading rollback).

Show worked answer

Same statement as the previous question; here is the proof written by contradiction, which some examiners prefer.

Let S satisfy strict 2PL and suppose S is not ACR. Then some transaction Tj reads X from an uncommitted Ti: the schedule contains wi(X) < rj(X) < ci (with no abort of Ti in between).

  • wi(X) requires xli(X) before it: xli(X) < wi(X).
  • rj(X) requires slj(X) before it, and slj(X) is incompatible with xli(X), so Ti must have unlocked X first: wi(X) < ui(X) < slj(X) < rj(X).
  • Combined with rj(X) < ci: ui(X) < ci. Ti released an exclusive lock before committing.

That contradicts the strict rule (exclusive locks are released only after the commit/abort record is on disk). Hence every strict 2PL schedule is ACR. As a consequence it is also recoverable (every ACR schedule is). The question bank's proof follows the same lines and is correct.

Summary: strict 2PL keeps exclusive locks until the commit or abort record is on disk, so nobody can read dirty data: every strict schedule is ACR (P1) and, being 2PL, conflict-serializable (P2). Rigorous 2PL keeps all locks until then, which makes the commit order a valid serial order. Strict ⊂ ACR ⊂ Recoverable and Strict ⊂ Serializable, while Serializable and Recoverable overlap without containment. An aborted transaction's buffered writes are undone by discarding pinned blocks (block-level locking) or by restoring old values from disk, the log, or a private memory log (smaller elements).
