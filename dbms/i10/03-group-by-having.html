GROUP BY and HAVING

Aggregates over the whole table answer "how much in total?". GROUP BY answers "how much per product, per department, per maker?". This chapter follows the slides' Purchase example step by step (FROM–WHERE, grouping, SELECT), adds HAVING, answers slide 26's "Why?", gives the full evaluation order including ORDER BY, and works a question-bank "find the fault" question on a self-join with GROUP BY.

1. The problem: totals per product (slides 19–20)

Find total sales after 10/04/2005 per product. The desired output (slide 19) has one row per product: Bagel 50, Banana 10. A single SUM over the table would give one number for everything; we need one SUM per product. Slide 20's query:

SELECT   product, SUM(price*quantity) AS "Total Sales"
FROM     Purchase
WHERE    day > '04-OCT-05'
GROUP BY product;
GROUP BY a1, …, ak
Partitions the rows that survive WHERE into groups: rows with equal values in all of a1, …, ak go into the same group. Every aggregate in SELECT (and HAVING) is then computed once per group, and each group produces exactly one output row.

A note on the date. day > '04-OCT-05' compares a DATE column with a string. Oracle converts the string to a date using the session's date format (by default DD-MON-RR, so '04-OCT-05' is 4 October 2005) and the query works. It is safer not to rely on the session setting and to write the date explicitly: day > DATE '2005-10-04' or day > TO_DATE('04-OCT-2005', 'DD-MON-YYYY'). The playground accepts all three forms.

2. What the query does, step by step (slides 21–24)

Slide 21 gives the recipe: (1) compute the FROM and WHERE clauses; (2) group by the attributes in GROUP BY; (3) compute the SELECT clause on the grouped attributes and aggregates.

  1. FROM–WHERE (slide 22): of the 4 purchases, the Banana of 10/03/2005 is not after 10/04/2005 and is removed. Three rows remain.
  2. GROUP BY product (slide 23): the two Bagel rows form one group, the remaining Banana row another.
  3. SELECT (slide 24): each group becomes one row: the product and SUM(price*quantity) over the group's rows. Bagel: 1 · 20 + 1.50 · 20 = 50. Banana: 1 · 10 = 10.

3. HAVING: conditions on groups (slide 25)

Find all products and their total sales which were sold at least 30 pieces after 10/04/2005. "At least 30 pieces" is a condition on the total quantity of a product, which exists only after grouping. That is what HAVING is for:

SELECT   product, SUM(price * quantity)
FROM     Purchase
WHERE    day > '04-OCT-05'
GROUP BY product
HAVING   SUM(quantity) >= 30;
HAVING condition
A condition tested once per group, after grouping. It may use aggregates and grouping attributes. Groups for which it is not TRUE are discarded. (Slide 25: "HAVING clause contains conditions on aggregates.")

Bagel's group has quantities 20 + 20 = 40 ≥ 30, so it stays; Banana's has 10, so it goes. Result: Bagel, 50. Note that HAVING tests SUM(quantity), an aggregate that is not even in the SELECT list; that is allowed.

A condition on a grouping attribute (e.g. product <> 'Banana') could go in either place and give the same answer, but WHERE is better: it removes rows before the expensive grouping.

4. The general form, and slide 26's "Why?"

SELECT   S
FROM     R1, …, Rn
WHERE    C1
GROUP BY a1, …, ak
HAVING   C2

Slide 26: S may contain the grouping attributes a1, …, ak and/or aggregates, but no other attributes; C1 is any condition on the attributes of R1, …, Rn; C2 is any condition on aggregate expressions (and grouping attributes).

Question (worked answer): slide 26, "Why?" may S contain no other attributes?

Because each group becomes one output row, and a non-grouping attribute can have several different values inside one group. In the Purchase example, the Bagel group contains two rows with day = 10/21/2005 and day = 10/25/2005. If we wrote SELECT product, day, SUM(price*quantity) … GROUP BY product, which day should the single Bagel row show? There is no correct answer, so SQL forbids it; Oracle reports ORA-00979: not a GROUP BY expression. A grouping attribute is safe because it has one value per group by definition, and an aggregate is safe because it turns the group's many values into one. (If you want the day too, either group by it as well, or aggregate it: MAX(day) is "the last day the product was sold".)

The full evaluation order (slide 27, plus ORDER BY)

Slide 27 lists the evaluation steps: (1) evaluate FROM–WHERE, applying C1; (2) group by a1, …, ak; (3) apply C2 to each group; (4) compute the aggregates in S and return the result. Adding the ORDER BY clause (which the slide does not show), the logical order of a complete query is

FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY

This order explains several rules at once. WHERE cannot use aggregates (they do not exist yet). In Oracle, a column alias defined in SELECT (like "Total Sales") cannot be used in WHERE, GROUP BY or HAVING (they run before SELECT), but it can be used in ORDER BY (which runs after). And ORDER BY may sort by an aggregate.

Grouping details

  • Several grouping columns: GROUP BY DEPARTMENTID, JOBID makes one group per combination, e.g. (80, SA_MAN) and (80, SA_REP) are different groups.
  • NULL forms its own group: for grouping, all NULLs are treated as equal. Employee Grant has no department, so GROUP BY DEPARTMENTID has a group with DEPARTMENTID NULL.
  • Groups only exist if rows exist: a department with no employees has no rows in EMPLOYEE and so no group. To report it with a count of 0, start from DEPARTMENT with a left outer join (Lecture 09) and count a column of EMPLOYEE: COUNT(e.EMPLOYEEID), not COUNT(*), which would count the NULL-padded row as 1.
  • GROUP BY without aggregates just returns one row per group, like SELECT DISTINCT.

BUET QBank · CSE 215 | L-2/T-2 | 2018–19 · 10 marks

(a) The following SQL query intended to show the last name of each manager along with the number of employees he is managing is not giving the correct result. Find the fault and rewrite it correctly:

SELECT E1.LAST_NAME, COUNT(*) AS "TOTAL MANAGED EMPLOYEES"
FROM EMPLOYEE E1 JOIN E2
ON (E1.MANAGER_ID = E2.EMPLOYEE_ID)
GROUP BY E1.MANAGER_ID
ORDER BY "TOTAL MANAGED EMPLOYEES" ASC;

(b) Write an SQL query to show the department id, job id, first hiring date, last hiring date and average salary of employees for each combination of department id and job id, where the average salary is more than 3000. Ensure no null values are printed and order the result by department id.

(The question shows Oracle's HR schema: employees(employee_id, first_name, last_name, email, phone_number, hire_date, job_id, salary, commission_pct, manager_id, department_id), jobs, job_history, departments, locations, countries, regions.)

Show worked answer

(a) Three faults.

  1. Missing table name. JOIN E2 names no table; E2 is meant to be a second alias of the employee table. It must be JOIN employees E2 (the schema's table is employees; the query also calls it EMPLOYEE). As written, Oracle reports ORA-00942: table or view does not exist.
  2. Roles swapped. The condition E1.MANAGER_ID = E2.EMPLOYEE_ID says "E2 is E1's manager". So E1 is the subordinate and E2 the manager, but the query prints E1.LAST_NAME, a subordinate's name.
  3. Invalid grouping. It groups by E1.MANAGER_ID but selects E1.LAST_NAME, which is not a grouping attribute and has many values per group (all the subordinates' names): ORA-00979: not a GROUP BY expression (slide 26's rule).

Corrected (group by the manager's id as well as the name, because two managers may share a last name):

SELECT E2.last_name, COUNT(*) AS "TOTAL MANAGED EMPLOYEES"
FROM   employees E1 JOIN employees E2
       ON (E1.manager_id = E2.employee_id)     -- E2 is E1's manager
GROUP BY E2.employee_id, E2.last_name
ORDER BY "TOTAL MANAGED EMPLOYEES" ASC;

COUNT(*) is correct here: each row of the join is one (employee, manager) pair. Employees who manage nobody do not appear, which matches "each manager". The ORDER BY may use the alias because ORDER BY runs after SELECT. On our HR data King manages 6, Zlotkey 3, Weiss 3, Hunold 2, Kochhar 2, and De Haan, Hartstein and Higgins 1 each.

(b)

SELECT   department_id, job_id,
         MIN(hire_date) AS first_hired, MAX(hire_date) AS last_hired,
         AVG(salary)    AS avg_salary
FROM     employees
WHERE    department_id IS NOT NULL AND job_id IS NOT NULL
GROUP BY department_id, job_id
HAVING   AVG(salary) > 3000
ORDER BY department_id;

WHERE removes rows with a NULL department or job before grouping, so no NULL group is printed (on our data, Grant has no department). MIN and MAX of the hire dates give the first and last hiring dates of each group, and HAVING keeps the groups whose average salary exceeds 3000. Hire dates and salaries are never NULL in HR, so the aggregates cannot be NULL either. The question bank's answers to (a) and (b) agree with this.

Summary: GROUP BY partitions the rows that pass WHERE into groups of equal grouping values; each group yields one row with the grouping attributes and the aggregates computed over the group. HAVING then filters groups with conditions that may use aggregates. The SELECT list may contain only grouping attributes and aggregates, because any other attribute could have several values in a group. Logical order: FROM, WHERE, GROUP BY, HAVING, SELECT, ORDER BY.
