Serial and Serializable Schedules

Which interleavings are safe? A serial schedule always is. A serializable schedule is any schedule with the same effect as some serial one. This chapter runs the slides' five schedules of T₁ and T₂ step by step with the values of A and B, and ends with the r/w notation used for the rest of the course.

1. The running example (slide 6)

The slides (and the textbook's Example 18.1) use two transactions on elements A and B. The variables t and s are local to T₁ and T₂.

T₁T₂
READ(A,t)READ(A,s)
t := t+100s := s*2
WRITE(A,t)WRITE(A,s)
READ(B,t)READ(B,s)
t := t+100s := s*2
WRITE(B,t)WRITE(B,s)

The only consistency constraint on the database is A = B. T₁ adds 100 to both, T₂ doubles both, so each transaction, run alone, turns a state with A = B into another state with A = B. The question is which interleavings of their twelve steps also keep A = B.

Consistency constraint
A condition every legal database state must satisfy (here A = B). A consistent state satisfies all constraints.
Correctness principle (textbook §17.1.3)
Every transaction, if executed in isolation from a consistent state, ends in a consistent state.

2. Serial schedules (slides 7–9)

Serial schedule
A schedule in which all actions of one transaction come first, then all actions of another transaction, and so on. No mixing of actions from different transactions. A serial schedule is written simply as the list of its transactions, e.g. (T₁, T₂).

With two transactions there are exactly two serial schedules: (T₁, T₂) and (T₂, T₁). With n transactions there are n! of them. Step through both, starting from A = B = 25 (the values in the slide's tables, as in the textbook's Figs. 18.3 and 18.4):

Slide 9 question: are the values of A and B the same at the end of the two serial schedules?

No. (T₁, T₂) computes 2(25 + 100) = 250 for both; (T₂, T₁) computes 2·25 + 100 = 150 for both. The final state depends on the order of the transactions. Both final states are consistent (A = B in each), which is all we require: the DBMS promises the effect of some serial order, not a particular one.

A note on the slide: its text says “assume initially A = B = 1000”, but its tables start from 25 (they are the textbook's figures). From 1000 the results would be 2(1000 + 100) = 2200 and 2·1000 + 100 = 2100: different again, and each consistent.

3. Serializable schedules (slides 10–12)

Slide 10 question: why does every serial schedule preserve database consistency?

By the correctness principle, each transaction alone maps a consistent state to a consistent state. A serial schedule runs the transactions one at a time, each starting from the state the previous one left. Start consistent; after the first transaction the state is still consistent; so the second starts from a consistent state and also ends consistent; and so on. By induction on the number of transactions, the final state is consistent. Nothing from another transaction ever sneaks in between the steps of a transaction, so the principle applies to each one exactly as if it ran alone.

Serial schedules are safe but slow (no overlap at all). Are there other safe schedules? Yes:

Serializable schedule
A schedule S is serializable if there is a serial schedule S′ such that, for every initial database state, the effects of S and S′ are the same.

The words “for every initial state” matter. Matching a serial schedule from one lucky starting state is not enough.

A serializable schedule (slide 10)

Here T₁ finishes with A before T₂ touches A, and finishes with B before T₂ touches B. T₂ works on A while T₁ is still busy elsewhere.

To prove it is serializable we must check every consistent initial state, not just 25. Every consistent state has A = B = c for some c. Following the schedule: A becomes c + 100, then 2(c + 100); B becomes c + 100, then 2(c + 100). So both end as 2(c + 100), exactly what (T₁, T₂) produces. The schedule is serializable with equivalent serial order (T₁, T₂).

A schedule that is not serializable (slide 11)

From A = B = 25 it ends with A = 250, B = 150: inconsistent. In effect it applied different computations to the two elements: A := 2(A + 100) but B := 2B + 100. A single bad starting state is enough to prove a schedule is not serializable, because serializability requires equal effects for every initial state and every serial schedule preserves A = B.

Serializable only because of what the transactions compute (slide 12)

Now change T₂ to add 200 instead of doubling, and keep exactly the order of Figure 3:

Now A = c + 100 + 200 and B = c + 200 + 100: both are c + 300 for every c, which is the effect of (T₁, T₂), and by coincidence also of (T₂, T₁), because additions commute. So this schedule is serializable, while the identical order with doubling was not. Serializability, as defined, depends on the actual arithmetic (“business operation”) inside the transactions.

The scheduler cannot see that arithmetic. Transactions are programs in a general-purpose language mixed with SQL; the scheduler only sees which elements are read and written. So the scheduler makes a safe assumption (textbook §18.1.4):

“No coincidences” assumption
Whenever a transaction writes an element, the value it writes may depend on the database state in any way, with no lucky arithmetic coincidences. In other words, if there is something T could do to an element that would make the state inconsistent, assume T does it. Under this assumption only the reads and writes matter, not the values.

4. Notation: transactions as reads and writes (slides 13–14)

Since only reads and writes matter, a transaction is written as its sequence of reads and writes:

Action ri(X) / wi(X)
Transaction Ti reads / writes database element X. (The slides also write RT(X), WT(X) for transaction T.)
Transaction Ti
A sequence of actions, all with subscript i.
Schedule S of a set of transactions
A sequence of all their actions in which, for each Ti, the actions of Ti appear in the same order as in Ti itself. S is called an interleaving of the transactions.
T₁: r₁(A); w₁(A); r₁(B); w₁(B);
T₂: r₂(A); w₂(A); r₂(B); w₂(B);

serializable schedule of Figure 2:
    r₁(A); w₁(A); r₂(A); w₂(A); r₁(B); w₁(B); r₂(B); w₂(B);

The rule that a schedule keeps each transaction's own order is the same rule an operating system obeys: it interleaves programs but never runs one program's instructions out of order.

How many schedules are there? Two transactions with m and n actions can be interleaved in C(m + n, m) = (m + n)! / (m! n!) ways, since a schedule is fixed once we choose which m of the m + n positions belong to the first transaction. T₁ and T₂ above (4 actions each) have C(8, 4) = 70 schedules, of which only 2 are serial.

Exam questions

Exam questions on these definitions also ask about conflict-serializability, so they are answered in Chapter 3 (counting schedules, serializable vs conflict-serializable) and Chapter 7 (defining serial, serializable, conflict-serializable and 2PL together).

Summary: a serial schedule runs transactions one after another and always preserves consistency, though different serial orders can give different (all consistent) results. A schedule is serializable if it has the same effect as some serial schedule from every initial state. Whether a schedule is serializable can depend on the transactions' arithmetic, which the scheduler cannot see, so it assumes “no coincidences” and reasons only about reads and writes, written ri(X) and wi(X).
