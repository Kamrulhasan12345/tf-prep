Why Databases Need Concurrency Control

Two transactions that each add 100 to the same value can leave the database 100 short. This chapter shows exactly how, introduces the scheduler that prevents it, and defines a schedule, the object the rest of this lecture studies.

1. Transactions running at the same time

A database serves many users at once. Each user's unit of work is a transaction, and the DBMS runs many transactions concurrently: while one waits for a disk read, another uses the CPU. This is good for speed, but it creates a new danger, because transactions can touch the same data.

Transaction
A sequence of database actions (reads and writes, plus local computation) that must behave as one indivisible unit of work. Example: “move 100 from account A to account B”.
Database element
A unit of data the DBMS reads or writes as a whole and can lock: a tuple, a disk block, or a whole relation. The slides write elements as single letters: A, B, X.
READ(X, t) and WRITE(X, t)
READ(X, t) copies element X into the transaction's local variable t. WRITE(X, t) copies t back into X. Local variables such as t and s belong to one transaction only; other transactions cannot see them.

Slide 2: the lost update

Two transactions do the same thing to the same element X:

T₁: READ(X,t);  t := t + 100;  WRITE(X,t)
T₂: READ(X,t);  t := t + 100;  WRITE(X,t)

(The slide writes the middle step as “A := A + 100”. It means the local variable: t := t + 100. Each transaction has its own private t.)

Start with X = 1000. If T₁ runs completely and then T₂ runs, T₂ reads 1100 and writes 1200. That is the correct answer: two increments of 100. Now let the operating system interleave them so that T₁'s read happens immediately after T₂'s read, exactly as the slide asks:

Slide 2 question: what happens when READ(X,t) of T₁ happens immediately after READ(X,t) of T₂?

Both reads see X = 1000, because neither transaction has written yet. Each transaction then adds 100 to its own private copy, so both compute 1100. Whichever transaction writes second simply overwrites the first one's 1100 with another 1100. The final value is 1100 instead of 1200: one update has been lost. No single step was wrong; the problem is purely the order in which the steps of the two transactions were mixed. The database is now in an inconsistent state, a state that no correct execution could produce.

2. Concurrency control and the scheduler (slides 3–4)

The slides compare this with threads in an operating system: two threads that update shared memory need a lock, semaphore or mutex, or they corrupt it. A DBMS has the same need, and the component that supplies the control is the scheduler.

Concurrency control
The work of making sure the database stays consistent while transactions execute concurrently.
Scheduler
The DBMS component that receives every read and write request from transactions and decides the order in which they actually reach the database buffers. It may execute a request at once, delay it, or (in some methods) abort the transaction that made it.
Transaction manager
The component that starts transactions and passes their read/write requests to the scheduler.

Slide 4 lists the scheduler's two choices for each request:

  1. Case 1, execute now. If the request is safe, the scheduler passes it straight to the buffers.
  2. Case 2, delay. If executing it now could lead to an inconsistent state, because another transaction is using the same element, the scheduler holds the request back until it is safe.

In Figure 1, a scheduler would have delayed T₁'s read until T₂ had written X. Then T₁ would read 1100 and write 1200. The rest of this lecture and the next one is about how the scheduler decides: first the theory of which orders are safe (serializability), then the practical mechanisms (locks, timestamps).

3. What a schedule is (slide 5)

Schedule
A sequence of the important database actions (reads and writes) of one or more transactions, in the order the scheduler lets them happen. Actions of different transactions may be interleaved in any order the scheduler chooses, but the actions of one transaction always stay in that transaction's own order.

Think of transactions as programs and the schedule as the order in which a multitasking operating system runs their instructions: it can switch between programs at any point, but it never runs the instructions of one program out of order. The purpose of a schedule is the safe execution of concurrent transactions.

Slide 5 adds two assumptions that the whole chapter uses (textbook §18.1.1):

  • Reads and writes happen in main-memory buffers, not on disk. When the buffers are written to disk is the DBMS's own business (the buffer and log managers decide; that is Lec 05–06). So the values shown in schedules are buffer values.
  • A buffer is shared. Once some transaction T brings element A into a buffer, other transactions read and write that same buffer copy. This is exactly why the interleaving in Figure 1 matters.

4. The three classic anomalies

The lost update is one of three standard ways a badly interleaved schedule goes wrong. The other two appear later in these notes (dirty reads in the timestamp chapter, unrepeatable reads in the isolation-level chapter), but exam questions ask for all three together, so here they are side by side.

Lost update (write–write)
Two transactions read the same value and both write a new value computed from it. The second write overwrites the first, so the first transaction's change disappears. (Figure 1.)
Dirty read (write–read on uncommitted data)
T₂ reads a value that T₁ has written but not committed. If T₁ then aborts, its write is undone, and T₂ has used a value that officially never existed.
Unrepeatable read (read–write)
T₁ reads X, then T₂ changes X and commits, then T₁ reads X again and sees a different value inside the same transaction.

BUET QBank · CSE 303 | L-3/T-1 | 2016–17 · 9 marks

Discuss three problems of non-serializable execution with necessary examples.

Show worked answer

A non-serializable execution is an interleaving of transactions whose effect is not the effect of running them one after another in any order. Three classic problems:

1. Lost update. Account A = 1000. T₁ withdraws 100, T₂ deposits 500.

timeT₁T₂A in buffer
1READ(A,t) → t = 10001000
2READ(A,s) → s = 10001000
3t := t − 100; WRITE(A,t)900
4s := s + 500; WRITE(A,s)1500

Final A = 1500, but either serial order gives 1400. T₁'s withdrawal is lost because T₂ wrote a value computed from a stale read.

2. Dirty read. T₁ transfers 100 from A to B: it writes A = 900, then fails before finishing and aborts, so A is restored to 1000. In between, T₂ reads A = 900 and B and computes the bank's total, which is 100 too low. T₂ read a value that was never committed, so its result matches no serial execution (in a serial execution T₂ sees either 1000 before T₁ or nothing of T₁ at all, since T₁ aborted).

3. Unrepeatable read. T₁ reads the number of free seats, 10, and shows it to a customer. T₂ books a seat (writes 9) and commits. T₁ reads the seats again before booking and sees 9. Inside one transaction the same read returned two different values. In any serial order T₁ would see the same value both times.

All three are prevented by a scheduler that only allows serializable schedules (Chapter 2), for example with two-phase locking (Chapter 7).

Summary: concurrent transactions share buffers, so the order in which their reads and writes interleave can produce states no correct execution would, such as a lost update (1100 instead of 1200). The scheduler sees every read and write request and either executes it, delays it, or aborts the requester, to keep the database consistent. A schedule is the resulting sequence of actions: transactions may be interleaved, but each transaction's own actions keep their order.
