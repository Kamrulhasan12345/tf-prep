Locks and the Locking Scheduler

The precedence-graph test checks a finished schedule. A real scheduler must decide request by request, and the usual way is locking. This chapter introduces the simplest lock, the two rules for using locks properly, and the locking scheduler, and shows that proper locking alone still does not guarantee serializability.

1. Locks (slide 30)

A scheduler cannot wait until a schedule is complete and then draw its precedence graph: it must decide, as each request arrives, whether to let it through. The most common method is locking. Before reading or writing an element, a transaction must obtain a lock on it; while one transaction holds the lock, the scheduler keeps other transactions away from that element.

Lock
A permission, recorded by the scheduler, for one transaction to access one database element. In this chapter there is only one kind of lock, needed for any access at all (Lec 03 adds shared and exclusive locks).
Lock table
The scheduler's record of which transaction holds a lock on which element (and, later, who is waiting).
li(X)
Transaction Ti requests a lock on X.
ui(X)
Transaction Ti releases (“unlocks”) its lock on X.

2. Using locks properly (slides 31–32)

Locks only help if transactions and the scheduler use them properly. Two rules:

R1, consistency of transactions
Actions and locks must relate: (1) a transaction may read or write an element only if it was granted a lock on it earlier and has not released it since; (2) every lock a transaction takes, it must later release.
Formally: whenever Ti has an action ri(X) or wi(X), there is a previous li(X) with no ui(X) in between, and there is a later ui(X).
R2, legality of schedules
Locks must mean what they say: no two transactions may hold a lock on the same element at the same time.
Formally: if li(X) is followed later by lj(X) (j ≠ i), then ui(X) appears somewhere between them.

R1 is a property of each transaction by itself; R2 is a property of the schedule (the interleaving). The slide ends with a warning: a legal schedule is not necessarily conflict-serializable. Section 3 shows why.

3. Slide 33: legal and consistent, yet not serializable

The transactions of Chapter 2 with locks added (textbook Example 18.10):

T₁: l₁(A); r₁(A); A := A+100; w₁(A); u₁(A); l₁(B); r₁(B); B := B+100; w₁(B); u₁(B);
T₂: l₂(A); r₂(A); A := A*2;   w₂(A); u₂(A); l₂(B); r₂(B); B := B*2;   w₂(B); u₂(B);

Slide 33 questions: why is each transaction consistent, and why is the schedule legal?

Consistent: every read and write of A by T₁ (r₁(A), w₁(A)) lies between l₁(A) and u₁(A), and every access to B between l₁(B) and u₁(B); each lock is later released. The same holds for T₂. So both satisfy R1.

Legal: the two transactions never hold a lock on the same element at once. T₂'s l₂(A) comes after u₁(A), and T₁'s l₁(B) comes after u₂(B). So R2 holds.

Yet it is not serializable: from A = B = 25 it ends with A = 250, B = 150. T₁ went first on A but T₂ went first on B; the locks only protected each single access, not the transaction as a whole. In conflict terms, w₁(A) before r₂(A) gives T₁ → T₂, and w₂(B) before r₁(B) gives T₂ → T₁: a cycle. The missing ingredient is two-phase locking (Chapter 7).

4. The locking scheduler (slides 34–35)

Locking scheduler
Grants a lock request if and only if granting it keeps the schedule legal. If a request cannot be granted, the requesting transaction is delayed: it waits, and its later actions wait with it, until the lock becomes available; then the lock is granted and the transaction resumes.

With one kind of lock, the lock table can be thought of as a relation Locks(element, transaction) containing a pair (X, T) for each lock T currently holds. Granting li(X) is legal exactly when no pair (X, Tj) with j ≠ i is present. Unlocking deletes the pair.

Slide 35 changes the transactions slightly: each locks B before unlocking A (textbook Example 18.11).

T₁: l₁(A); r₁(A); A := A+100; w₁(A); l₁(B); u₁(A); r₁(B); B := B+100; w₁(B); u₁(B);
T₂: l₂(A); r₂(A); A := A*2;   w₂(A); l₂(B); u₂(A); r₂(B); B := B*2;   w₂(B); u₂(B);

Watch the scheduler process the requests in the slide's order. The right side shows the lock table and each transaction's state:

Slide 35 question: why is the lock l₂(B) denied?

When T₂ asks for B, the lock table already contains (B, T₁): T₁ locked B before it unlocked A. Granting l₂(B) would let two transactions hold a lock on B at once, breaking legality (R2). So the scheduler denies the request and T₂ waits. T₁ goes on to read and write B (B = 125) and executes u₁(B). Now B is free, l₂(B) is granted, T₂ releases A and doubles B to 250. Because T₂ was forced to wait, it multiplied B after T₁ added 100, exactly as on A, and the final state A = B = 250 is consistent: it equals the serial schedule (T₁, T₂).

5. Try the locking scheduler

Type lock, read, write and unlock actions (l1(A) r1(A) u1(A) …) in the order transactions issue them. The scheduler grants or denies each lock, delays a waiting transaction's later actions, resumes it when the lock is freed, flags actions without a lock (R1 violations), and reports a deadlock if waiting transactions wait for each other. Below the input it tells you whether the reads and writes that reached the database form a conflict-serializable schedule.

Exam questions

Exam questions on locking ask about two-phase locking, so they are answered in Chapter 7 and in Lec 03.

Summary: a transaction locks an element before using it and unlocks it later (consistency, R1); no two transactions may hold a lock on the same element at once (legality, R2). The locking scheduler grants a lock only if the schedule stays legal and otherwise delays the requester until the lock is released. Consistent transactions in a legal schedule can still produce a non-serializable result if a transaction unlocks one element and later locks another.
