Conflicts and Conflict-Serializability

Real schedulers check a stronger, easier condition than serializability: can the schedule be turned into a serial one by swapping neighbouring actions that do not conflict? This chapter defines conflicts, animates the slides' swap sequence, and explains why conflict-serializability is sufficient but not necessary.

1. What a conflict is (slide 15)

Commercial schedulers enforce conflict-serializability, a condition stronger than serializability (every conflict-serializable schedule is serializable, Section 4). It is built on one idea:

Conflict
A pair of consecutive actions in a schedule such that, if their order is swapped, the behaviour of at least one of the transactions involved can change (the value it reads, or the final value it leaves in the database).

2. Which pairs conflict (slides 16–18)

Let Ti and Tj be different transactions (i ≠ j). Four kinds of pairs never conflict:

  1. ri(X); rj(Y) never conflict, even if X = Y. Neither action changes any element, so each reads the same value whichever goes first.
  2. ri(X); wj(Y) do not conflict if X ≠ Y. If Tj writes Y first, X is unchanged, so Ti reads the same X. And Ti's read of X has no effect on the value Tj writes into Y.
  3. wi(X); rj(Y) do not conflict if X ≠ Y, for the same reason.
  4. wi(X); wj(Y) do not conflict if X ≠ Y. They change different elements, so the final state is the same in either order.

Three kinds of pairs always conflict:

  1. Two actions of the same transaction, e.g. ri(X); wi(Y). The order of a transaction's own actions is fixed; the scheduler may never reorder them. (Slide 17 writes this as ri(X); wi(Y): note the same subscript i on both.)
  2. wi(X); wj(X): two writes of the same element by different transactions. As written, X ends with Tj's value; swapped, it ends with Ti's. By “no coincidences” the two values differ for some initial state.
  3. ri(X); wj(X) (and likewise wi(X); rj(X)): a read and a write of the same element by different transactions. Swapping changes the value Ti reads, which may change everything Ti does afterwards.

Slide 18 rule. Two adjacent actions of different transactions may be swapped unless (1) they involve the same database element and (2) at least one of them is a write. Both conditions must hold for a conflict: same element alone (two reads) is fine, and a write alone (on different elements) is fine.

3. Conflict-equivalent and conflict-serializable (slide 19)

Conflict-equivalent
Two schedules are conflict-equivalent if one can be turned into the other by a sequence of swaps of adjacent, non-conflicting actions.
Conflict-serializable
A schedule is conflict-serializable if it is conflict-equivalent to some serial schedule.

Each non-conflicting swap leaves every transaction's reads and the final database state unchanged (that is what “non-conflicting” means). So a whole sequence of such swaps also changes nothing, and if it ends at a serial schedule, the original schedule has exactly that serial schedule's effect.

Slide 19 question: why are only adjacent actions swapped?

Because the safety argument is about two actions with nothing in between. When two neighbours swap, the order of every other pair of actions in the schedule stays the same, so we only have to check that one pair. If we jumped an action several places at once, it would pass over every action in between, and some of those could conflict with it (for example, moving w₁(A) forward past r₂(A) changes what T₂ reads). Moving in adjacent steps forces us to check each pair it passes. It loses nothing: any rearrangement that keeps every conflicting pair in its original order can be built from adjacent swaps (this is how bubble sort or insertion sort works), and every rearrangement that changes the order of some conflicting pair is correctly forbidden.

4. Conflict-serializable vs serializable (slide 20)

  • Every conflict-serializable schedule is serializable. Conflict-serializability is a sufficient condition.
  • Some serializable schedules are not conflict-serializable. Conflict-serializability is not necessary.
  • DBMSs enforce conflict-serializability anyway, because the scheduler can check it from reads and writes alone (next chapter), with no knowledge of what the transactions compute.

Why conflict-serializability is not necessary: blind writes

The textbook's example (box in §18.2): T₁ and T₂ each write Y and then X, and T₃ writes X. None of them reads anything (writes without a preceding read are called blind writes).

S₁: w₁(Y); w₁(X); w₂(Y); w₂(X); w₃(X);     (serial: T₁, T₂, T₃)
S₂: w₁(Y); w₂(Y); w₂(X); w₁(X); w₃(X);

Both leave Y with T₂'s value and X with T₃'s value, and nobody reads anything, so S₂ has exactly the effect of the serial S₁ from every initial state: S₂ is serializable. But w₁(Y) must stay before w₂(Y) and w₂(X) must stay before w₁(X) (each is a write–write conflict), so T₁ would have to come both before and after T₂. No sequence of legal swaps reaches any serial schedule: S₂ is not conflict-serializable. The values T₁ and T₂ wrote into X are overwritten by T₃ and never seen, so their order does not matter, but the conflict rule cannot know that.

BUET QBank · CSE 303 | L-3/T-1 | 2013–14 · 5 marks

Define the following terms: conflict-equivalent and conflict-serializable.

Show worked answer

Two actions conflict if they belong to the same transaction, or if they belong to different transactions, access the same element, and at least one is a write.

Conflict-equivalent: two schedules (of the same transactions) are conflict-equivalent if one can be transformed into the other by a sequence of swaps of adjacent non-conflicting actions. Equivalently, they contain the same actions and every pair of conflicting actions appears in the same order in both.

Conflict-serializable: a schedule is conflict-serializable if it is conflict-equivalent to some serial schedule.

Example: S = r₁(A); w₁(A); r₂(A); w₂(A); r₁(B); w₁(B); r₂(B); w₂(B) is conflict-equivalent to the serial schedule (T₁, T₂) by the four swaps of Figure 3, so S is conflict-serializable. Swapping r₂(A) ahead of w₁(A) would not be allowed (same element, one write).

BUET QBank · CSE 303 | L-3/T-1 | 2012–13 · 5 marks

Why is conflict-serializability not necessary for serializability? Explain with an example.

Show worked answer

Conflict-serializability treats every write–write pair on the same element as order-sensitive. But when a later transaction overwrites an element without anyone reading the intermediate values, the order of the earlier writes is invisible. A schedule can then have the effect of a serial schedule even though its conflicts cannot be untangled by swaps.

Example (textbook §18.2): S₂: w₁(Y); w₂(Y); w₂(X); w₁(X); w₃(X).

  • Serializable: it leaves Y = T₂'s value and X = T₃'s value, and no transaction reads anything. The serial schedule (T₁, T₂, T₃) leaves the same values for every initial state.
  • Not conflict-serializable: w₁(Y) before w₂(Y) gives the arc T₁ → T₂; w₂(X) before w₁(X) gives T₂ → T₁. The precedence graph (next chapter) has a cycle, so no serial schedule is conflict-equivalent to S₂.

So S₂ is serializable without being conflict-serializable: the condition is sufficient but not necessary.

BUET QBank · CSE 303 | L-3/T-1 | 2010–11 · 10 marks

A concurrent schedule of three transactions T₁, T₂ and T₃ is given in Figure 3. Show the steps to transform the above schedule into an equivalent conflict serial schedule.

(The figure is missing from the question bank, which notes “No Figure found in PDF”. The method is shown on the textbook schedule of three transactions instead.)

Show worked answer

Method. (1) List the conflicting pairs (same element, different transactions, at least one write) and draw the precedence graph. (2) If it has a cycle, no conflict-equivalent serial schedule exists. (3) Otherwise pick a topological order. (4) Move the actions of the first transaction in that order to the front, one adjacent swap at a time, never passing an action it conflicts with; then the second transaction's actions behind them; and so on.

Example (textbook Example 18.7): S: r₂(A); r₁(B); w₂(A); r₃(A); w₁(B); w₃(A); r₂(B); w₂(B).

  1. Conflicts: on A, r₂(A)/w₂(A) before r₃(A)/w₃(A): T₂ → T₃. On B, r₁(B)/w₁(B) before w₂(B), and w₁(B) before r₂(B): T₁ → T₂. Graph T₁ → T₂ → T₃, acyclic. Order (T₁, T₂, T₃).
  2. Swap r₁(B) ahead of r₂(A) (different elements): r₁(B); r₂(A); w₂(A); r₃(A); w₁(B); w₃(A); r₂(B); w₂(B).
  3. Move w₁(B) up past r₃(A), w₂(A), r₂(A) (all on A): r₁(B); w₁(B); r₂(A); w₂(A); r₃(A); w₃(A); r₂(B); w₂(B).
  4. Move r₂(B) up past w₃(A), r₃(A) (different elements), then w₂(B) the same way: r₁(B); w₁(B); r₂(A); w₂(A); r₂(B); w₂(B); r₃(A); w₃(A). This is the serial schedule (T₁, T₂, T₃).

Summary: two actions conflict if they are from the same transaction, or if they touch the same element and at least one is a write. Adjacent non-conflicting actions can be swapped without changing any transaction's behaviour. A schedule is conflict-serializable if such swaps can turn it into a serial schedule. Conflict-serializable implies serializable, but not conversely: blind writes can make a schedule serializable while its conflicts form a cycle.
