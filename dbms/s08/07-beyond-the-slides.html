Exam Topics Beyond the Slides: Query Optimization, Size Estimation, Index Selection, Hybrid Hash Join

Past exams ask about topics the Lec 07–08 slides only touch: rewriting logical plans with algebraic laws, estimating result sizes, the cost of selections that use indexes, and the hybrid hash join. Each topic gets a short explanation first, then its exam questions with full answers.

1. Logical-plan optimization with algebraic laws

Lec 07, Chapter 1 showed query rewrite: the parse tree becomes a relational-algebra tree, which is then improved by equivalences, laws that never change the answer. The laws used in exams:

LawUse
σC1 ∧ C2(E) = σC1(σC2(E))split a selection so the parts can move separately
σC(E1 × E2) = σC(E1) × E2   if C mentions only E1's attributes (same for ⋈)push selections down, as near the leaves as possible
σθ(E1 × E2) = E1 ⋈θ E2turn a product plus a comparison between the two sides into a join
πL(E1 ⋈θ E2) = πL(πL1(E1) ⋈θ πL2(E2)), Li = attributes of Ei in L or in θpush projections down, keeping attributes still needed above
⋈ and × are commutative and associativechoose the join order (smallest intermediate results first)
σC(δ(R)) = δ(σC(R)); πL(R ∪ S) = πL(R) ∪ πL(S)δ commutes with σ; π distributes over ∪ (also for bags)
π does not commute with δ, and does not distribute over ∩ or −projection can make different tuples equal

The heuristic recipe: (1) split conjunctive selections; (2) push each selection to the lowest node that has all its attributes; (3) combine σ with × into joins; (4) push projections down, keeping join attributes; (5) order joins so the most selective come first.

DB QB · 23-24 5d · 7 marks  |  BUET QBank · CSE 215 | L-2/T-1 | 2023–24 · 7 marks

Given three relations R(a, b, c), S(d, e) and T(e, f, g), apply query optimization techniques to find the optimized logical plan for the expression given below: σa>100, b=20, c=d, f<100((R × S) ⋈ T)

Show worked answer
  1. Split the selection: σa>100 σb=20 σc=d σf<100((R × S) ⋈ T).
  2. Push down: a > 100 and b = 20 mention only R: apply them to R. f < 100 mentions only T: apply it to T. c = d mentions R and S: it can go down to (R × S) but no further.
  3. σ over × becomes a join: σc=d(σa>100 ∧ b=20(R) × S) = σa>100 ∧ b=20(R) ⋈c=d S.

(σa>100 ∧ b=20(R) ⋈c=d S) ⋈ σf<100(T)

The outer ⋈ is still the natural join on e (the attribute S and T share). The product R × S, which could be huge, never exists; every relation is filtered before it enters a join.

Observe the Schema and SQL query shown in the following figure. Construct an optimized query plan for the query using the equivalence rules of the figure. You have to draw the query plan using expression tree and justify the plan with explanations.

Schema: Student(sid, name, major), Enroll(sid, course, section, term, grade), Class(course, section, term, instructor, room, time)

SELECT S.name, C.instructor, C.term
FROM Student S, Enroll E, Class C
WHERE S.sid = E.sid AND E.course = C.course AND E.section = C.section
  AND E.term = C.term AND C.instructor = 'Hinon' AND S.major = 'ML';

Equivalence rules: (a) σθ(E1 × E2) = E1 ⋈θ E2; (b) σθ0(E1 ⋈θ E2) ≡ (σθ0(E1)) ⋈θ E2; (c) σθ1∧θ2(E1 ⋈θ E2) = (σθ1(E1)) ⋈θ (σθ2(E2)); (d) ΠL1∪L2(E1 ⋈θ E2) = ΠL1(E1) ⋈θ ΠL2(E2); (e) ΠL1∪L2(E1 ⋈θ E2) = ΠL1∪L2(ΠL1∪L3(E1) ⋈θ ΠL2∪L4(E2)). (The DB QB copy lost the figure; this is the schema, query and rule list from the CSE 215 bank copy of the same exam.)

Show worked answer

Initial plan: Πname, instructor, term(σθ((Student × Enroll) × Class)), with θ = all six conditions.

  1. Rule (a): the conditions S.sid = E.sid and E.course = C.course ∧ E.section = C.section ∧ E.term = C.term relate the operands of the products, so the products become joins: (Student ⋈sid Enroll) ⋈course, section, term Class, with σmajor='ML' ∧ instructor='Hinon' still on top.
  2. Rules (c) and (b): major = 'ML' mentions only Student, instructor = 'Hinon' only Class: push each down to its relation.
  3. Join order (associativity): σinstructor='Hinon'(Class) is probably tiny (one instructor's classes), so join it with Enroll first; that keeps only the enrollments in Hinon's classes. Then join with the ML students.
  4. Rule (e): keep only needed attributes. From Student: sid (join), name (output). From Enroll: sid, course, section, term (joins). From Class: course, section, term (join), instructor, term (output). grade, room, time and major are dropped early.

Πname, instructor, term( Πsid, name(σmajor='ML'(Student)) ⋈sid Πsid, instructor, term( Πsid, course, section, term(Enroll) ⋈course, section, term Πcourse, section, term, instructor(σinstructor='Hinon'(Class)) ) )

Justification: selections first shrink the inputs of every join (rule c); joins replace products so no full cross product is built (rule a); projections shrink every intermediate tuple so more fit per block (rule e); the most selective join is done first so the intermediate results stay small.

Consider the following database schema: R(A,B), S(B, C), T(C, D). Write a Relational Algebra Plan for the SQL query below. Your answer must be in the form of an expression first. Then convert it to a tree. Finally find the most optimized tree by pushing down selection(s) and projection(s) as much as possible.

SELECT R.A, T.D FROM T, S, R
WHERE T.C=S.C AND S.B=R.B AND T.D>20
Show worked answer

Expression (direct translation of FROM, WHERE, SELECT):

πR.A, T.D(σT.C=S.C ∧ S.B=R.B ∧ T.D>20(T × S × R))

Optimization: split the selection; T.D > 20 mentions only T, so push it onto T; the two equalities turn the products into joins R ⋈B S and (…) ⋈C T. Push projections: after R ⋈B S only A (output) and C (next join) are needed, so add πA,C; T must keep C and D.

πA, D( πA, C(R ⋈B S) ⋈C σD>20(T) )

(Projecting R or S alone gains nothing: R(A, B) and S(B, C) need all their attributes, A for the output, B and C for the joins.)

DB QB · 23-24 6b · 9 marks  |  BUET QBank · CSE 215 | L-2/T-1 | 2023–24 · 9 marks

For each of the following statements, determine whether it is true. If it is not, provide a counterexample to justify your answer. (i) δ(πL(R)) = πL(δ(R)). (ii) δ(σc(R)) = σc(δ(R)) (iii) πL(R ∪ S) = πL(R) ∪ πL(S)

Show worked answer

δ only matters for bags, so use bag semantics (π keeps duplicates).

(i) False. R(A, B) = {(1, 1), (1, 2)}, L = A. Left: πA(R) = {1, 1}, then δ gives {1}. Right: δ(R) = R (no duplicates), then πA gives {1, 1}. {1} ≠ {1, 1}: projection can create new duplicates after δ has run.

(ii) True. σ keeps or drops each tuple on its own and never changes a tuple. A tuple t appears in the left side once iff t satisfies c and occurs in R at least once; the same holds for the right side.

(iii) True, for sets and for bags. If t occurs m times in R and n times in S, R ∪ S (bag) has it m + n times; each copy projects to πL(t), so both sides contain πL(t) with the same total count. (For sets: πL(t) is in the left side iff some t in R or S projects to it, iff it is in πL(R) or πL(S).)

DB QB · 20-21 8a · 5 marks  |  BUET QBank · CSE 215 | L-2/T-2 | 2020–21 · 5 marks

Using an example show that, πa(R ∩ S) ≠ πa(R) ∩ πa(S)

Show worked answer

Let R(a, b) = {(1, 2)} and S(a, b) = {(1, 3)}. Then R ∩ S = ∅, so πa(R ∩ S) = ∅. But πa(R) = {1} and πa(S) = {1}, so πa(R) ∩ πa(S) = {1}. ∅ ≠ {1}. The tuples differ only in b; projecting first throws b away and makes them look equal. (So an optimizer may not push π below ∩.)

2. Estimating the size of a join

Cost-based optimization (Lec 07, Ch. 1) needs the sizes of intermediate results. The textbook (§16.4) estimates them from T and V, under two assumptions: values are uniformly distributed, and containment of value sets (if V(R, Y) ≤ V(S, Y), every Y-value of R also appears in S).

T(R ⋈ S) ≈ T(R)·T(S) / max(V(R, Y), V(S, Y))    (one join attribute Y)

Reason: a tuple of the relation with fewer Y-values meets, on average, T(other)/V(other, Y) matching tuples. Also: T(σA=c(R)) ≈ T(R)/V(R, A). Values of attributes not involved in the join keep their V (at most the size of the result).

DB QB · 21-22 5a · 15 marks  |  BUET QBank · CSE 215 | L-2/T-2 | 2021–22 · 15 marks

Consider the relations r1(A, B, C), r2(C, D, E), and r3(E, F). Assume that there are no primary keys. Let V(C, r1) be 900, V(C, r2) be 1100, V(E, r2) be 50, and V(E, r3) be 100. Assume that r1 has 1000 tuples, r2 has 1500 tuples, and r3 has 750 tuples. Compute the size r1 ⋈ r2 ⋈ r3.

Show worked answer

Step 1: r1 ⋈ r2 (join on C):

1000 × 1500 / max(900, 1100) = 1,500,000 / 1100 ≈ 1363.6

The intermediate result keeps r2's E-values: V(E, r1 ⋈ r2) = 50 (it cannot exceed V(E, r2)).

Step 2: (r1 ⋈ r2) ⋈ r3 (join on E):

1363.6 × 750 / max(50, 100) = 1,022,727 / 100 ≈ 10,227 tuples

Check with the other order: r2 ⋈ r3 = 1500 × 750 / max(50, 100) = 11,250; then ⋈ r1 on C: 11,250 × 1000 / max(1100, 900) = 10,227. The same, as it should be: in one formula, 1000 × 1500 × 750 / (1100 × 100) ≈ 10,227.

Note: the question bank's answer divides by 1100 at the end instead of by 100 and gets ≈ 1023, which is 10 times too small. The final division is by max(V(E, r12), V(E, r3)) = 100 only: 15,000/11 × 750/100 = 11,250,000/1,100 ≈ 10,227.

3. Selections that use indexes (Silberschatz's cost model)

Some questions come from Silberschatz, which charges tT per block transfer and tS per seek, and calls the height of a B+ tree index hi. With an index, a selection can be an index seek (Lec 07, Ch. 3) instead of a table scan:

  • Each level of the B+ tree costs one seek and one transfer (nodes are scattered on disk).
  • With a primary (clustering) index, matching records are contiguous: one seek, then sequential transfers.
  • With a secondary index, each matching record may be in a different block: one seek and one transfer per record.
BUET QBank · CSE 303 | L-3/T-1 | 2014–15 · 10 marks

Let tr and ts be the time to transfer a block of data and the time to seek a block in a disk subsystem, respectively. Estimate the query processing cost for: (a) A primary B+ tree index and equality on key. (b) A primary B+ tree index and comparison on key.

Show worked answer

Let hi = height of the B+ tree.

(a) Equality on the key (at most one matching record): traverse root to leaf, hi nodes, each one seek + one transfer; then fetch the one data block, one more seek + transfer:

Cost = (hi + 1)(tr + ts)

(b) Comparison on the key, e.g. A ≥ v: traverse to the first leaf entry with key ≥ v (hi(tr + ts)), then, because the file is sorted on the key (primary index), read the b blocks holding the matching records sequentially: one seek and b transfers:

Cost = hi(tr + ts) + ts + b·tr

(For A < v the index is not needed: scan the file from the start until the first record with A ≥ v, at cost ts + b·tr.) Example: hi = 3, ts = 4 ms, tr = 0.1 ms: (a) 4 × 4.1 = 16.4 ms; (b) with b = 50: 3 × 4.1 + 4 + 5 = 21.3 ms.

BUET QBank · CSE 215 | L-2/T-2 | 2018–19 · 7 marks

Explain the algorithm used to process the following SQL query given secondary indices on salary and district:

SELECT * FROM employee WHERE salary = 50000 OR district = 'Comilla'
Show worked answer

A disjunctive (OR) selection can use indexes only if every disjunct has one; here both do, so the DBMS uses disjunctive selection by union of record identifiers (Silberschatz algorithm A10):

  1. Index seek on the salary index for 50000: collect the set P1 of record pointers (RIDs).
  2. Index seek on the district index for 'Comilla': collect the pointer set P2.
  3. Compute P = P1 ∪ P2. A record satisfying both conditions appears once, so it is fetched and output once.
  4. Sort P by block address and fetch the records, reading each needed block once in disk order (fewer seeks than fetching in pointer order).

Cost ≈ the two index lookups + one block read per distinct block in P. If the conditions match many rows (low selectivity), so that P covers a large part of the table, a single table scan testing "salary = 50000 OR district = 'Comilla'" on every row is cheaper, and the optimizer should choose it. If only one of the two attributes had an index, the index would be useless for the OR, and a table scan would be required.

4. The hybrid hash join (textbook §15.5.6)

The two-pass hash join (Chapter 5) writes every bucket of both relations to disk. If memory is larger than one buffer per bucket, the hybrid hash join keeps some buckets of the smaller relation S in memory during phase 1, so the matching R tuples are joined immediately and neither side's bucket is ever written or reread.

  • Choose k buckets (k much less than M). Keep m of S's buckets entirely in memory and one buffer for each of the other k − m buckets: m·B(S)/k + k − m ≤ M.
  • Hash S: tuples of the m in-memory buckets stay in memory (with a search structure); the rest go to disk.
  • Hash R: a tuple whose bucket is in memory is joined at once; the rest go to disk buckets.
  • Phase 2: one-pass join of the k − m pairs of disk buckets.

Savings: 2 I/Os for every block of the in-memory buckets of both relations: 2(m/k)(B(R) + B(S)). The best choice is m = 1 with k as small as possible (buckets of about M blocks, k ≈ B(S)/M), giving

Hybrid hash join ≈ (3 − 2M/B(S))(B(R) + B(S)) disk I/Os; memory M ≥ √B(S)

DB QB · 23-24 5c · 11 marks  |  BUET QBank · CSE 215 | L-2/T-1 | 2023–24 · 11 marks

Describe the hybrid hash join algorithm. Compute the memory and I/O cost of the algorithm.

Show worked answer

Algorithm for R ⋈ S, S the smaller relation, M buffers:

  1. Pick k buckets and keep m of them for S in memory, so that m·B(S)/k + (k − m) ≤ M (in-memory buckets plus one output buffer per disk bucket).
  2. Hash S on the join attributes Y. Tuples hashing to buckets 1…m stay in memory, organized for fast lookup on Y; tuples of buckets m+1…k go through their buffers to disk.
  3. Hash R with the same function. A tuple t of R that hashes to bucket i ≤ m is probed against the in-memory S bucket and joined immediately (output); otherwise t goes to R's disk bucket i.
  4. Phase 2: for i = m+1…k, read Si into memory and stream Ri past it (one-pass join).

I/O cost. R and S are read once: B(R) + B(S). Only the fraction (k − m)/k of each is written and reread: 2(1 − m/k)(B(R) + B(S)). Total (3 − 2m/k)(B(R) + B(S)). Taking m = 1 and buckets of about M blocks (k ≈ B(S)/M): (3 − 2M/B(S))(B(R) + B(S)).

Memory: as for the hash join, approximately M ≥ √B(S): each disk bucket of S must fit in memory in phase 2.

Example (textbook Example 15.9): B(R) = 1000, B(S) = 500, M = 101. k = 5 would give S-buckets of 100 blocks, and 100 + 4 = 104 > 101 buffers, so take k = 6: one bucket of about 500/6 ≈ 83 blocks stays in memory, using 83 + 5 = 88 ≤ 101 buffers. Phase 1: read S (500), write 5 buckets (417); read R (1000), write 5/6 of it (833). Phase 2: read 417 + 833 = 1250. Total 1500 + 1250 + 1250 = 4000, against 4500 for the plain hash join. (Equivalently (3 − 2 × 1/6) × 1500 = 4000.)

Boundary cases: if S fits in memory (k = m), the cost is B(R) + B(S), a one-pass join; if no bucket can be kept (m = 0), it is the plain 3(B(R) + B(S)).
