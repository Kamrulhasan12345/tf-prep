Nested-Loop Joins: Tuple-Based and Block-Based

When neither relation fits in memory, the simplest join that still works is the nested-loop join. This chapter derives the cost of the tuple-based and block-based versions, works the slides' 1000/500/101 example both ways round, animates the memory chunks, and answers five exam questions on nested-loop joins.

1. "One and a half passes" (slide 2)

Nested-loop join
A family of join algorithms with two nested loops: an outer loop over one relation and an inner loop over the other. The tuples of one argument are read only once, while the other argument is read repeatedly, once per iteration of the outer loop. That is why the textbook calls them "one-and-a-half-pass" algorithms.

Properties (slide 2): they can be used for relations of any size; neither relation has to fit in main memory; M = 2 is sufficient (one buffer per relation). More memory only makes them faster.

2. Tuple-based nested-loop join (slide 3)

To compute R(X, Y) ⋈ S(Y, Z):

FOR each tuple s in S DO
    FOR each tuple r in R DO
        IF r and s join to make a tuple t THEN
            output t;

Cost. If we are careless about buffering, every (s, r) pair can cost a disk read: as much as T(R) × T(S) disk I/Os. If the inner relation is at least read a block at a time, each tuple s causes one scan of R, so the cost is about T(S) × B(R) + B(S); and if the outer relation is also handled a block at a time, every block of S meets every block of R once, so it drops to about B(R) × B(S). That last step is exactly the block-based algorithm below. The tuple-based join is still useful as an iterator (Lec 07, Chapter 5) and when an index on R's join attribute lets each s find its matches without scanning R.

3. Block-based nested-loop join (slides 4–5)

An improvement over the tuple-based join, assuming B(S) ≤ B(R) and B(S) > M (S does not fit; otherwise the one-pass join of Lec 07 is used). Two ideas:

  1. Access both relations by blocks, so each pass over R reads B(R) blocks, not T(R).
  2. Use as much memory as possible for the outer relation S: hold M − 1 blocks of S at once, so one pass over R serves M − 1 blocks' worth of S tuples.
FOR each chunk of M-1 blocks of S DO BEGIN
    read these blocks into main-memory buffers;
    organize their tuples into a search structure whose
        search key is the common attributes of R and S;
    FOR each block b of R DO BEGIN
        read b into main memory;
        FOR each tuple t of b DO BEGIN
            find the tuples of S in main memory that join with t;
            output the join of t with each of these tuples;
        END;
    END;
END;

The code looks like three loops, but there are really two: the outer one over (chunks of) S, and the inner one over R. The inner work is written as two loops only to stress that R is visited a block at a time, finishing each block before reading the next.

4. I/O cost (slides 6–7)

The slides' example (textbook Example 15.4): B(R) = 1000, B(S) = 500, M = 101. Use 100 buffers for chunks of S, so there are 500/100 = 5 chunks.

  • Each chunk: 100 disk I/Os to read the chunk of S, plus 1000 I/Os to read all of R in the inner loop.
  • Total = (500/100) × 1000 + 500 = 5 × 1000 + 500 = 5500.
  • If we read one block of S at a time instead of M − 1 (slide 6's "what if", and slide 5's question), the outer loop runs 500 times and each reads all of R: 500 × 1000 + 500 = 500,500 I/Os, about 91 times more. Using memory for big chunks is what makes the block-based join cheap.

The general formula (slide 7). With S the outer relation:

  • Number of outer iterations (chunks) = B(S)/(M − 1).
  • Each iteration reads M − 1 blocks of S and B(R) blocks of R.

I/Os = (B(S)/(M − 1)) × (M − 1 + B(R)) = B(S) + B(S)·B(R)/(M − 1)

≈ B(R)·B(S)/M when M is much smaller than B(R) and B(S). If B(S) ≤ M − 1, this is B(S) + B(R): the one-pass join.

When B(S) is not a multiple of M − 1, the last chunk is partial but still costs a full scan of R, so the exact count is B(S) + ⌈B(S)/(M − 1)⌉ · B(R). The calculators in this book use the ceiling.

Slide 7 question (worked answer): what if R is used in the outer loop instead of S?

Swap the roles: I/Os = B(R) + B(R)·B(S)/(M − 1). For the example: 1000 + (1000/100) × 500 = 1000 + 10 × 500 = 6000, against 5500 with S outside. The dominant term B(R)B(S)/(M − 1) is the same either way (5000); the difference is the once-only read of the outer relation, B(S) = 500 versus B(R) = 1000. So there is a slight advantage in putting the smaller relation in the outer loop, and the advantage is small. (The first exam question in Chapter 6, with B(R) = 8000, B(S) = 4000 and M = 101, shows how small the difference is: 324,000 against 328,000.)

The M for γ and δ is a loose approximation: γ really needs room for one entry per group and δ for one copy of each distinct tuple. Nested-loop join is quadratic in the sizes, which is why Lecture 08 goes on to two-pass algorithms whose cost is linear, 3(B(R) + B(S)). It remains useful when one relation is only a little bigger than memory, and as a subroutine when many tuples share one join value (Chapter 4).

BUET QBank · CSE 303 | L-3/T-1 | 2012–13 · 5 marks

Derive the total number of disk I/Os for nested loop join of two relations R and S, where the number of records in R is smaller than the number of records in S.

Show worked answer

R is smaller, so put R in the outer loop and S in the inner loop (the slides' derivation with the names swapped). Use the block-based nested-loop join with M buffers: M − 1 for a chunk of R, 1 for a block of S.

  1. R is split into chunks of M − 1 blocks: the outer loop runs B(R)/(M − 1) times.
  2. Each iteration reads its M − 1 blocks of R once, and then every block of S once: M − 1 + B(S) I/Os.
  3. Total = (B(R)/(M − 1)) × (M − 1 + B(S)) = B(R) + B(R)·B(S)/(M − 1) (exactly B(R) + ⌈B(R)/(M − 1)⌉·B(S)).

For large relations this is ≈ B(R)B(S)/M. With the smaller relation outside, the once-only term is B(R) rather than B(S), which is the cheaper choice. If B(R) ≤ M − 1, R fits in memory and the cost falls to B(R) + B(S). (For the tuple-based version with R outer: up to T(R)·T(S) if careless, or B(R) + T(R)·B(S) if S is read a block at a time.)

BUET QBank · CSE 303 | L-3/T-1 | 2013–14 · 3 marks

What is the I/O complexity of nested loop join?

Show worked answer

Nested-loop join is quadratic: its I/O cost is proportional to the product of the relation sizes. Tuple-based, it can be as much as T(R)·T(S). Block-based with M buffers and the smaller relation S outside, it is B(S) + B(S)·B(R)/(M − 1) ≈ B(R)·B(S)/M, that is, O(B(R)·B(S)/M). Only when the smaller relation fits in M − 1 buffers does it become linear, B(R) + B(S).

BUET QBank · CSE 303 | L-3/T-1 | 2014–15 · 10 marks

Let relation r1(A, B, C) and r2(C, D, E) have the following properties: r1 has 20,000 tuples, r2 has 45,000 tuples, 25 tuples of r1 fit on one block, and 30 tuples of r2 fit on one block. Estimate the number of block transfers and seeks required using: (a) Nested loop join. (b) Block nested loop join.

Show worked answer

This question uses the Silberschatz cost model, which counts seeks as well as block transfers, and assumes the worst case: memory holds only one block of each relation. Sizes: br1 = 20,000/25 = 800 blocks, br2 = 45,000/30 = 1,500 blocks.

(a) Tuple nested-loop join. For each outer tuple, the inner relation is scanned once (one seek, then binner sequential transfers); the outer relation is read once, a block at a time, with a seek per block because the disk head keeps moving to the inner relation.

  • Transfers = nouter × binner + bouter; seeks = nouter + bouter.
  • r1 outer: 20,000 × 1,500 + 800 = 30,000,800 transfers; 20,000 + 800 = 20,800 seeks.
  • r2 outer: 45,000 × 800 + 1,500 = 36,001,500 transfers; 46,500 seeks. So r1 should be the outer relation.

(b) Block nested-loop join. The inner relation is scanned once per outer block.

  • Transfers = bouter × binner + bouter; seeks = 2 × bouter (one to read the outer block, one to start the inner scan).
  • r1 outer: 800 × 1,500 + 800 = 1,200,800 transfers; 2 × 800 = 1,600 seeks.
  • r2 outer: 1,500 × 800 + 1,500 = 1,201,500 transfers; 3,000 seeks.

Best case (the smaller relation r1 fits in memory): both algorithms read each relation once: 800 + 1,500 = 2,300 transfers and 2 seeks. With M buffers and M − 2 used for the outer relation, block nested loop needs ⌈br1/(M − 2)⌉ × br2 + br1 transfers and 2⌈br1/(M − 2)⌉ seeks. (The slides use M − 1 for the outer relation because they do not count the output buffer.)

DB QB · 22-23 1a · 10 marks  |  BUET QBank · CSE 215 | L-2/T-1 | 2022–23 · 10 marks

Construct a one and a half pass algorithm for computing R ⟕ S natural join operation where ⟕ denotes the left outer join operation. Assume the R is the smaller relation. Compute the memory and disk I/O requirements.

Show worked answer

R ⟕ S keeps every tuple of R: joined with each matching S tuple, or, if no S tuple matches, padded with NULLs for S's attributes Z. A "one and a half pass" algorithm is a block nested-loop join; R is smaller, so R is the outer relation held in memory. That is also the natural choice for a left outer join, because the algorithm must remember which R tuples found a match, and an R tuple stays in memory for the whole scan of S.

FOR each chunk of M−1 blocks of R DO BEGIN
    read the chunk into memory; build a search structure on Y (the common attributes);
    give every R tuple in memory a flag matched := false;
    FOR each block b of S DO BEGIN          -- read into the last buffer
        FOR each tuple s of b DO
            FOR each tuple r in memory with r.Y = s.Y DO
                output (r, s); r.matched := true;
    END;
    FOR each tuple r in memory with r.matched = false DO
        output (r, NULL, …, NULL);           -- the dangling R tuples
END;

Why it is correct: during the scan of S every R tuple of the chunk meets every S tuple, so after the scan "matched = false" means "no S tuple joins with r", exactly the tuples to pad.

Memory: any M ≥ 2 works (one buffer of R, one of S). Disk I/O: R is read once and S once per chunk:

B(R) + ⌈B(R)/(M − 1)⌉ · B(S) ≈ B(R) + B(R)B(S)/(M − 1)

If B(R) ≤ M − 1 the whole of R fits, and it is a true one-pass algorithm costing B(R) + B(S). Example: B(R) = 500, B(S) = 1000, M = 101: 500 + 5 × 1000 = 5500 I/Os. (If the output buffer is counted, as in the bank's answer, use M − 2 in place of M − 1.)

Summary: nested-loop joins read one relation once and the other once per outer iteration, work for any sizes, and need only M ≥ 2. Tuple-based costs up to T(R)T(S). Block-based reads the smaller relation S in chunks of M − 1 blocks and scans R once per chunk: B(S) + ⌈B(S)/(M − 1)⌉B(R) ≈ B(R)B(S)/M (5500 for 1000/500/101; 6000 with R outside; 500,500 with one-block chunks). It equals the one-pass join when S fits in M − 1 buffers.
