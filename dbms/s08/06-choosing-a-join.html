Choosing a Join Algorithm: All the Costs Side by Side

Lectures 07 and 08 gave five ways to join two relations. This chapter puts their formulas and memory conditions in one table, gives a calculator that substitutes your numbers and picks the winner, and works the two exam questions that ask you to compare join algorithms.

1. The five joins in one table

Hash join (two-pass)3(B(R) + B(S))min(B(R), B(S)) ≤ M²Ch. 5

A practical decision rule follows from the table:

  1. If the smaller relation fits in M − 1 buffers, use the one-pass join (block nested loop then does the same thing).
  2. Otherwise, if two passes are possible, use hash join or sort-merge-join (both 3 I/Os per block). Hash join needs less memory; sort-merge-join gives sorted output and copes with skew.
  3. If only the larger relation is too big for sort-merge-join's sum rule, the simple sort-join (5 per block) or hash join still apply.
  4. Block nested loop is competitive only when the smaller relation is a small multiple of M (Example 15.4: 5500 versus 4500), and it is the fallback for any memory size and for tuples sharing one join value.

DB QB · 22-23 1b · 8 marks  |  BUET QBank · CSE 215 | L-2/T-1 | 2022–23 · 8 marks

Assume R and S are two database relations, the size of R and S in disk are B(R) = 8000, B(S) = 4000 and the number of available memory buffers is M = 101. Compute the I/O cost of the natural join operation for the following algorithms: (i) block based nested loop join, (ii) sort-based nested loop join, and (iii) hash-based nested-loop join.

Show worked answer

"Sort-based nested-loop join" and "hash-based nested-loop join" mean the sort-based join and the hash join. The smaller relation is S.

(i) Block-based nested-loop join, S (smaller) in the outer loop, chunks of M − 1 = 100 blocks:

B(S) + (B(S)/(M − 1))·B(R) = 4000 + (4000/100) × 8000 = 4000 + 40 × 8000 = 324,000

(With R outside: 8000 + 80 × 4000 = 328,000, slightly worse.)

(ii) Sort-based join. First check which version is possible with M = 101.

  • Efficient sort-merge-join needs B(R) + B(S) ≤ M²: 12,000 > 10,201. Counting sublists: ⌈8000/101⌉ + ⌈4000/101⌉ = 80 + 40 = 120 sublists, but only 101 buffers. Not possible in two passes.
  • Simple sort-join needs each relation to sort with TPMMS: 8000 ≤ 101 × 100 = 10,100 and 4000 ≤ 10,100. Possible. Cost: 4B(R) + 4B(S) to sort and store both, plus B(R) + B(S) to merge: 5 × 12,000 = 60,000 I/Os.

(iii) Hash join. Needs min(B(R), B(S)) ≤ M²: 4000 ≤ 10,201. With 100 buckets, S-buckets are about 40 blocks, which fit in the 100 available buffers. Cost: 3 × (8000 + 4000) = 36,000 I/Os.

Ranking: hash join 36,000 < sort-join 60,000 < block nested loop 324,000.

Note: the question bank's answer gives 332,000 for (i), because it reserves a buffer for output and uses chunks of M − 2 = 99 blocks (41 chunks of S: 4000 + 41 × 8000). That is a different convention from the slides, which do not count the output buffer. It also offers 36,000 as an "optimized" sort-merge cost, but that version is infeasible here (120 sublists > 101 buffers), so the sort-based answer with M = 101 is 60,000.

DB QB · 24-25 5d · 6 marks  |  BUET QBank · CSE 215 | L-2/T-1 | 2024–25 · 6 marks

Assuming no indexes exist, which one will you apply for faster operation: a Hash Join or a Sort-Merge Join? Explain why.

Show worked answer

Usually the hash join, for an equijoin of unsorted relations:

  • Same I/O, less memory. When both can run in two passes, both cost 3(B(R) + B(S)). But the hash join needs only M ≥ √min(B(R), B(S)), while sort-merge-join needs M ≥ √(B(R) + B(S)). So hash join runs in two passes in cases where sort-merge-join would need a third pass or must fall back to the 5(B(R) + B(S)) simple sort-join. Example: B(R) = 8000, B(S) = 4000, M = 101: hash join 36,000 I/Os, best sort-based join 60,000.
  • Less CPU: no sorting of whole sublists, just hashing each tuple once and probing.

Choose sort-merge-join instead when:

  • the inputs are already sorted on the join attribute (e.g. clustered on it): then the sorting passes are free and the merge costs only B(R) + B(S);
  • the result must be sorted on the join attribute (ORDER BY, or a later merge-based operator), since sort-merge produces sorted output;
  • the join values are skewed or have few distinct values, so some hash buckets would not fit in memory, whereas sorted runs are always balanced;
  • the condition is a range (non-equi) comparison such as R.a < S.b, which hashing cannot handle but a merge over sorted inputs can.

Note on the bank's answer: it argues that sort-merge costs "O(N log N)" I/Os. In the two-pass setting of this course both algorithms are linear, 3 I/Os per block; the real differences are memory, sortedness and skew, as listed above.

Summary: one-pass if the smaller relation fits; otherwise hash join or sort-merge-join at 3(B(R) + B(S)), with hash join needing only √min memory and sort-merge-join √sum but giving sorted output; simple sort-join at 5(B(R) + B(S)) when only √max memory is available; block nested loop B(S) + B(S)B(R)/(M − 1) when relations are small multiples of M or memory is tiny.
