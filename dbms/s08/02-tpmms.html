Two-Phase Multiway Merge Sort (TPMMS) and External Sorting

How to sort a relation far bigger than memory with only three disk I/Os per block. This chapter explains both phases, derives the memory limit B ≤ M(M − 1) and the cost 3B, corrects the slide's 1 GB example, extends the method to many passes, and works the eight external-sorting exam questions with an animator and calculators you can feed your own numbers.

1. The algorithm (slides 9–10)

Sorted sublist (run)
A sequence of blocks on disk whose tuples are in sorted order. Phase 1 produces runs of M blocks each.
Two-phase, multiway merge sort (TPMMS, also 2PMMS)
Sorts a relation R of B(R) > M blocks with M buffers in two phases:
  • Phase 1: repeatedly fill the M buffers with blocks of R from disk, sort them with any main-memory algorithm, and write the sorted sublist to disk.
  • Phase 2: merge all the sorted sublists into one sorted list, using one buffer per sublist and one buffer for output.

Phase 2 in detail. Assume there are at most M − 1 sublists. Allocate one memory block to each sublist and one block to the output, and keep a pointer into each input block to the first tuple not yet moved to the output. Then repeat:

  1. Find the smallest tuple among the first remaining tuples of all the input blocks. This is a main-memory operation: a linear search over at most M − 1 candidates, or a priority queue for O(log M) time.
  2. Move it to the first free position of the output block.
  3. If the output block is full, write it to disk and reuse the buffer for the next output block.
  4. If the input block it came from is now empty, read the next block of the same sorted sublist into that buffer. If the sublist has no more blocks, leave the buffer empty and ignore that sublist from now on.

Slide 9 question (worked answer): "Assume there are at most M − 1 sorted sublists. Constraint why?"

Phase 2 must see the current front of every sublist at the same time, because the smallest remaining tuple could be in any of them. So each sublist needs its own input buffer, and one more buffer holds the output block. With k sublists, phase 2 needs k + 1 ≤ M buffers, so k ≤ M − 1. With more sublists than that, a single merge is impossible and a third pass is needed (Section 4).

Interactive animation. Enter tuples (the first word is the sort key), the number of tuples per block and M. With few enough blocks you see pure TPMMS; with more than M(M − 1) blocks the animator automatically adds merge passes. Counters show the disk I/O.

2. Memory requirement (slide 11)

Each sublist is M blocks long, so phase 1 makes B(R)/M sublists. Phase 2 allows at most M − 1 of them:

B(R)/M ≤ M − 1  ⟹  B(R) ≤ M(M − 1)  ⟹  B(R) ≤ M² (for simplicity)  ⟹  M ≥ √B(R)

This is the striking fact about TPMMS: memory only has to grow like the square root of the data. Doubling M lets you sort four times as much in two passes.

3. I/O cost (slide 12)

  • Phase 1: read B(R) blocks, write B(R) blocks (the sublists).
  • Phase 2: read B(R) blocks (every block of every sublist, once).

TPMMS = 3B(R) disk I/Os, or 4B(R) if the sorted result must be stored on disk

As always (Lec 07, Chapter 4), the final write is left out because it is the same for every algorithm and the result is often pipelined.

Slide 13: the 1 GB example, and a correction

Blocks are 64 KB and memory is 1 GB. What is the largest R that TPMMS can sort?

  • M = 1 GB / 64 KB = 230/216 = 214 = 16K buffers (16,384).
  • B ≤ M² = (214)2 = 228 = 256M blocks.
  • Largest R = 256M blocks × 64 KB = 228 × 216 bytes = 244 bytes = 16 TB.

Correction: the slide writes the last line as "256M × 64K = 8 TB", and the textbook's Example 15.5 says 242 bytes = 4 TB because it takes 64 KB as 214. Both are arithmetic slips: 64 KB = 216 bytes, so the product is 244 bytes = 16 TB. (Using the exact bound M(M − 1) instead of M² gives 16,384 × 16,383 × 64 KB ≈ 15.999 TB, the same to three digits.) The lesson is unchanged: even a modest machine sorts almost any relation in two passes.

4. More than two passes (textbook §15.4.1, and the exam's "external sort-merge")

If B(R) > M(M − 1), phase 1 makes more than M − 1 sublists. The same idea then applies recursively: merge the sublists M − 1 at a time into longer runs, and repeat until one run is left. Each merge pass reads and writes every block once.

External sort-merge (Silberschatz's name)
The general algorithm: pass 0 makes ⌈B/M⌉ runs of M blocks; each later pass merges groups of M − 1 runs. Number of merge passes = ⌈logM−1⌈B/M⌉⌉.

Disk I/Os = B(2·⌈logM−1(B/M)⌉ + 1), plus B if the result is stored

TPMMS is the case of one merge pass: B(2 + 1) = 3B.

Derivation: pass 0 reads and writes B blocks (2B). Every merge pass except the last reads and writes B blocks (2B each). The last merge pass reads B blocks and its output is the result (not counted). With P merge passes: 2B + 2B(P − 1) + B = B(2P + 1).

Counting seeks (Silberschatz's model)

Some exam questions also count seeks and let each run use bb buffer blocks, so a run is read bb blocks at a time with one seek. Then the merge fan-in is ⌊M/bb⌋ − 1, and:

  • passes P = ⌈log⌊M/bb⌋−1(B/M)⌉;
  • transfers = B(2P + 1) (excluding the final write);
  • seeks = 2⌈B/M⌉ + ⌈B/bb⌉(2P − 1): two seeks per run in pass 0 (one read, one write of M contiguous blocks), then per merge pass one seek per bb blocks read and one per bb blocks written, without the final write.

DB QB · 19-20 3a · 20 marks  |  BUET QBank · CSE 215 | L-2/T-2 | 2019–20 · 15 marks

Memory size is M blocks and the number of blocks of a relation r is br. Find the number of runs N, number of merge passes, number of blocks transfer, and number of seeks to sort the relation r using external sort-merge algorithm for the following cases: i. Case 1: N < M   ii. Case 2: N = M   iii. Case 3: N > M

Show worked answer

In every case pass 0 reads M blocks at a time, so N = ⌈br/M⌉. A merge pass uses M − 1 input buffers and 1 output buffer (bb = 1), so it merges up to M − 1 runs. Counts below exclude writing the final result; add br transfers and br seeks if r_sorted is stored.

Merge passes PBlock transfersSeeks
Case 1: N < M, so N ≤ M − 11 (all runs merge at once: this is TPMMS)br(2·1 + 1) = 3br2N + br
Case 2: N = M⌈logM−1 M⌉ = 2 (M runs, only M − 1 input buffers)br(2·2 + 1) = 5br2N + 3br

Why the seeks: pass 0 needs one seek to read each run's M contiguous blocks and one to write it (2N). Each merge pass, with one block per buffer, needs a seek for every block read and every block written (2br), and the final pass has no write (br).

Case 2 note: ⌈logM−1 M⌉ = 2 for every M ≥ 3, because M − 1 < M ≤ (M − 1)². A smarter implementation would first merge just two runs (reading and writing only 2M blocks) and then merge the remaining M − 1 runs, but the standard formula charges full passes. Example: br = 1000, M = 10 gives N = 100 > M (Case 3), P = ⌈log9 100⌉ = 3, transfers 7000, seeks 200 + 5000 = 5200.

Note: the question bank's answer adds the final write in every case (4br, 6br, 2br(1 + P) transfers and 2N + 2brP seeks). That is right if the sorted relation is stored; say which convention you use.

DB QB · Jan 20 2a · 15 marks  |  BUET QBank · CSE 215 | L-2/T-2 | 2018–19 · 15 marks

The size of an unsorted relation r-unsorted is 36 blocks (B1, B2, B3, ..., B36) and the memory size to external sort merge the relation is 4 blocks. Show the diagram to sort the relation using the external sort merge algorithm and store it in the database as r-sorted. Using the diagram, explain the total number of blocks transfer needed to sort the relation and store it into the database.

Show worked answer

M = 4: pass 0 makes ⌈36/4⌉ = 9 runs of 4 blocks; merges are (M − 1) = 3-way, so pass 1 makes 3 runs of 12 blocks and pass 2 makes the single sorted run of 36 blocks.

Every pass reads all 36 blocks and writes all 36 blocks: 72 transfers per pass.

  • Pass 0 (run generation): 36 reads + 36 writes = 72.
  • Pass 1 (3-way merges into 3 runs): 36 + 36 = 72.
  • Pass 2 (final merge, written to the database as r-sorted): 36 + 36 = 72.

Total = 216 block transfers = 2br(1 + ⌈log3 9⌉) = 72 × 3. If the result were not stored, the last 36 writes would be dropped: 180 = 36 × (2·2 + 1).

BUET QBank · CSE 303 | L-3/T-1 | 2014–15 · 15 marks

Explain external sort-merge with an example. Show that the total number of block transfers for external sorting of a relation r is br(2⌈logM−1(br/M)⌉ + 1), where br is the number of blocks of relation r and M is the size of the main memory buffer.

Show worked answer

Algorithm. Pass 0: read M blocks, sort them in memory, write them as a run; repeat, giving ⌈br/M⌉ runs. Merge passes: with M − 1 input buffers and one output buffer, merge M − 1 runs at a time into one longer run (repeatedly move the smallest front tuple to the output; write the output buffer when full; refill an input buffer from its run when empty). Repeat merge passes until one run remains.

Example. br = 108, M = 5: pass 0 makes ⌈108/5⌉ = 22 runs (21 of 5 blocks, one of 3). 4-way merges: 22 → 6 → 2 → 1 run, so 3 merge passes. Transfers = 108 × (2·3 + 1) = 756 (864 if the result is written).

Proof of the formula.

  1. Each merge pass reduces the number of runs by a factor of M − 1 (rounding up). Starting from ⌈br/M⌉ runs, the number of merge passes needed to reach one run is ⌈logM−1(br/M)⌉.
  2. Pass 0 reads every block and writes every block: 2br.
  3. Each merge pass also reads and writes every block (2br), except that the final pass's output is the result, which (by convention) is not counted, so the final pass costs only br.
  4. Total = 2br + 2br⌈logM−1(br/M)⌉ − br = br(2⌈logM−1(br/M)⌉ + 1). ∎

(The symbol "C" in the question as printed is OCR damage of the ceiling bracket.)

BUET QBank · CSE 303 | L-3/T-1 | 2013–14 · 15 marks

Write down the steps of two-phase multiway merge sort. Consider a system where the block size is B bytes, memory size is M bytes, and record size is R bytes. What is the maximum number of records that can be sorted using two-phase merge sort? If the number of records exceeds this maximum, how can you sort them?

Show worked answer

Steps: as in Section 1: phase 1 fills memory, sorts, writes runs; phase 2 merges all runs with one input buffer each and one output buffer.

Maximum. Here M, B and R are in bytes. Memory holds k = ⌊M/B⌋ block buffers, and a block holds ⌊B/R⌋ records.

  • Phase 1 runs are k blocks long; phase 2 can merge at most k − 1 runs.
  • Largest relation: k(k − 1) blocks = ⌊M/B⌋(⌊M/B⌋ − 1) blocks.
  • Maximum records = ⌊B/R⌋ · ⌊M/B⌋ · (⌊M/B⌋ − 1) ≈ M²/(B·R).

Example: B = 64 KB, M = 1 GB, R = 100 bytes: k = 16,384, ⌊B/R⌋ = 655, maximum = 655 × 16,384 × 16,383 ≈ 1.76 × 1011 records.

More records than that: add passes. Use TPMMS to sort chunks of k(k − 1) blocks each into long sorted runs, then merge up to k − 1 of these long runs in a third pass (up to k(k − 1)² blocks), and so on: in general, external sort-merge with ⌈logk−1(blocks/k)⌉ merge passes. Each extra pass costs another 2 I/Os per block.

DB QB · 23 CT4 1 · 10 marks

Number of blocks = 1024. 16 pages are allocated to you. What is the number of merge steps if (a) bb = 1 (b) bb = 5 i.e. read 5 blocks at once.

Show worked answer

Pass 0 (run generation) uses all 16 pages: ⌈1024/16⌉ = 64 runs of 16 blocks.

(a) bb = 1. Each run gets 1 input page, plus 1 output page: fan-in = ⌊16/1⌋ − 1 = 15. Runs: 64 → ⌈64/15⌉ = 5 → 1. 2 merge passes. (Transfers 1024 × 5 = 5120; seeks 2 × 64 + 1024 × 3 = 3200, without the final write.)

(b) bb = 5. Every run, and the output, gets 5 pages: ⌊16/5⌋ = 3 groups, so fan-in = 3 − 1 = 2 (1 page is left unused). Runs: 64 → 32 → 16 → 8 → 4 → 2 → 1. 6 merge passes. (Transfers 1024 × 13 = 13,312; seeks 128 + ⌈1024/5⌉ × 11 = 128 + 205 × 11 = 2383.)

So bigger buffers per run mean fewer seeks per pass but a smaller fan-in, and therefore more passes. Use the seek calculator above to try other values.

DB QB · 23 CT4 2 · 10 marks

In [23 CT4 1]'s b, your friend suggested to use the extra page that is being wasted as output. Are there any hidden drawbacks to this? If yes, calculate the exact cost.

Show worked answer

The friend's plan: 3 input groups of 5 pages (15 pages) and the spare page as a 1-page output buffer. Fan-in becomes 3, so the runs go 64 → 22 → 8 → 3 → 1: 4 merge passes instead of 6, which saves transfers. The hidden drawback: the output is now written one block at a time, so every output block costs its own seek, instead of one seek per 5 blocks. Seeks are by far the expensive part of a disk access.

Summary: TPMMS: phase 1 sorts M blocks at a time into sublists; phase 2 merges up to M − 1 sublists with one input buffer each and one output buffer. It needs B(R) ≤ M(M − 1) ≈ M², i.e. M ≥ √B(R), and costs 3B(R) (4B(R) if the result is stored). 1 GB of 64 KB buffers sorts up to 244 bytes = 16 TB (not 8 TB or 4 TB). Larger inputs need ⌈logM−1(B/M)⌉ merge passes and B(2P + 1) I/Os; with bb-block buffers the fan-in drops to ⌊M/bb⌋ − 1 but seeks fall.
