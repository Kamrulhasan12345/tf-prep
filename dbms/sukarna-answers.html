Answering Sukarna sir's questions

This page skips the theory. It covers how to write answers that get full marks: every question type from Sukarna sir's half (Lec 01–08) in DB QB 2017–18 to 2024–25 and the older CSE 303 bank, and for each one, how to spot it, the steps to write on paper, a model answer, and where marks get lost.

How to drill each card (about 10 minutes): (1) read the italic question, (2) write your answer on paper using the template, (3) open Model answer and compare, (4) check yourself against the red Marks lost by list. When you get stuck on a concept, follow the Practice link to the chapter.

1. Eight rules for every answer in this half

  1. Verdict first and last. Open with the answer (“Not conflict-serializable”) and end with it boxed, plus the reason in a few words (“cycle T₁ → T₂ → T₁”). Markers look for it before they read your working.
  2. Use a trace table instead of paragraphs for anything step by step: locks, timestamps, wait-die, recovery, closures. One row per action, with columns action · check · result. A table is quicker to write and easier to mark.
  3. State your convention before using it: “S lock before each read, X lock before each write, locks held until commit”, “chunks of M − 1 blocks, output not counted”, “bag semantics”. If the bank uses a different convention, a stated one still gets the marks.
  4. Name the rule each time you apply it: “U1: log record before data”, “wait-die: older waits”, “TS < RT(X) → write too late → rollback”. Each named rule shows the marker you know why the step is right.
  5. Write “Show / Prove” answers in four parts: Definitions → Claim → Argument (numbered steps) → ∎. Most of the marks are for writing the definitions correctly.
  6. Answer “Define / Explain with example” in three parts: a one-sentence definition, a tiny concrete example, and one line on why it matters. Count about one point per 2 marks: a 5-mark question wants 3 points.
  7. For “Construct a schedule that is X but not Y”, give the schedule and then check both properties out loud: why it is X, and why it is not Y.
  8. Number questions: write the formula first, then the formula with the numbers put in, then the result with units (I/Os, tuples, runs). If the arithmetic slips, the first two lines still earn most of the marks.

3. Lec 01 · FDs, keys and normal forms (162 marks over 7 years)

Card 1 · Closure: does an FD follow? Is X a key?

Asked: 24-25 1b (10, compulsory) · 17-18 7a (10) · CSE303 16-17

TEMPLATE
  1. For each set X, write X⁺ as a chain: “start {B, C}; BC → E adds E; BE → D adds D; …; nothing more fires.”
  2. Does X → Y follow? Yes if Y ⊆ X⁺, no otherwise. Say which attribute is missing.
  3. Is X a key? Two checks, both written down: (a) X⁺ = R, so X is a superkey; (b) for each subset of X with one attribute removed, the closure ≠ R, so X is minimal.
  4. Verdict line for each part.

R(A, B, C, D, E), FDs A → C, BE → D, CD → A, BC → E, AD → B. (i) Do BC → AD and AC → BD follow? (ii) Are {A, B} and {A, E} keys?

Model answer

(i) (BC)⁺: start {B, C}; BC → E adds E; BE → D adds D; CD → A adds A. (BC)⁺ = ABCDE ⊇ AD, so BC → AD follows.

(AC)⁺: start {A, C}; A → C adds nothing; every other FD needs B, D or E. (AC)⁺ = {A, C}, which lacks B and D, so AC → BD does not follow.

(ii) (AB)⁺: A → C adds C; BC → E adds E; BE → D adds D: ABCDE, a superkey. Subsets: A⁺ = AC, B⁺ = B, neither is R. {A, B} is a key.

(AE)⁺: A → C adds C; nothing else fires: ACE ≠ R. {A, E} is not even a superkey, so not a key.

MARKS LOST BY
  • Checking only “superkey” and forgetting minimality when the question asks “key”.
  • Writing X⁺ = … with no chain of FDs, so the marker cannot see why.

Card 2 · All nontrivial FDs, all keys, superkeys that are not keys

Asked: 21-22 3b · 20-21 7c (15) · CSE303 10-11, 11-12, 15-16 (the standard textbook three-part question)

TEMPLATE
  1. Classify the attributes: on no right side → in every key; only on right sides → in no key. Write this sentence; it cuts down the work.
  2. Closure table of the subsets (all 15 for four attributes; skip supersets of known keys). Columns: X · X⁺.
  3. (i) FDs: for each X, the FDs are X → A for every A in X⁺ − X. List them, single attribute on the right.
  4. (ii) Keys: the smallest X with X⁺ = R.
  5. (iii) Superkeys that are not keys: every proper superset of a key. Count them as a check.

R(A, B, C, D), FDs AB → C, C → D, D → A. (i) All nontrivial FDs (single attribute on the right). (ii) All keys. (iii) Superkeys that are not keys.

Model answer

B appears on no right side, so B is in every key. Closures (only the useful rows): C⁺ = ACD, D⁺ = AD, AB⁺ = ABCD, AC⁺ = ACD, BC⁺ = ABCD, BD⁺ = ABCD, CD⁺ = ACD, A⁺ = A, B⁺ = B.

(i) 14 FDs: C → A, C → D, D → A, AB → C, AB → D, AC → D, BC → A, BC → D, BD → A, BD → C, CD → A, ABC → D, ABD → C, BCD → A.

(ii) B⁺ = B is not a superkey; AB, BC, BD all have closure ABCD. Keys: AB, BC, BD.

(iii) ABC, ABD, BCD, ABCD.

MARKS LOST BY
  • Listing trivial FDs (AB → A), or listing FDs whose left side contains an attribute already on the right.
  • Missing FDs whose left side has three attributes (ABC → D counts).
  • Skipping the closure table: without it the lists look guessed.

Card 3 · Count superkeys as a function of n

Asked: 24-25 1a (3, compulsory) · CSE303 15-16 (6)

TEMPLATE
  1. “A superkey is any set that contains a key.”
  2. One key of k attributes: the other n − k attributes are free, so there are 2ⁿ⁻ᵏ superkeys.
  3. Two keys K₁, K₂: inclusion–exclusion: 2ⁿ⁻|K₁| + 2ⁿ⁻|K₂| − 2ⁿ⁻|K₁ ∪ K₂|.
  4. Check with the smallest n by listing the sets.

(i) Only key is A₁. (ii) Only keys are {A₁, A₂} and {A₁, A₃}.

Model answer

(i) A₁ plus any subset of the other n − 1: 2ⁿ⁻¹.

(ii) Containing {A₁, A₂}: 2ⁿ⁻². Containing {A₁, A₃}: 2ⁿ⁻². Containing both ({A₁, A₂, A₃}): 2ⁿ⁻³. Total 2ⁿ⁻² + 2ⁿ⁻² − 2ⁿ⁻³ = 3 · 2ⁿ⁻³. Check n = 3: A₁A₂, A₁A₃, A₁A₂A₃ = 3 ✓.

(Keys {A₁} and {A₂, A₃}: 2ⁿ⁻¹ + 2ⁿ⁻² − 2ⁿ⁻³.)

MARKS LOST BY
  • Adding the two counts without subtracting the overlap.

Card 4 · BCNF decomposition

Asked: 24-25 2a (16) · 21-22 3c (10–20) · 20-21 7b (10) · 17-18 7b (15) · CSE303 10-11, 12-13, 15-16. The most frequent long question in Lec 01.

TEMPLATE
  1. Keys of R (use Card 2's classification trick).
  2. Violations: for each FD X → Y write X⁺; if X⁺ ≠ R, it is a violation. List them all if asked.
  3. Split on one violation X → Y: R₁ = X⁺, R₂ = X ∪ (R − X⁺).
  4. Project the FDs onto each piece (closures of subsets, kept inside the piece). Write each piece's FDs and key.
  5. Repeat on any piece that still violates BCNF.
  6. Final schema with keys underlined, then one closing line: “lossless (BCNF splits always are); dependency preserving? yes/no, because FD … spans pieces.”

R(A, B, C, D, E), FDs AB → C, DE → C, B → D. Decompose into BCNF; show the final schema with keys.

Model answer

Key. A, E are on no right side. (AE)⁺ = AE; (ABE)⁺: B → D, AB → C → ABCDE. ACE⁺ = ACE, ADE⁺ = ACDE. Only key: ABE.

Violations. AB⁺ = ABCD, DE⁺ = CDE, B⁺ = BD: none = R, so all three FDs violate BCNF.

Split on AB → C: R₁ = ABCD, R₂ = AB ∪ E = ABE. R₂: no nontrivial FDs, key ABE, BCNF. R₁: AB → C, B → D (DE → C needs E), key AB; B → D violates.

Split R₁ on B → D: R₃ = BD (key B), R₄ = ABC (AB → C, key AB). Both BCNF.

Final: R₂(A, B, E), R₃(B, D), R₄(A, B, C). Lossless. Not dependency preserving: DE → C has no piece containing D, E and C.

MARKS LOST BY
  • Splitting as (X, Y) and (R − Y) without using X⁺: correct only when X⁺ = X ∪ Y.
  • Copying the original FDs onto a piece instead of projecting them (missed derived FDs, or FDs that mention missing attributes).
  • No keys in the final schema (“including all keys” is in the question for a reason).

Card 5 · Is the decomposition lossless?

Asked: 19-20 8c (5–10) · inside many BCNF/3NF questions

TEMPLATE
  1. Two pieces: compute (R₁ ∩ R₂)⁺. Lossless iff it contains R₁ or R₂ (“the common attributes are a key of one piece”).
  2. Three or more pieces: chase tableau: one row per piece, plain letters for its attributes, subscripted otherwise; apply FDs to equate; lossless iff some row becomes all plain.
  3. Verdict line.

R(A, B, C, D, E) → (A, B, C), (A, D, E); FDs A → BC, CD → E, B → D, E → A.

Model answer

R₁ ∩ R₂ = {A}. A⁺: A → BC adds B, C; B → D adds D; CD → E adds E: A⁺ = ABCDE ⊇ R₁. A is a key of R₁, so the decomposition is lossless.

MARKS LOST BY
  • Saying “lossless because they share A” without computing A⁺: sharing an attribute is not enough.

Card 6 · Canonical cover, then 3NF synthesis

Asked: CSE303 16-17 (9) · 3NF synthesis is the follow-up in normalization questions

TEMPLATE
  1. Split right sides into single attributes; drop duplicates.
  2. Redundant FDs: for each FD X → A, compute X⁺ using the other FDs. If A is in it, delete the FD. Write one line per test.
  3. Shrink left sides: for XY → A, if X⁺ (using all FDs) contains A, replace it with X → A.
  4. 3NF synthesis: one relation per left side (X plus everything it determines) → if no relation contains a key of R, add one that is a key → drop relations contained in another.
  5. Closing line: “3NF synthesis is lossless and dependency preserving.”

R(A, B, C), F = {A → BC, B → C, A → B, AB → C}. (a) Canonical cover. (b) Lossless decomposition and the normal forms of the pieces.

Model answer

(a) Split: A → B, A → C, B → C, AB → C. Tests: A → B: A⁺ without it = AC, keep. A → C: A⁺ without it = ABC, remove. B → C: B⁺ = B, keep. AB → C: (AB)⁺ under {A → B, B → C} = ABC, remove. Fc = {A → B, B → C}.

(b) Key A. Synthesis: R₁(A, B), R₂(B, C). R₁ contains the key A, so nothing is added. Lossless: R₁ ∩ R₂ = B and B → C (B is a key of R₂). Both pieces are in BCNF (and so 3NF). The original R was only 2NF (B → C is transitive).

MARKS LOST BY
  • Testing an FD for redundancy with itself still in the set (everything looks redundant).
  • Forgetting the “add a key relation” step.

Card 7 · Normalize a real table up to 3NF

Asked: 23-24 2a (15) · 22-23 7a (20) · 21 CT2 (14) · Jan 20 8 (10) · CSE303 13-14, 14-15. The highest-mark Lec 01 question.

TEMPLATE (8 parts; each one is usually worth marks)
  1. Why normalize (if asked): remove redundancy and the update / insertion / deletion anomalies. Give one example of each from their table.
  2. Assumptions you read from the rows (“an invoice has one date: 211347's rows agree”).
  3. FDs, each with its evidence from the rows.
  4. Key of the whole table.
  5. Dependency diagram: key attributes in boxes on top; arrows below; label each arrow partial or transitive.
  6. 1NF: atomic values, one row per (key), repeating groups removed. Write the 1NF schema.
  7. 2NF: one new table per part of the key that has a partial dependency.
  8. 3NF: one new table per transitive dependency. Final schema: PK underlined, FKs marked with “→ Table”.

INVOICE table: INV_NUM, PROD_NUM, SALE_DATE, PROD_LABEL, VEND_CODE, VEND_NAME, QUANT_SOLD, PROD_PRICE (one row per product line of an invoice).

Model answer (condensed)

FDs: INV_NUM → SALE_DATE; PROD_NUM → PROD_LABEL, VEND_CODE, PROD_PRICE; VEND_CODE → VEND_NAME; INV_NUM, PROD_NUM → QUANT_SOLD. Key {INV_NUM, PROD_NUM}.

Diagram: partial: INV_NUM → SALE_DATE, PROD_NUM → PROD_LABEL, VEND_CODE, PROD_PRICE. Transitive: VEND_CODE → VEND_NAME.

1NF: INVOICE_LINE(INV_NUM, PROD_NUM, SALE_DATE, PROD_LABEL, VEND_CODE, VEND_NAME, QUANT_SOLD, PROD_PRICE).

2NF: INVOICE(INV_NUM, SALE_DATE); PRODUCT(PROD_NUM, PROD_LABEL, VEND_CODE, VEND_NAME, PROD_PRICE); LINE(INV_NUM, PROD_NUM, QUANT_SOLD).

3NF: INVOICE(INV_NUM, SALE_DATE); PRODUCT(PROD_NUM, PROD_LABEL, VEND_CODE → VENDOR, PROD_PRICE); VENDOR(VEND_CODE, VEND_NAME); LINE(INV_NUM → INVOICE, PROD_NUM → PRODUCT, QUANT_SOLD).

MARKS LOST BY
  • No dependency diagram when the question says “by drawing dependency diagram”.
  • Jumping straight to 3NF without writing the 1NF and 2NF stages.
  • Unstated assumptions: if the table is ambiguous (can a price change?), write the assumption you chose.
  • Checking 2NF against only the primary key when the table has other candidate keys.

Card 8 · “A table in 3NF but not in BCNF”

Asked: 23-24 1c (9, compulsory) · Jan 20 14 (10) · 19-20 8b · 17-18 7c · CSE303 13-14, 14-15. Learn one example by heart.

TEMPLATE
  1. Write “Yes, I agree” if the question asks for agreement, then give the two definitions (BCNF: every nontrivial X → Y has X a superkey; 3NF: or every attribute of Y − X is prime).
  2. Schema + FDs + keys.
  3. 3NF check: the bad FD's right side is prime.
  4. BCNF check: its left side is not a superkey.
  5. Two sample rows that show the redundancy.
  6. Fix: decompose on the bad FD; mention which FD is lost.
Model answer

Bookings(title, theatre, city), FDs: theatre → city; title city → theatre. Keys: {title, city} and {title, theatre}, so all three attributes are prime.

3NF: theatre → city has a prime right side (city); title city → theatre has a key on the left. In 3NF.

Not BCNF: theatre⁺ = {theatre, city} ≠ R, so theatre is not a superkey.

Redundancy: (Antz, Guild, Menlo Park), (Shrek, Guild, Menlo Park): Guild's city is stored once per movie.

BCNF design: Theatre(theatre, city) and Showing(theatre, title). Lossless (theatre is a key of Theatre). Price: title city → theatre is no longer enforceable in one table.

MARKS LOST BY
  • Giving an example that is not even 3NF (the right side of the bad FD is not prime).
  • Skipping the “modify the design” half.

Card 9 · Lec 01 theory short answers

Asked: anomalies (CSE303 11-12, 12-13, 13-14) · six rules (19-20 8d) · BCNF/3NF/4NF (CSE303 10-11, 17 marks) · MVD (17-18 7c) · two-attribute BCNF (CSE303 15-16) · PK choice (CSE303 13-14)

READY ANSWERS
  1. Anomalies (use one table for all three: Student(id, name, dept, deptHead)): redundancy: deptHead is repeated per student; update: changing a head means changing many rows, and missing one makes the data inconsistent; deletion: deleting the last student of a department loses its head; insertion: a new department cannot be stored until it has a student.
  2. Six rules with one example each: reflexivity (Y ⊆ X ⇒ X → Y), augmentation (X → Y ⇒ XZ → YZ), transitivity, union (X → Y, X → Z ⇒ X → YZ), decomposition (X → YZ ⇒ X → Y), pseudotransitivity (X → Y, YW → Z ⇒ XW → Z). Close with: “the first three are Armstrong's axioms, sound and complete; the last three are derived from them.”
  3. BCNF / 3NF / 4NF: one definition each, then: 4NF ⊂ BCNF ⊂ 3NF ⊂ 2NF ⊂ 1NF. BCNF may lose FDs, 3NF never does; 4NF also removes redundancy from MVDs.
  4. MVD X ↠ Y: for any two tuples that agree on X, swapping their Y values gives two tuples that are also in R. Example: Course(course, teacher, book), course ↠ teacher (teachers and books are independent).
  5. Any two-attribute relation R(A, B) is in BCNF: four cases: no nontrivial FD; only A → B (A is a key); only B → A (B is a key); both (both are keys). In every case, each nontrivial FD has a key on the left. ∎
  6. Choosing a PK: unique, never NULL, minimal, stable (never changes), short. Multivalued attribute: move it to its own table (owner key, value) with key on both.

4. Lec 02 · Serializability and 2PL (108 marks)

Card 10 · Precedence graph: conflict-serializable?

Asked: 24-25 1d (8, compulsory) · 22-23 1c (12, compulsory) · 21-22 7c · 19-20 4a · Jan 20 1b · 17-18 2a (21) · 6 CSE303 years

TEMPLATE
  1. Rule sentence: “Arc Tᵢ → Tⱼ when an action of Tᵢ precedes a conflicting action of Tⱼ on the same element (different transactions, at least one write).”
  2. Go element by element: write each element's actions in order, then its arcs. Write “r–r: no arc” where it applies; it shows the marker you checked.
  3. Draw the graph (circles + arrows).
  4. Cycle? Name it: “T₃ → T₄ → T₃, so not conflict-serializable.”
  5. Acyclic? Give the topological order(s). “All equivalent serial schedules” = every topological order; list them all.

(i) r₁(A); w₂(A); w₃(A); w₂(B); r₂(C); r₂(B); w₂(C)   (ii) w₁(A); r₂(A); w₂(B); r₂(B); w₃(C); r₄(C); w₄(D); r₃(D); r₁(C)

Model answer

(i) A: r₁, w₂, w₃ → 1→2, 1→3, 2→3. B, C: only T₂. Arcs {1→2, 1→3, 2→3}: acyclic. Conflict-serializable, order (T₁, T₂, T₃) (the only topological order).

(ii) A: w₁ before r₂ → 1→2. B: only T₂. C: w₃ before r₄ → 3→4; w₃ before r₁ → 3→1; r₄, r₁ both reads: no arc. D: w₄ before r₃ → 4→3. Cycle 3 → 4 → 3: not conflict-serializable.

MARKS LOST BY
  • Drawing an arc for two reads.
  • Drawing arcs only between neighbouring actions: every pair on the element counts (w₁ … w₃ also gives 1→3).
  • Giving one serial order when the question asks for all.

Card 11 · Serializable but not conflict-serializable; counting schedules

Asked: 23-24 5a (12, compulsory) · 24-25 2b (6–9) · CSE303 12-13

TEMPLATE
  1. Do Card 10 first. Acyclic ⇒ both serializable and conflict-serializable; done.
  2. Cyclic ⇒ check view-equivalence with each candidate serial order: same reads-from for every read, and the same last writer for every element. A match ⇒ serializable (this needs blind writes).
  3. Counting: total interleavings = C(n₁ + n₂, n₁). Find the conflicting pairs; a schedule is bad when two conflicts point in opposite directions. Count the bad ones; a small table of all schedules is the safest proof.

(ii) w₁(X); w₂(Y); w₁(Y); w₂(X); w₃(X) — serializable, conflict-serializable, both?

Model answer

X: w₁, w₂, w₃ → 1→2, 1→3, 2→3. Y: w₂ before w₁ → 2→1. Cycle 1 → 2 → 1: not conflict-serializable.

No reads, so only the last writers matter: X by T₃, Y by T₁. Serial (T₂, T₁, T₃) leaves Y = T₁'s value and X = T₃'s value. Serializable, equivalent to (T₂, T₁, T₃), because of the blind writes.

Counting example (T₁: r₁(A); w₁(B), T₂: r₂(A); w₂(A); w₂(B)): C(5, 2) = 10 schedules; conflicts r₁(A)/w₂(A) and w₁(B)/w₂(B); 3 schedules have them in opposite directions. Answer: 10 possible, 7 conflict-serializable, 7 serializable (the 3 bad ones match no serial order's reads-from + last writer).

MARKS LOST BY
  • Saying “cycle ⇒ not serializable”. A cycle only rules out conflict-serializable.

Practice → Conflicts · Serial and serializable

Card 12 · Transform to serial by swapping

Asked: CSE303 10-11, 14-15, 15-16 (20 marks)

TEMPLATE
  1. Get the target serial order from the precedence graph (Card 10).
  2. Move actions one adjacent swap at a time. After each swap, write the new schedule and the reason: “r₁(B) ↔ w₂(A): different elements, no conflict”.
  3. End with the serial schedule, and “verified by the precedence graph: arcs only T₁ → T₂”.

r₁(A); w₁(A); r₂(A); w₂(A); r₁(B); w₁(B); r₂(B); w₂(B)

Model answer

Arcs: A gives 1→2, B gives 1→2. Target (T₁, T₂).

r₁(A) w₁(A) r₂(A) w₂(A) r₁(B) w₁(B) r₂(B) w₂(B) r₁(A) w₁(A) r₂(A) r₁(B) w₂(A) w₁(B) r₂(B) w₂(B) r₁(B)↔w₂(A): different elements r₁(A) w₁(A) r₁(B) r₂(A) w₂(A) w₁(B) r₂(B) w₂(B) r₁(B)↔r₂(A): different elements r₁(A) w₁(A) r₁(B) r₂(A) w₁(B) w₂(A) r₂(B) w₂(B) w₁(B)↔w₂(A): different elements r₁(A) w₁(A) r₁(B) w₁(B) r₂(A) w₂(A) r₂(B) w₂(B) w₁(B)↔r₂(A): different elements

Result: the serial schedule (T₁, T₂), so the original is conflict-serializable.

MARKS LOST BY
  • Swapping two actions of the same transaction, or two conflicting actions.
  • Jumping several positions at once without showing each swap.

Card 13 · Proofs: 2PL ⇒ conflict-serializable; strict 2PL ⇒ ACR

Asked: 24-25 1c (9, compulsory) · 23-24 7a (10) · 23-24 5b and 22-23 1d (5, compulsory) · CSE303 12-13

TEMPLATE: 2PL ⇒ conflict-serializable (induction on n)
  1. Definitions: 2PL = every lock precedes every unlock in each transaction; conflict-serializable = conflict-equivalent to a serial schedule.
  2. Basis n = 1: already serial.
  3. Step: let uᵢ(X) be the first unlock in S, by Tᵢ. Claim: every action of Tᵢ can be swapped to the front.
  4. Contradiction: suppose wⱼ(Y) comes before a conflicting wᵢ(Y). Then … wⱼ(Y) … uⱼ(Y) … lᵢ(Y) … wᵢ(Y). Since uᵢ(X) is first, uᵢ(X) ≤ uⱼ(Y) < lᵢ(Y): Tᵢ locks after unlocking, which breaks 2PL.
  5. So S ≡ (Tᵢ's actions)(the rest); the rest is a 2PL schedule of n − 1 transactions, serializable by the hypothesis. ∎ Serial order = order of first unlocks.
TEMPLATE: strict 2PL ⇒ ACR
  1. Definitions: strict 2PL = 2PL and X locks are held until after commit/abort; ACR = transactions read only committed values.
  2. Tⱼ reads X last written by Tᵢ. Tᵢ held xlᵢ(X) to write; Tⱼ needs slⱼ(X), which conflicts, so it must wait for uᵢ(X).
  3. Strictness: uᵢ(X) comes after Tᵢ commits or aborts. Committed ⇒ Tⱼ reads a committed value. Aborted ⇒ X was restored first, so Tⱼ reads the earlier committed value.
  4. No dirty reads ⇒ ACR. ∎

When “define strict 2PL” comes first (24-25 1c), give the definition, then the proof. A timeline line helps: xlᵢ(X) wᵢ(X) … [Tⱼ waits] … cᵢ uᵢ(X) slⱼ(X) rⱼ(X).

MARKS LOST BY
  • Proving with one example: an example is not a proof.
  • Missing the definitions (half the marks in a 5-mark question).

Card 18 · Lec 03 theory: timestamps vs locks, MVCC, isolation levels

Asked: 23-24 7c (13) · 21-22 6c (15) · CSE303 13-14 (granularity, B+ tree locking)

READY ANSWERS
  1. Timestamps win when most transactions are read-only or conflicts are rare (no lock overhead, no deadlock). Locking wins when conflicts are frequent: locks delay transactions, while timestamps roll them back and waste work.
  2. MVCC rules: each write creates a version Xt with WT = t. A read by T returns the version with the largest WT ≤ TS(T), and never rolls back. A write by T is rolled back if the version T would overwrite (largest WT ≤ TS(T)) has RT > TS(T). Versions older than every active transaction can be deleted. Example: TS 1 reads A₀ even after T₂ wrote A₂.
  3. Isolation levels (one example schedule each): read uncommitted: may read uncommitted data (dirty read: T₂ reads T₁'s write, then T₁ aborts). Read committed: no dirty reads, but reading the same row twice can give two values (a non-repeatable read). Repeatable read: re-reads match, but new rows can appear (phantoms). Serializable: none of these.
  4. Lock granularity: large items (a whole table) mean little lock overhead but low concurrency; small items (rows) mean high concurrency but many locks. Intention locks (IS, IX) let both coexist.
  5. Trees: 2PL holds the root lock until the end, so it serializes everyone. Tree protocol: first lock anywhere, then lock a node only while holding its parent, release any time, never relock.

  2. Phases, numbered: what is read, the in-memory structure, what its search key is (whole tuple for ∪ ∩ − δ; grouping attributes for γ; join attributes for ⋈).
  3. Per-tuple action: output / discard / update the count.
  4. Why it is correct: one line (“equal tuples hash to the same bucket, so comparing bucket i with bucket i is enough”).
  5. Cost and memory: one-pass B(R) + B(S), needs min(B) ≤ M − 1. Two-pass 3(B(R) + B(S)), needs √ of the right quantity.

Two-pass hash-based R − S; memory and disk I/O.

Model answer

Phase 1: hash R on the whole tuple into M − 1 buckets, writing them to disk; same for S with the same h.

Phase 2: for each i: load Sᵢ into memory (hash table on the whole tuple); stream Rᵢ; output each tuple not found in the table.

Correct: equal tuples go to the same bucket index, so R − S = ⋃(Rᵢ − Sᵢ).

I/O 2(B(R) + B(S)) + (B(R) + B(S)) = 3(B(R) + B(S)). Memory: each Sᵢ ≈ B(S)/(M − 1) ≤ M − 1 ⇒ B(S) ≤ M² (approx.; load the smaller of each pair).

MARKS LOST BY
  • No memory condition: “analyze memory” is half the question.
  • Keying the structure on the wrong attributes.

Card 33 · RA law true/false; min and max tuples

Asked: 23-24 6b (9) · 20-21 8a (5) · 21-22 4c / 20-21 8d (8)

TEMPLATE
  1. State the semantics (bags or sets).
  2. False → the smallest counterexample: two tuples, computed on both sides, and “{1} ≠ {1, 1}”.
  3. True → a one-line argument per tuple (“σ keeps or drops each tuple independently”).
  4. Min/max: table expression · min · max · when.
Model answer

δ(πA(R)) = πA(δ(R)): false. R = {(1,1), (1,2)}: left {1}, right {1, 1}.

δ(σc(R)) = σc(δ(R)): true. πL(R ∪ S) = πL(R) ∪ πL(S): true for bags and sets.

πa(R ∩ S) ≠ πa(R) ∩ πa(S): R = {(1, 2)}, S = {(1, 3)}: left ∅, right {1}.

Bags: A ∩ B: 0 to min(nₐ, n_b); σ(A) − B: 0 to nₐ; A ∪ B: exactly nₐ + n_b; A ⟕ B: nₐ to nₐ·max(n_b, 1).

Card 34 · Lec 07–08 theory short answers

Asked: NLJ vs block NLJ (24-25 8a) · hash vs sort-merge (24-25 5d) · hybrid hash (23-24 5c, 11) · subsystems (CSE303 12-13) · pipelining (19-20 3b, 21-22 8a) · index cost (CSE303 14-15) · OR with indexes (18-19)

READY ANSWERS
  1. Tuple NLJ vs block NLJ: tuple-based: for each tuple of R, scan S: up to T(R)·T(S) I/Os. Block-based: read M − 1 blocks of the smaller S, then scan R once per chunk: B(S) + B(S)B(R)/(M − 1). Same result, far fewer I/Os.
  2. Hybrid hash join: while partitioning S, keep k buckets in memory; R tuples that hash to them join at once, so those buckets are never written or re-read. Cost ≈ (3 − 2M/B(S))(B(R) + B(S)). Memory: k buckets + buffers for the rest.
  3. Query-processing subsystems: parser (parse tree) → preprocessor (semantic check, views) → logical plan generator → rewriter / optimizer (cost-based, uses catalog statistics) → physical plan → execution engine (iterators) using the buffer manager.
  4. Iterators and pipelining: Open / GetNext / Close; each operator pulls tuples from its children, so no intermediate result is written to disk. Blocking operators (sort, γ, set difference) must read their whole input before output, so they gain little; δ can pipeline by outputting the first copy it sees.
  5. Index costs (tT transfer, tS seek, hi height): primary B+ equality on key (hi + 1)(tT + tS); comparison hi(tT + tS) + tS + b·tT. salary = x OR district = y with two secondary indexes: get both pointer sets, take their union, then fetch the records (sort the pointers first to save seeks).
