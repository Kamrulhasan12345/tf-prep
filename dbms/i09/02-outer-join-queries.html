Answering Questions with Outer Joins

Slides 7–19 use the four join types to answer four questions about makers: PCs and laptops, PCs but not laptops, laptops but not PCs, and PCs or laptops. The key pattern is the anti-join: an outer join followed by IS NULL. The chapter ends with slide 19's puzzle, "Can you write it? Why or why not?", worked in full.

All queries use the tables of slide 3: PC = {(1001, A), (1002, B), (1003, C)} and Laptop = {(2001, A), (2002, B), (2003, D)}. So A and B make both, C makes only PCs and D makes only laptops.

1. Makers of both PCs and laptops: inner join (slides 7–9)

A maker sells both exactly when some PC row and some laptop row have that maker, that is, when the PC row survives an inner join on maker (slide 8's result has rows for A and B). Slide 9 projects onto the maker:

SELECT DISTINCT PC.maker
FROM   PC INNER JOIN Laptop
       ON PC.maker = Laptop.maker;          -- A, B

DISTINCT matters as soon as a maker has several models: a maker with 3 PCs and 3 laptops produces 3 · 3 = 9 joined rows. On the full computer database of Lecture 08 this same question was answered with INTERSECT; both give the same set.

2. Makers of PCs but not laptops: the anti-join (slides 10–12)

The left outer join of slide 11 keeps every PC. A PC whose maker has a laptop is matched, so its Laptop columns are filled in. A PC whose maker has no laptop is dangling, so its Laptop columns are NULL. Therefore "maker has no laptop" is the same as "Laptop.maker IS NULL in the left join":

SELECT DISTINCT PC.maker
FROM   PC LEFT OUTER JOIN Laptop
       ON PC.maker = Laptop.maker
WHERE  PC.maker IS NOT NULL
AND    Laptop.maker IS NULL;                -- C
Anti-join
The rows of one table that have no match in another. Pattern: A LEFT JOIN B ON condition WHERE B.key IS NULL. The IS NULL test must be on a column of B that can never be NULL in a real B row (its key, or the join column), so that NULL can only mean "padded".

Why does slide 12 also test PC.maker IS NOT NULL? On this data it changes nothing, since every PC row has a maker. It protects against a PC stored with an unknown maker: that row would be dangling too (NULL = anything is never true), and without the test the answer would contain a NULL "maker". You must use IS NULL, never = NULL: a comparison with NULL is unknown, so Laptop.maker = NULL would be true for no row at all (Lecture 10, Chapter 1).

3. Makers of laptops but not PCs (slides 13–15)

The mirror image: the right outer join keeps every laptop, and the laptops whose maker has no PC have NULL in the PC columns (slide 14's last row).

SELECT DISTINCT Laptop.maker
FROM   PC RIGHT OUTER JOIN Laptop
       ON PC.maker = Laptop.maker
WHERE  PC.maker IS NULL
AND    Laptop.maker IS NOT NULL;            -- D

Writing FROM Laptop LEFT OUTER JOIN PC ON … with the same WHERE gives the same answer. This is the outer-join version of Lecture 08's laptop MINUS pc.

4. Makers of laptops or PCs or both (slides 16–19)

The full outer join (slide 17) contains every maker somewhere: A and B in matched rows, C in a row whose Laptop columns are NULL, D in a row whose PC columns are NULL. The difficulty is that the maker's name sits in different columns in different rows. Slide 18 collects it from both columns with two queries and a UNION:

SELECT DISTINCT PC.maker
FROM   PC FULL OUTER JOIN Laptop ON PC.maker = Laptop.maker
WHERE  PC.maker IS NOT NULL
UNION
SELECT DISTINCT Laptop.maker
FROM   PC FULL OUTER JOIN Laptop ON PC.maker = Laptop.maker
WHERE  Laptop.maker IS NOT NULL;            -- A, B, C, D

(The DISTINCTs are not needed, because UNION removes duplicates anyway; they do no harm.)

Question (worked answer): slide 19, "Can you write it? Why or why not?"

Slide 19 proposes a single query instead of the union:

SELECT DISTINCT PC.maker
FROM   PC FULL OUTER JOIN Laptop ON PC.maker = Laptop.maker
WHERE  PC.maker IS NOT NULL
OR     Laptop.maker IS NOT NULL;

No, this is wrong. The WHERE clause is fine: every row of the full join has at least one maker, so all 4 rows pass. The problem is the SELECT list. It always outputs PC.maker, and in the row for D (the laptop-only maker) PC.maker is NULL. The result is A, B, C, NULL: D is lost and a NULL appears in its place. The slide's circle around PC.maker marks exactly this.

The fix is to output whichever of the two maker columns is not NULL. Oracle's NVL(a, b) returns a unless it is NULL, in which case it returns b (COALESCE(a, b) is the standard equivalent):

SELECT DISTINCT NVL(PC.maker, Laptop.maker) AS maker
FROM   PC FULL OUTER JOIN Laptop ON PC.maker = Laptop.maker;   -- A, B, C, D

No WHERE clause is needed, since every row of the full join has a maker in at least one column. Of course, the simplest correct answer needs no join at all: SELECT maker FROM PC UNION SELECT maker FROM Laptop.

Summary: "both" is an inner join; "A but not B" is an anti-join, a left (or right) outer join keeping only the rows where B's columns are NULL (test with IS NULL on a B column that is never NULL in real rows); "either" is a full outer join, where the value may sit in either table's columns, so output NVL(left.col, right.col).
