Exam Topics Beyond the Slides: Views, Privileges and Roles

Two topics that the exams ask about but Lectures 3–5 do not teach. Views are stored queries that behave like tables; the exam asks what goes wrong when rows are inserted through one. Privileges and roles control who may read or change which table; three exam questions ask you to create users and roles and grant and revoke privileges. Each topic is taught briefly first, then the questions are worked in full.

1. Views

View
A named query that can be used like a table. It is the second of SQL's three kinds of relations (Lec 03, Chapter 2): its rows are not stored; they are computed from the base tables each time the view is used, so a view is always up to date.
CREATE VIEW Gadget AS
SELECT pname, price, manufacturer
FROM   Product
WHERE  category = 'Gadgets';

SELECT * FROM Gadget WHERE price > 20;      -- use it like a table
CREATE OR REPLACE VIEW Gadget AS …;         -- change its definition
DROP VIEW Gadget;                            -- remove it (the base table is untouched)

Uses of views: hiding complexity (a long query written once and reused by name), security (grant users access to a view that shows only some columns or rows, but not to the base table), and logical data independence (if the base tables are reorganised, the view can be redefined so that programs using it keep working).

Changing data through a view

Because a view stores no rows, an INSERT, UPDATE or DELETE on a view must be translated into changes of its base tables. That is only possible when each view row corresponds to exactly one base-table row that can be identified. Oracle allows modification through a view when:

  • the view is defined on one table (or, for a join view, the change affects only one key-preserved table: a table whose key is still a key of the view), and
  • the view has no DISTINCT, GROUP BY, aggregate functions, set operators (UNION, MINUS…), and the changed columns are plain columns, not expressions; and
  • for an INSERT, every NOT NULL column of the base table without a default is in the view.

Two more details: columns not in the view get NULL (or their DEFAULT) when inserting through it, and an inserted row may not satisfy the view's WHERE condition, so it "disappears" from the view right after it was inserted. WITH CHECK OPTION at the end of the view definition forbids such inserts and updates; WITH READ ONLY forbids all changes. (The playground's SQLite never allows changes through views, so only queries on views can be tried there.)

Exam question

BUET QBank · CSE 303 | L-3/T-1 | 2016–17 · 5 marks

Given the customer/account/transaction schema, a view is created:

customer(customer_id, name, street, city)
account(account_number, type, balance)
transaction(customer_id, account_number, date, amount)

CREATE VIEW cust_balance AS
  SELECT a.customer_id, balance
  FROM customer AS a, account AS b, transaction AS c
  WHERE a.customer_id = c.customer_id
    AND b.account_number = c.account_number;

Discuss the possible problems if insertion is allowed through the view cust_balance.

Show worked answer

The view combines three tables: for every transaction, it pairs the customer who made it with the balance of the account it was made on. A view row (customer_id, balance) is therefore derived from one customer row, one account row and one transaction row. Inserting a row such as ('C9', 5000) through the view would have to be turned into inserts into the base tables, and that causes these problems:

  1. Missing key values. The view has no account_number. To store the balance 5000, an account row must be created, but its primary key account_number is unknown and cannot be NULL, so the insert into account is impossible. The transaction row that should link them also needs account_number (and date, amount), which the view does not supply.
  2. Missing other values. A new customer row would get only customer_id; name, street and city become NULL (and fail if any is NOT NULL). The account type is unknown.
  3. Ambiguity. If customer C9 already exists, should a new customer row be inserted or the existing one used? Which existing account (if any) has balance 5000, or should a new one be made? Many different base-table changes would produce the same view row, so the DBMS cannot choose one.
  4. Several tables at once. One view row needs rows in three tables. Oracle allows a change through a join view only if it affects a single key-preserved table. Here neither customer nor account is key-preserved (one customer has many transactions, so customer_id is not a key of the view; one account has many transactions, so neither is account_number), so Oracle rejects the insert (ORA-01779 / ORA-01776).
  5. The row might not appear. Even if rows were inserted into customer and account, the new view row appears only if a matching transaction row exists. Without it the inserted row would immediately vanish from the view, and the user could not see the result of the insert.
  6. Duplicates and meaning. The view may already show the same (customer_id, balance) several times (one per transaction); an inserted duplicate has no clear meaning in the base tables.

Conclusion: cust_balance is a join view without the keys of the base tables, so insertion through it should not be allowed; changes must be made directly on customer, account and transaction. (Small syntax note: Oracle does not accept AS before a table alias; in Oracle write FROM customer a, account b, transaction c. Also date is a reserved word in Oracle, so a real table would need another column name.)

2. Privileges and roles (textbook §10.1)

Privilege
A permission to perform an action. Object privileges apply to one table or view: SELECT, INSERT, UPDATE, DELETE (and REFERENCES, ALTER, INDEX). System privileges allow actions on the database as a whole, such as CREATE SESSION (log in) or CREATE TABLE.
GRANT / REVOKE
GRANT privileges ON object TO user_or_role [WITH GRANT OPTION]; gives privileges; WITH GRANT OPTION lets the receiver pass them on. REVOKE privileges ON object FROM user_or_role; takes them back.
Role
A named set of privileges. Privileges are granted to the role, and the role is granted to users (or to other roles). A user holds every privilege of every role granted to them.
CREATE USER U1 IDENTIFIED BY pass1;      -- Oracle: a user needs a password
GRANT CREATE SESSION TO U1;              -- allow U1 to log in
CREATE ROLE clerk;
GRANT SELECT, INSERT ON Student TO clerk;
GRANT clerk TO U1;
REVOKE INSERT ON Student FROM clerk;     -- U1 loses INSERT too

Why roles? In an organisation many users need the same access, and access follows the job, not the person. Without roles, giving 50 clerks access to a new table takes 50 GRANT statements, and a clerk who changes job must have each privilege revoked one by one, which invites mistakes. With roles, privileges are granted once to the role; adding or removing a user is one GRANT or REVOKE of the role; changing what clerks may do is one GRANT or REVOKE on the role, and every member follows at once. Roles also make it easy to check who can do what, and to follow the principle of least privilege.

Exam questions

BUET QBank · CSE 215 | L-2/T-1 | 2023–24 · 10 marks

Why are roles used for assigning privileges to users? Create three users U1, U2, and U3 and assign them INSERT and UPDATE privileges on tables T1 and T2 by assigning them a role of "Admin". Then transfer these privileges to another role named "Super-Admin". Finally, revoke the UPDATE privilege from "Admin".

Show worked answer

Why roles: a role groups privileges under one name. Privileges are granted once to the role and the role is granted to users, so (1) many users get the same access with one GRANT each, (2) changing the access of a whole group is one GRANT/REVOKE on the role, (3) when a user changes job, one REVOKE of the role removes all of its privileges, and (4) access mirrors job functions, which makes it easier to audit and to keep to least privilege. Fewer statements mean fewer mistakes.

Statements (Oracle):

-- 1. users (Oracle requires a password; CREATE SESSION lets them log in)
CREATE USER U1 IDENTIFIED BY u1pass;
CREATE USER U2 IDENTIFIED BY u2pass;
CREATE USER U3 IDENTIFIED BY u3pass;
GRANT CREATE SESSION TO U1, U2, U3;

-- 2. role Admin with INSERT and UPDATE on T1 and T2, given to the users
CREATE ROLE Admin;
GRANT INSERT, UPDATE ON T1 TO Admin;
GRANT INSERT, UPDATE ON T2 TO Admin;
GRANT Admin TO U1, U2, U3;

-- 3. "transfer" the privileges to a second role
CREATE ROLE Super_Admin;
GRANT INSERT, UPDATE ON T1 TO Super_Admin;
GRANT INSERT, UPDATE ON T2 TO Super_Admin;

-- 4. revoke UPDATE from Admin
REVOKE UPDATE ON T1 FROM Admin;
REVOKE UPDATE ON T2 FROM Admin;

Resulting state: Admin (and therefore U1, U2, U3) has INSERT on T1 and T2; Super_Admin has INSERT and UPDATE on T1 and T2.

Why step 3 grants the privileges directly. A shorter alternative is GRANT Admin TO Super_Admin;, which makes Super_Admin inherit whatever Admin has. But then step 4 would also take UPDATE away from Super_Admin, since it holds UPDATE only through Admin. Granting the privileges to Super_Admin directly keeps them independent, which is what "transfer these privileges" intends. (A name with a hyphen, Super-Admin, would have to be written as a quoted identifier, "Super-Admin"; an underscore avoids that.)

BUET QBank · CSE 303 | L-3/T-1 | 2014–15 · 13 marks

Why are roles used for assigning privileges to users? Create three users U1, U2 and U3 and assign INSERT and UPDATE privileges to them on tables T1 and T2 respectively. Do this by assigning the users a role of "Admin". Then transfer these privileges to another role named "SuperAdmin". Finally, revoke UPDATE privilege from "Admin".

Show worked answer

Why roles: as in the previous question: privileges are granted once to a named role and the role to users, so groups of users are managed with single statements, access follows job functions, changes apply to all members at once, and errors and forgotten privileges are less likely.

"INSERT and UPDATE … on tables T1 and T2 respectively" means INSERT on T1 and UPDATE on T2.

CREATE USER U1 IDENTIFIED BY u1pass;
CREATE USER U2 IDENTIFIED BY u2pass;
CREATE USER U3 IDENTIFIED BY u3pass;
GRANT CREATE SESSION TO U1, U2, U3;

CREATE ROLE Admin;
GRANT INSERT ON T1 TO Admin;
GRANT UPDATE ON T2 TO Admin;
GRANT Admin TO U1, U2, U3;

CREATE ROLE SuperAdmin;
GRANT INSERT ON T1 TO SuperAdmin;
GRANT UPDATE ON T2 TO SuperAdmin;

REVOKE UPDATE ON T2 FROM Admin;

Final state: Admin, and so U1, U2 and U3, can only INSERT into T1; SuperAdmin can INSERT into T1 and UPDATE T2. As before, granting the privileges to SuperAdmin directly (instead of GRANT Admin TO SuperAdmin) keeps SuperAdmin's UPDATE when it is revoked from Admin.

BUET QBank · CSE 303 | L-3/T-1 | 2013–14 · 8 marks

Create three users U1, U2 and U3 and assign them SELECT and DELETE privileges respectively on T1 and T2 tables. Do this by assigning the users a role of "Admin". Then transfer these privileges to another role named "SuperAdmin".

Show worked answer

"SELECT and DELETE privileges respectively on T1 and T2" means SELECT on T1 and DELETE on T2.

CREATE USER U1 IDENTIFIED BY u1pass;
CREATE USER U2 IDENTIFIED BY u2pass;
CREATE USER U3 IDENTIFIED BY u3pass;
GRANT CREATE SESSION TO U1, U2, U3;

CREATE ROLE Admin;
GRANT SELECT ON T1 TO Admin;
GRANT DELETE ON T2 TO Admin;
GRANT Admin TO U1, U2, U3;

CREATE ROLE SuperAdmin;
GRANT SELECT ON T1 TO SuperAdmin;
GRANT DELETE ON T2 TO SuperAdmin;

U1, U2 and U3 now hold SELECT on T1 and DELETE on T2 through Admin; SuperAdmin holds the same two privileges directly. Since this question has no later REVOKE, GRANT Admin TO SuperAdmin; is an acceptable alternative for the last step: SuperAdmin then receives exactly Admin's privileges through the role. If "transfer" is meant as "move", finish with REVOKE SELECT ON T1 FROM Admin; REVOKE DELETE ON T2 FROM Admin; (and then the role-to-role alternative must not be used, because SuperAdmin would lose the privileges too).

The question bank's answers to these three questions use generic SQL without passwords; Oracle's CREATE USER requires IDENTIFIED BY, and users need CREATE SESSION to log in.

SQL exercises (views)

Summary: a view is a named, stored query; using it substitutes its definition into the query. Changes through a view are possible only when each view row maps to one identifiable row of one base table (no joins of non-key-preserved tables, DISTINCT, grouping or expressions); join views such as cust_balance cannot accept inserts. Privileges (SELECT, INSERT, UPDATE, DELETE on objects; CREATE SESSION etc.) are given with GRANT and taken back with REVOKE. Roles bundle privileges so groups of users are managed with single statements; a privilege held only through a role disappears when it is revoked from that role.
