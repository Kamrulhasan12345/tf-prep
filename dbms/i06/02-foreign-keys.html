Foreign Keys: Linking a Table to Another

A foreign key says "this value must be the key of some row over there". This chapter defines foreign keys and referential integrity on the slides' Department and Employee tables, explains why the master table must be created first and why a foreign key may only reference a PRIMARY KEY or UNIQUE column, and shows the two ways to declare one in Oracle.

1. The rule: a departmental head must be an employee (slide 10)

Slide 10 has two tables. Employee(id, name, address, gender) lists the employees, with id as primary key. Department(name, head) lists the departments, and head holds the id of the employee who heads the department: CSE is headed by employee 2 (B), EEE by employee 4 (D), ME by employee 1 (A).

The business rule is: a departmental head must be an employee. In table terms, every non-NULL value in Department.head must appear in Employee.id. Without a constraint nothing stops a row like ('CE', 5), headed by an employee who does not exist.

Foreign key
A column (or set of columns) of one table whose values must match the primary key or a UNIQUE key of some row in another table (or the same table), or be NULL.
Master table (parent table, referenced table)
The table being pointed at: Employee. The slides call it the master table and mark its column "PK/UK".
Foreign table (child table, referencing table)
The table that holds the foreign key: Department. The slides call it the foreign table and mark its column "FK".
Referential integrity
The property that every reference points at something that exists: no dangling foreign-key values. A foreign-key constraint is how SQL makes the DBMS enforce it.

2. Only a PRIMARY KEY or UNIQUE column can be referenced (slide 10)

Slide 10 states: "foreign keys, which reference attributes of a second relation, can only reference PRIMARY or UNIQUE KEY". The reason is that a reference must identify exactly one row. If Department.head referred to Employee.name, and two employees were both called "B", the head of CSE would be ambiguous; and the DBMS would need to search the whole table to check every insert. A key column guarantees at most one match, and Oracle already has a unique index on it, so each check is one index lookup.

If you try to reference a column that is neither, Oracle refuses the CREATE TABLE with ORA-02270: no matching unique or primary key for this column-list. SQLite accepts the CREATE TABLE and complains later, at the first INSERT, with foreign key mismatch:

3. Create the master table first (slide 11)

Because Department refers to Employee, Employee must exist before Department is created. The slide creates it like this (Oracle accepts INT and turns it into NUMBER(38)):

CREATE TABLE Employee (
  id      INT PRIMARY KEY,
  name    CHAR(20),
  address CHAR(20),
  gender  CHAR(1)
);

In Oracle, creating Department first fails with ORA-00942: table or view does not exist, because the REFERENCES clause is checked when the table is created. (SQLite is lazier: it accepts the CREATE TABLE and only fails when a row is inserted. Do not rely on that habit in an Oracle exam.) The same order applies to data: master rows first, then the rows that point at them. And when tables are dropped, the order reverses: DROP TABLE Employee fails with ORA-02449: unique/primary keys in table referenced by foreign keys while Department still refers to it. Drop Department first, or write DROP TABLE Employee CASCADE CONSTRAINTS, which drops the foreign-key constraints that point at Employee (the Department rows stay).

4. Declaring the foreign key: column form (slide 12)

CREATE TABLE Department (
  name CHAR(3),
  head INT REFERENCES Employee(id)
);

REFERENCES Employee(id) written after the column's type is a column constraint: it says that this one column refers to Employee.id. The word FOREIGN KEY does not appear in this form. If the column list is left out, REFERENCES Employee means Employee's primary key.

5. Declaring the foreign key: table form (slide 13)

CREATE TABLE Department (
  name CHAR(3),
  head INT,
  FOREIGN KEY (head) REFERENCES Employee(id)
);

This is the table constraint form. It means exactly the same thing. It is required when the foreign key has several columns, which must match a composite key of the master table column by column:

CREATE TABLE Section (course_id VARCHAR2(8), sec_id NUMBER(2), room VARCHAR2(10),
                      PRIMARY KEY (course_id, sec_id));
CREATE TABLE Takes (student_id NUMBER(7), course_id VARCHAR2(8), sec_id NUMBER(2),
                    FOREIGN KEY (course_id, sec_id) REFERENCES Section(course_id, sec_id));

Either form can be given a name, which Oracle shows in its error messages and which you need later to drop the constraint (Chapter 7):

CREATE TABLE Department (
  name CHAR(3),
  head INT CONSTRAINT dept_head_fk REFERENCES Employee(id)        -- named column constraint
);
-- or:  CONSTRAINT dept_head_fk FOREIGN KEY (head) REFERENCES Employee(id)

Question: may a foreign key be NULL?

Yes, unless the column is also declared NOT NULL. A NULL head means "this department has no head at the moment"; it does not point anywhere, so there is nothing to check. Oracle treats a composite foreign key as satisfied as soon as any of its columns is NULL (the standard's default "MATCH SIMPLE" rule). Chapter 4 uses this: ON DELETE SET NULL puts NULL into the foreign key on purpose.

Summary: A foreign key makes every non-NULL value of a child column match the PRIMARY KEY or UNIQUE key of a row in the master table; that is referential integrity. Only key columns can be referenced, because a reference must name exactly one row. Create (and fill) the master table first, drop it last. Declare the key inline with REFERENCES T(col) or as a table constraint FOREIGN KEY (cols) REFERENCES T(cols); the second form is needed for composite keys.
