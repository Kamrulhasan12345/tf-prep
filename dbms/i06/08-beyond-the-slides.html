Exam Topics Beyond the Slides: Kinds of Integrity Constraints and Deferred Checking

Two topics the slides do not name but exams and Oracle practice need: the classification of integrity constraints (domain, entity, key, referential, general), which the compulsory "create a table with all types of integrity constraints" question asks for, and deferrable constraints, which solve the chicken-and-egg problem of two tables that refer to each other.

1. The kinds of integrity constraints

Textbooks group the constraints of this lecture into a few families. When a question says "all types of integrity constraints", it means one example of each:

Domain constraint
Restricts the values a single attribute may take: its data type and size (NUMBER(3,2), VARCHAR2(50)), NOT NULL, DEFAULT, and an attribute-based CHECK (cgpa BETWEEN 0 AND 4). In standard SQL a reusable domain is CREATE DOMAIN (slide 51's VALUE keyword), which Oracle lacks.
Entity integrity constraint
Every row is identifiable: the PRIMARY KEY is unique and never NULL.
Key constraint
Alternate keys are unique: UNIQUE (usually with NOT NULL). Some books fold this into entity integrity.
Referential integrity constraint
References point at existing rows: FOREIGN KEY … REFERENCES …, with a referential action (ON DELETE CASCADE / SET NULL).
General (semantic) constraint
Any other business rule: tuple-based CHECK across columns of a row; assertions across rows and tables (standard SQL); triggers in Oracle.

2. Deferred constraint checking

Every constraint so far was checked immediately, at the end of each statement. Sometimes no order of statements can satisfy that. The classic case is a cycle of foreign keys:

CREATE TABLE Department (name CHAR(3) PRIMARY KEY, head INT NOT NULL);
CREATE TABLE Employee   (id INT PRIMARY KEY, name VARCHAR2(20),
                         dept CHAR(3) NOT NULL REFERENCES Department(name));
ALTER TABLE Department ADD CONSTRAINT dept_head_fk
  FOREIGN KEY (head) REFERENCES Employee(id);

Every employee must belong to an existing department, and every department must have an existing head. To start a new department CE with a new employee 5 as head, you need both rows at once: inserting the employee first fails (no department CE), inserting the department first fails (no employee 5), and NULL is forbidden. The chicken needs the egg and the egg needs the chicken.

Deferrable constraint
A constraint whose check may be postponed until the transaction COMMITs. During the transaction it may be temporarily violated; at COMMIT it must hold, otherwise the whole transaction is rolled back.
INITIALLY IMMEDIATE / INITIALLY DEFERRED
Whether a deferrable constraint starts each transaction checked per statement (IMMEDIATE, the default) or at commit (DEFERRED). A transaction can switch with SET CONSTRAINT name DEFERRED or SET CONSTRAINTS ALL DEFERRED.
-- Oracle
ALTER TABLE Department ADD CONSTRAINT dept_head_fk
  FOREIGN KEY (head) REFERENCES Employee(id)
  DEFERRABLE INITIALLY DEFERRED;

INSERT INTO Department VALUES ('CE', 5);       -- no employee 5 yet: allowed
INSERT INTO Employee   VALUES (5, 'E', 'CE');  -- CE exists: immediate FK OK
COMMIT;                                        -- dept_head_fk checked now: OK

If the second INSERT is forgotten, COMMIT fails with ORA-02091: transaction rolled back followed by ORA-02291: integrity constraint (…DEPT_HEAD_FK) violated - parent key not found, and both rows are gone. Constraints are NOT DEFERRABLE unless declared otherwise, and this cannot be changed later with ALTER (drop and re-create the constraint). The textbook covers this in §7.1.3.

Deferral is also Oracle's answer to the missing ON UPDATE CASCADE (Chapter 4): with a deferred foreign key, UPDATE Employee SET id = 9 WHERE id = 4; UPDATE Department SET head = 9 WHERE head = 4; COMMIT; works, because the dangling moment between the two updates is never checked.

In the playground. SQLite supports DEFERRABLE INITIALLY DEFERRED for foreign keys only (not for CHECK, UNIQUE or PRIMARY KEY), and has no SET CONSTRAINT(S) statement. The deferral only matters inside an explicit transaction BEGIN; … COMMIT; (otherwise every statement is its own transaction). One difference from Oracle: when COMMIT fails, SQLite leaves the transaction open instead of rolling it back, so run ROLLBACK; before trying again.

3. The compulsory question

DB QB · 24-25 5b · 13 marks · compulsory

Create a table SQL from a real life scenario, where you need to apply all types of integrity constraints.

Show worked answer

Scenario: course registration at a university. Departments offer courses; students belong to a department and enrol in courses each term. Rules: department codes and names are unique; every student has a unique id and a unique e-mail; CGPA lies between 0 and 4; a student's level is 1–4; a course's credit is one of 0.75, 1.5, 3, 4 and its contact hours are at least its credit; grades come from a fixed list; a student can enrol in a course only once per term; deleting a student removes the enrolments; closing a department leaves its students without a department; a course cannot be removed while students are enrolled in it.

CREATE TABLE Department (
  dept_code VARCHAR2(5)   CONSTRAINT dept_pk PRIMARY KEY,                    -- entity integrity
  dept_name VARCHAR2(50)  CONSTRAINT dept_name_nn NOT NULL                   -- domain
                          CONSTRAINT dept_name_uq UNIQUE,                    -- key (alternate key)
  budget    NUMBER(12,2)  DEFAULT 0
                          CONSTRAINT dept_budget_ck CHECK (budget >= 0)      -- domain (attribute CHECK)
);

CREATE TABLE Student (
  student_id NUMBER(7)    CONSTRAINT stu_pk PRIMARY KEY,
  name       VARCHAR2(50) CONSTRAINT stu_name_nn NOT NULL,
  email      VARCHAR2(60) CONSTRAINT stu_email_nn NOT NULL
                          CONSTRAINT stu_email_uq UNIQUE,
  dept_code  VARCHAR2(5)  CONSTRAINT stu_dept_fk REFERENCES Department(dept_code)
                          ON DELETE SET NULL,                                -- referential
  level_no   NUMBER(1)    DEFAULT 1 CONSTRAINT stu_level_ck CHECK (level_no BETWEEN 1 AND 4),
  cgpa       NUMBER(3,2)  CONSTRAINT stu_cgpa_ck CHECK (cgpa BETWEEN 0 AND 4)
);

CREATE TABLE Course (
  course_id     VARCHAR2(8)  CONSTRAINT crs_pk PRIMARY KEY,
  title         VARCHAR2(60) NOT NULL,
  credit        NUMBER(3,2)  CONSTRAINT crs_credit_ck CHECK (credit IN (0.75, 1.5, 3, 4)),
  contact_hours NUMBER(3,2),
  dept_code     VARCHAR2(5)  NOT NULL CONSTRAINT crs_dept_fk REFERENCES Department(dept_code),
  CONSTRAINT crs_hours_ck CHECK (contact_hours >= credit)                     -- general (tuple CHECK)
);

CREATE TABLE Enrollment (
  student_id NUMBER(7),
  course_id  VARCHAR2(8),
  term       VARCHAR2(10),
  grade      VARCHAR2(2),
  CONSTRAINT enr_pk     PRIMARY KEY (student_id, course_id, term),          -- composite key
  CONSTRAINT enr_stu_fk FOREIGN KEY (student_id) REFERENCES Student(student_id) ON DELETE CASCADE,
  CONSTRAINT enr_crs_fk FOREIGN KEY (course_id)  REFERENCES Course(course_id),  -- default: reject
  CONSTRAINT enr_grade_ck CHECK (grade IN ('A+','A','A-','B+','B','B-','C+','C','D','F'))
);

-- general constraint over several rows (standard SQL; in Oracle a trigger):
-- no student takes more than 25 credits in one term
CREATE ASSERTION credit_limit CHECK (NOT EXISTS (
  SELECT E.student_id, E.term
  FROM Enrollment E JOIN Course C ON E.course_id = C.course_id
  GROUP BY E.student_id, E.term
  HAVING SUM(C.credit) > 25));

Where each type appears.

  • Domain: data types and sizes on every column; NOT NULL on names, e-mail, title; DEFAULT on budget and level; attribute CHECKs on budget, level, CGPA, credit, grade.
  • Entity integrity: PRIMARY KEY on every table (dept_pk, stu_pk, crs_pk, and the composite enr_pk, whose columns are all NOT NULL).
  • Key: UNIQUE alternate keys dept_name and email (also NOT NULL).
  • Referential integrity: stu_dept_fk (ON DELETE SET NULL: a student survives a closed department), crs_dept_fk (default: a department with courses cannot be deleted), enr_stu_fk (ON DELETE CASCADE: enrolments are existence-dependent on the student), enr_crs_fk (default: a course with enrolments cannot be deleted).
  • General: the tuple-based CHECK crs_hours_ck relates two columns of a row; the assertion credit_limit involves many rows and two tables.

Showing that they work (each statement on the data after the previous ones):

INSERT INTO Department VALUES ('CSE', 'Computer Science and Engineering', 5000000);
INSERT INTO Student VALUES (2105001, 'Rafi', 'rafi@cse.buet.ac.bd', 'CSE', 2, 3.85);   -- OK
INSERT INTO Student VALUES (2105001, 'Nila', 'nila@cse.buet.ac.bd', 'CSE', 2, 3.60);   -- ORA-00001 (entity)
INSERT INTO Student VALUES (2105002, 'Nila', 'nila@cse.buet.ac.bd', 'EEE', 2, 3.60);   -- ORA-02291 (referential)
INSERT INTO Student VALUES (2105003, 'Tama', 'tama@cse.buet.ac.bd', 'CSE', 2, 4.20);   -- ORA-02290 (domain CHECK)
INSERT INTO Course  VALUES ('CSE215', 'Database', 3, 2, 'CSE');                        -- ORA-02290 (tuple CHECK)

Summary: Integrity constraints come in families: domain (type, NOT NULL, DEFAULT, attribute CHECK), entity (PRIMARY KEY), key (UNIQUE), referential (FOREIGN KEY with actions) and general (tuple CHECK, assertions, triggers). A DEFERRABLE constraint, when deferred, is checked at COMMIT instead of after each statement; that is how cycles of foreign keys are filled and how Oracle re-keys a parent without ON UPDATE CASCADE.
