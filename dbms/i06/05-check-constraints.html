CHECK Constraints: Attribute-Based and Tuple-Based

A CHECK constraint states any condition you could write after WHERE, and the DBMS refuses rows that make it false. This chapter covers CHECK on one attribute and on a whole tuple, the logic trick for turning "if P then Q" into a CHECK, what happens with NULL, and why the slides' CHECKs with subqueries are standard SQL that Oracle does not accept.

1. The CHECK clause (slides 24–25)

The syntax is CHECK (<condition>), where the condition is "a condition that must hold". Slide 24 adds: conditions are like the predicates written after a WHERE clause. You may use comparisons, AND/OR/NOT, BETWEEN, IN, LIKE, IS NULL, and arithmetic.

Slide 25 lists three levels, which the next sections (and Chapter 6) take in turn:

Attribute-based CHECK
Written with one column. Constrains the values of that column. Checked when a row is inserted or that column is updated.
Tuple-based CHECK
Written as a separate element of CREATE TABLE. May mention any columns of the table. Checked when a row is inserted or any column of a row is updated.
Database-level CHECK (assertion)
A separate schema object, CREATE ASSERTION, whose condition may involve several tables (Chapter 6).

When a row makes the condition false, the statement is rejected. Oracle's message is ORA-02290: check constraint (SCHEMA.NAME) violated.

Question: what does a CHECK do with NULL?

A comparison with NULL is neither true nor false but UNKNOWN. A CHECK rejects a row only when its condition is false, so a row that makes it UNKNOWN is accepted. For example, with CHECK (speed >= 2.0), a laptop with speed NULL is accepted. (A WHERE clause behaves the other way round: it keeps only the rows where the condition is true.) If NULL must be forbidden too, add NOT NULL, or write CHECK (speed IS NOT NULL AND speed >= 2.0).

2. Attribute-based CHECK (slides 26–28)

CREATE TABLE myTable (
  attrib1 type1 CHECK (<condition>),
  attrib2 type2,
  attrib3 type3 CHECK (<condition>)
);

Slide 27: in Laptop(model, speed, ram, hd, screen, price), "the speed of a laptop must be at least 2.0":

CREATE TABLE Laptop (
  model  CHAR(4) PRIMARY KEY,
  speed  NUMBER(3,2) CHECK (speed >= 2.0),
  ram    INT,  hd INT,  screen NUMBER(3,1),  price NUMBER(7,2)
);

(NUMBER(3,2) means 3 significant digits, 2 after the decimal point: values up to 9.99. The slide's schema line writes "sc" for screen.) The animation inserts the textbook's ten laptops into this table:

Slide 28: in Printer(model, type, price), "the only types of printers are laser, ink-jet and bubble-jet":

type CHAR(20) CHECK (type IN ('laser', 'ink-jet', 'bubble-jet'))

A list of allowed values like this is the usual way to declare a small fixed domain in Oracle (there is no ENUM type). Watch out for CHAR here: Oracle pads CHAR(20) with blanks, but compares CHAR values with blank-padded semantics, so 'laser' still matches. VARCHAR2(20) avoids the question.

In Oracle, a CHECK written as a column constraint may mention only its own column; speed NUMBER CHECK (speed > 0 OR price < 500) gives ORA-02438: Column check constraint cannot reference other columns. Such conditions are tuple-based (section 4).

3. A CHECK with a subquery (slides 29–30)

Slide 29 shows the Product table next to PC and Laptop and states: "a model of a product must also be the model of a PC, a laptop or a printer". Slide 30 writes it as an attribute-based CHECK with a subquery:

CREATE TABLE Product (
  maker CHAR(1),
  model CHAR(4) CHECK (model IN (SELECT model FROM PC
                                 UNION SELECT model FROM Laptop
                                 UNION SELECT model FROM Printer)),
  type  VARCHAR2(10)
);

(The slide is missing the final closing parenthesis of the CHECK; it is added above.) This looks like a foreign key, but it cannot be one: a foreign key references one table, and here the model may be in any of three. It is a referential-integrity rule that only a subquery can express.

The SQL standard allows this. Oracle does not: any subquery inside CHECK gives ORA-02251: subquery not allowed here. SQLite refuses it too (subqueries prohibited in CHECK constraints). In Oracle such rules need a trigger (Lec 12). Even in the standard, a CHECK with a subquery is only a partial guarantee:

Question: does slide 30's CHECK guarantee the rule at all times?

No. An attribute-based CHECK is evaluated only when a Product row is inserted or its model is updated. If later someone deletes PC 1001, the Product row (A, 1001, pc) now violates the rule, but no Product row changed, so the CHECK is never re-evaluated and the deletion is accepted. That is why slide 50 says CHECK constraints are "not guaranteed to hold if there is a subquery". A foreign key would block that delete; an assertion (Chapter 6) would too.

4. Tuple-based CHECK (slides 31–34)

CREATE TABLE myTable (
  attrib1 type1,
  attrib2 type2, …
  CHECK (<condition>)
);

The CHECK now stands on its own in the list, so its condition may use every column of the row. It is checked for a row whenever that row is inserted or updated.

From "if … then …" to a CHECK

Business rules usually come as implications: "if P then Q". A CHECK needs a plain condition, so the slides use the logical equivalence

P → Q  ≡  ¬P ∨ Q

An implication is false in exactly one case: P true and Q false. ¬P ∨ Q is also false in exactly that case. In words: either the "if" part does not apply, or the "then" part holds.

To write ¬P, negate the comparison: ¬(speed < 2.0) is speed >= 2.0; ¬(a = b) is a <> b; ¬(x AND y) is ¬x OR ¬y (De Morgan). If the "then" part is itself an OR, the result is one long OR: P → (Q ∨ R) ≡ ¬P ∨ Q ∨ R.

Slide 32. "If the head of the department's gender is male, then his name must not begin with 'Ms.'." P = gender is male, Q = name NOT LIKE 'Ms.%'. The slide writes ¬P as gender = 'F', which is correct as long as gender is only ever 'M' or 'F' (with a NULL gender the row is accepted anyway, since the OR is then UNKNOWN or true). The safest form of ¬P is gender <> 'M'.

CREATE TABLE Department (
  …,
  PRIMARY KEY …,
  FOREIGN KEY …,
  CHECK (gender = 'F' OR name NOT LIKE 'Ms.%')
);

(The slide puts the rule in Department, as if Department stored its head's name and gender; in the textbook the same example belongs to MovieStar(name, address, gender). The idea is the same. "PRIMAR KEY" is again a typo for PRIMARY KEY.)

Slide 33. "A PC with a processor speed less than 2.0 must not sell for more than $800." P = speed < 2.0, Q = price ≤ 800 ("not more than 800"):

CREATE TABLE PC (
  …,
  CHECK (speed >= 2.0 OR price <= 800)
);

Slide 34. "A laptop with a screen size less than 15 inches must have at least a 40 GB hard disk or sell for less than $1000." P = screen < 15, Q = hd ≥ 40, R = price < 1000; P → (Q ∨ R) ≡ ¬P ∨ Q ∨ R:

CREATE TABLE Laptop (
  …,
  CHECK (screen >= 15 OR hd >= 40 OR price < 1000)
);

The slide writes CREATE TABLE PC here; it must be Laptop, since PC has no screen column.

Tool: turn an implication into a CHECK

Type the "if" part P (one comparison, or several joined by AND) and the "then" part Q. The tool negates P, builds the CHECK, and lets you test a row.

5. A tuple-based CHECK across tables (slides 35–36)

"If the relation Product mentions a model and its type, then this model must appear in the relation appropriate to that type." Slide 35 shows the data; slide 36 writes a tuple-based CHECK on Product with three subqueries:

CREATE TABLE Product (
  …,
  CHECK (   (type = 'pc'      AND model IN (SELECT model FROM PC))
         OR (type = 'laptop'  AND model IN (SELECT model FROM Laptop))
         OR (type = 'printer' AND model IN (SELECT model FROM Printer)))
);

Read it as: the row is fine if it is a pc that is in PC, or a laptop that is in Laptop, or a printer that is in Printer. It is stronger than slide 30's rule: slide 30 accepts (A, 1001, laptop) because 1001 is in PC, but slide 36 rejects it because 1001 is not in Laptop. Like slide 30, it is standard SQL that Oracle refuses (ORA-02251), and it is only checked when Product changes. The same rule as an assertion is slide 47 in the next chapter. Below, the condition is used the only way the playground (and Oracle) allows: as a query that looks for rows breaking it. On the textbook data there are none; add a bad row and run again.

Quick check

Write it yourself

Exercises of the form "list the rows that violate…" practise the negation of a CHECK: a row violates CHECK (c) exactly when NOT (c) is true. The CREATE TABLE exercises end with a line that copies test rows into your table with INSERT OR IGNORE: this is a SQLite-only helper that silently skips the rows your CHECK rejects, so the checker can see which rows your constraint lets through. (Oracle has no INSERT OR IGNORE.)

Exam questions

BUET QBank · CSE 303 | L-3/T-1 | 2012–13 · 5 marks

Give an example of a CHECK constraint and discuss why it is used.

Show worked answer

A CHECK constraint attaches a condition (like a WHERE predicate) to a column or a table. The DBMS evaluates it for every inserted or updated row and rejects the statement if the condition is false (a NULL result, UNKNOWN, is accepted).

CREATE TABLE Laptop (
  model  CHAR(4) PRIMARY KEY,
  speed  NUMBER(3,2) CHECK (speed >= 2.0),                  -- attribute-based
  ram    INT,
  hd     INT          CHECK (hd > 0),
  screen NUMBER(3,1),
  price  NUMBER(7,2),
  CONSTRAINT small_screen_rule
    CHECK (screen >= 15 OR hd >= 40 OR price < 1000)        -- tuple-based
);
INSERT INTO Laptop VALUES ('2099', 1.5, 512, 60, 15.4, 900);
-- ORA-02290: check constraint (SCHEMA.SYS_C00…) violated   (speed < 2.0)

Why it is used. (1) It enforces domain rules and business rules that data types alone cannot express: ranges (speed ≥ 2.0), allowed values (type IN ('laser', 'ink-jet', 'bubble-jet')), and relationships between columns of one row ("small-screen laptops need a 40 GB disk or a price under $1000", written with P → Q ≡ ¬P ∨ Q). (2) The rule lives in the schema, so it holds no matter which program or user changes the data; no application can forget it. (3) It is declarative and cheap: the DBMS checks only the changed row, which is faster and more reliable than code in triggers or applications. (4) It documents the meaning of the data in the schema itself. Limits: in Oracle a CHECK may not contain a subquery, so rules involving other rows or tables need triggers (or assertions in standard SQL).

DB QB · 20-21 5c · 5 marks  |  BUET QBank · CSE 215 | L-2/T-2 | 2020–21 · 15 marks

Replace the below UNIQUE constraint using a CHECK constraint.

CREATE TABLE MyTable(
  …
  head INT UNIQUE,
  …
);
Show worked answer

UNIQUE on head means: no two rows have the same non-NULL head (NULLs may repeat). A CHECK can say "there is no head value that occurs more than once" with a subquery over the same table. In standard SQL:

CREATE TABLE MyTable (
  …
  head INT,
  …
  CONSTRAINT head_unique CHECK (
    NOT EXISTS (SELECT head
                FROM MyTable
                WHERE head IS NOT NULL
                GROUP BY head
                HAVING COUNT(*) > 1)
  )
);

How it works: when a row is inserted or updated, the condition is evaluated on the table including the new row. If the new head equals an existing one, that head's group has COUNT(*) = 2, the subquery returns it, NOT EXISTS is false, and the statement is rejected. WHERE head IS NOT NULL keeps the UNIQUE behaviour for NULLs (GROUP BY would otherwise put all NULLs in one group and reject a second NULL).

An equivalent attribute-based form counts the rows with the current row's value; the outer row must be referred to by the table name, and the subquery's copy needs an alias:

head INT CHECK (head IS NULL OR
                1 = (SELECT COUNT(*) FROM MyTable M WHERE M.head = MyTable.head))

Because the only table in the subquery is MyTable itself, and the check runs on every insert or update of MyTable, this CHECK is fully equivalent to UNIQUE (deleting rows can never create a duplicate). In Oracle neither version can be created: subqueries in CHECK give ORA-02251. In practice you keep UNIQUE (or a unique index); the question tests the standard-SQL semantics.

Note: the CSE 215 bank's answer writes WHERE M.head = head. An unqualified column name in a subquery refers to the nearest table that has such a column, which is M itself, so the condition reads M.head = M.head: it counts every non-NULL row of the table, and the CHECK would reject the second row inserted even when the heads differ. The outer row must be written MyTable.head. The marks also differ between the banks (5 in DB QB, 15 in the CSE 215 bank).

BUET QBank · CSE 303 | L-3/T-1 | 2011–12 · 5 marks (part a of a 20-mark question; part b is in Chapter 6)

A database schema consists of four relations: Product(maker, model, type), PC(model, speed, ram, hd, price), Laptop(model, speed, ram, hd, screen, price), Printer(model, color, type, price).

(a) Write the following check constraints: (i) The model number of a product must be a 7-digit number. (ii) A PC with a processor speed less than 2.0 GHz must have at least 512 MB RAM or sell for less than $800.

Show worked answer

(i) This is a rule on one attribute of Product, so an attribute-based CHECK. If model is stored as a number, "7 digits" means between 1,000,000 and 9,999,999:

CREATE TABLE Product (
  maker VARCHAR2(20),
  model NUMBER(7) PRIMARY KEY CHECK (model BETWEEN 1000000 AND 9999999),
  type  VARCHAR2(10)
);

If model is a string (so leading zeros such as '0012345' count), use Oracle's regular expressions:

model CHAR(7) CHECK (REGEXP_LIKE(model, '^[0-9]{7}$'))

Note: the bank's alternative model LIKE '[0-9][0-9]…' is SQL Server syntax. Oracle's LIKE knows only % and _, so in Oracle that pattern matches only the literal text "[0-9][0-9]…" and every real model would be rejected.

(ii) If P = speed < 2.0 then (Q = ram ≥ 512 or R = price < 800). P → (Q ∨ R) ≡ ¬P ∨ Q ∨ R, a tuple-based CHECK on PC:

CREATE TABLE PC (
  model CHAR(4) PRIMARY KEY,
  speed NUMBER(3,2), ram INT, hd INT, price NUMBER(7,2),
  CONSTRAINT slow_pc_rule CHECK (speed >= 2.0 OR ram >= 512 OR price < 800)
);
-- or on an existing table:
ALTER TABLE PC ADD CONSTRAINT slow_pc_rule CHECK (speed >= 2.0 OR ram >= 512 OR price < 800);

Check with a row: (1.8 GHz, 256 MB, $850): speed ≥ 2.0 false, ram ≥ 512 false, price < 800 false → rejected. (1.8, 256, $700) → accepted (cheap). All 13 PCs of the textbook data satisfy it. Exercise 5 above tests this constraint.

Summary: CHECK (condition) rejects rows that make the condition false (UNKNOWN passes). Attribute-based CHECKs sit on one column and are checked when that column changes; tuple-based CHECKs sit in the table and may use all columns of the row. Translate "if P then Q" as ¬P OR Q. The slides' CHECKs with subqueries (30, 36) are standard SQL; Oracle rejects them (ORA-02251), and even in the standard they are only checked when their own table changes.
