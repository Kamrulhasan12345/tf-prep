Referential Actions: CASCADE and SET NULL

Instead of rejecting a parent update or delete, a foreign key can be told to repair the children: copy the new key into them (CASCADE), delete them too (CASCADE), or set their reference to NULL (SET NULL). This chapter animates each action on the slides' tables, shows what Oracle supports (ON DELETE only), and answers the exam questions on choosing a policy.

1. Three policies (slides 22–23)

When a parent row's key is updated or the row is deleted while children still refer to it, the SQL standard lets the designer choose one of these referential actions for each foreign key, separately for UPDATE and DELETE:

Default policy (NO ACTION / RESTRICT)
Reject the statement. This is what you get when nothing is declared, and it is what Chapter 3 showed. (The standard distinguishes NO ACTION, checked at the end of the statement, from RESTRICT, checked immediately; for the cases in this course they behave the same. Oracle has only the default, under no keyword.)
CASCADE
Make the same change in the children. ON UPDATE CASCADE copies the new key value into every referencing row. ON DELETE CASCADE deletes every referencing row along with the parent.
SET NULL
Keep the children, but set their foreign-key column(s) to NULL. Only possible if those columns allow NULL.

Slide 22 picks one action for each operation, for the Department/Employee example:

  • "If the ID of a departmental head is changed, it needs to be updated in both tables" → ON UPDATE CASCADE.
  • "If the departmental head retires temporarily, it needs to be set null in the foreign table" → ON DELETE SET NULL.

Slide 23 says to "do it while creating the foreign table":

CREATE TABLE Department (
  name CHAR(3),
  head INT REFERENCES Employee(id)
           ON DELETE SET NULL
           ON UPDATE CASCADE
);

Oracle warning. This is standard SQL, and it runs in the playground (SQLite follows the standard here). Oracle supports only two actions, both for DELETE: ON DELETE CASCADE and ON DELETE SET NULL. Oracle has no ON UPDATE clause at all, so the statement above fails in Oracle with ORA-00907: missing right parenthesis (the parser does not expect ON UPDATE). In Oracle the slide's table is written

CREATE TABLE Department (
  name CHAR(3),
  head INT REFERENCES Employee(id) ON DELETE SET NULL
);

and a primary-key change must be propagated by hand (the three steps of Chapter 3's exercise 4), by a trigger (Lec 12), or with a deferrable constraint (Chapter 8). Oracle's designers argue that a primary key should never change in the first place; if ids can change, they were a poor choice of key.

2. ON DELETE SET NULL

D (id 4) retires. With ON DELETE SET NULL, DELETE FROM Employee WHERE id = 4 succeeds, and EEE stays in Department with head NULL.

If the foreign-key column is also declared NOT NULL, SET NULL cannot do its job, and the delete fails anyway (Oracle: ORA-01407: cannot update (…"HEAD") to NULL). SET NULL only makes sense for an optional reference.

3. ON UPDATE CASCADE (standard SQL)

D's id changes from 4 to 9. With ON UPDATE CASCADE, EEE's head follows: it becomes 9. The link is preserved, which is what slide 22 asks for.

4. ON DELETE CASCADE

The third combination: deleting the parent deletes the children. For departments this would be a strange rule (EEE disappears because its head retired), which is why the slide does not use it. It is the right rule when a child cannot exist without its parent: an order's line items, a building's rooms, a student's enrolment records. Then deleting the parent should clean up everything that belongs to it.

Cascades can chain. Suppose Course(code, dept) references Department(name) ON DELETE CASCADE, and Department(head) references Employee(id) ON DELETE CASCADE. One delete of an employee can then remove a department and all of its courses:

This power is also the danger of CASCADE: a single mistaken DELETE can silently remove many rows in several tables. Use it only where the children really have no meaning without the parent.

5. Which action where?

SituationON DELETEON UPDATE (standard SQL)
Child is part of the parent (order → order lines, weak entity)CASCADECASCADE
Link is optional; child lives on (department → its head; employee → manager)SET NULLCASCADE
Child is important history and must not lose its parent (sale → customer)default (reject)CASCADE or default

For UPDATE, CASCADE is almost always the right choice: the parent still exists, only its key value changed, so the children should follow it. SET NULL on update would throw away a link that is still true. For DELETE the parent is really gone, so it depends on whether the child can exist without it.

Exam questions

DB QB · 19-20 8a · 10 marks  |  BUET QBank · CSE 215 | L-2/T-2 | 2019–20, 2015–16 · 10 marks

What is the difference between referential integrity constraint and foreign key constraint? What are the three different policies for UPDATE and DELETE that can be mentioned for maintaining referential integrity? Among these, which one is more suitable for UPDATE, and which one is more suitable for DELETE? Why?

Show worked answer

Referential integrity vs foreign key. A referential integrity constraint is the general requirement that a value appearing in one place must also appear in another place: every reference must point at something that exists (no dangling references). A foreign key constraint is the specific SQL declaration that enforces one common kind of referential integrity: the values of some column(s) of a child table must match the PRIMARY KEY or UNIQUE key of a row of a parent table, or be NULL. Every foreign key is a referential integrity constraint, but not the other way round. Example: "the model of a Product must be the model of some PC, Laptop or Printer" (slide 29) is a referential integrity constraint, but no single FOREIGN KEY can express it, because it refers to the union of three tables; it needs a CHECK with a subquery or an assertion (Chapters 5–6).

The three policies (what to do when a referenced parent row is updated or deleted):

  1. Default (reject, NO ACTION/RESTRICT): the statement on the parent fails if any child refers to the old key. Example: DELETE FROM Employee WHERE id = 4 is rejected because EEE's head is 4.
  2. CASCADE: the change is repeated in the children. On update the children get the new key (EEE's head becomes 9 when 4 becomes 9); on delete the children are deleted too (EEE is deleted with employee 4).
  3. SET NULL: the children's foreign key becomes NULL (EEE's head becomes NULL when employee 4 is deleted or re-keyed).
CREATE TABLE Department (
  name CHAR(3),
  head INT REFERENCES Employee(id)
           ON DELETE SET NULL
           ON UPDATE CASCADE      -- standard SQL; Oracle supports only the ON DELETE actions
);

Most suitable for UPDATE: CASCADE. When a parent's key changes, the parent row still exists and is still the same real-world thing; only its identifier changed. The children still refer to it, so the correct repair is to give them the new identifier. Rejecting forces a manual three-step workaround, and SET NULL would destroy a relationship that is still true.

Most suitable for DELETE: SET NULL (this is the slides' choice). When a parent is deleted, the relationship really ends, but in general the child still exists: a department whose head retires is still a department. SET NULL keeps the child and records "no parent for now". CASCADE would delete children that have their own existence (losing data by accident), and rejecting would block a legitimate delete. CASCADE on delete is the right choice only when the child cannot exist without the parent (weak entities, such as an order's line items).

Note: the CSE 215 bank's answer recommends RESTRICT for DELETE. That is a defensible safety-first choice, but the question asks to pick among the policies for maintaining integrity automatically, and the slides (and the textbook's example, ON DELETE SET NULL ON UPDATE CASCADE) choose SET NULL. Mention both reasons in an exam: SET NULL when the child can exist alone, CASCADE when it cannot.

BUET QBank · CSE 303 | L-3/T-1 | 2012–13 · 10 marks

What are the different policies of maintaining referential integrity? Discuss them with examples.

Show worked answer

Referential integrity requires every foreign-key value to match an existing parent key. It can be broken from the child side (inserting or updating a reference to a key that does not exist) and from the parent side (deleting or re-keying a parent that is still referenced). Child-side violations are always rejected. For the parent side, SQL lets the designer choose a policy per foreign key, separately for DELETE and UPDATE. Example tables: Employee(id PK, name, …) and Department(name, head → Employee.id) with rows (CSE, 2), (EEE, 4), (ME, 1).

  1. Default / reject (NO ACTION or RESTRICT). The parent statement fails if a child refers to the affected key. DELETE FROM Employee WHERE id = 4 → error (Oracle ORA-02292, child record found); both tables unchanged. This is the policy when nothing is declared.
  2. CASCADE. The change propagates. With ON DELETE CASCADE, deleting employee 4 also deletes (EEE, 4). With ON UPDATE CASCADE, UPDATE Employee SET id = 9 WHERE id = 4 also changes EEE's head to 9. Typical use: existence-dependent children (order lines of an order).
  3. SET NULL. The children's foreign key is set to NULL. Deleting employee 4 leaves (EEE, NULL): the department remains, without a head. Requires the column to allow NULL. Typical use: optional relationships.
  4. SET DEFAULT (standard SQL). The children's foreign key is set to the column's DEFAULT value, which must itself be a valid parent key (e.g. a placeholder employee 0 "acting head"). Oracle does not support SET DEFAULT.
-- Oracle
CREATE TABLE Department (
  name CHAR(3) PRIMARY KEY,
  head INT CONSTRAINT dept_head_fk REFERENCES Employee(id) ON DELETE SET NULL
);
CREATE TABLE Course (
  code VARCHAR2(7) PRIMARY KEY,
  dept CHAR(3) REFERENCES Department(name) ON DELETE CASCADE
);

In Oracle only the default, ON DELETE CASCADE and ON DELETE SET NULL exist; updates of a referenced key are always rejected (no ON UPDATE clause). The CSE 215 bank's answer says RESTRICT is "the default policy in most relational databases": the default is formally NO ACTION, which for a single statement behaves the same.

Summary: A referential action tells the DBMS how to repair the children when a referenced parent is deleted or re-keyed: reject (default), CASCADE (follow the parent: update or delete the children) or SET NULL (cut the link). Slide 23's ON DELETE SET NULL ON UPDATE CASCADE is the textbook choice. Oracle supports only ON DELETE CASCADE and ON DELETE SET NULL; there is no ON UPDATE clause. Cascades can chain through several tables.
