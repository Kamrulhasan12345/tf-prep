Assertions: Constraints on the Whole Database

An assertion is a condition over any number of tables that must be true at all times. This chapter explains CREATE ASSERTION, the "negative approach" (NOT EXISTS of a violation) used in every example, works through all of the slides' assertions on real data, compares the three kinds of CHECK (slide 50), and answers the big 24-mark constraints question.

1. Database-level CHECK: the assertion (slide 37)

Assertion
A named, stand-alone schema element CREATE ASSERTION name CHECK (condition); whose condition (usually built from subqueries) may involve several tables. The condition must be true in every state of the database; any modification that would make it false is rejected.

Slide 37 lists the properties: assertions are database-level CHECK constraints; their condition checks over multiple relations; they are executed upon any modification to any relation mentioned in the assertion; and the SQL standard supports them.

That last line hides an important fact: Oracle does not implement CREATE ASSERTION (it fails with ORA-00901: invalid CREATE command), and neither do MySQL, PostgreSQL, SQL Server or SQLite. Checking an arbitrary condition after every change is expensive, so vendors leave it to triggers (Lec 12). You still need assertions for exams: they are the clean, declarative way to state a multi-table rule, and writing one is mostly writing the right query. The playground boxes below run that query: the set of rows that would violate the assertion.

2. Positive or negative approach? (slides 38–39)

Take the rule of slide 39: a departmental head must be an employee of the university.

  • Positive approach: look at each departmental head and make sure that he or she is an employee. This is a "for all" statement: for every Department row, the head is in Employee.
  • Negative approach: look for a departmental head who is not an employee, and make sure that such a head does not exist.

Question (slide 39): EXISTS or NOT EXISTS, which way to go?

NOT EXISTS, the negative approach. SQL has no "for all" quantifier, but it has EXISTS, and "for all x, rule(x)" is logically the same as "there is no x with NOT rule(x)". So we write a query that finds the violations, and assert that its result is empty:

CHECK (NOT EXISTS (query returning the violating rows))

This recipe works for every assertion in the lecture, and it has a practical bonus: the inner query, run on its own, shows you exactly which rows break the rule. A positive version (CHECK (EXISTS …)) would only say that some row is fine, which is not what we want.

3. The head must be an employee (slide 40)

CREATE ASSERTION checkHeadConstraint
CHECK (NOT EXISTS (SELECT head
                   FROM Department
                   WHERE head NOT IN (SELECT id FROM Employee)));

(The slide closes only two of the three parentheses.) This is the foreign key of Chapter 2 written as an assertion, and the comparison is instructive. Both reject a department whose head is not an employee, and both reject deleting an employee who heads a department, because the assertion mentions Employee and is re-checked when Employee changes. A row with head NULL is fine for both: NULL NOT IN (…) is UNKNOWN, so that row is not returned as a violation. But the foreign key can also do CASCADE or SET NULL, and it is supported everywhere, so for this rule the foreign key is the right tool; the assertion is here to show the method.

4. No manufacturer of PCs may also make laptops (slides 41–43)

The negative approach: "a manufacturer of a PC makes a laptop: such occurrences do NOT EXIST".

CREATE ASSERTION noPcLaptopMaker
CHECK (NOT EXISTS (SELECT maker
                   FROM Product
                   WHERE type = 'pc'
                     AND maker IN (SELECT maker FROM Product WHERE type = 'laptop')));

Only the Product table is involved, yet this cannot be a tuple-based CHECK: it compares different rows (a pc row and a laptop row of the same maker), and a tuple CHECK sees one row at a time. The slides name every assertion makeConstraint; in a real schema each needs its own name, so this chapter renames them. The slide is again one parenthesis short. An equivalent condition uses set operations: NOT EXISTS (SELECT maker FROM Product WHERE type = 'pc' INTERSECT SELECT maker FROM Product WHERE type = 'laptop').

On the textbook's data the rule is false: makers A, B and E make both. An assertion must hold when it is created, so CREATE ASSERTION itself would be rejected until the data is fixed.

5. More RAM must cost more (slides 44–45)

"If a laptop has a larger main memory than a PC, then the laptop must also have a higher price than the PC." For each pair (laptop, PC): P = Laptop.ram > PC.ram, Q = Laptop.price > PC.price. A violating pair has P true and Q false, so the violation query is a join of the two tables with P AND NOT Q:

CREATE ASSERTION ramPriceConstraint
CHECK (NOT EXISTS (SELECT Laptop.model, PC.model
                   FROM Laptop, PC
                   WHERE Laptop.ram > PC.ram
                     AND Laptop.price <= PC.price));

Two repairs to the slide: SELECT model is ambiguous because both tables have a model column (Oracle: ORA-00918: column ambiguously defined), so qualify it (or write SELECT *); and the slide has one closing parenthesis too many. On the textbook data three pairs violate it: (2002, 1002), (2006, 1001) and (2008, 1002). For example laptop 2002 has 1024 MB and costs $949, while PC 1002 has only 512 MB and costs $995.

6. The model must be in the table for its type (slides 46–47)

This is the rule of slide 36, now as an assertion. The violation is a Product row of type pc whose model is not in PC, or of type laptop not in Laptop, or of type printer not in Printer:

CREATE ASSERTION typeTableConstraint
CHECK (NOT EXISTS (
  SELECT model
  FROM Product
  WHERE (type = 'pc'      AND model NOT IN (SELECT model FROM PC))
     OR (type = 'laptop'  AND model NOT IN (SELECT model FROM Laptop))
     OR (type = 'printer' AND model NOT IN (SELECT model FROM Printer))));

Compare it with slide 36's CHECK: the condition inside is exactly the negation of the CHECK's condition (by De Morgan, NOT((A AND B) OR …) = (NOT A OR NOT B) AND …, and for the rows whose type is pc, laptop or printer that comes to the three ORed cases above). The difference is when it is checked. The CHECK on Product runs only when Product changes; the assertion also runs when PC, Laptop or Printer changes, so deleting PC 1001 while Product lists it is now rejected. The textbook data satisfies this rule.

7. A PC maker must also make a laptop at least as fast (slides 48–49)

"A manufacturer of a PC also makes a laptop with at least as great a processor speed." A violation is a PC whose speed is greater than the speed of every laptop of the same maker:

CREATE ASSERTION speedConstraint
CHECK (NOT EXISTS (SELECT maker
                   FROM Product P1 NATURAL JOIN PC
                   WHERE speed > ALL (SELECT speed
                                      FROM Product P2 NATURAL JOIN Laptop
                                      WHERE P2.maker = P1.maker)));

Product NATURAL JOIN PC joins on the only common column, model, giving each PC its maker. The subquery returns the speeds of that maker's laptops, and speed > ALL (…) is true when the PC is faster than all of them. A subtle point makes this exactly right: if the maker makes no laptops, the subquery is empty and > ALL of an empty set is true, so the PC counts as a violation. That is what the rule wants: such a maker does not "also make a laptop" at all. The same condition without ALL: WHERE NOT EXISTS (SELECT * FROM Product P2 NATURAL JOIN Laptop L WHERE P2.maker = P1.maker AND L.speed >= PC.speed). (In Oracle a column used for a NATURAL JOIN, here model, may not be qualified with a table name; maker and speed are not join columns, so P1.maker and P2.maker are fine.)

8. Comparing the three kinds of constraint (slide 50)

TypeWhere declaredWhen activatedGuaranteed to hold?
Attribute-based CHECKwith the attributeon insertion, or update of that attributenot if it has a subquery
Tuple-based CHECKin the relation schemaon insertion or update of a row of the relationnot if it has a subquery
Assertionin the database schemaon any change to any relation it mentionsyes

Read the last column with section 3 of Chapter 5 in mind. A CHECK is only evaluated for the rows of its own table that change. If its condition reads other tables (or other rows of its own table) through a subquery, those can change without the CHECK being re-evaluated, and the rule can silently become false. An assertion has no "own table": the DBMS re-evaluates it after a change to any table it mentions, so it always holds. The price is cost: a naive DBMS would re-run the whole query after every change, which is the main reason vendors do not offer assertions. Without subqueries, a CHECK only looks at the row being changed, and then it is guaranteed too.

DB QB · 21-22 4b · 24 marks  |  BUET QBank · CSE 215 | L-2/T-2 | 2021–22 · 24 marks

Consider the following relational database schema:

Product(maker, model, type)
PC(model, speed, ram, hd, price)
Laptop(model, speed, ram, hd, screen, price)
Printer(model, color, type, price)

The Product relation gives the manufacturer, model number and type (PC, laptop, or printer) of various products. Model numbers are unique over all manufacturers and product types. The PC relation gives for each model number that is a PC the speed (of the processor, in gigahertz), the amount of RAM (in megabytes), the size of the hard disk (in gigabytes), and the price. The Laptop relation is similar, except that the screen size (in inches) is also included. The Printer relation records for each printer model whether the printer produces color output ('T', if so; 'F' otherwise), the process type (laser or ink-jet, typically), and the price.

Write necessary constraints to implement the followings (answer each independently):
(i) speed, ram, hd, screen and price cannot be negative.
(ii) A model of a product must also be the model of a PC, a laptop, or a printer.
(iii) A laptop with a screen size less than 15 inches must have at least a 40 GB hard disk or sell for less than $1000.
(iv) No manufacturer of PCs may also make laptops.
(v) If a laptop has a larger main memory than a PC, then the laptop must also have a higher price than the PC.
(vi) A manufacturer of a PC also makes a laptop with at least as great a processor speed.

Show worked answer

Choose the weakest tool that can express each rule: a CHECK when one row is enough, an assertion when several rows or tables are involved. Product's type values are written 'pc', 'laptop', 'printer' as in the data (string comparison is case-sensitive, so be consistent).

(i) Non-negative values: attribute-based CHECKs (one condition per column, one row at a time).

CREATE TABLE PC (
  model CHAR(4) PRIMARY KEY,
  speed NUMBER(3,2) CHECK (speed >= 0),
  ram   INT         CHECK (ram >= 0),
  hd    INT         CHECK (hd >= 0),
  price NUMBER(7,2) CHECK (price >= 0)
);
CREATE TABLE Laptop (
  model  CHAR(4) PRIMARY KEY,
  speed  NUMBER(3,2) CHECK (speed >= 0),
  ram    INT         CHECK (ram >= 0),
  hd     INT         CHECK (hd >= 0),
  screen NUMBER(3,1) CHECK (screen >= 0),
  price  NUMBER(7,2) CHECK (price >= 0)
);
ALTER TABLE Printer ADD CONSTRAINT printer_price_nonneg CHECK (price >= 0);

(For existing tables the same conditions can be added with ALTER TABLE … ADD CONSTRAINT name CHECK (…), Chapter 7.)

(ii) Product model appears in PC, Laptop or Printer: assertion (other tables are involved; slide 30's CHECK with a subquery would only be checked when Product changes).

CREATE ASSERTION productModelExists
CHECK (NOT EXISTS (SELECT model FROM Product
                   WHERE model NOT IN (SELECT model FROM PC)
                     AND model NOT IN (SELECT model FROM Laptop)
                     AND model NOT IN (SELECT model FROM Printer)));

(iii) Small-screen laptops: tuple-based CHECK on Laptop, P → (Q ∨ R) ≡ ¬P ∨ Q ∨ R:

ALTER TABLE Laptop ADD CONSTRAINT small_screen_rule
  CHECK (screen >= 15 OR hd >= 40 OR price < 1000);

(iv) No PC maker makes laptops: assertion (compares different rows of Product).

CREATE ASSERTION noPcLaptopMaker
CHECK (NOT EXISTS (SELECT maker FROM Product
                   WHERE type = 'pc'
                     AND maker IN (SELECT maker FROM Product WHERE type = 'laptop')));

(v) More RAM, higher price: assertion over pairs (laptop, PC); a violation is ram larger but price not higher:

CREATE ASSERTION ramPriceConstraint
CHECK (NOT EXISTS (SELECT * FROM Laptop L, PC P
                   WHERE L.ram > P.ram AND L.price <= P.price));

(vi) PC makers have a laptop at least as fast: assertion; a violation is a PC with no laptop of the same maker at least as fast:

CREATE ASSERTION speedConstraint
CHECK (NOT EXISTS (
  SELECT * FROM Product P1, PC
  WHERE P1.model = PC.model
    AND NOT EXISTS (SELECT * FROM Product P2, Laptop L
                    WHERE P2.model = L.model
                      AND P2.maker = P1.maker
                      AND L.speed >= PC.speed)));

(Equivalently, slide 49's form with speed > ALL (…).)

In Oracle, (i) and (iii) work as written. Assertions do not exist in Oracle and CHECKs cannot contain subqueries, so (ii), (iv), (v), (vi) must be enforced with triggers that run the same NOT EXISTS query after each change to the tables involved (Lec 12). On the textbook's sample data, (ii) holds, but (iv), (v) and (vi) are violated (makers A, B, E; three laptop/PC pairs; ten PCs of makers A–E), so those assertions could not even be created until the data is corrected. Exercises 2, 3 and 5 above compute these violators.

BUET QBank · CSE 303 | L-3/T-1 | 2011–12 · 15 marks (part b; part a is in Chapter 5)

For the schema Product(maker, model, type), PC(model, speed, ram, hd, price), Laptop(model, speed, ram, hd, screen, price), Printer(model, color, type, price), write the following assertions: (i) The price of a laptop must be larger than the average price of PCs made by the same manufacturer. (ii) A manufacturer of a PC must also make Laptop(s). (iii) If a PC has a greater processor speed than a laptop then the PC must also have a higher price than the laptop.

Show worked answer

(i) Violation: a laptop whose price is at most the average PC price of its maker. The maker of a laptop comes from Product; the average from Product joined with PC.

CREATE ASSERTION laptopAbovePcAvg
CHECK (NOT EXISTS (
  SELECT * FROM Product PL, Laptop L
  WHERE PL.model = L.model
    AND L.price <= (SELECT AVG(PC.price)
                    FROM Product PP, PC
                    WHERE PP.model = PC.model
                      AND PP.maker = PL.maker)));

If a maker makes no PCs, AVG returns NULL, the comparison is UNKNOWN, and that laptop is (correctly) not a violation. On the textbook data two laptops violate it: 2004 of maker A ($1150 ≤ A's PC average $1195.67) and 2003 of maker E ($549 ≤ $712.33).

(ii) Violation: a maker that makes a PC but no laptop. In Oracle set difference is MINUS (EXCEPT in the standard):

CREATE ASSERTION pcMakerMakesLaptop
CHECK (NOT EXISTS (SELECT maker FROM Product WHERE type = 'pc'
                   MINUS
                   SELECT maker FROM Product WHERE type = 'laptop'));

or without set operators: NOT EXISTS (SELECT * FROM Product P WHERE type = 'pc' AND maker NOT IN (SELECT maker FROM Product WHERE type = 'laptop')). Violators on the textbook data: makers C and D.

(iii) P = PC.speed > Laptop.speed, Q = PC.price > Laptop.price; a violating pair has P AND NOT Q:

CREATE ASSERTION speedPriceConstraint
CHECK (NOT EXISTS (SELECT * FROM PC, Laptop
                   WHERE PC.speed > Laptop.speed
                     AND PC.price <= Laptop.price));

The textbook data has 82 such pairs (PCs are generally cheaper than laptops). As with every assertion, Oracle would need triggers; the conditions themselves are standard.

Summary: CREATE ASSERTION name CHECK (condition) states a rule over any tables; it is re-checked after any change to any table it mentions, so it is the only constraint that is always guaranteed (slide 50). Write it with the negative approach: NOT EXISTS (query for violations), translating "if P then Q" into the violation P AND NOT Q. Standard SQL only: Oracle has no assertions and enforces such rules with triggers.
