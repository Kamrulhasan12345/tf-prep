Enforcing a Foreign Key: Six Kinds of Change

Once Department.head references Employee.id, every INSERT, UPDATE and DELETE on either table might break the link. This chapter goes through the six cases of slides 14–21, animates each of the slides' statements, and explains which ones are always safe, which ones the DBMS must check, and why plain rejection is sometimes the wrong answer.

1. What happens next? (slide 14)

A foreign key connects two tables, and three kinds of modification (INSERTION, UPDATE, DELETION) can hit either table. That gives six cases. The question in each case is the same: can this change leave a Department row whose head matches no Employee?

Changeon the foreign table (Department)on the master table (Employee)
INSERTcheck: the new head must exist (slide 15)always safe (slide 18)
UPDATEcheck if head changes: the new head must exist (slide 16)check if id changes: no Department row may still use the old id (slide 19)
DELETEalways safe (slide 17)check: no Department row may use the deleted id (slide 20)

Notice the pattern. On the child side, danger comes from new references (insert, or change the reference). On the parent side, danger comes from removing a referenced key (delete, or change the key). The two "always safe" cases are the mirror images: removing a reference, and adding a key nobody refers to yet.

All animations start from the slides' data: Employee ids 1–4; Department (CSE, 2), (EEE, 4), (ME, 1).

2. INSERT into the foreign table (slide 15)

INSERT INTO Department VALUES ('CE', 3) is OK: employee 3 exists. INSERT INTO Department VALUES ('CE', 5) is REJECTED: there is no employee 5. Each animation below runs the two statements of its slide one after the other, each on the original data.

3. UPDATE on the foreign table (slide 16)

UPDATE Department SET head = 3 WHERE name = 'CSE' is OK (employee 3 exists). SET head = 7 is REJECTED. An update that changes the foreign-key column is checked exactly like an insert of the new value. An update of the name column would not be checked at all, since name is not part of the foreign key.

4. DELETE from the foreign table (slide 17)

"NO WORRIES, always permitted." Deleting a Department row removes a reference; it cannot create a dangling one. (If some third table referenced Department, deleting from Department would be the master-table case for that other foreign key. Each foreign key is checked on its own.)

5. INSERT into the master table (slide 18)

Also always permitted, as far as this foreign key is concerned: a new employee is a new possible target, and no existing Department row can point at an id that did not exist until now. The insert still has to pass Employee's own constraints, of course: a duplicate id breaks the primary key (ORA-00001).

6. UPDATE on the master table (slide 19)

UPDATE Employee SET id = 8 WHERE id = 3 is OK: nobody refers to employee 3. UPDATE Employee SET id = 9 WHERE id = 4 is REJECTED: EEE's head is 4, and after the update there would be no employee 4. Changing other Employee columns (name, address) is never a problem.

7. DELETE from the master table (slide 20)

DELETE FROM Employee WHERE id = 3 is OK; DELETE FROM Employee WHERE id = 4 is REJECTED, again because of EEE. In Oracle the message is ORA-02292: integrity constraint (…) violated - child record found. Compare it with the child-side error ORA-02291: … parent key not found: 02291 means "you pointed at a parent that is not there", 02292 means "you removed a parent that still has children". SQLite uses the same text, FOREIGN KEY constraint failed, for both.

Run the six cases yourself. Each statement is a separate run; press Reset between experiments to get the original rows back.

8. Rethink before rejection (slide 21)

Slide 21 repeats the two rejected master-table statements and asks us to think again. Rejecting is safe, but it is not always what the users want:

Question (slide 21): is rejecting UPDATE Employee SET id = 9 WHERE id = 4 and DELETE FROM Employee WHERE id = 4 the right behaviour?

The update. Employee D is still the same person and still heads EEE; only D's id number changed (say, after a re-numbering of staff ids). The sensible result is that EEE's head becomes 9 too. Rejecting forces the user to do it by hand in three steps: insert a copy of D with id 9, point EEE at 9, delete the old row 4. (Exercise 4 below makes you do exactly this.)

The delete. If D retires (or leaves temporarily), EEE still exists, it just has no head for now. The sensible result is that EEE's head becomes NULL, meaning "unknown / none". Rejecting forces the user to set EEE's head to NULL first and then delete D.

So the DBMS should let the designer choose, per foreign key, what to do with the children when a parent's key is updated or deleted. These choices are the referential actions of the next chapter: ON UPDATE CASCADE and ON DELETE SET NULL (slide 22).

Summary: A foreign key can be broken in four of the six cases: INSERT or UPDATE of the reference in the child (Oracle ORA-02291, parent key not found), and UPDATE or DELETE of a referenced key in the parent (ORA-02292, child record found). Deleting a child row and inserting a parent row are always safe. By default the DBMS rejects the violating statement; for parent updates and deletes that is often too strict, which motivates referential actions.
