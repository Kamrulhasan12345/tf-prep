Why Constraints? Keys, UNIQUE and NOT NULL

A constraint is a rule the DBMS checks on every change. This chapter explains why we want such rules, defines superkeys, candidate keys and primary keys, and shows how Oracle declares PRIMARY KEY, UNIQUE and NOT NULL, as column constraints and as table constraints. It ends with the subtle point of slide 9: two UNIQUE columns are not the same as one UNIQUE pair.

1. The need for constraints (slides 1–3)

The lecture's outline (slide 2) lists five topics, which are also the chapters of this lecture: the need for constraints, foreign-key constraints, attribute-based constraints, tuple-based constraints and assertions. (The title slide says "CSE 303, Lecture 09, Chapter 7": the slides come from an earlier course, and Chapter 7 is the chapter "Constraints and Triggers" of the textbook by Garcia-Molina, Ullman and Widom.)

Slide 3 gives the reason in three lines. There are certain properties we would like our database to hold: every employee has a different id, a department's head is a real employee, a price is never negative. Every INSERT, UPDATE or DELETE can break these properties, either by a typing mistake or by a bug in some program. So we build handlers into the database definition: we write the rules into the CREATE TABLE statement, and from then on the DBMS itself refuses any change that would break them. No application program can forget the rule, because the rule lives in the database.

Integrity constraint
A condition that every legal state of the database must satisfy. The DBMS checks it whenever a modification could violate it, and rejects (rolls back) the offending statement.
Column constraint (inline constraint)
A constraint written directly after a column's data type, e.g. name CHAR(30) PRIMARY KEY. It can only talk about that one column.
Table constraint (out-of-line constraint)
A constraint written as a separate item in the column list, e.g. PRIMARY KEY(name, address). It may involve several columns. Oracle's documentation calls the two forms inline and out-of-line.

2. Keys: the fundamental constraint

Slides 4–9 call keys "the fundamental constraint", because the relational model identifies a row only by its values. Before the syntax, here are the four words you need. (Sukarna sir's Lec 01, Chapter 3 treats keys through functional dependencies.)

Superkey
A set of attributes whose values can never be the same in two different rows. Any set that contains a superkey is also a superkey.
Candidate key (key)
A minimal superkey: remove any attribute and it stops being a superkey.
Primary key
The one candidate key the designer chooses as the main identifier of the rows. Declared with PRIMARY KEY. Its columns may not be NULL.
Alternate key (unique key)
Any other candidate key. Declared with UNIQUE.

Whether a set is a key is a fact about the meaning of the data (the schema), not about the rows that happen to be in the table today. A sample of rows can only disprove a key: if two rows agree on a set, it is not a superkey. The animation applies this to the MovieStar table of the slides, with some sample rows, under the textbook's assumption that no two stars share a name, and with the extra assumption of slide 6 that no two stars share an address.

3. Declaring a PRIMARY KEY (slide 4)

Slide 4 declares name as the primary key in the two equivalent ways:

-- column constraint
CREATE TABLE MovieStar (
  name    CHAR(30) PRIMARY KEY,
  address VARCHAR2(255),
  gender  CHAR(1)
);
-- table constraint
CREATE TABLE MovieStar (
  name    CHAR(30),
  address VARCHAR2(255),
  gender  CHAR(1),
  PRIMARY KEY (name)
);

The slides write VARCHAR(255). Oracle accepts VARCHAR as a synonym, but the Oracle type is VARCHAR2, so this book writes VARCHAR2. CHAR(30) is a fixed-length string: Oracle pads it with blanks to 30 characters.

4. UNIQUE (slides 5–6)

UNIQUE is written exactly like PRIMARY KEY, as a column constraint or a table constraint (slide 5). It says: no two rows may have the same non-NULL value here. Slide 5 claims that "the only difference between UNIQUE and PRIMARY KEY is that UNIQUE allows NULL values". That is the difference you notice first, but there are two more:

PRIMARY KEYUNIQUE
Duplicate valuesnot allowednot allowed (among non-NULL values)
NULLnot allowed (implies NOT NULL)allowed, even in many rows
How many per tableat most oneany number (slide 6)
Foreign keysthe default target: REFERENCES Employee means its primary keymay be referenced, but the column must be named
Index Oracle buildsa unique B-tree index on the key columns, in both cases (see Lec 15)

Why may a UNIQUE column hold many NULLs? NULL means "unknown". Two unknown addresses are not known to be equal, so they do not count as duplicates. Slide 6 shows that UNIQUE may be used "for any number of attributes": name and address are each unique on their own.

5. NOT NULL (slide 7)

NOT NULL forbids NULL in one column. Slide 7 combines it with UNIQUE: name CHAR(30) UNIQUE NOT NULL. A column that is UNIQUE and NOT NULL behaves exactly like a primary key column, except that it is not the primary key. This is the usual way to declare an alternate key.

CREATE TABLE MovieStar (
  name    CHAR(30) UNIQUE NOT NULL,
  address VARCHAR2(255) UNIQUE,
  gender  CHAR(1)
);

In Oracle, NOT NULL can only be written as a column constraint. There is no table-level NOT NULL(name); the table-level equivalent is CHECK (name IS NOT NULL), which is the CHECK constraint of Chapter 5.

6. Keys made of several columns (slide 8)

A combination of attributes can be the primary key or be unique. This needs the table-constraint form, because a column constraint can only mention its own column:

CREATE TABLE MovieStar (
  name    CHAR(30),
  address VARCHAR2(255),
  gender  CHAR(1),
  PRIMARY KEY (name, address)
);
CREATE TABLE MovieStar (
  name    CHAR(30),
  address VARCHAR2(255),
  gender  CHAR(1),
  UNIQUE (name, address)
);

The slide writes PRIMAR KEY; that is a typo for PRIMARY KEY, and Oracle would report a syntax error. With a composite primary key, slide 8 adds, "none of the attributes can be NULL": both name and address become NOT NULL.

Two rows may now share a name, provided their addresses differ: two different stars called "Mark Hamill" are fine if they live at different addresses. Writing name CHAR(30) PRIMARY KEY, address VARCHAR2(255) PRIMARY KEY would be an error (ORA-02260: table can have only one primary key), because each column constraint tries to declare its own primary key.

7. Two UNIQUE columns are not one UNIQUE pair (slide 9)

Slide 9 puts two declarations side by side and says they are not the same:

-- (a) two separate keys
CREATE TABLE MovieStar (
  name    CHAR(30) UNIQUE,
  address VARCHAR2(255) UNIQUE,
  gender  CHAR(1)
);
-- (b) one key made of two columns
CREATE TABLE MovieStar (
  name    CHAR(30),
  address VARCHAR2(255),
  gender  CHAR(1),
  UNIQUE (name, address)
);

Question (slide 9): why are these two declarations different?

(a) declares two keys: {name} is a key and {address} is a key. No name may repeat, and no address may repeat.

(b) declares one key, {name, address}. Only the combination may not repeat. A name may appear twice with different addresses, and an address may appear twice with different names.

So (a) is the stronger rule: every table that satisfies (a) also satisfies (b) (if the names already differ, the pairs differ), but not the other way round. In the language of section 2: under (a), {name, address} is a superkey that is not minimal, so it is not a candidate key. The animation feeds the same four INSERT statements to both tables.

A detail where Oracle differs from the standard. For a composite UNIQUE key, Oracle treats rows whose key columns are all NULL as never conflicting, but rows that are NULL in some key columns and equal in the others do conflict: inserting ('Ann', NULL) twice into table (b) gives ORA-00001 in Oracle. Standard SQL, PostgreSQL and SQLite (the playground) accept both rows. The playground also has one quirk of its own: SQLite lets a NULL into a PRIMARY KEY column unless the column is also declared NOT NULL. Oracle never does. When the playground accepts a NULL key, remember that Oracle would raise ORA-01400.

What is the difference between UNIQUE key and Primary key? (2012–13 wording: What are the differences between UNIQUE and PRIMARY KEY constraints in SQL?)

Show worked answer

Both constraints say that no two rows of the table may have the same value in the key column(s), and in Oracle both are enforced with a unique index. They differ in four ways:

  1. NULL values. A PRIMARY KEY column can never be NULL (PRIMARY KEY implies NOT NULL; Oracle raises ORA-01400). A UNIQUE column may be NULL, and several rows may have NULL there, because NULL means "unknown" and two unknowns are not known to be equal.
  2. Number per table. A table has at most one primary key. It may have any number of UNIQUE constraints (one for each alternate key).
  3. Role. The primary key is the chosen main identifier of a row. A UNIQUE constraint declares an alternate (candidate) key. To make a UNIQUE column behave like a key fully, add NOT NULL.
  4. Foreign keys. A foreign key may reference either, but REFERENCES T without a column list refers to T's primary key.
CREATE TABLE Employee (
  emp_id   NUMBER(6)     PRIMARY KEY,          -- unique, never NULL, only one per table
  email    VARCHAR2(50)  UNIQUE NOT NULL,      -- alternate key
  passport VARCHAR2(20)  UNIQUE,               -- unique when present; many NULLs allowed
  name     VARCHAR2(40)  NOT NULL
);
INSERT INTO Employee VALUES (1, 'a@x.com', NULL, 'Ann');   -- OK
INSERT INTO Employee VALUES (2, 'b@x.com', NULL, 'Bob');   -- OK: two NULL passports
INSERT INTO Employee VALUES (NULL, 'c@x.com', 'P1', 'Cy'); -- ORA-01400 (NULL primary key)
INSERT INTO Employee VALUES (3, 'a@x.com', 'P2', 'Di');    -- ORA-00001 (duplicate email)

Note: the CSE 215 bank's answer says a primary key creates a clustered index and UNIQUE a non-clustered one. That is true of SQL Server and MySQL/InnoDB, not of Oracle: an ordinary Oracle table is a heap, and both constraints get an ordinary unique B-tree index. (Only an index-organized table stores rows in primary-key order.)

Summary: Constraints are rules written into the schema and enforced by the DBMS on every change. A superkey never repeats; a candidate key is a minimal superkey; the primary key is the chosen candidate key and is never NULL; other candidate keys are declared UNIQUE (usually with NOT NULL). Single-column constraints can be written inline; multi-column keys need the table-constraint form. Two UNIQUE columns are two keys, which is stronger than one UNIQUE pair.
