Secondary Indices

A file can be sorted in only one order, but you often want to search by other attributes too. A secondary index makes that possible. This chapter shows how it is built (with buckets), answers the slide 13 question, and animates why it slows down updates and range scans.

1. What a secondary index is (slide 13)

The instructor file is sorted on ID, so the index on ID is its primary (clustering) index. But users also search by salary or by department. An index on one of those attributes is a secondary index: an index whose search key specifies an order different from the sequential order of the file. It is also called a non-clustering index, because records with nearby salaries are not stored near each other. They are scattered across the file.

That scattering has two consequences:

  1. A secondary index must be dense. A sparse index relies on scanning forward through sorted records, and here the file is not sorted by salary, so every salary value needs its own entry.
  2. One value can match many scattered records. Two instructors earn 80000 (Singh and Kim), and they are far apart in the file. So the index entry does not point at a record. It points to a bucket: a small list that holds pointers to all the records with that value.

Question (worked answer)

The primary index is on id. (a) How many secondary indices can be created for this relation? (b) Construct a secondary index on dept-name, showing only id and dept-name.

(a) A secondary index can be created on any attribute other than the one the file is sorted on. The relation has four attributes, and id is taken by the primary index, so there can be 3 single-attribute secondary indices: on name, on dept-name and on salary. (If composite search keys are counted, as in Chapter 6, more are possible: any combination of attributes, such as (dept-name, salary), can also be a secondary index.) A file can have only one primary index, because it can be physically sorted in only one order, but it can have as many secondary indices as you like.

2. Indices cost something on every change (slide 14)

Indices make searching much faster, but the slide warns that they impose overhead on every modification of the database. The index is a copy of information in the file (keys and locations), and every copy has to be kept correct.

Insert or delete: every index on the relation must be updated. Explain?

Example: INSERT INTO instructor VALUES (22225, 'David', 'History', 70000). Suppose the relation has a primary index on id, a secondary index on salary and a secondary index on dept-name. Step through what has to change:

One INSERT turned into four writes: the record, plus one change in each of the three indices. If David's row had not been added to, say, the salary index, then WHERE salary = 70000 would use the index and wrongly find nobody. A delete is the same in reverse: the record's entry or bucket pointer must be removed from every index.

Update: indices on the changed attribute must be updated. Explain?

Example: UPDATE instructor SET salary = 50000 WHERE id = 15151 (Mozart, currently 40000).

Only indices whose search key includes the changed attribute are affected. The id index and the dept-name index do not mention salary, so they stay as they are. The salary index must move Mozart from the 40000 entry to a 50000 entry. 40000's bucket becomes empty, so that entry is removed, and 50000 is a new value, so a new entry and bucket are created.

3. Range scans through a secondary index are expensive (slide 15)

Sequential scan using a clustering index is efficient, but a sequential scan using a secondary index is expensive on magnetic disk. Explain? Query: SELECT * FROM instructor WHERE salary <= 90000.

Using the salary index, the database walks the salary entries in order (40000, 60000, 62000, …) and fetches each record. But consecutive salaries belong to records in completely different places in the file. In the animation, the file has 3 records per block, and the memory holds one block at a time:

10 matching records cost 9 block fetches, because almost every record is in a different block from the previous one. The slide's numbers: each fetch from a magnetic disk takes about 5 to 10 milliseconds, mostly seek and rotation. So this query spends 45 to 90 ms on I/O. A plain scan of the whole file, in its stored order, reads each of its 4 blocks exactly once (about 4 fetches, and they are consecutive, so mostly without seeks) and simply skips the rows with salary > 90000.

That is the general lesson: through a clustering index, a range of keys is a run of neighbouring blocks. Through a secondary index, each record can be a separate random block read. When a range matches a large part of the table, the database is often better off ignoring the secondary index and scanning the file.

Construction. List the distinct B values in sorted order: b1, b2, b3. Each gets one index entry pointing to a bucket of at most 3 record pointers:

  • b1 → {a1, a4}
  • b2 → {a2, a5, a7} (the bucket is now full)
  • b3 → {a3, a8}

Inserting ⟨a8, b2, c2⟩. First the record must go into the file, and A is the primary key.

Case 1: the key a8 already exists. r already contains ⟨a8, b3, c1⟩, so the insert violates the primary-key constraint and is rejected. Neither the file nor the index changes. (If the intention were to update a8 to ⟨a8, b2, c2⟩, the pointer to a8 would move from b3's bucket to b2's bucket, which then overflows exactly as in case 3.)

The question most likely intends a new key; the missing key in the sequence is a6, and the next question in the same paper inserts a6. So take t = ⟨a6, b2, c2⟩. The record goes into the file between a5 and a7 (the file is sorted on A). For the index, the general cases are:

  1. The B value is new (for example b4): insert a new entry b4 into the index in sorted position and create a new bucket holding one pointer.
  2. The B value exists and its bucket has a free slot (b1 or b3): just add the pointer to that bucket.
  3. The B value exists and its bucket is full: this is our case, since b2's bucket already holds a2, a5, a7. Allocate an overflow bucket, chain it from b2's bucket, and put the pointer to a6 there. (Alternatively the bucket can be split into two chained buckets; the index entry for b2 still points to the first.)
DB QB · 20-21 3a · 10 marks  |  BUET QBank · CSE 215 | L-2/T-2 | 2020–21 · 10 marks

The student relation and query on the relation are given as follows:
Student (Id, name, f_name, m_name, cgpa, year_admit, division, district, thana, street, house_number, city, NID, DOB, total_credit).

SELECT * FROM student WHERE name = 'Abid' AND City = 'Feni' AND year_admit = 2015

The B+ tree secondary indices on name, city, and year_admit are given. The heights of the indices are 4, 2 and 1 respectively. The number of tuples (pointers) for name 'Abid', City = 'Feni', and year_admit = 2015 are 50, 20 and 1000 respectively. Seek cost is 10 ms and block transfer cost is 0.1 ms. The number of blocks of the student relation is 2000.

i. Find the worst-case costs of processing the above conjunctive selection query using the single index method.
ii. Explain clearly how this query will be executed in this method.

Show worked answer

The single index method (textbook algorithm A7, conjunctive selection using one index): pick one of the conditions that has an index, use that index to fetch the matching tuples, and test the remaining conditions on each fetched tuple in memory. The optimizer computes the cost for each usable index and picks the cheapest.

Cost of one secondary-index equality lookup (textbook algorithm A4, secondary index, equality on a non-key): traverse the tree, hi node reads, then fetch each of the n matching tuples. In the worst case each tuple is in a different block, and every read is a random access (seek + transfer):

cost = (hi + n) × (tS + tT) = (hi + n) × (10 + 0.1) ms

Index usedhinBlock readsCost
name = 'Abid'4505454 × 10.1 = 545.4 ms
city = 'Feni'2202222 × 10.1 = 222.2 ms
year_admit = 20151100010011001 × 10.1 = 10,110.1 ms

The worst-case cost with the single index method is therefore 222.2 ms, using the index on city.

(ii) Execution.

  1. The optimizer estimates the three costs above and chooses the city index, the most selective one (20 matching tuples).
  2. It searches the city B+ tree for 'Feni': root to leaf, 2 node reads.
  3. The leaf entry for 'Feni' gives 20 record pointers.
  4. It fetches the 20 records, 20 random block reads in the worst case.
  5. For each record in memory it tests the other two conditions, name = 'Abid' AND year_admit = 2015, outputs the records that pass and discards the rest. The name and year_admit indices are not used at all.

Check against a linear scan: one seek plus 2000 transfers = 10 + 2000 × 0.1 = 210 ms. That is in fact slightly cheaper than 222.2 ms, so a real optimizer comparing all plans would scan the file; the question, however, asks for the single index method.

Note: the question bank's answer charges (hi + 1) index reads and gets 232.3 ms. The textbook formula is (hi + n) × (tS + tT), where hi is the number of levels read from root to leaf; the extra +1 is only right if “height” is taken to count edges instead of levels. State your convention in the exam.

DB QB · Jan 20 2b · 15 marks  |  BUET QBank · CSE 215 | L-2/T-2 | 2018–19 · 8 marks

The Employee Management System of an organization has the following relational schema: employee (e-id, name, date-of-birth, salary, street, thana, district, NID). Total employees are 40000 and the size of the employee relation is 4000 blocks. The primary index is e-id and secondary indices are name, district and NID. The heights of the indices e-id, name, district and NID are 4, 3, 2 and 4 respectively. The time to transfer 1 block is 0.5 ms and the average seek time in the disk is 8 ms. The number of tuples with salary = 50000 is 100 and district = 'Comilla' is 2000. Consider each tuple is in a different block and non-overlapping.

(i) Find the query costs using the indices for the SQL: SELECT * FROM employee WHERE salary = 50000 OR district = 'Comilla'
(ii) Explain the algorithm you have used to process the SQL of this question.

Show worked answer

Disjunctive selection (textbook algorithm A10, union of record identifiers) can use indices only if every condition in the OR has an index: look each one up, take the union of the record pointers, and fetch those records. If even one condition has no index, the index results are useless, because a tuple satisfying only that condition could be anywhere in the file. Then the only correct plan is a linear scan that tests the whole OR on every tuple.

Here district has an index, but salary has none (the indices are on e-id, name, district and NID). So:

  • Using the district index alone is wrong: it finds the 2000 Comilla employees but misses the 100 employees with salary 50000 who live elsewhere. Its cost would already be (2 + 2000) × (8 + 0.5) = 17,017 ms, and a scan would still be needed for the salary condition.
  • Linear file scan (textbook A1): one seek, then 4000 consecutive block transfers: 8 + 4000 × 0.5 = 2,008 ms.

The query cost is therefore 2,008 ms, with a linear scan.

For comparison, if salary did have a secondary index of height 2 (not given), A10 would cost (2 + 100) × 8.5 + (2 + 2000) × 8.5 = 17,884 ms, still worse than the scan, because 2,100 random reads (each 8.5 ms) cost more than reading the whole relation sequentially.

(ii) Algorithm. Linear scan: seek to the first block of employee; read each of the 4000 blocks in order; for every tuple in the block, test salary = 50000 OR district = 'Comilla' and output it if true. Because the two sets are disjoint (“non-overlapping”), the result has 100 + 2000 = 2,100 tuples and no duplicates need to be removed.

Summary: a secondary (non-clustering) index is on an attribute the file is not sorted by. It must be dense, and each entry points to a bucket of pointers to all matching records. A relation can have many secondary indices but only one primary index. Every index must be updated on insert and delete (and on updates to its key attribute), and range scans through a secondary index can cost one random block fetch per record.
