Searching a B+ Tree

The find(v) algorithm from the slides, run step by step on the slides' trees with every comparison shown. You can type any name into the tracers and watch the search. Includes Question W-1 and why B+ trees need so few disk reads.

1. The find(v) algorithm (slide 32)

To find the record with search key V, start at the root and go down one level at a time. At each non-leaf node, pick the pointer whose key range (Chapter 8) contains V. At the leaf, look for V itself.

function find(V)
1.  C = root
2.  while (C is not a leaf node)
2.1     Let i be least number s.t. V ≤ C.Kᵢ
2.2     if there is no such number i then
2.3         Set C = last non-null pointer in C
2.4     else if (V = C.Kᵢ) Set C = C.Pᵢ₊₁
2.5     else set C = C.Pᵢ
3.  if for some i, Kᵢ = V then return C.Pᵢ
4.  else return null   /* no record with search-key value V exists */

Line by line, in plain words:

  • 2.1 Scan the node's keys from left to right and stop at the first key that is greater than or equal to V.
  • 2.2–2.3 If every key is smaller than V, V belongs to the rightmost subtree, so follow the last pointer.
  • 2.4 If that key equals V, follow the pointer to its right, Pi+1. Recall from Chapter 8 that the subtree right of Ki holds keys ≥ Ki, so V is there.
  • 2.5 Otherwise the key is strictly greater than V, so follow the pointer to its left, Pi, where keys are smaller than Ki.
  • 3–4 At the leaf, either V is one of its keys (return its record pointer) or it is not in the file at all.

2. Slide 31 question: find “Gold”

Given the B+ tree index on name, how is SELECT * FROM instructor WHERE name = 'Gold' executed? Press Play, or step through. The highlighted line in the code is the one being executed. You can also type another name and press Trace find(v).

In words: at the root, “Gold” ≤ “Mozart”, and they are not equal, so go left (line 2.5). At [Einstein, Gold], “Gold” ≤ “Einstein” is false, “Gold” ≤ “Gold” is true with i = 2, and V equals K₂, so follow P₃ (line 2.4) to the leaf [Gold, Katz, Kim]. K₁ = Gold matches, so return P₁ and fetch the record (33456, Gold, Physics, 87000). That is 3 node reads plus 1 record read.

Question W-1 (worked answer)

Explain how the following queries are executed using the given B+ tree index (slide 33's tree).

(a) SELECT * FROM instructor WHERE name = 'Crick'

  1. C = root [Mozart]. Crick ≤ Mozart, so i = 1. Not equal, so C = P₁ → [Califieri, Einstein, Gold].
  2. Crick ≤ Califieri? No (“Cr” comes after “Ca”). Crick ≤ Einstein? Yes, so i = 2. Not equal, so C = P₂ → leaf [Califieri, Crick].
  3. C is a leaf. K₂ = Crick matches, so return P₂ → record (76766, Crick, Biology, 72000).

(b) SELECT * FROM instructor WHERE name = 'Rafique'

  1. C = root [Mozart]. Rafique ≤ Mozart? No. There is no such i, so line 2.3: follow the last non-null pointer, P₂ → [Srinivasan].
  2. Rafique ≤ Srinivasan? Yes, i = 1. Not equal, so C = P₁ → leaf [Mozart, Singh].
  3. C is a leaf. Neither Mozart nor Singh equals Rafique, so line 4: return null. No instructor is called Rafique. The tree proves it after reading just 3 nodes. Rafique would sit between Mozart and Singh if it existed, and it is not there.

4. How many nodes does a search read? (slide 34)

Every search reads exactly one node per level, so its cost is the height of the tree. Because every non-root node has at least ⌈n/2⌉ children, each level multiplies the number of reachable keys by at least ⌈n/2⌉. So with K search-key values in the file:

height ≤ ⌈ log⌈n/2⌉(K) ⌉

Realistic numbers from the slide: a node is the size of a disk block, typically 4 KB, and with about 40 bytes per index entry (key + pointer), n is around 100. With 1 million search-key values:

log₅₀(1,000,000) ≈ 3.53, so at most 4 nodes are read

(50 = ⌈100/2⌉, the worst case where every node is only half full. 50⁴ = 6.25 million, which is more than 1 million, so 4 levels are always enough.)

Compare a balanced binary tree, where every node has only 2 children. Each level only doubles the reach, so 1 million keys need log₂(1,000,000) ≈ 20 levels, and a search reads around 20 nodes.

This is why the difference matters: every node access may need a disk I/O. 4 reads × 20 ms = 80 ms for the B+ tree, versus 20 × 20 ms = 400 ms for a binary tree. In practice the root and the second level of a B+ tree are almost always cached in memory, so a lookup often costs only 1 or 2 actual disk reads. That large fan-out is the whole reason databases use B+ trees rather than binary trees.

DB QB · 24-25 4b · 15 marks  |  BUET QBank · CSE 215 | L-2/T-1 | 2024–25 · 15 marks

Given a B+ tree index with 10 million records, suppose the node size is 4 kilobytes, search-key size is 8 bytes, and disk-pointer size is 4 bytes. Answer the following questions:
(i) Given a search-key, how many index blocks need to be read from the disk in the best case for finding the pointer to the data record?
(ii) Given a range query assuming 1000 records will be retrieved, how many index blocks need to be read from the disk in the best case for finding the pointers to all the data records?
(iii) Given a search-key, how many index blocks need to be read from the disk in the best and worst cases to find the data pointer if we use a hash index instead of a B+ tree index? Assume that the hash index requires at most three overflow blocks.

Show worked answer

Fan-out. A node of 4,096 bytes holds n pointers and n − 1 keys: 4n + 8(n − 1) ≤ 4096 ⇒ 12n ≤ 4104 ⇒ n = 342. A leaf therefore holds up to 341 keys (with 341 record pointers and the next-leaf pointer).

Height. Count the levels for 10,000,000 keys:

  • Full nodes: ⌈10⁷/341⌉ = 29,326 leaves → ⌈29,326/342⌉ = 86 nodes → 1 root: 3 levels.
  • Least full nodes allowed (leaves 171 keys, internal nodes 171 children, root 2 children): a 4-level tree would need at least 2 × 171 × 171 = 58,482 leaves, but 10⁷ keys fill at most ⌊10⁷/171⌋ = 58,479 leaves of 171 keys. So 4 levels are impossible, and the tree has exactly 3 levels however full it is.

(i) A B+ tree lookup always goes from the root to a leaf, and the record pointers are only in the leaves: 3 index blocks (root, one internal node, one leaf). Because the height is always 3, this is also the worst case.

(ii) Descend once to the leaf holding the first key in the range (3 blocks), then follow the leaf chain. In the best case the leaves are full and the range starts at the first key of a leaf, so 1000 keys occupy ⌈1000/341⌉ = 3 leaves (341 + 341 + 318). The first of them was already read during the descent, so 2 more leaf reads: 3 + 2 = 5 index blocks.

(iii) A hash index computes the bucket number from the key, so there is no tree to descend. Best case: the pointer is in the bucket's primary block: 1 block. Worst case: the bucket has the maximum three overflow blocks and the key is in the last one (or is absent, which also requires reading the whole chain): 1 + 3 = 4 blocks. (Hashing is taught in Static hashing.) The hash index can beat the B+ tree on a point lookup, but it cannot do part (ii): a hash index has no key order, so a range query cannot use it.

DB QB · 22-23 8b · 5 marks  |  BUET QBank · CSE 215 | L-2/T-1 | 2022–23 · 5 marks

For a degree 5 B+ tree, what will be the height of the B+ tree when the numbers from 1 to 100 are inserted sequentially? Hint: a tree with l leaves and internal nodes of degree d (some constant number of internal nodes can have degree > d) has height approximately logd l.

Show worked answer

Degree 5 means n = 5: at most 5 pointers and 4 keys per node. The standard insertion algorithm (taught in the B+ tree insertion chapter after this lecture) splits an overfull leaf of 5 keys into 3 + 2 keys, and an overfull internal node of 6 pointers into 3 + 3 pointers.

Sequential inserts always go into the rightmost leaf. When it splits, the left half (3 keys) is never touched again. So every leaf except the last ends with exactly 3 keys, and likewise every internal node except the rightmost one on each level ends with 3 children: nodes stay partly empty (3 of 4 key slots in a leaf, 3 of 5 pointers in an internal node), and the effective degree is d ≈ 3.

  • Leaves: 32 leaves of 3 keys (1–96) and a last leaf with 4 keys (97–100): 33 leaves.
  • Level above the leaves: 33 pointers, 3 per node: 11 nodes.
  • Next level: 11 pointers as 3 + 3 + 5: 3 nodes, [10, 19], [37, 46], [64, 73, 82, 91].
  • Root: 3 pointers: [28, 55].

The tree has 4 levels (root, two internal levels, leaves), so its height is 3 counted in edges (4 counted in nodes, the convention of the find(v) cost). The hint agrees: with d ≈ 3 and l = 33, log₃ 33 ≈ 3.2, about 3 levels above the leaves. With full nodes (d = 5) it would be lower: 25 leaves of 4 keys need only ⌈log₅ 25⌉ = 2 levels above them.

This was checked by running the insertion algorithm for 1…100 with n = 5 and testing the tree's invariants (sorted keys, all leaves at one depth, occupancy limits).

Summary: find(V) walks from the root to a leaf. At each node it finds the first key ≥ V: if equal, it goes right of that key; if greater, left of it; if none, to the last pointer. At the leaf it either finds V and returns the record pointer, or returns null. A search reads one node per level, and with fan-out around 100 even a million keys need at most 4 levels, compared with about 20 for a binary tree.
