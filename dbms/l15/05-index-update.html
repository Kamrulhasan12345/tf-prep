Updating an Index: Deletion and Insertion

When records are deleted or inserted, every index has to follow. This chapter gives the rules for dense, sparse and multilevel indices, animates each case, writes out the algorithms the slides ask for, and works the 160-million-record NID question.

1. The general rule for deletion (slides 18–19)

The slides start with a rule that applies to every index: if the deleted record was the only record in the file with its particular search-key value, the search key is deleted from the index too. If other records still have that value (for example, deleting one of three Comp. Sci. instructors from a dept-name index), the index entry stays, because it is still needed to find the others.

2. Deleting from a dense index

For a dense index, deleting a search key is similar to deleting a file record (Lecture 14, Chapter 3). The index is just a sorted file of entries, so the entry is removed and the gap is closed by shifting or by a free list.

Slide 18's example: DELETE FROM instructor WHERE id = 22222.

Question (worked answer): algorithm for deletion in a dense index

delete_dense(K):
    1. Use the index to find the record(s) with search key K; delete the record from the file.
    2. if no other record in the file has search key K:
           delete the index entry for K
           (shift the following entries up, or put the slot on a free list)
    3. else if the index entry pointed at the deleted record:
           change its pointer to the next record with key K
           (for an index with buckets: just remove that pointer from K's bucket)

3. Deleting from a sparse index

A sparse index only has entries for some keys, so there are three possibilities when record K is deleted:

  1. K has no index entry. Nothing to do in the index. This is the slide's own example: with the sparse index (10101, 32343, 76766), deleting 22222 changes only the file.
  2. K has an entry, and the next key in the file does not. Replace the entry for K by the next search-key value in the file (in search-key order). The entry then points to that next record, which is now where the run of records starts.
  3. K has an entry, and the next key already has one. Delete the entry instead of replacing it, since there is nothing between the two entries any more.

The animation uses a block-level sparse index (one entry per block, as recommended in Chapter 2). The file has 3 slots per block, and some blocks have free slots, which also prepares us for insertion.

Question (worked answer): algorithm for deletion in a sparse index

delete_sparse(K):
    1. Find the largest index entry ≤ K, follow it, and delete record K from the file.
    2. if the index has no entry for K:
           done                                   -- case 1
    3. else:
           K' = the next search-key value after K in the file
                (for a block-level index: the next key in the same block)
           if K' exists and K' has no index entry:
               replace entry K by (K', pointer to K')  -- case 2
           else:
               delete entry K                     -- case 3

4. Inserting into a dense index (slide 20)

Every insertion starts the same way: perform a lookup using the search-key value of the record to be inserted, to find where it belongs. For a dense index: if the search-key value does not appear in the index, insert it. The slide notes two practical details:

  • Indices are maintained as sequential files, sorted by key, so the new entry must go in its sorted position, and the entries after it shift down.
  • Space may need to be created for the new entry, and when the index block is full, an overflow block may be required: an extra block chained to the full one that holds entries that did not fit.

Slide 20's example: INSERT INTO instructor VALUES (45566, 'Karim', 'Physics', 70000).

5. Inserting into a sparse index (slide 21)

For a sparse index with one entry per block: no change needs to be made to the index unless a new block is created. If a new block is created, the first search-key value appearing in the new block is inserted into the index. The slide assumes 3 records per block and inserts two records:

  • (98400, 'Abid', 'History', 50000): no new block needed.
  • (32400, 'Atika', 'Comp. Sci', 80000): a new block is needed.

Question (worked answer): insertion algorithms for single-level dense and sparse indices

insert_dense(record r with key K):
    1. Look up K in the index.
    2. Insert r into the file in key order (use a free slot; if the block is full,
       use an overflow block or split the block).
    3. if K is not in the index:
           insert entry (K, pointer to r) in sorted position,
           shifting later entries (overflow block if the index block is full)
       else (K already present):
           secondary index: add a pointer to r in K's bucket
           clustering index: nothing (the entry already points at the first K)

insert_sparse(record r with key K):        -- one entry per block
    1. Find the largest index entry ≤ K; it names block B.
    2. if B has a free slot:
           put r into B in key order        -- index unchanged
    3. else:
           create a new block B'; move the records of B that come after r's
           position (or r itself) into B', keeping key order
           insert entry (first key of B', pointer to B') into the index

6. Multilevel indices (slide 22)

Multilevel insertion and deletion algorithms are simple extensions of the single-level algorithms. Treat each level as a single-level index on the level below it, and work from the bottom up:

  • Insertion: insert into the data file. If that created a new data block, insert its first key into the level-1 index. If that created a new level-1 block, insert its first key into level 2. Continue upward until some level absorbs the change without creating a new block.
  • Deletion: delete from the data file. If that removed or replaced a level-1 entry, apply the sparse deletion rules to level 1. If a level-1 block's first entry changed or the block became empty, apply the same rules one level up, and so on.

Most of the time the change stops at the bottom level, because blocks usually have free space. In the animation above, inserting Abid changed nothing in the index at all, and inserting Atika changed only level 1.

Question (worked answer): a 4-level index for an NID database

Write the deletion/insertion algorithms for a multilevel index with an example of 4 levels for an NID (national ID) database with 160 million records. Block size is 16 KB, and each block can hold 16 NID records or 800 index records.

Building the levels. The data file is sorted on NID, so every index level can be sparse, with one entry per block of the level below:

LevelWhat it indexesEntriesBlocks
Level 0: data file160,000,000 records, 16 per block160,000,000160,000,000 ÷ 16 = 10,000,000
Level 1 indexone entry per data block10,000,00010,000,000 ÷ 800 = 12,500
Level 2 indexone entry per level-1 block12,500⌈12,500 ÷ 800⌉ = 16
Level 3 index (root)one entry per level-2 block161

That gives the 4 levels: three index levels plus the data level. The root is a single 16 KB block, easily kept in memory. Finding any NID reads 1 block per level below the root: level 2, level 1, then the data block, so 3 block reads (4 if the root is not cached). Binary search on the 10,000,000 data blocks would need about log₂(10⁷) ≈ 24 reads.

Insertion of a new person with NID K:

insert_multilevel(r with key K):
    1. Starting at the root (level 3), at each level follow the largest entry ≤ K
       down to the data block B that should hold K.        -- 3 block reads
    2. if B has a free slot: put r in B. Done.              -- by far the common case
    3. else split B: create B', move the upper half of B's records into it.
       Insert (first key of B', pointer to B') into the level-1 block L1 above B.
    4. if L1 had room: done.
       else split L1 into L1 and L1', and insert (first key of L1', pointer)
       into the level-2 block above.
    5. Repeat upward. If the root splits, create a new root with two entries:
       the index gains a 5th level.

Example: inserting an NID into a data block that has 11 of its 16 slots used changes 1 block. Only when that data block is full does level 1 change, and only when a level-1 block reaches 800 entries does level 2 change.

Deletion of NID K:

delete_multilevel(K):
    1. Follow the levels down to data block B and delete record K.
    2. if K was the first key of B (so it is B's level-1 entry):
           if B still has records: replace the level-1 entry by B's new first key
           else (B is now empty): delete the level-1 entry and free B
    3. If that changed the first entry of a level-1 block, or emptied it,
       apply the same rule to its level-2 entry; repeat upward.

Example: deleting an NID that is in the middle of its data block changes only that data block. Deleting the last NID of a data block also deletes one level-1 entry, and that level-1 block still has hundreds of other entries, so the change stops there.

DB QB · 20-21 2a · 10 marks  |  BUET QBank · CSE 215 | L-2/T-2 | 2020–21 · 10 marks

Given that one block contains only three records, and no overflow block is allowed. Show the index structure with the concerned blocks after insertion of the following tuples: (12122, Rafique, History, 40000) and (83820, Abid, Comp. Sci., 90000).

Show worked answer

The index is a block-level sparse index (slide 21): the index changes only when a block is created, or when a block's first key changes. No overflow blocks are allowed, so a full block has to be split into two blocks.

Insert 12122 (Rafique). Lookup: largest entry ≤ 12122 is 10101, so the record belongs in block 0, between 12121 and 15151. Block 0 is full (10101, 12121, 15151). Create a new block after block 0. In key order the four records are 10101, 12121, 12122, 15151: block 0 keeps the first three, and 15151 moves to the new block. The new block's first key, 15151, is inserted into the index between 10101 and 22222.

Insert 83820 (Abid). 83820 is just below 83821, so it belongs immediately before Brandt in key order. The last block (83821, 98345) has one free slot, so place 83820 at the start of that block (83820, 83821, 98345). No block is created, but the block's smallest key changed, so its index entry 83821 is replaced by 83820. Without this change a search for 83820 would go to the previous block and miss it.

Two equally valid variants, if you state them: (1) when splitting block 0, a half-and-half split (10101, 12121 | 12122, 15151) gives the new index entry 12122 instead of 15151 (this is the question bank's answer); (2) following the lookup rule literally sends 83820 to the block before 83821; if that block is full, a new block holding 83820 is created and the entry 83820 is inserted, keeping 83821's entry. The version above uses the free slot and creates no extra block.

First, the file order. As printed, the file is sorted on department_code (CSE before EEE), not on student_id: 1205016 is followed by 1204001. A sparse index on student_id needs the file sorted on student_id (Section 3 of Chapter 2), so we store it in student_id order: 1204001, 1204002, 1204003, 1205001, 1205004, 1205007, 1205010, 1205013, 1205016. Then student_id gives the primary (clustering) index, and department_code, which is no longer the file order, gets a secondary index.

(a) Sparse index with the three given entries, each pointing to its record: 1204001 → record 1204001, 1205001 → record 1205001, 1205010 → record 1205010. A search for, say, 1205007 starts at 1205001 and scans forward.

(b) Secondary index on department_code: one entry per value, each pointing to a bucket: CSE → {1205001, 1205004, 1205007, 1205010, 1205013, 1205016}, EEE → {1204001, 1204002, 1204003}.

(c) Delete 1205010. Remove the record. In the sparse index, 1205010 has an entry and the next key, 1205013, has none, so the entry is replaced by 1205013. In the secondary index, CSE still has other students, so the CSE entry stays and only the pointer to 1205010 is removed from its bucket.

(d) Insert {1205011, N114, EEE, 3, 1}. In the file it goes between 1205007 and 1205013. The sparse index is unchanged: a search for 1205011 starts at entry 1205001 and scans forward to it. In the secondary index, EEE already exists, so a pointer to the new record is added to EEE's bucket (now 4 pointers).

Summary: a deleted key leaves the index only if no other record has that key. Dense indices delete or insert their entry like a sequential file. Sparse indices change only when an indexed key is deleted (replace it with the next key, or delete it) or when a new block is created (insert its first key). Multilevel indices apply the same rules level by level, bottom up, and changes rarely travel far.
