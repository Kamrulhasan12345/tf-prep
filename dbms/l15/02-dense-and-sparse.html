Primary, Dense and Sparse Indices

An ordered index can have an entry for every key (dense) or only for some keys (sparse). This chapter explains both, animates a sparse-index lookup, answers the slide 10 question, and shows why the usual choice is one entry per block.

1. Ordered and primary indices (slide 7)

In an ordered index, the index entries are stored sorted by search-key value. Recall from Lecture 14 that a file can itself be kept in order: a sequentially ordered file stores its records sorted on some attribute. The instructor file in the slides is sorted on ID.

A primary index is an index whose search key is the same attribute the file is sorted on. Since the file and the index are in the same order, consecutive index entries point to consecutive records. Two notes from the slide:

  • A primary index is also called a clustering index, because records with nearby key values are physically clustered together in the file.
  • The search key of a primary index is usually the primary key, but not necessarily. If the file were sorted on dept_name, an index on dept_name would be the primary (clustering) index, even though dept_name is not a key. Section 2 shows exactly that case.

2. Dense indices (slides 8–9)

A dense index has an index entry for every search-key value that appears in the file. The index on ID (Figure 1) is dense: 12 distinct IDs, 12 entries.

Slide 9 shows a dense index on dept_name, with the instructor file now sorted on dept_name. Some departments have several instructors, but a dense index needs one entry per distinct value, not per record. Each entry points to the first record with that value. Because the file is sorted on dept_name, the other records with the same department follow right after it, so you read forward until the department changes.

3. Sparse indices (slide 10)

A sparse index has entries for only some of the search-key values. That only works when the file is sorted on the search key, because the sorting is what lets you find the keys that have no entry. The slide's lookup rule for a key K:

  1. Find the index entry with the largest search-key value ≤ K.
  2. Follow its pointer and scan the file forward from that record until you find K, or pass it.

The slide writes “< K”, but it should be “≤ K”: if K itself has an entry, you start exactly there. Since the index is sorted, the largest entry ≤ K is the right place to start: every record before it is too small, and K must lie between this entry and the next one.

Question (worked answer)

(a) Explain how SELECT * FROM instructor WHERE id = 45565 is executed using the given sparse index (entries 10101, 32343, 76766).

  1. Look through the index for the largest key ≤ 45565. 10101 ≤ 45565, 32343 ≤ 45565, but 76766 > 45565. So the entry is 32343.
  2. Follow its pointer to record 32343 (El Said). Not a match.
  3. Read forward: 33456 (Gold), not a match. Then 45565 (Katz): found.

3 records read after the index lookup. The scan can stop early at any record larger than 45565 too, because the file is sorted: if 45565 did not exist, reaching 58583 would prove it.

4. Trade-offs, with examples (slide 11)

Sparse: less space and less maintenance

Example: INSERT INTO instructor VALUES (12120, 'Rafique', 'Physics', 60000). 12120 sits between 10101 and 12121 in the sorted file.

The dense index must insert a brand-new entry 12120 into its sorted list, shifting the entries after it. The sparse index does nothing: 12120 lies between its entries 10101 and 32343, so a later search for 12120 will start at 10101 and scan forward to it. That is the “less maintenance overhead” on the slide.

Sparse: generally slower to locate a record

Example: SELECT * FROM instructor WHERE id = 76543. With the dense index, one lookup gives the exact record. With the sparse index, the largest entry ≤ 76543 is 32343, and the scan must read 32343, 33456, 45565, 58583 and finally 76543: 5 records instead of 1.

5. The good trade-off: one entry per block (slide 12)

Here is the key insight that makes sparse indices practical. The expensive part of reading is the block transfer, not looking at a record inside a block that is already in memory. So give the sparse index exactly one entry per block, holding the smallest search key in that block.

Now a lookup finds the right block from the index, reads that one block, and searches inside it in memory. That costs the same single block transfer as a dense index, while the index has only as many entries as there are blocks: here 3 instead of 12, and in real files often 1/100th the size of a dense index.

The slide adds the case where this does not work: for an unclustered index (the file is not sorted on the index's key), a sparse index is impossible on its own, because the records with nearby keys are not next to each other. The solution there is a dense index, with a sparse index built on top of it. That is a multilevel index, covered in Chapter 4.

DB QB · Jan 20 3a · 15 marks  |  BUET QBank · CSE 215 | L-2/T-2 | 2018–19 · 15 marks (first part)

Explain how the following queries will be executed using the sparse index shown in the figure (the sparse index 10101, 32343, 76766 on the instructor file of slide 10).

(i) SELECT * FROM instructor WHERE id = 22222
(ii) SELECT * FROM instructor WHERE id = 99999

(The deletion part of the CSE 215 version is answered in Updating an index.)

Show worked answer

Rule for a sparse index: find the index entry with the largest key ≤ K, follow its pointer, then read the file forward in key order until K is found or a larger key (or the end of the file) proves K is absent.

(i) id = 22222. Compare with the index: 10101 ≤ 22222 ✓, 32343 ≤ 22222 ✗. The largest entry ≤ 22222 is 10101. Follow it to Srinivasan's record and scan forward: 10101 (no), 12121 (no), 15151 (no), 22222 (match, Einstein). Four records are examined. If records are packed several to a block, this is one or two block reads.

(ii) id = 99999. Every index key is ≤ 99999, so the largest one, 76766, is chosen. Follow it to Crick and scan: 76766 (no), 83821 (no), 98345 (no), then the end of the file. Since the file is sorted on id and no record ≥ 99999 was met, 99999 does not exist and the query returns an empty result. Three records are examined.

DB QB · 17-18 1b · 5 marks  |  BUET QBank · CSE 215 | L-2/T-2 | 2017–18 · 5 marks

Consider a dictionary where each page contains only a single word along with its description. If we take the word from each page and form indexing based on the taken words, then what type of indexing (Dense/Sparse) would it be? Explain your answer.

Show worked answer

It is a dense index. A dense index has an entry for every search-key value in the file. Here every page holds exactly one word, and we take the word from every page, so every search-key value (word) gets its own index entry.

It also happens to be the block-level layout of slide 12: one entry per page (block), holding the smallest key of that page. The two definitions coincide because each block holds exactly one record. In the usual dictionary, with many words per page and only the first word of each page in the index (the guide words at the top of the page), the same construction would be sparse. The deciding test is always: does every search-key value have an entry? Here yes, so dense.

Because the dictionary is sorted by word, this is also a primary (clustering) index.

Summary: a primary (clustering) index uses the key the file is sorted on. A dense index has an entry for every key value. A sparse index has entries for only some keys, finds the largest entry ≤ K, and scans forward from there. Sparse indices are smaller and cheaper to maintain but need a sorted file and are slower per lookup, unless they keep one entry per block, which gives the best of both.
