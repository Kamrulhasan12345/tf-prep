What an Index Is

An index is a small, sorted lookup table that tells the database exactly where a record is, so it does not have to read the whole file. This chapter defines the basic terms, compares a file scan with an index lookup step by step (Question Q1), and lists the yardsticks used to judge any index.

1. The problem an index solves

In Lecture 14 (Chapter 2), finding id = 76766 without any help meant a linear file scan: read the file from the first block, check every record, and stop when you find it. On a table with millions of rows, that can mean reading millions of blocks for one answer.

The slide's one-line definition: indexing mechanisms are used to speed up access to desired data. The idea is the same as the index at the back of a textbook. To find “B+ tree” you do not read the book page by page. You look the term up in the alphabetical index, which says “page 642”, and you go straight there. A database index does the same: a sorted list of values, each with the location of the matching record.

2. Question Q1: file scan versus index

Query: SELECT * FROM instructor WHERE id = 76766. The instructor relation and an index on id are given. Each record is stored in its own block. How is the query executed (a) without the index, using a linear file scan, and (b) using the index?

“Each record is stored in one block” is a simplification the slide makes so counting is easy: reading one record costs exactly one block transfer, and the 12 records occupy 12 blocks.

(a) Without the index: linear file scan

Press Play or Next to watch the scan. Each step reads one block and compares its ID with 76766.

76766 (Crick) is the 10th record, so the scan reads 10 blocks. Because ID is the primary key, it can stop as soon as it finds the record. If the ID were not unique, it would have to read all 12.

(b) With the index

The index is sorted, so 76766 can be found in it quickly (even reading every entry of an in-memory index is cheap, and a binary search takes about 4 comparisons for 12 entries). The entry's pointer gives the record's exact block, so the disk reads 1 block.

Question (worked answer): the index is kept in memory

(a) Best and worst case of the linear scan.

  • Best case: the record we want is the first record in the file. The scan reads 1 block and stops. For this query that would happen if we searched for 10101.
  • Worst case: the record is the last one, or it does not exist at all. The scan reads every block: 12 here, and N for a file of N blocks. Searching for 98345, or for 99999 (absent), costs 12 block reads.
  • On average, a search for a value that exists reads about half the file, roughly N/2 blocks.

(b) When is the index faster? With the index in memory, searching it costs no disk I/O, and following the pointer costs exactly 1 block read, whatever the record's position. The linear scan costs 1 block only in its best case. So the index is faster in every case except when the record happens to be first in the file, where both cost 1 block (a tie). It is also far faster when the value does not exist: the index says so with 0 block reads, while the scan reads all 12.

3. Basic vocabulary (slides 3–5)

Search key
The attribute, or set of attributes, used to look up records. An index on ID has search key ID, an index on name has search key name, and an index on dept-name has search key dept-name. A search key does not have to be unique and does not have to be the primary key. That is a different idea.
Index file
A separate file holding the index. It is made of records called index entries.
Index entry
A pair (search-key, pointer). The search-key is a value such as 76766. The pointer is the location of the record with that value: which block, and where in the block (for example, a slot number from Lecture 14's slotted page).

Index files are much smaller than the data file

An index entry stores only the key and a pointer, for example 5 bytes of ID plus an 8-byte pointer, versus a full row with name, department, salary and possibly dozens of other columns. So many more index entries fit in a block. An index on a 10 GB table might be only a few hundred megabytes, small enough to keep mostly in memory.

Two basic kinds of index

Ordered index
The index entries are kept sorted by search key, like the index at the back of a book. Sorting lets you find a value quickly and also find all values in a range. Chapters 2–9 of this lecture are about ordered indices, ending with the B+ tree.
Hash index
The search keys are spread across a number of buckets by a hash function: a formula that turns a key into a bucket number, for example id mod 10. To find 76766 you compute its bucket and look only there. Hashing is very fast for exact matches, but the keys are in no particular order, so it does not help with ranges. (The slides stop here. Hash indices are taught in the “beyond the slides” chapters Static hashing and after, because exams ask about them.)

DB QB · 18 CT3 4 · 4 marks  |  BUET QBank · CSE 303 | L-3/T-1 | 2010–11 · 5 marks

There are different types of indexing methods and structures used in every DBMS. Explain the metrics that are used to compare the performance of different indexing methods. (CSE 303 wording: Explain the factors by which an indexing technique can be evaluated.)

Show worked answer

No index is best for every workload, so indices are compared on five metrics (slide 6, and the textbook's list):

  1. Access types supported efficiently. Which kinds of query the index speeds up. A point query asks for one value (WHERE id = 76766); a range query asks for a range (WHERE id >= 76766). An ordered index (sparse, dense, B+ tree) supports both. A hash index supports only point queries well, because hashing scatters neighbouring keys into unrelated buckets.
  2. Access time. The time to find the wanted record(s) through the index: the index blocks read plus the data blocks read. Example: a dense index kept in memory finds id = 76766 with 1 data-block read, while a linear scan reads 10 blocks (Section 2).
  3. Insertion time. The time to insert a record including placing its entry in the index: finding the position, plus any shifting, overflow blocks or node splits.
  4. Deletion time. The time to delete a record including removing or replacing its index entry, plus any merging of underfull nodes.
  5. Space overhead. The extra storage the index occupies. A sparse index (one entry per block) is far smaller than a dense one (one entry per key).

The first two measure the benefit for reads. The last three measure the cost paid on every modification and in disk space. An update to an indexed attribute counts as a deletion followed by an insertion in that index, so it costs both. The designer picks an index whose benefit for the frequent queries outweighs this cost.

Summary: an index is a separate, smaller file of (search-key, pointer) entries that lets the database jump straight to records instead of scanning the file. Ordered indices keep entries sorted (good for points and ranges). Hash indices spread them over buckets (good for exact matches). Indices are judged by the queries they speed up, access time, insertion time, deletion time and space overhead.
