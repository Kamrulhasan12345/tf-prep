Deleting from a B+ Tree

Deletion is insertion run backwards: a node that becomes too empty either borrows a key from a sibling or merges with it, and a merge can ripple up to the root and make the tree shorter. This chapter teaches the standard algorithm (Silberschatz, §14.3.3), shows every case in an animator, and answers the exam questions that mix insertions and deletions, including one on plain B-trees.

1. Underflow

Removing a key from a leaf is easy. The problem is what it leaves behind. Every node except the root must stay at least half full (Chapter 10, Section 1): a leaf needs at least ⌈(n−1)/2⌉ keys and an internal node at least ⌈n/2⌉ pointers. A node that drops below its minimum has an underflow, and the tree must repair it before the operation ends.

Underflow
A non-root node with fewer entries than the minimum: fewer than ⌈(n−1)/2⌉ keys in a leaf, or fewer than ⌈n/2⌉ pointers in an internal node.
Sibling
A node immediately to the left or right of a node under the same parent. The repair only ever uses a sibling, because then exactly one separator key in the parent sits between the two nodes.
Coalesce (merge)
Combine an underflowing node with a sibling into one node, and delete the separator between them (plus the pointer to the removed node) from the parent. Allowed when the two nodes' contents fit in one node.
Redistribute (borrow)
Move one entry from a sibling that has more than it needs into the underflowing node, and update the separator in the parent so it still divides the two nodes correctly. The parent loses nothing, so the repair stops here.

2. The four repairs

Whether the node is a leaf or an internal node changes how keys move, because leaves keep every key while internal nodes only keep separators.

MergeBorrow
LeafAppend all keys of the right node to the left node and fix the leaf chain. Delete the separator and the right node's pointer from the parent. The separator simply disappears, since it was a copy.Move the sibling's nearest key (the last key of a left sibling, the first key of a right sibling) into this leaf. Replace the separator in the parent with the smallest key of the right-hand node of the pair.
InternalLeft node + the separator pulled down from the parent + right node. The separator comes down because the merged node needs one key between the two groups of pointers.A rotation through the parent: the sibling's nearest pointer moves over, the parent's separator comes down into this node, and the sibling's nearest key goes up to become the new separator.

A merge removes one entry from the parent, so the parent may underflow next, and the repair continues one level up. If the parent is the root and it loses its last key, it has a single child: that child becomes the new root and the tree gets one level shorter. This is the only way the height decreases, the mirror image of a root split.

Do you have to replace a deleted key that is also a separator?

No. If you delete 19 and 19 is a separator in an internal node, the separator still works: everything in the subtree to its right is still ≥ 19. Silberschatz leaves such keys alone. Many exam answers replace the separator with the new smallest key on its right, which is also correct. Either way, mention what you did.

3. The algorithm (Silberschatz)

procedure delete(value K, pointer P)
    find the leaf node L that contains (K, P)
    delete_entry(L, K, P)

procedure delete_entry(node N, value K, pointer P)
    delete (P, K) from N
    if (N is the root and N has only one remaining child)
        then make the child of N the new root of the tree and delete N
    else if (N has too few values/pointers) then begin
        Let N′ be the previous or next child of parent(N)
        Let K′ be the value between pointers N and N′ in parent(N)
        if (entries in N and N′ can fit in a single node)
        then begin   /* Coalesce nodes */
            if (N is a predecessor of N′) then swap_variables(N, N′)
            if (N is not a leaf)
                then append K′ and all pointers and values in N to N′
                else append all (Kᵢ, Pᵢ) pairs in N to N′;  set N′.Pₙ = N.Pₙ
            delete_entry(parent(N), K′, N);  delete node N
        end
        else begin   /* Redistribution: borrow an entry from N′ */
            if (N′ is a predecessor of N) then begin
                if (N is a nonleaf node) then begin
                    let m be such that N′.Pₘ is the last pointer in N′
                    remove (N′.Kₘ₋₁, N′.Pₘ) from N′
                    insert (N′.Pₘ, K′) as the first pointer and value in N
                    replace K′ in parent(N) by N′.Kₘ₋₁
                end
                else begin
                    let m be such that (N′.Pₘ, N′.Kₘ) is the last pair in N′
                    remove (N′.Pₘ, N′.Kₘ) from N′
                    insert (N′.Pₘ, N′.Kₘ) as the first pointer and value in N
                    replace K′ in parent(N) by N′.Kₘ
                end
            end
            else … symmetric to the then case …
        end
    end

Read it in this order. The node loses an entry. If it is the root with one child left, the root is discarded. Otherwise, if it is too empty, pick one sibling N′ (Silberschatz uses the previous sibling when there is one, else the next). If both fit in one node, merge them, which deletes K′ from the parent through a recursive call. If they do not fit, the sibling must be fuller than the minimum, so borrow one entry from it. Like insertion, deletion only walks up the search path, so it costs O(height).

Merge first, or borrow first?

Silberschatz checks the merge first: it merges whenever the two nodes fit together, and borrows only when they do not. Other textbooks (Ramakrishnan & Gehrke, many exam solutions) check the opposite order: borrow if either sibling can spare an entry, and merge only when neither can. Both produce valid B+ trees, and they often produce the same tree, but not always. The animator lets you pick the rule, and the worked answers below show both trees where they differ.

5. A note on B-trees

A B-tree (no plus) stores each key exactly once, in whichever node it lands, with its record pointer right there. There are no copies of keys in internal nodes and no leaf chain. Insertion is the same idea as for B+ trees, but every split, including a leaf split, moves the middle key up. Deleting a key from an internal node replaces it with its in-order predecessor (largest key in its left subtree) or successor (smallest key in its right subtree), then deletes that key from its leaf, which may underflow and be fixed by borrowing or merging, where a merge pulls the parent's key down between the two nodes. B-trees save a little space, but range scans are harder and internal nodes hold fewer keys (each key also carries a record pointer), so databases prefer B+ trees (Silberschatz §14.4.5).

Its sibling is [5, 11] (3 pointers); 3 + 1 = 4 pointers fit in one node, so merge the internal nodes, pulling the root's separator 19 down: [5, 11, 19]. BUET QBank · CSE 303 | L-3/T-1 | 2012–13 · 17 marks

Draw the B-tree to index the following elements: 2, 3, 5, 13, 17, 19, 23, 29, 31, 37, 41, 43, and 47. Delete elements 31 and 43 and redraw the tree.

Show worked answer

This asks for a B-tree (Section 5): every key appears once, and splits move the middle key up. No order is given, so assume order m = 3 (at most 3 children and 2 keys per node, at least 1 key in a non-root node), the smallest order that shows splits clearly. A node that reaches 3 keys splits into its left key and its right key and moves the middle key up.

  1. 2, 3 → [2, 3]. 5 → [2, 3, 5] splits: 3 goes up. Root [3] over [2] [5].
  2. 13 → [5, 13]. 17 → [5, 13, 17] splits, 13 up → root [3, 13] over [2] [5] [17].
  3. 19 → [17, 19]. 23 → splits, 19 up → root [3, 13, 19] splits, 13 up: root [13] over [3] and [19].
  4. 29 → [23, 29]. 31 → splits, 29 up → [19, 29]. 37 → [31, 37]. 41 → splits, 37 up → [19, 29, 37] splits, 29 up → root [13, 29] over [3] [19] [37].
  5. 43 → [41, 43]. 47 → splits, 43 up → [37, 43].

Delete 31. Leaf [31] becomes empty. Its only sibling under [37, 43] is [41], which has the minimum 1 key and cannot lend. Merge: empty leaf + separator 37 (pulled down) + [41] → [37, 41]. The parent becomes [43], which still has 1 key. Done.

Delete 43. 43 is in an internal node. Replace it with its in-order predecessor, the largest key in its left subtree, 41, and delete 41 from leaf [37, 41], which leaves [37] (1 key, fine).

The question bank's answer is correct for order 3. With a different assumed order the trees differ (for m = 4 the first tree is [31] over [5, 19] and [43]), so always state the order.

Summary: delete the key from its leaf. If a non-root node falls below its minimum (⌈(n−1)/2⌉ keys in a leaf, ⌈n/2⌉ pointers in an internal node), use a sibling under the same parent. If the two fit in one node, merge them and delete the separator from the parent (for internal nodes the separator comes down into the merged node); the parent may underflow in turn. Otherwise borrow one entry and fix the separator (for internal nodes, rotate through the parent). When the root is left with one child, that child becomes the root and the tree shrinks. Silberschatz merges first; many exam solutions borrow first. Both are valid if stated.
