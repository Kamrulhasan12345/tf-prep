Multilevel Indices

When an index is too big to keep in memory, searching it costs disk reads too. The fix is to index the index. This chapter explains why, builds a two-level index, and animates a lookup through it.

1. The problem: an index that does not fit in memory (slide 16)

So far we assumed the index sits in memory, so searching it is free and only the final record costs a block read. Real indices can be huge. Take a table with 1,000,000 records and a dense index with 100 entries per block: the index is 10,000 blocks, around 40 MB, and a database has many such indices competing for memory.

If the index does not fit in memory, access becomes expensive. Explain? The index then lives on disk like any other file, and searching it needs block reads. The best way to search a sorted file is binary search: read the middle block, decide whether the key is in the left or right half, and repeat on that half. Each step halves the search space, so it takes about log₂(b) block reads for b blocks:

log₂(10,000) ≈ 14 block reads, just to search the index

Each of those reads is a random access (5 to 10 ms each), so finding one record could take over 100 ms. And if the index also has overflow blocks (Chapter 7), binary search does not even work properly on them.

2. The solution: an index on the index

The slide's solution: treat the index kept on disk as an ordinary sequential file, sorted by key, and build a sparse index on it. Recall from Chapter 2 that a sparse index with one entry per block is tiny and works on any sorted file. The index file is sorted, so it qualifies.

Inner index
The original (basic) index file. It points to the data.
Outer index
A sparse index of the inner index: one entry per block of the inner index, holding that block's first key. It points to inner index blocks.

If even the outer index is too large to fit in memory, build yet another sparse index on top of it, and so on, until the top level fits in one block. Each level is about 100 times smaller than the one below it (one entry per block of ~100 entries), so very few levels are ever needed:

Top level1001

A lookup reads one block per level: 3 index reads plus 1 data read = 4, instead of 14 + 1 with binary search. Keeping the top level in memory saves one more. This idea, a tree of sparse indices where each level indexes the level below, is exactly what a B+ tree is (Chapter 8).

3. A two-level sparse index (slide 17)

Slide 17 draws a two-level index where the file is sorted on id and both levels are sparse. The figure below uses the complete instructor file with 3 records per data block, so every number can be checked. (The slide skips some blocks with “⋮”, so its inner index shows 83821 where ours has 76766.)

  • The inner index has one entry per data block: its first id (10101, 22222, 45565, 76766). It is stored in index blocks of 2 entries.
  • The outer index has one entry per inner index block: its first key (10101, 45565).

Every level uses the same rule as a single sparse index: find the largest entry ≤ K and follow it. Each step narrows the search from the whole file to one block of the level below.

The slide's last point: indices at all levels must be updated on insertion or deletion from the file. If a new data block is created, the inner index gains an entry; if that fills an inner index block and a new one is created, the outer index gains an entry. Chapter 5 works through those algorithms.

BUET QBank · CSE 303 | L-3/T-1 | 2016–17 · 6 marks

Is it possible to implement an unclustered-sparse indexing scheme? If so, give an example. Otherwise, briefly explain the reason.

Show worked answer

Directly on the data file: no. A sparse index finds key K by jumping to the largest entry ≤ K and scanning the file forward. That works only if the records between two entries are exactly the records whose keys lie between those entries, which is true only when the file is sorted on the key. In an unclustered (secondary) index the file is sorted on some other attribute, so the records after an entry have unrelated key values and the forward scan has no stopping point. Example: the instructor file is sorted on id; a sparse index on salary with entries 40000 and 80000 would send a search for 65000 to Mozart (40000), and the records after Mozart (Einstein 95000, El Said 60000, …) are in no salary order, so 65000 (Srinivasan, record 0) is never reached. So the lowest level of a secondary index must be dense.

As an upper level: yes, and slide 12 recommends it. The dense secondary index is itself a file sorted on the search key. A sparse index can therefore be built on top of it: “for unclustered index: sparse index on top of dense index (multilevel index)”. Example: a dense secondary index on salary (one entry per salary value, each pointing to a bucket) stored in index blocks of 4 entries, and an outer sparse index holding the first salary of each index block (40000, 72000, 90000). A search for 87000 reads the outer index (largest entry ≤ 87000 is 72000), then that one inner block, then the bucket and the records. The outer level is sparse and the index as a whole is unclustered.

Note: the question bank says this is “fundamentally impossible”. That is true only for a sparse index placed directly on the data; the multilevel form above is a standard unclustered index with a sparse level, as slide 12 states.

Summary: an index that does not fit in memory costs about log₂(b) block reads to search. A multilevel index fixes this by building a sparse index (outer) on the index file (inner), and repeating until the top level fits in memory. A lookup then reads one block per level.
