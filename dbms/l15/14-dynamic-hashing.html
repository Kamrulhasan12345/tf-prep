Dynamic Hashing: Extendible and Linear Hashing

A static hash file has a fixed number of buckets, so it degrades as the file grows. Extendible hashing and linear hashing let the number of buckets grow with the data. This chapter teaches both (Silberschatz §14.5 and Garcia-Molina §14.3.5–14.3.8), animates every insertion, gives you two interactive tools, and answers every hashing question from the question banks.

1. Why the bucket count must change

The previous chapter built a static hash file: a fixed set of B buckets and a hash function h that sends each search key to one of them. When the file grows past what B buckets can hold, every bucket grows an overflow chain and lookups get slower. Choosing a huge B up front wastes space, and rebuilding the whole file with a new hash function stops the database while it runs.

Dynamic hashing solves this by letting the number of buckets change one split at a time while the database keeps running. The trick in both methods below is the same: compute a long bit string h(K) once, and use only a few of its bits to choose a bucket. When the file grows, use one more bit. A bucket whose records agree on j bits can be split in two by looking at bit j + 1, without touching any other bucket.

Hash value as a bit string
The hash function produces a b-bit binary number (Silberschatz assumes b = 32; exam questions use 3, 4 or 16 bits). Example: with h(x) = x mod 7 the values are 0 to 6, so 3 bits suffice, and h(19) = 5 = 101.
Dynamic hashing
A hash organization whose number of buckets grows (and shrinks) gradually as records are inserted (and deleted). The two standard methods are extendible hashing and linear hashing.

2. Extendible hashing

2.1 The structure

An extendible hash table (Garcia-Molina calls it extensible) has two parts: a directory (also called the bucket address table) of 2i pointers, and the buckets themselves. To find the bucket for key K, take the first i bits of h(K), read them as a binary number, and follow that directory entry.

Global depth i
The number of hash bits the directory currently uses. The directory has exactly 2i entries.
Local depth ij
Stored in the header of bucket j (Garcia-Molina's "nub"): the number of bits that all records in that bucket are guaranteed to share. Always ij ≤ i.
Sharing rule
Exactly 2i − ij directory entries point to bucket j. A bucket with local depth 1 in a directory of depth 3 is shared by 22 = 4 entries.

Which bits? Silberschatz (§14.5.1) and Garcia-Molina (§14.3.5) both take the first (high-order, leftmost) i bits. With first bits, the 2i − ij entries that share a bucket sit next to each other in the directory. Many web tutorials and the CSE215 question-bank answers take the last (low-order) bits instead. The algorithm is identical with either choice; only the final picture differs, because different keys end up together. In an exam, state which bits you use in the first line of your answer. This book uses first bits unless a question only makes sense with last bits (Question 2 below explains such a case).

2.2 Lookup

Compute h(K), take its first i bits, follow that directory entry, and search the one bucket it points to. If the directory fits in memory, a lookup costs a single block read, however large the file grows. That is the main attraction of extendible hashing.

2.3 Insertion (the algorithm to learn)

To insert a record with key K, find its bucket j as for a lookup. If bucket j has room, put the record there and stop. If it is full, split it:

  1. If ij = i (only one directory entry points to the bucket): first double the directory. Increase i by 1. Each old entry w becomes two entries w0 and w1, both pointing to the bucket w pointed to. No bucket changes yet, and now ij < i, so continue with case 2.
  2. If ij < i (several entries share the bucket): split the bucket without touching the directory size. Create a new bucket, set both local depths to ij + 1, and move every record whose bit number ij + 1 is 1 into the new bucket. Re-point the half of the sharing entries whose bit ij + 1 is 1 to the new bucket.
  3. Retry the insertion. If all the old records and the new one had the same next bit, one half is still full, so the split repeats (possibly doubling again).

One exception: if every record in the full bucket has the same hash value as the new record, no number of extra bits can ever separate them. Then the new record goes into an overflow bucket chained to the full one. This happens with duplicate search keys (Question 6 below).

2.4 Deletion

Find the record and remove it. If its bucket becomes empty, the bucket can be removed: its directory entries are pointed at its buddy (the bucket whose first ij − 1 bits are the same), and that buddy's local depth drops by 1. Buckets may also be coalesced when two buddies together fit in one bucket. When no bucket has local depth equal to i any more, the directory can be halved. Real systems often skip halving, because files rarely shrink for long.

3. Linear hashing

Extendible hashing has three weaknesses (Garcia-Molina §14.3.7). Doubling a large directory is a lot of work at one moment. A doubled directory may stop fitting in memory. And with small buckets, a few unlucky keys that share a long prefix can force a huge directory while most buckets are nearly empty (you will see this in Question 2: six keys produce a 256-entry directory). Linear hashing has no directory at all and adds buckets one at a time, in a fixed order.

3.1 The structure (Garcia-Molina's version)

n
The current number of buckets, numbered 0 to n − 1. The buckets are stored in an array, so bucket m can be found directly.
i
The number of hash bits in use: i = ⌈log2 n⌉. Linear hashing always uses the last (low-order) i bits.
r
The current number of records. The policy keeps the ratio r/n below a fixed threshold. The textbook (and the exam questions) use r ≤ 1.7n with 2 records per block, so a bucket is about 85% full on average.
Overflow blocks
Allowed. A full bucket simply grows a chain; the chain disappears later when that bucket is split.

3.2 Where does a record go?

Let m be the last i bits of h(K), read as a number. If m < n, bucket m exists and the record belongs there. If m ≥ n, bucket m has not been created yet, so the record goes to bucket m − 2i−1: the bucket you get by changing the first of the i bits from 1 to 0. Lookups use exactly the same rule.

bucket(K) = m if m < n, otherwise m − 2i−1

3.3 Insertion

  1. Put the record in its bucket (in an overflow block if the bucket is full). Increase r.
  2. If now r > 1.7n, add one bucket. Its number is the old n, written in binary as 1a2…ai. Increase n; if n now exceeds 2i, increase i by 1 first (no data moves when i grows: the old bucket numbers just gain a leading 0).
  3. Split the bucket numbered 0a2…ai. Its records all end in a2…ai, so they differ only in bit i from the right. Those with a 1 there move to the new bucket.

Notice the surprise: the bucket that gets split is decided by n, not by where the insertion happened. A bucket with a long overflow chain may have to wait its turn. Over a full round every bucket gets split once, and then i grows by one.

3.4 The other version: split on overflow (Litwin)

Many courses and the CSE215 question-bank answers use Litwin's original rule instead of a load threshold. There is a split pointer s, starting at 0, and a level ℓ. With N0 = 2 starting buckets, hℓ(K) is the last ℓ + 1 bits of h(K).

  • Address: compute a = hℓ(K). If a < s, bucket a has already been split in this round, so use hℓ+1(K) (one more bit).
  • Split: whenever an insertion has to use an overflow block (anywhere), split bucket s with hℓ+1 into s and the new bucket s + 2ℓ+1, then increase s.
  • End of round: when s reaches 2ℓ+1, every bucket of the round has been split: set s = 0 and increase ℓ.

Both versions share the essential ideas (no directory, buckets split in a fixed linear order, overflow chains as a temporary buffer). They differ only in when a split happens, so they give different pictures for the same input. If a question states the 1.7n rule, use Garcia-Molina's version. If it says nothing, say which rule you use. The animator below does both.

Show worked answer

Hash values. x mod 7 is between 0 and 6, so 3 bits hold every hash value.

3-bit binary010011101000100011101010

Convention: the directory uses the first bits of the hash value, as in the textbooks. Keys are inserted in the given order into an initially empty structure (global depth 0, one bucket).

  1. 2, 3, 5 fill the single bucket.
  2. 7 finds it full with local depth 0 = global depth 0: double (i = 1), then split on the first bit. 2 (0..), 3 (0..) stay; 5 (1..) moves. 7 (000) joins bucket 0: [2, 3, 7].
  3. 11 (100) goes to bucket 1: [5, 11].
  4. 17 (011) finds bucket 0 full with local depth 1 = i: double (i = 2), split on bit 2: 7 (00) stays in bucket 00; 2 and 3 (01) move to bucket 01. 17 joins bucket 01: [2, 3, 17].
  5. 19 (101) follows entry 10 to the shared bucket [5, 11] (local depth 1): [5, 11, 19].
  6. 23 (010) finds bucket 01 full with local depth 2 = i: double (i = 3), split on bit 3: 2 (010) stays; 3 and 17 (011) move. 23 joins 2.

With last bits (the convention of the question-bank answer) the same algorithm gives global depth 2 and four buckets of local depth 2: 00 → [7, 11], 01 → [5, 19], 10 → [2, 23], 11 → [3, 17]. The steps: 7 causes the first split (keys ending 0: 2, 7; ending 1: 3, 5); 19 overflows [3, 5, 17] and forces the directory to depth 2 (3, 17 end in 11; 5, 19 end in 01); 23 overflows [2, 7, 11], which splits without doubling (7, 11 end in 00; 2, 23 end in 10).

Note: the question-bank answer is correct for the last-bits convention. Either convention earns the marks if you state it; the textbooks use first bits.

BUET QBank · CSE 303 | L-3/T-1 | 2012–13 · 13 marks

Discuss Linear Hashing and Extensible Hashing with examples. How do they differ from each other?

Show worked answer

Extensible hashing keeps a directory of 2i bucket pointers indexed by the first i bits of h(K) (global depth). Each bucket records its local depth j ≤ i, and 2i−j entries point to it. When an insertion finds its bucket full: if j < i, split the bucket on bit j + 1 and re-point half its entries; if j = i, first double the directory. Example: Figure 1 above (Garcia-Molina's example): with capacity 2, inserting 1010 into the bucket [1001, 1100] (local depth 1 = i) doubles the directory to i = 2 and splits it into [1001, 1010] (prefix 10) and [1100] (prefix 11).

Linear hashing has no directory. It keeps n buckets, uses the last i = ⌈log2 n⌉ bits, and sends a record to bucket m (the last i bits) or, if m ≥ n, to m − 2i−1. When the load r/n passes a threshold (1.7 records per bucket for 2-record blocks), it adds bucket n and splits the bucket whose number differs from it only in the leading bit. Overflow blocks are allowed. Example: Figure 3 above: inserting 0101 into a table with r = 3, n = 2 makes r = 4 > 3.4, so bucket 10 is added and bucket 00 is split (1010 moves).

Note: the question-bank answer says linear hashing splits whenever any bucket overflows. That is Litwin's variant; Garcia-Molina's version (the course textbook) splits when r/n exceeds the threshold. Both are linear hashing.

Summary: Dynamic hashing uses a growing number of bits of a fixed hash value. Extendible hashing keeps a directory of 2i pointers (global depth i) to buckets with local depths; a full bucket splits on its next bit, and the directory doubles only when the bucket's local depth equals i. Lookups read one bucket. Linear hashing has no directory: it uses the last i bits, sends m ≥ n to m − 2i−1, and adds one bucket at a time in a fixed order when r/n passes a threshold (Garcia-Molina) or on any overflow (Litwin), using overflow blocks in between. Always state which bits and which split rule you use.
