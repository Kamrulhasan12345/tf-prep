Indices on Multiple Keys

An index can be built on two or more attributes together. This chapter explains composite search keys, the dictionary-style ordering they use, and works the thana and district question.

1. Composite search keys

Every index so far had a single attribute as its search key. A composite search key is made of several attributes taken together. The slide's examples are an index on instructor with search key (name, ID), and one with search key (name, dept-name). Each index entry then holds a pair of values plus a pointer.

Lexicographic ordering

To keep composite keys sorted, they are compared lexicographically, which is the way a dictionary orders words: compare the first attribute; only if it is equal, compare the second; and so on. Formally, (a₁, a₂) < (b₁, b₂) if a₁ < b₁, or if a₁ = b₁ and a₂ < b₂. The slide's examples:

  • (John, 12121) < (John, 13514): the names are equal, so the IDs decide, and 12121 < 13514.
  • (John, 13514) < (Peter, 11223): the names already differ, John < Peter, so the IDs are never looked at, even though 13514 > 11223.

Which queries it helps

The slide says the (name, ID) index can serve queries on just name, or on (name, ID). Since entries are sorted by name first, all entries for one name sit together, so a query on name alone can use the index. A query on ID alone cannot: the IDs are only sorted within each name, so they are scattered across the whole index. This is the same as a phone book sorted by (surname, first name): easy to find everyone called “Rahman”, useless for finding everyone called “Karim” as a first name.

2. Example: a composite index on (name, dept-name)

SELECT * FROM instructor
WHERE name = 'Gold' AND dept-name = 'Physics';

Slide 23 lists the (name, dept-name) pairs in the order of the file (Srinivasan, Wu, Mozart, …). An ordered index stores them sorted lexicographically, so the animation below shows the sorted version: Brandt first, Wu last.

Because both conditions are part of the key, the index lands on exactly the matching entry, and only that record is fetched. With a separate single-attribute index on name, the database would fetch every instructor called Gold and then check each one's department.

Question (worked answer): thanas and districts

There are 460 thanas and 64 districts. (a) Find the number of search keys of the (thana, district) composite index and of a simple thana index. Query: SELECT * FROM person WHERE thana = 'Sadar' AND district = 'Sylhet'. (b) Compare query performance using the composite index and the simple index.

The key fact: thana names are not unique across the country. The clearest example is “Sadar”: almost every district has a thana called Sadar (Sylhet Sadar, Cumilla Sadar, Bogura Sadar, and so on). A thana is identified uniquely only by its name together with its district.

(a) Number of search keys.

  • Composite (thana, district) index: one search key for each distinct (thana, district) pair that actually occurs. Every thana belongs to exactly one district, so there are 460 search keys. (Not 460 × 64 = 29,440: most combinations, such as a Sylhet thana paired with Khulna district, never occur.)
  • Simple thana index: one search key per distinct thana name, which is fewer than 460, because repeated names share a key. If, say, 64 thanas are all called “Sadar”, they collapse into one key, giving at most 460 − 63 = 397 search keys.

(b) Query performance.

  • With the simple thana index: look up “Sadar”. Its bucket points to every person living in any Sadar thana, roughly 64 thanas' worth of people. The database must fetch all of those records (each one possibly a separate block read, Chapter 3) and then discard every one whose district is not Sylhet. About 63/64 of the work is wasted.
  • With the composite index: look up (Sadar, Sylhet) directly. Its bucket points only to people in Sylhet Sadar, so every fetched record is part of the answer. Roughly 64 times fewer record fetches.

The composite index is clearly better for this query. The price is the usual one: a bigger index (460 keys instead of fewer, and each key holds two values), and one more index to update on every insert and delete.

Practice

Key terms

Quick check

Summary: a composite search key combines several attributes and is sorted lexicographically: first attribute first, later ones only to break ties. It serves queries on the whole key or on a leading part of it, but not on a later attribute alone. When a query constrains all the key's attributes, a composite index fetches only matching records, while a single-attribute index fetches extra records that must be filtered out.
