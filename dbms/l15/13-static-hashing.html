Static Hashing

Slide 5 named the second basic kind of index, the hash index, and then the lecture moved on to B+ trees. Exams ask about hashing anyway. This chapter explains hash file organization and hash indices (Silberschatz §14.5, Garcia-Molina §14.3.1–14.3.4), what makes a hash function good, why buckets overflow and how overflows are handled, and why a fixed number of buckets eventually fails.

1. Hashing instead of searching

Every index so far kept search keys in sorted order and found a key by searching: binary search in a sorted index, or a walk down a B+ tree. Hashing skips the search. A function computes, straight from the key, where the record lives.

Bucket
A unit of storage that holds one or more records. Usually one disk block, possibly with more blocks chained to it.
Hash function h
A function from the set K of all search-key values to the set B of bucket addresses, h: K → {0, 1, …, nB − 1}.
Hash file organization
The records themselves are stored in the buckets: record with key K lives in bucket h(K).
Hash index
An index whose entries (search key, record pointer) are stored in buckets by hashing the search key. The records themselves can be stored in any order.
Static hashing
Hashing with a fixed number of buckets nB, chosen when the file is created.

The three operations are short:

  • Insert a record with key K: compute h(K) and store the record in that bucket (if there is space).
  • Look up key K: compute h(K) and search that one bucket. The search must compare the keys of the records in the bucket, because two different keys can hash to the same bucket (a collision).
  • Delete: look the record up and remove it from its bucket.

Here is a hash index on the ID of the instructor relation with 8 buckets, 2 entries per bucket, and h(ID) = ID mod 8. Each entry is (ID, pointer to the instructor record); the pointers are left out of the drawing.

Silberschatz makes one more remark worth knowing for short questions: a hash index is only ever useful as a secondary index. If the file itself is organized by hashing on that key, the file already is the hash structure, and a separate hash index adds nothing. The term hash index is therefore used both for separate secondary hash structures and for hash-organized files.

2. What makes a hash function good

The worst possible hash function sends every key to the same bucket; a lookup then has to scan everything. The ideal one spreads the keys out so that each bucket gets about the same number of records. Silberschatz names two properties:

Uniform
Each bucket is assigned the same number of search-key values from the set of all possible values.
Random
Each bucket gets about the same number of values from the keys that actually occur, whatever their pattern. The hash value should not be correlated with any visible ordering of the keys, such as alphabetical order or the length of the name.

Two bad examples from the textbook make the difference clear. Hashing instructor names into 26 buckets by first letter is simple, but not uniform in practice: far more names start with B or R than with Q or X. Hashing salaries into buckets of 10,000-wide ranges (0–9,999, 10,000–19,999, …) is uniform over all possible salaries, but not random: real salaries cluster in a few middle ranges.

Typical hash functions do arithmetic on the binary representation of the key:

  • Division: h(K) = K mod nB. Choose nB prime, or at least not a power of 2: K mod 8 keeps only the last 3 bits of K, so any pattern in those bits (many IDs ending in odd digits, say) goes straight into the bucket numbers. That is what happened in Figure 1.
  • Strings: treat the characters as numbers and combine them, for example Java's s[0]·31n−1 + s[1]·31n−2 + … + s[n−1], then take the result mod nB. Every character influences the bucket.
  • Multiplication: h(K) = ⌊nB · frac(K · A)⌋ for a constant 0 < A < 1 (Knuth suggests A ≈ 0.618). Here a power-of-2 nB is fine.

Whatever the formula, a practical check is to hash a sample of the real keys and look at the bucket counts.

3. Bucket overflow

A bucket overflow happens when a record hashes to a bucket that has no space left. There are two causes:

  1. Insufficient buckets. The number of buckets must satisfy nB > nr / fr, where nr is the number of records and fr is the number of records per bucket. If the file grows past what was planned, overflow is unavoidable.
  2. Skew. Some buckets receive more records than others, either because many records have the same search key (duplicates always hash together) or because the hash function distributes the actual keys unevenly.

To leave room for skew, Silberschatz suggests allocating extra buckets with a fudge factor d, typically about 0.2:

nB = (nr / fr) × (1 + d)

Example: 10,000 records, 20 per block, d = 0.2 gives 500 × 1.2 = 600 buckets. About 20% of the space is deliberately empty; that is the price of fewer overflows.

3.1 Overflow chaining (closed addressing)

Even with a fudge factor, some bucket will overflow eventually. The standard solution in databases is overflow chaining: when bucket b is full, allocate an overflow bucket and link it to b; when that is full, link another, forming a chain. A lookup reads the primary bucket and then every block in its chain. Silberschatz calls this closed addressing (some books say closed hashing), because a record always stays in the bucket h(K) chose for it.

3.2 Open addressing

The alternative keeps the set of buckets fixed and allows no chains. When h(K) is full, the record goes into some other bucket chosen by a probe rule. With linear probing that is the next bucket with space: (h(K) + 1) mod nB, then + 2, and so on. In Figure 2, key 18 would go to bucket 3 (which has one free slot) instead of an overflow block. Silberschatz calls this open addressing (or open hashing). Be careful: in data-structures courses "open hashing" usually means chaining. State the mechanism, not just the name.

Open addressing is used in compilers and assemblers, but databases avoid it. Lookups of a missing key must keep probing until an empty slot proves the key absent, deletion is awkward (a removed record can break other records' probe sequences), and each probe may be another random disk read.

4. Cost, and why static hashing is not enough

With a good hash function and no overflow, a lookup reads exactly one block, independent of the file size: better than the 3 or 4 levels of a B+ tree. An insertion or deletion is one read and one write. Overflow chains add one read per chain block.

Hashing has two weaknesses compared with B+ trees:

  • No range queries. A good hash function scatters neighbouring keys on purpose, so WHERE salary BETWEEN 60000 AND 80000 cannot use a hash index: it would have to try every possible value or scan every bucket. B+ trees keep keys in order and answer ranges directly.
  • A fixed nB fits only one size of file. Size the buckets for today's file and the chains grow as the file grows, so performance degrades. Size them for the future and space is wasted now. Rebuilding with a new nB and a new hash function means rehashing every record, which is expensive and blocks access while it runs.

The second problem is solved by dynamic hashing, which changes the number of buckets gradually: extendible hashing and linear hashing, the topic of the next chapter.

BUET QBank · CSE 303 | L-3/T-1 | 2016–17 · 6 marks

What is the key property of a good hash function? How can you choose such a function?

Show worked answer

Key property: the hash function must distribute the search keys evenly over the buckets, so that every bucket receives about the same number of records and a lookup reads about one block. Silberschatz splits this into two properties:

  • Uniform: each bucket is assigned the same number of values from the set of all possible search-key values.
  • Random: in the average case each bucket gets the same number of the keys that actually occur, regardless of how those keys are distributed. The bucket number should not depend on any visible order of the keys.

It must also be deterministic (the same key always gives the same bucket) and cheap to compute.

Choosing one:

  1. Use all of the key. Hashing names by their first letter is uniform over the alphabet but not random over real names (many B and R names, few Q and X). Hashing salaries by 10,000-wide range is uniform but not random (salaries cluster in a few ranges).
  2. For integer keys, use the division method h(K) = K mod nB with nB a prime not close to a power of 2. With nB = 8 the bucket is just the last 3 bits of K, and any pattern in those bits shows up as skew (Figure 1: twelve instructor IDs leave three of eight buckets empty).
  3. For strings, combine every character's code, for example s[0]·31n−1 + … + s[n−1], mod nB; or use the multiplication method ⌊nB · frac(K·A)⌋ with A ≈ 0.618, which also works when nB is a power of 2.
  4. Test it: hash a sample of the real keys and check that the bucket counts are close to equal.

The question-bank answer is correct; its mention of cryptographic hashes (SHA-256 and similar) is fine but unnecessary for a DBMS, where speed matters more than unpredictability.

BUET QBank · CSE 303 | L-3/T-1 | 2010–11 · 10 marks

Describe static hash file organization with an example. How can bucket overflows be handled?

Show worked answer

Static hash file organization. The file is divided into a fixed number nB of buckets (each one or more disk blocks), chosen when the file is created. A hash function h maps every search-key value to a bucket number 0 … nB − 1. A record with key K is stored in bucket h(K); to find it, compute h(K) and search only that bucket. Different keys can collide in the same bucket, so the search compares keys inside the bucket. A lookup costs one block read when there is no overflow.

Example. nB = 4 buckets of 2 records, h(K) = K mod 4. Insert 40, 21, 33, 10, 14, 15: h = 0, 1, 1, 2, 2, 3, giving bucket 0 = [40], 1 = [21, 33], 2 = [10, 14], 3 = [15]. Inserting 18 (h = 2) finds bucket 2 full: a bucket overflow (Figure 2 animates all of this).

Why overflows happen: too few buckets for the number of records (nB ≤ nr/fr), or skew (duplicate keys, or a hash function that spreads the actual keys unevenly). Allocating nB = (nr/fr)(1 + d) buckets with fudge factor d ≈ 0.2 reduces overflows but cannot rule them out.

Handling overflows:

  1. Overflow chaining (closed addressing): link an overflow bucket to the full bucket and put the record there; further overflows extend the chain. Key 18 goes to an overflow block chained to bucket 2. A lookup in bucket 2 now reads 2 blocks. This is what database systems use.
  2. Open addressing (linear probing): put the record in the next bucket with space, (h(K) + 1) mod nB, … ; key 18 would go to bucket 3. No chains, but lookups and deletions get complicated and may read many buckets, so databases avoid it.
  3. Change the structure: when chains get long, rebuild with more buckets and a new hash function, or use dynamic hashing (extendible or linear hashing), which adds buckets gradually.

The question-bank answer is correct; its quadratic probing and double hashing are further open-addressing variants.

Summary: A hash function maps each search key to one of nB buckets, so a lookup reads one bucket instead of searching. A good hash function is uniform and random; use all of the key and a prime number of buckets for the division method. Buckets overflow because there are too few of them or because of skew; databases handle this with overflow chains (closed addressing) rather than open addressing. Hashing cannot answer range queries, and a fixed number of buckets degrades as the file grows, which motivates dynamic hashing.
