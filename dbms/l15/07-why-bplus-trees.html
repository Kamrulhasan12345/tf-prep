Why B+ Trees

The indices in Chapters 2–6 work well on a file that does not change. On a file that keeps growing, they slowly fall apart. This chapter shows how (with an animation of overflow blocks piling up), and what a B+ tree does differently.

1. Indexed-sequential files and their weakness (slide 24)

An indexed-sequential file is what Chapters 2–5 built: a data file kept sorted on a key, plus a (possibly multilevel) index on that key. Lookups are fast as long as the file stays in sorted order, block after block.

The slide names the disadvantage: performance degrades as the file grows, since many overflow blocks get created. And: periodic reorganization of the entire file is required.

How do overflow blocks get created?

Records must stay in key order. When a new record belongs inside a block that is already full, there are two options. Splitting the block and shifting all later blocks along would mean rewriting much of the file. So instead, the system attaches an overflow block to the full block: an extra block, stored wherever there is free space on disk, linked from the full block by a pointer. The new record goes there. Three things went wrong, and they get worse the more the file grows:

  1. Lookups get slower. The index only knows about the main blocks. To find a key in the overflow range, the system reads the main block and then follows the chain, one block read per overflow block, each one possibly a random seek.
  2. Sequential scans get slower. The file is no longer physically in order. Reading it “in order” means jumping out to overflow blocks and back.
  3. The only cure is a full reorganization: rewrite the entire file in order without overflow blocks, and rebuild the index. On a big table that takes a long time, and the table may be unavailable meanwhile.

2. The B+ tree answer (slide 25)

A B+ tree is a multilevel index (Chapter 4) designed so that it never needs a full reorganization. Its advantages, from the slide:

  • It automatically reorganizes itself with small, local changes when records are inserted and deleted. When a node is full, it splits into two half-full nodes and adds one entry to its parent. When a node becomes too empty, it borrows from or merges with a neighbour. Only a few nodes on one root-to-leaf path change.
  • Reorganization of the entire file is not required to maintain performance. There are no overflow chains, so lookup cost stays the same however many inserts happen.

And its (minor) disadvantages:

  • Extra insertion and deletion overhead: occasionally an insert or delete has to split or merge nodes, which costs a few extra block writes.
  • Space overhead: nodes are kept between half full and full, so up to half of each node can be empty space.

The slide's conclusion: the advantages of B+ trees outweigh the disadvantages, and B+ trees are used extensively. In practice, almost every relational database (PostgreSQL, MySQL, Oracle, SQL Server, SQLite) uses a B+ tree as its default index.

Summary: indexed-sequential files degrade as they grow, because inserts into full blocks create overflow chains that slow lookups and scans, until the whole file is reorganized. A B+ tree keeps itself balanced with small local splits and merges, so it never needs reorganizing. It costs a little extra on updates and some empty space, which is well worth it.
