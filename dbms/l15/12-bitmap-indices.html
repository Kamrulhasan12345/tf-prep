Bitmap Indices

A bitmap index stores one string of bits per attribute value instead of lists of record pointers. It is tiny for attributes with few distinct values, and it answers queries with several conditions by plain AND, OR and NOT on bits. This chapter follows Silberschatz §14.9, shows the bitmap index scan that rescues secondary indices, compares bitmaps with B+ trees and hashing, and answers every bitmap question in the banks.

1. One bitmap per value

A bitmap index needs the records of the relation to be numbered sequentially, 0, 1, 2, …, and it needs a quick way to fetch record number i. With fixed-size records that is easy: record i sits at a computable block and offset (Lec 14, Chapter 2).

Bitmap
An array of bits, one bit per record of the relation.
Bitmap index on attribute A
One bitmap for each value v that A takes. Bit i of the bitmap for v is 1 if record i has A = v, and 0 otherwise.
Cardinality of an attribute
The number of distinct values it takes. Gender or status has low cardinality; ID or NID has high cardinality (one value per record).

Silberschatz's example is a relation instructor_info(ID, gender, income_level) with five records. The bitmap index on gender has two bitmaps; the one on income_level has five (L1 to L5), one per income band.

A single-value selection such as gender = 'f' is answered by scanning the bitmap for f and fetching the records whose bit is 1. On its own that is no better than any other index. Bitmaps shine when a query has several conditions.

2. Operations on bitmaps

2.1 AND, OR, NOT

Take SELECT * FROM instructor_info WHERE gender = 'f' AND income_level = 'L2'. Fetch the bitmap for f (01101) and the bitmap for L2 (01000), and AND them bit by bit: 01101 ∧ 01000 = 01000. Only record 1 satisfies both conditions, and we found that out without reading a single record.

  • Intersection (conditions joined by AND) is the bitwise AND of the bitmaps.
  • Union (OR) is the bitwise OR.
  • Complement (NOT) flips every bit. The bitmap for NOT gender = 'm' is NOT 10010 = 01101.

These operations are very fast: a computer ANDs 32 or 64 bits in one instruction, so a relation with 1 million records needs only 1,000,000 / 64 = 15,625 instructions per AND. The bitmaps for a million records are 125 KB each, small enough to read and combine in memory.

2.2 The existence bitmap

Complement has a trap. If record i has been deleted, its bit is 0 in every value's bitmap, so NOT turns it into a 1 and the query would return a record that does not exist. The same happens with null values. The fix is an existence bitmap: bit i is 1 if record i exists. NOT B is computed as (NOT B) AND existence. For nulls, the result is also ANDed with the complement of the bitmap for null.

2.3 Counting

Some queries only need a count: SELECT COUNT(*) … WHERE gender = 'f' AND income_level = 'L2'. Count the 1 bits of the result bitmap and stop. No record is read at all. Silberschatz notes a cheap way to count: a 256-entry table gives the number of 1s in each possible byte, so the count is one table lookup per byte.

3. Size, and when bitmaps are the right choice

A bitmap has one bit per record. If records are 100 bytes (800 bits) long, one bitmap is 1/800 of the relation's size. An attribute with 8 values needs 8 bitmaps, together only 1% of the relation. Compare a B+ tree or a list of record pointers, which needs a 4- to 8-byte pointer (32 to 64 bits) for every record.

The picture reverses for high-cardinality attributes. A bitmap index on ID would have one bitmap per record, each with a single 1 among a million 0s. Silberschatz's rule of thumb: for a value that occurs in more than 1/64 of the records, a bitmap (1 bit per record) is smaller than a list of 64-bit record identifiers; for rarer values a list is smaller. Some systems combine the two inside a B+ tree: leaf entries for frequent values hold a bitmap, entries for rare values hold a list.

Updates are the other cost. Inserting a record appends a bit to every bitmap of the attribute; changing a value flips bits in two bitmaps. That is cheap for one record, but bitmaps are usually stored compressed and are shared by many records, so frequent concurrent updates to them are slow.

So bitmap indices are preferred when:

  1. the attribute has few distinct values (gender, status, region, income band, rating);
  2. queries combine several conditions on such attributes, or only need counts;
  3. the data is read-mostly, as in data warehouses and decision-support systems, where data is loaded in batches.

4. Bitmap index scan: making a secondary index safe for big results

The same bit idea fixes a real weakness of ordinary secondary indices. Recall from Chapter 3 that a secondary index lists matching records in key order, and those records are scattered over the file. A plain secondary index scan follows each pointer immediately: one random block read per matching record. If 2 matching records sit in the same block, that block may be read twice, because by the time the second pointer comes along the block may have left the buffer.

A bitmap index scan (the name PostgreSQL uses; Silberschatz describes it in the query-processing chapter) works in two phases:

  1. Build: scan the index and, instead of fetching records, set a bit in an in-memory bitmap for every block (or record) that contains a match. Several conditions can each build a bitmap and be ANDed or ORed here.
  2. Fetch (the "bitmap heap scan"): go through the bitmap in order and read each block whose bit is 1. Every needed block is read exactly once, in physical order, in one sweep of the disk arm.

Why this matters, with numbers (Silberschatz's disk parameters: seek tS = 4 ms, block transfer tT = 0.1 ms). A relation has 1,000,000 records in 10,000 blocks. A query matches 20,000 records (2%) through a secondary index of height 3.

  • Linear scan: one seek, then 10,000 sequential transfers: 4 + 10,000 × 0.1 = 1,004 ms.
  • Plain secondary index scan: 3 index blocks plus one random block access per match: (3 + 20,000) × 4.1 ms ≈ 82,012 ms, 82 times slower than the linear scan. The two costs are equal at only about 242 matching records (0.024% of the relation).
  • Bitmap index scan: 20,000 matches scattered at random hit about 10,000 × (1 − (1 − 1/10,000)20,000) ≈ 8,647 distinct blocks. They are read once each in disk order in one sweep, so the cost is close to a linear scan (≈ 1 s) instead of 82 s. When only a handful of records match, it reads only those few blocks, like an index scan.

So the bitmap index scan is never much worse than the better of the two plain strategies, which is why optimizers use it when they cannot predict the result size well.

DB QB · 21-22 7a · 15 marks  /  BUET QBank · CSE 215 | L-2/T-2 | 2021–22 · 15 marks

"Without bitmap index scan strategy, secondary index scan can sometimes perform worse than linear file scan." Justify or criticize this statement with proper explanation.

Show worked answer

The statement is correct.

Why a secondary index scan can lose. A secondary index is ordered on a key different from the file's order, so consecutive index entries point to records in unrelated blocks. A plain secondary index scan fetches the record for each pointer as it meets it: one random block access (a seek plus a transfer) per matching record, and the same block may be fetched several times if it holds several matches. A linear scan reads every block exactly once, sequentially, with essentially one seek. When many records match, the random accesses cost far more than the sequential reads.

Numbers. 1,000,000 records in 10,000 blocks, tS = 4 ms, tT = 0.1 ms, index height 3, and a condition matching 20,000 records (2%):

  • Linear scan: tS + 10,000 tT = 4 + 1,000 = 1,004 ms.
  • Secondary index scan: (3 + 20,000)(tS + tT) = 20,003 × 4.1 ≈ 82,012 ms, about 82 times slower.
  • Break-even: (3 + N) × 4.1 = 1,004 gives N ≈ 242 matching records. Above roughly 0.024% of the relation, the index scan already loses.

When only a few records match (say 10: 13 × 4.1 ≈ 53 ms) the index scan wins easily. That is why the statement says "sometimes": it depends on how many records match, which the optimizer can only estimate.

What the bitmap index scan changes. It first scans the index and only sets bits in an in-memory bitmap with one bit per block (or per record). Then it reads the blocks whose bit is 1 in physical order. Each needed block is read once, in one sweep of the disk arm. In the example the 20,000 matches fall in about 8,647 distinct blocks, read in order: close to the 1 s linear scan instead of 82 s. With 10 matches it reads at most 10 blocks, as cheaply as the plain index scan. So the bitmap strategy never does much worse than the better of the two, and several index conditions can be ANDed or ORed in the bitmap before any block is read (Figure 3 animates the difference).

The question-bank answer reaches the same conclusion; its "5% to 15%" threshold is a rule of thumb for real systems with caching, while the pure cost model above puts the break-even much lower.

DB QB · 17-18 2c · 5 marks  /  BUET QBank · CSE 215 | L-2/T-2 | 2017–18 · 5 marks  /  BUET QBank · CSE 303 | L-3/T-1 | 2012–13 · 5 marks

Give an example where the Bit-map index is preferred over other indexing techniques.

Show worked answer

Example. A national census or bank data warehouse holds a relation person(NID, name, gender, division, income_level, …) with 10 million rows. Gender has 2 values, division 8, income_level 5. Analysts run queries like

SELECT COUNT(*) FROM person
WHERE gender = 'f' AND division = 'Sylhet' AND income_level = 'L2';

With bitmap indices on the three attributes, the system reads three bitmaps of 10,000,000 bits (1.25 MB each), ANDs them (about 156,000 64-bit operations per AND) and counts the 1 bits. No record is read at all. On a small sample with gender bitmap f = 01101 and income bitmap L2 = 01000 (Figure 1), f AND L2 = 01000: one matching record.

Why other indices are worse here.

  • A B+ tree on gender returns about 5 million record pointers for 'f' (40 MB of 64-bit pointers), and intersecting three such lists is slow. All three bitmaps together cost 2 + 8 + 5 = 15 bitmaps × 1.25 MB, smaller than one such pointer list.
  • A hash index helps only one equality condition at a time and cannot combine conditions cheaply.
  • The data is loaded in batches and rarely updated, so the update cost of bitmaps does not matter.

Bitmaps would be a poor choice for NID (10 million distinct values) or for a heavily updated OLTP table.

BUET QBank · CSE 303 | L-3/T-1 | 2015–16 · 5 marks

Write a short note on bitmap indexing.

Show worked answer

A bitmap index on attribute A of relation r keeps, for every distinct value v of A, a bitmap with one bit per record: bit i is 1 if record i has A = v. Records must be numbered sequentially and record i must be fetchable quickly (for example with fixed-size records). Example: instructor_info with genders m, f, f, m, f has bitmaps m = 10010 and f = 01101.

Query processing. Conjunctions are answered by AND of bitmaps, disjunctions by OR, negations by NOT ANDed with an existence bitmap (so deleted records and nulls are not returned). Counting the 1s of the result answers COUNT queries without reading records. Bitwise operations handle 64 records per instruction.

Space. One bit per record per value: for 100-byte records a bitmap is 1/800 of the relation's size, far smaller than a pointer per record when the attribute has few values. For a value that occurs in fewer than about 1/64 of the records, a list of record identifiers is smaller, so some systems store bitmaps inside B+ tree leaves only for frequent values.

Use. Best for low-cardinality attributes in read-mostly data warehouses with multi-condition and counting queries. Poor for high-cardinality keys and for frequently updated OLTP data. The bitmap idea also powers the bitmap index scan, which makes secondary-index lookups read each block once in physical order.

BUET QBank · CSE 303 | L-3/T-1 | 2013–14 · 6 marks

Compare Hash-based index, B+ -tree index, and Bitmap index.

Show worked answer

The table in Section 5 is the answer. In short:

  • Hash index: computes the bucket from the key, so an equality lookup costs about one block. No range queries, no ordered output. Static hashing degrades as the file grows; dynamic hashing (extendible, linear) fixes that.
  • B+ tree: keeps keys sorted in a balanced tree; equality lookups cost the tree height (3 to 4 block reads for millions of keys), range queries follow the leaf chain. Updates are local splits and merges. The general-purpose default.
  • Bitmap: one bit per record per value. Tiny for low-cardinality attributes, and multi-condition and COUNT queries become bitwise AND/OR/NOT on bitmaps. Bad for high-cardinality attributes and frequent updates; used in data warehouses.

Note: the question-bank answer lists bitmap operations as "O(1)". They are linear in the number of records (n/64 machine words per operation); they are fast because that constant is tiny, not because they are constant time.

Summary: A bitmap index keeps one bitmap per attribute value, one bit per record. Multi-condition queries become bitwise AND, OR and NOT (with an existence bitmap), and counts need no record reads. Bitmaps are tiny for low-cardinality attributes and suit read-mostly warehouses; they are poor for high-cardinality or frequently updated attributes. A bitmap index scan collects matches from an ordinary index into a bitmap and then reads each needed block once in physical order, so a secondary index never becomes far worse than a linear scan. Hash indices are best for equality, B+ trees for equality and ranges, bitmaps for combinations of low-cardinality conditions.
