RAID and Disk Striping

Why databases use many disks at once, and the two ways of spreading data over them: bit-level and block-level striping. Answers the slides' “Find i-th byte?” question and the discussion of points 1 and 2.

1. RAID (slide 12)

Chapter 3 showed that one magnetic disk manages only 50–200 random reads per second, and that one disk failure loses everything on it. The answer to both problems is to use many disks together.

RAID: Redundant Arrays of Independent Disks
Disk organisation techniques that manage a large number of disks while giving the rest of the system the logical view of a single disk that has
  • high capacity and high speed, by using multiple disks in parallel, and
  • high reliability, by storing data redundantly, so that data can be recovered even if a disk fails.
Array
A group of disks that the computer treats as one big disk.
Redundant
Storing extra information (copies or parity) that is not strictly needed, so that lost data can be rebuilt from what remains.

This chapter covers the speed half: striping. Chapters 6–8 add the redundancy half.

2. Goals of parallelism (slide 13)

If one disk is slow, use eight of them at the same time. A supermarket with eight checkout lanes serves customers faster than one lane, but only if the customers spread out across the lanes. So the question is how to spread a table's data across the disks. The slide lists what parallelism should achieve:

Throughput: load-balance multiple small accesses
Throughput is how many requests the system finishes per second. Load balancing means spreading the requests evenly so no disk is overloaded while others sit idle. Many small independent lookups should go to different disks and run at the same time.
Response time: parallelise large accesses
Response time is how long one request takes from start to finish. One big request, split among 8 disks, finishes roughly 8 times sooner.
Transfer rate: stripe data across multiple disks
With 8 disks streaming at once, the combined data-transfer rate is about 8 times that of one disk.

The technique is striping: cut the data into pieces and deal the pieces out across the disks, like dealing cards around a table. The pieces lined up across all disks at the same position form a stripe. Slide 13 cuts the data into bits; slide 14 cuts it into blocks.

3. Bit-level striping (slide 13)

Bit-level striping
Split the bits of each byte across multiple disks. In an array of eight disks, write bit i of each byte to disk i.

The slide's student relation starts with the bytes 10101111, 00000000, 11111111, … Watch the first two bytes being stored.

No single disk holds a whole byte. Each disk holds one “column” of bits: disk 0 has the first bit of every byte, disk 1 the second bit, and so on.

Good: reading everything (sequential access)

SELECT * FROM student; reads the whole relation in order. All eight disks stream together, and in the time one disk delivers one bit, the eight deliver a whole byte. This is the slide's “each access can read data at eight times the rate of a single disk (sequential access)”.

Bad: finding one thing

SELECT * FROM student WHERE id = 05050; wants one record, a few bytes in the middle of the relation. Every one of those bytes is split across all 8 disks.

Slide 13: “Find i-th byte?” (worked answer)

Byte i of the relation is stored as bit position i on each of the eight disks: its first bit is the i-th bit on disk 0, its second bit the i-th bit on disk 1, and so on. To read that one byte, all eight disks must seek to position i and rotate it under their heads, and the byte is complete only when the slowest of the eight has delivered its bit. So:

  • the access time is the worst of eight seeks and eight rotational latencies, which on average is longer than one disk's access time; and
  • all eight disks are busy serving this one tiny request, so no other request can run meanwhile.

This is the slide's “seek/access time worse than for a single disk”. Since databases mostly do many small lookups, bit-level striping is not used much any more.

4. Block-level striping (slide 14)

Block-level striping
With n disks, block i of a file goes to disk (i mod n) + 1.
mod
The remainder after division: 10 mod 8 = 2, because 10 = 1 × 8 + 2. Like a clock, block numbers wrap around every n blocks.

The “+ 1” is there only because that formula numbers the disks 1 to n. The slide's pictures number the disks 0 to 7, so with them the rule is simply block i → disk i mod n. This book uses 0-based disk numbers, as the slides' figures do.

BlockCalculation (n = 8)Disk

The key difference from bit-level striping: each block sits whole on one disk, so any record inside a block can be read from a single disk with a single seek.

Discussion (slide 14): explain points 1 and 2 of block-level striping

Point 1: “Requests for different blocks can run in parallel if the blocks reside on different disks.” Suppose Alice runs SELECT * FROM student WHERE id >= 05005 and her rows are in block B3, while at the same moment Bob needs a row in B10. B3 is on disk 3 and B10 on disk 10 mod 8 = 2. Different disks, so both arms seek at the same time and both requests finish in about one access time. Neither waits for the other, and the other six disks remain free for more users. With bit-level striping, Alice's request alone would have occupied all eight disks. This is the throughput goal: small accesses are load-balanced across the disks.

Point 2: “A request for a long sequence of blocks can utilize all disks in parallel.” SELECT * FROM student needs every block, B0 to B13. Consecutive blocks were dealt to different disks, so B0–B7 are read at the same moment by disks 0–7, and in the next round disks 0–5 read B8–B13. The relation arrives in 2 rounds instead of 14. This is the response time goal, and it gives the same benefit for big scans that bit-level striping gave.

The textbook (§13.3.3, Example 13.5) puts numbers on point 2: striping a 1024-block relation over four Megatron 747 disks cuts the time to read it from about 139 ms to about 40 ms per disk, a speed-up of about three (not four, because the request must wait for the slowest of the four seeks).

BUET QBank · CSE 303 | L-3/T-1 | 2010–11 · 5 marks

Explain block level striping with an example of storing 1, 2, …, n logical blocks into a disk subsystem consisting of 8 disks.

Show worked answer

Block-level striping divides a file into blocks and deals consecutive blocks round-robin over the disks, so each block is stored whole on one disk and consecutive blocks are on different disks. With 8 disks numbered 1 to 8 and blocks numbered from 1, block i goes to disk ((i − 1) mod 8) + 1. (With blocks numbered from 0, as on slide 14, block i goes to disk (i mod 8) + 1.)

…block n is on disk ((n − 1) mod 8) + 1, in stripe ⌈n/8⌉

For example, block 21 goes to disk (20 mod 8) + 1 = 5, in stripe 3.

Benefits. (1) Requests for different blocks on different disks run in parallel, so many small requests are load-balanced and throughput rises. (2) A long sequential read uses all 8 disks at once, e.g. blocks 1–8 are read in one round, so the transfer rate is about 8 times that of one disk and response time drops. Unlike bit-level striping, a single-block lookup still needs only one disk and one seek.

Limitation. Striping alone (RAID 0) has no redundancy: if any of the 8 disks fails, every stripe loses a block.

Summary: RAID makes many disks look like one disk that is large, fast (parallel) and reliable (redundant). Striping spreads data over the disks. Bit-level striping puts bit i of every byte on disk i: 8× transfer rate for scans, but every lookup occupies all disks and waits for the slowest seek, so it is rarely used. Block-level striping puts block i on disk i mod n: big scans use all disks in parallel and small requests for blocks on different disks run side by side.
