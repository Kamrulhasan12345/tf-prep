The Primitive Operations: INPUT, READ, WRITE, OUTPUT

Every logging method is described in terms of four primitive operations that move data between disk, memory buffers and a transaction's local variables. This chapter defines them, traces the textbook's transaction “A := A*2; B := B*2” step by step, and answers the slide's two crash questions. The interactive animator lets you run and crash your own action sequences.

1. Three places where a value can live (slide 14)

When a transaction reads or writes a database element, three address spaces are involved (textbook §17.1.4):

  1. The disk blocks that hold the database (non-volatile).
  2. The memory buffers managed by the buffer manager (volatile).
  3. The local address space of the transaction: its own variables, such as t (volatile).

To read an element, the transaction first has it brought from disk into a buffer, then copies the buffer value into a local variable. To write, it computes a new value locally, copies it into the buffer, and at some later time the buffer is copied to disk. The slide names the two policies for “later”:

Immediate modification
The updated buffer is written to disk right away.
Deferred modification
Copying updated buffers to disk is delayed, to save disk I/Os (a buffer changed ten times is written once).

Deferring writes is good for speed and bad for safety: until the buffer reaches disk, a crash loses the change. The logging rules in the next chapters say exactly when a write may be delayed and when it must happen.

2. The four primitives (slide 15)

Let X be a database element (think of it as a disk block).

INPUT(X)
Copy the disk block containing X into a memory buffer.
READ(X, t)
Copy the value of X into the transaction's local variable t. If X is not in a memory buffer, INPUT(X) is executed first.
WRITE(X, t)
Copy the value of local variable t into X in its memory buffer. If X is not in a buffer, INPUT(X) is executed first. The disk is not touched.
OUTPUT(X)
Copy the buffer containing X to disk.

Who issues them: READ and WRITE are issued by the transaction (through the transaction manager); INPUT and OUTPUT are normally issued by the buffer manager. (The log manager can also cause an OUTPUT, as later chapters show.) The textbook adds one assumption used everywhere in this chapter: a database element is no larger than a single block, so OUTPUT(X) writes X atomically.

3. The transaction A := A*2; B := B*2 (slides 16–17)

The textbook's running example (Example 17.1). The database has two elements A and B with the consistency rule A = B. Transaction T doubles both:

A := A*2;
B := B*2;

If T starts with A = B, it ends with A = B, so it is correct. In primitive steps, T is:

READ(A,t); t := t*2; WRITE(A,t); READ(B,t); t := t*2; WRITE(B,t);

The buffer manager adds INPUT(A) and INPUT(B) before the READs (because A and B are not yet in memory) and, eventually, OUTPUT(A) and OUTPUT(B) after T ends. With A = B = 8 initially, the slide's table (textbook Fig. 17.2) is:

Read the table column by column. t := t*2 changes only t. WRITE changes only the memory copy. Only OUTPUT changes the disk, and the two OUTPUTs are separate actions, so there is a moment (between them) when the disk holds A = 16, B = 8.

Slide 17 questions (worked answers)

What happens if the system crashes before OUTPUT(A)? Every change so far exists only in memory (t, Mem A, Mem B). The crash wipes memory. The disk still holds A = 8, B = 8, exactly the state before T began. The database is consistent, as if T never executed. The user's transaction is lost, but it can be run again from scratch.

What happens if the system crashes after OUTPUT(A) but before OUTPUT(B)? The disk holds A = 16 (written) and B = 8 (not yet written). Memory, with the new B = 16, is gone. A ≠ B, so the database is in an inconsistent state. T executed partially, which the converse of the correctness principle says is not allowed. Nothing on disk tells us what T had done, so the system cannot repair it. A log is needed: with it, recovery can either reset A to 8 (undo) or set B to 16 (redo). Set “Crash after step” to 6 and then to 7 in the animator to see both outcomes.

Quick check

Summary: INPUT and OUTPUT move blocks between disk and memory buffers (issued by the buffer manager); READ and WRITE move values between buffers and the transaction's local variables (issued by the transaction). WRITE never touches the disk. A crash before any OUTPUT leaves the old consistent state; a crash between two OUTPUTs can leave a mix of old and new values, which only a log can repair.
