The Log: Log Records and Write-Ahead Logging

What the log manager writes, the four kinds of log record, why an undo log stores only old values and a redo log only new values, and the write-ahead logging principle that all three logging methods are built on.

1. The log and the log manager (slide 18)

Log
An append-only file of log records, each describing something a transaction has done. It is kept on non-volatile storage (log files on disk) and used to recover the database after a crash.
Log buffer
Memory blocks allocated for the log. New log records are first appended here, like any other block in memory.
FLUSH LOG
The command that makes the buffer manager copy to disk every log block that is new or has changed since it was last copied. Only after a flush is a log record safe from a crash.

The log manager maintains the log records, keeps them in log buffers, and sends them to disk “when needed” or “when feasible”. As the next chapters show, “when needed” is exactly what the logging rules define: certain log records must reach disk before certain other things happen. The log is what lets the database return to a consistent state after a crash.

2. Types of log record (slides 19–20)

<START T>
Transaction T has begun.
<COMMIT T>
T has completed successfully and will make no more changes. Every change T made must end up on disk.
<ABORT T>
T could not complete successfully. No change T made may remain on disk.
<T, X, v>
An update record: T has changed database element X. In an undo log, v is the previous (old) value of X. In a redo log, v is the new value. (Undo/redo logging, Lecture 06, uses <T, X, v, w> with both.)

Two facts about update records from slide 20 are easy to get wrong:

  • The update record is written in response to WRITE(X,t), the change in the memory buffer, not to OUTPUT(X). The log describes changes as they happen in memory.
  • Changes normally happen in memory buffers first, so when the update record is written the disk usually still has the old value.

Slide 19 question: <COMMIT T> is written, but what if the buffers are not copied to disk?

A COMMIT record promises that T's changes are permanent, but the buffer manager decides on its own when to copy buffers to disk. A crash right after the COMMIT could lose changes that were still only in memory. The slide's answer: the recovery manager ensures the changes will be reflected. How it does so depends on the logging method. Undo logging (next chapter) forbids writing the COMMIT record to disk until all of T's changes are on disk, so the problem cannot arise. Redo logging (Lecture 06) lets the COMMIT go first and keeps the new values in the log, so recovery can write them again.

Slide 19 question: what if the buffer manager writes updated buffers to disk before the transaction aborts?

Then the disk holds values written by a transaction that must leave no trace. Again the recovery manager ensures the changes will not be reflected: the update records on the log hold the old values, so recovery (or the abort itself) writes the old values back. Undo logging allows exactly this situation and repairs it; redo logging forbids it by never writing a change to disk before the COMMIT record.

Slide 20 questions: why does an undo log not store the new value, and a redo log not the old value?

Each method only ever needs one of the two. Undo logging repairs a crash by cancelling incomplete transactions: it writes old values back. Its rules guarantee that committed transactions already have all their changes on disk, so the new value is never needed. Redo logging repairs a crash by repeating committed transactions: it writes new values. Its rules guarantee that an uncommitted transaction never wrote anything to disk, so there is never an old value to restore. Storing only what is needed keeps the log smaller. Undo/redo logging stores both and in exchange gets more freedom in when buffers may be written.

3. Write-ahead logging (slide 21)

Write-ahead logging (WAL)
The database must write a log record to stable storage before writing the corresponding changed data page to disk.

The slide's example: a transaction changes an account balance from 10,000 to 9,000. The DBMS first records the change in the log; the data page itself may reach disk much later. This ordering is what makes recovery possible in both directions:

  • Crash before COMMIT: if the page with 9,000 did reach disk, the log record (which reached disk first) tells recovery the old value 10,000, so the incomplete transaction can be undone.
  • Crash after COMMIT, page not yet on disk: the disk still shows 10,000, but the log has the change, so the committed transaction can be redone.

Without WAL, a page could reach disk with no trace in the log; after a crash nobody would know it had to be undone. WAL is the main mechanism behind atomicity (all or nothing) and durability (committed changes survive crashes). Rule U1 of undo logging, rule R1 of redo logging and rule UR1 of undo/redo logging are all versions of WAL.
