Recovery Using an Undo Log

After a crash, the recovery manager reads the undo log backward and resets every change of every incomplete transaction. This chapter gives the algorithm, explains why the scan must go backward and why ABORT records are written, shows that recovery can safely crash and restart, and analyses the slide's four crash points. The recovery simulator replays any undo log you type.

1. The problem (slide 25)

Suppose the system fails while transaction T is running. Some of T's changes may have reached disk and others not. T did not complete, so it was not executed atomically, and the database may be inconsistent. The solution: the recovery manager uses the log records to revert the partial changes of T. Once all of them are reversed, the database is back in a consistent state, as if T never ran.

2. Committed or not? (slides 26–27)

Step 1: for each transaction T, the recovery manager decides whether T committed.

  • Step 2a: <COMMIT T> is on the log on disk. Then T is committed. By rule U2 the COMMIT record was written only after all of T's updates were on disk, so T cannot have left the database inconsistent. Nothing needs to be done for T.
  • Step 2b: <START T> is on the log but <COMMIT T> is not. Then T is treated as uncommitted (aborted). Some of its updates may be on disk; it is incomplete and may have left the database inconsistent. The recovery manager looks at every record <T, X, v> and resets X to its old value v. Rule U1 makes this complete: if the new X was written to disk, then <T,X,v> reached disk before it, so the record is there to be found.

Note that recovery does not check whether X actually changed on disk. It simply writes v. If X already had value v, the write is redundant and harmless.

3. The recovery algorithm (slide 28)

When several uncommitted transactions are on the log, all their updates are undone, and the order matters. The algorithm:

Scan the log BACKWARD from the end. For each log record l:
    if l is <COMMIT T> (or <ABORT T>):  record T as completed
    if l is <T, X, v> and T is completed:  do nothing
    if l is <T, X, v> and T is not completed:  write X = v on disk
At the end: write <ABORT T> for every incomplete T that was not already aborted,
            then FLUSH LOG.

Scanning backward has a nice side effect: when the scan meets an update record of T, it has already passed everything that comes after it, including T's COMMIT if there is one. So the single backward pass both classifies transactions and undoes them.

Why is the order of reverting important?

Suppose two incomplete transactions both changed X: the log contains <T1, X, 5> (X was 5 before T1) and later <T2, X, 7> (X was 7, the value T1 wrote, before T2). The correct result is X = 5, the value before either transaction. Backward: first X = 7, then X = 5. Correct. Forward: first X = 5, then X = 7, which leaves T1's uncommitted value in the database. Undoing latest-first peels changes off in the reverse order they were made. (With proper concurrency control two uncommitted transactions should not both write X, as Lectures 02–04 show, but the backward order is correct regardless.)

Slide 28 question: why write <ABORT T> at the end?

It marks T as finished in the log, so no later recovery treats it as incomplete again. That matters for correctness. Suppose recovery undoes T (X = 5) but writes no ABORT. Normal work resumes: transaction U changes X from 5 to 9, commits, and X = 9 reaches disk. Another crash. The next recovery scans backward, skips U's records (U committed), reaches the old record <T, X, 5>, sees no COMMIT for T, and writes X = 5, destroying U's committed update. With <ABORT T> on the log, the backward scan meets the ABORT first and ignores T's records. ABORT records are also needed for checkpointing (next chapter), which requires every transaction before a checkpoint to have a COMMIT or ABORT record. The log is flushed so the ABORT records themselves survive a crash.

4. Crashes during recovery (slide 29)

Idempotent
An operation is idempotent if doing it several times has exactly the same effect as doing it once.

What if the system crashes again while it is recovering? Undoing <T,X,v> means “write v into X”. It does not matter what X currently holds; we just write v. Writing v twice leaves X = v, the same as writing it once. So the whole recovery procedure is idempotent: if it is interrupted at any point, it is simply started again from the beginning, and the outcome is the same as one uninterrupted run. This works because undo records store the old value, not the change. A record “X was decreased by 100” would add 100 each time it was replayed. (The same argument holds for redo and undo/redo logging.)

5. Analysing crash points (slide 30)

Slide 30 repeats the 12-step undo-logging table of the previous chapter and asks what the recovery manager does for four crash points. Recall: step 4 logs <T,A,8>, step 7 logs <T,B,8>, step 8 flushes the log, steps 9–10 output A and B, step 11 writes <COMMIT T> and step 12 flushes it.

Slide 30 (worked answers)

Crash after step 12. <COMMIT T> is on disk. T is committed; recovery ignores all its records. By U2, A = 16 and B = 16 are already on disk. Result: A = B = 16.

Crash before step 11 (anywhere from just after step 8 up to step 10). The COMMIT record was never written, so T is incomplete. The log on disk has <START T>, <T,A,8>, <T,B,8> (flushed at step 8). Scanning backward: <T,B,8> → write B = 8; <T,A,8> → write A = 8. Then write <ABORT T> and flush. Whether the crash came before step 9, between 9 and 10 or after 10, some, none or all of the 16s were on disk; recovery writes 8 for both anyway. Result: A = B = 8. (Between steps 11 and 12 the COMMIT may or may not have reached disk, for instance because another transaction flushed the log. If it did, the case is the same as “after step 12”, otherwise the same as this one.)

Crash before step 6. No FLUSH LOG and no OUTPUT has happened yet (both come at step 8 or later), so the disk has A = B = 8. The log on disk may be empty, or, if some other transaction flushed the log, may contain <START T> and <T,A,8>. In the first case recovery finds nothing about T. In the second it writes A = 8 (redundant) and logs <ABORT T>. Either way A = B = 8.

Crash before step 4. T has not written anything, not even to memory. At most <START T> is on the log on disk. If it is, T is incomplete with no update records, so recovery only writes <ABORT T>. A = B = 8.

Animated, the “before step 11” case: the log on disk is <START T> <T,A,8> <T,B,8>, and the crash happened after step 9, so disk holds A = 16, B = 8.

The following is a sequence of undo-log records written by two transactions T and U:

<START T>; <T, A, 10>; <START U>; <U, B, 20>; <T, C, 30>; <U, D, 40>;
<COMMIT U>; <T, E, 50>; <COMMIT T>.

Assume that the recovery manager takes an action <X, V> meaning database element X is restored to the value V in the disk. Determine the actions that will be taken by the recovery manager, if there is a crash and the last log record to appear on disk is one of the following: (i) <COMMIT U> (ii) <T, E, 50> (iii) <COMMIT T>

Show worked answer

Undo recovery scans backward from the last record on disk, remembers committed transactions, and restores the old value of every update of an uncommitted transaction.

(i) Last record <COMMIT U>. Backward: <COMMIT U>: U committed. <U,D,40>: U committed, ignore. <T,C,30>: T has no COMMIT, undo → <C, 30>. <U,B,20>: ignore. <START U>. <T,A,10>: undo → <A, 10>. <START T>. Actions: <C,30>, <A,10>, then <ABORT T> is written to the log and flushed.

(ii) Last record <T, E, 50>. Backward: <T,E,50>: T uncommitted → <E, 50>. <COMMIT U>: U committed. Then as in (i): <C, 30>, <A, 10>. Actions: <E,50>, <C,30>, <A,10>, then <ABORT T>.

(iii) Last record <COMMIT T>. Both T and U have COMMIT records, so by U2 all their changes are on disk. No actions; nothing is written to the log either.

Summary: a transaction with <COMMIT T> on disk needs nothing (U2). Every other transaction is undone by scanning the log backward and writing the old value of each of its update records (U1 guarantees they are there). Backward order restores the earliest old value. Afterwards <ABORT T> is logged and flushed so no later recovery undoes T again. Recovery is idempotent, so a crash during recovery is handled by just starting again.
