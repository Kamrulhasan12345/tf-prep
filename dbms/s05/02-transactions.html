Transactions, Atomicity and Consistency

What a transaction is, why it must be atomic, which DBMS components keep it so (transaction, log, buffer and recovery managers), and what “consistent state” and the correctness principle mean.

1. What is a transaction? (slide 7)

Transaction
The unit of execution of database operations: a group of reads and writes that the DBMS treats as one piece of work.
COMMIT
The command that ends a transaction successfully: all its changes become permanent.
ROLLBACK (abort)
The command that ends a transaction unsuccessfully: all its changes are cancelled, as if it never ran.

The slide describes how transactions look to an SQL user (the textbook says the same in §17.1.2):

  • A transaction starts when a session is created with the database, that is, as soon as you connect and issue the first statement.
  • Each SQL statement is part of the ongoing transaction. Several UPDATEs in a row belong to the same transaction.
  • The transaction ends when COMMIT or ROLLBACK is issued.
  • A new transaction automatically starts after COMMIT or ROLLBACK, so the session is always inside some transaction.
-- one transaction: transfer 100 from B to A
UPDATE account SET balance = balance + 100 WHERE id = 'A';   -- credit A
UPDATE account SET balance = balance - 100 WHERE id = 'B';   -- debit B
COMMIT;                                                      -- a new transaction begins here

2. Atomicity (slide 8)

Atomicity
A transaction executes fully or not at all. There is no visible state in which only part of it has happened. (“Atomic” means indivisible.)

For the transfer above, either both the credit and the debit happen, or neither does. If only one happens, money is created or destroyed and the database is inconsistent. Atomicity is kept by two parties:

  • The user chooses the boundaries: they issue COMMIT when the whole unit of work is done, or ROLLBACK to cancel it.
  • The transaction manager makes sure that, whatever happens (including crashes), either all changes of a committed transaction are saved, or no change of an aborted or unfinished transaction is.

3. The components that keep transactions safe (slides 9–10)

Slides 9 and 10 show the textbook's Figure 17.1. The arrows show which component talks to which.

Transaction manager
Runs transactions. It sends the queries of a transaction to the query processor; it tells the log manager what to record; and it ensures an appropriate isolation level (SERIALIZABLE, READ COMMITTED, …) so that concurrent transactions do not interfere (Lectures 02–04).
Log manager
Maintains the log: a record of all changes made to the database. Log records are first written to log buffers in memory and later flushed to disk. Because the log is on disk, lost changes can be re-applied after a crash.
Buffer manager
Manages the memory buffers. It reads data blocks from disk into memory and writes them back. All changes are made in memory first and flushed to disk later.
Recovery manager
Activated after a crash. It examines the log records and repairs the data, by reapplying changes (redo) or undoing them.

4. Database elements and database state (slide 11)

Database element
A unit of data that has a value and can be read or written by transactions. Depending on the system it may be a relation, a disk block (page), or a tuple. The textbook recommends disk blocks, and assumes no element is larger than one block.
Database state
The value of every element of the database at one moment.
Consistent state
A state that satisfies all the constraints the data should obey: (1) the explicit constraints in the schema (keys, foreign keys, CHECK), (2) implicit constraints enforced by triggers, and (3) implicit constraints that exist only in the mind of the database designer.

The third kind is the troublesome one. “Credit and debit happen together” is a business rule. You cannot write it as a CHECK, primary key or foreign key, because it is about how two updates relate, not about what one row looks like. So the DBMS cannot test for it. It can only make sure transactions run atomically, and trust that a complete transaction keeps the rule.

(Do not confuse the database state with the transaction's state: the latter is the transaction's position in its code plus its local variables.)

5. The correctness principle and its converse (slides 12–13)

Correctness principle. If a transaction executes in the absence of any other transactions or system failures, and it starts with the database in a consistent state, then the database is also in a consistent state when the transaction ends.

In words: each transaction, run alone and to completion, is assumed to be correct. The DBMS does not check this; the person who writes the transaction is trusted to know the business rules. (Explicit constraints are enforced anyway: a transaction that violates one is rejected.)

The converse lists what can break consistency even though every transaction is individually correct:

  1. Partial execution. If only part of a transaction executes, the database state may become inconsistent. That is why a transaction must be atomic. Guarding against partial execution after a crash is the job of logging and recovery, Lectures 05–06.
  2. Simultaneous execution. Transactions running at the same time are likely to lead to an inconsistent state unless the system controls how they interact. That is the job of concurrency control, Lectures 02–04.

Practice

Key terms

Quick check

Summary: a transaction is the unit of execution; it ends with COMMIT or ROLLBACK and a new one starts automatically. It must be atomic. The transaction manager drives execution and isolation, the log manager keeps the log, the buffer manager moves blocks between memory and disk, and the recovery manager repairs the database from the log after a crash. A complete transaction takes a consistent state to a consistent state (correctness principle); partial or uncontrolled concurrent execution can break consistency.
