Undo Logging: Rules U1 and U2

Undo logging keeps old values in the log and repairs crashes by undoing incomplete transactions. For that to work, log records, data and the COMMIT record must reach disk in a fixed order. This chapter states the two rules, walks through the slide's 12-step table, and answers the slide's questions about synchronous and asynchronous commit.

1. The two rules (slide 22)

U1
If transaction T modifies database element X, then the log record <T, X, v> (v = old value) must be written to disk before the updated X is written to disk.
U2
If T commits, its <COMMIT T> log record must be written to disk only after all elements updated by T have been written to disk (and, the textbook adds, as soon as possible after that).

Together, for one transaction, things reach disk in this order:

(a) update log records → (b) updated elements → (c) <COMMIT T>

The order between (a) and (b) applies to each element individually. <T,A,…> must precede A on disk and <T,B,…> must precede B, but B's log record may reach disk after A's new value (the slide: “order is not necessary for all database elements combinedly changed by a transaction”). Rule U1 is write-ahead logging; rule U2 is what makes the COMMIT record trustworthy: if it is on disk, so is everything T changed.

2. The slide's example, step by step (slide 23)

The same transaction as before, A := A*2; B := B*2, with A = B = 8, now with undo logging (textbook Fig. 17.3, Example 17.2):

StepActiontM-AM-BD-AD-BLog
1<START T>
2READ(A,t)8888
3t := t*216888
4WRITE(A,t)161688<T,A,8>
5READ(B,t)816888

7WRITE(B,t)16161688<T,B,8>

9OUTPUT(A)161616168
10OUTPUT(B)1616161616

12FLUSH LOG

Step by step, as the slide narrates it:

  • (1) <START T> is written to the log (buffer).
  • (2–3) READ and the local computation change nothing in the database, so they need no log record.
  • (4) WRITE(A,t) changes A in memory, so <T,A,8> is logged. 8 is the old value; the new value 16 does not appear in an undo log.
  • (7) Likewise <T,B,8> is logged for B.
  • (8) FLUSH LOG puts both update records on disk. Only now may A and B be written (U1).
  • (9–10) The updated A and B are written to disk.
  • (11) Only now may T commit: <COMMIT T> is appended to the log (U2).
  • (12) FLUSH LOG puts <COMMIT T> on disk.

Slide typo: the slide's text list says “(4) <T,B,8> is written to log”. The table on the same slide is right: step 4 writes <T,A,8>, step 7 writes <T,B,8>.

Why flush the log again at step 12? Without it, T might have committed from the user's point of view while the log on disk does not say so. If a crash came much later, recovery would see no COMMIT and undo a transaction the user was told had finished long ago (textbook Example 17.2).

Run it, change it, break it

The animator is set to undo logging. The colour of each log record shows whether it is still only in the memory buffer or already on disk. Try moving OUTPUT(A) above FLUSH LOG, or COMMIT + FLUSH LOG above the OUTPUTs, and press Run: the tool flags the broken rule. Set a crash step to see the recovery result.

3. Commit of transactions (slide 24)

Synchronous (durable) commit
The COMMIT (or ABORT) record is written to the log and flushed to disk before the user is told that the transaction is complete.
Asynchronous commit
The user is told the transaction is complete as soon as the COMMIT record is in the log buffer; the flush to disk happens later.

Slide 24 questions (worked answers)

Synchronous commit prevents data loss during a crash. How? The confirmation reaches the user only after <COMMIT T> is on disk, and by U2 all of T's changes reached disk even earlier. After any crash, recovery finds <COMMIT T> on disk and leaves T alone, and T's changes are already on disk. Everything the user was told about survives.

Asynchronous commit can lose updates. How? The user is told “committed”, but <COMMIT T> is only in memory. If the system crashes before the next log flush, the record is lost. Recovery sees <START T> and T's update records but no COMMIT, so it treats T as incomplete and undoes it, writing the old values back. A transaction the user believes finished has vanished. (The gain is speed: commits do not wait for a disk write.)

In both cases the database remains consistent. How? Recovery either finds the COMMIT record on disk, and then by U2 every change of T is on disk, or it does not find it, and then it undoes every change of T that reached disk (U1 guarantees the old values are in the log). Either way T is applied entirely or not at all, so atomicity, and hence consistency, holds. Asynchronous commit only weakens durability: a confirmed transaction can be lost, but never half-applied.

Key terms

Quick check

Summary: U1: an element's update record reaches disk before the element does. U2: the COMMIT record reaches disk only after all the transaction's elements have. So the disk order is log records → data → COMMIT, per element. Synchronous commit confirms after the COMMIT is flushed (durable); asynchronous commit confirms earlier and can lose a confirmed transaction, but never breaks atomicity.
