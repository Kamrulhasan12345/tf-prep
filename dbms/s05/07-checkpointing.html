Checkpointing an Undo Log: Quiescent and Nonquiescent

Without help, recovery would read the entire log, which grows forever. A checkpoint marks a point before which the log is no longer needed. This chapter covers the simple (quiescent) checkpoint, the nonquiescent checkpoint that does not stop the system, how far back recovery must scan in each case, and several exam questions.

1. Why checkpoint? (slide 31)

The log only grows. After months of operation it is huge, and scanning all of it after every crash would take far too long. Yet with undo logging, most of it is useless: once a transaction's COMMIT record is on disk, its log records are never needed again (recovery ignores committed transactions). We cannot simply cut the log after each COMMIT, though, because many transactions run at once, and cutting could throw away records of some other transaction that is still active and might need undoing.

Checkpoint
A point marked in the log such that log records before it need not be examined during recovery (and may be deleted). For undo logging, every transaction that started before the checkpoint must have a COMMIT or ABORT record on the log.

2. Quiescent checkpointing (slide 32)

The simple checkpoint (textbook §17.2.4):

Step 1: Stop accepting new transactions.
Step 2: Wait until all active transactions commit or abort
        (and have written their COMMIT or ABORT record).
Step 3: Flush the log to disk.
Step 4: Write a log record <CKPT> and flush the log again.
Step 5: Resume accepting new transactions.
Quiescent
“Quiet”: the system is brought to a state with no active transactions while the checkpoint is taken.

Recovery: scan backward from the end as usual. On reaching <CKPT>, stop. Every transaction that began before it has a COMMIT or ABORT on disk, and by U2 its changes are on disk, so nothing before <CKPT> needs undoing. Every incomplete transaction began after <CKPT>, so all of its records have already been seen.

Textbook Example 17.4

The log begins <START T1> <T1,A,5> <START T2> <T2,B,10> and we decide to checkpoint. T1 and T2 are active, so we must wait for both to finish before writing <CKPT>. Fig. 17.4 continues: <T2,C,15> <T1,D,20> <COMMIT T1> <COMMIT T2> <CKPT> <START T3> <T3,E,25> <T3,F,30>, then a crash. Scanning backward, T3 is the only incomplete transaction: restore F = 30, then E = 25. At <CKPT> we stop.

3. Nonquiescent checkpointing (slide 33)

The trouble with a quiescent checkpoint: all new transactions must wait until every running transaction completes. One long transaction can make the database look shut down for a long time. A nonquiescent checkpoint lets new transactions start while the checkpoint is in progress:

Step 1: Write <START CKPT(T1, …, Tk)> and flush the log.
        T1 … Tk are all the transactions active at this moment.
Step 2: Wait until T1 … Tk all commit or abort.
        Do not prevent new transactions from starting.
Step 3: When all of T1 … Tk have finished, write <END CKPT> and flush the log.

4. Recovery with a nonquiescent checkpoint (slide 34)

Recovery scans backward from the end and undoes incomplete transactions exactly as before. What changes is where it may stop. There are two cases, depending on which checkpoint record it meets first:

  • Case 1: it meets <END CKPT> first. The checkpoint completed, so all of T1 … Tk finished before END CKPT. Any incomplete transaction must therefore have started after <START CKPT(T1,…,Tk)>. Scan back as far as that START CKPT and stop.
  • Case 2: it meets <START CKPT(T1,…,Tk)> first (no END CKPT after it). The crash happened during the checkpoint. The only incomplete transactions are those met so far in the scan, plus those among T1 … Tk that did not finish. Scan back to the earliest <START Ti> among the unfinished Ti and stop there.

As a rule, once an <END CKPT> is on disk, the log before the matching START CKPT can be deleted. The textbook adds a practical tip: chaining together the log records of each transaction (each record points to the transaction's previous record) lets recovery jump straight to the records it needs instead of reading everything in between.

Textbook Example 17.5, case 1 (Fig. 17.5)

The checkpoint starts after <T2,B,10> with T1 and T2 active, so <START CKPT(T1,T2)> is written. T3 starts during the checkpoint. T1 and T2 commit, <END CKPT> is written, and the crash comes after <T3,F,30>. Scanning backward: T3 is incomplete, so F = 30. Then <END CKPT>: case 1. Continue to <START CKPT>: on the way <T3,E,25> gives E = 25; T1's and T2's records are ignored because they committed. Stop at <START CKPT(T1,T2)>.

Textbook Example 17.5, case 2 (Fig. 17.6)

Now the crash comes during the checkpoint, after <T3,E,25> (T1 committed, T2 did not). Backward: E = 25 (T3), <COMMIT T1>, ignore <T1,D,20>, <START T3>, C = 15 (T2). Then <START CKPT(T1,T2)> with no END: case 2. Of T1 and T2 only T2 is unfinished, so continue to <START T2>, restoring B = 10 on the way, and stop there. <T1,A,5> and <START T1> are never read.

Consider the following sequence of undo log records:

<START S>; <S, A, 60>; <COMMIT S>; <START T>; <T, A, 10>; <START U>;
<U, B, 20>; <T, C, 30>; <START V>; <U, D, 40>; <V, F, 70>; <COMMIT U>;
<T, E, 50>; <COMMIT T>; <V, B, 80>; <COMMIT V>.

(3a) Suppose that we begin a nonquiescent checkpoint immediately after the <U, B, 20> log record has been written (in memory). Determine the last log record that must be sent to disk before each of the following events: (i) <START CKPT (...)> is written to disk and (ii) <END CKPT> is written to disk.

(3b) For the given undo log records, suppose we begin a nonquiescent checkpoint after the log record <U, B, 20> and a system crash occurs after one of the following: (i) <V, B, 80> and (ii) <T, E, 50>. For each case, determine the oldest log record that the recovery manager needs to scan to find all possible incomplete transactions.

Show worked answer

The checkpoint record. Right after <U,B,20>, S has committed and T and U have started without committing. So the record is <START CKPT(T, U)>.

3a (i). Step 1 writes <START CKPT(T,U)> and flushes the log. Log records reach disk in order, so everything before it goes first. The last record that must be on disk before it is <U, B, 20>.

3a (ii). Under undo logging, <END CKPT> may be written only after both T and U have finished. U commits at <COMMIT U>, T later at <COMMIT T>. So <END CKPT> comes right after <COMMIT T>, and the last record that must be on disk before it is <COMMIT T>. The full log is then:

<START S> <S,A,60> <COMMIT S> <START T> <T,A,10> <START U> <U,B,20>
<START CKPT(T,U)> <T,C,30> <START V> <U,D,40> <V,F,70> <COMMIT U>
<T,E,50> <COMMIT T> <END CKPT> <V,B,80> <COMMIT V>

3b (i), crash after <V,B,80>. <END CKPT> is already on the log (it follows <COMMIT T>). Scanning backward, the first checkpoint record met is <END CKPT>: case 1. Every incomplete transaction (here only V) started after the START CKPT. The oldest record to scan is <START CKPT(T, U)>. (Recovery writes B = 80 and F = 70 and logs <ABORT V>.)

3b (ii), crash after <T,E,50>. T has not committed, so no <END CKPT> exists. The first checkpoint record met is <START CKPT(T,U)>: case 2. U committed (its COMMIT was seen in the scan), T did not, so we must reach T's start. The oldest record to scan is <START T>. (Recovery writes E = 50, F = 70, C = 30, A = 10 and logs <ABORT T>, <ABORT V>.)

The following is a sequence of undo log records found in the disk after a crash:

<START T1> <T1, A, 10> <START T2> <T2, B, 5> <T1, C, 7> <START T3> <T3, D, 12>
<COMMIT T1> <START CKPT ?> <START T4> <T2, E, 5> <COMMIT T2> <T3, F, 1>
<T4, G, 15> <END CKPT> <COMMIT T3> <START T5> <T5, H, 3> <START CKPT ?> <COMMIT T5>

Now answer the following questions: (i) What are the correct values of the two "?"-s in the log record? (ii) Describe the action of recovery manager, showing changes to both the disk and the log.

Show worked answer

(i) A START CKPT record lists the transactions active (started, not committed or aborted) when it is written.

  • First ?: T1, T2, T3 have started and T1 has just committed. Active: <START CKPT(T2, T3)>.
  • Second ?: T2 and T3 have committed; T4 and T5 have started and not finished. Active: <START CKPT(T4, T5)>.

A remark on the given log: under undo logging the first <END CKPT> may only be written after both T2 and T3 finish, but here it appears before <COMMIT T3>. The list must still be (T2, T3), because T3 was active; the END CKPT is simply placed too early in the question. It does not affect the recovery below, which is governed by the second checkpoint.

(ii) Scan backward from the end:

RecordAction
<COMMIT T5>T5 committed.
<START CKPT(T4,T5)>First checkpoint record met, and it is a START with no END after it: case 2. Of T4 and T5, T5 has committed, so we must scan back to <START T4>.
<T5,H,3>T5 committed: ignore.
<START T5>, <COMMIT T3>T3 committed.
<END CKPT>Belongs to an older checkpoint; we already know where to stop.
<T4,G,15>T4 has no COMMIT: write G = 15 on disk.
<T3,F,1>T3 committed: ignore.
<COMMIT T2>, <T2,E,5>T2 committed: ignore.
<START T4>Start of the last unfinished listed transaction: stop.

DB QB · 19-20 4c · 25 marks (as printed)  |  BUET QBank · CSE 215 | L-2/T-2 | 2019–20 · 5 marks

Explain checkpoint in database recovery.

Show worked answer

Need. Recovery reads the log, and in principle the whole log, which grows without bound. Most of it concerns transactions that finished long ago and whose changes are safely on disk. A checkpoint is a record in the log guaranteeing that nothing before a certain point is needed for recovery, so recovery stops there and the older log can be deleted.

Quiescent checkpoint (undo logging): stop accepting new transactions; wait until every active transaction commits or aborts; flush the log; write <CKPT> and flush; resume. On recovery, scan backward and stop at <CKPT>: every transaction before it is finished and (rule U2) on disk. Drawback: the system stalls while long transactions finish.

Nonquiescent checkpoint: write <START CKPT(T1,…,Tk)> naming the active transactions, flush; let new transactions start; when T1…Tk have all finished, write <END CKPT> and flush. On recovery, scanning backward: if <END CKPT> is met first, stop at the matching <START CKPT>; if <START CKPT(T1…Tk)> is met first, stop at the earliest <START Ti> of the unfinished Ti.

With redo and undo/redo logging (Lecture 06), the checkpoint instead writes dirty buffers to disk between START CKPT and END CKPT (only those of committed transactions for redo logging, all of them for undo/redo), and does not wait for the active transactions.

Example: in the timeline above (Fig. 17.5), recovery after the crash reads only from <START CKPT(T1,T2)> to the end.

Note on the CSE215 bank's answer: it describes the Silberschatz-style checkpoint (suspend transactions, flush all dirty buffers, write <checkpoint L>). That is a valid scheme from another textbook, but for this course give the quiescent and nonquiescent checkpoints above.

BUET QBank · CSE 303 | L-3/T-1 | 2012–13 · 10 marks

What properties of a recovery system allow us to recover from a crash while recovering a previous crash? What are the purposes of checkpointing and nonquiescent checkpointing?

Show worked answer

Recovering from a crash during recovery. The key property is that recovery is idempotent: running it twice, or running part of it and then all of it, has the same effect as running it once. This holds because:

  • Update records store values (the old value for undo, the new value for redo), not changes such as “add 100”. Undo writes v into X regardless of X's current value; doing it again writes the same v.
  • Recovery does not depend on what is currently on disk; it decides everything from the log, which it does not modify until the end.
  • The log records that recovery relies on are already on disk (write-ahead rules), and recovery only appends <ABORT T> records after all undo work is done, then flushes. If it crashes before that, the next recovery simply redoes the same work; if after, the ABORTs tell it the work is done.

Purpose of checkpointing: to bound the part of the log recovery must read, so recovery is fast, and to allow the log before the checkpoint to be deleted, so the log does not grow forever.

Purpose of nonquiescent checkpointing: a quiescent checkpoint stops new transactions until all active ones finish, which can make the system unavailable for a long time. A nonquiescent checkpoint gets the same benefit without stopping the system: new transactions keep starting while the checkpoint waits (undo logging) or while dirty buffers are flushed (redo, undo/redo logging), marked by <START CKPT(…)> and <END CKPT>.

Note: the CSE215 bank's answer explains idempotence through ARIES (LSNs, PageLSN, compensation log records). That is correct for ARIES, which is not part of this course; the answer above uses the course's logging methods.

Summary: a quiescent checkpoint waits for all active transactions to finish, then writes <CKPT>; recovery stops there. A nonquiescent checkpoint writes <START CKPT(active list)>, lets new transactions run, and writes <END CKPT> when the listed ones finish. Recovery that meets END CKPT first stops at the matching START CKPT; recovery that meets START CKPT first goes back to the earliest START of the unfinished listed transactions.
