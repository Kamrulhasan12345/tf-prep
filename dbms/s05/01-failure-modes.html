What Can Go Wrong: Failure Modes

A database must survive bad input, broken disks, fires and sudden power cuts. This chapter sorts failures into four kinds, says which tool protects against each, and explains why the rest of Chapter 17 is about one of them: the system failure.

1. Four kinds of failure (slide 2)

The slides list the things that can go wrong while a database is being queried and modified. The textbook (§17.1.1) adds a fourth kind, the system failure, which slide 6 treats separately. Each kind loses something different, so each needs a different remedy.

Failure mode
A category of things that can go wrong, grouped by what is lost or corrupted (a value, a disk, a whole site, or the contents of main memory).
Volatile storage
Storage whose contents vanish when the power goes: main memory (RAM).
Non-volatile storage
Storage that keeps its contents without power: disks, SSDs, tape, optical disks.

2. Erroneous data entry (slide 3)

Some wrong data cannot be detected at all. If a clerk mistypes one digit of your phone number, the result still looks like a valid phone number, possibly someone else's, and no program can tell it is wrong.

Other errors are detectable. If the clerk omits a digit, the value no longer has the form of a phone number. Such errors are caught by:

  • Constraints and triggers in the database: for example a CHECK that the phone number has exactly 11 digits, or a trigger that rejects a malformed value.
  • Validation in the application front end (the form the clerk types into) and the back end (the server code that receives it).

Logging does nothing for this kind of error: the database faithfully stores and logs the wrong value.

3. Media failures (slide 4)

A media failure damages the disk itself. There are two sizes of damage:

  • Local failure: a bit or a few bits of a sector are corrupted. This is detected by the parity checks stored with each disk sector (Lecture 13): the stored parity no longer matches the data, so the disk reports a read error instead of returning wrong data.
  • Head crash: the read/write head touches the platter and the entire disk becomes unreadable. Three remedies:
    1. RAID (Lecture 13): keep redundant disks (mirrors or parity) so the lost disk can be rebuilt from the others.
    2. Archiving: periodically copy the whole database to tape or optical disk and store the copy at a safe location, away from the database. Lecture 06, Chapter 5 shows how to restore from an archive plus the log.
    3. Online redundant copies: keep live copies of the database at several sites. The slides call this a DRS (disaster recovery site).

4. Catastrophic failures (slide 5)

A catastrophic failure destroys the storage media completely: an explosion, a fire or vandalism at the site of the database. The protections are archived copies, online redundant copies, and a DRS that can take over and keep the business running.

Slide 5 question: RAID will not help. Why?

RAID protects against the failure of one disk (or two, for RAID 6) by keeping redundant information on the other disks of the same array. All those disks sit in the same machine room. A fire or explosion destroys the data disks and their parity or mirror disks at the same moment, so there is nothing left to rebuild from. Only a copy stored somewhere else survives: an archive kept at a safe distance, or a redundant copy at another site.

5. System failures (slide 6)

System failure (crash)
A failure that loses the contents of main memory but leaves the disk intact. Examples on the slide: a memory failure, a power failure, an operating-system failure while the database software is running. A software bug that overwrites memory has the same effect.
Transaction
A process that queries and modifies the database as a sequence of steps (defined fully in the next chapter).

A transaction usually changes the database in several steps. The slides' example is a transfer: credit account A, debit account B. A system failure can stop the transaction between the steps, for example after A was credited but before B was debited. The database is then in an inconsistent state: money appeared in A that never left B.

Worse, after a crash we no longer know which steps happened. Main memory, which held the transaction's progress, is gone. Running the transaction again is not safe either: if it adds 100 to A and the addition may or may not have reached the disk, repeating it may add 100 twice.

The protection is logging: every database change is recorded in a separate file on non-volatile storage, called the log. After a failure, the exact changes can be read back from the log and either reversed (undone) or reapplied (redone). How to do this safely is the subject of the rest of Lectures 05 and 06.

Quick check

Summary: erroneous data entry is fought with constraints, triggers and validation; media failures with parity checks, RAID, archives and remote copies; catastrophic failures only with copies stored elsewhere (RAID dies with the building). System failures lose main memory but not the disk, and can leave a transaction half done. Logging every change on non-volatile storage lets the recovery manager undo or redo exactly what is needed.
