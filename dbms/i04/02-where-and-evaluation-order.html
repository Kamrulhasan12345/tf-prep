WHERE, DISTINCT on Several Columns, and the Order of Evaluation

How DISTINCT works when several columns are selected, the WHERE clause, and the most useful mental model in SQL: a query is written SELECT–FROM–WHERE but evaluated FROM, then WHERE, then SELECT (then DISTINCT and ORDER BY). A labelled anatomy of a query and a step-through on a real table make the order concrete.

1. Duplicates from several columns (slides 12–15)

Slides 12–15 switch to the products database of the textbook, whose Product(maker, model, type) table lists 30 products of manufacturers A to H. (This is a different table from the 4-row Product of Chapter 1; the playground calls up the right one for each box.)

Slide 12's question (worked answer): what does SELECT maker, type FROM Product return?

One row for each of the 30 products, with only the maker and type columns. Projecting away model, which was the key, leaves many identical rows: A makes three PCs, so (A, pc) appears three times; (A, laptop) three times; (B, pc) three times; and so on (slide 13). The answer has 30 rows but only 13 different ones.

With SELECT DISTINCT maker, type (slides 14–15), rows are duplicates only if they agree on both columns. (A, pc) and (A, laptop) differ in type, so both stay. The result is one row per (maker, type) combination: 13 rows.

2. The WHERE clause (slide 16)

SELECT <attributes>          -- 3
FROM   <one or more relations> -- 1
WHERE  <conditions>          -- 2
WHERE clause
A condition (also called a predicate) tested on each row produced by FROM. Only rows for which the condition is TRUE reach the SELECT clause. This is relational-algebra selection (σ).

The numbers 3, 1, 2 that the slide writes next to the clauses are the order in which the DBMS (logically) uses them: first FROM, then WHERE, then SELECT. The order of writing is fixed by the grammar and differs from the order of evaluation.

Two practical consequences of the evaluation order: WHERE can test a column that SELECT does not output (SELECT pname FROM Product WHERE price > 100 is fine), and ORDER BY, which comes last, sees the finished output.

4. The semantics as a loop (slides 17–18)

Slides 17 and 18 define exactly what a single-table query means, as a program:

-- SELECT a1,…,ak FROM R WHERE conditions
Answer = {}
for each x in R do
    if conditions satisfied then
        Answer = Answer + {(a1,…,ak)}
return Answer
-- SELECT DISTINCT a1,…,ak FROM R WHERE …
Answer = {}
for each x in R do
    if conditions satisfied then
        Answer = Answer ∪ {(a1,…,ak)}
return Answer

The only difference is the operator that adds a row. + is bag addition: adding a row that is already present makes a second copy. ∪ is set union: adding a row that is already present changes nothing. So DISTINCT turns the bag of answers into a set.

The loop is the meaning of the query, not necessarily how the DBMS runs it: the optimizer may use an index to skip rows, or remove duplicates by sorting at the end. Every method must produce the same answer as this loop.

Summary: DISTINCT removes rows that are equal in all selected columns. WHERE keeps only rows whose condition is TRUE. A query is written SELECT, FROM, WHERE, ORDER BY but evaluated FROM → WHERE → SELECT → DISTINCT → ORDER BY. Its meaning is a loop over the rows of the table that adds the selected values of each qualifying row to the answer, as a bag (+) or, with DISTINCT, as a set (∪).
