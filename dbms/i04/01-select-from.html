SELECT and FROM: Reading a Table

The simplest SQL queries: all columns with SELECT *, chosen columns with a SELECT list, and duplicate removal with DISTINCT. Along the way: what "selection" and "projection" mean, and how a query turns an input schema into an output schema.

Lecture 3 used the DDL to create tables. Lecture 4 starts the DML: first querying one table, then (Lecture 5) inserting, deleting and modifying rows. All examples use slide 3's Product table:

2. The basic form (slide 4)

SELECT <attributes>
FROM   <one or more relations>
SELECT clause
The list of attributes (columns) the answer should contain, separated by commas, or * meaning "all attributes, in their declared order".
FROM clause
The table (or tables) the rows come from. In Lectures 4 and 5 it is always one table; Lecture 8 uses several.

"Plus many many more bells and whistles": WHERE, DISTINCT, ORDER BY and the rest are optional additions to this core, introduced one at a time in this lecture.

3. The simplest query: SELECT * (slides 5–6)

Show all entries from the product table.

SELECT *
FROM   Product;

The result is the whole table: every row, every column. The slide labels this "selection". In relational algebra, selection (written σ) is the operation that picks rows; a query with no condition selects every row, so it is a selection with the condition "always true".

4. Choosing columns: projection (slide 7)

Show all product categories.

SELECT category
FROM   Product;
Projection (π)
The operation that keeps only some columns of a relation. In SQL, the SELECT list performs projection.
Selection (σ)
The operation that keeps only some rows. In SQL, the WHERE clause (Chapter 2) performs selection.

This query selects all rows and projects onto one column, hence the slide's label "selection and projection". Beware of the names: SQL's keyword SELECT does projection, while relational algebra's selection is SQL's WHERE.

Look closely at the result: Gadgets appears twice. Gizmo and Powergizmo are both gadgets, and SQL keeps one output row per input row. Removing columns can make rows that were different become identical.

5. Removing duplicates: DISTINCT (slides 8–9)

Show all product categories, each once:

SELECT DISTINCT category
FROM   Product;
DISTINCT
A keyword placed right after SELECT that removes duplicate rows from the answer: two output rows are duplicates if they are equal in every selected column. Without it SQL uses ALL (the default), keeping every row.
SELECT DISTINCT category
SELECT category

Why is ALL the default, when the relational model says relations are sets? Removing duplicates costs time: the DBMS must sort or hash the whole answer to find equal rows. SQL lets you pay that cost only when you ask for it. Duplicates also carry information sometimes (for example, to count how many products are gadgets).

6. Several columns (slide 10)

List all products along with their price and manufacturers.

SELECT pname, price, manufacturer
FROM   Product;

The columns appear in the order of the SELECT list, which need not be the table's order: SELECT manufacturer, pname puts manufacturer first. Column names are case-insensitive, so pname, PName and PNAME all work.

Summary: SELECT list FROM table returns one output row per input row, with the listed columns (* = all). Picking columns is projection (π, done by SELECT); picking rows is selection (σ, done by WHERE). Projection can create duplicate rows; SQL keeps them unless you write DISTINCT, which removes rows equal in every selected column. A query maps an input schema to an output schema, and its result is again a relation.
