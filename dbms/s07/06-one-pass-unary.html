Kinds of Algorithms, and One-Pass Algorithms for σ, π, δ and γ

Algorithms for physical operators are classified by how many times they read the data (one, two or many passes), and operations by how much of a relation they need at once. This chapter sets up both classifications and then gives the one-pass algorithms for the unary operations: selection, projection, duplicate elimination and grouping, with their costs and memory needs.

1. One-pass, two-pass and many-pass algorithms (slides 35–36)

One-pass algorithm
Reads each block of data from disk only once. Usually requires at least one argument to fit in main memory (σ and π are the exceptions).
Two-pass algorithm
For relations too large for main memory. It reads the data a first time from disk, processes it in some way, writes it all (or almost all) back to disk, and reads it a second time to finish. So each block is read twice. These are Lecture 08's sort-based and hash-based algorithms.
Many-pass (multipass) algorithm
For data too large even for two passes: three or more passes, so each block is read three or more times. These are recursive generalizations of the two-pass algorithms (Lec 08, Chapter 2 shows the sorting case).

The textbook adds a second axis, the method: sorting-based, hash-based and index-based algorithms (§15.2). The nested-loop joins of Lecture 08 sit in between: "one and a half" passes.

Slide 38 question (worked answer): why do γ and δ need all or most of the tuples in memory at once?

Because the decision about one tuple depends on tuples that may be anywhere else in R.

  • For δ, deciding whether tuple t is a duplicate means knowing whether t was already seen, and the earlier copy could be in any block read so far. So one copy of every distinct tuple seen so far must stay in memory until the end.
  • For γ, a group's aggregate (say SUM(salary) for the CSE department) is not final until every tuple of that group has been read, and the last one could be in the last block. So every group's running total must stay in memory until R is finished.

Compare σ: whether a tuple passes the condition depends on that tuple alone, so it can be decided and forgotten at once.

3. One-pass σ and π (slide 40)

Approach: read the blocks of R one at a time into an input buffer; apply the operation to each tuple; move the selected tuples, or the projected tuples, to the output.

  • Requirement: M ≥ 1, regardless of B(R). The output buffer is not counted because it may be the input buffer of the next operator, or may go straight to the user.
  • I/O cost depends only on how R is read: B(R) if R is clustered or a table scan is used; T(R) if R is not clustered and an index scan is used (very expensive, Chapter 4).
  • Exception: for a selection whose predicate compares an indexed attribute with a constant (such as eid = 101), use the index to retrieve only a subset of R's blocks. The cost of this index seek is less than B(R), often much less.

4. One-pass duplicate elimination δ(R) (slides 41–42)

Slide slip: slide 41 labels this operation "γ(R) [Duplicate elimination]". Duplicate elimination is δ; γ is grouping.

Memory plan: one buffer holds the current block of R; the remaining M − 1 buffers hold a single copy of every tuple seen so far (textbook Fig. 15.6).

for each block of R: read it into the input buffer
    for each tuple t in the block:
        if t is already among the stored tuples: discard t      (do not output)
        else: copy t to the output, and store t in the M−1 buffers

The cost of checking (slide 42)

"Is t already stored?" is asked once per tuple of R, so its speed matters:

  • If we just keep a list and compare t with every stored tuple, each check costs O(n), where n is the number of stored tuples, and the whole operation costs O(n²) processor time. With millions of tuples that is no longer negligible next to the disk time, which breaks the "only I/O matters" assumption.
  • With a hash table with many buckets (or a balanced search tree, O(log n)), each check is O(1) on average, and the whole operation is about linear. The structure needs a little extra space (bucket array, pointers), which we ignore.

Requirement: one copy of each distinct tuple must fit in M − 1 buffers: B(δ(R)) ≤ M − 1, simplified to B(δ(R)) < M. Disk I/O: B(R).

What if B(δ(R)) > M? The distinct tuples do not fit, so stored tuples must be moved out to disk and back as they are needed for checking. This is thrashing, and it raises the I/O cost sharply. The trouble is that B(δ(R)) is not known until δ(R) has been computed, so the optimizer must estimate it; an underestimate is expensive. Lecture 08's two-pass algorithms avoid the problem.

5. One-pass grouping γL(R) (slides 43–44)

A grouping operation γL has zero or more grouping attributes and one or more aggregated attributes. The algorithm creates one entry per group in main memory (one per value of the grouping attributes), then scans R one block at a time. For each tuple it finds its group's entry and updates the accumulated values:

AggregateKept in the group's entryUpdate per tuple
MIN(a), MAX(a)smallest / largest a seen so farreplace it if the new a is smaller / larger
COUNT(a)a counteradd one
SUM(a)a running sumadd the value of a (skip NULLs)
AVG(a)two accumulations: SUM(a) and COUNT(a)update both; at the end output SUM/COUNT

Result generation (slide 44): only when all tuples of R have been read can the output be produced: one tuple per group, from the entries in memory. (So γ is a blocking operator, Chapter 5.)

Requirements: an efficient structure to find a tuple's group entry, keyed on the grouping attributes only: a hash table or a balanced tree. Disk I/Os: B(R), as for any one-pass unary algorithm.

Memory: slide 44 states the requirement as "δ(R) < M: size of R with unique rows should fit in M − 1 buffers". More precisely (textbook §15.2.2), what must fit is the set of group entries, one per group, so the real condition is that the number of groups times the entry size fits in M − 1 buffers. That is not tied to B(R) in a simple way: there may be far fewer groups than tuples (then even a huge R works), and an entry may be shorter or longer than a tuple. "B(R) ≤ M" is only a safe rough rule.

BUET QBank · CSE 303 | L-3/T-1 | 2012–13 · 20 marks

Write the steps of performing a one-pass algorithm for finding the maximum value of an attribute for relation R. If the buffer size is M, what is the relationship between R and M? Derive the relationship between M and R for a two-pass aggregate operation.

Show worked answer

One-pass MAX(a) over the whole of R (a γ with no grouping attributes, so exactly one group):

  1. Set max := −∞ (or "no value yet"). This single entry is all the memory state.
  2. Read R one block at a time into one input buffer.
  3. For each tuple t in the block: if t.a is not NULL and t.a > max, set max := t.a.
  4. When the last block has been processed, output max.

Relationship between R and M: only one buffer (for the current block) plus one value is needed, so M ≥ 1 suffices for any B(R); the cost is B(R) disk I/Os. (If the question means MAX per group, γg, MAX(a)(R), the one-pass algorithm keeps one (g, max) entry per group, and the requirement is that all group entries fit in M − 1 buffers; the rough rule is B(R) ≤ M.)

Two-pass aggregation (sort-based, Lec 08, Ch. 3): phase 1 reads M blocks at a time, sorts them on the grouping attributes and writes a sorted sublist, giving ⌈B(R)/M⌉ sublists. Phase 2 needs one input buffer per sublist and one output buffer, so

⌈B(R)/M⌉ ≤ M − 1  ⟹  B(R) ≤ M(M − 1) ≈ M²  ⟹  M ≥ √B(R)

The hash-based version gives the same bound: phase 1 makes M − 1 buckets of about B(R)/(M − 1) blocks, and phase 2 needs each bucket's group entries to fit in M buffers, so B(R)/(M − 1) ≤ M, again B(R) ≤ M(M − 1) ≈ M². Either way the cost is 3B(R) I/Os. For example, with M = 101 a two-pass aggregate handles up to 101 × 100 = 10,100 blocks, against 100 for one pass.

Summary: one-pass algorithms read each block once and usually need one argument in memory; two-pass algorithms read, write and reread; many-pass ones need three or more passes. σ and π are tuple-at-a-time: M ≥ 1, cost B (T if unclustered via an index, less than B with an index seek). δ keeps one copy of each distinct tuple in M − 1 buffers with a hash table: cost B, needs B(δ(R)) < M, thrashes otherwise. γ keeps one entry per group (MIN, MAX, COUNT, SUM, or SUM and COUNT for AVG), outputs only at the end, costs B, and needs the group entries to fit in memory.
