Scanning: Table Scan, Index Scan, Index Seek and Sort Scan

The most basic physical operators bring a relation's tuples into memory. This chapter defines each scan the slides name, works through every slide example block by block, and explains when each one wins.

1. What scanning is (slide 19)

Scanning
Reading the contents of a relation R into main memory so that some operator (or the user) can use its tuples.
Full table scan
Read all blocks of R.
Predicate-based scan
Read only those tuples (ideally, only those blocks) of R that satisfy a given predicate, such as eid = 101.

The slides name four ways to do this: table-scan, index-scan, clustered-index-scan and index-seek. The textbook (§15.1.1) uses only two names, table-scan and index-scan, and lets "index-scan" cover both reading a whole index and using it to find particular values. The slides' finer split follows SQL Server's vocabulary, where "Index Scan" reads the leaf level and "Index Seek" descends the tree.

2. Table scan (slides 20–21)

Table-scan
R is stored in a set of disk blocks; the DBMS knows which blocks belong to R from its storage metadata (Chapter 2). It reads those blocks sequentially, one after another, and examines every tuple in them. Table scans are usually performed on heap-organized tables.

Examples (slide 21). SELECT * FROM R: read all blocks of R one by one. SELECT * FROM R WHERE eid = 101: still read all blocks of R one by one, and keep only the rows with eid = 101. Without an index, the DBMS cannot know where eid 101 is, so a predicate does not reduce the blocks read.

When the optimizer chooses a table scan:

  • When all or most rows must be returned (SELECT * FROM R).
  • When no useful index exists for the selection predicate.
  • When the predicate matches a large fraction of the table. Then following an index entry per matching row could read more blocks than simply reading the table once (see Example C below).

3. Index scan (slides 22–23)

Index-scan
An index exists on attribute A of R. An index scan reads the index leaf nodes directly, starting from the first leaf and following the leaf links. It does not descend from the root to find a particular row. It reads index blocks, not data blocks, and may read all index entries or a large part of them. If columns not in the index are needed, it then follows each entry's row pointer to the data block.
Covering index
(Standard term, not on the slide.) An index that contains every column a query needs, so the query can be answered from the index alone. The first example below uses a covering index.

Examples (slide 23), with a B+ tree index on manager_id:

  • SELECT manager_id FROM R: read all index leaf nodes to get every manager_id, and return them. No need to read the table at all. The index is much smaller than the table, so this is cheaper than a table scan.
  • SELECT manager_id, emp_name FROM R: read all the leaves for the manager_ids, and for each one follow the record pointer to the table block to get emp_name. This may not be efficient: with a non-clustered index, consecutive entries point to unrelated blocks, so the same table block can be fetched many times. A direct table scan is usually better.

4. Clustered-index scan (slide 24)

Clustered-index-scan
R is organized by a clustered index on A, so the leaves hold the rows themselves. The scan reads the leaf nodes directly (no root-to-leaf traversal), covering all or a large part of the index, and the rows come with it. It does not use the tree to locate a particular row.

A clustered-index scan is effectively the table scan of a clustered table: the leaf pages are the table's data pages. It reads every data block once and, as a bonus, returns the rows sorted on A.

5. Index seek (slides 25–26)

Index-seek
The DBMS uses the B+ tree to locate the needed entries: it starts at the root, follows the key-range pointers down through the internal nodes, and reaches the leaf that holds the target entry and its row pointer. Root-to-leaf traversal is required. If needed, it then follows the row pointer to the table block.

Examples (slide 26), index on manager_id:

  • SELECT manager_id FROM employee WHERE manager_id BETWEEN 101 AND 110: traverse the index to the first entry ≥ 101, read entries until one exceeds 110, return them. No table block is needed.
  • SELECT eid FROM employee WHERE manager_id BETWEEN 101 AND 110: the same seek, but eid is not in the index, so for each matching entry the DBMS visits the table block to get the row.

6. All the scans on one small table

The animation runs every slide example on one heap table of 12 employees in 4 blocks (3 rows per block), with a non-clustered B+ tree on manager_id whose 12 entries fill 3 leaves. The counter is the number of blocks read, which is what the next chapter uses as the cost.

7. Sorting while scanning (slides 27–28)

Why would a scan sort its output? Two reasons (slide 27, textbook §15.1.2):

  • The query has an ORDER BY clause, so the final output must be sorted.
  • Some algorithms for relational-algebra operations need one or both arguments sorted. These are the sort-based algorithms of Lecture 08 (sort-based duplicate elimination, grouping, union, join).
Sort-scan
A physical operator that takes a relation R and a list of attributes, and produces R's tuples sorted on those attributes.

Slide 28 lists how sort-scan can be implemented, from cheapest to most expensive:

  1. R is stored as a clustered index on A: an index scan (clustered-index scan) already produces R sorted on A.
  2. R must be sorted on A and there is a B+ tree index on A: an index scan of the leaves, plus a table-block access per entry, produces R in sorted order (possibly with many random block reads, as in Example C).
  3. R fits in main memory: retrieve its tuples with a table scan or index scan, then sort them with any main-memory sorting algorithm (quicksort, heapsort).
  4. R is too large for main memory: use the external multiway merge-sort (TPMMS), taught in Lecture 08, Chapter 2.

No question-bank question asks about the scan types alone. The cost of each scan is examined in Chapter 4; the bank question about using two secondary indexes for an OR condition is answered in Lecture 08, Chapter 7.

Summary: a table scan reads every block of R in sequence (the default for heaps, for no useful index, and for unselective predicates). An index scan reads the index leaves from the first leaf on, without descending the tree, and answers the query from the index alone when it covers the needed columns; otherwise it fetches a table block per entry, which can be worse than a table scan. A clustered-index scan reads the data pages of a clustered table and returns them sorted. An index seek descends from the root to the first matching entry. Sort-scan returns R sorted: free with a clustered index, by index scan with a B+ tree, by in-memory sort if R fits, and by external merge sort otherwise.
