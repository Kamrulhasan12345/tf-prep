The Query Processor: From SQL to a Physical Plan

What happens between typing an SQL query and getting rows back: parsing, query rewrite, and physical plan generation, plus the metadata the optimizer uses to pick a plan. This chapter sets up the vocabulary for the whole of Lectures 07 and 08.

1. What the query processor does (slide 2)

SQL is a declarative language: a query says what rows you want, never how to find them. Something inside the DBMS has to turn that request into a concrete sequence of disk reads, comparisons and copies. That component is the query processor.

Query processor
The part of the DBMS that (1) converts a high-level SQL query into a sequence of low-level database operations, and (2) chooses and runs an efficient algorithm for each of those operations.
Query compilation
The first major part: turning the SQL text into a physical query plan. It has three steps: parsing → query rewrite → physical plan generation.
Query execution
The second major part: running the physical plan's algorithms on the stored data and producing the answer.

The slide's schematic is SQL → compiler → physical plan → executor. The figure (from the textbook, Fig. 15.2) shows the three compilation steps and the tree each one hands to the next. The two middle steps, choosing a logical plan and choosing a physical plan, are together called query optimization, because both try to make the query cheaper.

2. Parsing (slide 3)

Parsing
Checking the syntax (is this legal SQL?) and the semantics (do the named tables and columns exist, are the types compatible?) of the query, and building a parse tree.
Parse tree (syntax tree)
A tree whose shape follows the SQL grammar: the root is the whole statement, its children are the clauses, and the leaves are names and constants.

The slide's example is SELECT title FROM ParamountMovies WHERE year = 1979;. Its parse tree has a SELECT-statement root with three children, one per clause. The WHERE clause holds a condition node, which splits into year, = and 1979.

3. Query rewrite (slide 4)

Logical query plan
A relational-algebra (RA) expression for the query, usually drawn as a tree (an RA tree): leaves are stored relations, inner nodes are RA operators (σ, π, ⋈, ×, ∪, …). It says which operations to do, but not which algorithm to use for each.
Query rewrite
Translating the parse tree into an initial logical plan, then improving it with algebraic equivalences (laws such as "a selection with an AND can be split into two selections"). The result computes the same answer, more cheaply.

The slide's example starts from πB,D(σR.A="c" ∧ R.C=S.C(R × S)) and splits the selection into σR.C=S.C(σR.A="c"(R × S)). Splitting is only the first step. The reason to split is that each piece can then move to where it is cheapest. The animation finishes the rewrite and reaches the "best logical plan" that slide 5 starts from.

4. Physical plan generation (slides 5–6)

Physical query plan
A logical plan in which every operator has been given a concrete algorithm (for example hash join instead of nested-loop join), every relation has an access method (table scan or index scan), and any needed sorting is made explicit.
Physical operator
A piece of code that implements one step of a physical plan, such as Table scan, Index scan, Sort, Hash join or Nested-loop join.

Slide 5 turns the best logical plan πB,D(σR.A="c"(R) ⋈ S) into a physical plan. The selection on R becomes an index scan (there is presumably an index on R.A, so only rows with A = "c" are read), S is read by a table scan, the natural join becomes a hash join, and π becomes a Project operator.

Slide 6 explains how the choice is made. A single logical plan usually has many candidate physical plans P1, P2, …, Pn (hash join or nested-loop join? index scan or table scan? which relation first?). The optimizer estimates the cost C1, C2, …, Cn of each candidate and picks the minimum. This is called cost-based optimization. Chapters 4 to 7 and all of Lecture 08 are about how those costs are computed.

Logical plan versus physical plan (slide 7)

Slide 7 gives a second example. The logical plan is "select the rows with salary > 5000, then project the name". A possible physical plan is: use an index scan on the table, apply the selection predicate salary > 50000 to each row, then apply the projection to keep only name. The same logical plan could also be run with a table scan; deciding between those is exactly physical plan generation.

Two small slide slips: the logical plan writes the constant as 5000 and the physical plan as 50000; they should be the same number. The relation is called department, although a salary column belongs more naturally to an employee or instructor relation. Neither affects the idea.

5. Metadata the optimizer needs (slides 8–11)

To estimate the cost of a plan without running it, the optimizer reads statistics that the DBMS keeps in its catalog (data dictionary). The slides list four kinds.

MetadataWhat it isHow the optimizer uses it
Size of each relation (slide 8)Number of rows (tuples), and number of disk blocks.Estimates how long a scan or join takes. A small table can simply be scanned; a large one may call for an index or a different join order.
Value statistics (slide 9)Approximate number of distinct values and how often values occur, kept as histograms or summaries.Estimates the selectivity of a condition such as WHERE age > 40: the fraction of rows that match.
Existing indexes (slide 10)Which columns have B+ tree or hash indexes.An index can speed retrieval a lot, but only if it exists and using it is cheaper than scanning the whole table.
Data layout on disk (slide 11)Row-wise or columnar storage, clustering of rows, block size.Sequential reads are faster than random reads, and well-clustered data needs fewer block reads.
Selectivity
The fraction of a relation's rows that satisfy a condition. The slides use "high selectivity" to mean few matches (the condition is very selective): then an index is likely worth using. "Low selectivity" means many matches: then reading the whole table by a scan is usually cheaper than following an index pointer for each row.
Histogram
A summary of a column's value distribution: the value range is split into buckets, and the catalog stores how many rows fall into each bucket.

The textbook's own short list of such statistics, B(R), T(R) and V(R, a), is defined in Chapter 4 of this lecture; it is the notation used in every cost formula.

6. Physical query plan operators (slide 12)

The last slide of this part pairs the two vocabularies:

  • Logical operations are the relational-algebra operations: selection, projection, join, union, intersection, difference, and so on.
  • Physical operators implement those logical operations in the plan: table scan, index scan, sort, hash, nested-loop join, hash join, sort-merge join, and others.

Some physical operators implement no RA operation at all. A scan just brings a relation's tuples into memory so that another operator can use them, and a sort puts them in order. The textbook (§15.1) points this out: physical plans need these extra building blocks.

BUET QBank · CSE 303 | L-3/T-1 | 2012–13 · 10 marks

Discuss the subsystems that are related to query processing in a Database Management System (DBMS).

Show worked answer

A query passes through these subsystems, in order:

  1. Parser and translator. Checks syntax and semantics (using the catalog to confirm that tables and columns exist) and builds a parse tree, then translates it into an initial relational-algebra expression (the logical query plan).
  2. Query rewriter (logical optimizer). Applies algebraic equivalences to the logical plan: splits conjunctive selections, pushes selections and projections down, turns σ over × into joins, and so on. The output is a better logical plan.
  3. Physical plan generator (cost-based optimizer). For the logical plan it enumerates candidate physical plans (choice of join algorithm, scan type, join order, where to sort), estimates the cost of each in disk I/Os, and picks the cheapest.
  4. Catalog / statistics manager. Supplies the metadata used by steps 1–3: relation sizes B(R) and T(R), distinct-value counts V(R, a) and histograms, which indexes exist, and how data is laid out.
  5. Execution engine. Runs the physical plan. Operators are usually implemented as iterators (Open, GetNext, Close), so results can be pipelined from one operator to the next instead of being written to disk (Chapter 5).
  6. Buffer manager and storage manager. The execution engine asks for blocks; the buffer manager keeps up to M buffers of them in memory and reads or writes disk blocks through the storage manager. Every disk I/O counted in our cost formulas happens here.

Summary: the query processor compiles SQL into a physical plan and then executes it. Compilation is parsing (syntax and semantic check, parse tree), query rewrite (RA tree improved by algebraic laws), and physical plan generation (choose an algorithm and access method for every node, estimate costs, keep the cheapest). The cost estimates rely on catalog metadata: relation sizes, value statistics, indexes and data layout.
