How Tables Are Stored: Heaps, Clustered and Non-clustered Indexes

Before we can say what a scan costs, we need to know how a table sits on disk. This chapter covers heap tables, clustered indexes (where the index is the table), B+ tree and hash indexes, and non-clustered indexes, and answers the slide's question: if a hash index finds a key in O(1), why do databases use B+ trees?

1. Heap tables (slides 13–14)

Heap (heap-organized table)
A table whose rows are stored in no particular key order. Blocks (pages) are allocated to the table only when they are needed, and a new row may go into any page that has enough free space.
RID (row identifier)
The pair (page number, slot number) that locates a row in a heap. Because rows are found through a page's slot array (the slotted-page layout of Lec 14), the RID stays valid even if the row moves inside its page.

The DBMS must remember which blocks belong to a heap, since they need not be contiguous. It keeps this in metadata. The slide gives two real systems:

  • SQL Server: Table/Index → Allocation Unit → Extent → Pages (blocks).
  • Oracle: Segment → Extent → Blocks. For example, the EMPLOYEE table might be segment #123 with extent 1 = blocks 1000–1063, extent 2 = blocks 2000–2063, extent 3 = blocks 3000–3127.

An extent is a run of consecutive blocks allocated in one go, so that a scan can read many neighbouring blocks cheaply even though the table as a whole is scattered.

Slide 14's figure shows a heap of three pages. Each page has a header (free space and so on), a slot array, and the row records (eid, dept_id). The eids are in no order: page 1 holds 105, 101, 109. 2. Clustered index (slide 15)

Clustered index
An index organization in which the table's rows are stored physically in sorted order of the index column. Usually the leaf nodes of the B+ tree contain the table rows themselves, not pointers to them. There is no separate storage for the table: the index is the table.

Three consequences follow directly from the definition:

  1. Only one clustered index per table, because the rows can be physically ordered in only one way.
  2. It is usually built on the primary key (the last line of slide 15).
  3. It is efficient for range queries and ordered scans: rows with keys 110 to 125 sit next to each other in consecutive leaf pages, and reading the leaves left to right returns the whole table in key order.

3. B+ tree index (slide 16)

Lec 15 covered B+ trees in detail. The slide's summary: a balanced tree with several levels; internal nodes hold key ranges and pointers to children; leaf nodes hold the indexed values with pointers to the table rows (R1, R2, …), and the leaves are linked in a list. Two properties matter for query execution:

  • Efficient for range search. Find the first key of the range by going root to leaf, then follow the leaf links.
  • Preserves the order of tuples when all tuples are retrieved through the index: reading the leaves left to right gives the keys in sorted order.

The slide's picture has leaves [3, 8, 12], [17, 21, 29], [35, 40, 48], [52, 61, 70] under internal nodes [8, 29] and [40, 61]; those internal keys do not separate the leaves correctly (for example, 8 and 12 sit left of the key 8). A consistent tree for the same leaves is drawn in the animation in Section 6.

4. Hash index (slide 17)

Hash index
An array of buckets (a hash table on disk). A hash function h maps each search key to a bucket, and each bucket holds (key, row pointer) entries. When a bucket fills, extra entries go to an overflow bucket chained to it (a collision).

In the slide's picture, keys 205 and 530 hash to bucket 0, which is full, so 412 (also hashed to bucket 0) goes to an overflow bucket; 101 is in bucket 1 and 317 in bucket 2. A hash index is efficient for equality search (compute h(key), read one bucket) but does not preserve order: neighbouring keys land in unrelated buckets, so reading the buckets in turn returns tuples in a scrambled order.

5. Non-clustered index (slide 18)

Non-clustered index
Any index other than the clustered one. A table may be organized by a clustered index on one attribute and have one or more indexes on other columns; all of those are non-clustered. Their leaves hold the key plus a row locator, and the rows themselves are stored elsewhere, in a different order.

In slide 18's figure the table is clustered on CustomerID, and a non-clustered B+ tree on LastName has leaf entries such as Ahmed → 105 and Baker → 110. When the table has a clustered index, the non-clustered index typically stores the clustered key (here the CustomerID) as the row locator. To fetch a row by last name, the DBMS looks up LastName in the non-clustered index, gets CustomerID 105, then searches the clustered index for 105. In a heap table the locator is the RID instead.

6. Why use a B+ tree when hashing is O(1)? (slide 18)

Slide question (worked answer): "If hash index gives O(1) search, why is B+ tree used?"

Because many searches are range queries, such as deptid > 10 or deptid BETWEEN 10 AND 20, and hashing is bad at range search.

  • A hash function deliberately scatters keys, so the keys 10, 11, …, 20 are spread over unrelated buckets. To answer a range query from a hash index you would have to hash every possible value in the range (impossible for real-valued or string keys) or read every bucket, which is a full scan.
  • A B+ tree keeps keys sorted. The DBMS descends once to the first key ≥ 10 (a few block reads, the tree height), then walks the linked leaves until it passes 20. The cost is the height plus the number of leaf blocks that actually hold matching keys.
  • The B+ tree also returns tuples in key order, which helps ORDER BY and the sort-based algorithms of Lecture 08. For equality search alone a B+ tree costs only a few more reads than hashing (height 3 or 4 with the root cached), so it is the better general-purpose choice.

Summary: a heap stores rows in no order, in pages allocated on demand and tracked by metadata; rows are located by RID = (page, slot). A clustered index stores the rows themselves in its leaves, sorted by the key: one per table, usually on the primary key, ideal for ranges. Other indexes are non-clustered and point to rows by RID or by clustered key. Hash indexes are fastest for equality but useless for ranges and scramble order, which is why B+ trees are the default.
