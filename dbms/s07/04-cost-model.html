Measuring Cost: Disk I/Os and the Parameters M, B, T, V

Every algorithm in Lectures 07 and 08 is judged by one number: how many disk blocks it reads and writes. This chapter states the cost model and its assumptions, defines the parameters every formula uses, and derives the cost of each scan from Chapter 3.

1. The computation model (slide 29)

The slides make two assumptions and choose one cost measure. Both come from the textbook, §15.1.3.

  • Assumption 1: the arguments of a physical operator are on disk. Reading them costs disk I/Os.
  • Assumption 2: the final result is left in main memory, or is pipelined to the next operator. Writing the result is not charged to the operator.
  • Measure of cost: the number of disk I/Os (block reads plus block writes). The slide calls it the primary cost.

Slide 29 question (worked answer): why does disk I/O measure the cost?

Getting data from disk takes far longer than doing anything useful with it once it is in memory. A disk block read costs milliseconds (seek plus rotational latency, Lec 13), while comparing or copying the tuples of a block in memory takes microseconds. So the number of block transfers dominates the running time, and an algorithm that does fewer I/Os is faster, almost regardless of its CPU work. (This assumes the in-memory work is close to linear; Chapter 6 shows a case, naive duplicate checking, where it is not.)

Slide 29 question (worked answer): "Final result is left in main memory or pipelines; this doesn't matter for cost calculation. Why?"

We use the cost to compare algorithms for the same operation. Whatever algorithm computes the result, the result itself is the same set of tuples, so writing it to disk would cost the same number of blocks for every algorithm. Adding that constant changes no comparison. Moreover, often the result is never written at all:

  • If the operator produces the final answer, it is usually sent to the user or an application (printed, displayed), so its disk cost is zero or depends on something outside the DBMS.
  • If the operator is inside a plan, its result is usually pipelined into the parent operator a tuple (or block) at a time (Chapter 5), so it is never written and never re-read.

When a query really does store its result, we simply add the size of the result in blocks at the end. That is why TPMMS costs "3B, or 4B if the sorted result must be stored on disk" in Lecture 08.

2. The parameters (slides 30–31)

M (main-memory cost metric)
Main memory available for query processing is divided into buffers, each the size of one disk block. M is the number of buffers available to one operator. It may be much less than the whole memory, since several operators can share memory at once.
Block (page)
The unit of transfer between disk and main memory. All counts are in blocks, never in bytes or tuples.
B(R)
The number of disk blocks occupied by relation R. Written B when R is clear from the context.
T(R)
The number of tuples in R. Written T when R is clear. The number of tuples that fit in one block is the ratio T(R)/B(R). (Slide 31 writes this as "T(B)", which is not standard notation; the textbook uses T/B.)
V(R, a)
The number of distinct values of attribute a in R. More generally V(R, [a1, …, an]) is the number of distinct combinations, that is, the number of tuples in δ(πa1,…,an(R)).

Clustered and unclustered relations

Clustered relation
(Textbook §15.1.4.) A relation whose tuples are packed into about B(R) blocks that hold only R's tuples. Reading all of R then costs about B(R) I/Os.
Unclustered relation
A relation whose tuples are scattered among blocks holding tuples of other relations. Reading all of R can then cost one I/O per tuple, that is, about T(R) I/Os.

Slide 32 states the default: we assume all relations are clustered (stored as a clustered index) unless stated otherwise. Any relation an operator produces can also be assumed clustered, since there is no reason to store a temporary result in a scattered way.

The non-clustered index scan, carefully

Slide 33 reasons: read the index first (B(I) blocks); then, for each row pointer, read the corresponding data block, assuming one block read per row. That is T block reads for the rows, so the total is B(I) + T(R), and since the index is much smaller than the relation (B(I) ≪ B(R) ≤ T(R)), it is about T(R).

Slide slip: the slide's formula line reads "Total = B(R) + B(I) = B(R)", which contradicts its own previous line ("T blocks read for rows"). With one block read per row the data part is T, not B. B(R) + B(I) is the cost when the index is clustered (consecutive entries point into the same block, so each data block is read once). Slide 40 in Chapter 6 uses the correct value: "T(R) if R is not clustered index and index-scan is used [very expensive]".

The conclusion of slide 33: a non-clustered index scan is not useful when all of R is required, but it is useful when only part of R is required, because then only the relevant blocks are retrieved (the index seek of Chapter 3).

Summary: cost = number of disk block I/Os; arguments start on disk and the result is not charged, because writing it costs the same for every algorithm. M = buffers available, B(R) = blocks, T(R) = tuples, T/B = tuples per block, V(R, a) = distinct values. Relations are assumed clustered. Table scan and clustered-index scan cost B; a non-clustered index scan of all of R costs B(I) + T ≈ T; sort-scan costs B with a clustered index or if R fits in memory, and more otherwise.
