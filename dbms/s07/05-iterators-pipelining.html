Iterators and Pipelining

Slide 29 says an operator's result is "left in main memory or pipelines". This chapter explains what that means: physical operators are built as iterators with Open, GetNext and Close, so tuples can flow up a plan one at a time without ever being written to disk. It includes an interactive animation of a join over two scans, and answers the two question-bank questions on materialization and pipelining.

Scope note: iterators are textbook §15.1.6, which the syllabus list skips and the slides only mention in passing. They are taught here because the exams ask about pipelining, and because they explain why output writes are not counted.

1. Two ways to evaluate a plan

Materialization
Evaluate the plan bottom-up, one operator at a time. Each operator computes its entire result and stores it (usually on disk, as a temporary relation) before its parent starts. The parent then reads that temporary relation as its input.
Pipelining
Run many operators at once. As soon as a child produces a tuple, the tuple is passed in memory to the parent, which can use it immediately. Intermediate results are never stored as a whole, so their write and re-read costs disappear.
Blocking operator
An operator that cannot produce its first output tuple until it has read all of its input (textbook Exercise 15.2.2). Sorting and grouping (γ) are blocking. A blocking operator breaks the pipeline: everything below it must finish before anything above it receives a tuple.

2. The iterator interface (book §15.1.6)

Iterator
A group of three methods that lets the consumer of an operator's result get the result one tuple at a time:
  1. Open() starts the process of getting tuples but does not get one. It initializes data structures and calls Open() on the operator's arguments (its children).
  2. GetNext() returns the next tuple of the result and updates the state so the following tuple can be found. It usually calls GetNext() on its children one or more times. When there are no more tuples it returns a special value NotFound.
  3. Close() ends the iteration, usually by calling Close() on the children.

Example 15.1: a table-scan iterator. It keeps a block pointer b and a tuple pointer t.

Open() {
    b := the first block of R;
    t := the first tuple of block b;
}
GetNext() {
    IF (t is past the last tuple on block b) {
        increment b to the next block;
        IF (there is no next block) RETURN NotFound;
        ELSE t := first tuple on block b;      /* b is a new block */
    }
    oldt := t;
    increment t to the next tuple of b;
    RETURN oldt;
}
Close() { }

Notice that each block of R is read once, when GetNext first steps into it: the scan costs B(R) I/Os no matter how slowly the consumer asks for tuples.

Example 15.2: sort-scan as an iterator does most of its work in Open(). The first tuple in sorted order could be the last tuple of R, so Open() must read all of R (here assumed to fit in memory) and sort it; GetNext() then just returns the tuples one by one. That is a blocking operator expressed as an iterator: the iterator interface still works, but nothing flows until Open() has finished.

Example 15.3: bag union R ∪B S built from the iterators of R and S, using a variable CurRel that says which input is being read:

Open()   { R.Open(); CurRel := R; }
GetNext() {
    IF (CurRel = R) {
        t := R.GetNext();
        IF (t <> NotFound) RETURN t;      /* R is not exhausted */
        ELSE { S.Open(); CurRel := S; }    /* R is exhausted */
    }
    RETURN S.GetNext();    /* NotFound when S is exhausted too: correct for us */
}
Close()  { R.Close(); S.Close(); }

Bag union needs only one buffer and never stores anything: it is perfectly pipelined.

3. A join iterator over two scans (book §15.3.2)

The tuple-based nested-loop join R(X, Y) ⋈ S(Y, Z) (Lecture 08, Chapter 1) also fits the iterator framework (textbook Fig. 15.7). S is the outer loop and R the inner loop; when R is exhausted for the current s, the join closes R, gets the next s, and reopens R.

Open()  { R.Open(); S.Open(); s := S.GetNext(); }
GetNext() {
    REPEAT {
        r := R.GetNext();
        IF (r = NotFound) {          /* R is exhausted for the current s */
            R.Close(); s := S.GetNext();
            IF (s = NotFound) RETURN NotFound;   /* both are exhausted */
            R.Open(); r := R.GetNext();
        }
    } UNTIL (r and s join);
    RETURN the join of r and s;
}
Close() { R.Close(); S.Close(); }

Interactive animation. Type your own small relations (up to 4 tuples each; the join attribute is B, the second value of an R tuple and the first value of an S tuple) and step through every call. Watch the first output reach the consumer long before R and S have been read completely: that is pipelining.

4. Which operators pipeline well?

Operator (one-pass algorithm)Can output flow before all input is read?
σ, π, bag unionYes, fully pipelined: each input tuple is handled and passed on at once.
δ (duplicate elimination)Yes: the first copy of a tuple is output as soon as it is seen (Chapter 6).
γ (grouping, aggregation)No, blocking: a group's SUM or COUNT is unknown until the last tuple has been read.
Set ∪, ∩, R − S, ⋈, × (S in memory)Partly: S must be read completely first, then output flows while R is streamed.
S − R (S in memory)No: S's surviving tuples are known only after all of R is read.
Sort, and every two-pass (sort- or hash-based) algorithmNo for the first pass: all input must be partitioned or sorted into sublists before the second pass outputs anything. The second pass's output can then be pipelined.

DB QB · 19-20 3b · 15 marks  |  BUET QBank · CSE 215 | L-2/T-2 | 2019–20 · 20 marks

The following relations are given:
Student (id, name, CGPA, street, city)
takes (id, course-id, semester, year)
course (course-id, title, credit)

SELECT id, name, course-id, title
FROM student s, takes t, course c
WHERE s.id = t.id AND t.course-id = c.course-id
  AND s.city = 'Dhaka' AND c.credit = 3

i. Construct an expression tree for the given SQL.
ii. Explain materialization evaluation and pipeline evaluation using the expression tree.

Show worked answer

(i) Push each single-relation selection down to its relation and turn each equality between relations into a join:

πid, name, course-id, title((σcity='Dhaka'(student) ⋈s.id=t.id takes) ⋈t.course-id=c.course-id σcredit=3(course))

(ii) Materialization. Evaluate one node at a time, from the leaves up, storing each result as a temporary relation on disk:

  1. ① Temp1 = σcity='Dhaka'(student); Temp2 = σcredit=3(course). Each reads its base relation and writes its result.
  2. ② Temp3 = Temp1 ⋈ takes: read Temp1 and takes, write Temp3.
  3. ③ Temp4 = Temp3 ⋈ Temp2: read Temp3 and Temp2, write Temp4.
  4. ④ Read Temp4, project, output.

Cost: the I/Os of every operator's algorithm plus, for every temporary relation, one write and one read of all its blocks. Advantage: simple, and works for every operator, including blocking ones. Disadvantage: the temporary writes and reads, and no output until the very end.

Pipelining. All operators are iterators running at the same time. The projection calls GetNext() on join ③, which calls GetNext() on join ②, which pulls tuples from σcity, which pulls tuples from a scan of student. Each student tuple from Dhaka is joined with its takes tuples, each result goes straight up to join ③, and every tuple surviving ③ is projected and output at once. No Temp1, Temp3 or Temp4 is ever written, which saves 2 × (their sizes in blocks) disk I/Os, and the first answer rows appear early. The limits: a join algorithm usually needs one input completely in memory first (σcredit=3(course) is read in full to build the hash table or search structure of join ③, the dashed "build side"), and a blocking operator such as sorting or γ would cut the pipeline into separate stages.

DB QB · 21-22 8a · 10 marks  |  BUET QBank · CSE 215 | L-2/T-2 | 2021–22 · 10 marks

Describe how aggregation and set operations of SQL query are processed and whether pipelining can improve their performance.

Show worked answer

Aggregation (GROUP BY with SUM, COUNT, AVG, MIN, MAX; the γ operator):

  • One pass (Chapter 6), when one entry per group fits in memory: read R a block at a time; for each tuple find its group's entry in a hash table or balanced tree (key = grouping attributes) and update it: MIN/MAX keep the extreme so far, COUNT adds 1, SUM adds the value, AVG keeps SUM and COUNT. Output one tuple per group at the end. Cost B(R).
  • Two pass, sort-based (Lec 08, Ch. 3): sort R into sublists on the grouping attributes, then merge them; tuples of one group meet consecutively, so each group is aggregated and output when the next key appears. Cost 3B(R), needs B(R) ≤ M².
  • Two pass, hash-based (Lec 08, Ch. 5): hash R on the grouping attributes into M − 1 buckets, then aggregate each bucket in one pass. Cost 3B(R), needs about B(R) ≤ M².

Set operations (UNION, INTERSECT, EXCEPT, set semantics):

  • One pass (Chapter 7): read the smaller relation S into M − 1 buffers with a search structure keyed on the whole tuple, then stream R and decide per tuple (∪: output S, then R-tuples not in S; ∩: R-tuples in S; R − S: R-tuples not in S). Cost B(R) + B(S), needs min(B(R), B(S)) ≤ M.
  • Two pass: sort both into sublists and merge them, handling all copies of the smallest tuple together; or hash both with the same function and run the one-pass algorithm per bucket pair. Cost 3(B(R) + B(S)).
  • UNION ALL (bag union) just copies R then S: cost B(R) + B(S), one buffer.

Can pipelining help? Yes, in two ways, but limited by blocking:

  • Input side: the input of γ or a set operation can always be pipelined from the operator below, through GetNext(). That avoids writing the child's result and reading it back: a saving of 2 × B(child result) I/Os.
  • Output side: it depends on the operator. γ is blocking: no group's aggregate is final until all input is read, so its output cannot start early (with sorted input it could output each group as soon as the key changes). Bag union is fully pipelined. Set union, intersection and R − S with S in memory output while R streams, after S has been read. S − R is blocking. Two-pass algorithms must finish their first pass (sublists or buckets) before any output, but the second pass can pipeline its output to the next operator.

So pipelining always saves the I/O of materializing the inputs, and saves output materialization except where the operator itself blocks.

Summary: materialization stores every intermediate result; pipelining passes tuples up the plan as they are produced. Operators are built as iterators: Open() initializes and opens the children, GetNext() returns one tuple or NotFound, Close() ends. Scans, σ, π, bag union and δ pipeline fully; joins and set operations pipeline after reading their in-memory argument; γ, sort and S − R are blocking. This is why our costs do not charge an operator for writing its output.
